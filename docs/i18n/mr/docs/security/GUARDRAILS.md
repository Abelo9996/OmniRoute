> **सत्याचा अधिकृत स्रोत:** `src/lib/guardrails/`
> **शेवटचे अद्यतन:** 2026-08-29 — v3.8.51 (Video Bridge प्रतिलेखाचा उगम कॉलरद्वारे घोषित केला जातो,
> अद्याप सर्व्हरद्वारे सत्यापित केलेला नाही — #11661 नुसार स्पष्टीकरण दिले)

Guardrails, OmniRoute आणि अपस्ट्रीम प्रदात्यांच्या सीमेवर सुरक्षितता, धोरणे आणि आशय रूपांतरे लागू करतात. प्रत्येक guardrail विनंती payloads (`preCall`) आणि अपस्ट्रीम प्रतिसाद (`postCall`) तपासू शकतो (आणि पर्यायाने नाकारू, रूपांतरित करू किंवा त्यांवर भाष्य नोंदवू शकतो).

प्रणाली **fail-open** आहे: एखाद्या guardrail च्या अंमलबजावणीदरम्यान अपवाद निर्माण झाल्यास, विनंती अयशस्वी करण्याऐवजी registry त्रुटीची नोंद करून पुढील guardrail वर प्रक्रिया सुरू ठेवते. अवरोधित करणे हा नेहमी स्पष्ट निर्णय (`block: true`) असतो, अपघाताने ते कधीही होत नाही.

(`registry.ts` → `registerDefaultGuardrails()` पहा):

### व्हिजन ब्रिज (`visionBridge.ts`) — मोडॅलिटी ब्रिज PR-1

**व्हिजन नसलेल्या मॉडेल्सना** उद्देशून केलेल्या, प्रतिमा असलेल्या विनंत्या अडवते आणि
एकतर संपूर्ण विनंती व्हिजन-सक्षम मॉडेलकडे पुनर्निर्देशित करते किंवा अपस्ट्रीम
कॉलपूर्वी प्रतिमांचे भाग कॉन्फिगर करता येणाऱ्या व्हिजन मॉडेलने तयार केलेल्या
मजकूर वर्णनांनी बदलते. यामुळे केवळ-मजकूर प्रदाते मल्टिमोडल पेलोड्स पारदर्शकपणे
हाताळू शकतात.

प्रवाह:

1. लक्ष्य मॉडेल आधीपासूनच व्हिजनला समर्थन देत असल्यास वगळा (जोपर्यंत ते
   सक्तीच्या-ब्रिज सूची `isVisionBridgeForcedModel` मध्ये दिसत नाही).
2. `extractImageParts(messages)` द्वारे प्रतिमेचे भाग एक्स्ट्रॅक्ट करा
   (`visionBridgeHelpers.ts`), जे `open-sse/utils/mediaParts.ts` मधील
   **एकीकृत मीडिया शोधक** `detectMediaParts()` कडे कार्य सोपवते — कॉम्बो
   सुसंगतता फिल्टरसोबत सामायिक केलेला सत्याचा एकमेव स्रोत.
   एक्स्ट्रॅक्शन फक्त `replaceImageParts` पुन्हा जोडू शकत असलेल्या आकारांच्या
   उच्च-स्तरीय भागांपुरते अनुमती-सूचीबद्ध आहे (एक्स्ट्रॅक्ट↔रिप्लेस करार): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, आणि Responses API `input_image`. नेस्टेड जुळण्या आणि
   केवळ-सूचक आकार हे कॉम्बो-फिल्टरसाठीचे घटक आहेत आणि ते कधीही एक्स्ट्रॅक्ट
   केले जात नाहीत. काहीही आढळले नाही तर वगळा.
3. `resolveVisionBridgeRuntimeSettings()` द्वारे रनटाइम कॉन्फिगचे निराकरण करा
   (`src/shared/constants/modalityBridgeDefaults.ts`): नवीन `modalityBridge*`
   सेटिंग्ज कीजना प्राधान्य मिळते; जुने `visionBridge*` कीज **एका-सायकलचा
   फॉलबॅक** (रोलबॅक विंडो) म्हणून कायम राहतात. ब्रिज अक्षम असल्यास कोणत्याही
   मीडिया ट्रॅव्हर्सलपूर्वी वगळा.
4. मोड निवडक (`modalityBridgeVisionMode`, खालील तक्ता पहा) पुनर्निर्देशन किंवा
   वर्णन यांपैकी काय करायचे ते ठरवतो. पुनर्निर्देशन फक्त `model` बदललेला
   `modifiedPayload`, तसेच `{ rerouted, fromModel, toModel, imagesKept }`
   मेटा परत करते.
5. वर्णन मार्ग: प्रतिमांची संख्या `maxImages` पर्यंत मर्यादित करा, कार्य-जागरूक
   प्रॉम्प्ट तयार करा, वर्णन कॅशे तपासा, व्हिजन मॉडेलला **समांतरपणे**
   (`Promise.allSettled`) कॉल करा आणि त्यांच्या जागी
   `[Image N]: <description>` मजकूर भाग इंजेक्ट करा. वर्णन अयशस्वी झाल्यास
   `null` मिळते आणि मूळ प्रतिमा भाग **जतन केला जातो** (#4012) — मात्र कॉम्बो
   वर्णन मार्गावर सर्व वर्णने अयशस्वी झाल्यास, पुष्टी झालेल्या नॉन-व्हिजन
   अपस्ट्रीमला त्याऐवजी
   `(अनुपलब्ध — कोणताही व्हिजन-सक्षम प्रदाता जोडलेला नाही)` स्टब मिळतो (#8430).
6. `modifiedPayload` + मेटा (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) परत करा.

#### मोड निवडक (`modalityBridgeVisionMode`)

| मोड        | डीफॉल्ट | वर्तन                                                                                                                                                                                                                                                                                                          |
| ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | जुने ह्युरिस्टिक, अपरिवर्तित (#6640/#7204): मूळ मॉडेलकडे आधीपासून वापरण्यायोग्य क्रेडेन्शियल्स नसल्यास नॉन-कॉम्बो/`auto/` मॉडेल्स सर्वोत्तम व्हिजन मॉडेलकडे पुनर्निर्देशित होतात (असल्यास वर्णन करतात); कॉम्बो लक्ष्य नेहमी वर्णन करतात.                                                                       |
| `describe` |         | नेहमी वर्णन करा — पुनर्निर्देशन ब्लॉक पूर्णपणे वगळला जातो; वापरकर्त्याने निवडलेले मॉडेल नेहमी उत्तर देते.                                                                                                                                                                                                      |
| `reroute`  |         | पुनर्निर्देशनाची सक्ती करा: क्रेडेन्शियल असलेले मॉडेल कायम ठेवणारा गार्ड बायपास केला जातो. पुनर्निर्देशन-**लक्ष्य** क्रेडेन्शियल गार्ड तरीही लागू राहतो — वापरण्यायोग्य व्हिजन लक्ष्य उपलब्ध नसल्यास, विनंती वर्णनाकडे पुढे जाते, जेणेकरून कच्च्या प्रतिमा केवळ-मजकूर बॅकएंडपर्यंत कधीही पोहोचत नाहीत (#8430). |

सक्तीचे मोड ऑटो ह्युरिस्टिक चालण्याच्या **आधीच** शॉर्ट-सर्किट होतात; `auto` चे
वर्तन PR-1 पूर्वीच्या सुरक्षा-नियंत्रणाशी बाइट-टू-बाइट समान आहे.

#### API-कीची व्याप्ती (`visionBridgeKeyScope.ts`)

कॉलरची API की `allowedConnections`, कोटा पूल्स (`allowedQuotas`) किंवा
मॉडेल्स (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) प्रतिबंधित करत
असल्यास, ब्रिज केवळ त्या कीला वापरता येणारी पुनर्निर्देशन आणि वर्णन मॉडेल्स,
तसेच त्या कीला वापरता येणाऱ्या कनेक्शन्सवरील मॉडेल्स निवडतो. त्यानंतर वर्णन
कॉल नेहमी `x-omniroute-self-loop-key-id` हेडरसह OmniRoute सेल्फ-लूपमधून
जातो, जेणेकरून प्राप्त होणारी चॅट विनंती त्या कीचे कनेक्शन आणि मॉडेल धोरण
पुन्हा लागू करेल. `enforceApiKeyPolicy()` त्या हेडरचा स्वीकार फक्त सेल्फ-लूप
बेअररसहच करते, त्यामुळे ते फक्त प्रवेश अधिक मर्यादित करू शकते आणि निराकरण न
होणारा id नाकारला जातो.

कीसाठी कोणतेही व्हिजन मॉडेल अनुमत नसल्यास, वर्णन मार्ग बाजूला होतो आणि
विनंती अपरिवर्तितपणे पुढे जाते; हे अक्षम सुरक्षा-नियंत्रणासारखेच फेल-ओपन
वर्तन आहे (मेटा `{ skipped: true, reason: "no_permitted_vision_model" }`).
की नसलेल्या विनंत्या आणि असे निर्बंध नसलेल्या कीज पूर्वीप्रमाणेच वागतात.

#### कार्य-जागरूक वर्णन प्रॉम्प्ट (`modalityBridgeVisionTaskAware`)

डीफॉल्ट **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) बेस
describe प्रॉम्प्टमध्ये **शेवटच्या वापरकर्ता संदेशाचा** मजकूर (500 वर्णांपर्यंत संक्षिप्त केलेला)
जोडते, ज्यामुळे वर्णन वापरकर्त्याने प्रत्यक्षात काय विचारले त्यानुसार निर्देशित होते
(codex-vision-proxy पॅटर्न) आणि vision मॉडेलला दृश्यमान मजकूर लिप्यंतरित करण्यास सांगितले
जाते. फ्लॅग बंद असल्यास — किंवा वापरकर्त्याचा मजकूर नसल्यास — बेस प्रॉम्प्ट कोणताही बदल न करता वापरला जातो.

describe self-loop ची स्वतःची OpenAI-सुसंगत विनंती (`callVisionModelSingle()`
`visionBridgeHelpers.ts` मध्ये) नेहमी `image_url.detail: "high"` ची विनंती करते —
बिनशर्त, प्रत्येक caller/provider साठी, कोणत्याही क्लायंट सिग्नलवर अवलंबून न राहता.
कमी तपशीलाचे sampling, या प्रॉम्प्टने मागितलेल्या text-transcription कार्यासाठी OCR ची
अचूकता कमी करते, म्हणून मूळ inbound विनंतीने कोणतीही detail level वापरली असली
तरीही describe कॉल स्वतः नेहमी उच्च तपशीलाची विनंती करतो. याचा परिणाम फक्त अंतर्गत
describe विनंतीच्या body वर होतो; प्राथमिक विनंतीवर OmniRoute caller चे स्वतःचे
`image_url.detail` कसे forward करते, हे यामुळे बदलत नाही — तो डीफॉल्ट स्वतंत्रपणे लागू
केला जातो आणि तोही फक्त शोधलेल्या OpenCode क्लायंटसाठी,
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) मध्ये. describe
self-loop च्या Anthropic wire-format शाखेत `detail` फील्ड नाही आणि या दोन्ही
डीफॉल्टपैकी कोणाचाही तिच्यावर परिणाम होत नाही.

#### Describe आउटपुट मर्यादा (`modalityBridgeVisionMaxChars`)

| Key                            | डीफॉल्ट | मर्यादा             |
| ------------------------------ | ------- | ------------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` किंवा 100–50000 |

`0` (डीफॉल्ट) म्हणजे **कोणतीही मर्यादा नाही** — `callVisionModel()` ने परत केलेले
वर्णन कोणताही बदल न करता पुढे पाठवले जाते, ज्यामुळे विद्यमान वर्तन कायम राहते.
100–50000 या मर्यादेतील कोणतेही मूल्य, वर्णन `[Image N]: <description>` म्हणून
पुन्हा जोडण्यापूर्वी त्याच्या शेवटी `…` प्रत्यय लावून ते संक्षिप्त करते
(`VisionBridgeGuardrail.preCall()` `src/lib/guardrails/visionBridge.ts` मध्ये).
तपशीलप्रधान OCR कार्यांसाठी, downstream मॉडेलला पूर्ण लिप्यंतरण आवश्यक असल्यास,
हे मूल्य वाढवा; अधिक बोलके vision मॉडेल वापरताना token वापर मर्यादित ठेवण्यासाठी
ते कमी करा. डॅशबोर्ड फील्ड Vision टॅबच्या Advanced पॅनेलवर आहे
(`modality-bridge-max-chars` `ModalityBridgeVisionTab.tsx` मध्ये) आणि स्पष्टपणे
दिलेल्या `0` ला न बदलता, 1 ते 99 मधील कोणतेही मूल्य किमान 100 पर्यंत वाढवते —
`0` हे केवळ "unset" डीफॉल्ट नसून स्वतःच एक वैध Zod मूल्य आहे
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`).

#### Describe कॅशे (`modalityBridge/bridgeCache.ts`)

describe आउटपुटसाठी in-memory LRU + TTL कॅशे, जी संपूर्ण process मध्ये सामायिक
केली जाते. Key = `sha256(imageRef + composedPrompt + configuredBridgeModel)`,
length-prefix framing सह (field-boundary collisions होत नाहीत). मॉडेल घटक म्हणजे
**कॉन्फिगर केलेले** bridge मॉडेल, प्रत्यक्षात उत्तर देणारे मॉडेल नव्हे —
`callVisionModel` अंतर्गत fallback वापरू शकते आणि प्रत्येक प्रयत्नानुसार key
ठेवल्यास कॅशेचे तुकडे होतील. अयशस्वी describe परिणाम कधीही कॅशे केले जात नाहीत.
सेटिंग्ज:

| Key                             | डीफॉल्ट | मर्यादा |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### Remote image normalization (self-loop describe/base64 fetch)

जेव्हा bridge स्वतः एखादी **remote** image fetch करते — Anthropic describe
self-call आणि claude-wire-format base64 conversion
(`ensureBase64ImagesForClaudeWire`), ही दोन्ही `visionBridgeHelpers.ts` मधील
`fetchRemoteImageAsDataUri()` द्वारे — तेव्हा परिणामी data URI, vision-model
विनंतीमध्ये embed करण्यापूर्वी `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) मधून पाठवला जातो. आकाराने अतिशय मोठ्या
images ची **2048px long edge** पर्यंत आकारकपात केली जाते (OpenAI/Anthropic आधीच
server-side लागू करत असलेल्या resize मर्यादेशी सुसंगत), ज्यामुळे vision मॉडेलला
दिसणाऱ्या गोष्टीत बदल न करता upload bytes/latency कमी होतात. Resizing साठी
dynamic import द्वारे लोड केलेले `sharp` वापरले जाते: ज्या platform वर त्याची
native binary लोड होऊ शकत नाही, तिथे `normalizeDataUri()` **कधीही throw करत
नाही** — ते मूळ bytes च्या passthrough वर fallback करते, त्यामुळे
describe/base64-conversion मार्ग नेहमी कार्यरत राहतो. Non-image bytes (decodable
image परत न करणारा fetch) देखील कोणताही बदल न करता पुढे पाठवले जातात. हे
normalization फक्त bridge ने स्वतःच्या self-call साठी fetch केलेल्या images पुरते
मर्यादित आहे — caller च्या raw passthrough payload वर ते कधीही लागू केले जात नाही,
जे opt-in-only mutation तत्त्वाशी सुसंगत आहे (Hard Rule #20).

#### सेटिंग्ज schema + migration

नवीन `modalityBridge*` keys, `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`) मध्ये Zod द्वारे validate केल्या
जातात: `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*` चे त्रिकूट आणि Audio Bridge द्वारे वापरला जाणारा

legacy `visionBridge*` मूल्ये जुळणाऱ्या नवीन keys मध्ये कॉपी करते (idempotent,

release cycle साठी legacy keys read fallback म्हणून स्वीकारल्या जात राहतात.

#### पारदर्शकता header + आकडेवारी

Describe द्वारे रूपांतरित responses मध्ये
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
असतो (`buildModalityBridgeHeader()` द्वारे `modalityBridge/bridgeStats.ts` मध्ये
तयार केलेला, `withModalityBridgeHeader()` द्वारे
`src/sse/handlers/chatHelpers.ts` मध्ये stamp केलेला).
Reroute केलेल्या विनंत्यांना **कोणताही** header मिळत नाही — payload मध्ये बदल
झालेला नसतो आणि model swap आधीच response body च्या `model` फील्डमध्ये दिसतो.

`GET /api/modality-bridge/stats` (`GET /api/settings` प्रमाणेच समान स्तराचे management auth) `vision`, `audio`, आणि `video` साठी इन-मेमरी, प्रति-मोडॅलिटी काउंटर
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` परत करते. `averageLatencyMs` त्याचा
भाजक म्हणून सर्व प्रयत्नांऐवजी `latencySamples` वापरते; वेळमापन नसलेले ऑपरेशन
शून्य-मिलिसेकंदाचा बनावट नमुना तयार करत नाही. यशस्वी रूपांतरणांसाठी `bridged`
हा मागील आवृत्त्यांशी सुसंगत alias राहतो; अयशस्वी प्रयत्नांमुळे तो वाढत नाही.
डिझाइननुसार, प्रक्रिया रीस्टार्ट झाल्यावर काउंटर रीसेट होतात
(हे टेलिमेट्री आहे, लेखांकन नाही).

#### डॅशबोर्ड कॉन्फिगरेशन

समर्पित डॅशबोर्ड पृष्ठ
`/dashboard/settings/modality-bridge` आहे. त्याचे URL-द्वारे प्रवेशयोग्य `Vision`, `Audio`,
आणि `Video` टॅब `tab` मूल्य बदलताना क्वेरी पॅरामीटर्स जतन करतात.
Vision टॅब सक्षमकरण, मोड, मॉडेल निवड (स्वयंचलित डीफॉल्टसह),
कार्य-जागरूक प्रॉम्प्टिंग, प्रगत timeout/image/description-length/cache
मर्यादा, रनटाइम काउंटर आणि संरक्षित नमुना विनंती उपलब्ध करून देतो. Audio टॅबही
कार्यरत आहे: तो सक्षमकरण, Auto असलेला फक्त-STT मॉडेल पिकर, timeout/max-clip
मर्यादा, ऑडिओ काउंटर आणि `input_audio` नमुना चाचणी उपलब्ध करून देतो. Video
टॅब कार्यक्षम आहे: तो FFmpeg/ffprobe रनटाइम स्थिती दाखवतो — चार स्पष्ट UI
स्थितींपैकी एक (`unknown`, जेव्हा प्रोब सुरू असतो किंवा पूर्ण होऊ शकत नाही;
`restricted`, जेव्हा डॅशबोर्ड होस्ट non-loopback असल्यामुळे प्रोब client-side
वगळला जातो; `unavailable`, प्रोब केल्यानंतर उपलब्ध नसल्याची पुष्टी झाल्यावर;
किंवा FFmpeg/ffprobe आवृत्त्यांसह `available`) — enable/model/frame/video/timeout
मर्यादा कायम ठेवतो, मॉडेल पिकर फक्त vision-सक्षम मॉडेल्सपुरता फिल्टर करतो आणि
व्हिडिओ काउंटर उपलब्ध करून देतो.

AI सेटिंग्जखालील पूर्वीचे Vision Bridge कार्ड आता नवीन पृष्ठाची compatibility
लिंक आहे; त्यात यापुढे फॉर्मची दुसरी प्रत नसते. विद्यमान Speech-to-Text
playground न काढता, Media Providers हे Image-to-Text आणि Speech-to-Text
वर्कफ्लो संबंधित Modality Bridge टॅबशी जोडते.

**Self-loop admission bypass:** describe कॉल OmniRoute च्या स्वतःच्या `/v1`
self-loop मधून (non-standard provider model) रूट होत असताना, उप-विनंती
`x-omniroute-admission-bypass: internal` पाठवते आणि resolved self-loop
credential वापरून प्रमाणीकृत केली जाते — local mode मधील स्थानिक
`sk_omniroute` sentinel किंवा ऑपरेटरने कॉन्फिगर केलेली `OMNIROUTE_API_KEY` /
`ROUTER_API_KEY` env key (#1350), जेणेकरून `REQUIRE_API_KEY=true` असलेली
deployments देखील describe कॉल चालवू शकतील. हा bypass फक्त याच अचूक
credentials साठी स्वीकारला जातो, त्यामुळे बाह्य clients हा header वापरून
admission वगळू शकत नाहीत.

Legacy defaults `src/shared/constants/visionBridgeDefaults.ts` मध्ये आहेत;
नवीन mode/task-aware/cache defaults आणि settings resolver
`src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत. guardrail एक
`deps` constructor पर्याय उपलब्ध करून देते, ज्यामुळे चाचण्या बनावट
`getSettings` आणि `callVisionModel` implementations inject करू शकतात.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ऑडिओ इनपुट स्वीकारते असे ज्ञात नसलेल्या लक्ष्यापर्यंत पोहोचण्यापूर्वी,
ऑडिओ असलेल्या chat विनंत्या intercept करते. ते chat विनंती कधीही पुन्हा
रूट करत नाही: विद्यमान OpenAI-सुसंगत multipart endpoint द्वारे ऑडिओ भागांचे
लिप्यंतरण केले जाते आणि निवडलेले chat मॉडेल मजकूर लिप्यंतरणांसह पुढे सुरू राहते.

प्रवाह:

1. `getResolvedModelCapabilities()` द्वारे `supportsAudio` resolve करा. प्रथम
   स्पष्ट provider-registry metadata ला प्राधान्य दिले जाते, त्यानंतर static
   model metadata आणि मग synced `modalities_input`. `audio` नसलेली घोषित
   input list म्हणजे `false`; कोणताही capability पुरावा नसल्यास मूल्य `null`
   राहते. `false` आणि `null` दोन्ही conservative bridge सक्रिय करतात, तर
   `true` तो bypass करते.
2. `modalityBridgeAudio*` settings resolve करा आणि सामायिक
   `detectMediaParts()` detector द्वारे प्रत्येक संदेशातून splice करता येणारे
   top-level audio भाग काढा. समर्थित wire shapes म्हणजे OpenAI `input_audio`,
   `audio_url`, आणि `source.media_type: "audio/*"`. Routing साठी nested audio
   शोधला जातो, परंतु splice path द्वारे तो काढला जात नाही. कामाची मर्यादा
   `modalityBridgeAudioMaxClips` द्वारे ठरते; त्यानंतरचे भाग न बदलता ठेवले जातात.
3. कॉन्फिगर केलेले `provider/model` वापरा किंवा `selectAudioBridgeModel()` ला
   स्थिर catalog क्रमाने `AUDIO_TRANSCRIPTION_PROVIDERS` मधून जाऊ द्या आणि
   वापरण्यायोग्य सक्रिय provider credential असलेले पहिले मॉडेल निवडू द्या.
4. `callAudioTranscription()` base64/data-URI ऑडिओचे multipart `file` मध्ये
   रूपांतर करते किंवा DNS pinning आणि 25 MB मर्यादेसह public-only outbound
   guard द्वारे remote `audio_url` डाउनलोड करते. त्यानंतर ती file आणि निवडलेले
   मॉडेल स्थानिक `/v1/audio/transcriptions` self-loop वर POST करते आणि
   `resolveSelfLoopBearer()` द्वारे प्रमाणीकरण करते. विद्यमान transcription
   route सामान्य credential lookup, cooldown/rate-limit हाताळणी आणि provider
   dispatch करते.
5. यशस्वी कॉल त्यांच्या भागांना `[Audio N]: <transcript>` ने बदलतात. कॉल
   `Promise.allSettled` वापरून चालतात: स्वतंत्र अपयश आल्यास मूळ ऑडिओ भाग
   जतन केला जातो (#4012 contract). सर्व कॉल अयशस्वी झाल्यास आणि लक्ष्याचे
   `supportsAudio === false` असल्याचे सिद्ध झाल्यास, भाग
   `[Audio N]: (अनुपलब्ध — कोणताही STT provider जोडलेला नाही)` असे होतात
   (#8430 contract). अज्ञात लक्ष्याच्या (`null`) बाबतीत, सर्व कॉल अयशस्वी
   झाल्यास विनंती न बदलता ठेवली जाते. वापरण्यायोग्य STT credential नसलेल्या
   सिद्ध text-only लक्ष्याला network call न करता हाच स्पष्ट stub मिळतो.

यशस्वी लिप्यंतरणे process-wide Modality Bridge LRU/TTL cache वापरतात. key मध्ये
audio reference, स्थिर `audio-transcription` operation label आणि निवडलेले STT
मॉडेल एकत्र केले जातात; अपयश कधीही cache केले जात नाही. Audio प्रयत्न सामायिक
`bridged`, `cacheHits`, `failures`, आणि `lastUsedAt` काउंटर अपडेट करतात.
रूपांतरित प्रतिसादांमध्ये
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` असते;
न बदललेल्या विनंत्यांना Audio Bridge segment मिळत नाही.

रनटाइम सेटिंग्ज DB-backed आणि Zod-validated आहेत:

| की                            | डीफॉल्ट | श्रेणी                 |
| ----------------------------- | ------- | ---------------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                      |
| `modalityBridgeAudioModel`    | `""`    | स्वयंचलित किंवा STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000            |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10                   |

सामायिक कॅशे अजूनही `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, आणि `modalityBridgeCacheMaxEntries` द्वारे नियंत्रित केली जाते.

### व्हिडिओ ब्रिज (`videoBridge.ts`, `videoBridgePipeline.ts`)

ज्ञात मूळ व्हिडिओ समर्थन नसलेल्या लक्ष्याला कॉल करण्यापूर्वी Chat Completions
`messages` आणि Responses API `input` मधील शीर्ष-स्तरीय व्हिडिओ भाग इंटरसेप्ट करतो.
समर्थित स्वरूपे `input_video`, `video_url`, `video_source`, HTTPS URLs,
आणि `data:video/*;base64,...` डेटा URIs आहेत. मजकुरातील साधी फाइलनावे व्हिडिओ
म्हणून हाताळली जात नाहीत.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) विनंतीचे ट्रॅव्हर्सल,
क्षमता/धोरण तपासणी, प्रत्येक-विनंती एकत्रीकरण आणि प्रतिसाद पेलोड हाताळते.
प्रत्येक-व्हिडिओचे कार्य — प्राप्ती, संपूर्ण-निकाल कॅशे, फ्रेम
अनुक्रमाचे वर्णन (जे कॉलरने घोषित केलेला कोणताही ऑडिओ ट्रान्सक्रिप्ट एकत्रित करते), आणि प्रत्येक-प्रयत्नाचे
मेट्रिक्स/अॅबॉर्ट/क्लीनअप — `videoBridgePipeline.ts` मधील `processVideoPart` च्या
मागे लपवलेले आहे, ज्याला `preCall` च्या लूपमध्ये प्रत्येक व्हिडिओ भागासाठी एकदा कॉल केले जाते.
ते मॉड्यूल स्पष्ट पोर्ट सीमा `VideoMediaBrokerPort`
(बाइट्स प्राप्त करणे आणि नमुना घेतलेल्या फ्रेम्स काढणे), `VideoAudioTranscriptionPort`
(कॉलरने घोषित केलेला ऑडिओ ट्रान्सक्रिप्ट नमुना घेतलेल्या कॅप्शन्ससह एकत्रित करणे), आणि
`VideoDrilldownPort` (फ्रेम ड्रिल-डाउन स्थायित्व सीमा; अद्याप
`processVideoPart` शी जोडलेली नाही — सध्या केवळ स्वतंत्र `/api/modality-bridge/video/drilldown`
रूट ड्रिल-डाउन नोंदी लिहितो) देखील परिभाषित करते.

सार्वजनिक `/v1` विनंती पथ कधीही सबप्रोसेस इम्पोर्ट किंवा इनव्होक करत नाही. रिमोट
व्हिडिओ 50 MiB मर्यादेत डाउनलोड केले जातात; इनलाइन base64 व्हिडिओंना
प्रत्येक व्हिडिओसाठी सावधगिरीची 36 MiB डीकोडेड मर्यादा आहे, ज्यामुळे मॉडेल/संदेश/फ्रेमिंग एन्व्हलप
50 MiB च्या सार्वजनिक JSON विनंती प्रवेश मर्यादेत राहू शकतो. वाटपापूर्वी
इनलाइन लांबी आणि डीकोडेड-आकाराच्या अंदाजांची तपासणी केली जाते. प्रारंभिक रिमोट URL आणि प्रत्येक
रीडायरेक्टसाठी HTTPS आवश्यक आहे, ज्यासाठी DNS पिनिंगसह विद्यमान
केवळ-सार्वजनिक आउटबाउंड गार्ड वापरला जातो. त्यानंतर बाइट्स अचूक अंतर्गत
`POST /api/modality-bridge/video/extract` ब्रोकर सीमा ओलांडतात. तो रूट
`LOCAL_ONLY` आणि `SPAWN_CAPABLE` दोन्ही आहे, केवळ प्रत्येक-प्रक्रियेसाठी प्रमाणीकरण केलेली,
विश्वसनीय-लूपबॅक विनंती स्वीकारतो आणि URL, फाइलसिस्टम पथ, एक्झिक्युटेबल
किंवा आर्ग्युमेंट सूची कधीही स्वीकारत नाही. API बॉडी-आकार पाइपलाइन आणि हँडलरचा वाढीव बॉडी
रीडर स्वतंत्रपणे 50 MiB ब्रोकर इनपुट मर्यादा लागू करतात. त्याची मर्यादित क्यू
एका वेळी एक एक्स्ट्रॅक्शन चालवते, चार प्रलंबित जॉबना परवानगी देते आणि प्रलंबित इनपुटला
100 MiB पर्यंत मर्यादित करते.

ब्रोकरच्या आत, `ffprobe` खाजगी स्थानिक फाइल वाचतो; निश्चित फॉरमॅट
अनुमतीसूची प्लेलिस्ट आणि मॅनिफेस्ट फॉरमॅट वगळते. अनुमत MOV-कुटुंबातील
कंटेनर्ससाठी, बाह्य MOV डेटा संदर्भ डीफॉल्टनुसार अक्षमच राहतात आणि
निश्चित कमांड त्यांना निवडून सक्षम करत नाही. `ffprobe` आणि `ffmpeg` दोन्ही
केवळ-`file` प्रोटोकॉल अनुमतीसूची, एक थ्रेड, निश्चित आर्ग्युमेंट अॅरे, शेलशिवाय,
आणि `PATH` मधून निराकरण केलेले एक्झिक्युटेबल वापरतात. संलग्न-चित्र कव्हर स्ट्रीम्स
प्लेबॅकयोग्य उमेदवार नाहीत. सर्व प्लेबॅकयोग्य स्ट्रीम्सनी मर्यादा पूर्ण केल्या पाहिजेत आणि
निश्चित सर्वात-कमी-इंडेक्स फॉलबॅकपूर्वी स्पष्ट डीफॉल्ट स्ट्रीमला प्राधान्य दिले जाते.
व्हिडिओ 600 सेकंद, प्रत्येक परिमाणात 8,192 पिक्सेल आणि
33,554,432 स्रोत पिक्सेलपर्यंत मर्यादित आहेत. FFmpeg 1–16 मध्यबिंदू JPEG फ्रेम्सचे नमुने घेतो,
लहान इनपुट अपस्केल न करता लांब कडा जास्तीत जास्त 1,024 पिक्सेलपर्यंत
कमी करतो आणि त्याला कधीही URL दिला जात नाही. डीफॉल्टनुसार सॅम्पलिंग `uniform` असते. पर्यायी
`scene_aware` आणि प्रायोगिक `segment_aware` धोरणे आधीच पडताळलेल्या
स्थानिक स्ट्रीमवर एक अतिरिक्त निश्चित FFmpeg पास करतात, मर्यादित
`showinfo` दृश्य टाइमस्टॅम्प निवडतात आणि डिटेक्टर अपयश, टाइमआउट, विकृत आउटपुट किंवा रिक्त
उमेदवार संच असल्यास त्याच एकसमान मध्यबिंदूंवर निर्धारपूर्वक फॉलबॅक करतात. सेगमेंट-अवेयर मोड
पडताळलेल्या दृश्य अंतरालांच्या प्रमाणात मध्यबिंदू नमुने वाटप करतो; सेगमेंट-अवेयर पुरावे आणि फॉलबॅक वर्तन
खाली तपशीलवार दिले आहे. प्रत्येक धोरणात निवडीनंतर
16-फ्रेमची कठोर मर्यादा लागू केली जाते. सीन-अवेयर विनंतीकडे केवळ
एका-फ्रेमचे बजेट असल्यास, ती सक्रिय पूर्ण-व्हिडिओ किंवा फोकस विंडोचा एकसमान मध्यबिंदू वापरते
आणि `policyEffective: uniform` नोंदवते: निवडलेली एकच दृश्य फ्रेम
दोन्ही कालिक टोके जतन करू शकत नाही. कॉलर पर्यायाने
मर्यादित फोकस विंडो (`start`/`end` सेकंद) देऊ शकतो; सीमा मीडिया
कालावधीपर्यंत क्लॅम्प केल्या जातात, उलट किंवा असमर्यादित विंडो नाकारल्या जातात आणि सर्व सॅम्पलिंग
धोरणे केवळ सामान्यीकृत अंतरालातच पार पाडली जातात. परिणामी
विंडो सॅम्पलिंग मेटाडेटामध्ये आणि अविश्वसनीय वर्णन
उपसर्गामध्ये समाविष्ट केली जाते, जेणेकरून डाउनस्ट्रीम मॉडेल्स पूर्ण टाइमलाइनपासून केंद्रित उतारा वेगळा ओळखू शकतील.

सिमॅंटिक कॅप्शन फोकस ही स्वतंत्र, स्पष्ट सेटिंग आहे. डीफॉल्ट `full`
विश्लेषण मोड विद्यमान फ्रेम प्रॉम्प्ट जतन करतो आणि विनंतीचा मजकूर कधीही
कॅप्शन मॉडेलकडे पाठवत नाही. `focused` मोडमध्ये, ब्रिज त्याच Chat किंवा Responses
कंटेनरमधून फक्त सर्वात अलीकडील रिक्त नसलेला वापरकर्त्याने लिहिलेला `text`/`input_text` वाचतो,
त्याचे NFC मध्ये सामान्यीकरण करतो, नियंत्रण वर्ण आणि व्हाइटस्पेस संक्षिप्त करतो
आणि त्याला 500 Unicode कोड पॉइंट्सपर्यंत मर्यादित करतो. रिक्त निकाल अचूक
`full` प्रॉम्प्टवर फॉलबॅक करतो. वापरण्यायोग्य संकेत समर्पित
अविश्वसनीय-वापरकर्ता-संदर्भ ब्लॉकमध्ये JSON म्हणून सिरियलाइझ केला जातो आणि तो केवळ निरीक्षणयोग्य तपशीलांना प्राधान्य देऊ शकतो;
तो मीडियामध्ये दृश्यमान किंवा ऐकू येणाऱ्या सूचनांचे पालन न करण्याबाबतच्या स्वतंत्र इशाऱ्याला
ओव्हरराइड करू शकत नाही. मजकूर-केंद्रित फोकस कधीही `start`/`end` चा अंदाज लावत नाही किंवा
कालिक सॅम्पलर बदलत नाही.

#### FU-07 संरचनात्मक सेगमेंट पुरावे

`segment_aware` आधीच प्रमाणित केलेल्या स्थानिक व्हिडिओ प्रवाहावर एक मर्यादित
पूर्व-विश्लेषण फेरी वापरते. निश्चित फिल्टर शृंखला प्रथम रुंदी जास्तीत जास्त 320 पिक्सेलपर्यंत
स्केल करते, दृश्यांमधील बदल आणि गोठलेली मध्यांतरे शोधते, त्यानंतर अस्पष्टता, सरासरी ल्युमा
आणि अवकाशीय/कालिक माहितीसाठी दर सेकंदाला 1 फ्रेमचे नमुनीकरण करते. ही फेरी
600 संरचनात्मक नमुने, एक FFmpeg/filter थ्रेड, तीच केवळ-`file` प्रोटोकॉल आणि कंटेनर अनुमतसूची,
1 MiB प्रक्रिया-आउटपुट मर्यादा आणि ब्रोकरच्या सामायिक रद्दीकरण/अंतिम मुदतीमध्ये
जास्तीत जास्त 30 सेकंदांपर्यंत मर्यादित आहे. ती विनंतीमधून आदेश, फिल्टर, पथ किंवा URL
कधीही स्वीकारत नाही.

संरचनात्मक मूल्ये म्हणजे निर्धारक नमुनीकरण पुरावा आहे, अर्थविषयक व्हिडिओ
आकलन नव्हे. ती विषय, कृती, मथळे, संभाषण किंवा वापरकर्त्याचा
हेतू यांचा अंदाज लावत नाहीत. दृश्य आणि गोठण-सीमा विभाग तयार करतात; गोठण व्याप्ती, अस्पष्टता,
प्रकाशमानता, अवकाशीय तपशील आणि कालिक बदल केवळ विद्यमान
1–16 फ्रेमचे बजेट कसे वाटले जाते यावर प्रभाव टाकतात. पूर्णपणे गोठलेला विभाग एका फ्रेमपुरता मर्यादित असतो,
तर न गोठलेले विभाग उर्वरित बजेटसाठी स्पर्धा करतात. जेव्हा सीमांची संख्या
फ्रेमपेक्षा जास्त असते, तेव्हा कालरेषेची एकसमान व्याप्ती कायम ठेवली जाते, जेणेकरून सुरुवातीचे वेगवान कट
शेवटचा दीर्घ विभाग लपवू शकणार नाहीत. गोठण-सीमेच्या 1-सेकंद
विश्लेषण रिझोल्यूशनमध्ये येणाऱ्या दृश्य-सीमा एकत्रित केल्या जातात.

फिल्टर उपलब्ध नसणे, विकृत/रिक्त पुरावा, डिटेक्टर त्रुटी किंवा मर्यादित
पूर्व-विश्लेषण कालबाह्यता झाल्यास अचूक एकसमान मध्यबिंदू धोरणावर खुले अपयश होते. कॉलरकडून
रद्दीकरण किंवा ब्रोकरची अंतिम मुदत झाल्यास खुले अपयश होत नाही: त्यामुळे सुरू असलेली
उपप्रक्रिया समाप्त होते, त्यानंतरचे फ्रेम निष्कर्षण रोखले जाते आणि खासगी तात्पुरते ट्री
`finally` मध्ये काढून टाकले जाते.

`scripts/perf/video-bridge-fu07-eval.ts` डीडुप्लिकेशननंतरच्या मथळा-कॉल बचतीसाठी, सघन-गती बजेट वाटपासाठी,
अस्पष्टता/प्रकाशमानता/SI-TI पुराव्यासाठी, दीर्घ शेवटासह वेगवान कटसाठी आणि क्रमिक-फेड
खोट्या सकारात्मक परिणामांसाठी निर्धारक वास्तविक FFmpeg
फिक्स्चर निर्माण करते. ते पूर्व-विश्लेषणाचा प्रत्यक्ष कालावधी आणि, जिथे `/usr/bin/time`
उपलब्ध असेल तिथे, चाइल्ड CPU व कमाल RSS नोंदवते. त्याच्या गुणवत्ता तपासण्या केवळ संरचनात्मक ओरॅकल्स
आहेत. वास्तविक मथळा-मॉडेलची गुणवत्ता `HOLD` वरच राहते, कारण या हार्नेसकडे कोणताही
अधिकृत एंडपॉइंट किंवा स्थिर जज नाही. आर्थिक बचतदेखील `HOLD`
वरच राहते, जोपर्यंत `--caption-cost-per-call-usd` स्पष्ट सकारात्मक प्रति-कॉल
अंदाज पुरवत नाही; स्क्रिप्ट यांपैकी कोणताही परिणाम कधीही बनावट तयार करत नाही.

प्रत्येक फ्रेम 4 MiB पर्यंत, सर्व रॉ फ्रेम एकत्रितपणे 23 MiB पर्यंत आणि
क्रमबद्ध केलेला ब्रोकर प्रतिसाद 32 MiB पर्यंत मर्यादित असतो. खासगी तात्पुरती निर्देशिका
`finally` मध्ये काढून टाकली जाते. OmniRoute मध्ये FFmpeg समाविष्ट नसते आणि ते सानुकूल
एक्झिक्युटेबल पथ स्वीकारत नाही. मथळे तयार करण्यापूर्वी, ब्रिज एक सावध दृश्य
डीडुप्लिकेशन फेरी लागू करतो: प्रत्येक JPEG ला 16×16 ग्रेस्केल बफरमध्ये संक्षिप्त केले जाते आणि
त्याची तुलना केवळ शेवटी राखून ठेवलेल्या फ्रेमशी केली जाते. एका फ्रेमपेक्षा अधिक मथळा बजेटची
विनंती असल्यास, निष्कर्षण त्या बजेटच्या जास्तीत जास्त दुप्पट आकाराचा
मर्यादित उमेदवार संच पुरवते आणि तो कधीही 16 फ्रेमपेक्षा जास्त नसतो.
विनंती केलेली कमाल मर्यादा केवळ डीडुप्लिकेशननंतर लागू केली जाते; बजेट किमान
दोन असताना अंतिम विरळीकरणादरम्यान पहिला आणि अंतिम
निवडलेला उमेदवार जतन केला जातो. आवृत्तीकृत
`grayscale-16x16-mean-cells-v2` धोरण सरासरी ल्युमा डेल्टा आणि
ज्या थंबनेल सेलचा सामान्यीकृत डेल्टा किमान 0.05 आहे त्यांच्या गुणोत्तरापैकी मोठे मूल्य वापरते.
डुप्लिकेट थ्रेशोल्ड हा स्थिरांक 0.04 आहे, जो रनटाइम सेटिंग म्हणून
उघड करण्याऐवजी पूर्वानुमानक्षमतेसाठी निवडला आहे. हा दुय्यम
उच्च-कॉन्ट्रास्ट संकेत लहान हालचाली आणि दृश्यमान-मजकूरातील बदल जतन करतो, जे
केवळ-सरासरी तुलना लपवू शकते. कंपॅरेटर किंवा डीकोडर त्रुटींमध्ये खुले अपयश होते आणि
व्याप्ती कायम ठेवली जाते. आउटपुट मेटाडेटा निष्कर्षित उमेदवार, यशस्वीरित्या वापरलेल्या
फ्रेम आणि वगळलेले दृश्य डुप्लिकेट वेगळे दाखवतो.

स्पष्टपणे चिन्हांकित केलेला व्हिडिओ भाग टाइमस्टॅम्प असलेल्या कॉन्टॅक्ट शीटची विनंती करू शकतो.
ब्रिज जास्तीत जास्त 4-स्तंभांची, 16-फ्रेमची JPEG ग्रिड तयार करतो. प्रत्येक 512-पिक्सेल सेल
त्याचा स्रोत टाइमस्टॅम्प उच्च-कॉन्ट्रास्ट तळाच्या पट्ट्यात कोरतो, तर तेच टाइमस्टॅम्प
पुढील टप्प्यातील संबंधजोडणी आणि लेखापरीक्षणासाठी मजकूर मेटाडेटामध्ये कायम राहतात. संपूर्ण
JPEG 32 MiB पर्यंत मर्यादित राहते. `sharp` ग्रिड डीकोड किंवा कंपोझ करू शकत नसल्यास,
ब्रिज स्वतंत्र JPEG फ्रेमवर फॉलबॅक करतो; क्लायंटकडून रद्दीकरण तरीही
शीट ऑपरेशनमधून प्रसारित होते.

प्रमोशन पुरावा कृत्रिम रचना
मायक्रोबेंचमार्कपासून मुद्दाम वेगळा ठेवला आहे. `scripts/perf/video-bridge-contact-sheet-eval.ts` वास्तविक OpenAI-सुसंगत व्हिजन मॉडेलसाठी
स्कीमा-आवृत्तीकृत A/B हार्नेस परिभाषित करते. ते
प्रदात्याने नोंदवलेले टोकन, एंड-टू-एंड प्रत्यक्ष विलंब (शीट रचनेसह),
मॉडेल-कॉल संख्या आणि मॅनिफेस्टद्वारे परिभाषित तथ्य धारणा मोजते. रॉ मॉडेल प्रतिसाद
अहवालात लिहिले जात नाहीत; केवळ SHA-256 डायजेस्ट आणि जुळलेले तथ्य ID राखून ठेवले जातात.
`--execute-real` दिलेले नसल्यास आणि
`--model`, `OMNIROUTE_BASE_URL` व `OMNIROUTE_API_KEY` कॉन्फिगर केलेले नसल्यास, हार्नेस कोणताही नेटवर्क किंवा सशुल्क मॉडेल कॉल करत नाही. अशी
स्पष्ट वास्तविक रन नसल्यास, त्याचा मशीन-वाचनीय निकाल `HOLD` राहतो; केवळ कृत्रिम
पेलोड/कॉल-संख्या मोजमाप प्रमोशन पुरावा नाहीत.

कॉलरकडे आधीच संरेखित मजकूर असल्यास, ते समर्थित व्हिडिओ
भागाला वैकल्पिक `transcript.cues` अॅरे जोडू शकतात. प्रत्येक क्यूमध्ये `text`,
तपासलेल्या कालावधीतील मर्यादित `start`/`end` मध्यांतर आणि अनुमतसूचीतील
`source` (`client`, `embedded`, किंवा `audio-bridge`) असणे आवश्यक आहे; `confidence` चे डीफॉल्ट मूल्य
`1` असते आणि ते `0` व `1` यांच्या दरम्यानच राहिले पाहिजे. पूर्णपणे समान क्यू एकत्र केले जातात.
OmniRoute या मेटाडेटावरून कधीही ट्रान्सक्रिप्शन सुरू करत नाही: प्रमाणित क्यू
स्रोत, विश्वासमान आणि मध्यांतरासह वर्णन केलेल्या परिणामात कॉपी केले जातात आणि
फ्रेम मथळ्यांसोबत अविश्वसनीय निरीक्षणे म्हणून रेंडर केले जातात. अवैध,
मर्यादेबाहेरील किंवा उगम-माहिती नसलेला मजकूर मथळा प्रवाहात मिसळण्याऐवजी नाकारला जातो.
दोन्ही विनंती-बॉडी ट्रान्सक्रिप्ट चॅनेल पुरवलेला उगम `client` म्हणून सामान्यीकृत करतात,
यात स्वतः घोषित केलेली `embedded` किंवा `audio-bridge`
लेबलेही समाविष्ट आहेत. केवळ सर्व्हरच्या मालकीचा अॅडॅप्टर कोड-केवळ `trustedSource`
आर्ग्युमेंटद्वारे ती विश्वसनीय लेबले नियुक्त करू शकतो; विनंतीतील JSON फील्ड त्या
आर्ग्युमेंटपर्यंत पोहोचू शकत नाही. ट्रान्सक्रिप्ट मजकूर त्याच्या उगमाची पर्वा न करता
अविश्वसनीय माध्यम-व्युत्पन्न सामग्रीच राहतो आणि त्याने कधीही अधिकृतता निश्चित करू नये.

प्रगत कॉलर त्याच व्हिडिओसाठी `audioTranscript` ट्रॅक प्रदान करू शकतो;
तो क्लायंटने प्रदान केलेला मजकूर मानला जातो, सर्व्हर ट्रान्सक्रिप्शनचा पुरावा नाही.
फ्यूजन सीम एका अंतिम मुदतीच्या आणि रद्दीकरण सिग्नलच्या अधीन राहून दृश्य व ऑडिओ निरीक्षणे चालवते, त्यांना
एका सामायिक टाइमलाइनवर क्रमबद्ध करते, अगदी तंतोतंत असलेल्या डुप्लिकेट नोंदी एकत्र करते,
आणि केवळ एक बाजू यशस्वी झाल्यास आंशिक परिणाम नोंदवते.
अवैध `audioTranscript` मुळे संपूर्ण व्हिडिओ अयशस्वी होण्याऐवजी तो आंशिक परिणाम मिळतो —
दृश्य वर्णन कायम ठेवले जाते आणि ऑडिओ शाखा निर्जंतुक केलेला अपयश कोड नोंदवते.
प्रत्येक शाखेची उपलब्धता, आंशिक फ्लॅग आणि निर्जंतुक केलेले अपयश कोड वर्णन केलेल्या परिणामात,
गार्डरेल मेटाडेटामध्ये (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), परिणाम-कॅश मेटाडेटामध्ये आणि ब्रिज
फ्यूजन काउंटरमध्ये जतन केले जातात. डीफॉल्ट Video Bridge मार्ग स्पीच-टू-टेक्स्ट सुरू करत नाही
किंवा मीडियाची दुसरी प्रत डाउनलोड करत नाही; त्या स्पष्ट ट्रॅकशिवाय तो
केवळ-व्हिडिओ स्वरूपातच राहतो.

**ट्रान्सक्रिप्ट प्रतिधारण (#12150 P1).** Video Bridge (जो स्वतः ऑप्ट-इन आहे)
ट्रान्सक्रिप्ट क्यू रेंडर करतो तेव्हा हे आपोआप लागू होते — यासाठी स्वतंत्र
प्रतिधारण फ्लॅग नाही. जेव्हा एखादी विनंती कोणताही ट्रान्सक्रिप्ट क्यू (कॉलरने घोषित केलेला
`transcript` किंवा फ्यूज केलेला `audioTranscript`) रेंडर करते, तेव्हा गार्डरेल त्याला
`videoBridgeObserved` म्हणून चिन्हांकित करते आणि व्हिडिओ वर्णनाची संपादित शॅडो प्रत तयार करते —
एकसारखे रेंडरिंग, ज्यामध्ये प्रत्येक क्यूचा मुक्त-मजकूर भाग
`[redacted-video-transcript]` ने बदलला जातो; स्ट्रिंग जोडण्यापूर्वी संरचित क्यू फील्ड
बदलून ही प्रत तयार केली जाते (सपाट केलेला मजकूर पार्स करून कधीही नाही, त्यामुळे
कोणतीही क्यू सामग्री — प्रतिकूल किंवा सामान्य, तसेच `]` असलेले भाग जसे की
`[inaudible]`/`[music]` — टिकून राहू शकत नाही). कायम ठेवलेल्या कॉल-लॉगमधील विनंतीचा भाग
सामग्री समानतेद्वारे जुळवून, प्रत्येक व्हिडिओ-व्युत्पन्न मजकूर भागाऐवजी ती संपादित शॅडो प्रत
ठेवतो; पूर्ण झालेल्या प्री-कॉल गार्डरेल पेलोडमधून `fullText` अँकर पुन्हा वाचला जातो,
त्यामुळे नंतरचे साखळी गार्डरेल (PII आणि क्रेडेन्शियल मास्कर, प्राधान्ये 10/95) वर्णनाचा
मजकूर त्याच ठिकाणी पुन्हा लिहितात आणि सिस्टम-प्रॉम्प्ट/हँडऑफ/मेमरी इंजेक्शन संदेश अॅरेला
नवा आकार देतात, त्यानंतरही जुळणी यशस्वी होते. मॉडेलला अपस्ट्रीम पाठवलेला भाग बदलत नाही.
निरीक्षित विनंती कोणतीही टिकाऊ Memory देखील भरत नाही (विनंती- आणि प्रतिसाद-व्युत्पन्न
दोन्ही एक्स्ट्रॅक्शन वगळली जातात), त्यामुळे मॉडेलचा स्वतःचा प्रतिसाद ट्रान्सक्रिप्टचा मजकूर
Memory मध्ये प्रतिध्वनित करू शकत नाही.

**कच्ची व्हिडिओ फील्ड्स (#12430).** ब्रिज सक्षम असताना आणि नेटिव्ह व्हिडिओ समर्थन अज्ञात किंवा अनुपस्थित असताना, परिभाषित `transcript`/`audioTranscript` फील्ड्स वर्णन अयशस्वी झाल्यानंतर किंवा `maxVideos` मर्यादा लागू झाल्यानंतरही `videoBridgeObserved` सक्रिय करतात. `null` आणि रिकाम्या स्ट्रिंग मोजल्या जातात; अनुपस्थित फील्ड्स आणि व्हिडिओ नसलेले मेटाडेटा मोजले जात नाहीत. जतन केलेल्या प्रतींमध्ये ही फील्ड्स संपादित केली जातात किंवा विनंती वगळली जाते आणि कॅश/Memory बायपास केल्या जातात.

त्या फॉलबॅक मार्गांवर, वैध कॉलर क्यूज गैर-मानक प्रदाता फील्ड्सऐवजी समर्थित `text`/`input_text`
भाग बनतात. विनंतीत पुरवलेले दोन्ही ट्रॅक अविश्वसनीय `client` निरीक्षणे म्हणूनच राहतात,
आणि व्हिडिओचे वर्णन केले गेले नाही व टाइमस्टॅम्प मीडियाशी पडताळले गेले नाहीत अशी स्पष्ट
चेतावणी दिली जाते. विद्यमान 256-क्यू/64-KiB एकूण आणि प्रत्येक क्यूसाठीची बजेट मर्यादा दोन्ही
ट्रॅकवर एकत्रितपणे लागू होते; टाइमस्टॅम्प ब्रोकरच्या 600-सेकंद कमाल मर्यादेत आणि पुरवलेल्या
कोणत्याही फोकस विंडोमध्ये बसले पाहिजेत. अवैध ट्रॅक टाकून दिले जातात, मनमाना मजकूर म्हणून
फॉरवर्ड केले जात नाहीत; त्यांचे एकत्रित बजेट ओलांडले जात नसेल तर वैध सहोदर ट्रॅक वापरला
जाऊ शकतो. Null/रिकामी फील्ड्स कोणताही मजकूर जोडत नाहीत. या फॉलबॅकमुळे कोणतेही मीडिया
फेचिंग किंवा ट्रान्सक्रिप्शन जोडले जात नाही. फॉलबॅक व्हिडिओ कॅरियर आणि त्याच्या
`video_url`/`source` ऑब्जेक्टमधून ट्रान्सक्रिप्ट एक्स्टेंशन फील्ड्स काढून टाकली जातात.
OpenAI वायर अलाउलिस्ट कठोरच राहते; अज्ञात-नेटिव्ह व्हिडिओ कॅरियर उपलब्ध राहतात आणि ज्ञात
केवळ-मजकूर लक्ष्ये सुरक्षित मार्कर कायम ठेवतात. संरचित संपादन शॅडो जोडलेल्या ट्रान्सक्रिप्ट
मजकुराचे संरक्षण करतात, तर कॉलरच्या मालकीची मूळ विनंती बदलत नाही. नेटिव्ह समर्थन असलेली
लक्ष्ये आणि अक्षम केलेले ब्रिज त्यांचे विद्यमान बायपास वर्तन कायम ठेवतात.

अतिरिक्त जतन केलेल्या प्रती समान निरीक्षित-विनंती सिग्नल वापरतात. कच्चा
प्री-गार्डरेल क्लायंट-विनंती स्नॅपशॉट, इन-मेमरी प्रलंबित विनंती आणि लवकर
नाकारलेल्या विनंतीचा लॉग व्हिडिओ भागांमधील ट्रान्सक्रिप्ट फील्ड्स संरचनात्मकरीत्या बदलतात;
पाइपलाइन टप्पे आणि संदर्भ हँडऑफद्वारे तयार केलेले स्ट्रिंग प्रॉम्प्ट्स
कायम-विनंती-भाग सिंकवर संपादित केले जातात. कायम ठेवलेला `video_content_removed` मार्कर
`previous_response_id` सातत्याला जाणूनबुजून टाकून दिलेला मजकूर पुन्हा तयार करण्याऐवजी
सुरक्षितरीत्या अयशस्वी करतो. निरीक्षित विनंतीने लॉगिंगपूर्वी तिची प्रत्येक-भागासाठीची संपादन
शॅडो गमावल्यास, किंवा नंतरच्या विनंतीतील बदलांनंतर अनेक व्हिडिओ शॅडोपैकी एकाची जुळणीही
अयशस्वी झाल्यास, अंशतः संपादित ट्रान्सक्रिप्ट जतन करण्याऐवजी जतन केलेला विनंती भाग पूर्णपणे
वगळला जातो.

निरीक्षित विनंतीसाठी, मॉडेलचा प्रतिसाद संरचित क्यू सीमेशिवाय ट्रान्सक्रिप्टचा कोणताही भाग
उद्धृत करू शकतो. म्हणून त्याचा कायम ठेवलेला कॉल-लॉग `responseBody` वगळण्याच्या मार्करने
बदलला जातो; तपशीलवार पाइपलाइन आर्टिफॅक्ट (ज्यामध्ये अपस्ट्रीम/क्लायंट भाग आणि स्ट्रीम खंड
असू शकतात) जतन केला जात नाही. त्या विनंतीसाठी सिमॅंटिक, आयडेम्पोटन्सी आणि
रीझनिंग-रिप्ले कॅशमधील वाचन व लेखन बायपास केले जाते. प्रदाता विनंती आणि क्लायंटला दिसणारा
प्रतिसाद बदलत नाहीत. तपशीलवार आर्टिफॅक्ट वगळला जातो तेव्हा तात्पुरत्या बफरमधील सुरुवातीचे
कीपअलाइव्ह बाइट्स काढून टाकले जातात. Kiro ची विकृत EventStream चेतावणी केवळ पेलोडमधील
बाइट्सची संख्या नोंदवते, त्यातील सामग्री किंवा JSON पार्सरची कच्ची त्रुटी कधीही नोंदवत नाही.
यात प्रत्येक असंबंधित प्रदाता/प्लगइन निदानाचे ऑडिट झाले असल्याचा दावा केलेला नाही;
अधिक व्यापक जतन-सिंक तपासणी #11658 मध्ये ट्रॅक केली आहे.

अंतर्गत `/api/modality-bridge/video/drilldown` जीवनचक्र हे स्वतंत्र,
लूपबॅक/टोकन-प्रमाणीकृत कॅशे अधःस्तर आहे. प्रत्येक ऑपरेशनसाठी प्रमाणित अपारदर्शक
प्रिन्सिपल ID देखील आवश्यक असतो. एखादा उत्पादन कॉलर सक्षम करण्यापूर्वी, त्याने
प्रमाणीकृत टेनंटवरून तो ID व्युत्पन्न केला पाहिजे आणि क्लायंटने निवडलेले मूल्य
कधीही अग्रेषित करू नये. कॅशे की त्या प्रिन्सिपलला प्रमाणित सत्र आणि
व्हिडिओ-संदर्भ ID शी बांधतात, केवळ त्यांच्या SHA-256-व्युत्पन्न की साठवतात आणि
वाचन तसेच हटवणे या दोन्हींची व्याप्ती त्याच प्रिन्सिपलपुरती मर्यादित करतात. कॅशे
प्रत्येक नोंदीमध्ये जास्तीत जास्त 16 व्युत्पन्न JPEG फ्रेम साठवते, दहा मिनिटांनंतर
त्यांची मुदत संपवते आणि मर्यादित `start`/`end` वाचन किंवा स्पष्ट सत्र हटवण्यास
समर्थन देते.

प्रत्येक प्रिन्सिपलसाठी 16 नोंदी आणि 64 MiB प्रमाणित JPEG डेटाची मर्यादा आहे. या
मर्यादा जागतिक 64-नोंदी/256 MiB कमाल मर्यादेपासून स्वतंत्र आहेत: जागतिक LRU
बेदखलीचा विचार करण्यापूर्वी, प्रिन्सिपल कोट्यावरील दबाव फक्त त्या प्रिन्सिपलच्या
सर्वांत कमी अलीकडे वापरलेल्या नोंदी बेदखल करतो. कॅशे क्रियाकलापादरम्यान मुदत
संपलेल्या नोंदी प्रिन्सिपल आणि जागतिक अशा दोन्ही लेखांकनातून काढून टाकल्या जातात,
तर रद्दीकरण आणि प्रमाणीकरणातील अपयशामुळे अंशतः पुनर्स्थापना कमिट होत नाही.

कॅशे अप्रमाणित Base64, अतिरिक्त पॅडिंग, JPEG नसलेले माध्यम, विकृत किंवा
अपूर्ण JPEG आणि मर्यादित पूर्ण-प्रतिमा `sharp` डीकोडदरम्यान इशारा निर्माण करणारे
JPEG नाकारते. ती प्रत्येक स्वीकारलेली प्रतिमा प्रमाणित JPEG म्हणून पुन्हा एन्कोड
करते, कॉलरच्या फील्डवर विश्वास ठेवण्याऐवजी डीकोड केलेल्या बाइट्समधून रुंदी आणि उंची
व्युत्पन्न करते आणि शेवटी जोडलेले कोणतेही पॉलीग्लॉट बाइट्स राखून न ठेवता टाकून देते.
दोन्ही कोट्यांमध्ये फक्त मर्यादित प्रमाणित संकुचित बफरची गणना केली जाते. JSON वायर
मर्यादेत 32 MiB डीकोडेड-इनपुट कमाल मर्यादेसाठी Base64 ओव्हरहेड समाविष्ट आहे. प्रत्येक
साठवलेल्या व्युत्पत्तीमध्ये तिचे प्रमाणित JPEG स्वरूप/रिझोल्यूशन, सॅम्पलिंग धोरण,
व्युत्पत्ती आवृत्ती, निर्मिती वेळ, सर्व्हरने मोजलेला सामग्री हॅश आणि हॅश केलेला मूळ
संदर्भ तसेच विश्वसनीय कॉलरचा मूळ-सामग्री हॅश नोंदवला जातो. अणुसदृश कॅशे कमिटपूर्वी
असिंक्रोनस डीकोड/हॅश टप्प्यांदरम्यान रद्दीकरण तपासले जाते.

हा टप्पा अद्याप उत्पादन प्रोड्युसरला रूटशी जोडत नाही आणि बहु-रिझोल्यूशन प्रकार
निवड उपलब्ध करून देत नाही. त्यामुळे पारदर्शक Video Bridge विनंती मार्गावर कोणतेही
अतिरिक्त काम होत नाही, तर टेनंट-बद्ध प्रिन्सिपल व्युत्पत्ती आणि संपूर्ण FU-08
बहु-रिझोल्यूशन जीवनचक्र हे पूर्ण वर्तन म्हणून दस्तऐवजीकरण न करता स्पष्टपणे पुढील
काम म्हणून ठेवले आहेत.

कॉन्फिगर केलेल्या Video मॉडेलद्वारे फ्रेमना अनुक्रमे मथळे दिले जातात. रिकामा
Video ओव्हरराइड Vision सेटिंगचा वारसा घेतो; दोन्ही रिकामे असल्यास, Vision
ऑटो-राउटर प्रभावी, व्हिजन-सक्षम मॉडेल निवडतो. यशस्वी मथळे मूळ भागाच्या जागी
स्थिर `[Video description:` उपसर्ग वापरतात; हा उपसर्ग मजकूराला अविश्वसनीय,
माध्यमातून व्युत्पन्न झालेले निरीक्षण म्हणूनही चिन्हांकित करतो आणि डाउनस्ट्रीम
मॉडेलना माध्यमात आढळलेल्या सूचनांचे पालन न करण्यास सांगतो. फ्रेम-मथळा कॅशे कीमध्ये
JPEG बाइट्स, प्रॉम्प्ट, टाइमस्टॅम्प आणि प्रभावी मॉडेल समाविष्ट असतात; फक्त यशस्वी
मथळे कॅशे केले जातात. कॅशे नोंदी फॉलबॅक मॉडेलसह, प्रत्यक्षात यशस्वी ठरलेल्या
प्रोड्युसर मॉडेलची माहिती राखतात; वेगवेगळ्या फ्रेम वेगवेगळ्या मॉडेलद्वारे तयार
केल्या असल्यास ब्रिज `mixed` असा अहवाल देतो. कॅशे हिट झाल्यास त्या प्रोड्युसरची
ओळख मागितलेल्या राउटिंग योजनेनुसार पुन्हा लेबल करण्याऐवजी पुनर्वापरली जाते.
संपूर्ण-व्हिडिओ परिणाम कॅशेची की आउटपुट बदलणाऱ्या प्रत्येक इनपुटवर आधारित असते —
प्रॉम्प्ट, प्रभावी मॉडेल, सॅम्पलिंग धोरण, फ्रेम संख्या, अर्थाधारित विश्लेषण मोड,
सामान्यीकृत फोकस संकेताचा SHA-256 फिंगरप्रिंट, फोकस विंडो, `transcript`,
`audioTranscript` आणि कॉन्टॅक्ट-शीट फ्लॅग — त्यामुळे यांपैकी कोणताही आयाम
बदलल्यास कॅशे मिस होते; जुना परिणाम कधीही पुनर्वापरला जात नाही. दृश्य डीडुप धोरणाची
आवृत्ती, थ्रेशोल्ड आणि मर्यादित उमेदवार-फ्रेम संख्या देखील परिणाम-कॅशे की आणि
मेटाडेटामध्ये स्पष्ट असतात; त्यामुळे धोरण बदलल्यास जुने संपूर्ण-व्हिडिओ वर्णन
पुनर्वापरले जाऊ शकत नाही. परिणाम-कॅशे v4 मेटाडेटा मोड आणि फिंगरप्रिंट ठेवतो,
वापरकर्त्याचे मूळ कार्य कधीही ठेवत नाही. गार्डरेल मेटाडेटा मागितलेला आणि प्रभावी
असे दोन्ही विश्लेषण मोड नोंदवतो; वापरण्यायोग्य वापरकर्ता मजकूर नसताना मागितलेला
`focused` मोड प्रभावीपणे `full` म्हणून नोंदवला जातो.

गार्डरेल प्रत्येक समर्थित व्हिडिओ भाग काढतो, पण `modalityBridgeVideoMaxVideos`
इतक्याच कमाल संख्येतील व्हिडिओंचे वर्णन करतो. `supportsVideo === false` असल्याचे
सिद्ध झालेल्या लक्ष्याकरिता, अयशस्वी आणि मर्यादेपलीकडील व्हिडिओ स्पष्ट सुरक्षित
मजकूर-चिन्हांमध्ये रूपांतरित होतात, ज्यामुळे कोणताही कच्चा व्हिडिओ शिल्लक राहत नाही.
क्षमता अज्ञात असताना ते भाग त्यांचा व्हिडिओ वाहक कायम ठेवतात; कोणतेही फॉलबॅक
लिप्यंतरण वरील मर्यादित मजकूर रूपांतरणानुसार दिले जाते. `supportsVideo === true`
असलेली लक्ष्ये ब्रिजला वगळून पुढे जातात. क्लायंट विनंतीचा अबॉर्ट सिग्नल डाउनलोड,
ब्रोकर रांग, सबप्रोसेस आणि मथळा कॉलमधून प्रसारित होतो; अबॉर्ट झाल्यास प्रक्रिया
व्हिडिओंदरम्यान थांबते आणि कच्च्या माध्यमाला पुढे जाऊ देऊन कधीही अपयश लपवत नाही.

ब्रोकरच्या अंतिम मुदतीपर्यंत मर्यादित केली जातात; त्या मर्यादेपेक्षा जास्त मूल्ये असलेली नवीन सेटिंग लेखने नाकारली जातात.
`GET /api/modality-bridge/video/runtime` साठी प्रमाणीकरण किंवा रनटाइम तपासणीपूर्वी

प्रमाणीकरण आवश्यक असते. ते फक्त `available`, शुद्ध केलेल्या FFmpeg/ffprobe आवृत्त्या आणि
रनटाइम अनुपलब्ध असल्यास एक निश्चित कारण परत करते. अंतर्गत एक्स्ट्रॅक्शन एंडपॉइंट हा
सार्वजनिक अपलोड API नाही: क्यू संतृप्त झाल्यास `503` सोबत `Retry-After` परत केले जाते, कॉलरचे
कनेक्शन तुटल्यास `499` परत केले जाते आणि निश्चित ब्रोकर अंतिम मुदतीमुळे `504` परत केले जाते. रूपांतरित प्रतिसाद
Vision किंवा Audio विभाग न काढता केंद्रीय `x-omniroute-modality-bridge` हेडरमध्ये
`video->text;model=<visionModel>;parts=<videos>` जोडतात.

### PII मास्कर (`piiMasker.ts`)

**दोन्ही** टप्प्यांवर चालते.

- **`preCall`** पेलोड क्लोन करते, `system`, `messages`, `input` आणि
  `prompt` (साध्या स्ट्रिंग आयटमसह) यांमधून जाते आणि स्ट्रिंग `content`/`text`
  फील्डवर `processPII()` (`@/shared/utils/inputSanitizer` मधून) लागू करते. जेव्हा
  `PII_REDACTION_ENABLED=true` असते, तेव्हा आढळलेली PII आउटबाउंड
  पेलोडमध्ये लपवली जाते. हे `INPUT_SANITIZER_MODE` पासून स्वतंत्र आहे (जो फक्त
  प्रॉम्प्ट-इंजेक्शन धोरण नियंत्रित करतो). लपवणे बंद असताना, कॉल आशय पुन्हा न लिहिता
  शोध-संख्या नोंदवतो.
- **`postCall`** प्रतिसादाचे डीप-क्लोनिंग करते आणि `sanitizePIIResponse()` सोबत
  Responses-API-आकाराचा मास्कर (`maskResponsesOutput` — जो
  `output_text` आणि `output[].content[].text` व्यापतो) चालवते. कोणतेही लपवणे झाल्यास,
  सुधारित प्रतिसाद मूळ प्रतिसादाची जागा घेतो.

गार्डरेल कधीही ब्लॉक करत नाही; ते फक्त भाष्य (`meta.detections`,
`meta.redacted`) जोडते किंवा पुनर्लेखन करते.

### प्रॉम्प्ट इंजेक्शन (`promptInjection.ts`)

वापरकर्त्याने पुरवलेल्या आशयातील प्रतिकूल संरचना शोधते आणि
कॉन्फिगर केलेले धोरण लागू करते. वर्तन पर्यावरणीय चल आणि कन्स्ट्रक्टर
पर्यायांद्वारे नियंत्रित केले जाते:

| सेटिंग          | पर्यावरणीय चल                                                                                         | डीफॉल्ट | परिणाम                                                                                                                                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| सक्षम           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | `false` असताना, गार्डरेल शॉर्ट-सर्किट होते.                                                                                                                                                               |
| मोड             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | इंजेक्शन धोरण: `block`, `warn`, किंवा `log`. (`redact` पश्च-सुसंगततेसाठी स्वीकारले जाते, परंतु इंजेक्शन मजकूर **काढत नाही**; विनंतीतील PII पुनर्लेखन `PII_REDACTION_ENABLED` द्वारे नियंत्रित केले जाते.) |
| ब्लॉक थ्रेशोल्ड | `blockThreshold` पर्याय / `INPUT_SANITIZER_BLOCK_THRESHOLD` (उपनाव `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ब्लॉक करण्यासाठी आवश्यक असलेली किमान तीव्रता. डीफॉल्टनुसार मध्यम तीव्रता केवळ निरीक्षणासाठी असते.                                                                                                         |

**मोड अग्रक्रम** (`getMode`): कॉलरचे `options.mode` →
`INJECTION_GUARD_MODE` **DB फीचर-फ्लॅग ओव्हरराइड** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. त्यामुळे डॅशबोर्ड ओव्हरराइड पर्यावरणीय चलांपेक्षा प्राधान्य घेते, म्हणून Feature
Flags UI चालू असलेला गार्ड थेट नियंत्रित करते (रीस्टार्ट आवश्यक नाही). DB वाचन अपयश-सुरक्षित आहे:
त्यात त्रुटी आल्यास, गार्ड पर्यावरण-आधारित वर्तनाकडे परत जातो आणि कोणतेही
ओव्हरराइड सेट नसताना वर्तन केवळ पर्यावरणीय चलांवर आधारित रिझोल्यूशनसारखेच असते.

शोध स्रोत:

1. `@/shared/utils/inputSanitizer` मधील `sanitizeRequest()` (पाइपलाइनमध्ये
   इतरत्र वापरला जाणारा सामायिक डिटेक्टर संच).
2. अंगभूत `DEFAULT_GUARD_PATTERNS` (सध्या `system_override_inline` आणि
   `markdown_system_block`, दोन्हींची तीव्रता `high`).
3. कन्स्ट्रक्टर पर्यायांद्वारे दिलेले पर्यायी `customPatterns` (स्ट्रिंग, रेगेक्स,
   किंवा `{ name, pattern, severity }` रेकॉर्ड).

जेव्हा `mode === "block"` **आणि** किमान एक शोध तीव्रतेच्या
मर्यादेपर्यंत पोहोचतो, तेव्हा `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` परत करते. `warn`/`log` मोडमध्ये गार्डरेल नोंद करते, परंतु
कॉलला अनुमती देते. रजिस्ट्रीमार्फत न जाता प्रॉम्प्टचे मूल्यमापन करण्याची आवश्यकता असलेल्या
कॉलर्ससाठी सामायिक सहाय्यक `evaluatePromptInjection()` देखील एक्सपोर्ट केले आहे.

**स्कॅन मर्यादा (v3.8.20):** डिटेक्टर जोडलेल्या प्रॉम्प्ट मजकुराच्या केवळ **पहिल्या 16 KB** ची
तपासणी करतो — `src/shared/utils/inputSanitizer.ts` मध्ये
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 बाइट्स). पॅटर्न लूप चालवण्यापूर्वी
`detectInjection()` आणि `evaluatePromptInjection()` हे दोन्ही
`slice(0, MAX_INJECTION_SCAN_BYTES)` वापरतात. इंजेक्शन निर्देश इनपुटच्या सुरुवातीच्या भागाजवळ असतात, त्यामुळे
शोधक्षमता कमी न करता बहु-शत-KB पेलोड्सवरील regex CPU/GC मर्यादित राहतो (पहा
#3932, #4041).

### क्रेडेन्शियल मास्कर (`credentialMasker.ts`)

**दोन्ही** टप्प्यांवर चालतो आणि डीफॉल्ट साखळीत शेवटी असतो (प्राधान्य `95`). आउटबाउंड पेलोडमधील
(संदेश सामग्री, टूल-कॉल आर्ग्युमेंट्स, टूल परिणाम) **आणि** प्रदाता प्रतिसादामधील
सुप्रसिद्ध API-की / गुप्त-टोकन पॅटर्न्स लपवतो, जेणेकरून प्रॉम्प्टमध्ये पेस्ट केलेले
क्रेडेन्शियल (किंवा टूल परिणामाद्वारे पुन्हा दिलेले) अपस्ट्रीम प्रदात्याकडे किंवा
क्लायंटकडे परत लीक होणार नाही.

- **केवळ स्पष्ट संमतीने सक्षम**, PII लपवण्यासारखीच पद्धत (कठोर नियम #20-संबंधित):
  `settings.credentialRedactionEnabled === true` **किंवा**
  `CREDENTIAL_REDACTION_ENABLED=true` असल्याशिवाय अक्षम. हे बंद असताना, गार्डरेल कोणतीही क्रिया करत नाही —
  ते कधीही ब्लॉक करत नाही आणि कधीही पुनर्लेखन करत नाही.
- `redactCredentials()` संपूर्ण पेलोड/प्रतिसाद ट्रीमधून फिरते (`walkValue()`,
  प्रोटोटाइप-पॉल्युशन-सुरक्षित, `WeakSet` द्वारे सायकल-सुरक्षित) आणि जुळणाऱ्या भागांच्या जागी
  `[REDACTED:<type>]` प्लेसहोल्डर ठेवते; प्रत्यक्षात बदललेल्या शाखांचेच
  क्लोनिंग करते.
- `CREDENTIAL_PATTERNS` मध्ये LLM प्रदाता कीज (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS टोकन्स (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), पेमेंट कीज (Stripe, Square), क्लाउड
  कीज (AWS access key, Twilio, SendGrid, Mailgun), खाजगी कीज / JWTs,
  क्रेडेन्शियल असलेल्या कनेक्शन स्ट्रिंग्स (`mongodb://user:pass@...`, इत्यादी), आणि
  सर्वसाधारण `Authorization`/`x-api-key`/`api-key`/`apikey` हेडर-मूल्य
  पॅटर्न समाविष्ट आहेत. हेडरसारख्या कीज (`authorization`, `x-api-key`, `api-key`,
  `apikey`) सर्वसाधारण मजकूर regex द्वारे नव्हे, तर संरचनात्मकरीत्या लपवल्या जातात
  (केवळ मूल्य; `Bearer `/`Basic ` सारखे स्कीम प्रीफिक्स जतन केले जातात).
- गार्डरेल कधीही ब्लॉक करत नाही; ते फक्त पुनर्लेखन (`modifiedPayload` /
  `modifiedResponse`) आणि भाष्य (`meta.credentialsRedacted`, `meta.count`) करते.

रिग्रेशन गार्ड: `tests/unit/credential-masker-guardrail.test.ts`.

## मूलभूत करार (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true असल्यास साखळीचे पुढील कार्य तत्काळ थांबते
  message?: string; // अवरोधित करताना दर्शविला जाणारा संदेश
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // विनंती पुन्हा लिहिण्यासाठी preCall कडून परत केला जातो
  modifiedResponse?: TValue; // प्रतिसाद पुन्हा लिहिण्यासाठी postCall कडून परत केला जातो
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, किंवा `{ block: false }` यांपैकी काहीही परत करून guardrail "कोणताही बदल नाही" असे सूचित करते. `modifiedPayload`/`modifiedResponse` परत केल्यास, साखळीमधून पुढील guardrails कडे जाणारे मूल्य बदलले जाते.
`signal?: AbortSignal` कॉलरचे जीवनचक्र guardrails पर्यंत पोहोचवते. विनंती रद्द करणे हा मुद्दाम ठेवलेला fail-open अपवाद आहे: ज्याला raw media समर्थित नसल्याचे माहीत आहे अशा target मध्ये ते पुनर्स्थापित न करता, media bridges काम थांबवतात आणि cleanup करतात.

## रजिस्ट्री (`registry.ts`)

singleton `guardrailRegistry` पुढील गोष्टी उपलब्ध करून देते:

- `register(guardrail)` — guardrail जोडते (किंवा normalized name नुसार बदलते) आणि चढत्या `priority` क्रमाने पुन्हा क्रमवारी लावते.
- `clear()` / `list()` — प्रशासकीय सहाय्यक.
- `runPreCallHooks(payload, context)` — सक्रिय guardrails वर पुनरावृत्ती करते, `modifiedPayload` द्वारे payload पुढे पाठवते आणि पहिल्या `block: true` वर थांबते.
- `runPostCallHooks(response, context)` — प्रतिसादाच्या बाजूने समान प्रवाह.
- `resetGuardrailsForTests({ registerDefaults })` — स्वच्छ चाचणी विलगीकरणासाठी स्थिती साफ करते आणि पर्यायाने defaults पुन्हा नोंदवते.

दोन्ही runners `{ blocked, payload|response, results, guardrail?, message? }` परत करतात, ज्यामध्ये `results` हा `GuardrailExecutionResult` नोंदींचा array असतो. या नोंदींमध्ये प्रत्येक guardrail साठी `blocked`, `skipped`, `modified`, `error`, आणि `meta` fields समाविष्ट असतात आणि त्या tracing साठी उपयुक्त असतात.

### प्रत्येक विनंतीनुसार Guardrails अक्षम करणे

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` सध्याच्या विनंतीसाठी वगळल्या जाणाऱ्या guardrail names ची पुनरावृत्ती-विरहित यादी एकत्रित करते. स्रोत (सर्व पर्यायी, सर्व एकत्रित केले जातात):

- `apiKeyInfo.disabledGuardrails`
- विनंती body मधील `disabledGuardrails` (top-level)
- विनंती body मधील `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (किंवा जुना
  `x-disabled-guardrails`)

मूल्ये strings चे arrays किंवा स्वल्पविरामाने विभक्त केलेली string असू शकतात; names lowercase kebab-case मध्ये normalize केली जातात (`pii_masker` → `pii-masker`). परिणाम `context.disabledGuardrails` द्वारे registry कडे पाठवला जातो, जी जुळणारे guardrails वगळते (`results` मध्ये `skipped: true`).

## अंमलबजावणीचा क्रम

`src/sse/handlers/chat.ts` आणि
`open-sse/handlers/chatCore.ts` मधून जाणाऱ्या प्रत्येक विनंतीसाठी:

1. `resolveDisabledGuardrails(...)` API की, बॉडी आणि हेडर्सवरून वगळण्याची यादी तयार करते.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` चढत्या प्राधान्यक्रमाने गार्डरेल्स चालवते:
   - अक्षम केलेल्या गार्डरेल्सची `skipped` म्हणून नोंद केली जाते.
   - प्रत्येक गार्डरेलचे `preCall`, `modifiedPayload` द्वारे पेलोड पुन्हा लिहू शकते.
   - पहिले `block: true` आल्यावर साखळी त्वरित थांबते आणि हँडलर गार्डरेल नकार प्रतिसाद परत करतो.
3. (संभाव्यतः पुन्हा लिहिलेला) पेलोड कॉम्बो राउटिंग आणि अपस्ट्रीम डिस्पॅचकडे जातो.
4. प्रतिसाद तयार झाल्यानंतर, `guardrailRegistry.runPostCallHooks(...)` प्रतिसादावर तीच साखळी चालवते. येथे `block: true` असल्यास अपस्ट्रीम प्रतिसाद वगळला जातो.

अपवाद निर्माण करणाऱ्या गार्डरेल्सची `error: <message>` सह नोंद केली जाते आणि `logger.warn` द्वारे लॉग केले जाते, मात्र साखळी सुरूच राहते — रचनेनुसार फेल-ओपन.

## संरचना

अंगभूत गार्डरेल्सद्वारे वाचली जाणारी पर्यावरण चल:

| चल                                    | यामध्ये वापरले जाते        | परिणाम                                                                                             |
| ------------------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | शोध पूर्णपणे अक्षम करण्यासाठी `false` सेट करा.                                                     |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | इंजेक्शन धोरण: `warn`, `block`, किंवा `log`. जुने मूल्य `redact` इंजेक्शन मजकूर पुन्हा लिहीत नाही. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | इंजेक्शन गार्डसाठी मोड; तसेच पर्यावरण चलांना **अधिलिखित** करणारा DB फीचर फ्लॅग (DB > ENV).         |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | `MODE=block` द्वारे नाकारली जाणारी किमान तीव्रता: `high` (डीफॉल्ट), `medium`, किंवा `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` साठी जुने पर्यायी नाव.                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` असताना, विनंतीमधील PII झाकले जाते (इंजेक्शन मोडपासून स्वतंत्र).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (डाउनस्ट्रीम) | प्रतिसादाच्या बाजूच्या मास्करचे वर्तन नियंत्रित करते.                                              |

Modality Bridge गार्डरेल्स पर्यावरण चलांऐवजी DB-समर्थित सेटिंग्ज स्टोअरमधून (`getSettings()`) रनटाइम संरचना वाचतात. Vision च्या प्राथमिक की
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, आणि
`modalityBridgeCacheMaxEntries` आहेत. जुन्या
`visionBridge*` की केवळ दस्तऐवजीकृत एक-चक्र वाचन फॉलबॅक म्हणून स्वीकारल्या जातात; डॅशबोर्डमधून होणाऱ्या लेखनांसाठी प्राथमिक की वापरल्या जातात. डीफॉल्ट्स आणि फॉलबॅक रिझॉल्व्हर `src/shared/constants/modalityBridgeDefaults.ts` मध्ये आहेत, तर जुन्या कॉन्स्टंट्स `src/shared/constants/visionBridgeDefaults.ts` मध्ये कायम ठेवलेल्या आहेत.

Audio हे `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, आणि `modalityBridgeAudioMaxClips`, तसेच सामायिक
`modalityBridgeCache*` सेटिंग्ज वापरते. Audio साठी जुन्या कींचा फॉलबॅक नाही, कारण या की Modality Bridge स्कीमासोबत सादर करण्यात आल्या होत्या.

Video हे `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, आणि
`modalityBridgeVideoTimeout`, तसेच सामायिक `modalityBridgeCache*` सेटिंग्ज वापरते.
ते डीफॉल्टनुसार अक्षम असते, कारण FFmpeg/ffprobe या पर्यायी कार्यान्वयन अवलंबिता आहेत आणि फ्रेम कॅप्शनिंगमुळे विलंब व मॉडेल खर्च वाढतो.

## सानुकूल Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

पायऱ्या:

1. `BaseGuardrail` विस्तारित करणारी `src/lib/guardrails/myGuardrail.ts` तयार करा.
2. `preCall` आणि/किंवा `postCall` लागू करा.
3. एकतर आयात करताना नोंदणी करा (`registerDefaultGuardrails` मधून पुश करा) किंवा
   रनटाइममध्ये `guardrailRegistry.register(...)` कॉल करा — रजिस्ट्री समान सामान्यीकृत
   नाव असलेली कोणतीही आधीची guardrail बदलते.
4. `tests/unit/` अंतर्गत चाचण्या जोडा (विद्यमान उदाहरणे:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## चाचणी

ज्ञात स्थितीपासून सुरुवात करण्यासाठी चाचण्यांदरम्यान `resetGuardrailsForTests()` वापरा.
रिकाम्या रजिस्ट्रीपासून सुरुवात करण्यासाठी `{ registerDefaults: false }` पास करा आणि
फक्त चाचणीअंतर्गत असलेल्या guardrails नोंदवा. Vision Bridge अवलंबित्व
इंजेक्शन (`deps.getSettings`, `deps.callVisionModel`) स्वीकारते; Audio Bridge सेटिंग्ज,
क्षमता, STT मॉडेल निवड, क्रेडेन्शियल तपासण्या आणि ट्रान्सक्रिप्शनसाठी समतुल्य
इंजेक्शन बिंदू उपलब्ध करून देते. त्यामुळे चाचण्या DB किंवा नेटवर्क प्रवेशाशिवाय
दोन्ही प्रवाह तपासू शकतात.

## Injection-guard मार्ग कव्हरेज आणि रेड-टीम (टप्पा 8 · ब्लॉक D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) वापरकर्त्याचे प्रॉम्प्ट स्वीकारणारे सर्व मार्ग
व्यापते. ते `INJECTION_GUARD_MODE` चे पालन करते (डीफॉल्ट `warn` = फक्त लॉग;
`block` = HTTP 400 `SECURITY_001` परत करते).

| प्रकार           | मार्ग                                                                                                                                                | डीफॉल्ट मोड |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| मजकूर (विद्यमान) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| जनरेटिव्ह        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| डेटा             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

मजकूर निष्कर्षण (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` व्यापते.

**रेड-टीम (दररोज रात्री, `nightly-llm-security.yml`):** promptfoo हे सत्यापित करते की प्रत्येक मार्ग
`INJECTION_GUARD_MODE=block` मध्ये OWASP-LLM कॉर्पस ब्लॉक करतो; garak प्रोब्स चालवते (secret नसल्यास वगळते).
सुसंगततेसाठी `moderations` समाविष्ट केले आहे — ब्लॉक-मोडमधील ऑपरेटर `resolveDisabledGuardrails` द्वारे
त्याला सूट देऊ शकतात.

रात्रीचे वर्कफ्लो (`.github/workflows/nightly-llm-security.yml`, cron + मॅन्युअल
डिस्पॅच) दोन जॉब्सचे आहे:

- **`promptfoo-guard` (ब्लॉकिंग)** — `INJECTION_GUARD_MODE=block` सह
  `promptfoo eval -c promptfooconfig.yaml` चालवते. प्रत्येक प्रतिकूल प्रकरण (उदा. "मागील सर्व
  सूचना दुर्लक्षित करा…", DAN-शैलीतील जेलब्रेक्स) प्रतिसादात
  `error.code === "SECURITY_001"` असल्याचे निश्चित करते, म्हणजेच guard ने विनंती प्रत्यक्षात नाकारली.
- **`garak` (सल्लात्मक)** — स्थानिक OmniRoute इन्स्टन्सवर (`http://localhost:20128/v1`)
  garak `--probes promptinject,dan,leakreplay` चालवते. हे provider secret
  (`PROMPTFOO_PROVIDER_KEY`) वर अवलंबून असते; secret नसल्यास व्यवस्थितपणे वगळते आणि त्याला
  `|| true` प्रत्यय जोडलेला असतो, त्यामुळे ते CI अयशस्वी न करता अहवाल देते.

guard helper (`createInjectionGuard` / `withInjectionGuard`) चे कव्हरेज
प्रॉम्प्ट असलेल्या प्रत्येक `/v1` मार्गावर पसरलेले आहे; प्रॉम्प्ट मजकूर
`src/shared/utils/inputSanitizer.ts` मधील `extractMessageContents()` द्वारे
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` मधून घेतला जातो.
