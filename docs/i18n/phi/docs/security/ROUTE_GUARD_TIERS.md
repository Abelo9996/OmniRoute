## Pangkalahatang-ideya

Ang lahat ng ruta ng API sa pamamahala ng OmniRoute ay inuuri sa isa sa tatlong antas ng
proteksiyon. Hindi nagbabago ang pag-uuri, tinutukoy ito sa `src/server/authz/routeGuard.ts`,
at sinusuri bago tumakbo ang anumang iba pang sangay ng awtentikasyon.

## Mga Tier

### Tier 1 — LOCAL_ONLY

**Ipinapatupad ng:** `isLocalOnlyPath(path)` → pagsusuri sa loopback host
**Pag-bypass:** Wala bilang default. May limitadong eksepsiyon para sa mga path sa
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` kapag may wastong API key ang request
na may saklaw na `manage` (tingnan ang [Eksepsiyon para sa manage scope](#manage-scope-carve-out)).

Ang mga rutang ito ay naglulunsad ng mga child process o nagpapatakbo ng runtime code. Ang paglalantad sa mga ito sa
trapikong hindi loopback ay magbibigay-daan sa isang attacker na nakakuha ng wastong JWT (hal.,
sa pamamagitan ng Cloudflared/Ngrok tunnel) na makapagsimula ng paglulunsad ng process — isang kilalang klase ng
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Ano ang GHSA-fhh6-4qxv-rpqj (ang klase ng pag-atake):** ang isang management/agent server
ay naglalantad ng endpoint na naglulunsad ng subprocess (`npm install`, `node`, isang browser,
isang proxy, `git`, `tar`, …). Kung maa-access ang endpoint na iyon mula sa labas ng host — dahil
inilagay ng operator ang OmniRoute sa likod ng isang nginx/Cloudflare/Tailscale tunnel at may
na-leak na JWT, o maling na-configure ang auth — nagagawa ng attacker na gawing "mag-call ng API" ang "magpatakbo ng
command sa host" (remote code execution). Isinasara ito ng OmniRoute sa pamamagitan ng walang-kondisyong pagpapatupad ng
**pagsusuri sa loopback host bago ang anumang pagsusuri sa auth**, sa bawat
rutang may kakayahang mag-spawn: kahit ang na-leak na token sa pamamagitan ng tunnel ay hindi pa rin makakarating sa spawn.

**Ang kumpletong hanay ng LOCAL_ONLY.** Ang awtoritatibong source ay
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` sa
`src/server/authz/routeGuard.ts`; ipinapakita ng talahanayan sa ibaba ang kasalukuyang estado. Inililista ng
`check-route-guard-membership` gate ang bawat `route.ts` sa ilalim ng mga
prefix na may kakayahang mag-spawn at ibinabagsak ang CI kung may alinmang hindi nauuri bilang local-only.

#### Eksepsyon para sa manage scope

MAAARING ma-access din mula sa non-loopback ang isang subset ng mga LOCAL_ONLY path kung at
tanging kung may dalang `Authorization: Bearer <api-key>` ang request na ang
metadata ay may kasamang `manage` scope (o `admin`). Tahasang nililimitahan
ang eksepsyon sa bawat path sa pamamagitan ng `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` upang
manatiling strict-loopback ang default para sa anumang bagong LOCAL_ONLY path. Ang mga hindi authenticated na
request at mga request na gumagamit ng mga key na walang manage scope ay tinatanggihan pa rin gamit ang
`403 LOCAL_ONLY`.

Sa kasalukuyan, ang tanging prefix na maaaring magkaroon ng eksepsyon ay `/api/mcp/`. Sadyang hindi kasama ang `/api/cli-tools/runtime/` at
`/api/services/` dahil maaari silang mag-spawn ng mga arbitraryong
subprocess (`npm install`, `node`), na siyang eksaktong uri ng CVE na
nilalayong pigilan ng LOCAL_ONLY tier.

**#7895 — makitid na scope ng `mcp:connect`:** tinatanggap DIN ng eksepsyon sa `/api/mcp/`
ang isang Bearer key na may makitid na `mcp:connect` scope
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), na sinusuri sa pamamagitan ng
`hasMcpConnectOrManageScope()` sa `src/server/authz/policies/management.ts`.
Saklaw nito ang `/api/mcp/` LAMANG — walang ibinibigay na pahintulot ang `mcp:connect` sa anumang iba pang
management route (kabilang ang lahat ng iba pang LOCAL_ONLY bypass prefix, kung sakaling
may maidagdag), at sadyang hindi ito kasama sa
`MANAGEMENT_API_KEY_SCOPES`. Ang key na may `manage`/`admin` ay papasa pa rin sa
eksepsyon gaya ng dati; ang `mcp:connect` ay isang alternatibong may mas mababang pribilehiyo
para sa mga remote na caller na MCP-only at hindi dapat mangailangan ng malawak na management access.

| Request                                               | Path                       | Resulta                  |
| ----------------------------------------------------- | -------------------------- | ------------------------ |
| Non-loopback, walang Bearer                           | `/api/mcp/*`               | 403 LOCAL_ONLY           |
| Non-loopback, Bearer na may `manage` scope            | `/api/mcp/*`               | Payagan                  |
| Non-loopback, Bearer na may `mcp:connect` scope       | `/api/mcp/*`               | Payagan                  |
| Non-loopback, Bearer na walang `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY           |
| Non-loopback, Bearer na may `mcp:connect` scope       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY           |
| Non-loopback, Bearer na may `manage` scope            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY           |
| Loopback, mayroon/walang Bearer                       | anumang LOCAL_ONLY         | Payagan (pumasa sa gate) |

#### Patnubay para sa operator at pag-audit

Kung pinapatakbo mo ang OmniRoute sa likod ng reverse proxy o tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), pinoprotektahan pa rin ng loopback check ang mga route sa itaas
na maaaring mag-spawn — ang request na may non-loopback na client address ay tinatanggihan gamit ang
`403 LOCAL_ONLY` **bago patakbuhin ang auth**, kaya hindi maaabot ng isang na-leak na JWT ang spawn. May natitira pang dalawang
responsibilidad ang operator:

- **Huwag "ayusin" ang isang 403 sa pamamagitan ng pagpapanggap na loopback ang IP ng client.** Ang pagtatakda ng
  `X-Forwarded-For: 127.0.0.1`, o paggamit ng proxy na muling nagsusulat sa source address bilang
  loopback, ay muling nagbubukas sa mismong klase ng RCE na isinasara ng tier na ito. Ilantad ang
  dashboard/API sa pamamagitan ng proxy — huwag kailanman ang mga rutang may kakayahang mag-spawn.
- **Panatilihing minimal ang bypass ng manage scope.** Tanging `/api/mcp/` ang maaaring i-bypass, at
  sa pamamagitan lamang ng API key na may `manage` scope. Ang `SPAWN_CAPABLE_PREFIXES` ay hindi kailanman
  maaaring idagdag sa listahan ng bypass — tinatanggihan ang mga ito ng zod schema at
  hindi pinahihintulutan ng `isLocalOnlyBypassableByManageScope` ang mga ito sa runtime (defence-in-depth),
  na siyang ibig sabihin ng dashboard sa "cannot be made bypassable". Kasama rin sa parehong
  deny-list ang ilang LOCAL_ONLY route na hindi nag-i-spawn ngunit hindi rin dapat kailanman
  maabot nang remote — `/api/oauth/kiro/auto-import` (nagbabasa ng mga credential file ng Kiro na lokal sa
  host), `/api/discovery/` at `/api/issue-agent/`. Inaalis din ng runtime
  snapshot loader ang gayong mga entry mula sa nakaimbak na settings row, at ang
  legacy JSON import (`/api/settings/import-json`) ay hindi kailanman nagsusulat ng mga bypass key.
  Ang bawat entry ng `LOCAL_ONLY_API_PREFIXES` ay dapat nasa deny-list o
  nasuri bilang karapat-dapat sa bypass (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Ang mga rutang may dynamic segment
  at static path na may kakayahang mag-spawn sa ilalim ng `/api/providers/` (hal. `/login`,
  `/refresh-cursor`) ay saklaw ng regex-based na katuwang na `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` sa
  `src/shared/constants/spawnCapablePrefixes.ts`, hindi ng flat na
  `SPAWN_CAPABLE_PREFIXES` array — kakailanganing saklawin ng flat array ang
  buong `/api/providers/` prefix upang mahuli ang mga ito, na labis na magpapalawak sa isang route tree
  na lehitimong ginagamit ng mga remote dashboard para sa CRUD ng provider.

**Pag-audit ng access** — upang tiyaking walang nagmumula sa labas ng host na nakaaabot sa mga rutang ito:

- Buksan ang **Authorization Inventory** sa `/dashboard/settings/security`: ipinapakita nito ang
  live na listahan ng LOCAL_ONLY prefix, kung aling mga prefix ang maaaring i-bypass, at ang compile-time na
  hanay na may kakayahang mag-spawn ("cannot be made bypassable").
- I-grep ang inyong reverse-proxy / access logs para sa mga prefix sa itaas na ipinares sa isang
  client address na hindi loopback. Ang anumang ganitong hit na nagbalik ng `200` sa halip na
  `403 LOCAL_ONLY` ay nangangahulugang itinatago ng proxy ang tunay na client IP — ayusin ang proxy.
- Ang `403 LOCAL_ONLY` sa mga log ng OmniRoute para sa isa sa mga path na ito ay nangangahulugang
  gumagana ang guard ayon sa nilalayon, hindi ito isang error na dapat pigilan.

### Tier 2 — ALWAYS_PROTECTED

**Ipinapatupad ng:** `isAlwaysProtectedPath(path)` → laktawan ang bypass na `requireLogin=false`
**Bypass:** Wala kapag `requireLogin=false`; palaging kinakailangan ang JWT

Mapanira o hindi na mababawi ang mga rutang ito. Kung pahihintulutan ang mga ito sa isang installation na "walang password",
magagawa ng sinuman sa parehong LAN na burahin ang database o patayin ang
proseso ng server.

| Path                                      | Dahilan                                                          |
| ----------------------------------------- | ---------------------------------------------------------------- |
| `/api/shutdown`                           | Tinatapos ang proseso ng server                                  |
| `/api/settings/database`                  | Pag-export, pag-import, at pagbura ng database                   |
| `/api/db-backups`                         | Access sa buong archive ng backup ng database                    |
| `/api/settings/export-json`               | Ine-export ang buong settings blob (kabilang ang mga secret)     |
| `/api/settings/import-json`               | Pinapalitan ang buong settings blob                              |
| `/api/providers/health-autopilot/actions` | Isinasagawa ang mga remediation action ng autopilot              |
| `/api/settings/obsidian`                  | Lumilikha ng reusable na WebDAV creds para sa anumang vault root |

**Tugon sa paglabag:** `401 Authentication required`

Saklaw ng `/api/settings/obsidian` ang child nitong `/webdav`: itinuturo ng `POST` ang WebDAV file service —
na sineserbisyuhan ng custom na Node layer bago ang Next.js, sa labas ng pipeline na ito — sa root na pinili
ng caller at ibinabalik ang bagong likhang Basic credentials, iniikot ng `DELETE` ang mga ito, at iniimbak
ng parent na `POST` ang Obsidian REST API token. Itinago lamang ng GHSA-62vw ang pagsisiwalat ng password sa `GET`;
nasa fail-open tier pa rin ang pag-isyu (GHSA-7pq4-8pvv-rx7r). Bukod dito,
tinatanggihan ng `enableObsidianVaultSync()` ang vault na siya mismo ang data directory, nasa loob nito,
o naglalaman nito.

#### Para lamang sa operator ang mga pag-export ng credential

Tinutukoy lamang ng tier sa itaas kung kinakailangan ang _anumang_ credential. Nagdaragdag ang mga rutang
nagda-download ng mga nakaimbak na credential ng pangalawang pagsusuri sa handler: tinatawag ng `GET /api/settings/export-json` (mga na-decrypt
na koneksyon ng provider at mga raw API key), `GET /api/db-backups/export` (ang SQLite file), at
`GET /api/db-backups/exportAll` (ang buong archive) ang `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Tinatanggap nito ang isang dashboard session, ang lokal na CLI subject, o
isang instance na naka-disable ang login, at tumutugon ng `403` sa mga API key ng anumang scope (kabilang ang `manage`
at `admin`) at sa mga `oma_` access token. Ginagamit ng pag-isyu ng sync token (`POST /api/sync/tokens`) ang
parehong helper, kasama ang pinagkakatiwalaang internal-service token sa loopback.

### Loopback-only ang bootstrap ng bagong installation — ayon sa tunay na peer, hindi sa `Host`

Kapag walang naka-configure na management password (at walang `INITIAL_PASSWORD`), pinananatili ng `isAuthRequired()` sa
`src/shared/utils/apiAuth.ts` na bukas ang anonymous bootstrap **para lamang sa mga loopback peer**.
Tinutukoy ang loopback mula sa mga pinagkakatiwalaang peer signal, ayon sa pagkakasunod-sunod: ang real TCP peer na nilagyan
ng token stamp (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, na siyang nakikita ng policy), ang sariling
`AUTHZ_HEADER_PEER_LOCALITY` verdict ng pipeline (na siyang nakikita ng mga route handler, pinagkakatiwalaan lamang habang
nakatakda ang `OMNIROUTE_PEER_STAMP_TOKEN`), o isang tunay na socket peer para sa mga direktang caller. Ang `Host` /
`nextUrl.hostname` ay hindi kailanman sinusuri, at ang pagsusulat ng unang password
(`POST /api/settings/require-login`) ay nasa ilalim ng parehong limitasyon sa halip na bukas sa bawat
network peer (GHSA-7pq4-8pvv-rx7r). Tahasang ipinapasa ng `managementPolicy` ang sarili nitong `peerContext` verdict
pababa, kaya hindi kailanman ito tinutukoy ng mga header ng ORIGINAL (bago i-strip) na request.

### Tier 3 — MANAGEMENT (default)

Lahat ng iba pang ruta ng pamamahala. Kinakailangan ang pagpapatotoo maliban kung naka-configure ang `requireLogin=false`. Maaaring gamitin ang mga CLI token upang magpatotoo sa mga rutang ito (loopback + wastong HMAC).

## Pagkakasunod-sunod ng pagsusuri

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → magpatuloy
     → non-loopback, manage-scope Bearer
        AT isLocalOnlyBypassableByManageScope    → payagan (management_key)
     → kung hindi                                → tanggihan 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → payagan (system)
  3. hasValidCliToken(headers)?
     → payagan (cli) [loopback + pagsusuri ng HMAC gamit ang timingSafeEqual]
  4. isAlwaysProtectedPath(path) o requireLogin=true?
     → isDashboardSessionAuthenticated?
        → payagan (dashboard_session)
     → manage-scope Bearer sa isang non-bypassable na path?
        → payagan (management_key)
     → tanggihan 401/403
  5. requireLogin=false?
     → payagan (anonymous)
```

Ang sangay na manage-scope sa Hakbang 1 ang tanging authenticated na path na maaaring tumugon sa isang
LOCAL_ONLY na route; nagbabalik ng 503 (hindi 403) ang failure mode ng auth-backend upang hindi
tahimik na bumaba sa "deny" ang isang expired na DB.

## Pagdaragdag ng bagong route na maaaring mag-spawn

1. Idagdag ang path prefix sa `LOCAL_ONLY_API_PREFIXES` sa
   `src/server/authz/routeGuard.ts`
2. Magdagdag ng test sa `tests/unit/authz/routeGuard.test.ts` na nagpapatunay na
   nagbabalik ng true ang `isLocalOnlyPath()` para sa bagong prefix
3. **Huwag kailanman laktawan ang hakbang na ito** — tingnan ang Mahigpit na Panuntunan #15 sa `CLAUDE.md`
4. Magpasya: kabilang DIN ba ang route na ito sa `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Ang default na sagot ay **hindi**. Mag-opt in lamang kapag ligtas na ilantad ang route sa isang
   may hawak ng manage-scope (ibig sabihin, HINDI ito nag-i-spawn ng arbitraryong code na kontrolado ng user).

## Pagdaragdag ng path na maaaring i-bypass ng manage-scope

1. Kumpirmahing hindi nagpapatupad ang route ng code o command na ibinigay ng user. Kung
   nagpapatupad ito, huminto — hindi tamang kasangkapan ang pagbubukod na ito.
2. Idagdag ang prefix sa `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` sa
   `src/server/authz/routeGuard.ts`
3. Magdagdag ng coverage sa `tests/unit/authz/management-policy.test.ts` para sa lahat ng apat na
   anyo ng request: walang Bearer (403), manage Bearer (payagan), non-manage Bearer
   (403), at ang regression sa bawat prefix na tinitiyak na nananatiling
   strict-loopback ang `/api/cli-tools/runtime/*` kahit may manage Bearer.

## Pagdodokumento ng mga Security Tier sa OpenAPI

Kapag nagdaragdag ng bagong route sa `docs/openapi.yaml`, ilapat ang kaukulang
vendor extension kung inuri ng `routeGuard.ts` ang route:

| Klasipikasyon sa routeGuard.ts      | YAML annotation                  | Pagpapatupad                                          |
| ----------------------------------- | -------------------------------- | ----------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`           | `x-loopback-only: true`          | Walang kondisyong bina-block mula sa non-loopback     |
| `ALWAYS_PROTECTED_API_PATHS`        | `x-always-protected: true`       | Kinakailangan ang auth kahit may `requireLogin=false` |
| Internal na admin/debug route       | `x-internal: true`               | Nakatago sa /dashboard/api-endpoints bilang default   |
| Wala (pampubliko / karaniwang auth) | (walang annotation na kailangan) | Karaniwang access na kinokontrol ng `requireLogin`    |

### Pagpapatunay

Dalawang script ang nagpapatupad ng pagkakapare-pareho sa pagitan ng mga YAML annotation at `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — mabibigo kung < 99% ang coverage
- `scripts/check/check-openapi-security-tiers.mjs` — mabibigo kung naiiba ang mga annotation na `x-loopback-only` o
  `x-always-protected` sa mga compile-time constant

Parehong tumatakbo ang dalawang script sa pre-commit hook at sa CI.

### Panuntunan sa False Positive

Kung inilagay ang annotation na `x-always-protected` o `x-loopback-only` sa isang route na HINDI nasa
constant ng `routeGuard.ts`, mabibigo ang coverage script. Ang tamang pag-aayos ay palaging ihanay ang
YAML sa kung ano ang aktuwal na ipinapatupad ng `routeGuard.ts` — hindi ang pagdaragdag ng mga route sa `routeGuard.ts`
nang hindi rin ipinapatupad ang enforcement logic.
