> **ಸತ್ಯದ ಮೂಲ:** `src/lib/guardrails/`
> **ಕೊನೆಯ ನವೀಕರಣ:** 2026-08-29 — v3.8.51 (Video Bridge ಪ್ರತಿಲೇಖದ ಮೂಲವನ್ನು ಕರೆಮಾಡುವವರು ಘೋಷಿಸುತ್ತಾರೆ,
> ಸರ್ವರ್ ಇನ್ನೂ ಅದನ್ನು ಪರಿಶೀಲಿಸುವುದಿಲ್ಲ — #11661 ಪ್ರಕಾರ ಸ್ಪಷ್ಟಪಡಿಸಲಾಗಿದೆ)

Guardrails, OmniRoute ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪೂರೈಕೆದಾರರ ನಡುವಿನ ಗಡಿಯಲ್ಲಿ ಸುರಕ್ಷತೆ,
ನೀತಿ ಮತ್ತು ವಿಷಯ ರೂಪಾಂತರಗಳನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಪ್ರತಿಯೊಂದು guardrail ವಿನಂತಿಯ
ಪೇಲೋಡ್ಗಳನ್ನು (`preCall`) ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು (`postCall`)
ಪರಿಶೀಲಿಸಬಹುದು (ಮತ್ತು ಐಚ್ಛಿಕವಾಗಿ ತಿರಸ್ಕರಿಸಬಹುದು, ರೂಪಾಂತರಿಸಬಹುದು ಅಥವಾ ಟಿಪ್ಪಣಿ ಸೇರಿಸಬಹುದು).

ಈ ವ್ಯವಸ್ಥೆಯು **fail-open** ಆಗಿದೆ: ಕಾರ್ಯಗತಗೊಳ್ಳುವಾಗ guardrail ದೋಷವನ್ನು ಎಸೆದರೆ,
registry ಆ ದೋಷವನ್ನು ದಾಖಲಿಸಿ, ವಿನಂತಿಯನ್ನು ವಿಫಲಗೊಳಿಸುವ ಬದಲು ಮುಂದಿನ guardrail
ಜೊತೆಗೆ ಮುಂದುವರಿಯುತ್ತದೆ. ನಿರ್ಬಂಧಿಸುವುದು ಸ್ಪಷ್ಟ ನಿರ್ಧಾರವಾಗಿದೆ (`block: true`),
ಎಂದಿಗೂ ಆಕಸ್ಮಿಕವಲ್ಲ.

## ಅಂತರ್ನಿರ್ಮಿತ ಸುರಕ್ಷತಾ ನಿಯಮಗಳು

ಆಮದು ಮಾಡುವಾಗ ರಿಜಿಸ್ಟ್ರಿಯು ಆದ್ಯತೆಯ ಕ್ರಮದಲ್ಲಿ ಆರು ಸುರಕ್ಷತಾ ನಿಯಮಗಳನ್ನು ಸ್ವಯಂಚಾಲಿತವಾಗಿ ಲೋಡ್ ಮಾಡುತ್ತದೆ
(`registry.ts` → `registerDefaultGuardrails()` ನೋಡಿ):

| ಆದ್ಯತೆ | ಹೆಸರು               | ಹಂತ(ಗಳು)       | ಫೈಲ್                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ಕಡಿಮೆ ಆದ್ಯತಾ ಸಂಖ್ಯೆಗಳು **ಮೊದಲು** ಚಾಲನೆಯಾಗುತ್ತವೆ.

### ವಿಷನ್ ಬ್ರಿಡ್ಜ್ (`visionBridge.ts`) — ಮೊಡಾಲಿಟಿ ಬ್ರಿಡ್ಜ್ PR-1

**ವಿಷನ್ ಬೆಂಬಲಿಸದ ಮಾದರಿಗಳಿಗೆ** ಉದ್ದೇಶಿಸಲಾದ ಚಿತ್ರಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳನ್ನು ತಡೆಹಿಡಿದು,
ಸಂಪೂರ್ಣ ವಿನಂತಿಯನ್ನು ವಿಷನ್ ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾದರಿಗೆ ಮರುಮಾರ್ಗಗೊಳಿಸುತ್ತದೆ ಅಥವಾ ಅಪ್ಸ್ಟ್ರೀಮ್
ಕರೆಗೆ ಮೊದಲು ಚಿತ್ರ ಭಾಗಗಳನ್ನು ಸಂರಚಿಸಬಹುದಾದ ವಿಷನ್ ಮಾದರಿಯು ರಚಿಸಿದ ಪಠ್ಯ ವಿವರಣೆಗಳಿಂದ
ಬದಲಾಯಿಸುತ್ತದೆ. ಇದು ಪಠ್ಯ-ಮಾತ್ರ ಪೂರೈಕೆದಾರರು ಮಲ್ಟಿಮೋಡಲ್ ಪೇಲೋಡ್ಗಳನ್ನು ಪಾರದರ್ಶಕವಾಗಿ
ನಿರ್ವಹಿಸಲು ಅನುವು ಮಾಡಿಕೊಡುತ್ತದೆ.

ಹರಿವು:

1. ಗುರಿ ಮಾದರಿಯು ಈಗಾಗಲೇ ವಿಷನ್ ಬೆಂಬಲಿಸಿದರೆ ಬಿಟ್ಟುಬಿಡಿ (ಅದು ಬಲವಂತದ-ಬ್ರಿಡ್ಜ್ ಪಟ್ಟಿ
   `isVisionBridgeForcedModel`ನಲ್ಲಿ ಕಾಣಿಸಿಕೊಂಡಿದ್ದರೆ ಹೊರತುಪಡಿಸಿ).
2. `extractImageParts(messages)` ಮೂಲಕ ಚಿತ್ರ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ
   (`visionBridgeHelpers.ts`); ಇದು `open-sse/utils/mediaParts.ts`ನಲ್ಲಿರುವ
   **ಏಕೀಕೃತ ಮೀಡಿಯಾ ಪತ್ತೆಕಾರಕ** `detectMediaParts()`ಗೆ ನಿಯೋಜಿಸುತ್ತದೆ — ಇದು
   ಕಾಂಬೊ ಹೊಂದಾಣಿಕೆ ಫಿಲ್ಟರ್ನೊಂದಿಗೆ ಹಂಚಿಕೊಳ್ಳುವ ಏಕೈಕ ಅಧಿಕೃತ ಮೂಲವಾಗಿದೆ.
   ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು `replaceImageParts` ಮರಳಿ ಸೇರಿಸಬಹುದಾದ ಆಕಾರಗಳ ಮೇಲ್ಮಟ್ಟದ
   ಭಾಗಗಳಿಗೆ ಅನುಮತಿ ಪಟ್ಟಿಯ ಮೂಲಕ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ (ಹೊರತೆಗೆಯುವಿಕೆ↔ಬದಲಿಸುವಿಕೆ ಒಪ್ಪಂದ):
   OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, ಮತ್ತು Responses API `input_image`. ನೆಸ್ಟೆಡ್ ಹೊಂದಾಣಿಕೆಗಳು
   ಮತ್ತು ಸೂಚಕ-ಮಾತ್ರ ಆಕಾರಗಳು ಕಾಂಬೊ-ಫಿಲ್ಟರ್ ವಸ್ತುಗಳಾಗಿದ್ದು, ಅವುಗಳನ್ನು ಎಂದಿಗೂ
   ಹೊರತೆಗೆಯಲಾಗುವುದಿಲ್ಲ. ಯಾವುದೂ ಕಂಡುಬರದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡಿ.
3. `resolveVisionBridgeRuntimeSettings()` ಮೂಲಕ ರನ್ಟೈಮ್ ಸಂರಚನೆಯನ್ನು ಪರಿಹರಿಸಿ
   (`src/shared/constants/modalityBridgeDefaults.ts`): ಹೊಸ `modalityBridge*`
   ಸೆಟ್ಟಿಂಗ್ಗಳ ಕೀಗಳು ಮೇಲುಗೈ ಸಾಧಿಸುತ್ತವೆ; ಹಳೆಯ `visionBridge*` ಕೀಗಳು
   **ಒಂದು-ಚಕ್ರದ ಪರ್ಯಾಯವಾಗಿ** ಉಳಿಯುತ್ತವೆ (ರೋಲ್ಬ್ಯಾಕ್ ವಿಂಡೋ). ಬ್ರಿಡ್ಜ್
   ನಿಷ್ಕ್ರಿಯವಾಗಿದ್ದರೆ ಯಾವುದೇ ಮೀಡಿಯಾ ಟ್ರಾವರ್ಸಲ್ಗೆ ಮೊದಲು ಬಿಟ್ಟುಬಿಡಿ.
4. ಮೋಡ್ ಆಯ್ಕೆಕಾರಕ (`modalityBridgeVisionMode`, ಕೆಳಗಿನ ಕೋಷ್ಟಕ ನೋಡಿ)
   ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆ ಅಥವಾ ವಿವರಣೆಯನ್ನು ನಿರ್ಧರಿಸುತ್ತದೆ. ಮರುಮಾರ್ಗಗೊಳಿಸುವಿಕೆಯು
   ಕೇವಲ `model` ಅನ್ನು ಬದಲಾಯಿಸಿದ `modifiedPayload` ಜೊತೆಗೆ
   `{ rerouted, fromModel, toModel, imagesKept }` ಮೆಟಾವನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ.
5. ವಿವರಣೆ ಪಥ: ಚಿತ್ರಗಳ ಸಂಖ್ಯೆಯನ್ನು `maxImages`ಗೆ ಮಿತಿಗೊಳಿಸಿ, ಕಾರ್ಯ-ಅರಿವುಳ್ಳ
   ಪ್ರಾಂಪ್ಟ್ ಅನ್ನು ರಚಿಸಿ, ವಿವರಣೆ ಕ್ಯಾಶ್ ಅನ್ನು ಪರಿಶೀಲಿಸಿ, ವಿಷನ್ ಮಾದರಿಯನ್ನು
   **ಸಮಾನಾಂತರವಾಗಿ** (`Promise.allSettled`) ಕರೆ ಮಾಡಿ ಮತ್ತು ಅವುಗಳ ಸ್ಥಾನದಲ್ಲಿ
   `[Image N]: <description>` ಪಠ್ಯ ಭಾಗಗಳನ್ನು ಸೇರಿಸಿ. ವಿಫಲವಾದ ವಿವರಣೆಯು `null`
   ಅನ್ನು ನೀಡುತ್ತದೆ ಮತ್ತು ಮೂಲ ಚಿತ್ರ ಭಾಗವನ್ನು **ಉಳಿಸಲಾಗುತ್ತದೆ** (#4012) — ಆದರೆ
   ಕಾಂಬೊ ವಿವರಣೆ ಪಥದಲ್ಲಿ ಪ್ರತಿಯೊಂದು ವಿವರಣೆಯೂ ವಿಫಲವಾದಾಗ ಇದಕ್ಕೆ ಅಪವಾದವಿದೆ; ಅಲ್ಲಿ
   ದೃಢೀಕರಿಸಿದ ವಿಷನ್ ಬೆಂಬಲಿಸದ ಅಪ್ಸ್ಟ್ರೀಮ್ಗೆ ಅದರ ಬದಲು
   `(ಲಭ್ಯವಿಲ್ಲ — ಯಾವುದೇ ವಿಷನ್-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಪೂರೈಕೆದಾರ ಸಂಪರ್ಕಗೊಂಡಿಲ್ಲ)` ಸ್ಟಬ್
   ನೀಡಲಾಗುತ್ತದೆ (#8430).
6. `modifiedPayload` + ಮೆಟಾವನ್ನು (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ಹಿಂದಿರುಗಿಸಿ.

ಹರಿವು:

1. `getResolvedModelCapabilities()` ಮೂಲಕ `supportsAudio` ಅನ್ನು ಪರಿಹರಿಸಿ.
   ಮೊದಲು ಸ್ಪಷ್ಟ ಪೂರೈಕೆದಾರ-ರಿಜಿಸ್ಟ್ರಿ ಮೆಟಾಡೇಟಾಗೆ, ನಂತರ ಸ್ಥಿರ ಮಾದರಿ ಮೆಟಾಡೇಟಾಗೆ,
   ಆಮೇಲೆ ಸಿಂಕ್ ಮಾಡಲಾದ `modalities_input` ಗೆ ಆದ್ಯತೆ ಸಿಗುತ್ತದೆ. `audio` ಇಲ್ಲದ
   ಘೋಷಿತ ಇನ್ಪುಟ್ ಪಟ್ಟಿ `false` ಆಗಿರುತ್ತದೆ; ಯಾವುದೇ ಸಾಮರ್ಥ್ಯ ಪುರಾವೆ ಇಲ್ಲದಿದ್ದರೆ
   `null` ಉಳಿಯುತ್ತದೆ. `false` ಮತ್ತು `null` ಎರಡೂ ಸಂರಕ್ಷಿತ ಬ್ರಿಡ್ಜ್ ಅನ್ನು
   ಸಕ್ರಿಯಗೊಳಿಸುತ್ತವೆ, ಆದರೆ `true` ಅದನ್ನು ಬೈಪಾಸ್ ಮಾಡುತ್ತದೆ.
2. `modalityBridgeAudio*` ಸೆಟ್ಟಿಂಗ್ಗಳನ್ನು ಪರಿಹರಿಸಿ ಮತ್ತು ಹಂಚಿಕೊಂಡ
   `detectMediaParts()` ಡಿಟೆಕ್ಟರ್ ಮೂಲಕ ಪ್ರತಿಯೊಂದು ಸಂದೇಶದಿಂದ ಸ್ಪ್ಲೈಸ್ ಮಾಡಬಹುದಾದ
   ಉನ್ನತ-ಹಂತದ ಆಡಿಯೊ ಭಾಗಗಳನ್ನು ಹೊರತೆಗೆಯಿರಿ. ಬೆಂಬಲಿತ ವೈರ್ ಆಕಾರಗಳೆಂದರೆ OpenAI
   `input_audio`, `audio_url`, ಮತ್ತು `source.media_type: "audio/*"`. ನೆಸ್ಟೆಡ್
   ಆಡಿಯೊವನ್ನು ರೂಟಿಂಗ್ಗಾಗಿ ಪತ್ತೆಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸ್ಪ್ಲೈಸ್ ಪಥದಿಂದ
   ತೆಗೆದುಹಾಕಲಾಗುವುದಿಲ್ಲ. ಕಾರ್ಯವನ್ನು `modalityBridgeAudioMaxClips` ಮೂಲಕ
   ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ; ನಂತರದ ಭಾಗಗಳು ಬದಲಾಗದೆ ಉಳಿಯುತ್ತವೆ.
3. ಸಂರಚಿಸಲಾದ `provider/model` ಅನ್ನು ಗೌರವಿಸಿ, ಅಥವಾ `selectAudioBridgeModel()`
   ಸ್ಥಿರ ಕ್ಯಾಟಲಾಗ್ ಕ್ರಮದಲ್ಲಿ `AUDIO_TRANSCRIPTION_PROVIDERS` ಮೂಲಕ ಸಾಗಲು ಮತ್ತು
   ಬಳಸಬಹುದಾದ ಸಕ್ರಿಯ ಪೂರೈಕೆದಾರ ರುಜುವಾತು ಹೊಂದಿರುವ ಮೊದಲ ಮಾದರಿಯನ್ನು ಆಯ್ಕೆಮಾಡಲು
   ಬಿಡಿ.
4. `callAudioTranscription()` base64/data-URI ಆಡಿಯೊವನ್ನು ಮಲ್ಟಿಪಾರ್ಟ್ `file`
   ಆಗಿ ಪರಿವರ್ತಿಸುತ್ತದೆ, ಅಥವಾ DNS ಪಿನ್ನಿಂಗ್ ಮತ್ತು 25 MB ಮಿತಿಯೊಂದಿಗೆ
   ಸಾರ್ವಜನಿಕ-ಮಾತ್ರದ ಔಟ್ಬೌಂಡ್ ಗಾರ್ಡ್ ಮೂಲಕ ದೂರಸ್ಥ `audio_url` ಅನ್ನು ಡೌನ್ಲೋಡ್
   ಮಾಡುತ್ತದೆ. ನಂತರ ಅದು ಫೈಲ್ ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ ಮಾದರಿಯನ್ನು ಸ್ಥಳೀಯ
   `/v1/audio/transcriptions` ಸ್ವಯಂ-ಲೂಪ್ಗೆ POST ಮಾಡುತ್ತದೆ ಮತ್ತು
   `resolveSelfLoopBearer()` ಮೂಲಕ ದೃಢೀಕರಿಸುತ್ತದೆ. ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಲಿಪ್ಯಂತರ
   ರೂಟ್ ಸಾಮಾನ್ಯ ರುಜುವಾತು ಲುಕಪ್, ಕೂಲ್ಡೌನ್/ದರ-ಮಿತಿ ನಿರ್ವಹಣೆ ಮತ್ತು ಪೂರೈಕೆದಾರ
   ಡಿಸ್ಪ್ಯಾಚ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
5. ಯಶಸ್ವಿ ಕರೆಗಳು ಅವುಗಳ ಭಾಗಗಳನ್ನು `[Audio N]: <transcript>` ನೊಂದಿಗೆ
   ಬದಲಾಯಿಸುತ್ತವೆ. ಕರೆಗಳು `Promise.allSettled` ಮೂಲಕ ಚಲಿಸುತ್ತವೆ: ವೈಯಕ್ತಿಕ ವೈಫಲ್ಯವು
   ಆ ಮೂಲ ಆಡಿಯೊ ಭಾಗವನ್ನು ಉಳಿಸುತ್ತದೆ (#4012 ಒಪ್ಪಂದ). ಪ್ರತಿಯೊಂದು ಕರೆ ವಿಫಲವಾದರೆ
   ಮತ್ತು ಗುರಿಯು `supportsAudio === false` ಎಂದು ಸಾಬೀತಾಗಿದ್ದರೆ, ಭಾಗಗಳು
   `[Audio N]: (unavailable — no STT provider connected)` ಆಗುತ್ತವೆ (#8430
   ಒಪ್ಪಂದ). ತಿಳಿದಿಲ್ಲದ ಗುರಿಗೆ (`null`), ಎಲ್ಲವೂ ವಿಫಲವಾದ ಫಲಿತಾಂಶವು ಬದಲಾಗದೆ
   ಉಳಿಯುತ್ತದೆ. ಬಳಸಬಹುದಾದ STT ರುಜುವಾತು ಇಲ್ಲದ, ಪಠ್ಯ-ಮಾತ್ರದ ಎಂದು ಸಾಬೀತಾದ ಗುರಿಯು
   ನೆಟ್ವರ್ಕ್ ಕರೆ ನೀಡದೆಯೇ ಅದೇ ಸ್ಪಷ್ಟ ಸ್ಟಬ್ ಅನ್ನು ಪಡೆಯುತ್ತದೆ.

ಯಶಸ್ವಿ ಲಿಪ್ಯಂತರಗಳು ಪ್ರಕ್ರಿಯೆ-ವ್ಯಾಪಿ Modality Bridge LRU/TTL ಕ್ಯಾಶ್ ಅನ್ನು
ಬಳಸುತ್ತವೆ. ಕೀಲಿಯು ಆಡಿಯೊ ಉಲ್ಲೇಖ, ಸ್ಥಿರ `audio-transcription` ಕಾರ್ಯಾಚರಣೆ ಲೇಬಲ್
ಮತ್ತು ಆಯ್ಕೆಮಾಡಿದ STT ಮಾದರಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ; ವೈಫಲ್ಯಗಳನ್ನು ಎಂದಿಗೂ ಕ್ಯಾಶ್
ಮಾಡಲಾಗುವುದಿಲ್ಲ. ಆಡಿಯೊ ಪ್ರಯತ್ನಗಳು ಹಂಚಿಕೊಂಡ `bridged`, `cacheHits`, `failures`,
ಮತ್ತು `lastUsedAt` ಕೌಂಟರ್ಗಳನ್ನು ನವೀಕರಿಸುತ್ತವೆ. ರೂಪಾಂತರಗೊಂಡ ಪ್ರತಿಕ್ರಿಯೆಗಳು
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ಅನ್ನು
ಹೊಂದಿರುತ್ತವೆ; ಬದಲಾಗದ ವಿನಂತಿಗಳು Audio Bridge ವಿಭಾಗವನ್ನು ಪಡೆಯುವುದಿಲ್ಲ.

ರನ್ಟೈಮ್ ಸೆಟ್ಟಿಂಗ್ಗಳು DB-ಬೆಂಬಲಿತವಾಗಿದ್ದು Zod ಮೂಲಕ ಮೌಲ್ಯೀಕರಿಸಲ್ಪಡುತ್ತವೆ:

| ಕೀ                            | ಪೂರ್ವನಿಯೋಜಿತ | ವ್ಯಾಪ್ತಿ          |
| ----------------------------- | ------------ | ----------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —                 |
| `modalityBridgeAudioModel`    | `""`         | ಸ್ವಯಂ ಅಥವಾ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000       |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10              |

ಹಂಚಿಕೆಯ ಕ್ಯಾಶ್ ಅನ್ನು `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, ಮತ್ತು `modalityBridgeCacheMaxEntries` ನಿಯಂತ್ರಿಸುತ್ತವೆ.

### ವೀಡಿಯೊ ಬ್ರಿಡ್ಜ್ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಬೆಂಬಲವಿದೆ ಎಂದು ತಿಳಿದಿಲ್ಲದ ಗುರಿಯನ್ನು ಕರೆ ಮಾಡುವ ಮೊದಲು, Chat Completions
`messages` ಮತ್ತು Responses API `input` ನಲ್ಲಿನ ಉನ್ನತ-ಮಟ್ಟದ ವೀಡಿಯೊ ಭಾಗಗಳನ್ನು
ಪ್ರತಿಬಂಧಿಸುತ್ತದೆ. ಬೆಂಬಲಿತ ಸ್ವರೂಪಗಳೆಂದರೆ `input_video`, `video_url`, `video_source`,
HTTPS URLಗಳು, ಮತ್ತು `data:video/*;base64,...` ಡೇಟಾ URIಗಳು. ಪಠ್ಯದಲ್ಲಿನ ಸರಳ ಫೈಲ್ ಹೆಸರುಗಳನ್ನು
ವೀಡಿಯೊ ಎಂದು ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ವಿನಂತಿಯ ಟ್ರಾವರ್ಸಲ್,
ಸಾಮರ್ಥ್ಯ/ನೀತಿ ಪರಿಶೀಲನೆ, ಪ್ರತಿ-ವಿನಂತಿಯ ಒಟ್ಟುಗೂಡಿಸುವಿಕೆ, ಮತ್ತು ಪ್ರತಿಕ್ರಿಯೆ ಪೇಲೋಡ್ ಅನ್ನು ನಿರ್ವಹಿಸುತ್ತದೆ.
ಪ್ರತಿ-ವೀಡಿಯೊದ ಕೆಲಸ — ಸ್ವಾಧೀನಪಡಿಸಿಕೊಳ್ಳುವಿಕೆ, ಸಂಪೂರ್ಣ-ಫಲಿತಾಂಶದ ಕ್ಯಾಶ್, ಫ್ರೇಮ್
ಅನುಕ್ರಮವನ್ನು ವಿವರಿಸುವಿಕೆ (ಇದು ಕರೆಮಾಡುವವರು ಘೋಷಿಸಿದ ಯಾವುದೇ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು ಸಂಯೋಜಿಸುತ್ತದೆ),
ಮತ್ತು ಪ್ರತಿ-ಪ್ರಯತ್ನದ ಮೆಟ್ರಿಕ್ಗಳು/ಸ್ಥಗಿತಗೊಳಿಸುವಿಕೆ/ಸ್ವಚ್ಛಗೊಳಿಸುವಿಕೆ — ಇವೆಲ್ಲವನ್ನೂ
`videoBridgePipeline.ts` ನಲ್ಲಿನ `processVideoPart` ಹಿಂದೆ ಮರೆಮಾಡಲಾಗಿದೆ; ಇದನ್ನು
`preCall` ಲೂಪ್ನ ಒಳಗೆ ಪ್ರತಿ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಒಮ್ಮೆ ಕರೆಯಲಾಗುತ್ತದೆ.
ಆ ಮಾಡ್ಯೂಲ್ ಸ್ಪಷ್ಟವಾದ ಪೋರ್ಟ್ ಗಡಿಗಳಾದ `VideoMediaBrokerPort`
(ಬೈಟ್ಗಳನ್ನು ಸ್ವಾಧೀನಪಡಿಸಿಕೊಳ್ಳುವುದು ಮತ್ತು ಮಾದರಿಯಾಗಿ ಆಯ್ದ ಫ್ರೇಮ್ಗಳನ್ನು ಹೊರತೆಗೆಯುವುದು),
`VideoAudioTranscriptionPort`
(ಕರೆಮಾಡುವವರು ಘೋಷಿಸಿದ ಆಡಿಯೊ ಪ್ರತಿಲಿಪಿಯನ್ನು ಮಾದರಿಯಾಗಿ ಆಯ್ದ ಶೀರ್ಷಿಕೆಗಳೊಂದಿಗೆ ಸಂಯೋಜಿಸುವುದು), ಮತ್ತು
`VideoDrilldownPort` (ಫ್ರೇಮ್ ಡ್ರಿಲ್-ಡೌನ್ ಸ್ಥಿರತೆ ಗಡಿ; ಇನ್ನೂ
`processVideoPart` ಗೆ ಜೋಡಿಸಲಾಗಿಲ್ಲ — ಪ್ರಸ್ತುತ ಪ್ರತ್ಯೇಕ `/api/modality-bridge/video/drilldown`
ರೂಟ್ ಮಾತ್ರ ಡ್ರಿಲ್-ಡೌನ್ ನಮೂದುಗಳನ್ನು ಬರೆಯುತ್ತದೆ) ಅನ್ನೂ ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ.

ಸಾರ್ವಜನಿಕ `/v1` ವಿನಂತಿ ಪಥವು ಎಂದಿಗೂ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಆಮದು ಮಾಡುವುದಿಲ್ಲ ಅಥವಾ ಆಹ್ವಾನಿಸುವುದಿಲ್ಲ.
ದೂರಸ್ಥ ವೀಡಿಯೊಗಳನ್ನು 50 MiB ಮಿತಿಯೊಳಗೆ ಡೌನ್ಲೋಡ್ ಮಾಡಲಾಗುತ್ತದೆ; ಇನ್ಲೈನ್ base64 ವೀಡಿಯೊಗಳಿಗೆ
ಪ್ರತಿ-ವೀಡಿಯೊಗೆ ಸಂರಕ್ಷಣಾತ್ಮಕವಾದ 36 MiB ಡಿಕೋಡ್ ಮಿತಿ ಇದೆ, ಇದರಿಂದ ಮಾದರಿ/ಸಂದೇಶಗಳು/ಫ್ರೇಮಿಂಗ್
ಆವರಣವು 50 MiB ಸಾರ್ವಜನಿಕ JSON ವಿನಂತಿ ಸ್ವೀಕಾರ ಮಿತಿಯೊಳಗೆ ಉಳಿಯಬಹುದು. ಇನ್ಲೈನ್
ಉದ್ದ ಮತ್ತು ಡಿಕೋಡ್ ಗಾತ್ರದ ಅಂದಾಜುಗಳನ್ನು ಹಂಚಿಕೆಗೂ ಮೊದಲು ಪರಿಶೀಲಿಸಲಾಗುತ್ತದೆ. ಆರಂಭಿಕ ದೂರಸ್ಥ
URL ಮತ್ತು ಪ್ರತಿ ಮರುನಿರ್ದೇಶನಕ್ಕೂ HTTPS ಅಗತ್ಯವಿದ್ದು, DNS ಪಿನ್ನಿಂಗ್ನೊಂದಿಗೆ ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ
ಸಾರ್ವಜನಿಕ-ಮಾತ್ರದ ಹೊರಹೋಗುವಿಕೆ ರಕ್ಷಣೆಯನ್ನು ಬಳಸಲಾಗುತ್ತದೆ. ನಂತರ ಬೈಟ್ಗಳು ನಿಖರವಾದ ಆಂತರಿಕ
`POST /api/modality-bridge/video/extract` ಬ್ರೋಕರ್ ಗಡಿಯನ್ನು ದಾಟುತ್ತವೆ. ಆ ರೂಟ್
`LOCAL_ONLY` ಮತ್ತು `SPAWN_CAPABLE` ಎರಡೂ ಆಗಿದ್ದು, ಪ್ರತಿ-ಪ್ರಕ್ರಿಯೆಗೆ ದೃಢೀಕರಿಸಿದ,
ವಿಶ್ವಾಸಾರ್ಹ-ಲೂಪ್ಬ್ಯಾಕ್ ವಿನಂತಿಯನ್ನು ಮಾತ್ರ ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು URL, ಫೈಲ್ಸಿಸ್ಟಮ್ ಪಥ,
ಕಾರ್ಯಗತಗೊಳಿಸಬಹುದಾದ ಫೈಲ್, ಅಥವಾ ಆರ್ಗ್ಯುಮೆಂಟ್ ಪಟ್ಟಿಯನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ. API ಬಾಡಿ-ಗಾತ್ರದ
ಪೈಪ್ಲೈನ್ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ನ ಕ್ರಮೇಣ ಬಾಡಿ ರೀಡರ್ ಸ್ವತಂತ್ರವಾಗಿ 50 MiB ಬ್ರೋಕರ್ ಇನ್ಪುಟ್
ಮಿತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ. ಅದರ ಮಿತಿಗೊಳಿಸಿದ ಕ್ಯೂ ಒಂದು ಸಮಯದಲ್ಲಿ ಒಂದು ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು
ನಡೆಸುತ್ತದೆ, ಬಾಕಿಯಿರುವ ನಾಲ್ಕು ಜಾಬ್ಗಳಿಗೆ ಅವಕಾಶ ನೀಡುತ್ತದೆ, ಮತ್ತು ಬಾಕಿಯಿರುವ ಇನ್ಪುಟ್ ಅನ್ನು
100 MiB ಗೆ ಮಿತಿಗೊಳಿಸುತ್ತದೆ.

#### FU-07 ರಚನಾತ್ಮಕ ಸೆಗ್ಮೆಂಟ್ ಸಾಕ್ಷ್ಯ

`segment_aware` ಈಗಾಗಲೇ ಮೌಲ್ಯೀಕರಿಸಲಾದ ಸ್ಥಳೀಯ ವೀಡಿಯೊ ಸ್ಟ್ರೀಮ್ ಮೇಲೆ ಒಂದು ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣಾ ಪಾಸ್ ಅನ್ನು ಬಳಸುತ್ತದೆ. ಸ್ಥಿರ ಫಿಲ್ಟರ್ ಸರಪಳಿಯು ಮೊದಲು ಅಗಲವನ್ನು ಗರಿಷ್ಠ 320 ಪಿಕ್ಸೆಲ್ಗಳಿಗೆ ಸ್ಕೇಲ್ ಮಾಡುತ್ತದೆ, ದೃಶ್ಯ ಬದಲಾವಣೆಗಳು ಮತ್ತು ಸ್ಥಿರಗೊಂಡ ಮಧ್ಯಂತರಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ, ನಂತರ ಮಸುಕು, ಸರಾಸರಿ ಲ್ಯೂಮಾ ಮತ್ತು ಸ್ಥಳೀಯ/ಕಾಲಿಕ ಮಾಹಿತಿಗಾಗಿ ಪ್ರತಿ ಸೆಕೆಂಡಿಗೆ 1 ಫ್ರೇಮ್ನಂತೆ ಮಾದರಿಗಳನ್ನು ತೆಗೆದುಕೊಳ್ಳುತ್ತದೆ. ಈ ಪಾಸ್ ಅನ್ನು 600 ರಚನಾತ್ಮಕ ಮಾದರಿಗಳು, ಒಂದು FFmpeg/ಫಿಲ್ಟರ್ ಥ್ರೆಡ್, ಅದೇ `file`-ಮಾತ್ರದ ಪ್ರೋಟೋಕಾಲ್ ಮತ್ತು ಕಂಟೇನರ್ ಅನುಮತಿ ಪಟ್ಟಿಗಳು, 1 MiB ಪ್ರಕ್ರಿಯೆ-ಔಟ್ಪುಟ್ ಮಿತಿ ಹಾಗೂ ಬ್ರೋಕರ್ನ ಹಂಚಿಕೆಯ ರದ್ದತಿ/ಗಡುವಿನೊಳಗಿನ ಗರಿಷ್ಠ 30 ಸೆಕೆಂಡುಗಳಿಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗಿದೆ. ಇದು ವಿನಂತಿಯಿಂದ ಯಾವುದೇ ಕಮಾಂಡ್, ಫಿಲ್ಟರ್, ಪಥ ಅಥವಾ URL ಅನ್ನು ಎಂದಿಗೂ ಸ್ವೀಕರಿಸುವುದಿಲ್ಲ.

ರಚನಾತ್ಮಕ ಮೌಲ್ಯಗಳು ನಿರ್ಣಾಯಕ ಮಾದರಿ ಸಾಕ್ಷ್ಯವಾಗಿದ್ದು, ಅರ್ಥಾಧಾರಿತ ವೀಡಿಯೊ ಗ್ರಹಿಕೆಯಲ್ಲ. ಅವು ವಿಷಯಗಳು, ಕ್ರಿಯೆಗಳು, ಶೀರ್ಷಿಕೆಗಳು, ಮಾತು ಅಥವಾ ಬಳಕೆದಾರರ ಉದ್ದೇಶವನ್ನು ಊಹಿಸುವುದಿಲ್ಲ. ದೃಶ್ಯ ಮತ್ತು ಸ್ಥಿರೀಕರಣದ ಗಡಿಗಳು ವಿಭಾಗಗಳನ್ನು ರೂಪಿಸುತ್ತವೆ; ಸ್ಥಿರೀಕರಣ ವ್ಯಾಪ್ತಿ, ಮಸುಕು, ಎಕ್ಸ್ಪೋಷರ್, ಸ್ಥಳೀಯ ವಿವರ ಮತ್ತು ಕಾಲಿಕ ಬದಲಾವಣೆಗಳು ಈಗಿರುವ 1–16 ಫ್ರೇಮ್ ಬಜೆಟ್ ಅನ್ನು ಹೇಗೆ ಹಂಚಲಾಗುತ್ತದೆ ಎಂಬುದರ ಮೇಲೆ ಮಾತ್ರ ಪ್ರಭಾವ ಬೀರುತ್ತವೆ. ಸಂಪೂರ್ಣವಾಗಿ ಸ್ಥಿರಗೊಂಡ ವಿಭಾಗವನ್ನು ಒಂದು ಫ್ರೇಮ್ಗೆ ಮಿತಿಗೊಳಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಸ್ಥಿರಗೊಳ್ಳದ ವಿಭಾಗಗಳು ಉಳಿದ ಬಜೆಟ್ಗಾಗಿ ಸ್ಪರ್ಧಿಸುತ್ತವೆ. ಗಡಿಗಳ ಸಂಖ್ಯೆ ಫ್ರೇಮ್ಗಳ ಸಂಖ್ಯೆಯನ್ನು ಮೀರಿದಾಗ, ವೇಗವಾದ ಆರಂಭಿಕ ಕಟ್ಗಳು ದೀರ್ಘವಾದ ಕೊನೆಯ ವಿಭಾಗವನ್ನು ಮರೆಮಾಡದಂತೆ ಏಕರೂಪ ಕಾಲರೇಖೆ ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. ಸ್ಥಿರೀಕರಣದ ಗಡಿಯ 1-ಸೆಕೆಂಡ್ ವಿಶ್ಲೇಷಣಾ ರೆಸಲ್ಯೂಷನ್ನೊಳಗಿನ ದೃಶ್ಯ ಗಡಿಗಳನ್ನು ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ.

ಕಾಣೆಯಾದ ಫಿಲ್ಟರ್ಗಳು, ದೋಷಪೂರಿತ/ಖಾಲಿ ಸಾಕ್ಷ್ಯ, ಡಿಟೆಕ್ಟರ್ ದೋಷ ಅಥವಾ ಮಿತಿಗೊಳಿಸಲಾದ ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ಕಾಲಾವಧಿ ಮೀರಿಕೆಯು ನಿಖರವಾದ ಏಕರೂಪ ಮಧ್ಯಬಿಂದು ನೀತಿಗೆ ಮುಕ್ತವಾಗಿ ಹಿಂತಿರುಗುತ್ತದೆ. ಕಾಲರ್ನ ರದ್ದತಿ ಅಥವಾ ಬ್ರೋಕರ್ನ ಗಡುವು ಮುಕ್ತವಾಗಿ ಹಿಂತಿರುಗುವುದಿಲ್ಲ: ಅದು ಚಾಲ್ತಿಯಲ್ಲಿರುವ ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ, ನಂತರದ ಫ್ರೇಮ್ ಹೊರತೆಗೆಯುವಿಕೆಯನ್ನು ತಡೆಯುತ್ತದೆ ಮತ್ತು ಖಾಸಗಿ ತಾತ್ಕಾಲಿಕ ಟ್ರೀಯನ್ನು `finally` ನಲ್ಲಿ ತೆಗೆದುಹಾಕಲಾಗುತ್ತದೆ.

`scripts/perf/video-bridge-fu07-eval.ts` ಡೀಡ್ಯೂಪ್ ನಂತರದ ಶೀರ್ಷಿಕೆ-ಕರೆ ಉಳಿತಾಯ, ದಟ್ಟ-ಚಲನೆಯ ಬಜೆಟ್ ಹಂಚಿಕೆ, ಮಸುಕು/ಎಕ್ಸ್ಪೋಷರ್/SI-TI ಸಾಕ್ಷ್ಯ, ದೀರ್ಘ ಕೊನೆಯ ಭಾಗವಿರುವ ವೇಗವಾದ ಕಟ್ಗಳು ಮತ್ತು ಕ್ರಮೇಣ ಫೇಡ್ನ ತಪ್ಪು ಧನಾತ್ಮಕ ಫಲಿತಾಂಶಗಳಿಗಾಗಿ ನಿರ್ಣಾಯಕ ನೈಜ FFmpeg ಫಿಕ್ಚರ್ಗಳನ್ನು ರಚಿಸುತ್ತದೆ. ಇದು ಪೂರ್ವ-ವಿಶ್ಲೇಷಣೆಯ ವಾಸ್ತವ ಸಮಯವನ್ನು ಹಾಗೂ `/usr/bin/time` ಲಭ್ಯವಿರುವಲ್ಲಿ ಚೈಲ್ಡ್ CPU ಮತ್ತು ಗರಿಷ್ಠ RSS ಅನ್ನು ದಾಖಲಿಸುತ್ತದೆ. ಇದರ ಗುಣಮಟ್ಟ ಪರಿಶೀಲನೆಗಳು ರಚನಾತ್ಮಕ ನಿರ್ಣಾಯಕಗಳು ಮಾತ್ರ. ಈ ಹಾರ್ನೆಸ್ನಲ್ಲಿ ಅಧಿಕೃತ ಎಂಡ್ಪಾಯಿಂಟ್ ಅಥವಾ ಸ್ಥಿರಗೊಳಿಸಿದ ನಿರ್ಣಾಯಕ ಇಲ್ಲದ ಕಾರಣ ನೈಜ ಶೀರ್ಷಿಕೆ-ಮಾದರಿಯ ಗುಣಮಟ್ಟವು `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. `--caption-cost-per-call-usd` ಪ್ರತಿ ಕರೆಗೆ ಸ್ಪಷ್ಟವಾದ ಧನಾತ್ಮಕ ವೆಚ್ಚದ ಅಂದಾಜನ್ನು ಒದಗಿಸದ ಹೊರತು ಹಣಕಾಸಿನ ಉಳಿತಾಯವೂ `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ; ಸ್ಕ್ರಿಪ್ಟ್ ಈ ಫಲಿತಾಂಶಗಳಲ್ಲಿ ಯಾವುದನ್ನೂ ಕೃತಕವಾಗಿ ಸೃಷ್ಟಿಸುವುದಿಲ್ಲ.

ಹೆಚ್ಚಿನ-ಕಾಂಟ್ರಾಸ್ಟ್ ಸಂಕೇತವು ಸರಾಸರಿ-ಮಾತ್ರದ ಹೋಲಿಕೆಯು ಮರೆಮಾಡಬಹುದಾದ ಸಣ್ಣ ಚಲನೆ ಮತ್ತು ಗೋಚರ ಪಠ್ಯ ಬದಲಾವಣೆಗಳನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತದೆ. ಕಂಪೇರೇಟರ್ ಅಥವಾ ಡಿಕೋಡರ್ ದೋಷಗಳು ಮುಕ್ತವಾಗಿ ಮುಂದುವರಿದು ವ್ಯಾಪ್ತಿಯನ್ನು ಉಳಿಸಿಕೊಳ್ಳುತ್ತವೆ. ಔಟ್ಪುಟ್ ಮೆಟಾಡೇಟಾವು ಹೊರತೆಗೆದ ಅಭ್ಯರ್ಥಿಗಳು, ಯಶಸ್ವಿಯಾಗಿ ಬಳಸಿದ ಫ್ರೇಮ್ಗಳು ಮತ್ತು ಕೈಬಿಟ್ಟ ದೃಶ್ಯ ನಕಲುಗಳನ್ನು ಪ್ರತ್ಯೇಕಿಸುತ್ತದೆ.

ಸ್ಪಷ್ಟವಾಗಿ ಗುರುತಿಸಲಾದ ವೀಡಿಯೊ ಭಾಗವು ಸಮಯಮುದ್ರೆಯಿರುವ ಕಾಂಟ್ಯಾಕ್ಟ್ ಶೀಟ್ ಅನ್ನು ವಿನಂತಿಸಬಹುದು. ಬ್ರಿಡ್ಜ್ ಗರಿಷ್ಠ 4 ಕಾಲಮ್ಗಳು ಮತ್ತು 16 ಫ್ರೇಮ್ಗಳ JPEG ಗ್ರಿಡ್ ಅನ್ನು ನಿರ್ಮಿಸುತ್ತದೆ. ಪ್ರತಿ 512-ಪಿಕ್ಸೆಲ್ ಸೆಲ್ ತನ್ನ ಮೂಲ ಸಮಯಮುದ್ರೆಯನ್ನು ಹೆಚ್ಚಿನ-ಕಾಂಟ್ರಾಸ್ಟ್ನ ಕೆಳಗಿನ ಬ್ಯಾಂಡ್ನಲ್ಲಿ ಮುದ್ರಿಸುತ್ತದೆ; ಇದೇ ಸಮಯಮುದ್ರೆಗಳು ಕೆಳಹಂತದ ಸಂಬಂಧ ಜೋಡಣೆ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆಗಾಗಿ ಪಠ್ಯ ಮೆಟಾಡೇಟಾದಲ್ಲಿಯೂ ಉಳಿಯುತ್ತವೆ. ಸಂಪೂರ್ಣ JPEG ಅನ್ನು 32 MiB ಗೆ ಸೀಮಿತಗೊಳಿಸಲಾಗುತ್ತದೆ. `sharp` ಗ್ರಿಡ್ ಅನ್ನು ಡಿಕೋಡ್ ಮಾಡಲು ಅಥವಾ ಸಂಯೋಜಿಸಲು ಸಾಧ್ಯವಾಗದಿದ್ದರೆ, ಬ್ರಿಡ್ಜ್ ಪ್ರತ್ಯೇಕ JPEG ಫ್ರೇಮ್ಗಳಿಗೆ ಹಿಂತಿರುಗುತ್ತದೆ; ಕ್ಲೈಂಟ್ ರದ್ದತಿಯು ಶೀಟ್ ಕಾರ್ಯಾಚರಣೆಯ ಮೂಲಕವೂ ಪ್ರಸಾರವಾಗುತ್ತದೆ.

ಪ್ರೊಮೋಷನ್ ಸಾಕ್ಷ್ಯವನ್ನು ಸಂಶ್ಲೇಷಿತ ಸಂಯೋಜನಾ ಮೈಕ್ರೋಬೆಂಚ್ಮಾರ್ಕ್ನಿಂದ ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಪ್ರತ್ಯೇಕಿಸಲಾಗಿದೆ. `scripts/perf/video-bridge-contact-sheet-eval.ts` ನೈಜ OpenAI-ಹೊಂದಾಣಿಕೆಯ ದೃಶ್ಯ ಮಾದರಿಗಳಿಗಾಗಿ ಸ್ಕೀಮಾ-ಆವೃತ್ತಿಗೊಳಿಸಲಾದ A/B ಹಾರ್ನೆಸ್ ಅನ್ನು ವ್ಯಾಖ್ಯಾನಿಸುತ್ತದೆ. ಇದು ಪೂರೈಕೆದಾರರು ವರದಿ ಮಾಡಿದ ಟೋಕನ್ಗಳು, ಶೀಟ್ ಸಂಯೋಜನೆಯನ್ನು ಒಳಗೊಂಡ ಅಂತ್ಯದಿಂದ ಅಂತ್ಯದವರೆಗಿನ ವಾಸ್ತವ ವಿಳಂಬ, ಮಾದರಿ-ಕರೆಗಳ ಸಂಖ್ಯೆ ಮತ್ತು ಮ್ಯಾನಿಫೆಸ್ಟ್ ನಿರ್ಧರಿಸಿದ ವಾಸ್ತವಾಂಶ ಧಾರಣೆಯನ್ನು ಅಳೆಯುತ್ತದೆ. ಕಚ್ಚಾ ಮಾದರಿ ಪ್ರತಿಕ್ರಿಯೆಗಳನ್ನು ವರದಿಗೆ ಬರೆಯಲಾಗುವುದಿಲ್ಲ; SHA-256 ಡೈಜೆಸ್ಟ್ಗಳು ಮತ್ತು ಹೊಂದಿಕೆಯಾಗಿರುವ ವಾಸ್ತವಾಂಶ ID ಗಳನ್ನು ಮಾತ್ರ ಉಳಿಸಿಕೊಳ್ಳಲಾಗುತ್ತದೆ. `--execute-real` ಅನ್ನು ಪಾಸ್ ಮಾಡದಿದ್ದರೆ ಮತ್ತು `--model`, `OMNIROUTE_BASE_URL` ಹಾಗೂ `OMNIROUTE_API_KEY` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದಿದ್ದರೆ ಹಾರ್ನೆಸ್ ಯಾವುದೇ ನೆಟ್ವರ್ಕ್ ಅಥವಾ ಪಾವತಿಸಿದ ಮಾದರಿ ಕರೆಯನ್ನು ಮಾಡುವುದಿಲ್ಲ. ಆ ಸ್ಪಷ್ಟ ನೈಜ ರನ್ ಇಲ್ಲದಿದ್ದರೆ, ಅದರ ಯಂತ್ರ-ಓದಬಹುದಾದ ತೀರ್ಪು `HOLD` ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ; ಸಂಶ್ಲೇಷಿತ ಪೇಲೋಡ್/ಕರೆ-ಸಂಖ್ಯೆ ಮಾಪನಗಳು ಮಾತ್ರ ಪ್ರೊಮೋಷನ್ ಸಾಕ್ಷ್ಯವಲ್ಲ.

ಕಾಲರ್ಗಳು ಈಗಾಗಲೇ ಹೊಂದಾಣಿಕೆಗೊಳಿಸಿದ ಪಠ್ಯವನ್ನು ಹೊಂದಿರುವಾಗ ಬೆಂಬಲಿತ ವೀಡಿಯೊ ಭಾಗಕ್ಕೆ ಐಚ್ಛಿಕ `transcript.cues` ಅರೇಯನ್ನು ಲಗತ್ತಿಸಬಹುದು. ಪ್ರತಿಯೊಂದು ಕ್ಯೂ `text`, ಪ್ರೋಬ್ ಮಾಡಿದ ಅವಧಿಯೊಳಗಿನ ಪರಿಮಿತ `start`/`end` ಮಧ್ಯಂತರ ಮತ್ತು ಅನುಮತಿ ಪಟ್ಟಿಯಲ್ಲಿರುವ `source` (`client`, `embedded`, ಅಥವಾ `audio-bridge`) ಅನ್ನು ಹೊಂದಿರಬೇಕು; `confidence` ನ ಡೀಫಾಲ್ಟ್ ಮೌಲ್ಯ `1` ಆಗಿದ್ದು, ಅದು `0` ಮತ್ತು `1` ನಡುವೆ ಇರಬೇಕು. ನಿಖರವಾಗಿ ನಕಲಾದ ಕ್ಯೂಗಳನ್ನು ಒಗ್ಗೂಡಿಸಲಾಗುತ್ತದೆ. OmniRoute ಈ ಮೆಟಾಡೇಟಾದಿಂದ ಎಂದಿಗೂ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ ಪ್ರಾರಂಭಿಸುವುದಿಲ್ಲ: ಮೌಲ್ಯೀಕರಿಸಲಾದ ಕ್ಯೂಗಳನ್ನು ಮೂಲ, ವಿಶ್ವಾಸಮಟ್ಟ ಮತ್ತು ಮಧ್ಯಂತರದೊಂದಿಗೆ ವಿವರಿಸಲಾದ ಫಲಿತಾಂಶಕ್ಕೆ ನಕಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು ಫ್ರೇಮ್ ಶೀರ್ಷಿಕೆಗಳ ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ವೀಕ್ಷಣೆಗಳಾಗಿ ರೆಂಡರ್ ಮಾಡಲಾಗುತ್ತದೆ. ಅಮಾನ್ಯ, ವ್ಯಾಪ್ತಿಯಿಂದ ಹೊರಗಿನ ಅಥವಾ ಮೂಲಸಂಬಂಧವಿಲ್ಲದ ಪಠ್ಯವನ್ನು ಶೀರ್ಷಿಕೆ ಸ್ಟ್ರೀಮ್ನಲ್ಲಿ ಬೆರೆಸುವ ಬದಲು ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ. ವಿನಂತಿ-ಬಾಡಿಯ ಎರಡೂ ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಚಾನಲ್ಗಳು ಸ್ವಯಂ-ಪ್ರತಿಪಾದಿತ `embedded` ಅಥವಾ `audio-bridge` ಲೇಬಲ್ಗಳನ್ನು ಒಳಗೊಂಡಂತೆ ಒದಗಿಸಲಾದ ಮೂಲಸಂಬಂಧವನ್ನು `client` ಗೆ ಸಾಮಾನ್ಯೀಕರಿಸುತ್ತವೆ. ಸರ್ವರ್-ಸ್ವಾಮ್ಯದ ಅಡಾಪ್ಟರ್ ಮಾತ್ರ ಕೋಡ್-ಮಾತ್ರದ `trustedSource` ಆರ್ಗ್ಯುಮೆಂಟ್ ಮೂಲಕ ಆ ವಿಶ್ವಾಸಾರ್ಹ ಲೇಬಲ್ಗಳನ್ನು ನಿಯೋಜಿಸಬಹುದು; ವಿನಂತಿಯ JSON ಫೀಲ್ಡ್ ಆ ಆರ್ಗ್ಯುಮೆಂಟ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಟ್ ಪಠ್ಯವು ಅದರ ಮೂಲಸಂಬಂಧವನ್ನು ಲೆಕ್ಕಿಸದೆ ವಿಶ್ವಾಸಾರ್ಹವಲ್ಲದ ಮಾಧ್ಯಮ-ಉತ್ಪನ್ನ ವಿಷಯವಾಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಮತ್ತು ಅದು ಎಂದಿಗೂ ಅಧಿಕಾರ ನಿರ್ಧಾರವನ್ನು ನಿಯಂತ್ರಿಸಬಾರದು.

**ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ.

- **`preCall`** ಪೇಲೋಡ್ ಅನ್ನು ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `system`, `messages`, `input` ಮತ್ತು
  `prompt` ಮೂಲಕ ಸಂಚರಿಸುತ್ತದೆ (ಸರಳ ಸ್ಟ್ರಿಂಗ್ ಐಟಂಗಳನ್ನು ಒಳಗೊಂಡಂತೆ), ಮತ್ತು ಸ್ಟ್ರಿಂಗ್
  `content`/`text` ಕ್ಷೇತ್ರಗಳಿಗೆ (`@/shared/utils/inputSanitizer`ನಿಂದ)
  `processPII()` ಅನ್ನು ಅನ್ವಯಿಸುತ್ತದೆ. `PII_REDACTION_ENABLED=true` ಆಗಿರುವಾಗ, ಪತ್ತೆಯಾದ PII ಅನ್ನು ಹೊರಹೋಗುವ
  ಪೇಲೋಡ್ನಲ್ಲಿ ಪರಿಷ್ಕರಿಸಲಾಗುತ್ತದೆ. ಇದು `INPUT_SANITIZER_MODE`ನಿಂದ ಸ್ವತಂತ್ರವಾಗಿದೆ (ಇದು ಕೇವಲ
  ಪ್ರಾಂಪ್ಟ್-ಇಂಜೆಕ್ಷನ್ ನೀತಿಯನ್ನು ನಿಯಂತ್ರಿಸುತ್ತದೆ). ಪರಿಷ್ಕರಣೆ ಆಫ್ ಆಗಿರುವಾಗ, ವಿಷಯವನ್ನು ಪುನಃ ಬರೆಯದೆಯೇ ಕರೆ ಪತ್ತೆ
  ಎಣಿಕೆಗಳನ್ನು ದಾಖಲಿಸುತ್ತದೆ.
- **`postCall`** ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಡೀಪ್-ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ, `sanitizePIIResponse()` ಜೊತೆಗೆ
  Responses-API-ಆಕಾರದ ಮರೆಮಾಚುವಿಕೆಯನ್ನು (`maskResponsesOutput` — ಇದು
  `output_text` ಮತ್ತು `output[].content[].text` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ) ಚಲಾಯಿಸುತ್ತದೆ. ಯಾವುದೇ ಪರಿಷ್ಕರಣೆ ಸಂಭವಿಸಿದರೆ,
  ಮಾರ್ಪಡಿಸಲಾದ ಪ್ರತಿಕ್ರಿಯೆಯು ಮೂಲ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಬದಲಿಸುತ್ತದೆ.

ಗಾರ್ಡ್ರೈಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಅದು ಕೇವಲ ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ (`meta.detections`,
`meta.redacted`) ಅಥವಾ ಪುನಃ ಬರೆಯುತ್ತದೆ.

### ಪ್ರಾಂಪ್ಟ್ ಇಂಜೆಕ್ಷನ್ (`promptInjection.ts`)

ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ವಿಷಯದಲ್ಲಿನ ಪ್ರತಿಕೂಲ ರಚನೆಗಳನ್ನು ಪತ್ತೆಹಚ್ಚುತ್ತದೆ ಮತ್ತು ಸಂರಚಿಸಲಾದ
ನೀತಿಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತದೆ. ವರ್ತನೆಯು ಪರಿಸರ ಚರಾಂಶಗಳು ಮತ್ತು ಕನ್ಸ್ಟ್ರಕ್ಟರ್
ಆಯ್ಕೆಗಳಿಂದ ನಿರ್ಧರಿಸಲ್ಪಡುತ್ತದೆ:

| ಸೆಟ್ಟಿಂಗ್         | ಪರಿಸರ ಚರಾಂಶ                                                                                                 | ಪೂರ್ವನಿಯೋಜಿತ | ಪರಿಣಾಮ                                                                                                                                                                                                                       |
| ----------------- | ----------------------------------------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ಸಕ್ರಿಯಗೊಳಿಸಲಾಗಿದೆ | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`       | `false` ಆಗಿರುವಾಗ, ಗಾರ್ಡ್ರೈಲ್ ತಕ್ಷಣವೇ ನಿರ್ಗಮಿಸುತ್ತದೆ.                                                                                                                                                                         |
| ಮೋಡ್              | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`       | ಇಂಜೆಕ್ಷನ್ ನೀತಿ: `block`, `warn`, ಅಥವಾ `log`. (ಹಿಂದಿನ ಹೊಂದಾಣಿಕೆಗಾಗಿ `redact` ಅನ್ನು ಸ್ವೀಕರಿಸಲಾಗುತ್ತದೆ, ಆದರೆ ಅದು ಇಂಜೆಕ್ಷನ್ ಪಠ್ಯವನ್ನು ತೆಗೆದುಹಾಕುವುದಿಲ್ಲ; ವಿನಂತಿಯ PII ಪುನಃ ಬರವಣಿಗೆಯನ್ನು `PII_REDACTION_ENABLED` ನಿಯಂತ್ರಿಸುತ್ತದೆ.) |
| ನಿರ್ಬಂಧ ಮಿತಿ      | `blockThreshold` ಆಯ್ಕೆ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ಪರ್ಯಾಯ ಹೆಸರು `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ನಿರ್ಬಂಧಿಸಲು ಅಗತ್ಯವಿರುವ ಕನಿಷ್ಠ ತೀವ್ರತೆ. ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ Medium ಕೇವಲ ವೀಕ್ಷಣೆಗೆ ಸೀಮಿತವಾಗಿದೆ.                                                                                                                                   |

**ಮೋಡ್ ಆದ್ಯತೆ** (`getMode`): ಕರೆ ಮಾಡುವವರ `options.mode` →
`INJECTION_GUARD_MODE` **DB ವೈಶಿಷ್ಟ್ಯ-ಫ್ಲ್ಯಾಗ್ ಓವರ್ರೈಡ್** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` ಪರಿಸರ ಚರಾಂಶ → `INPUT_SANITIZER_MODE` ಪರಿಸರ ಚರಾಂಶ →
`warn`. ಆದ್ದರಿಂದ ಡ್ಯಾಶ್ಬೋರ್ಡ್ ಓವರ್ರೈಡ್ ಪರಿಸರ ಚರಾಂಶಗಳಿಗಿಂತ ಆದ್ಯತೆ ಪಡೆಯುತ್ತದೆ, ಹೀಗಾಗಿ Feature
Flags UI ಚಾಲನೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ ಅನ್ನು ನೇರವಾಗಿ ನಿಯಂತ್ರಿಸುತ್ತದೆ (ಮರುಪ್ರಾರಂಭ ಅಗತ್ಯವಿಲ್ಲ). DB ಓದುವಿಕೆ ವೈಫಲ್ಯ-ಸುರಕ್ಷಿತವಾಗಿದೆ:
ಅದು ದೋಷಗೊಂಡರೆ, ಗಾರ್ಡ್ ಪರಿಸರ-ಆಧಾರಿತ ವರ್ತನೆಗೆ ಹಿಂತಿರುಗುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ
ಓವರ್ರೈಡ್ ಹೊಂದಿಸದಿದ್ದಾಗ ವರ್ತನೆಯು ಕೇವಲ ಪರಿಸರ-ಆಧಾರಿತ ನಿರ್ಣಯಕ್ಕೆ ಸಮಾನವಾಗಿರುತ್ತದೆ.

ಪತ್ತೆ ಮೂಲಗಳು:

1. `@/shared/utils/inputSanitizer`ನಿಂದ `sanitizeRequest()` (ಪೈಪ್ಲೈನ್ನ
   ಇತರೆಡೆ ಬಳಸಲಾಗುವ ಹಂಚಿಕೆಯ ಪತ್ತೆಕಾರಕ ಸಮೂಹ).
2. ಅಂತರ್ನಿರ್ಮಿತ `DEFAULT_GUARD_PATTERNS` (ಪ್ರಸ್ತುತ `system_override_inline` ಮತ್ತು
   `markdown_system_block`, ಎರಡೂ `high` ತೀವ್ರತೆಯವು).
3. ಕನ್ಸ್ಟ್ರಕ್ಟರ್ ಆಯ್ಕೆಗಳ ಮೂಲಕ ರವಾನಿಸಲಾದ ಐಚ್ಛಿಕ `customPatterns` (ಸ್ಟ್ರಿಂಗ್ಗಳು, regex,
   ಅಥವಾ `{ name, pattern, severity }` ದಾಖಲೆಗಳು).

`mode === "block"` **ಆಗಿರುವಾಗ** ಮತ್ತು ಕನಿಷ್ಠ ಒಂದು ಪತ್ತೆಯಾದ ಅಂಶವು ತೀವ್ರತೆಯ
ಮಿತಿಯನ್ನು ತಲುಪಿದಾಗ, `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ. `warn`/`log` ಮೋಡ್ಗಳಲ್ಲಿ ಗಾರ್ಡ್ರೇಲ್ ಲಾಗ್ ಮಾಡುತ್ತದೆ, ಆದರೆ
ಕರೆಗೆ ಅನುಮತಿಸುತ್ತದೆ. ರಿಜಿಸ್ಟ್ರಿಯ ಮೂಲಕ ಹೋಗದೆ ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಮೌಲ್ಯಮಾಪನ ಮಾಡಬೇಕಾದ
ಕಾಲರ್ಗಳಿಗಾಗಿ ಹಂಚಿಕೆಯ ಸಹಾಯಕ `evaluatePromptInjection()` ಅನ್ನೂ ಎಕ್ಸ್ಪೋರ್ಟ್ ಮಾಡಲಾಗಿದೆ.

**ಸ್ಕ್ಯಾನ್ ಮಿತಿ (v3.8.20):** ಡಿಟೆಕ್ಟರ್ ಸಂಯೋಜಿತ ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯದ **ಮೊದಲ 16 KB** ಅನ್ನು
ಮಾತ್ರ ಪರಿಶೀಲಿಸುತ್ತದೆ — `src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ಬೈಟ್ಗಳು). ಪ್ಯಾಟರ್ನ್ ಲೂಪ್ ಅನ್ನು
ಚಲಾಯಿಸುವ ಮೊದಲು `detectInjection()` ಮತ್ತು `evaluatePromptInjection()` ಎರಡೂ
`slice(0, MAX_INJECTION_SCAN_BYTES)` ಅನ್ನು ಬಳಸುತ್ತವೆ. ಇಂಜೆಕ್ಷನ್ ನಿರ್ದೇಶನಗಳು ಇನ್ಪುಟ್ನ
ಮೇಲ್ಭಾಗದ ಸಮೀಪದಲ್ಲಿರುವುದರಿಂದ, ಪತ್ತೆಹಚ್ಚುವಿಕೆಯ ಸಾಮರ್ಥ್ಯವನ್ನು ದುರ್ಬಲಗೊಳಿಸದೆ
ಬಹು-ನೂರು-KB ಪೇಲೋಡ್ಗಳಲ್ಲಿ regex CPU/GC ಬಳಕೆಯನ್ನು ಇದು ಮಿತಿಗೊಳಿಸುತ್ತದೆ (cf.
#3932, #4041).

### ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಮಾಸ್ಕರ್ (`credentialMasker.ts`)

**ಎರಡೂ** ಹಂತಗಳಲ್ಲಿ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತದೆ ಮತ್ತು ಡೀಫಾಲ್ಟ್ ಸರಪಳಿಯಲ್ಲಿ ಕೊನೆಯದಾಗಿರುತ್ತದೆ (ಆದ್ಯತೆ `95`). ಹೊರಹೋಗುವ
ಪೇಲೋಡ್ನಿಂದ (ಸಂದೇಶದ ವಿಷಯ, ಟೂಲ್-ಕಾಲ್ ಆರ್ಗ್ಯುಮೆಂಟ್ಗಳು, ಟೂಲ್ ಫಲಿತಾಂಶಗಳು) **ಹಾಗೂ**
ಪ್ರೊವೈಡರ್ ಪ್ರತಿಕ್ರಿಯೆಯಿಂದ ಸುಪರಿಚಿತ API-ಕೀ / ರಹಸ್ಯ-ಟೋಕನ್ ಪ್ಯಾಟರ್ನ್ಗಳನ್ನು ಮರೆಮಾಡುತ್ತದೆ; ಹೀಗಾಗಿ
ಪ್ರಾಂಪ್ಟ್ಗೆ ಅಂಟಿಸಲಾದ ಕ್ರೆಡೆನ್ಶಿಯಲ್ (ಅಥವಾ ಟೂಲ್ ಫಲಿತಾಂಶದಿಂದ ಮರಳಿ ಪ್ರತಿಧ್ವನಿಸಲಾದದ್ದು) ಅಪ್ಸ್ಟ್ರೀಮ್
ಪ್ರೊವೈಡರ್ಗೆ ಅಥವಾ ಕ್ಲೈಂಟ್ಗೆ ಮರಳಿ ಸೋರಿಕೆಯಾಗುವುದಿಲ್ಲ.

- **ಆಯ್ಕೆ ಮಾಡಿಕೊಂಡಾಗ ಮಾತ್ರ ಸಕ್ರಿಯ**, PII ಮರೆಮಾಡುವಿಕೆಯಂತೆಯೇ ಅದೇ ನಿಯಮಾವಳಿ (Hard Rule #20-ಗೆ ಹೊಂದಿಕೊಂಡ):
  `settings.credentialRedactionEnabled === true` **ಅಥವಾ**
  `CREDENTIAL_REDACTION_ENABLED=true` ಆಗಿರದಿದ್ದರೆ ನಿಷ್ಕ್ರಿಯವಾಗಿರುತ್ತದೆ. ಇದು ಆಫ್ ಆಗಿರುವಾಗ ಗಾರ್ಡ್ರೇಲ್ ಯಾವುದೇ
  ಕಾರ್ಯ ಮಾಡುವುದಿಲ್ಲ — ಇದು ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ ಮತ್ತು ಎಂದಿಗೂ ಮರುಬರೆಯುವುದಿಲ್ಲ.
- `redactCredentials()` ಸಂಪೂರ್ಣ ಪೇಲೋಡ್/ಪ್ರತಿಕ್ರಿಯೆ ಟ್ರೀ ಮೂಲಕ ಸಾಗುತ್ತದೆ (`walkValue()`,
  ಪ್ರೋಟೋಟೈಪ್-ಪೊಲ್ಯೂಷನ್ನಿಂದ ಸುರಕ್ಷಿತ, `WeakSet` ಮೂಲಕ ಸೈಕಲ್-ಸುರಕ್ಷಿತ) ಮತ್ತು ಹೊಂದಾಣಿಕೆಗಳನ್ನು
  `[REDACTED:<type>]` ಪ್ಲೇಸ್ಹೋಲ್ಡರ್ನಿಂದ ಬದಲಾಯಿಸುತ್ತದೆ; ವಾಸ್ತವವಾಗಿ ಬದಲಾದ
  ಶಾಖೆಗಳನ್ನು ಮಾತ್ರ ಕ್ಲೋನ್ ಮಾಡುತ್ತದೆ.
- `CREDENTIAL_PATTERNS` LLM ಪ್ರೊವೈಡರ್ ಕೀಗಳು (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ಟೋಕನ್ಗಳು (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), ಪಾವತಿ ಕೀಗಳು (Stripe, Square), ಕ್ಲೌಡ್
  ಕೀಗಳು (AWS access key, Twilio, SendGrid, Mailgun), ಪ್ರೈವೇಟ್ ಕೀಗಳು / JWTಗಳು,
  ಕ್ರೆಡೆನ್ಶಿಯಲ್ಗಳನ್ನು ಹೊಂದಿರುವ ಕನೆಕ್ಷನ್ ಸ್ಟ್ರಿಂಗ್ಗಳು (`mongodb://user:pass@...`, ಇತ್ಯಾದಿ), ಮತ್ತು
  ಸಾಮಾನ್ಯ `Authorization`/`x-api-key`/`api-key`/`apikey` ಹೆಡರ್-ಮೌಲ್ಯ
  ಪ್ಯಾಟರ್ನ್ ಅನ್ನು ಒಳಗೊಂಡಿದೆ. ಹೆಡರ್ ರೂಪದ ಕೀಗಳನ್ನು (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ಸಾಮಾನ್ಯ ಪಠ್ಯ regex ಮೂಲಕ ಅಲ್ಲದೆ ರಚನಾತ್ಮಕವಾಗಿ ಮರೆಮಾಡಲಾಗುತ್ತದೆ (ಮೌಲ್ಯವನ್ನು ಮಾತ್ರ;
  `Bearer `/`Basic ` ನಂತಹ ಸ್ಕೀಮ್ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಉಳಿಸಲಾಗುತ್ತದೆ).
- ಗಾರ್ಡ್ರೇಲ್ ಎಂದಿಗೂ ನಿರ್ಬಂಧಿಸುವುದಿಲ್ಲ; ಇದು ಮರುಬರೆಯುತ್ತದೆ (`modifiedPayload` /
  `modifiedResponse`) ಮತ್ತು ಟಿಪ್ಪಣಿ ಸೇರಿಸುತ್ತದೆ (`meta.credentialsRedacted`, `meta.count`).

ರಿಗ್ರೆಷನ್ ಗಾರ್ಡ್: `tests/unit/credential-masker-guardrail.test.ts`.

## ಮೂಲ ಒಪ್ಪಂದ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ಸರಪಳಿಯನ್ನು ತಕ್ಷಣವೇ ಸ್ಥಗಿತಗೊಳಿಸುತ್ತದೆ
  message?: string; // ನಿರ್ಬಂಧಿಸುವಾಗ ಪ್ರದರ್ಶಿಸಲಾಗುತ್ತದೆ
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ವಿನಂತಿಯನ್ನು ಮರುಬರೆಯಲು preCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
  modifiedResponse?: TValue; // ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಮರುಬರೆಯಲು postCall ಮೂಲಕ ಹಿಂತಿರುಗಿಸಲಾಗುತ್ತದೆ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, ಅಥವಾ `{ block: false }` ಇವುಗಳಲ್ಲಿ ಯಾವುದನ್ನಾದರೂ ಹಿಂತಿರುಗಿಸುವ ಮೂಲಕ guardrail "ಯಾವುದೇ ಬದಲಾವಣೆ ಇಲ್ಲ" ಎಂದು ಸೂಚಿಸುತ್ತದೆ. `modifiedPayload`/`modifiedResponse` ಅನ್ನು ಹಿಂತಿರುಗಿಸುವುದರಿಂದ, ನಂತರದ guardrailಗಳಿಗಾಗಿ ಸರಪಳಿಯ ಮೂಲಕ ಹರಿಯುವ ಮೌಲ್ಯವನ್ನು ಅದು ಬದಲಿಸುತ್ತದೆ.
`signal?: AbortSignal` ಕಾಲರ್ನ ಜೀವನಚಕ್ರವನ್ನು guardrailಗಳಿಗೆ ಒಯ್ಯುತ್ತದೆ. ವಿನಂತಿಯ ರದ್ದತಿಯು ಉದ್ದೇಶಪೂರ್ವಕ fail-open ಅಪವಾದವಾಗಿದೆ: media bridgeಗಳು ಕೆಲಸವನ್ನು ನಿಲ್ಲಿಸಿ cleanup ಮಾಡುತ್ತವೆ ಮತ್ತು ಅದನ್ನು ಬೆಂಬಲಿಸುವುದಿಲ್ಲ ಎಂದು ತಿಳಿದಿರುವ ಗುರಿಗೆ raw media ಅನ್ನು ಮರುಸ್ಥಾಪಿಸುವುದಿಲ್ಲ.

## ರಿಜಿಸ್ಟ್ರಿ (`registry.ts`)

singleton `guardrailRegistry` ಈ ಕೆಳಗಿನವುಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ:

- `register(guardrail)` — guardrail ಅನ್ನು ಸೇರಿಸುತ್ತದೆ (ಅಥವಾ normalized name ಆಧಾರದಲ್ಲಿ ಬದಲಿಸುತ್ತದೆ) ಮತ್ತು ಏರಿಕೆ ಕ್ರಮದ `priority` ಪ್ರಕಾರ ಮರು-ವಿಂಗಡಿಸುತ್ತದೆ.
- `clear()` / `list()` — ಆಡಳಿತಾತ್ಮಕ ಸಹಾಯಕಗಳು.
- `runPreCallHooks(payload, context)` — ಸಕ್ರಿಯ guardrailಗಳ ಮೂಲಕ ಪುನರಾವರ್ತಿಸುತ್ತದೆ, `modifiedPayload` ಮೂಲಕ payload ಅನ್ನು ಮುಂದಕ್ಕೆ ಕೊಂಡೊಯ್ಯುತ್ತದೆ ಮತ್ತು ಮೊದಲ `block: true` ದೊರೆತಾಗ ನಿಲ್ಲುತ್ತದೆ.
- `runPostCallHooks(response, context)` — response ಭಾಗದಲ್ಲಿಯೂ ಇದೇ ಹರಿವನ್ನು ಅನುಸರಿಸುತ್ತದೆ.
- `resetGuardrailsForTests({ registerDefaults })` — ಸ್ಥಿತಿಯನ್ನು ತೆರವುಗೊಳಿಸುತ್ತದೆ ಮತ್ತು ಸ್ವಚ್ಛ test isolationಗಾಗಿ ಐಚ್ಛಿಕವಾಗಿ defaults ಅನ್ನು ಮರು-ನೋಂದಾಯಿಸುತ್ತದೆ.

ಎರಡೂ runnerಗಳು `{ blocked, payload|response, results, guardrail?, message? }` ಅನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತವೆ, ಇಲ್ಲಿ `results` ಎಂಬುದು ಪ್ರತಿಯೊಂದು guardrailಗೆ ಸಂಬಂಧಿಸಿದ `blocked`, `skipped`, `modified`, `error`, ಮತ್ತು `meta` ಕ್ಷೇತ್ರಗಳನ್ನು ಒಳಗೊಂಡಿರುವ `GuardrailExecutionResult` recordಗಳ array ಆಗಿದ್ದು, tracingಗೆ ಉಪಯುಕ್ತವಾಗಿದೆ.

### ಪ್ರತಿ ವಿನಂತಿಗೆ Guardrailಗಳನ್ನು ನಿಷ್ಕ್ರಿಯಗೊಳಿಸುವುದು

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` ಪ್ರಸ್ತುತ ವಿನಂತಿಗಾಗಿ ಬಿಟ್ಟುಬಿಡಬೇಕಾದ guardrail ಹೆಸರುಗಳ duplicate ತೆಗೆದುಹಾಕಿದ ಪಟ್ಟಿಯನ್ನು ಒಟ್ಟುಗೂಡಿಸುತ್ತದೆ. ಮೂಲಗಳು (ಎಲ್ಲವೂ ಐಚ್ಛಿಕ, ಎಲ್ಲವನ್ನೂ ವಿಲೀನಗೊಳಿಸಲಾಗುತ್ತದೆ):

- `apiKeyInfo.disabledGuardrails`
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `disabledGuardrails` (top-level)
- ವಿನಂತಿಯ bodyಯಲ್ಲಿನ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (ಅಥವಾ ಹಳೆಯ
  `x-disabled-guardrails`)

ಮೌಲ್ಯಗಳು stringಗಳ array ಆಗಿರಬಹುದು ಅಥವಾ comma-separated string ಆಗಿರಬಹುದು; ಹೆಸರುಗಳನ್ನು lowercase kebab-caseಗೆ normalize ಮಾಡಲಾಗುತ್ತದೆ (`pii_masker` → `pii-masker`). ಫಲಿತಾಂಶವನ್ನು `context.disabledGuardrails` ಮೂಲಕ registryಗೆ ರವಾನಿಸಲಾಗುತ್ತದೆ, ಅದು ಹೊಂದಿಕೆಯಾಗುವ guardrailಗಳನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ (`results` ನಲ್ಲಿ `skipped: true`).

## ಕಾರ್ಯಗತಗೊಳಿಸುವ ಕ್ರಮ

`src/sse/handlers/chat.ts` ಮತ್ತು
`open-sse/handlers/chatCore.ts` ಮೂಲಕ ಹರಿಯುವ ಪ್ರತಿ ವಿನಂತಿಗಾಗಿ:

1. `resolveDisabledGuardrails(...)` API ಕೀ, ಬಾಡಿ ಮತ್ತು ಹೆಡರ್ಗಳಿಂದ ಬಿಟ್ಟುಬಿಡುವ ಪಟ್ಟಿಯನ್ನು ರಚಿಸುತ್ತದೆ.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು ಆದ್ಯತೆಯ ಆರೋಹಣ ಕ್ರಮದಲ್ಲಿ ಚಲಾಯಿಸುತ್ತದೆ:
   - ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಲಾದ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `skipped` ಎಂದು ದಾಖಲಿಸಲಾಗುತ್ತದೆ.
   - ಪ್ರತಿ ಗಾರ್ಡ್ರೇಲ್ನ `preCall`, `modifiedPayload` ಮೂಲಕ ಪೇಲೋಡ್ ಅನ್ನು ಮರುಬರೆಯಬಹುದು.
   - ಮೊದಲ `block: true` ಸರಪಳಿಯನ್ನು ಅಲ್ಲಿಯೇ ನಿಲ್ಲಿಸುತ್ತದೆ ಮತ್ತು ಹ್ಯಾಂಡ್ಲರ್ ಗಾರ್ಡ್ರೇಲ್ ನಿರಾಕರಣೆಯ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಹಿಂತಿರುಗಿಸುತ್ತದೆ.
3. (ಸಂಭಾವ್ಯವಾಗಿ ಮರುಬರೆಯಲಾದ) ಪೇಲೋಡ್ ಕಾಂಬೊ ರೂಟಿಂಗ್ ಮತ್ತು ಅಪ್ಸ್ಟ್ರೀಮ್ ಡಿಸ್ಪ್ಯಾಚ್ಗೆ ಹರಿಯುತ್ತದೆ.
4. ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಜೋಡಿಸಿದ ನಂತರ, `guardrailRegistry.runPostCallHooks(...)` ಪ್ರತಿಕ್ರಿಯೆಯ ಮೇಲೆ ಅದೇ ಸರಪಳಿಯನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇಲ್ಲಿ `block: true` ಅಪ್ಸ್ಟ್ರೀಮ್ ಪ್ರತಿಕ್ರಿಯೆಯನ್ನು ಕೈಬಿಡುತ್ತದೆ.

ದೋಷ ಎಸೆಯುವ ಗಾರ್ಡ್ರೇಲ್ಗಳನ್ನು `error: <message>` ಜೊತೆಗೆ ದಾಖಲಿಸಲಾಗುತ್ತದೆ ಮತ್ತು
`logger.warn` ಮೂಲಕ ಲಾಗ್ ಮಾಡಲಾಗುತ್ತದೆ, ಆದರೆ ಸರಪಳಿ ಮುಂದುವರಿಯುತ್ತದೆ — ವಿನ್ಯಾಸದ ಪ್ರಕಾರ ದೋಷ ಸಂಭವಿಸಿದಾಗಲೂ ಅನುಮತಿಸಲಾಗುತ್ತದೆ.

## ಕಸ್ಟಮ್ ಗಾರ್ಡ್ರೈಲ್ಗಳು

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ಹಂತಗಳು:

1. `BaseGuardrail` ಅನ್ನು ವಿಸ್ತರಿಸುವ `src/lib/guardrails/myGuardrail.ts` ಅನ್ನು ರಚಿಸಿ.
2. `preCall` ಮತ್ತು/ಅಥವಾ `postCall` ಅನ್ನು ಅನುಷ್ಠಾನಗೊಳಿಸಿ.
3. ಇಂಪೋರ್ಟ್ ಸಮಯದಲ್ಲಿಯೇ ನೋಂದಾಯಿಸಿ (`registerDefaultGuardrails` ನಿಂದ ಪುಶ್ ಮಾಡಿ) ಅಥವಾ
   ರನ್ಟೈಮ್ನಲ್ಲಿ `guardrailRegistry.register(...)` ಅನ್ನು ಕರೆ ಮಾಡಿ — ಅದೇ ಸಾಮಾನ್ಯೀಕರಿಸಿದ
   ಹೆಸರನ್ನು ಹೊಂದಿರುವ ಯಾವುದೇ ಹಿಂದಿನ ಗಾರ್ಡ್ರೈಲ್ ಅನ್ನು ರಿಜಿಸ್ಟ್ರಿ ಬದಲಿಸುತ್ತದೆ.
4. `tests/unit/` ಅಡಿಯಲ್ಲಿ ಪರೀಕ್ಷೆಗಳನ್ನು ಸೇರಿಸಿ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ಉದಾಹರಣೆಗಳು:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ಪರೀಕ್ಷೆ

ತಿಳಿದಿರುವ ಸ್ಥಿತಿಯಿಂದ ಪ್ರಾರಂಭಿಸಲು ಪರೀಕ್ಷೆಗಳ ನಡುವೆ `resetGuardrailsForTests()` ಅನ್ನು ಬಳಸಿ.
ಖಾಲಿ ರಿಜಿಸ್ಟ್ರಿಯೊಂದಿಗೆ ಪ್ರಾರಂಭಿಸಲು `{ registerDefaults: false }` ಅನ್ನು ಪಾಸ್ ಮಾಡಿ ಮತ್ತು
ಪರೀಕ್ಷೆಯಲ್ಲಿರುವ ಗಾರ್ಡ್ರೈಲ್ಗಳನ್ನು ಮಾತ್ರ ನೋಂದಾಯಿಸಿ. Vision Bridge ಡಿಪೆಂಡೆನ್ಸಿ
ಇಂಜೆಕ್ಷನ್ ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge,
ಸೆಟ್ಟಿಂಗ್ಗಳು, ಸಾಮರ್ಥ್ಯಗಳು, STT ಮಾದರಿ ಆಯ್ಕೆ, ಕ್ರೆಡೆನ್ಶಿಯಲ್ ಪರಿಶೀಲನೆಗಳು ಮತ್ತು
ಟ್ರಾನ್ಸ್ಕ್ರಿಪ್ಷನ್ಗಾಗಿ ಸಮಾನವಾದ ಸೀಮ್ಗಳನ್ನು ಒದಗಿಸುತ್ತದೆ. ಆದ್ದರಿಂದ ಪರೀಕ್ಷೆಗಳು DB
ಅಥವಾ ನೆಟ್ವರ್ಕ್ ಪ್ರವೇಶವಿಲ್ಲದೆಯೇ ಎರಡೂ ಫ್ಲೋಗಳನ್ನು ಪರೀಕ್ಷಿಸಬಹುದು.

## ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ ರೂಟ್ ವ್ಯಾಪ್ತಿ ಮತ್ತು ರೆಡ್-ಟೀಮ್ (ಹಂತ 8 · ಬ್ಲಾಕ್ D)

ಇಂಜೆಕ್ಷನ್-ಗಾರ್ಡ್ (`createInjectionGuard` / `withInjectionGuard`) ಬಳಕೆದಾರರ
ಪ್ರಾಂಪ್ಟ್ಗಳನ್ನು ಸ್ವೀಕರಿಸುವ ಎಲ್ಲಾ ರೂಟ್ಗಳನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ. ಇದು `INJECTION_GUARD_MODE`
ಅನ್ನು ಗೌರವಿಸುತ್ತದೆ (ಡೀಫಾಲ್ಟ್ `warn` = ಲಾಗ್ ಮಾತ್ರ; `block` = HTTP 400 `SECURITY_001` ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ).

| ಪ್ರಕಾರ                     | ರೂಟ್ಗಳು                                                                                                                                              | ಡೀಫಾಲ್ಟ್ ಮೋಡ್ |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| ಪಠ್ಯ (ಅಸ್ತಿತ್ವದಲ್ಲಿರುವುದು) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn          |
| ಜನರೇಟಿವ್                   | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn          |
| ಡೇಟಾ                       | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn          |

ಪಠ್ಯ ಹೊರತೆಗೆಯುವಿಕೆ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ.

**ರೆಡ್-ಟೀಮ್ (ಪ್ರತಿ ರಾತ್ರಿ, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block`
ನಲ್ಲಿ ಪ್ರತಿಯೊಂದು ರೂಟ್, `OWASP-LLM` ಕಾರ್ಪಸ್ ಅನ್ನು ನಿರ್ಬಂಧಿಸುತ್ತದೆ ಎಂಬುದನ್ನು promptfoo
ಮೌಲ್ಯೀಕರಿಸುತ್ತದೆ; garak ಪ್ರೋಬ್ಗಳನ್ನು ಚಲಾಯಿಸುತ್ತದೆ (ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ).
ಸ್ಥಿರತೆಗಾಗಿ `moderations` ಅನ್ನು ಸೇರಿಸಲಾಗಿದೆ — ಬ್ಲಾಕ್-ಮೋಡ್ನಲ್ಲಿರುವ ಆಪರೇಟರ್ಗಳು
`resolveDisabledGuardrails` ಮೂಲಕ ಅದಕ್ಕೆ ವಿನಾಯಿತಿ ನೀಡಬಹುದು.

ಪ್ರತಿ ರಾತ್ರಿಯ ವರ್ಕ್ಫ್ಲೋ (`.github/workflows/nightly-llm-security.yml`, cron + ಮ್ಯಾನುಯಲ್
ಡಿಸ್ಪ್ಯಾಚ್) ಎರಡು ಜಾಬ್ಗಳನ್ನು ಹೊಂದಿದೆ:

- **`promptfoo-guard` (ನಿರ್ಬಂಧಿಸುವುದು)** — `INJECTION_GUARD_MODE=block` ಜೊತೆಗೆ
  `promptfoo eval -c promptfooconfig.yaml` ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಪ್ರತಿಯೊಂದು ಪ್ರತಿಕೂಲ
  ಪ್ರಕರಣವು (ಉದಾ. "ಹಿಂದಿನ ಎಲ್ಲಾ ಸೂಚನೆಗಳನ್ನು ನಿರ್ಲಕ್ಷಿಸಿ…", DAN-ಶೈಲಿಯ ಜೈಲ್ಬ್ರೇಕ್ಗಳು)
  ಪ್ರತಿಕ್ರಿಯೆಯು `error.code === "SECURITY_001"` ಅನ್ನು ಹೊಂದಿದೆ ಎಂದು ದೃಢೀಕರಿಸುತ್ತದೆ,
  ಅಂದರೆ ಗಾರ್ಡ್ ನಿಜವಾಗಿಯೂ ವಿನಂತಿಯನ್ನು ತಿರಸ್ಕರಿಸಿದೆ.
- **`garak` (ಸಲಹಾತ್ಮಕ)** — ಸ್ಥಳೀಯ OmniRoute ಇನ್ಸ್ಟನ್ಸ್
  (`http://localhost:20128/v1`) ವಿರುದ್ಧ garak `--probes promptinject,dan,leakreplay`
  ಅನ್ನು ಚಲಾಯಿಸುತ್ತದೆ. ಇದು ಪ್ರೊವೈಡರ್ ಸೀಕ್ರೆಟ್ (`PROMPTFOO_PROVIDER_KEY`) ಮೇಲೆ
  ಅವಲಂಬಿತವಾಗಿದೆ; ಸೀಕ್ರೆಟ್ ಇಲ್ಲದಿದ್ದರೆ ಸರಾಗವಾಗಿ ಬಿಟ್ಟುಬಿಡುತ್ತದೆ ಮತ್ತು `|| true`
  ಪ್ರತ್ಯಯವನ್ನು ಹೊಂದಿರುತ್ತದೆ, ಆದ್ದರಿಂದ CI ವಿಫಲಗೊಳಿಸದೆಯೇ ವರದಿ ಮಾಡುತ್ತದೆ.

ಗಾರ್ಡ್ ಹೆಲ್ಪರ್ನ (`createInjectionGuard` / `withInjectionGuard`) ವ್ಯಾಪ್ತಿಯು ಪ್ರಾಂಪ್ಟ್
ಹೊಂದಿರುವ ಪ್ರತಿಯೊಂದು `/v1` ರೂಟ್ಗೆ ವಿಸ್ತರಿಸುತ್ತದೆ; ಪ್ರಾಂಪ್ಟ್ ಪಠ್ಯವನ್ನು
`src/shared/utils/inputSanitizer.ts` ನಲ್ಲಿರುವ `extractMessageContents()` ಮೂಲಕ
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ನಿಂದ
ಪಡೆಯಲಾಗುತ್ತದೆ.
