## ಅವಲೋಕನ

ಎಲ್ಲಾ OmniRoute ನಿರ್ವಹಣಾ API ಮಾರ್ಗಗಳನ್ನು ಮೂರು ರಕ್ಷಣಾ ಹಂತಗಳಲ್ಲಿ ಒಂದಕ್ಕೆ
ವರ್ಗೀಕರಿಸಲಾಗಿದೆ. ವರ್ಗೀಕರಣವು ಸ್ಥಿರವಾಗಿದ್ದು, `src/server/authz/routeGuard.ts` ನಲ್ಲಿ
ವ್ಯಾಖ್ಯಾನಿಸಲಾಗಿದೆ ಮತ್ತು ಇತರ ಯಾವುದೇ ದೃಢೀಕರಣ ಶಾಖೆ ಕಾರ್ಯನಿರ್ವಹಿಸುವ ಮೊದಲು ಮೌಲ್ಯಮಾಪನ ಮಾಡಲಾಗುತ್ತದೆ.

## ಹಂತಗಳು

### ಹಂತ 1 — LOCAL_ONLY

**ಜಾರಿಗೊಳಿಸುವುದು:** `isLocalOnlyPath(path)` → ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆ  
**ಬೈಪಾಸ್:** ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ ಯಾವುದೂ ಇಲ್ಲ. ವಿನಂತಿಯು `manage` ವ್ಯಾಪ್ತಿಯ ಮಾನ್ಯ API ಕೀಲಿಯನ್ನು ಹೊಂದಿರುವಾಗ, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿರುವ ಪಥಗಳಿಗೆ ಸೀಮಿತ ವಿನಾಯಿತಿ (ನೋಡಿ [ನಿರ್ವಹಣಾ-ವ್ಯಾಪ್ತಿಯ ವಿನಾಯಿತಿ](#manage-scope-carve-out)).

ಈ ಮಾರ್ಗಗಳು ಚೈಲ್ಡ್ ಪ್ರಕ್ರಿಯೆಗಳನ್ನು ಪ್ರಾರಂಭಿಸುತ್ತವೆ ಅಥವಾ ರನ್ಟೈಮ್ ಕೋಡ್ ಅನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತವೆ. ಅವುಗಳನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಟ್ರಾಫಿಕ್ಗೆ ತೆರೆದಿಡುವುದರಿಂದ, ಮಾನ್ಯ JWT ಅನ್ನು ಪಡೆದ ಆಕ್ರಮಣಕಾರರು (ಉದಾ., Cloudflared/Ngrok ಟನಲ್ ಮೂಲಕ) ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ಪ್ರಚೋದಿಸಲು ಸಾಧ್ಯವಾಗುತ್ತದೆ — ಇದು ಪರಿಚಿತ CVE ವರ್ಗವಾಗಿದೆ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj ಎಂದರೇನು (ಆಕ್ರಮಣ ವರ್ಗ):** ನಿರ್ವಹಣಾ/ಏಜೆಂಟ್ ಸರ್ವರ್ ಒಂದು ಉಪಪ್ರಕ್ರಿಯೆಯನ್ನು (`npm install`, `node`, ಬ್ರೌಸರ್, ಪ್ರಾಕ್ಸಿ, `git`, `tar`, …) ಪ್ರಾರಂಭಿಸುವ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಬಹಿರಂಗಪಡಿಸುತ್ತದೆ. ಆ ಎಂಡ್ಪಾಯಿಂಟ್ ಅನ್ನು ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ತಲುಪಲು ಸಾಧ್ಯವಾದರೆ — ಆಪರೇಟರ್ OmniRoute ಅನ್ನು nginx/Cloudflare/Tailscale ಟನಲ್ನ ಹಿಂದೆ ಇರಿಸಿರುವುದರಿಂದ ಮತ್ತು JWT ಸೋರಿಕೆಯಾಗಿರುವುದರಿಂದ, ಅಥವಾ ದೃಢೀಕರಣವನ್ನು ತಪ್ಪಾಗಿ ಸಂರಚಿಸಿರುವುದರಿಂದ — ಆಕ್ರಮಣಕಾರರು "API ಅನ್ನು ಕರೆಮಾಡುವುದನ್ನು" "ಹೋಸ್ಟ್ನಲ್ಲಿ ಕಮಾಂಡ್ ಚಲಾಯಿಸುವುದಾಗಿ" (ರಿಮೋಟ್ ಕೋಡ್ ಕಾರ್ಯಗತಗೊಳಿಸುವಿಕೆ) ಪರಿವರ್ತಿಸುತ್ತಾರೆ. ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪ್ರತಿಯೊಂದು ಮಾರ್ಗದಲ್ಲೂ **ಯಾವುದೇ ದೃಢೀಕರಣ ಪರಿಶೀಲನೆಗಿಂತ ಮೊದಲು, ಷರತ್ತಿಲ್ಲದೆ ಲೂಪ್ಬ್ಯಾಕ್ ಹೋಸ್ಟ್ ಪರಿಶೀಲನೆಯನ್ನು** ಜಾರಿಗೊಳಿಸುವ ಮೂಲಕ OmniRoute ಇದನ್ನು ತಡೆಯುತ್ತದೆ: ಟನಲ್ ಮೂಲಕ ಸೋರಿಕೆಯಾದ ಟೋಕನ್ ಇದ್ದರೂ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸುವಿಕೆಯನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ.

**ಸಂಪೂರ್ಣ LOCAL_ONLY ಸಮೂಹ.** ಅಧಿಕೃತ ಮೂಲವು `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ಆಗಿದೆ; ಕೆಳಗಿನ ಕೋಷ್ಟಕವು ಪ್ರಸ್ತುತ ಸ್ಥಿತಿಯನ್ನು ಪ್ರತಿಬಿಂಬಿಸುತ್ತದೆ. `check-route-guard-membership` ಗೇಟ್ ಪ್ರಕ್ರಿಯೆ ಪ್ರಾರಂಭಿಸಬಲ್ಲ ಪೂರ್ವಪ್ರತ್ಯಯಗಳ ಅಡಿಯಲ್ಲಿರುವ ಪ್ರತಿಯೊಂದು `route.ts` ಅನ್ನು ಎಣಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದಾದರೂ ಸ್ಥಳೀಯ-ಮಾತ್ರ ಎಂದು ವರ್ಗೀಕರಿಸದಿದ್ದರೆ CI ವಿಫಲಗೊಳ್ಳುತ್ತದೆ.

#### ನಿರ್ವಹಣಾ-ಸ್ಕೋಪ್ ವಿನಾಯಿತಿ

LOCAL_ONLY ಪಥಗಳ ಒಂದು ಉಪಸಮೂಹವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಸ್ಥಳದಿಂದಲೂ ಪ್ರವೇಶಿಸಬಹುದು, ಆದರೆ
ವಿನಂತಿಯು `Authorization: Bearer <api-key>` ಅನ್ನು ಹೊಂದಿದ್ದು, ಅದರ
ಮೆಟಾಡೇಟಾದಲ್ಲಿ `manage` ಸ್ಕೋಪ್ (ಅಥವಾ `admin`) ಇದ್ದರೆ ಮಾತ್ರ. ಈ ವಿನಾಯಿತಿಯನ್ನು
ಪ್ರತಿ-ಪಥಕ್ಕೆ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಮೂಲಕ ಸ್ಪಷ್ಟವಾಗಿ ನಿಯಂತ್ರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ
ಯಾವುದೇ ಹೊಸ LOCAL_ONLY ಪಥದ ಡೀಫಾಲ್ಟ್ ಕಟ್ಟುನಿಟ್ಟಾದ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ. ದೃಢೀಕರಿಸದ
ವಿನಂತಿಗಳು ಮತ್ತು ನಿರ್ವಹಣಾ ಸ್ಕೋಪ್ ಇಲ್ಲದ ಕೀಲಿಗಳನ್ನು ಹೊಂದಿರುವ ವಿನಂತಿಗಳನ್ನು ಇನ್ನೂ
`403 LOCAL_ONLY` ಮೂಲಕ ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ.

ಪ್ರಸ್ತುತ ವಿನಾಯಿತಿ ನೀಡಬಹುದಾದ ಏಕೈಕ ಪೂರ್ವಪ್ರತ್ಯಯ `/api/mcp/` ಆಗಿದೆ. `/api/cli-tools/runtime/` ಮತ್ತು
`/api/services/` ಅನ್ನು ಉದ್ದೇಶಪೂರ್ವಕವಾಗಿ ಹೊರಗಿಡಲಾಗಿದೆ, ಏಕೆಂದರೆ ಅವು ಯಾವುದೇ
ಉಪಪ್ರಕ್ರಿಯೆಗಳನ್ನು (`npm install`, `node`) ಸ್ಪಾನ್ ಮಾಡಬಲ್ಲವು; LOCAL_ONLY ಹಂತವು
ತಡೆಯಲು ಅಸ್ತಿತ್ವದಲ್ಲಿರುವ ನಿಖರವಾದ CVE ವರ್ಗವೇ ಇದು.

**#7895 — `mcp:connect` ಕಿರಿದಾದ ಸ್ಕೋಪ್:** `/api/mcp/` ವಿನಾಯಿತಿಯು ಕಿರಿದಾದ
`mcp:connect` ಸ್ಕೋಪ್ ಹೊಂದಿರುವ Bearer ಕೀಲಿಯನ್ನೂ ಸ್ವೀಕರಿಸುತ್ತದೆ

#### ಆಪರೇಟರ್ ಮಾರ್ಗದರ್ಶನ ಮತ್ತು ಲೆಕ್ಕಪರಿಶೋಧನೆ

ನೀವು OmniRoute ಅನ್ನು ರಿವರ್ಸ್ ಪ್ರಾಕ್ಸಿ ಅಥವಾ ಟನಲ್ (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ಹಿಂದೆ ಚಲಾಯಿಸಿದರೆ, ಲೂಪ್ಬ್ಯಾಕ್ ಪರಿಶೀಲನೆಯು ಮೇಲಿನ ಸ್ಪಾನ್-ಸಮರ್ಥ
ಮಾರ್ಗಗಳನ್ನು ಇನ್ನೂ ರಕ್ಷಿಸುತ್ತದೆ — ಕ್ಲೈಂಟ್ ವಿಳಾಸವು ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ವಿನಂತಿಯನ್ನು
`403 LOCAL_ONLY` ಮೂಲಕ **ದೃಢೀಕರಣ ನಡೆಯುವ ಮೊದಲು** ತಿರಸ್ಕರಿಸಲಾಗುತ್ತದೆ, ಆದ್ದರಿಂದ ಸೋರಿಕೆಯಾದ JWT
ಸ್ಪಾನ್ ಅನ್ನು ತಲುಪಲು ಸಾಧ್ಯವಿಲ್ಲ. ಆಪರೇಟರ್ಗೆ ಇನ್ನೂ ಎರಡು ಜವಾಬ್ದಾರಿಗಳು ಉಳಿದಿವೆ:

- **ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ನಂತೆ ನಕಲಿ ಮಾಡಿ 403 ಅನ್ನು "ಸರಿಪಡಿಸಬೇಡಿ".** `X-Forwarded-For: 127.0.0.1` ಅನ್ನು ಹೊಂದಿಸುವುದು, ಅಥವಾ ಮೂಲ ವಿಳಾಸವನ್ನು ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮರುಬರೆಯುವ ಪ್ರಾಕ್ಸಿಯನ್ನು ಬಳಸುವುದು, ಈ ಹಂತವು ಮುಚ್ಚುವ ಅದೇ RCE ವರ್ಗವನ್ನು ಮತ್ತೆ ತೆರೆಯುತ್ತದೆ. ಪ್ರಾಕ್ಸಿಯ ಮೂಲಕ dashboard/API ಅನ್ನು ಬಹಿರಂಗಪಡಿಸಿ — spawn-ಸಾಮರ್ಥ್ಯದ ರೂಟ್ಗಳನ್ನು ಎಂದಿಗೂ ಬಹಿರಂಗಪಡಿಸಬೇಡಿ.
- **manage-scope ಬೈಪಾಸ್ ಅನ್ನು ಕನಿಷ್ಠ ಮಟ್ಟದಲ್ಲಿಡಿ.** `/api/mcp/` ಅನ್ನು ಮಾತ್ರ ಬೈಪಾಸ್ ಮಾಡಬಹುದು, ಅದೂ `manage`-ವ್ಯಾಪ್ತಿಯ API ಕೀಲಿಯೊಂದಿಗೆ ಮಾತ್ರ. `SPAWN_CAPABLE_PREFIXES` ಅನ್ನು ಎಂದಿಗೂ ಬೈಪಾಸ್ ಪಟ್ಟಿಗೆ ಸೇರಿಸಲಾಗುವುದಿಲ್ಲ — zod ಸ್ಕೀಮಾ ಅವುಗಳನ್ನು ತಿರಸ್ಕರಿಸುತ್ತದೆ ಮತ್ತು ರನ್ಟೈಮ್ನಲ್ಲಿ `isLocalOnlyBypassableByManageScope` ಅವುಗಳನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ (ಬಹುಪದರ ರಕ್ಷಣೆ); dashboard ನಲ್ಲಿ "ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ" ಎಂಬುದರ ಅರ್ಥ ಇದೇ. ಅದೇ ನಿರಾಕರಣೆ-ಪಟ್ಟಿಯು spawn ಮಾಡದಿದ್ದರೂ ಎಂದಿಗೂ ದೂರದಿಂದ ಪ್ರವೇಶಿಸಬಾರದ ಕೆಲವು LOCAL_ONLY ರೂಟ್ಗಳನ್ನೂ ಒಳಗೊಂಡಿದೆ — `/api/oauth/kiro/auto-import` (ಹೋಸ್ಟ್ನ ಸ್ಥಳೀಯ Kiro ಕ್ರೆಡೆನ್ಷಿಯಲ್ ಫೈಲ್ಗಳನ್ನು ಓದುತ್ತದೆ), `/api/discovery/` ಮತ್ತು `/api/issue-agent/`. ರನ್ಟೈಮ್ snapshot loader ಕೂಡ ಸಂಗ್ರಹಿತ settings ಸಾಲಿನಿಂದ ಅಂತಹ ನಮೂದುಗಳನ್ನು ಕೈಬಿಡುತ್ತದೆ ಮತ್ತು ಹಳೆಯ JSON import (`/api/settings/import-json`) ಎಂದಿಗೂ ಬೈಪಾಸ್ ಕೀಲಿಗಳನ್ನು ಬರೆಯುವುದಿಲ್ಲ. ಪ್ರತಿಯೊಂದು `LOCAL_ONLY_API_PREFIXES` ನಮೂದು ನಿರಾಕರಣೆ-ಪಟ್ಟಿಯಲ್ಲಿರಬೇಕು ಅಥವಾ ಬೈಪಾಸ್ಗೆ ಅರ್ಹವೇ ಎಂಬುದಕ್ಕಾಗಿ ಪರಿಶೀಲಿಸಲ್ಪಟ್ಟಿರಬೇಕು (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/` ಅಡಿಯಲ್ಲಿರುವ dynamic-segment ಮತ್ತು static-path spawn-ಸಾಮರ್ಥ್ಯದ ರೂಟ್ಗಳು (ಉದಾ. `/login`, `/refresh-cursor`) `src/shared/constants/spawnCapablePrefixes.ts` ನಲ್ಲಿನ regex-ಆಧಾರಿತ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ಸಹಚರದಿಂದ ಆವರಿಸಲ್ಪಟ್ಟಿವೆ, ಸಮತಟ್ಟಾದ `SPAWN_CAPABLE_PREFIXES` array ನಿಂದಲ್ಲ — ಅವುಗಳನ್ನು ಹಿಡಿಯಲು ಸಮತಟ್ಟಾದ array ಸಂಪೂರ್ಣ `/api/providers/` prefix ಅನ್ನು ಒಳಗೊಳ್ಳಬೇಕಾಗುತ್ತದೆ; ಇದರಿಂದ ದೂರಸ್ಥ dashboards provider CRUD ಗಾಗಿ ನ್ಯಾಯಸಮ್ಮತವಾಗಿ ಬಳಸುವ route tree ಅನಗತ್ಯವಾಗಿ ಅತಿ-ವಿಸ್ತಾರಗೊಳ್ಳುತ್ತದೆ.

**ಪ್ರವೇಶದ ಲೆಕ್ಕಪರಿಶೋಧನೆ** — ಹೋಸ್ಟ್ನ ಹೊರಗಿನಿಂದ ಯಾವುದೂ ಈ ರೂಟ್ಗಳನ್ನು ತಲುಪುತ್ತಿಲ್ಲವೆಂದು ಪರಿಶೀಲಿಸಲು:

- `/dashboard/settings/security` ನಲ್ಲಿ **Authorization Inventory** ತೆರೆಯಿರಿ: ಅದು ಸಕ್ರಿಯ LOCAL_ONLY prefix ಪಟ್ಟಿಯನ್ನು, ಯಾವ prefix ಗಳನ್ನು ಬೈಪಾಸ್ ಮಾಡಬಹುದು ಎಂಬುದನ್ನು ಮತ್ತು compile-time spawn-ಸಾಮರ್ಥ್ಯದ ("ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದಂತೆ ಮಾಡಲು ಸಾಧ್ಯವಿಲ್ಲ") ಸಮೂಹವನ್ನು ಪ್ರದರ್ಶಿಸುತ್ತದೆ.
- ಮೇಲಿನ prefix ಗಳೊಂದಿಗೆ ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಕ್ಲೈಂಟ್ ವಿಳಾಸವು ಜೋಡಿಯಾಗಿರುವುದನ್ನು ಕಂಡುಹಿಡಿಯಲು ನಿಮ್ಮ reverse-proxy / access ಲಾಗ್ಗಳಲ್ಲಿ grep ಮಾಡಿ. ಅಂತಹ ಯಾವುದೇ ಹಿಟ್ `403 LOCAL_ONLY` ಬದಲಿಗೆ `200` ಹಿಂತಿರುಗಿಸಿದ್ದರೆ, ಪ್ರಾಕ್ಸಿಯು ನಿಜವಾದ ಕ್ಲೈಂಟ್ IP ಅನ್ನು ಮರೆಮಾಚುತ್ತಿದೆ ಎಂದರ್ಥ — ಪ್ರಾಕ್ಸಿಯನ್ನು ಸರಿಪಡಿಸಿ.
- ಈ ಪಥಗಳಲ್ಲಿ ಒಂದಕ್ಕಾಗಿ OmniRoute ಲಾಗ್ಗಳಲ್ಲಿನ `403 LOCAL_ONLY`, guard ಉದ್ದೇಶಿಸಿದಂತೆ ಕಾರ್ಯನಿರ್ವಹಿಸುತ್ತಿದೆ ಎಂಬುದನ್ನು ಸೂಚಿಸುತ್ತದೆ; ಅದು ನಿಗ್ರಹಿಸಬೇಕಾದ ದೋಷವಲ್ಲ.

### ಹಂತ 2 — ALWAYS_PROTECTED

**ಇದರಿಂದ ಜಾರಿಗೊಳಿಸಲಾಗಿದೆ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` ಬೈಪಾಸ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡುತ್ತದೆ  
**ಬೈಪಾಸ್:** `requireLogin=false` ಆಗಿರುವಾಗ ಯಾವುದೂ ಇಲ್ಲ; JWT ಯಾವಾಗಲೂ ಅಗತ್ಯ

ಈ ರೂಟ್ಗಳು ವಿನಾಶಕಾರಿ ಅಥವಾ ಹಿಂತಿರುಗಿಸಲಾಗದವು. "ಪಾಸ್ವರ್ಡ್-ರಹಿತ" ಅನುಸ್ಥಾಪನೆಯಲ್ಲಿ ಇವುಗಳನ್ನು ಅನುಮತಿಸಿದರೆ, ಅದೇ LAN ನಲ್ಲಿರುವ ಯಾರಾದರೂ database ಅನ್ನು ಅಳಿಸಬಹುದು ಅಥವಾ server process ಅನ್ನು ಸ್ಥಗಿತಗೊಳಿಸಬಹುದು.

| ಪಥ                                        | ಕಾರಣ                                                                            |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| `/api/shutdown`                           | server process ಅನ್ನು ಕೊನೆಗೊಳಿಸುತ್ತದೆ                                            |
| `/api/settings/database`                  | Database export, import ಮತ್ತು wipe                                              |
| `/api/db-backups`                         | ಸಂಪೂರ್ಣ database backup archive ಪ್ರವೇಶ                                          |
| `/api/settings/export-json`               | ಸಂಪೂರ್ಣ settings blob ಅನ್ನು export ಮಾಡುತ್ತದೆ (ರಹಸ್ಯಗಳನ್ನೂ ಒಳಗೊಂಡಂತೆ)            |
| `/api/settings/import-json`               | ಸಂಪೂರ್ಣ settings blob ಅನ್ನು ಬದಲಿಸುತ್ತದೆ                                         |
| `/api/providers/health-autopilot/actions` | autopilot ಪರಿಹಾರ ಕ್ರಮಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುತ್ತದೆ                                  |
| `/api/settings/obsidian`                  | ಯಾವುದೇ vault root ಗಾಗಿ ಮರುಬಳಕೆ ಮಾಡಬಹುದಾದ WebDAV credentials ಅನ್ನು ಸೃಷ್ಟಿಸುತ್ತದೆ |

**ಉಲ್ಲಂಘನೆಯಾಗಿರುವಾಗ ಪ್ರತಿಕ್ರಿಯೆ:** `401 Authentication required`

`/api/settings/obsidian` ಅದರ `/webdav` child ಅನ್ನು ಒಳಗೊಳ್ಳುತ್ತದೆ: `POST`, ಈ pipeline ನ ಹೊರಗೆ Next.js ಗಿಂತ ಮೊದಲು custom Node layer ಮೂಲಕ ಒದಗಿಸಲಾಗುವ WebDAV file service ಅನ್ನು ಕರೆ ಮಾಡುವವರು ಆಯ್ಕೆಮಾಡಿದ root ಗೆ ನಿರ್ದೇಶಿಸುತ್ತದೆ ಮತ್ತು ಹೊಸದಾಗಿ ಸೃಷ್ಟಿಸಿದ Basic credentials ಅನ್ನು ಪ್ರತಿಧ್ವನಿಸುತ್ತದೆ; `DELETE` ಅವುಗಳನ್ನು ಬದಲಾಯಿಸುತ್ತದೆ ಮತ್ತು parent `POST` Obsidian REST API token ಅನ್ನು ಸಂಗ್ರಹಿಸುತ್ತದೆ. GHSA-62vw ಕೇವಲ `GET` password ಬಹಿರಂಗಪಡಿಸುವಿಕೆಯನ್ನು ಮರೆಮಾಚಿತ್ತು; issuance ಇನ್ನೂ fail-open ಹಂತದಲ್ಲಿಯೇ ಇತ್ತು (GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` ಹೆಚ್ಚುವರಿಯಾಗಿ data directory ಆಗಿರುವ, ಅದರೊಳಗಿರುವ ಅಥವಾ ಅದನ್ನು ಒಳಗೊಂಡಿರುವ vault ಅನ್ನು ನಿರಾಕರಿಸುತ್ತದೆ.

#### Credential export ಗಳು operator ಗೆ ಮಾತ್ರ

ಮೇಲಿನ ಹಂತವು _ಯಾವುದಾದರೂ_ credential ಅಗತ್ಯವಿದೆಯೇ ಎಂಬುದನ್ನು ಮಾತ್ರ ನಿರ್ಧರಿಸುತ್ತದೆ. ಸಂಗ್ರಹಿಸಿದ credentials ಅನ್ನು download ಮಾಡುವ ರೂಟ್ಗಳು handler ನಲ್ಲಿ ಎರಡನೇ ಪರಿಶೀಲನೆಯನ್ನು ಸೇರಿಸುತ್ತವೆ: `GET /api/settings/export-json` (decrypt ಮಾಡಿದ provider connections ಮತ್ತು raw API keys), `GET /api/db-backups/export` (SQLite file) ಮತ್ತು `GET /api/db-backups/exportAll` (ಸಂಪೂರ್ಣ archive) ಇವು `requireOperatorCredential()` ಅನ್ನು ಕರೆಯುತ್ತವೆ (`src/lib/api/operatorCredential.ts`). ಇದು dashboard session, local CLI subject ಅಥವಾ login ನಿಷ್ಕ್ರಿಯಗೊಳಿಸಿರುವ instance ಅನ್ನು ಸ್ವೀಕರಿಸುತ್ತದೆ ಮತ್ತು ಯಾವುದೇ scope ನ API keys ಗೆ (`manage` ಮತ್ತು `admin` ಸೇರಿದಂತೆ) ಹಾಗೂ `oma_` access tokens ಗೆ `403` ಉತ್ತರಿಸುತ್ತದೆ. Sync token issuance (`POST /api/sync/tokens`) ಅದೇ helper ಜೊತೆಗೆ ವಿಶ್ವಾಸಾರ್ಹ loopback internal-service token ಅನ್ನು ಬಳಸುತ್ತದೆ.

### ಹೊಸ ಅನುಸ್ಥಾಪನೆಯ bootstrap ಲೂಪ್ಬ್ಯಾಕ್ಗೆ ಮಾತ್ರ — ನಿಜವಾದ peer ಆಧಾರಿತ, `Host` ಆಧಾರಿತವಲ್ಲ

ಯಾವುದೇ management password ಕಾನ್ಫಿಗರ್ ಮಾಡದಿರುವಾಗ (ಮತ್ತು `INITIAL_PASSWORD` ಇಲ್ಲದಿರುವಾಗ), `src/shared/utils/apiAuth.ts` ನಲ್ಲಿನ `isAuthRequired()` ಅನಾಮಧೇಯ bootstrap ಅನ್ನು **loopback peers ಗೆ ಮಾತ್ರ** ತೆರೆದಿಡುತ್ತದೆ. ವಿಶ್ವಾಸಾರ್ಹ peer signals ನಿಂದ, ಈ ಕ್ರಮದಲ್ಲಿ loopback ಅನ್ನು ನಿರ್ಧರಿಸಲಾಗುತ್ತದೆ: token-stamped ನಿಜವಾದ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy ನೋಡುವುದು), pipeline ನ ಸ್ವಂತ `AUTHZ_HEADER_PEER_LOCALITY` verdict (route handlers ನೋಡುವುದು, `OMNIROUTE_PEER_STAMP_TOKEN` ಹೊಂದಿರುವಾಗ ಮಾತ್ರ ವಿಶ್ವಾಸಾರ್ಹ), ಅಥವಾ ನೇರ caller ಗಳ ನಿಜವಾದ socket peer. `Host` / `nextUrl.hostname` ಅನ್ನು ಎಂದಿಗೂ ಪರಿಗಣಿಸಲಾಗುವುದಿಲ್ಲ ಮತ್ತು first-password write (`POST /api/settings/require-login`) ಪ್ರತಿಯೊಂದು network peer ಗೆ ತೆರೆದಿರುವ ಬದಲು ಇದೇ ನಿರ್ಬಂಧಕ್ಕೆ ಒಳಪಟ್ಟಿರುತ್ತದೆ (GHSA-7pq4-8pvv-rx7r). `managementPolicy` ತನ್ನದೇ `peerContext` verdict ಅನ್ನು ಸ್ಪಷ್ಟವಾಗಿ ಕೆಳಗೆ ರವಾನಿಸುತ್ತದೆ; ಆದ್ದರಿಂದ ORIGINAL (strip ಮಾಡುವುದಕ್ಕೆ ಮುಂಚಿನ) request ನ headers ಎಂದಿಗೂ ಅದನ್ನು ನಿರ್ಧರಿಸುವುದಿಲ್ಲ.

### ಹಂತ 3 — MANAGEMENT (ಡೀಫಾಲ್ಟ್)

ಎಲ್ಲಾ ಇತರ ನಿರ್ವಹಣಾ ಮಾರ್ಗಗಳು. `requireLogin=false` ಅನ್ನು ಕಾನ್ಫಿಗರ್ ಮಾಡದ ಹೊರತು ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ. CLI ಟೋಕನ್ಗಳು ಈ ಮಾರ್ಗಗಳಲ್ಲಿ ದೃಢೀಕರಿಸಬಹುದು (ಲೂಪ್ಬ್ಯಾಕ್ + ಮಾನ್ಯ HMAC).

## ಮೌಲ್ಯಮಾಪನ ಕ್ರಮ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ಲೂಪ್ಬ್ಯಾಕ್                                  → ಮುಂದುವರಿಸಿ
     → ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ, manage-scope Bearer
        ಮತ್ತು isLocalOnlyBypassableByManageScope   → ಅನುಮತಿಸಿ (management_key)
     → ಇಲ್ಲದಿದ್ದರೆ                                  → 403 LOCAL_ONLY ತಿರಸ್ಕರಿಸಿ
  2. isInternalModelSyncRequest(ctx)?
     → ಅನುಮತಿಸಿ (system)
  3. hasValidCliToken(headers)?
     → ಅನುಮತಿಸಿ (cli) [ಲೂಪ್ಬ್ಯಾಕ್ + timingSafeEqual HMAC ಪರಿಶೀಲನೆ]
  4. isAlwaysProtectedPath(path) ಅಥವಾ requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ಅನುಮತಿಸಿ (dashboard_session)
     → ಬೈಪಾಸ್ ಮಾಡಲಾಗದ ಪಥದಲ್ಲಿ manage-scope Bearer?
        → ಅನುಮತಿಸಿ (management_key)
     → 401/403 ತಿರಸ್ಕರಿಸಿ
  5. requireLogin=false?
     → ಅನುಮತಿಸಿ (anonymous)
```

ಹಂತ 1ರ manage-scope ಶಾಖೆಯು LOCAL_ONLY ಮಾರ್ಗವನ್ನು ಪೂರೈಸಬಲ್ಲ ಏಕೈಕ ದೃಢೀಕೃತ ಪಥವಾಗಿದೆ; ಅವಧಿ ಮೀರಿದ DB ಸದ್ದಿಲ್ಲದೆ "ನಿರಾಕರಿಸಿ" ಎಂಬುದಕ್ಕೆ ಕೆಳದರ್ಜೆಗಿಳಿಯದಂತೆ auth-backend ವೈಫಲ್ಯ ಸ್ಥಿತಿಯು 503 ಅನ್ನು (403 ಅಲ್ಲ) ಹಿಂದಿರುಗಿಸುತ್ತದೆ.

## ಹೊಸ spawn-ಸಾಮರ್ಥ್ಯವುಳ್ಳ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವುದು

1. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_API_PREFIXES` ಗೆ ಪಥದ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
2. ಹೊಸ ಪೂರ್ವಪ್ರತ್ಯಯಕ್ಕಾಗಿ `isLocalOnlyPath()` true ಅನ್ನು ಹಿಂದಿರುಗಿಸುತ್ತದೆ ಎಂದು ದೃಢಪಡಿಸುವ ಪರೀಕ್ಷೆಯನ್ನು `tests/unit/authz/routeGuard.test.ts` ನಲ್ಲಿ ಸೇರಿಸಿ
3. **ಈ ಹಂತವನ್ನು ಎಂದಿಗೂ ಬಿಟ್ಟುಬಿಡಬೇಡಿ** — `CLAUDE.md` ನಲ್ಲಿರುವ ಕಠಿಣ ನಿಯಮ #15 ಅನ್ನು ನೋಡಿ
4. ನಿರ್ಧರಿಸಿ: ಈ ಮಾರ್ಗವು `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ನಲ್ಲಿಯೂ ಇರಬೇಕೇ?
   ಪೂರ್ವನಿಯೋಜಿತ ಉತ್ತರ **ಇಲ್ಲ**. manage-scope ಹೊಂದಿರುವವರಿಗೆ ಮಾರ್ಗವನ್ನು ಬಹಿರಂಗಪಡಿಸುವುದು ಸುರಕ್ಷಿತವಾಗಿರುವಾಗ ಮಾತ್ರ ಆಯ್ಕೆಮಾಡಿ (ಅಂದರೆ, ಅದು ಬಳಕೆದಾರ-ನಿಯಂತ್ರಿತ ಯಾವುದೇ ಕೋಡ್ ಅನ್ನು spawn ಮಾಡುವುದಿಲ್ಲ).

## manage-scope ಮೂಲಕ ಬೈಪಾಸ್ ಮಾಡಬಹುದಾದ ಪಥವನ್ನು ಸೇರಿಸುವುದು

1. ಮಾರ್ಗವು ಬಳಕೆದಾರರು ಒದಗಿಸಿದ ಕೋಡ್ ಅಥವಾ ಆದೇಶಗಳನ್ನು ಕಾರ್ಯಗತಗೊಳಿಸುವುದಿಲ್ಲ ಎಂಬುದನ್ನು ದೃಢಪಡಿಸಿ. ಅದು ಹಾಗೆ ಮಾಡುತ್ತಿದ್ದರೆ, ನಿಲ್ಲಿಸಿ — ಈ ವಿನಾಯಿತಿಯು ತಪ್ಪಾದ ಸಾಧನವಾಗಿದೆ.
2. `src/server/authz/routeGuard.ts` ನಲ್ಲಿರುವ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ಗೆ ಪೂರ್ವಪ್ರತ್ಯಯವನ್ನು ಸೇರಿಸಿ
3. ಎಲ್ಲಾ ನಾಲ್ಕು ವಿನಂತಿ ಸ್ವರೂಪಗಳಿಗಾಗಿ `tests/unit/authz/management-policy.test.ts` ನಲ್ಲಿ ವ್ಯಾಪ್ತಿಯನ್ನು ಸೇರಿಸಿ: Bearer ಇಲ್ಲ (403), manage Bearer (ಅನುಮತಿಸಿ), manage ಅಲ್ಲದ Bearer (403), ಮತ್ತು manage Bearer ಇದ್ದರೂ `/api/cli-tools/runtime/*` ಕಟ್ಟುನಿಟ್ಟಾಗಿ ಲೂಪ್ಬ್ಯಾಕ್ ಆಗಿಯೇ ಉಳಿಯುತ್ತದೆ ಎಂಬ ಪ್ರತಿ-ಪೂರ್ವಪ್ರತ್ಯಯ ಹಿಂಜರಿತ ಪರೀಕ್ಷೆ.

## OpenAPI ನಲ್ಲಿ ಭದ್ರತಾ ಹಂತಗಳನ್ನು ದಾಖಲಿಸುವುದು

`docs/openapi.yaml` ಗೆ ಹೊಸ ಮಾರ್ಗವನ್ನು ಸೇರಿಸುವಾಗ, ಮಾರ್ಗವನ್ನು `routeGuard.ts` ವರ್ಗೀಕರಿಸಿದ್ದರೆ ಅದಕ್ಕೆ ಅನುಗುಣವಾದ vendor extension ಅನ್ನು ಅನ್ವಯಿಸಿ:

| routeGuard.ts ವರ್ಗೀಕರಣ                     | YAML ಟಿಪ್ಪಣಿ                | ಜಾರಿಗೊಳಿಸುವಿಕೆ                                                     |
| ------------------------------------------ | --------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                  | `x-loopback-only: true`     | ಲೂಪ್ಬ್ಯಾಕ್ ಅಲ್ಲದ ಮೂಲಗಳಿಂದ ಬರುವುದನ್ನು ಬೇಷರತ್ತಾಗಿ ನಿರ್ಬಂಧಿಸಲಾಗುತ್ತದೆ |
| `ALWAYS_PROTECTED_API_PATHS`               | `x-always-protected: true`  | `requireLogin=false` ಇದ್ದರೂ ದೃಢೀಕರಣ ಅಗತ್ಯವಿದೆ                      |
| ಆಂತರಿಕ admin/debug ಮಾರ್ಗ                   | `x-internal: true`          | ಪೂರ್ವನಿಯೋಜಿತವಾಗಿ /dashboard/api-endpoints ನಿಂದ ಮರೆಮಾಡಲಾಗುತ್ತದೆ     |
| ಯಾವುದೂ ಇಲ್ಲ (ಸಾರ್ವಜನಿಕ / ಪ್ರಮಾಣಿತ ದೃಢೀಕರಣ) | (ಯಾವುದೇ ಟಿಪ್ಪಣಿ ಅಗತ್ಯವಿಲ್ಲ) | ಪ್ರಮಾಣಿತ `requireLogin`-ನಿಯಂತ್ರಿತ ಪ್ರವೇಶ                           |

### ಮೌಲ್ಯೀಕರಣ

ಎರಡು ಸ್ಕ್ರಿಪ್ಟ್ಗಳು YAML ಟಿಪ್ಪಣಿಗಳು ಮತ್ತು `routeGuard.ts` ನಡುವಿನ ಸ್ಥಿರತೆಯನ್ನು ಜಾರಿಗೊಳಿಸುತ್ತವೆ:

- `scripts/check/check-openapi-coverage.mjs` — ವ್ಯಾಪ್ತಿ < 99% ಆಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` ಅಥವಾ
  `x-always-protected` ಟಿಪ್ಪಣಿಗಳು compile-time ಸ್ಥಿರಾಂಕಗಳಿಂದ ಭಿನ್ನವಾಗಿದ್ದರೆ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ

ಎರಡೂ ಸ್ಕ್ರಿಪ್ಟ್ಗಳು pre-commit hook ಮತ್ತು CI ನಲ್ಲಿ ಚಲಿಸುತ್ತವೆ.

### ತಪ್ಪು ಧನಾತ್ಮಕ ನಿಯಮ

`routeGuard.ts` ಸ್ಥಿರಾಂಕದಲ್ಲಿ ಇಲ್ಲದ ಮಾರ್ಗದ ಮೇಲೆ `x-always-protected` ಅಥವಾ `x-loopback-only` ಅನ್ನು ಟಿಪ್ಪಣಿಯಾಗಿ ಸೇರಿಸಿದರೆ, ವ್ಯಾಪ್ತಿ ಸ್ಕ್ರಿಪ್ಟ್ ವಿಫಲಗೊಳ್ಳುತ್ತದೆ. ಸರಿಪಡಿಸುವ ವಿಧಾನವೆಂದರೆ ಯಾವಾಗಲೂ YAML ಅನ್ನು `routeGuard.ts` ನಿಜವಾಗಿ ಜಾರಿಗೊಳಿಸುವುದಕ್ಕೆ ಹೊಂದಿಸುವುದು — ಜಾರಿಗೊಳಿಸುವಿಕೆ ತರ್ಕವನ್ನೂ ಅನುಷ್ಠಾನಗೊಳಿಸದೆ `routeGuard.ts` ಗೆ ಮಾರ್ಗಗಳನ್ನು ಸೇರಿಸುವುದಲ್ಲ.
