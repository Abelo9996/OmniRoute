## მიმოხილვა

OmniRoute-ის მართვის API-ის ყველა მარშრუტი დაცვის სამი დონიდან ერთ-ერთს
მიეკუთვნება. კლასიფიკაცია სტატიკურია, განსაზღვრულია `src/server/authz/routeGuard.ts`-ში
და მოწმდება ავტორიზაციის ნებისმიერი სხვა განშტოების შესრულებამდე.

## დონეები

### დონე 1 — LOCAL_ONLY

**უზრუნველყოფილია:** `isLocalOnlyPath(path)` → loopback ჰოსტის შემოწმება  
**გვერდის ავლა:** ნაგულისხმევად შეუძლებელია. ვიწრო გამონაკლისი ვრცელდება
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში შემავალ ბილიკებზე, როდესაც მოთხოვნა შეიცავს მოქმედ
API გასაღებს `manage` მოქმედების არით (იხილეთ [გამონაკლისი manage მოქმედების არისთვის](#manage-scope-carve-out)).

ეს მარშრუტები შვილობილ პროცესებს უშვებს ან შესრულების გარემოს კოდს ასრულებს. მათი
არა-loopback ტრაფიკისთვის გახსნა თავდამსხმელს, რომელმაც მოქმედი JWT მოიპოვა (მაგ.,
Cloudflared/Ngrok გვირაბის მეშვეობით), პროცესების გაშვების საშუალებას მისცემდა — ეს არის ცნობილი CVE
კლასი ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**რა არის GHSA-fhh6-4qxv-rpqj (შეტევის კლასი):** მართვის/აგენტის სერვერი
ხელმისაწვდომს ხდის საბოლოო წერტილს, რომელიც ქვეპროცესს უშვებს (`npm install`, `node`, ბრაუზერს,
პროქსის, `git`, `tar`, …). თუ ეს საბოლოო წერტილი ჰოსტის გარედან ხელმისაწვდომია — რადგან
ოპერატორმა OmniRoute nginx/Cloudflare/Tailscale გვირაბის უკან განათავსა და JWT
გაჟონა, ან ავთენტიფიკაცია არასწორად იყო გამართული — თავდამსხმელი „API-ის გამოძახებას“ „ჰოსტზე
ბრძანების გაშვებად“ აქცევს (კოდის დისტანციური შესრულება). OmniRoute ამას აღკვეთს
**loopback ჰოსტის შემოწმების უპირობოდ, ავთენტიფიკაციის ნებისმიერ შემოწმებამდე აღსრულებით**
ყველა მარშრუტზე, რომელსაც პროცესის გაშვება შეუძლია: გვირაბის გავლით გაჟონილი ტოკენიც კი ვერ მისწვდება პროცესის გაშვებას.

**LOCAL_ONLY-ის სრული ნაკრები.** ავტორიტეტული წყაროა
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ფაილში
`src/server/authz/routeGuard.ts`; ქვემოთ მოცემული ცხრილი მიმდინარე მდგომარეობას ასახავს.
`check-route-guard-membership` შემოწმება პროცესის გაშვების შესაძლებლობის მქონე პრეფიქსების ქვეშ არსებულ ყველა `route.ts`-ს ჩამოთვლის

#### მართვის არეალის გამონაკლისი

LOCAL_ONLY გზების ქვეჯგუფზე წვდომა არალოკალური ინტერფეისიდანაც შეიძლება მხოლოდ და
მხოლოდ მაშინ, თუ მოთხოვნა შეიცავს `Authorization: Bearer <api-key>`-ს, რომლის
მეტამონაცემებიც მოიცავს `manage` არეალს (ან `admin`-ს). გამონაკლისი თითოეული გზისთვის
ცალსახად იმართება `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ის მეშვეობით, რათა
ნებისმიერი ახალი LOCAL_ONLY გზისთვის ნაგულისხმევად კვლავ მკაცრი ლოკალური ინტერფეისის შეზღუდვა მოქმედებდეს. ავტორიზაციის გარეშე
გაგზავნილი მოთხოვნები და მართვის უფლების არმქონე გასაღებებით გაგზავნილი მოთხოვნები კვლავ უარყოფილია
`403 LOCAL_ONLY`-ით.

ამჟამად გამონაკლისის დაშვება მხოლოდ `/api/mcp/` პრეფიქსისთვისაა შესაძლებელი. `/api/cli-tools/runtime/` და
`/api/services/` განზრახ გამორიცხულია, რადგან მათ შეუძლიათ ნებისმიერი

თავიდან ასაცილებლადაც არსებობს LOCAL_ONLY დონე.

#### ოპერატორის მითითებები და აუდიტი

თუ OmniRoute-ს უკუპროქსის ან გვირაბის (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) მიღმა გაუშვებთ, ლოკალური ინტერფეისის შემოწმება კვლავ იცავს ზემოთ ჩამოთვლილ,
პროცესების გაშვების შესაძლებლობის მქონე მარშრუტებს — მოთხოვნა, რომლის კლიენტის მისამართიც არალოკალურია, უარყოფილია
`403 LOCAL_ONLY`-ით **ავტორიზაციის გაშვებამდე**, ამიტომ გაჟონილი JWT გაშვებამდე ვერ მიაღწევს. ოპერატორს
კვლავ ორი პასუხისმგებლობა ეკისრება:

- **ნუ ეცდებით 403-ის „გამოსწორებას“ კლიენტის IP-ის loopback მისამართად გაყალბებით.**
  `X-Forwarded-For: 127.0.0.1`-ის დაყენება ან ისეთი proxy-ის გამოყენება, რომელიც წყაროს მისამართს
  loopback მისამართით ანაცვლებს, ხელახლა ხსნის ზუსტად იმ RCE კლასს, რომელსაც ეს დონე კეტავს.
  proxy-ის გავლით ხელმისაწვდომი გახადეთ dashboard/API — არასოდეს გახადოთ ხელმისაწვდომი პროცესების
  გაშვების უნარის მქონე მარშრუტები.
- **manage-სკოუპის გვერდის ავლა მინიმალური დატოვეთ.** გვერდის ავლა შესაძლებელია მხოლოდ
  `/api/mcp/`-ისთვის და მხოლოდ `manage`-სკოუპის API გასაღებით. `SPAWN_CAPABLE_PREFIXES`
  ვერასოდეს დაემატება გვერდის ავლის სიას — zod schema მათ უარყოფს, ხოლო
  `isLocalOnlyBypassableByManageScope` შესრულებისას მათზე წვდომას კრძალავს (მრავალშრიანი დაცვა),
  რასაც dashboard-ში „გვერდის ავლის დაშვება შეუძლებელია“ ნიშნავს. იგივე უარყოფის სია ასევე
  შეიცავს რამდენიმე LOCAL_ONLY მარშრუტს, რომლებიც პროცესებს არ უშვებენ, თუმცა მათი დისტანციურად
  ხელმისაწვდომობა ასევე დაუშვებელია — `/api/oauth/kiro/auto-import` (კითხულობს ჰოსტზე ლოკალურად
  შენახულ Kiro-ს ავტორიზაციის მონაცემების ფაილებს), `/api/discovery/` და `/api/issue-agent/`.
  შესრულების დროის snapshot-ის ჩამტვირთავი შენახული პარამეტრების ჩანაწერიდან ასეთ ელემენტებსაც
  შლის, ხოლო მოძველებული JSON იმპორტი (`/api/settings/import-json`) გვერდის ავლის გასაღებებს
  არასოდეს წერს. `LOCAL_ONLY_API_PREFIXES`-ის თითოეული ელემენტი ან უარყოფის სიაში უნდა იყოს,
  ან უნდა შემოწმდეს, როგორც გვერდის ავლისთვის დაშვებული
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`-ის ქვეშ
  არსებული დინამიკური სეგმენტებისა და სტატიკური ბილიკების მქონე, პროცესების გაშვების უნარის
  მარშრუტები (მაგალითად, `/login`, `/refresh-cursor`) დაფარულია regex-ზე დაფუძნებული
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` თანმხლები მექანიზმით
  `src/shared/constants/spawnCapablePrefixes.ts`-ში და არა ბრტყელი `SPAWN_CAPABLE_PREFIXES`
  მასივით — მათ დასაფარად ბრტყელ მასივს მთლიანი `/api/providers/` პრეფიქსის დაფარვა
  დასჭირდებოდა, რაც ზედმეტად გააფართოებდა იმ მარშრუტების ხეს, რომელსაც დისტანციური dashboard-ები
  provider-ების CRUD ოპერაციებისთვის კანონიერად იყენებენ.

  გაშვების მდგომარეობის ასლის ჩამტვირთველი ასეთ ჩანაწერებს შენახული პარამეტრების სტრიქონიდანაც შლის, ხოლო ძველი JSON იმპორტი (`/api/settings/import-json`) გვერდის ავლის გასაღებებს არასოდეს წერს. `LOCAL_ONLY_API_PREFIXES`-ის ყოველი ჩანაწერი ან აკრძალვის სიაში უნდა იყოს, ან შემოწმების შემდეგ გვერდის ავლისთვის დაშვებულად ჩაითვალოს. (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)

**წვდომის აუდიტი** — იმის შესამოწმებლად, რომ ამ მარშრუტებზე ჰოსტის გარედან არაფერი ხვდება:

- გახსენით **Authorization Inventory** მისამართზე `/dashboard/settings/security`: ის აჩვენებს
  მოქმედ LOCAL_ONLY პრეფიქსების სიას, პრეფიქსებს, რომლებზეც გვერდის ავლა დასაშვებია, და
  კომპილაციის დროს განსაზღვრულ, პროცესების გაშვების უნარის მქონე („გვერდის ავლის დაშვება
  შეუძლებელია“) ნაკრებს.
- თქვენს reverse-proxy / წვდომის ჟურნალებში მოძებნეთ ზემოთ მოცემული პრეფიქსები, რომლებიც
  დაწყვილებულია არა-loopback კლიენტის მისამართთან. ნებისმიერი ასეთი მოთხოვნა, რომელმაც
  `403 LOCAL_ONLY`-ის ნაცვლად `200` დააბრუნა, ნიშნავს, რომ proxy რეალურ კლიენტის IP-ს
  ნიღბავს — შეასწორეთ proxy.
- OmniRoute-ის ჟურნალებში ერთ-ერთი ასეთი ბილიკისთვის `403 LOCAL_ONLY` ნიშნავს, რომ დამცავი
  მექანიზმი დანიშნულებისამებრ მუშაობს და არა იმას, რომ ეს ჩასახშობი შეცდომაა.

`GET`-ით პაროლის გამჟღავნება დაფარა; მონაცემების გაცემა კვლავ fail-open დონეზე რჩებოდა
(GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` დამატებით უარს ამბობს vault-ზე, რომელიც
მონაცემთა დირექტორიაა, მის შიგნით მდებარეობს ან მას შეიცავს.

#### ავტორიზაციის მონაცემების ექსპორტი მხოლოდ ოპერატორისთვისაა

ზემოთ მოცემული დონე მხოლოდ იმას განსაზღვრავს, საჭიროა თუ არა _რაიმე_ ავტორიზაციის მონაცემი.
მარშრუტები, რომლებიც შენახულ ავტორიზაციის მონაცემებს ჩამოტვირთავენ, handler-ში მეორე შემოწმებას
ამატებენ: `GET /api/settings/export-json` (გაშიფრული provider კავშირები და დაუმუშავებელი API
გასაღებები), `GET /api/db-backups/export` (SQLite ფაილი) და `GET /api/db-backups/exportAll`
(სრული არქივი) იძახებენ `requireOperatorCredential()`-ს
(`src/lib/api/operatorCredential.ts`). ის იღებს dashboard-ის სესიას, ლოკალური CLI-ის სუბიექტს
ან ინსტანციას, რომელშიც შესვლა გამორთულია, ხოლო ნებისმიერი სკოუპის API გასაღებს (`manage`-ისა
და `admin`-ის ჩათვლით) და `oma_` წვდომის token-ებს `403`-ით პასუხობს. სინქრონიზაციის
token-ის გაცემა (`POST /api/sync/tokens`) იყენებს იმავე helper-ს და დამატებით — სანდო loopback
შიდა სერვისის token-ს.

### ახალი ინსტალაციის საწყისი კონფიგურაცია მხოლოდ loopback-იდანაა შესაძლებელი — რეალური peer-ის მიხედვით და არა `Host`-ის

როდესაც მართვის პაროლი კონფიგურირებული არ არის (და არც `INITIAL_PASSWORD` არსებობს),
`src/shared/utils/apiAuth.ts`-ში `isAuthRequired()` ანონიმურ საწყის კონფიგურაციას ღიას ტოვებს
**მხოლოდ loopback peer-ებისთვის**. loopback შემდეგი პრიორიტეტით განისაზღვრება სანდო peer
სიგნალებიდან: token-ით მონიშნული რეალური TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`,
რასაც policy ხედავს), pipeline-ის საკუთარი `AUTHZ_HEADER_PEER_LOCALITY` ვერდიქტი (რასაც
მარშრუტების handler-ები ხედავენ და რომელიც სანდოა მხოლოდ მაშინ, როცა
`OMNIROUTE_PEER_STAMP_TOKEN` დაყენებულია), ან პირდაპირი გამომძახებლებისთვის რეალური socket
peer. `Host` / `nextUrl.hostname` არასოდეს მოწმდება, ხოლო პაროლის პირველად ჩაწერა
(`POST /api/settings/require-login`) იმავე შეზღუდვას ექვემდებარება და ყველა ქსელური
peer-ისთვის ღია არ არის (GHSA-7pq4-8pvv-rx7r). `managementPolicy` საკუთარ `peerContext`
ვერდიქტს პირდაპირ გადასცემს ქვემოთ, ამიტომ გადაწყვეტილებას ORIGINAL (გასუფთავებამდე)
მოთხოვნის header-ები არასოდეს განსაზღვრავს.

### დონე 3 — MANAGEMENT (ნაგულისხმევი)

ყველა სხვა მართვის მარშრუტი. ავთენტიფიკაცია სავალდებულოა, თუ კონფიგურაციაში `requireLogin=false` არ არის მითითებული. CLI ტოკენებით შესაძლებელია ამ მარშრუტებზე ავთენტიფიკაცია (loopback + მოქმედი HMAC).

## შეფასების თანმიმდევრობა

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → შემდეგ ეტაპზე გადასვლა
     → non-loopback, manage-სკოპის Bearer
        AND isLocalOnlyBypassableByManageScope   → დაშვება (management_key)
     → სხვა შემთხვევაში                           → უარყოფა 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → დაშვება (system)
  3. hasValidCliToken(headers)?
     → დაშვება (cli) [loopback + timingSafeEqual HMAC შემოწმება]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → დაშვება (dashboard_session)
     → manage-სკოპის Bearer არაგვერდასავლელ მარშრუტზე?
        → დაშვება (management_key)
     → უარყოფა 401/403
  5. requireLogin=false?
     → დაშვება (anonymous)
```

1-ლი ნაბიჯის manage-სკოპის განშტოება ერთადერთი ავთენტიფიცირებული გზაა, რომელსაც
LOCAL_ONLY მარშრუტის დაკმაყოფილება შეუძლია; ავთენტიფიკაციის ბექენდის გაუმართაობის
რეჟიმი აბრუნებს 503-ს (და არა 403-ს), რათა ვადაგასული DB შეუმჩნევლად არ
გადავიდეს „უარყოფის“ რეჟიმზე.

## ახალი პროცესის გაშვების უნარის მქონე მარშრუტის დამატება

1. დაამატეთ გზის პრეფიქსი `LOCAL_ONLY_API_PREFIXES`-ში,
   `src/server/authz/routeGuard.ts` ფაილში
2. დაამატეთ ტესტი `tests/unit/authz/routeGuard.test.ts`-ში, რომელიც ადასტურებს,
   რომ ახალი პრეფიქსისთვის `isLocalOnlyPath()` აბრუნებს true-ს
3. **არასოდეს გამოტოვოთ ეს ნაბიჯი** — იხილეთ მკაცრი წესი #15 `CLAUDE.md`-ში
4. გადაწყვიტეთ: უნდა შედიოდეს თუ არა ეს მარშრუტი ასევე
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ში?
   ნაგულისხმევი პასუხია **არა**. ჩართეთ მხოლოდ მაშინ, როდესაც მარშრუტის
   manage-სკოპის მფლობელისთვის გახსნა უსაფრთხოა (ანუ ის არ უშვებს მომხმარებლის
   მიერ სრულად კონტროლირებად ნებისმიერ კოდს).

## manage-სკოპით შემოვლის დაშვების მქონე გზის დამატება

1. დაადასტურეთ, რომ მარშრუტი არ ასრულებს მომხმარებლის მიერ მოწოდებულ კოდს ან
   ბრძანებებს. თუ ასრულებს, შეჩერდით — ეს გამონაკლისი ამისთვის არასწორი
   ინსტრუმენტია.

### ვალიდაცია

ორი სკრიპტი უზრუნველყოფს YAML ანოტაციებსა და `routeGuard.ts`-ს შორის
თანმიმდევრულობას:

- `scripts/check/check-openapi-coverage.mjs` — მარცხდება, თუ დაფარვა < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — მარცხდება, თუ `x-loopback-only`
  ან `x-always-protected` ანოტაციები კომპილაციის დროის კონსტანტებს არ ემთხვევა

ორივე სკრიპტი სრულდება წინასწარი commit-ის hook-ში და CI-ში.

### ცრუ დადებითი შედეგის წესი

თუ `x-always-protected` ან `x-loopback-only` ანოტაცია მითითებულია მარშრუტზე,
რომელიც `routeGuard.ts`-ის კონსტანტაში არ შედის, დაფარვის სკრიპტი მარცხდება.
გამოსავალი ყოველთვის არის YAML-ის შესაბამისობაში მოყვანა იმასთან, რასაც
`routeGuard.ts` რეალურად აღასრულებს — და არა მარშრუტების `routeGuard.ts`-ში
დამატება აღსრულების ლოგიკის იმავდროულად განხორციელების გარეშე.
