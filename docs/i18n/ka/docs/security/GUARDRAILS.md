> **ბოლოს განახლდა:** 2026-08-29 — v3.8.51 (ვიდეო ხიდის ტრანსკრიპტის წარმომავლობა დეკლარირებულია გამომძახებლის მიერ, ჯერ არ არის სერვერის მიერ დამოწმებული — განმარტებულია #11661-ის მიხედვით)

Guardrails უზრუნველყოფენ უსაფრთხოებას, პოლიტიკას და კონტენტის ტრანსფორმაციებს OmniRoute-სა და upstream პროვაიდერებს შორის საზღვარზე. თითოეულ guardrail-ს შეუძლია შეამოწმოს (და სურვილისამებრ უარყოს, გარდაქმნას ან ანოტირება გაუკეთოს) მოთხოვნის payload-ები (`preCall`) და upstream პასუხები (`postCall`).

სისტემა არის **fail-open**: თუ guardrail-ის შესრულებისას შეცდომა მოხდა, რეგისტრატორი აღრიცხავს შეცდომას და აგრძელებს შემდეგ guardrail-ზე, ნაცვლად მოთხოვნის შეწყვეტისა. დაბლოკვა არის მკაფიო გადაწყვეტილება (`block: true`), არასდროს შემთხვევითობა.

### ხედვის ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

ახდენს **ხედვის არმქონე მოდელებისთვის** განკუთვნილი, სურათების შემცველი მოთხოვნების
გადაჭერას და ან მთელ მოთხოვნას გადაამისამართებს ხედვის შესაძლებლობის მქონე მოდელზე,
ან აღმავალ გამოძახებამდე სურათის ნაწილებს ჩაანაცვლებს კონფიგურირებადი ხედვის მოდელის
მიერ შექმნილი ტექსტური აღწერებით. ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს
მულტიმოდალური სასარგებლო დატვირთვების გამჭვირვალედ დამუშავების საშუალებას აძლევს.

ნაკადი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს ხედვის მხარდაჭერა (გარდა იმ შემთხვევისა,
   როცა ის იძულებითი ხიდის სიაში `isVisionBridgeForcedModel` გვხვდება).
2. სურათის ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც დელეგირებას უკეთებს **მედიის ერთიან
   დეტექტორს** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` — ეს არის
   ჭეშმარიტების ერთადერთი წყარო, რომელიც კომბინირებული თავსებადობის ფილტრთან
   საზიაროა. ამოღება ნებადართულია მხოლოდ ზედა დონის იმ ფორმის ნაწილებისთვის,
   რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია (ამოღება↔ჩანაცვლების კონტრაქტი):
   OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` და Responses API `input_image`. ჩადგმული დამთხვევები და
   მხოლოდ ინდიკატორის შემცველი ფორმები კომბინირებული ფილტრისთვის განკუთვნილი
   მასალაა და არასოდეს ამოიღება. გამოტოვება, თუ არცერთი არ მოიძებნა.
3. გაშვების დროის კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ის
   მეშვეობით (`src/shared/constants/modalityBridgeDefaults.ts`): ახალ
   `modalityBridge*` პარამეტრების გასაღებებს უპირატესობა ენიჭება; ძველი
   `visionBridge*` გასაღებები რჩება **ერთი ციკლის სათადარიგო ვარიანტად**
   (უკუგდების ფანჯარა). თუ ხიდი გამორთულია, გამოტოვება ხდება მედიის ნებისმიერ
   შემოვლამდე.
4. რეჟიმის სელექტორი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი)
   წყვეტს, შესრულდეს გადამისამართება თუ აღწერა. გადამისამართება აბრუნებს
   `modifiedPayload`-ს მხოლოდ შეცვლილი `model`-ით, დამატებით კი მეტამონაცემებს
   `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: სურათების რაოდენობის შეზღუდვა `maxImages`-ით, ამოცანაზე მორგებული
   მოთხოვნის შედგენა, აღწერის კეშის შემოწმება, ხედვის მოდელის **პარალელურად**
   გამოძახება (`Promise.allSettled`) და მათ ადგილას `[Image N]: <description>`
   ტექსტური ნაწილების ჩასმა. წარუმატებელი აღწერა იძლევა `null`-ს და სურათის
   თავდაპირველი ნაწილი **შენარჩუნდება** (#4012) — გარდა კომბინირებული აღწერის
   გზისა, როცა ყველა აღწერა წარუმატებელია; ასეთ შემთხვევაში დადასტურებული
   ხედვის არმქონე აღმავალი სისტემა მის ნაცვლად იღებს
   `(მიუწვდომელია — ხედვის შესაძლებლობის მქონე პროვაიდერი დაკავშირებული არ არის)`
   ჩამნაცვლებელს (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) დაბრუნება.

#### API გასაღების მოქმედების არე (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტის
პულებს (`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი
გადამისამართებისა და აღწერისთვის ირჩევს მხოლოდ იმ მოდელებს, რომელთა გამოყენებაც
გასაღებს შეუძლია, და მხოლოდ იმ კავშირებზე, რომელთა გამოყენებაც გასაღებისთვის
ნებადართულია. შემდეგ აღწერის გამოძახება ყოველთვის OmniRoute-ის თვითმარყუჟის
გავლით სრულდება `x-omniroute-self-loop-key-id` სათაურით, რათა მიმღებმა ჩატის
მოთხოვნამ ამ გასაღების კავშირისა და მოდელის პოლიტიკა კვლავ აღასრულოს.
`enforceApiKeyPolicy()` ამ სათაურს მხოლოდ თვითმარყუჟის bearer-თან ერთად
ითვალისწინებს, ამიტომ მას მხოლოდ წვდომის შევიწროება შეუძლია, ხოლო იდენტიფიკატორი,
რომლის ამოცნობაც ვერ ხერხდება, უარყოფილი იქნება.

თუ გასაღებისთვის ხედვის არცერთი მოდელი არ არის ნებადართული, აღწერის გზა განზე
დგება და მოთხოვნა უცვლელად გაივლის — ეს იგივე ღიად გაგრძელების ქცევაა, რაც
გამორთული დამცავი მექანიზმის შემთხვევაში (მეტამონაცემები
`{ skipped: true, reason: "no_permitted_vision_model" }`). მოთხოვნები გასაღების
გარეშე და ამ შეზღუდვების არმქონე გასაღებები ზუსტად ისე იქცევა, როგორც ადრე.

#### ამოცანაზე მორგებული აღწერის მოთხოვნა (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო აღწერის მოთხოვნას ურთავს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს 500 სიმბოლომდე), რათა აღწერა მიმართოს იმისკენ, რაც მომხმარებელმა რეალურად მოითხოვა (codex-vision-proxy შაბლონი), და ხედვის მოდელს ხილული ტექსტის ტრანსკრიფციას სთხოვს. თუ ალამი გამორთულია — ან მომხმარებლის ტექსტი არ არსებობს — საბაზისო მოთხოვნა უცვლელად გამოიყენება.

აღწერის თვითციკლის საკუთარი OpenAI-თავსებადი მოთხოვნა (`callVisionModelSingle()`
ფაილში `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"` —
უპირობოდ, ყოველი გამომძახებლისა და პროვაიდერისთვის, კლიენტის რომელიმე სიგნალზე დამოკიდებულების გარეშე.
დაბალი დეტალიზაციის შერჩევა OCR-ის სიზუსტეს სწორედ იმ ტექსტის ტრანსკრიფციის
ამოცანისთვის აუარესებს, რომელსაც ეს მოთხოვნა ითხოვს, ამიტომ თავად აღწერის გამოძახება ყოველთვის
ითხოვს მაღალ დეტალიზაციას, მიუხედავად იმისა, დეტალიზაციის რა დონე გამოიყენა თავდაპირველმა შემომავალმა მოთხოვნამ. ეს
მხოლოდ აღწერის შიდა მოთხოვნის სხეულზე მოქმედებს; ის არ ცვლის, თუ როგორ
გადასცემს OmniRoute გამომძახებლის საკუთარ `image_url.detail`-ს ძირითად მოთხოვნაში —
ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და მხოლოდ აღმოჩენილი OpenCode კლიენტებისთვის,
`defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის
თვითციკლის Anthropic wire-format განშტოებას `detail` ველი არ აქვს
და არცერთი ნაგულისხმევი მნიშვნელობა მასზე არ მოქმედებს.

#### აღწერის გამოტანის ლიმიტი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს **ლიმიტის გარეშე** — `callVisionModel()`-ის მიერ
დაბრუნებული აღწერა უცვლელად გადაეცემა, რაც არსებულ ქცევას ინარჩუნებს.
100–50000 დიაპაზონის ნებისმიერი მნიშვნელობა აღწერას `…` სუფიქსით ამოკლებს,
ვიდრე ის `[Image N]: <description>` ფორმით კვლავ ჩაისმება
(`VisionBridgeGuardrail.preCall()` ფაილში `src/lib/guardrails/visionBridge.ts`).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR ამოცანებისთვის, სადაც შემდგომ მოდელს
სრული ტრანსკრიფცია სჭირდება; შეამცირეთ ის მრავალსიტყვიანი ხედვის მოდელების მიერ ტოკენების
გამოყენების შესაზღუდად. მართვის პანელის ველი Vision ჩანართის Advanced პანელშია
(`modality-bridge-max-chars` ფაილში `ModalityBridgeVisionTab.tsx`) და 1-დან 99-მდე
ნებისმიერ მნიშვნელობას მინიმალურ 100-მდე ზრდის, ხოლო ცხადად მითითებულ `0`-ს
უცვლელად ტოვებს — `0` დამოუკიდებლად არის Zod-ის დასაშვები მნიშვნელობა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა უბრალოდ
ნაგულისხმევი მნიშვნელობა „არ არის დაყენებული“.

#### აღწერის კეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში განთავსებული LRU + TTL კეში აღწერის შედეგებისთვის, რომელიც მთელი პროცესის მასშტაბით საზიაროა.
გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)`,
სიგრძის პრეფიქსით ჩარჩოების გამოყენებით (ველების საზღვრებს შორის კოლიზიების გარეშე). მოდელის კომპონენტი არის
**კონფიგურირებული** ხიდის მოდელი და არა მოდელი, რომელმაც რეალურად უპასუხა —
`callVisionModel`-მა შეიძლება შიგნით სათადარიგო ვარიანტი გამოიყენოს, ხოლო თითოეული მცდელობის მიხედვით
გასაღების შექმნა კეშს დააქუცმაცებდა. წარუმატებელი აღწერები არასოდეს კეშირდება. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### დისტანციური სურათის ნორმალიზაცია (თვითციკლის აღწერა/base64 ჩამოტვირთვა)

როდესაც ხიდი **დისტანციურ** სურათს თავად ჩამოტვირთავს — Anthropic-ის აღწერის
თვითგამოძახებისა და claude-wire-format base64 გარდაქმნისას
(`ensureBase64ImagesForClaudeWire`), ორივე შემთხვევაში `fetchRemoteImageAsDataUri()`-ის
მეშვეობით ფაილში `visionBridgeHelpers.ts` — მიღებული მონაცემთა URI გადის
`normalizeDataUri()`-ში
(`open-sse/utils/imageNormalize.ts`), ვიდრე ხედვის მოდელის მოთხოვნაში ჩაშენდება.
ზედმეტად დიდი სურათების ზომა მცირდება **2048px სიგრძის გვერდამდე** (რაც ემთხვევა
ზომის ლიმიტს, რომელსაც OpenAI/Anthropic უკვე იყენებენ სერვერის მხარეს), რაც ამცირებს
ატვირთვის ბაიტებს/დაყოვნებას ისე, რომ არ ცვლის იმას, რასაც ხედვის მოდელი ხედავს. ზომის შეცვლა
იყენებს `sharp`-ს, რომელიც დინამიკური იმპორტით იტვირთება: პლატფორმაზე, სადაც მისი ნატიური
ბინარული ფაილი ვერ იტვირთება, `normalizeDataUri()` **არასოდეს წარმოქმნის გამონაკლისს** —
ის საწყისი ბაიტების უცვლელად გადაცემაზე გადადის, ამიტომ აღწერის/base64-გარდაქმნის
გზა ყოველთვის აგრძელებს მუშაობას. არა-სურათული ბაიტებიც (ჩამოტვირთვა, რომელმაც
დეკოდირებადი სურათი არ დააბრუნა) უცვლელად გადაეცემა. ეს ნორმალიზაცია
ვრცელდება მხოლოდ იმ სურათებზე, რომლებსაც ხიდი საკუთარი თვითგამოძახებისთვის ჩამოტვირთავს —
ის არასოდეს გამოიყენება გამომძახებლის დაუმუშავებლად გადაცემულ payload-ზე, რაც შეესაბამება
მხოლოდ თანხმობის შემთხვევაში ცვლილების პრინციპს (მკაცრი წესი #20).

#### პარამეტრების სქემა + მიგრაცია

ახალი `modalityBridge*` გასაღებები Zod-ით მოწმდება `updateSettingsSchema`-ში
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCache*` სამეული და
Audio Bridge-ის მიერ გამოყენებული `modalityBridgeAudio*` ჯგუფი. მიგრაცია
`141_modality_bridge_settings.sql` არსებულ მოძველებულ
`visionBridge*` მნიშვნელობებს შესაბამის ახალ გასაღებებში აკოპირებს (იდემპოტენტურად და ოპერატორის მიერ
დაყენებულ `modalityBridge*` მნიშვნელობას არასოდეს გადაწერს); მოძველებული გასაღებები ერთი
რელიზის ციკლის განმავლობაში კვლავ მიიღება წაკითხვის სათადარიგო ვარიანტის სახით.

#### გამჭვირვალობის სათაური + სტატისტიკა

აღწერით გარდაქმნილ პასუხებს თან ახლავს
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(აგებულია `buildModalityBridgeHeader()`-ით ფაილში `modalityBridge/bridgeStats.ts`,
ემატება `withModalityBridgeHeader()`-ით ფაილში `src/sse/handlers/chatHelpers.ts`).
გადამისამართებულ მოთხოვნებს **არ აქვს** სათაური — payload ხელუხლებელი დარჩა, ხოლო მოდელის
ჩანაცვლება უკვე ჩანს პასუხის სხეულის `model` ველში.

`GET /api/modality-bridge/stats` (მართვის ავტორიზაცია, იგივე დონე, რაც
`GET /api/settings`-ისთვის) აბრუნებს მეხსიერებაში შენახულ, თითოეული მოდალობის
მრიცხველებს
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` მოდალობებისთვის `vision`, `audio` და
`video`. `averageLatencyMs` მნიშვნელის სახით იყენებს `latencySamples`-ს და არა
ყველა მცდელობას; დროის გაზომვის გარეშე შესრულებული ოპერაცია ნულმილიწამიან
ნიმუშს ხელოვნურად არ ქმნის. `bridged` წარმატებული გარდაქმნებისთვის
უკუთავსებად ფსევდონიმად რჩება; წარუმატებელი მცდელობები მას არ ზრდის.
მრიცხველები პროცესის ხელახლა გაშვებისას განზრახ ნულდება
(ტელემეტრია და არა აღრიცხვა).

#### საინფორმაციო დაფის კონფიგურაცია

სპეციალური საინფორმაციო დაფის გვერდია
`/dashboard/settings/modality-bridge`. მისი URL-ით მისაწვდომი `Vision`, `Audio`
და `Video` ჩანართები `tab` მნიშვნელობის შეცვლისას მოთხოვნის პარამეტრებს
ინარჩუნებს. Vision ჩანართი იძლევა ჩართვის, რეჟიმის, მოდელის არჩევის
(ავტომატური ნაგულისხმევის ჩათვლით), დავალებაზე მორგებული მითითებების,
დამატებითი ტაიმაუტის/გამოსახულების/აღწერის სიგრძის/ქეშის ლიმიტების, შესრულების
მრიცხველებისა და დაცული საცდელი მოთხოვნის მართვის საშუალებას. Audio ჩანართიც
აქტიურია: ის გთავაზობთ ჩართვის მართვას, მხოლოდ STT მოდელების ამომრჩევს Auto
ვარიანტით, ტაიმაუტისა და კლიპის მაქსიმალური სიგრძის ლიმიტებს, აუდიოს
მრიცხველებსა და `input_audio` საცდელ ტესტს. Video ჩანართი ფუნქციურია: ის
აჩვენებს FFmpeg/ffprobe-ის შესრულების გარემოს მდგომარეობას — ოთხი ცხადად
განსაზღვრული UI მდგომარეობიდან ერთ-ერთს (`unknown`, სანამ შემოწმება მიმდინარეობს
ან მისი დასრულება ვერ მოხერხდა; `restricted`, როდესაც საინფორმაციო დაფის ჰოსტი
არ არის loopback და შემოწმება კლიენტის მხარეს გამოტოვებულია; `unavailable`,

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

აუდიოს შემცველ ჩატის მოთხოვნებს იჭერს, სანამ ისინი აუდიოშეტანის მხარდაჭერის
არმქონედ ცნობილ სამიზნემდე მიაღწევს. ის ჩატის მოთხოვნას არასოდეს უცვლის
მარშრუტს: აუდიო ნაწილები არსებული OpenAI-თავსებადი მრავალნაწილიანი საბოლოო
წერტილის მეშვეობით ტექსტად გარდაიქმნება, ხოლო არჩეული ჩატის მოდელი მუშაობას
ტექსტური ტრანსკრიპტებით აგრძელებს.

ნაკადი:

1. განსაზღვრეთ `supportsAudio` `getResolvedModelCapabilities()`-ის მეშვეობით.
   უპირატესობა ენიჭება პროვაიდერის რეესტრში ცხადად მითითებულ მეტამონაცემებს,
   შემდეგ მოდელის სტატიკურ მეტამონაცემებს, შემდეგ კი სინქრონიზებულ
   `modalities_input`-ს. გამოცხადებული შეტანის სია `audio`-ს გარეშე არის
   `false`; შესაძლებლობის დამადასტურებელი მონაცემების არარსებობისას რჩება
   `null`. როგორც `false`, ისე `null` ააქტიურებს კონსერვატიულ ხიდს, ხოლო
   `true` მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და თითოეული შეტყობინებიდან
   საზიარო `detectMediaParts()` დეტექტორის მეშვეობით ამოიღეთ ზედა დონის,
   ჩასანაცვლებლად ვარგისი აუდიო ნაწილები. მხარდაჭერილი სადენური ფორმატებია
   OpenAI-ის `input_audio`, `audio_url` და `source.media_type: "audio/*"`.
   ჩადგმული აუდიო მარშრუტიზაციისთვის ამოიცნობა, მაგრამ ჩანაცვლების გზით არ
   იშლება. სამუშაოს მოცულობა შეზღუდულია `modalityBridgeAudioMaxClips`-ით;
   მომდევნო ნაწილები უცვლელი რჩება.
3. გამოიყენეთ კონფიგურირებული `provider/model`, ან მიეცით
   `selectAudioBridgeModel()`-ს საშუალება, სტაბილური კატალოგის რიგითობით
   გაიაროს `AUDIO_TRANSCRIPTION_PROVIDERS` და აირჩიოს პირველი მოდელი, რომელსაც
   აქტიური პროვაიდერის გამოსაყენებელი ავტორიზაციის მონაცემი აქვს.
4. `callAudioTranscription()` base64/data-URI აუდიოს გარდაქმნის მრავალნაწილიან
   `file`-ად, ან ჩამოტვირთავს დისტანციურ `audio_url`-ს მხოლოდ საჯარო
   გასასვლელი დაცვის მექანიზმის გავლით, DNS-ის ფიქსაციითა და 25 MB-იანი
   შეზღუდვით. შემდეგ ის ფაილსა და არჩეულ მოდელს POST მოთხოვნით აგზავნის
   ლოკალურ `/v1/audio/transcriptions` თვითციკლში, ავტორიზაციისთვის
   `resolveSelfLoopBearer()`-ის გამოყენებით. ტრანსკრიფციის არსებული მარშრუტი
   ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, დაყოვნების/სიხშირის ლიმიტის
   მართვასა და პროვაიდერთან გადაგზავნას ასრულებს.
5. წარმატებული გამოძახებები შესაბამის ნაწილებს `[Audio N]: <transcript>`-ით
   ანაცვლებს. გამოძახებები `Promise.allSettled`-ით სრულდება: ცალკეული
   წარუმატებლობა ინარჩუნებს შესაბამის თავდაპირველ აუდიო ნაწილს (#4012
   კონტრაქტი). თუ ყველა გამოძახება წარუმატებელია და სამიზნისთვის
   `supportsAudio === false` დადასტურებულია, ნაწილები ხდება
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი).
   უცნობი სამიზნის (`null`) შემთხვევაში ყველა გამოძახების წარუმატებლობისას
   მოთხოვნა უცვლელი რჩება. მხოლოდ ტექსტის მხარდაჭერის მქონე დადასტურებული
   სამიზნე გამოსაყენებელი STT ავტორიზაციის მონაცემის გარეშე იმავე ცხად
   ჩამნაცვლებელს იღებს ქსელური გამოძახების გარეშე.

წარმატებული ტრანსკრიპტები პროცესის მასშტაბით მოქმედ Modality Bridge-ის
LRU/TTL ქეშს იყენებს. გასაღები აერთიანებს აუდიოს მითითებას, სტაბილურ
`audio-transcription` ოპერაციის იარლიყსა და არჩეულ STT მოდელს; წარუმატებლობები
არასოდეს ქეშირდება. აუდიოს მცდელობები აახლებს საზიარო `bridged`, `cacheHits`,
`failures` და `lastUsedAt` მრიცხველებს. გარდაქმნილ პასუხებს თან ახლავს
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`;
უცვლელი მოთხოვნები Audio Bridge-ის სეგმენტს არ იღებს.

შესრულების გარემოს პარამეტრები DB-ში ინახება და Zod-ით ვალიდირდება:

| გასაღები                      | ნაგულისხმევი მნიშვნელობა | დიაპაზონი            |
| ----------------------------- | ------------------------ | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`                   | —                    |
| `modalityBridgeAudioModel`    | `""`                     | ავტომატური ან STT ID |
| `modalityBridgeAudioTimeout`  | `60000`                  | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`                      | 1–10                 |

საერთო კეშს კვლავ მართავს `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` და `modalityBridgeCacheMaxEntries`.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

სამიზნე სისტემის გამოძახებამდე, რომელსაც ვიდეოს ნატივური მხარდაჭერა დადასტურებულად არ აქვს, Chat Completions-ის `messages`-სა და Responses
API-ის `input`-ში ზედა დონის ვიდეონაწილებს იჭერს.
მხარდაჭერილი ფორმატებია `input_video`, `video_url`, `video_source`, HTTPS URL-ები
და `data:video/*;base64,...` მონაცემთა URI-ები. ტექსტში უბრალო ფაილის სახელები
ვიდეოდ არ განიხილება.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) მართავს მოთხოვნის შემოვლას,
შესაძლებლობის/პოლიტიკის შემოწმებას, თითოეული მოთხოვნის აგრეგაციასა და საპასუხო მონაცემებს.
თითოეულ ვიდეოზე შესასრულებელი სამუშაო — მიღება, მთლიანი შედეგის კეში, კადრების
თანმიმდევრობის აღწერა (რომელიც გამომძახებლის მიერ გამოცხადებულ აუდიოტრანსკრიპტსაც აერთიანებს)
და თითოეული მცდელობის მეტრიკები/შეწყვეტა/გასუფთავება — დამალულია
`videoBridgePipeline.ts`-ში არსებული `processVideoPart`-ის უკან, რომელსაც `preCall`-ის
ციკლში თითოეული ვიდეონაწილისთვის ერთხელ იძახებენ.
ეს მოდული ასევე განსაზღვრავს პორტების მკაფიო საზღვრებს: `VideoMediaBrokerPort`
(ბაიტების მიღება და შერჩეული კადრების ამოღება), `VideoAudioTranscriptionPort`
(გამომძახებლის მიერ გამოცხადებული აუდიოტრანსკრიპტის შერჩეული კადრების აღწერებთან გაერთიანება)
და `VideoDrilldownPort` (კადრების დეტალიზაციის შენახვის საზღვარი; ჯერ არ არის
დაკავშირებული `processVideoPart`-თან — ამჟამად დეტალიზაციის ჩანაწერებს მხოლოდ ცალკე
`/api/modality-bridge/video/drilldown` მარშრუტი წერს).

საჯარო `/v1` მოთხოვნის გზა არასოდეს ახდენს ქვეპროცესის იმპორტირებას ან გამოძახებას.
დისტანციური ვიდეოები იტვირთება 50 MiB შეზღუდვით; ჩაშენებულ base64 ვიდეოებს თითო ვიდეოზე
აქვს კონსერვატიული 36 MiB დეკოდირებული მონაცემების ლიმიტი, რათა მოდელის/შეტყობინებების/ჩარჩოების
გარსი საჯარო JSON მოთხოვნის მიღების 50 MiB ლიმიტში დარჩეს. ჩაშენებული მონაცემების
სიგრძე და დეკოდირებული ზომის შეფასებები მეხსიერების გამოყოფამდე მოწმდება. საწყისი
დისტანციური URL-ისა და ყოველი გადამისამართებისთვის HTTPS სავალდებულოა; გამოიყენება
მხოლოდ საჯარო მისამართებზე გათვლილი არსებული გამავალი მოთხოვნების დამცავი DNS-ის
ფიქსაციით. შემდეგ ბაიტები კვეთს ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` ბროკერის საზღვარს. ეს მარშრუტი ერთდროულად
არის `LOCAL_ONLY` და `SPAWN_CAPABLE`, იღებს მხოლოდ პროცესისთვის სპეციფიკურად

Video გადაფარვა Vision პარამეტრს მემკვიდრეობით იღებს; თუ ორივე ცარიელია, Vision-ის
ავტომარშრუტიზატორი ირჩევს ეფექტურ, ხედვის უნარის მქონე მოდელს. წარმატებული წარწერები
თავდაპირველ ნაწილს ცვლის სტაბილური `[Video description:` პრეფიქსით, რომელიც ასევე
ტექსტს მონიშნავს, როგორც არასანდო, მედიიდან წარმოებულ დაკვირვებას და ქვემდგომ
მოდელებს მიუთითებს, არ შეასრულონ მედიაში აღმოჩენილი ინსტრუქციები. კადრის წარწერის ქეშის გასაღებები
მოიცავს JPEG ბაიტებს, მოთხოვნას, დროის ნიშნულსა და ეფექტურ მოდელს; ქეშდება მხოლოდ წარმატებული
წარწერები. ქეშის ჩანაწერები ინარჩუნებს რეალურად წარმატებული მწარმოებელი მოდელის იდენტობას,
მათ შორის სარეზერვო მოდელისას; სხვადასხვა კადრის სხვადასხვა მოდელის მიერ
შექმნისას bridge აბრუნებს `mixed`-ს. ქეშში დამთხვევა ხელახლა იყენებს ამ მწარმოებლის იდენტობას
და არ ანიჭებს მას მოთხოვნილი მარშრუტიზაციის გეგმის იარლიყს. მთლიანი ვიდეოს შედეგის
ქეშის გასაღები ეფუძნება ყველა შეყვანას, რომელიც გამომავალს ცვლის — მოთხოვნას, ეფექტურ
მოდელს, სემპლირების პოლიტიკას, კადრების რაოდენობას, სემანტიკური ანალიზის რეჟიმს, ნორმალიზებული
ფოკუსის მინიშნების SHA-256
ანაბეჭდს, ფოკუსის ფანჯარას, `transcript`-ს,
`audioTranscript`-სა და საკონტაქტო ფურცლის ალამს — ამიტომ ამ
განზომილებებიდან ნებისმიერის შეცვლა იწვევს ქეშში აცდენას და არასოდეს — მოძველებული შედეგის ხელახლა გამოყენებას.
ვიზუალური დედუპლიკაციის პოლიტიკის ვერსია, ზღვრული მნიშვნელობა და კანდიდატი კადრების შეზღუდული რაოდენობაც
აშკარად შედის შედეგის ქეშის გასაღებსა და მეტამონაცემებში; შესაბამისად, პოლიტიკის ცვლილება ვერ გამოიყენებს
მთლიანი ვიდეოს მოძველებულ აღწერას. შედეგის ქეშის v4 მეტამონაცემები ინახავს რეჟიმსა და
ანაბეჭდს, მაგრამ არასოდეს — მომხმარებლის დაუმუშავებელ დავალებას. დამცავი შეზღუდვების მეტამონაცემები ასახავს როგორც
მოთხოვნილ, ისე ეფექტურ ანალიზის რეჟიმებს; მოთხოვნილი `focused` რეჟიმი გამოსადეგი
მომხმარებლის ტექსტის გარეშე აღირიცხება, როგორც ეფექტურად `full`.

დამცავი მექანიზმი ყველა მხარდაჭერილ ვიდეო ნაწილს ამოიღებს, თუმცა აღწერს არაუმეტეს
`modalityBridgeVideoMaxVideos` რაოდენობისა. სამიზნისთვის, რომლის შემთხვევაშიც დადასტურებულია
`supportsVideo === false`, წარუმატებელი და ლიმიტს გადაცილებული ვიდეოები გარდაიქმნება აშკარა უსაფრთხო
ტექსტურ მარკერებად, რათა არცერთი დაუმუშავებელი ვიდეო არ დარჩეს. როდესაც შესაძლებლობა უცნობია, ეს ნაწილები
ინარჩუნებს ვიდეოს მატარებელს; ნებისმიერი სარეზერვო ტრანსკრიპტი ზემოთ აღწერილ შეზღუდულ ტექსტურ
კონვერტაციას მიჰყვება. სამიზნეები, რომლებისთვისაც `supportsVideo === true`, bridge-ს გვერდს უვლის.
კლიენტის მოთხოვნის გაუქმების სიგნალი ვრცელდება ჩამოტვირთვაზე, ბროკერის რიგზე,
ქვეპროცესებსა და წარწერის გამოძახებებზე; გაუქმება პროცესს ვიდეოებს შორის აჩერებს და არასოდეს უშვებს
დაუმუშავებელ მედიას შეცდომისას.

### PII-ის შემნიღბავი (`piiMasker.ts`)

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** ქმნის payload-ის ასლს, გადის `system`, `messages`, `input` და
  `prompt` ველებს (უბრალო სტრიქონული ელემენტების ჩათვლით) და სტრიქონულ
  `content`/`text` ველებზე იყენებს `processPII()`-ს
  (`@/shared/utils/inputSanitizer`-დან). როდესაც
  `PII_REDACTION_ENABLED=true`, აღმოჩენილი PII გამავალი payload-იდან იფარება.
  ეს დამოუკიდებელია `INPUT_SANITIZER_MODE`-ისგან (რომელიც მხოლოდ prompt-ის
  ინიექციის პოლიტიკას მართავს). როდესაც დაფარვა გამორთულია, გამოძახება
  აღმოჩენათა რაოდენობებს შიგთავსის გადაწერის გარეშე აღრიცხავს.
- **`postCall`** ქმნის პასუხის ღრმა ასლს და უშვებს `sanitizePIIResponse()`-ს,
  ასევე Responses-API-ის ფორმის შემნიღბავს (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე დაფარვა
  განხორციელდება, შეცვლილი პასუხი ჩაანაცვლებს თავდაპირველს.

დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ ანოტაციას აკეთებს
(`meta.detections`, `meta.redacted`) ან გადაწერს.

### Prompt-ის ინიექცია (`promptInjection.ts`)

აღმოაჩენს მომხმარებლის მიერ მოწოდებულ შიგთავსში მტრულ სტრუქტურებს და
უზრუნველყოფს კონფიგურირებული პოლიტიკის აღსრულებას. ქცევას მართავს გარემოს
ცვლადები და კონსტრუქტორის პარამეტრები:

| პარამეტრი         | გარემოს ცვლადი                                                                                                | ნაგულისხმევი | ეფექტი                                                                                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ჩართულია          | `INPUT_SANITIZER_ENABLED`                                                                                     | `true`       | როდესაც `false`-ია, დამცავი მექანიზმი მუშაობას დაუყოვნებლივ ასრულებს.                                                                                                                    |
| რეჟიმი            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                               | `warn`       | ინიექციის პოლიტიკა: `block`, `warn`, ან `log`. (`redact` მიიღება უკუთავსებადობისთვის, მაგრამ ინიექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას `PII_REDACTION_ENABLED` მართავს.) |
| ბლოკირების ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ფსევდონიმი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | ბლოკირებისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად `Medium` მხოლოდ დაკვირვების რეჟიმშია.                                                                                            |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE`-ის **DB ფუნქციის ალმის გადაფარვა** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` გარემოს ცვლადი →
`INPUT_SANITIZER_MODE` გარემოს ცვლადი → `warn`. შესაბამისად, dashboard-ის
გადაფარვას გარემოს ცვლადებზე მეტი პრიორიტეტი აქვს, ამიტომ Feature Flags-ის UI
მუშა დამცავ მექანიზმს რეალურ დროში მართავს (გადატვირთვის გარეშე). DB-დან
წაკითხვა შეცდომამედეგია: შეცდომის შემთხვევაში დამცავი მექანიზმი გარემოს
ცვლადებზე დაფუძნებულ ქცევას უბრუნდება, ხოლო როდესაც გადაფარვა დაყენებული არ
არის, ქცევა მხოლოდ გარემოს ცვლადებით განსაზღვრული ქცევის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` `@/shared/utils/inputSanitizer`-დან (საერთო დეტექტორების
   ნაკრები, რომელიც pipeline-ის სხვა ნაწილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმის).
3. არასავალდებულო `customPatterns`, რომლებიც კონსტრუქტორის პარამეტრებით
   გადაიცემა (სტრიქონები, რეგულარული გამოსახულებები ან
   `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** მინიმუმ ერთი აღმოჩენილი შემთხვევა სიმკაცრის
ზღვარს აკმაყოფილებს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ჩანაწერს
ჟურნალში ამატებს, თუმცა გამოძახებას უშვებს. საერთო დამხმარე `evaluatePromptInjection()` ასევე
ექსპორტირებულია იმ გამომძახებლებისთვის, რომლებსაც მოთხოვნების რეესტრის გვერდის ავლით
შეფასება სჭირდებათ.

### ავტორიზაციის მონაცემების შემნიღბავი (`credentialMasker.ts`)

მუშაობს **ორივე** ეტაპზე და ნაგულისხმევ ჯაჭვში ბოლოა (პრიორიტეტი `95`). გამავალ
მონაცემებში (შეტყობინების შიგთავსი, ინსტრუმენტის გამოძახების არგუმენტები,
ინსტრუმენტის შედეგები) **და** პროვაიდერის პასუხში კარგად ცნობილ API-გასაღებების /
საიდუმლო ტოკენების შაბლონებს ფარავს, რათა მოთხოვნაში ჩასმული ავტორიზაციის მონაცემები
(ან ინსტრუმენტის შედეგის მიერ დაბრუნებული მონაცემები) არც ზემდგომ პროვაიდერს
გადაეცეს და არც კლიენტს დაუბრუნდეს.

- **მხოლოდ აშკარა ჩართვით**, იმავე წესით, როგორც PII-ის რედაქცია (Hard Rule #20-თან
  დაკავშირებული): გამორთულია, თუ `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true` არ არის მითითებული. გამორთულ მდგომარეობაში
  დამცავი მექანიზმი არაფერს აკეთებს — ის არასდროს ბლოკავს და არასდროს გადაწერს.
- `redactCredentials()` მონაცემების/პასუხის სრულ ხეს შემოუვლის (`walkValue()`,
  დაცულია პროტოტიპის დაბინძურებისგან და ციკლებისგან `WeakSet`-ის მეშვეობით) და
  დამთხვევებს `[REDACTED:<type>]` ჩამნაცვლებლით ანაცვლებს, ამასთან კლონავს მხოლოდ
  რეალურად შეცვლილ განშტოებებს.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square),
  ღრუბლოვანი სერვისების გასაღებებს (AWS access key, Twilio, SendGrid, Mailgun),
  კერძო გასაღებებს / JWT-ებს, ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს
  (`mongodb://user:pass@...` და სხვ.) და ზოგად
  `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის შაბლონს.
  სათაურის ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) სტრუქტურულად რედაქტირდება (მხოლოდ მნიშვნელობა; სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია), ნაცვლად ზოგადი ტექსტური regex-ის გამოყენებისა.
- დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ანოტაციებს ამატებს (`meta.credentialsRedacted`, `meta.count`).

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // მოთხოვნის გადასაწერად აბრუნებს preCall
  modifiedResponse?: TValue; // პასუხის გადასაწერად აბრუნებს postCall
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილება არ არის“ მდგომარეობის შესახებ მიანიშნებს `void`-ის, `{}`-ის ან
`{ block: false }`-ის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება
ჩაანაცვლებს ჯაჭვში გამავალ მნიშვნელობას მომდევნო დამცავი მექანიზმებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა წინასწარგანზრახული fail-open გამონაკლისია: მედია-ხიდები წყვეტენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელი მედია არ აღადგინონ სამიზნეზე, რომლის შესახებაც ცნობილია, რომ მას მხარს არ უჭერს.

## რეგისტრატორი (`registry.ts`)

სინგლტონი `guardrailRegistry` აჩვენებს:

- `register(guardrail)` — ამატებს (ან ცვლის ნორმალიზებული სახელით) გარდრეილს და
  ხელახლა ალაგებს ზრდადი `priority`-ის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარეები.
- `runPreCallHooks(payload, context)` — ახდენს აქტიური გარდრეილების იტერაციას,
  გადასცემს `payload`-ს `modifiedPayload`-ის გავლით და ჩერდება პირველ `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე ნაკადი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და სურვილისამებრ
  ხელახლა არეგისტრირებს ნაგულისხმევ პარამეტრებს ტესტის სუფთა იზოლაციისთვის.

ორივე რანერი აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც მოიცავს
თითოეული გარდრეილის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც სასარგებლოა ტრეისინგისთვის.

### გარდრეილების გამორთვა თითო მოთხოვნაზე

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აგროვებს
გარდრეილების სახელების დედუპლიცირებულ სიას, რომლებიც უნდა გამოტოვებულ იქნას
მიმდინარე მოთხოვნისთვის. წყაროები (ყველა არასავალდებულო, ყველა გაერთიანებულია):

- `apiKeyInfo.disabledGuardrails`
- მოთხოვნის სხეული `disabledGuardrails` (ზედა დონის)
- მოთხოვნის სხეული `metadata.disabledGuardrails`
- ჰედერი `x-omniroute-disabled-guardrails` (ან მოძველებული
  `x-disabled-guardrails`)

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი;
სახელები ნორმალიზდება პატარა ასოებით kebab-case-ში (`pii_masker` → `pii-masker`).
შედეგი გადაეცემა `context.disabledGuardrails`-ის გავლით რეგისტრატორს,
რომელიც გამოტოვებს შესაბამის გარდრეილებს (`skipped: true` `results`-ში).

## შესრულების თანმიმდევრობა

ყოველი მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და `open-sse/handlers/chatCore.ts`-ის გავლით:

1.  `resolveDisabledGuardrails(...)` აგებს გამოტოვების სიას API გასაღებიდან, სხეულიდან და სათაურებიდან.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` ასრულებს დამცავ მექანიზმებს პრიორიტეტის ზრდადი თანმიმდევრობით:
    - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
    - თითოეული დამცავი მექანიზმის `preCall`-მა შეიძლება გადაწეროს მონაცემთა პაკეტი `modifiedPayload`-ის მეშვეობით.
    - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს დამცავი მექანიზმის უარყოფის პასუხს.
3.  (პოტენციურად გადაწერილი) მონაცემთა პაკეტი მიედინება კომბინირებულ მარშრუტიზაციასა და ზედა დინების გაგზავნაში.
4.  პასუხის აწყობის შემდეგ, `guardrailRegistry.runPostCallHooks(...)` აწარმოებს იმავე ჯაჭვს პასუხზე. `block: true` აქ აგდებს ზედა დინების პასუხს.

დამცავი მექანიზმები, რომლებიც შეცდომას აგდებენ, აღირიცხება `error: <message>`-ით და აღინიშნება `logger.warn`-ის მეშვეობით, მაგრამ ჯაჭვი გრძელდება — დიზაინით ღიაა წარუმატებლობისთვის.

## კონფიგურაცია

ჩაშენებული დამცავი მექანიზმების მიერ წაკითხული გარემოს ცვლადები:

| ცვლადი                                | გამოიყენება                 | ეფექტი                                                                                                      |
| :------------------------------------ | :-------------------------- | :---------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`          | დააყენეთ `false` გამოვლენის სრულად გამორთვისთვის.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`          | ინექციის პოლიტიკა: `warn`, `block`, ან `log`. მოძველებული მნიშვნელობა `redact` არ გადაწერს ინექციის ტექსტს. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`          | რეჟიმი ინექციის დამცავისთვის; ასევე DB ფუნქციის დროშა, რომელიც **გადაფარავს** გარემოს ცვლადებს (DB > ENV).  |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`          | მინიმალური სიმძიმე, რომელსაც `MODE=block` უარყოფს: `high` (ნაგულისხმევი), `medium`, ან `low`.               |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`          | მოძველებული ფსევდონიმი `INPUT_SANITIZER_BLOCK_THRESHOLD`-ისთვის.                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                | როდესაც `true`, მოთხოვნის PII რედაქტირდება (ინექციის რეჟიმისგან დამოუკიდებლად).                             |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ქვედა დინება) | აკონტროლებს პასუხის მხარის ნიღბის ქცევას.                                                                   |

Modality Bridge-ის დამცავი მექანიზმები კითხულობენ გაშვების კონფიგურაციას DB-ზე დაფუძნებული პარამეტრების საცავიდან (`getSettings()`), და არა გარემოს ცვლადებიდან. Vision-ის ძირითადი გასაღებებია `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, და `modalityBridgeCacheMaxEntries`. მოძველებული `visionBridge*` გასაღებები მიიღება მხოლოდ როგორც დოკუმენტირებული ერთციკლიანი წაკითხვის სარეზერვო ვარიანტი; დაფის ჩანაწერები იყენებენ ძირითად გასაღებებს. ნაგულისხმევი მნიშვნელობები და სარეზერვო გადამწყვეტი განთავსებულია `src/shared/constants/modalityBridgeDefaults.ts`-ში, მოძველებული კონსტანტები შენარჩუნებულია `src/shared/constants/visionBridgeDefaults.ts`-ში.

აუდიო იყენებს `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout`, და `modalityBridgeAudioMaxClips`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. აუდიოს არ აქვს მოძველებული გასაღების სარეზერვო ვარიანტი, რადგან ეს გასაღებები შემოღებულ იქნა Modality Bridge სქემასთან ერთად.

ვიდეო იყენებს `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos`, და `modalityBridgeVideoTimeout`, პლუს გაზიარებულ `modalityBridgeCache*` პარამეტრებს. ის ნაგულისხმევად გამორთულია, რადგან FFmpeg/ffprobe არის არჩევითი ოპერაციული დამოკიდებულებები და კადრების წარწერა ზრდის შეყოვნებასა და მოდელის ღირებულებას.

## მორგებული Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1.  შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც აფართოებს `BaseGuardrail`-ს.
2.  განახორციელეთ `preCall` და/ან `postCall`.
3.  ან დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-დან დამატებით) ან გამოიძახეთ `guardrailRegistry.register(...)` გაშვების დროს — რეესტრი ჩაანაცვლებს ნებისმიერ წინა guardrail-ს იგივე ნორმალიზებული სახელით.
4.  დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

გამოიყენეთ `resetGuardrailsForTests()` ტესტებს შორის, რათა დაიწყოთ ცნობილი მდგომარეობიდან. გადაეცით `{ registerDefaults: false }`, რათა დაიწყოთ ცარიელი რეესტრით და დაარეგისტრიროთ მხოლოდ ტესტირებადი guardrails. Vision Bridge იღებს დამოკიდებულების ინექციას (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge აჩვენებს ექვივალენტურ წერტილებს პარამეტრებისთვის, შესაძლებლობებისთვის, STT მოდელის არჩევისთვის, სერთიფიკატების შემოწმებისთვის და ტრანსკრიფციისთვის. ამიტომ, ტესტებს შეუძლიათ ორივე ნაკადის შემოწმება მონაცემთა ბაზის ან ქსელზე წვდომის გარეშე.

## ინექციისგან დამცავი მარშრუტების დაფარვა და წითელი გუნდი (ფაზა 8 · ბლოკი D)

ინექციისგან დამცავი მექანიზმი (`createInjectionGuard` / `withInjectionGuard`) მოიცავს ყველა მარშრუტს, რომელიც იღებს მომხმარებლის მოთხოვნებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალი; `block` = აბრუნებს HTTP 400 `SECURITY_001`).

| ტიპი            | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| Text (existing) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| Generative      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| Data            | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-ს.

**წითელი გუნდი (ღამის, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს OWASP-LLM კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak აწარმოებს ზონდებს (გამოტოვებს საიდუმლოს გარეშე). `moderations` შედის თანმიმდევრულობისთვის — ოპერატორებს ბლოკირების რეჟიმში შეუძლიათ მისი გათავისუფლება `resolveDisabledGuardrails`-ის მეშვეობით.

ღამის სამუშაო პროცესი (`.github/workflows/nightly-llm-security.yml`, cron + ხელით გაშვება) მოიცავს ორ დავალებას:

- **`promptfoo-guard` (ბლოკირება)** — აწარმოებს `promptfoo eval -c promptfooconfig.yaml`-ს `INJECTION_GUARD_MODE=block`-ით. თითოეული მტრული შემთხვევა (მაგ. „უგულებელყავით ყველა წინა ინსტრუქცია…“, DAN-ის სტილის jailbreaks) ადასტურებს, რომ პასუხი შეიცავს `error.code === "SECURITY_001"`, ანუ guard-მა რეალურად უარყო მოთხოვნა.
- **`garak` (საკონსულტაციო)** — აწარმოებს garak `--probes promptinject,dan,leakreplay`-ს ლოკალური OmniRoute ინსტანციის წინააღმდეგ (`http://localhost:20128/v1`). დაცულია პროვაიდერის საიდუმლო გასაღებით (`PROMPTFOO_PROVIDER_KEY`); გამოტოვებს შეცდომის გარეშე და დამატებულია `|| true`, ასე რომ, ის აფიქსირებს CI-ის ჩავარდნის გარეშე.

guard დამხმარის (`createInjectionGuard` / `withInjectionGuard`) დაფარვა მოიცავს ყველა მოთხოვნის შემცველ `/v1` მარშრუტს; მოთხოვნის ტექსტი ამოღებულია `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`-დან `extractMessageContents()` ფუნქციის მიერ `src/shared/utils/inputSanitizer.ts`-ში.
