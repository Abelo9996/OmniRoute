> **Последнее обновление:** 2026-08-29 — v3.8.51 (Происхождение стенограммы Video Bridge объявляется вызывающей стороной,
> еще не проверено сервером — уточнено согласно #11661)

Защитные механизмы (guardrails) обеспечивают безопасность, соблюдение политик и преобразования контента на границе между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и опционально отклонять, преобразовывать или аннотировать) полезные данные запросов (`preCall`) и ответы вышестоящих систем (`postCall`).

Система является **открытой при сбое (fail-open)**: если защитный механизм выдает ошибку во время выполнения, реестр записывает ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы отклонять запрос. Блокировка — это явное решение (`block: true`), а не случайность.

## Встроенные защитные механизмы

При импорте реестр автоматически загружает шесть защитных механизмов в порядке приоритета
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Имя                 | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **первыми**.

### Мост для изображений (`visionBridge.ts`) — мост модальностей PR-1

Перехватывает запросы с изображениями, направленные **моделям без поддержки изображений**, и либо перенаправляет весь запрос модели с поддержкой изображений, либо перед вызовом вышестоящего сервиса заменяет части с изображениями текстовыми описаниями, созданными настраиваемой моделью обработки изображений. Благодаря этому провайдеры, поддерживающие только текст, могут прозрачно обрабатывать мультимодальные данные.

Порядок работы:

1. Пропустить обработку, если целевая модель уже поддерживает изображения (если только она не присутствует в списке принудительного использования моста `isVisionBridgeForcedModel`).
2. Извлечь части с изображениями с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), которая делегирует работу **унифицированному
   детектору мультимедиа** `detectMediaParts()` из `open-sse/utils/mediaParts.ts` —
   единственному источнику истины, совместно используемому фильтром совместимости комбо.
   Извлечение ограничено разрешённым списком частей верхнего уровня тех форм,
   которые `replaceImageParts` может вставить обратно (контракт извлечения↔замены): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` и Responses API `input_image`. Вложенные совпадения и
   формы, содержащие только индикаторы, предназначены для комбо-фильтра и никогда не извлекаются.
   Пропустить обработку, если ничего не найдено.
3. Определить конфигурацию среды выполнения с помощью `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` сохраняются в качестве **резервного
   варианта на один цикл** (окно отката). Если мост отключён, пропустить обработку до
   любого обхода мультимедиа.
4. Селектор режима (`modalityBridgeVisionMode`, см. таблицу ниже) выбирает
   перенаправление или описание. При перенаправлении возвращается `modifiedPayload`, в котором
   заменено только поле `model`, а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничить количество изображений значением `maxImages`, составить учитывающий задачу промпт,
   проверить кеш описаний, вызвать модель обработки изображений **параллельно**
   (`Promise.allSettled`) и вставить вместо изображений текстовые части
   `[Image N]: <description>`. При ошибке создания описания возвращается `null`, а исходная часть с изображением
   **сохраняется** (#4012) — кроме пути описания для комбо, когда не удалось
   создать ни одного описания: в этом случае подтверждённо не поддерживающему изображения
   вышестоящему сервису вместо изображения передаётся заглушка
   `(unavailable — no vision-capable provider connected)` (#8430).
6. Вернуть `modifiedPayload` и метаданные (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режима (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                          |
| ---------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔            | Устаревшая эвристика без изменений (#6640/#7204): модели, не являющиеся комбо, и модели `auto/` перенаправляются лучшей модели с поддержкой изображений, если у исходной модели уже нет пригодных учётных данных (в этом случае создаётся описание); цели-комбо всегда используют описание.                                                                                        |
| `describe` |              | Всегда создавать описание — блок перенаправления полностью пропускается; всегда отвечает выбранная пользователем модель.                                                                                                                                                                                                                                                           |
| `reroute`  |              | Принудительно перенаправлять: проверка сохранения модели с учётными данными обходится. Проверка учётных данных **целевой модели** перенаправления по-прежнему применяется — если подходящей модели обработки изображений нет, запрос переходит к созданию описания, чтобы необработанные изображения никогда не попадали в серверную систему, поддерживающую только текст (#8430). |

Принудительные режимы завершают выбор **до** запуска автоматической эвристики; поведение `auto`
побайтово идентично защитному механизму до PR-1.

#### Область действия API-ключа (`visionBridgeKeyScope.ts`)

Когда API-ключ вызывающей стороны ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает для
перенаправления и создания описаний только те модели, которые разрешено использовать этому ключу,
и только в разрешённых ему подключениях. Затем вызов для создания описания всегда проходит
через внутренний цикл OmniRoute с заголовком `x-omniroute-self-loop-key-id`, чтобы
принимающий запрос чата повторно применил политики подключений и моделей этого ключа.
`enforceApiKeyPolicy()` учитывает этот заголовок только вместе с bearer-токеном внутреннего цикла,
поэтому он может лишь сужать доступ, а идентификатор, который не удаётся разрешить, отклоняется.

Если ключу не разрешена ни одна модель обработки изображений, путь создания описания не вмешивается,
и запрос передаётся без изменений — это то же отказоустойчивое поведение, что и у отключённого
защитного механизма (метаданные `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений обрабатываются точно так же, как
раньше.

#### Учитывающий задачу промпт для создания описания (`modalityBridgeVisionTaskAware`)

По умолчанию — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту описания, направляя описание на то, о чём фактически спросил пользователь
(паттерн codex-vision-proxy), и просит визуальную модель транскрибировать видимый
текст. Если флаг отключён или пользовательский текст отсутствует, базовый промпт
используется без изменений.

Собственный OpenAI-совместимый запрос цикла описания (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`) всегда запрашивает `image_url.detail: "high"` —
безусловно, для каждого вызывающего кода и провайдера, независимо от каких-либо
сигналов клиента. Выборка с низкой детализацией ухудшает точность OCR именно для
задачи транскрибирования текста, указанной в этом промпте, поэтому сам вызов
описания всегда запрашивает высокую детализацию независимо от уровня детализации,
использованного в исходном входящем запросе. Это влияет только на тело внутреннего
запроса описания; это не изменяет то, как OmniRoute передаёт собственное значение
`image_url.detail` вызывающей стороны в основном запросе — это значение по
умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). В ветке
цикла описания с форматом передачи данных Anthropic поле `detail` отсутствует,
поэтому ни одно из значений по умолчанию на неё не влияет.

#### Ограничение размера результата описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | Значение по умолчанию | Диапазон          |
| ------------------------------ | --------------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`                   | `0` или 100–50000 |

`0` (значение по умолчанию) означает **отсутствие ограничения** — описание,
возвращённое `callVisionModel()`, передаётся без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание с добавлением
суффикса `…` перед его вставкой в виде `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для задач OCR с большим количеством деталей, где
последующей модели нужна полная транскрипция; уменьшите его, чтобы ограничить
расход токенов многословными визуальными моделями. Поле панели управления
находится в разделе Advanced вкладки Vision
(`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и повышает любое
значение от 1 до 99 до минимального порога 100, оставляя явно заданный `0` без
изменений — `0` сам по себе является допустимым значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию для состояния «не задано».

#### Кэш описаний (`modalityBridge/bridgeCache.ts`)

Внутрипроцессный кэш LRU + TTL для результатов описания, совместно используемый
всем процессом. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)`
с фреймированием по длине (без коллизий на границах полей). Компонент модели —
это **настроенная** модель моста, а не модель, которая фактически ответила:
`callVisionModel` может внутренне переключиться на резервную модель, а создание
ключа для каждой попытки фрагментировало бы кэш. Неудачные описания никогда не
кэшируются. Настройки:

| Ключ                            | Значение по умолчанию | Диапазон |
| ------------------------------- | --------------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`                | —        |
| `modalityBridgeCacheTtlMinutes` | `60`                  | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`                 | 10–5000  |

#### Нормализация удалённых изображений (цикл описания/получение base64)

Когда мост самостоятельно получает **удалённое** изображение — для внутреннего
вызова описания Anthropic и преобразования в base64 формата передачи данных
Claude (`ensureBase64ImagesForClaudeWire`), в обоих случаях через
`fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts`, — полученный URI данных
перед встраиванием в запрос к визуальной модели пропускается через
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`). Слишком большие
изображения уменьшаются до **2048px по длинной стороне** (в соответствии с
ограничением изменения размера, уже применяемым OpenAI/Anthropic на стороне
сервера), что сокращает объём загружаемых данных и задержку, не изменяя того, что
видит визуальная модель. Для изменения размера используется `sharp`, загружаемый
через динамический импорт: на платформе, где его нативный бинарный файл не удаётся
загрузить, `normalizeDataUri()` **никогда не выдаёт исключение** — вместо этого
он передаёт исходные байты без изменений, поэтому путь описания/преобразования в
base64 продолжает работать. Данные, не являющиеся изображением (если при
получении не было возвращено декодируемое изображение), также передаются без
изменений. Эта нормализация применяется только к изображениям, которые мост
получает для собственного внутреннего вызова, — она никогда не применяется к
необработанной транзитной полезной нагрузке вызывающей стороны, что соответствует
принципу изменения только при явном согласии (Hard Rule #20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проверяются Zod в `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, три ключа `modalityBridgeCache*` и группа
`modalityBridgeAudio*`, используемая Audio Bridge. Миграция
`141_modality_bridge_settings.sql` копирует существующие устаревшие значения
`visionBridge*` в соответствующие новые ключи (идемпотентно и без перезаписи
значений `modalityBridge*`, заданных оператором); устаревшие ключи продолжают
приниматься как резервный источник при чтении в течение одного цикла выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные посредством описания, содержат
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(создаётся `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`,
устанавливается `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`).
Перенаправленные запросы **не** получают этот заголовок — полезная нагрузка не
изменялась, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (с авторизацией для управления, того же уровня, что и
`GET /api/settings`) возвращает хранящиеся в памяти счётчики для каждой модальности:
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и
`video`. В качестве знаменателя `averageLatencyMs` использует `latencySamples`,
а не все попытки; для операции без замера времени не создаётся фиктивный
образец с нулевой задержкой. `bridged` остаётся обратно совместимым псевдонимом
для успешных преобразований; неудачные попытки не увеличивают его значение.
Счётчики намеренно сбрасываются при перезапуске процесса
(это телеметрия, а не учёт).

#### Конфигурация панели управления

Специальная страница панели управления доступна по адресу
`/dashboard/settings/modality-bridge`. Её вкладки `Vision`, `Audio` и
`Video`, доступные по URL, сохраняют параметры запроса при переключении значения
`tab`. Вкладка Vision предоставляет включение функции, выбор режима и модели
(включая автоматический вариант по умолчанию), формирование подсказок с учётом
задачи, расширенные ограничения времени ожидания, изображения, длины описания и
кэша, счётчики среды выполнения и защищённый тестовый запрос. Вкладка Audio
также работает: она предоставляет включение функции, выбор только STT-модели с
вариантом Auto, ограничения времени ожидания и максимальной длительности клипа,
счётчики аудио и тестовый запрос `input_audio`. Вкладка Video функциональна: она
показывает состояние среды выполнения FFmpeg/ffprobe — одно из четырёх явно
определённых состояний интерфейса (`unknown`, пока проверка выполняется или не
может быть завершена; `restricted` на хосте панели управления, не являющемся
loopback-хостом, где проверка пропускается на стороне клиента; `unavailable`
после выполнения проверки и подтверждения отсутствия; либо `available` с
версиями FFmpeg/ffprobe), сохраняет ограничения включения, модели, кадров,
видео и времени ожидания, фильтрует список моделей, оставляя модели с поддержкой
зрения, и предоставляет счётчики видео.

Прежняя карточка Vision Bridge в настройках ИИ теперь является ссылкой
совместимости на новую страницу; отдельная копия формы в ней больше не
находится. Раздел Media Providers также связывает рабочие процессы Image-to-Text
и Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя при
этом существующую тестовую площадку Speech-to-Text.

**Обход допуска для self-loop:** когда вызов описания направляется через
собственный `/v1` self-loop OmniRoute (нестандартная модель провайдера),
подзапрос отправляет `x-omniroute-admission-bypass: internal` и проходит
аутентификацию с разрешёнными учётными данными self-loop — локальным значением
`sk_omniroute` в локальном режиме либо настроенным оператором ключом окружения
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развёртывания с
`REQUIRE_API_KEY=true` по-прежнему могли выполнять вызов описания. Обход
разрешён только для этих точных учётных данных, поэтому внешние клиенты не могут
использовать этот заголовок для пропуска допуска.

Устаревшие значения по умолчанию находятся в
`src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для
режима, учёта задачи и кэша, а также резолвер настроек находятся в
`src/shared/constants/modalityBridgeDefaults.ts`. Защитный механизм предоставляет
параметр конструктора `deps`, чтобы тесты могли внедрять фиктивные реализации
`getSettings` и `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает запросы чата, содержащие аудио, до того, как они достигнут целевого
объекта, для которого не подтверждена поддержка аудиоввода. При этом запрос чата
никогда не перенаправляется: аудиочасти транскрибируются через существующую
OpenAI-совместимую multipart-конечную точку, а выбранная модель чата продолжает
работу с текстовыми транскрипциями.

Порядок работы:

1. Разрешить `supportsAudio` через `getResolvedModelCapabilities()`. Явно
   заданные метаданные реестра провайдеров имеют приоритет, затем идут статические
   метаданные модели, а после них — синхронизированное значение
   `modalities_input`. Объявленный список входных данных без `audio` даёт
   `false`; отсутствие данных о возможностях даёт `null`. И `false`, и `null`
   активируют консервативный мост, тогда как `true` обходит его.
2. Разрешить настройки `modalityBridgeAudio*` и извлечь из каждого сообщения
   доступные для вставки аудиочасти верхнего уровня с помощью общего детектора
   `detectMediaParts()`. Поддерживаются форматы передачи OpenAI `input_audio`,
   `audio_url` и `source.media_type: "audio/*"`. Вложенное аудио обнаруживается
   для маршрутизации, но не удаляется путём вставки. Объём работы ограничивается
   `modalityBridgeAudioMaxClips`; последующие части остаются без изменений.
3. Использовать настроенное значение `provider/model` либо позволить
   `selectAudioBridgeModel()` последовательно обойти
   `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбрать первую
   модель с пригодными активными учётными данными провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64/data-URI в
   multipart-`file` либо загружает удалённый `audio_url` через защитный механизм
   исходящих подключений только к публичным ресурсам, с закреплением DNS и
   ограничением в 25 МБ. Затем функция отправляет POST-запрос с файлом и
   выбранной моделью в локальный self-loop `/v1/audio/transcriptions`, проходя
   аутентификацию с помощью `resolveSelfLoopBearer()`. Существующий маршрут
   транскрибирования выполняет обычный поиск учётных данных, обработку периода
   ожидания/ограничения частоты и отправку провайдеру.
5. При успешных вызовах соответствующие части заменяются на
   `[Audio N]: <transcript>`. Вызовы выполняются через `Promise.allSettled`:
   отдельный сбой сохраняет исходную аудиочасть (контракт #4012). Если все вызовы
   завершаются неудачно и для целевого объекта доказано
   `supportsAudio === false`, части заменяются на
   `[Audio N]: (unavailable — no STT provider connected)` (контракт #8430).
   Для неизвестного целевого объекта (`null`) результат при сбое всех вызовов
   остаётся без изменений. Целевой объект с подтверждённой поддержкой только
   текста и без пригодных учётных данных STT получает ту же явную заглушку без
   выполнения сетевого вызова.

Успешные транскрипции используют общий для процесса LRU/TTL-кэш Modality Bridge.
Ключ объединяет ссылку на аудио, стабильную метку операции
`audio-transcription` и выбранную STT-модель; ошибки никогда не кэшируются.
Попытки обработки аудио обновляют общие счётчики `bridged`, `cacheHits`,
`failures` и `lastUsedAt`. Преобразованные ответы содержат
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; запросы,
оставленные без изменений, не получают сегмент Audio Bridge.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | По умолчанию | Диапазон        |
| ----------------------------- | ------------ | --------------- |
| `modalityBridgeAudioEnabled`  | `true`       | —               |
| `modalityBridgeAudioModel`    | `""`         | Авто или ID STT |
| `modalityBridgeAudioTimeout`  | `60000`      | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`          | 1–10            |

Общий кэш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Мост для видео (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает части верхнего уровня с видео в `messages` API Chat Completions и
`input` API Responses до вызова целевой модели, о которой неизвестно, что она
поддерживает видео нативно. Поддерживаются форматы `input_video`, `video_url`,
`video_source`, URL-адреса HTTPS и URI данных `data:video/*;base64,...`.
Обычные имена файлов в тексте не рассматриваются как видео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса,
проверку возможностей и политик, агрегацию в рамках запроса и полезную нагрузку
ответа. Работа с отдельными видео — получение данных, кэширование всего
результата, описание последовательности кадров (с объединением с объявленной
вызывающей стороной расшифровкой аудио), а также метрики, прерывание и очистка
для каждой попытки — скрыта за `processVideoPart` в `videoBridgePipeline.ts`,
которая вызывается по одному разу для каждой части с видео внутри цикла
`preCall`. Этот модуль также определяет явные границы портов
`VideoMediaBrokerPort` (получение байтов и извлечение кадров с выборкой),
`VideoAudioTranscriptionPort` (объединение объявленной вызывающей стороной
расшифровки аудио с подписями к выбранным кадрам) и `VideoDrilldownPort`
(граница сохранения детализации кадров; пока не подключена к
`processVideoPart` — в настоящее время записи детализации создаёт только
отдельный маршрут `/api/modality-bridge/video/drilldown`).

Публичный путь запросов `/v1` никогда не импортирует и не запускает подпроцесс.
Удалённые видео загружаются с ограничением 50 МиБ; для встроенных видео в
формате base64 установлен консервативный лимит в 36 МиБ декодированных данных
на одно видео, чтобы оболочка модели, сообщений и фрейминга оставалась в
пределах публичного лимита приёма JSON-запроса в 50 МиБ. Длина встроенных
данных и оценки декодированного размера проверяются до выделения памяти. Для
исходного удалённого URL-адреса и каждого перенаправления требуется HTTPS;
используется существующая защита исходящих соединений только с публичными
адресами и закреплением DNS. Затем байты передаются через точную внутреннюю
границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут
одновременно имеет атрибуты `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только
аутентифицированные в рамках процесса запросы через доверенный loopback-интерфейс
и никогда не принимает URL-адрес, путь в файловой системе, исполняемый файл или
список аргументов. Конвейер ограничения размера тела API и инкрементальный
обработчик чтения тела независимо друг от друга обеспечивают соблюдение лимита
входных данных брокера в 50 МиБ. Его ограниченная очередь выполняет одно
извлечение за раз, допускает четыре ожидающих задания и ограничивает общий
объём ожидающих входных данных 100 МиБ.

Внутри брокера `ffprobe` читает закрытый локальный файл; фиксированный список
разрешённых форматов исключает форматы плейлистов и манифестов. Для разрешённых
контейнеров семейства MOV внешние ссылки на данные MOV по умолчанию остаются
отключёнными, и фиксированная команда их не включает. И `ffprobe`, и `ffmpeg`
используют список разрешённых протоколов только с `file`, один поток,
фиксированные массивы аргументов, не используют оболочку, а исполняемые файлы
разрешаются через `PATH`. Потоки обложек типа attached picture не считаются
кандидатами для воспроизведения. Все воспроизводимые потоки должны
соответствовать ограничениям; перед детерминированным откатом к потоку с
наименьшим индексом предпочтение отдаётся явно заданному потоку по умолчанию.
Видео ограничены продолжительностью 600 секунд, 8 192 пикселями по каждому
измерению и 33 554 432 исходными пикселями. FFmpeg выбирает от 1 до 16
серединных JPEG-кадров, уменьшает длинную сторону максимум до 1 024 пикселей,
не увеличивая меньшие исходные изображения, и никогда не получает URL-адрес.
По умолчанию используется стратегия выборки `uniform`. Необязательная политика
`scene_aware` и экспериментальная политика `segment_aware` выполняют один
дополнительный фиксированный проход FFmpeg по уже проверенному локальному
потоку, выбирают ограниченный набор временных меток сцен `showinfo` и
детерминированно возвращаются к тем же равномерным серединным точкам при сбое
детектора, истечении времени ожидания, некорректном выводе или пустом наборе
кандидатов. В режиме segment-aware серединные выборки распределяются
пропорционально проверенным интервалам сцен; свидетельства для segment-aware и
поведение при откате подробно описаны ниже. Жёсткое ограничение в 16 кадров
применяется после выбора при любой политике. Если запрос scene-aware допускает
только один кадр, используется равномерная середина активного окна всего видео
или окна фокусировки, а в отчёте указывается `policyEffective: uniform`:
единственный выбранный кадр сцены не позволяет сохранить оба временных края.
Вызывающая сторона может дополнительно указать конечное окно фокусировки
(`start`/`end` в секундах); границы ограничиваются продолжительностью
медиафайла, окна с обратным порядком границ или неконечными значениями
отклоняются, а все политики выборки применяются только внутри нормализованного
интервала. Полученное окно включается в метаданные выборки и в префикс
ненадёжного описания, чтобы последующие модели могли отличить сфокусированный
фрагмент от полной временной шкалы.

Семантическая фокусировка подписей — это отдельная явная настройка. Режим
анализа `full`, используемый по умолчанию, сохраняет существующий запрос для
кадров и никогда не передаёт текст запроса модели подписей. В режиме `focused`
мост считывает только последний непустой пользовательский `text`/`input_text`
из того же контейнера Chat или Responses, нормализует его в NFC, сворачивает
управляющие символы и пробельные последовательности и ограничивает длину 500
кодовыми точками Unicode. Пустой результат приводит к откату к точному запросу
`full`. Пригодная подсказка сериализуется как JSON в отдельном блоке
ненадёжного пользовательского контекста и может лишь задавать приоритет
наблюдаемым деталям; она не может переопределить отдельное предупреждение о
том, что нельзя следовать инструкциям, видимым или слышимым в медиаматериале.
Текстовая фокусировка никогда не выводит значения `start`/`end` и не изменяет
временной сэмплер.

#### Структурные свидетельства сегментов FU-07

`segment_aware` использует один ограниченный проход предварительного анализа уже проверенного
локального видеопотока. Фиксированная цепочка фильтров сначала уменьшает ширину
до не более чем 320 пикселей, обнаруживает смены сцен и интервалы неподвижности,
а затем выполняет выборку с частотой 1 кадр в секунду для оценки размытия,
средней яркости и пространственной/временной информации. Проход ограничен
600 структурными выборками, одним потоком FFmpeg/фильтра, теми же списками
разрешённых протоколов только для `file` и контейнеров, ограничением вывода
процесса в 1 МиБ и не более чем 30 секундами в пределах общего механизма
прерывания/крайнего срока брокера. Он никогда не принимает из запроса команду,
фильтр, путь или URL.

Структурные значения являются детерминированными свидетельствами выборки, а не
результатом семантического понимания видео. Они не определяют объекты, действия,
субтитры, речь или намерения пользователя. Границы сцен и интервалов неподвижности
формируют сегменты; доля неподвижности, размытие, экспозиция, пространственная
детализация и временные изменения влияют только на распределение существующего
бюджета в 1–16 кадров. Полностью неподвижный сегмент ограничивается одним кадром,
тогда как сегменты с движением конкурируют за оставшийся бюджет. Если границ
больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы
частые ранние склейки не могли скрыть длинный завершающий сегмент. Границы сцен,
находящиеся в пределах 1-секундного разрешения анализа от границы интервала
неподвижности, объединяются.

При отсутствии фильтров, некорректных/пустых свидетельствах, ошибке детектора или
истечении ограниченного времени предварительного анализа система без ошибки
переходит к точной политике равномерного выбора средних точек. Прерывание со
стороны вызывающего кода или крайний срок брокера не приводят к такому переходу:
они завершают выполняющийся подпроцесс, предотвращают последующее извлечение
кадров, а приватное временное дерево удаляется в `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` создаёт детерминированные реальные
тестовые данные FFmpeg для оценки сокращения числа вызовов создания описаний
после устранения дубликатов, распределения бюджета при интенсивном движении,
свидетельств размытия/экспозиции/SI-TI, быстрых склеек с длинным завершающим
сегментом и ложных срабатываний при плавном затемнении. Скрипт регистрирует
полное время предварительного анализа и, если доступен `/usr/bin/time`,
процессорное время дочернего процесса и пиковый RSS. Его проверки качества
являются только структурными оракулами. Качество реальной модели создания
описаний остаётся `HOLD`, поскольку у этого стенда нет авторизованной конечной
точки или зафиксированного оценщика. Денежная экономия также остаётся `HOLD`,
если только `--caption-cost-per-call-usd` не задаёт явную положительную оценку
стоимости одного вызова; скрипт никогда не фабрикует ни один из этих результатов.

Размер каждого кадра ограничен 4 МиБ, совокупный размер всех необработанных
кадров — 23 МиБ, а размер сериализованного ответа брокера — 32 МиБ. Приватный
временный каталог удаляется в `finally`. OmniRoute не включает FFmpeg в комплект
поставки и не принимает пользовательский путь к исполняемому файлу. Перед
созданием описаний мост выполняет консервативное визуальное устранение
дубликатов: каждый JPEG преобразуется в буфер оттенков серого размером 16×16 и
сравнивается только с последним сохранённым кадром. Если запрошенный бюджет
описаний превышает один кадр, при извлечении формируется ограниченный пул
кандидатов размером не более удвоенного бюджета и не более 16 кадров.
Запрошенное ограничение применяется только после устранения дубликатов, причём
при окончательном прореживании сохраняются первый и последний выбранные
кандидаты, если бюджет составляет не менее двух кадров. Версионированная
политика `grayscale-16x16-mean-cells-v2` использует большее из двух значений:
среднюю разницу яркости или долю ячеек миниатюры, нормализованная разница
которых составляет не менее 0.05. Порог дубликата равен константе 0.04,
выбранной ради предсказуемости, а не предоставления в качестве параметра
времени выполнения. Этот дополнительный высококонтрастный сигнал сохраняет
небольшие движения и изменения видимого текста, которые может скрыть сравнение
только по среднему значению. При ошибках компаратора или декодера система без
ошибки сохраняет покрытие. Метаданные результата раздельно отражают извлечённых
кандидатов, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно помеченная видеочасть может запросить контактный лист с временными метками.
Мост создаёт JPEG-сетку не более чем из 4 столбцов и 16 кадров. Для каждой
512-пиксельной ячейки временная метка исходного кадра впечатывается в
высококонтрастную нижнюю полосу, а те же временные метки сохраняются в текстовых
метаданных для последующего сопоставления и аудита. Размер итогового JPEG
ограничен 32 МиБ. Если `sharp` не может декодировать или скомпоновать сетку, мост
возвращается к отдельным JPEG-кадрам; прерывание со стороны клиента по-прежнему
распространяется на операцию создания листа.

Свидетельства для продвижения намеренно отделены от синтетического
микротеста производительности компоновки.
`scripts/perf/video-bridge-contact-sheet-eval.ts` определяет версионированный
по схеме A/B-стенд для реальных моделей компьютерного зрения, совместимых с
OpenAI. Он измеряет сообщаемое провайдером количество токенов, сквозную задержку
(включая компоновку листа), число вызовов модели и сохранение фактов,
определённых манифестом. Необработанные ответы модели не записываются в отчёт;
сохраняются только дайджесты SHA-256 и идентификаторы совпавших фактов. Стенд не
выполняет сетевые обращения или платные вызовы модели, если не передан
`--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и
`OMNIROUTE_API_KEY`. Без такого явно запрошенного реального запуска его
машиночитаемый вердикт остаётся `HOLD`; одни лишь синтетические измерения
полезной нагрузки/числа вызовов не являются свидетельствами для продвижения.

Вызывающая сторона может добавить необязательный массив `transcript.cues` к
поддерживаемой видеочасти, если у неё уже есть синхронизированный текст. Каждая
реплика должна содержать `text`, конечный интервал `start`/`end` в пределах
определённой длительности и значение `source` из списка разрешённых вариантов
(`client`, `embedded` или `audio-bridge`); значение `confidence` по умолчанию
равно `1` и должно оставаться в диапазоне от `0` до `1`. Полностью совпадающие
реплики объединяются. OmniRoute никогда не запускает транскрибирование на
основании этих метаданных: проверенные реплики копируются в описанный результат
вместе с источником, уверенностью и интервалом и отображаются как недоверенные
наблюдения рядом с описаниями кадров. Некорректный текст, текст вне допустимого
диапазона или текст без указания происхождения отклоняется, а не смешивается с
потоком описаний. Оба канала расшифровки в теле запроса нормализуют указанное
происхождение до `client`, включая самостоятельно заявленные метки `embedded`
или `audio-bridge`. Только принадлежащий серверу адаптер может назначать эти
доверенные метки через доступный только из кода аргумент `trustedSource`; поле
JSON запроса не может передать значение этому аргументу. Текст расшифровки
остаётся недоверенным содержимым, полученным из медиа, независимо от его
происхождения, и никогда не должен определять авторизацию.

Опытный вызывающий код может предоставить дорожку `audioTranscript` для того же видео;
она считается текстом, предоставленным клиентом, а не подтверждением серверной транскрипции.
На уровне объединения визуальные и аудионаблюдения обрабатываются с общими
крайним сроком и сигналом прерывания, упорядочиваются на общей временной шкале,
точные дубликаты сворачиваются, а если успешно обработана только одна сторона,
возвращается частичный результат.
Недопустимый `audioTranscript` приводит к такому частичному результату — визуальное
описание сохраняется, а аудиоветвь записывает очищенный код ошибки, —
вместо сбоя обработки всего видео. Доступность каждой ветви, флаг частичного
результата и очищенные коды ошибок сохраняются в полученном результате, в
метаданных защитного механизма (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), в метаданных кеша результатов и в счетчиках
объединения моста. Стандартный путь Video Bridge не запускает преобразование
речи в текст и не загружает вторую копию медиафайла; без явно указанной дорожки
он по-прежнему обрабатывает только видео.

**Хранение транскриптов (#12150 P1).** Это применяется автоматически всякий раз,
когда Video Bridge (который сам необходимо включить явно) визуализирует реплику
транскрипта — отдельного флага хранения нет. Когда запрос визуализирует любую
реплику транскрипта (объявленный вызывающим кодом `transcript` или объединенный
`audioTranscript`), защитный механизм помечает его как `videoBridgeObserved` и
создает отредактированную теневую копию описания видео — идентичное
представление, в котором свободный текст каждой реплики заменен на
`[redacted-video-transcript]`; оно формируется путем подстановки значения
структурированного поля реплики до сборки строки (и никогда путем разбора
сведенного текста, поэтому никакое содержимое реплики — вредоносное или обычное,
включая текст с символом `]`, например `[inaudible]`/`[music]`, — не может
сохраниться). В сохраняемом теле запроса журнала вызовов каждая текстовая часть,
полученная из видео, заменяется этой отредактированной теневой копией при
совпадении содержимого; опорное значение `fullText` повторно считывается из
готовых данных защитного механизма перед вызовом, поэтому совпадение продолжает
срабатывать после того, как последующие защитные механизмы цепочки (маскировщики
персональных данных и учетных данных с приоритетами 10/95) перезаписывают текст
описания на месте, а также после того, как внедрение системного запроса, передачи
контекста и памяти изменяет структуру массива сообщений. Тело, отправляемое
модели, остается неизменным. Наблюдаемый запрос также не заполняет постоянную
Memory (извлечение как из запроса, так и из ответа пропускается), поэтому даже
собственный ответ модели не сможет продублировать текст транскрипта в Memory.

**Необработанные поля видео (#12430).** Когда мост включен, а наличие встроенной
поддержки видео неизвестно или она отсутствует, заданные поля
`transcript`/`audioTranscript` также активируют `videoBridgeObserved`, даже после
ошибки описания или достижения ограничения `maxVideos`. Значения `null` и пустые
строки учитываются; отсутствующие поля и метаданные, не относящиеся к видео, не
учитываются. В сохраняемых копиях эти поля редактируются либо сам запрос
исключается, а кеши и Memory обходятся.

На этих резервных путях допустимые реплики, предоставленные вызывающим кодом,
преобразуются в поддерживаемые части `text`/`input_text`, а не в нестандартные
поля провайдера. Обе предоставленные в запросе дорожки остаются недоверенными
наблюдениями `client` с явным предупреждением о том, что видео не было описано,
а временные метки не были сверены с медиафайлом. Существующие ограничения в
256 реплик и 64 КиБ суммарно, а также ограничения на каждую реплику применяются
к обеим дорожкам вместе; временные метки должны укладываться в установленный
брокером предел в 600 секунд и в любое заданное окно фокусировки. Недопустимые
дорожки отбрасываются и не передаются как произвольный текст; допустимая парная
дорожка все еще может использоваться, если их общий бюджет не превышен.
Пустые поля и поля со значением `null` не добавляют текст. Этот резервный путь
не добавляет загрузку медиафайла или транскрипцию. Поля расширения транскрипта
удаляются из резервного контейнера видео и его объектов `video_url`/`source`.
Белый список протокола OpenAI остается строгим; контейнеры видео с неизвестной
встроенной поддержкой остаются доступными, а известные цели, поддерживающие
только текст, сохраняют безопасные маркеры. Структурированные теневые копии с
редактированием защищают добавленный текст транскрипта, при этом исходный запрос,
принадлежащий вызывающей стороне, остается неизменным. Цели со встроенной
поддержкой и отключенные мосты сохраняют существующее поведение обхода.

В дополнительных сохраняемых копиях используется тот же сигнал наблюдаемого
запроса. В необработанном снимке клиентского запроса до применения защитных
механизмов, ожидающем запросе в памяти и журнале раннего отклонения запроса поля
транскрипта в частях видео заменяются структурно; строковые запросы,
синтезированные этапами конвейера и при передаче контекста, редактируются в точке
сохранения тела запроса. Сохраняемый маркер `video_content_removed` приводит к
безопасному отказу продолжения по `previous_response_id`, а не к восстановлению
намеренно удаленного текста. Если наблюдаемый запрос теряет свою теневую копию
для редактирования отдельной части до записи в журнал или хотя бы одна из
нескольких теневых копий видео не совпадает после последующих изменений запроса,
сохраняемое тело запроса полностью исключается вместо сохранения частично
отредактированного транскрипта.

Для наблюдаемого запроса ответ модели может цитировать любую часть транскрипта
без структурированной границы реплики. Поэтому сохраняемое поле `responseBody`
журнала вызовов заменяется маркером пропуска; подробный артефакт конвейера
(который может включать тела upstream-запросов и клиентских запросов, а также
фрагменты потока) не сохраняется. Для такого запроса семантический кеш, кеш
идемпотентности и кеш повторного воспроизведения рассуждений не используются
ни для чтения, ни для записи. Запрос к провайдеру и видимый клиенту ответ
остаются неизменными. Ранние байты keepalive удаляются из временного буфера,
когда подробный артефакт исключается. Предупреждение Kiro о некорректном
EventStream сообщает только количество байтов полезной нагрузки и никогда не
включает ее содержимое или необработанную ошибку JSON-парсера.
Это не означает, что все несвязанные диагностические сообщения провайдеров или
плагинов были проверены; более широкий аудит мест сохранения отслеживается в
#11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную кэш-подсистему с обратным подключением и аутентификацией по токену. Для каждой операции также требуется канонический непрозрачный идентификатор субъекта. Прежде чем рабочему вызывающему компоненту будет разрешён доступ, он должен получить этот идентификатор из данных аутентифицированного арендатора и ни в коем случае не передавать значение, выбранное клиентом. Ключи кэша связывают этот субъект с каноническими идентификаторами сеанса и видеоссылки, хранят только полученные на их основе ключи SHA-256 и ограничивают как чтение, так и удаление тем же субъектом. Кэш хранит не более 16 полученных кадров JPEG на запись, удаляет их через десять минут и поддерживает ограниченное чтение с параметрами `start`/`end` либо явное удаление сеанса.

Для каждого субъекта действует ограничение в 16 записей и 64 МиБ канонических данных JPEG. Эти ограничения не зависят от общего предела в 64 записи/256 МиБ: при исчерпании квоты субъекта сначала вытесняются только наименее недавно использованные записи этого субъекта, и лишь затем рассматривается глобальное вытеснение по LRU. При обращении к кэшу просроченные записи удаляются как из учёта субъекта, так и из глобального учёта, а отмена и ошибка валидации не приводят к фиксации частичной замены.

Кэш отклоняет неканонический Base64, избыточное дополнение, данные не в формате JPEG, некорректные или усечённые JPEG, а также JPEG, при полном декодировании которых с помощью `sharp` в заданных пределах возникает предупреждение. Каждое принятое изображение повторно кодируется в канонический JPEG; ширина и высота определяются по декодированным байтам, а не по полям вызывающей стороны; любые завершающие полиглотные байты отбрасываются, а не сохраняются. В обеих квотах учитывается только ограниченный канонический сжатый буфер. Ограничение передаваемых данных JSON учитывает накладные расходы Base64 для предела декодированных входных данных в 32 МиБ. Для каждого сохранённого результата сохраняются проверенные формат и разрешение JPEG, политика выборки, версия формирования, время создания, вычисленная сервером хэш-сумма содержимого, хэшированная ссылка на родительский объект, а также хэш родительского содержимого от доверенной вызывающей стороны. Отмена проверяется между асинхронными этапами декодирования и хэширования до атомарной фиксации в кэше.

На этом этапе рабочий производитель ещё не подключён к маршруту, а выбор вариантов с разными разрешениями не реализован. Поэтому прозрачный путь запросов Video Bridge не создаёт дополнительной нагрузки, а получение привязанного к арендатору идентификатора субъекта и полный жизненный цикл FU-08 с несколькими разрешениями остаются явно обозначенной последующей работой и не документируются как уже реализованное поведение.

Кадры последовательно снабжаются описаниями с помощью настроенной модели Video. Пустое переопределение Video наследует настройку Vision; если обе настройки пусты, автоматический маршрутизатор Vision выбирает подходящую модель с поддержкой зрения. Успешные описания заменяют исходную часть текстом со стабильным префиксом `[Video description:`, который также помечает текст как ненадёжное наблюдение, полученное из медиаданных, и предписывает последующим моделям не выполнять инструкции, обнаруженные в медиаданных. Ключи кэша описаний кадров включают байты JPEG, запрос, временную метку и фактически используемую модель; кэшируются только успешно созданные описания. Записи кэша сохраняют фактическую модель-производитель, успешно обработавшую запрос, включая резервную модель; если разные кадры были обработаны разными моделями, мост сообщает `mixed`. При попадании в кэш идентификатор этой модели-производителя используется повторно, а не заменяется меткой запрошенного плана маршрутизации. Ключ кэша результата для всего видео включает все входные данные, влияющие на результат: запрос, фактически используемую модель, политику выборки, количество кадров, режим семантического анализа, SHA-256-отпечаток нормализованной подсказки фокуса, окно фокуса, `transcript`, `audioTranscript` и флаг контактного листа. Поэтому изменение любого из этих параметров приводит к промаху кэша, а не к повторному использованию устаревшего результата. Версия политики визуальной дедупликации, порог и ограниченное количество кадров-кандидатов также явно включаются в ключ и метаданные кэша результатов; следовательно, изменение политики не может привести к повторному использованию устаревшего описания всего видео. Метаданные кэша результатов v4 сохраняют режим и отпечаток, но никогда не сохраняют исходную пользовательскую задачу. Метаданные защитного механизма содержат как запрошенный, так и фактический режим анализа; запрошенный режим `focused` без пригодного пользовательского текста указывается как фактически работающий в режиме `full`.

Защитный механизм извлекает все поддерживаемые части видео, но описывает не более `modalityBridgeVideoMaxVideos`. Для целевого компонента, для которого доказано `supportsVideo === false`, неудачно обработанные и превышающие лимит видео заменяются явными безопасными текстовыми маркерами, чтобы необработанные видеоданные не сохранились. Если возможность неизвестна, эти части сохраняют свой видеоконтейнер; любой резервный транскрипт подвергается описанному выше ограниченному преобразованию в текст. Целевые компоненты с `supportsVideo === true` обходят мост. Сигнал отмены клиентского запроса распространяется на загрузку, очередь брокера, подпроцессы и вызовы создания описаний; при отмене обработка останавливается между видео, и необработанные медиаданные никогда не пропускаются в результате отказа.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                                | По умолчанию | Диапазон / поведение                                                                                                                |
| ----------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | Необязательная среда выполнения, включаемая явно                                                                                    |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` сохраняет универсальные описания; `focused` использует ограниченный, недоверенный контекст последнего сообщения пользователя |
| `modalityBridgeVideoModel`          | `""`         | Наследует модель Vision Bridge                                                                                                      |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                                                |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора используется `uniform`                            |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                                                 |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 мс                                                                                                                      |

Сохранённые устаревшие значения тайм-аута видео свыше 120 секунд ограничиваются
крайним сроком брокера; новые значения настроек, превышающие этот предел, отклоняются.
`GET /api/modality-bridge/video/runtime` требует доверенного, подтверждённого штампом
локального loopback-подключения перед аутентификацией или проверкой среды выполнения,
а затем требует управленческой аутентификации. Он возвращает только `available`,
очищенные версии FFmpeg/ffprobe и фиксированную причину, если среда выполнения
недоступна. Внутренняя конечная точка извлечения не является общедоступным API
загрузки: переполнение очереди возвращает `503` вместе с `Retry-After`, отключение
вызывающей стороны возвращает `499`, а достижение фиксированного крайнего срока
брокера возвращает `504`. Преобразованные ответы добавляют
`video->text;model=<visionModel>;parts=<videos>` в центральный заголовок
`x-omniroute-modality-bridge`, не удаляя сегменты Vision или Audio.

### Маскирование PII (`piiMasker.ts`)

Выполняется на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и
  `prompt` (включая элементы, являющиеся обычными строками) и применяет `processPII()` (из
  `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда
  `PII_REDACTION_ENABLED=true`, обнаруженные PII редактируются в исходящей
  полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет
  только политикой защиты от внедрения промптов). Когда редактирование отключено,
  вызов регистрирует количество обнаружений, не изменяя содержимое.
- **`postCall`** создаёт глубокую копию ответа, выполняет `sanitizePIIResponse()` и
  маскирование структуры Responses API (`maskResponsesOutput` — охватывает
  `output_text` и `output[].content[].text`). Если происходит какое-либо
  редактирование, изменённый ответ заменяет исходный.

Защитный механизм никогда не блокирует; он только добавляет аннотации
(`meta.detections`, `meta.redacted`) или изменяет содержимое.

### Внедрение промптов (`promptInjection.ts`)

Обнаруживает вредоносные структуры в предоставленном пользователем содержимом и
применяет настроенную политику. Поведение определяется переменными окружения и
параметрами конструктора:

| Настройка        | Переменная окружения                                                                                        | По умолчанию | Эффект                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Включено         | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`       | При значении `false` защитный механизм немедленно завершает работу.                                                                                                                                 |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`       | Политика внедрения: `block`, `warn` или `log`. (`redact` поддерживается для обратной совместимости, но **не** удаляет текст внедрения; изменением PII в запросе управляет `PII_REDACTION_ENABLED`.) |
| Порог блокировки | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдоним `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | Минимальный уровень серьёзности, необходимый для блокировки. При настройках по умолчанию средний уровень используется только для наблюдения.                                                        |

**Приоритет режимов** (`getMode`): `options.mode` вызывающей стороны →
**переопределение флагом функции из БД** для `INJECTION_GUARD_MODE` (Панель управления → Настройки →
Флаги функций) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения
`INPUT_SANITIZER_MODE` → `warn`. Таким образом, переопределение в панели управления
имеет приоритет над переменными окружения, поэтому интерфейс флагов функций управляет
работающим защитным механизмом в реальном времени (без перезапуска). Чтение из БД
отказоустойчиво: при ошибке защитный механизм возвращается к поведению на основе
переменных окружения, а если переопределение не задано, поведение идентично разрешению
только через переменные окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов,
   используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и
   `markdown_system_block`, оба с уровнем серьёзности `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора (строки,
   регулярные выражения или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение соответствует порогу
серьёзности, `preCall` возвращает `{ block: true, message: "Request rejected:
suspicious content detected" }`. В режимах `warn`/`log` защитный механизм
записывает событие в журнал, но разрешает вызов. Общая вспомогательная функция
`evaluatePromptInjection()` также экспортируется для вызывающих сторон, которым
необходимо проверять промпты без использования реестра.

**Ограничение сканирования (v3.8.20):** детектор проверяет только **первые 16 КБ**
объединённого текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта)
в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и
`evaluatePromptInjection()` выполняют `slice(0, MAX_INJECTION_SCAN_BYTES)` перед
запуском цикла проверки шаблонов. Директивы инъекций располагаются ближе к началу
входных данных, поэтому это ограничивает нагрузку регулярных выражений на CPU/GC
для полезных нагрузок размером в сотни КБ без снижения эффективности обнаружения
(см. #3932, #4041).

### Маскирование учётных данных (`credentialMasker.ts`)

Выполняется на **обоих** этапах, последним в цепочке по умолчанию (приоритет `95`).
Скрывает известные шаблоны API-ключей / секретных токенов в исходящей полезной
нагрузке (содержимом сообщений, аргументах вызовов инструментов, результатах
работы инструментов) **и** в ответе провайдера, чтобы учётные данные, вставленные
в промпт (или возвращённые результатом работы инструмента), не были переданы
внешнему провайдеру или обратно клиенту.

- **Только по явному включению**, согласно тому же принципу, что и для скрытия
  персональных данных (смежно с жёстким правилом №20): отключено, если только
  `settings.credentialRedactionEnabled === true` **или**
  `CREDENTIAL_REDACTION_ENABLED=true`. Когда функция отключена, защитный механизм
  ничего не делает — он никогда не блокирует и не изменяет данные.
- `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`,
  с защитой от загрязнения прототипа и циклов посредством `WeakSet`) и заменяет
  совпадения заполнителем `[REDACTED:<type>]`, клонируя только те ветви, которые
  действительно изменились.
- `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платёжные ключи (Stripe, Square),
  облачные ключи (ключ доступа AWS, Twilio, SendGrid, Mailgun), закрытые ключи /
  JWT, строки подключения с учётными данными (`mongodb://user:pass@...` и т. п.),
  а также универсальный шаблон значения заголовка
  `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи, имеющие форму заголовков
  (`authorization`, `x-api-key`, `api-key`, `apikey`), скрываются структурно
  (только значение, с сохранением префикса схемы, например `Bearer `/`Basic `),
  а не с помощью универсального текстового регулярного выражения.
- Защитный механизм никогда не блокирует; он только изменяет данные
  (`modifiedPayload` / `modifiedResponse`) и добавляет аннотации
  (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // значение true прерывает цепочку
  message?: string; // отображается при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается методом preCall для изменения запроса
  modifiedResponse?: TValue; // возвращается методом postCall для изменения ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сообщает об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload`/`modifiedResponse` заменяет
значение, передаваемое по цепочке последующим защитным механизмам.
`signal?: AbortSignal` передаёт жизненный цикл вызывающей стороны защитным механизмам. Прерывание запроса является намеренным исключением из принципа fail-open: медиамосты прекращают работу и выполняют очистку, не восстанавливая необработанные медиаданные для целевой системы, которая заведомо их не поддерживает.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  повторно сортирует по возрастанию `priority`.
- `clear()` / `list()` — вспомогательные функции администрирования.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, пропускает
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — тот же поток на стороне ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и опционально
  повторно регистрирует значения по умолчанию для чистой изоляции тестов.

Оба запускатора возвращают `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` — это массив записей `GuardrailExecutionResult`, которые включают
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
полезные для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Источники (все опциональные, все объединенные):

- `apiKeyInfo.disabledGuardrails`
- Тело запроса `disabledGuardrails` (верхний уровень)
- Тело запроса `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (или устаревший
  `x-disabled-guardrails`)

Значения могут быть массивами строк или строкой, разделенной запятыми; имена
нормализуются в нижний регистр kebab-case (`pii_masker` → `pii-masker`). Результат
передается через `context.disabledGuardrails` в реестр, который пропускает
соответствующие защитные механизмы (`skipped: true` в `results`).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` формирует список исключений из ключа API, тела запроса
    и заголовков.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке
    возрастания приоритета:
    - Отключенные защитные механизмы записываются как `skipped`.
    - Метод `preCall` каждого защитного механизма может переписывать полезную нагрузку через `modifiedPayload`.
    - Первый `block: true` прерывает цепочку, и обработчик возвращает
      ответ об отклонении защитным механизмом.
3.  (Потенциально переписанная) полезная нагрузка поступает в комбинированную маршрутизацию и
    диспетчеризацию вышестоящему сервису.
4.  После сборки ответа `guardrailRegistry.runPostCallHooks(...)`
    запускает ту же цепочку для ответа. `block: true` здесь отбрасывает
    ответ вышестоящего сервиса.

Защитные механизмы, которые выбрасывают исключения, записываются с `error: <message>` и
логируются через `logger.warn`, но цепочка продолжается — по замыслу, система
открыта к сбоям.

## Конфигурация

Переменные окружения, считываемые встроенными защитными механизмами:

| Переменная                            | Используется                  | Эффект                                                                                                                 |
| :------------------------------------ | :---------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`            | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не переписывает текст инъекции.             |
| `INJECTION_GUARD_MODE`                | `prompt-injection`            | Режим для защиты от инъекций; также флаг функции БД, который **переопределяет** переменные окружения (БД > ОКРУЖЕНИЕ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`            | Минимальная серьезность, при которой `MODE=block` отклоняет: `high` (по умолчанию), `medium` или `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`            | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`                  | Если `true`, PII запроса скрывается (независимо от режима инъекции).                                                   |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ниже по потоку) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек,
поддерживаемого БД (`getSettings()`), а не из переменных окружения. Основные ключи Vision:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного одноциклового
резервного чтения; записи с панели управления используют основные ключи. Значения по умолчанию и
резервный резолвер находятся в `src/shared/constants/modalityBridgeDefaults.ts`,
при этом устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Аудио использует `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Аудио нет резервного варианта для устаревших ключей,
поскольку эти ключи были введены со схемой Modality Bridge.

Видео использует `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
По умолчанию оно отключено, поскольку FFmpeg/ffprobe являются необязательными
операционными зависимостями, а создание подписей к кадрам увеличивает задержку и
стоимость модели.

## Пользовательские Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1.  Создайте `src/lib/guardrails/myGuardrail.ts`, расширяющий `BaseGuardrail`.
2.  Реализуйте `preCall` и/или `postCall`.
3.  Либо зарегистрируйте во время импорта (push из `registerDefaultGuardrails`), либо
    вызовите `guardrailRegistry.register(...)` во время выполнения — реестр заменяет
    любой предыдущий guardrail с тем же нормализованным именем.
4.  Добавьте тесты в `tests/unit/` (существующие примеры:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами, чтобы начать с известного состояния.
Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и
зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки расширения
для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции.
Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты,
которые принимают пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование;
`block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| :------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------- |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует
корпус OWASP-LLM в режиме `INJECTION_GUARD_MODE=block`; garak запускает зонды (пропускает без секрета).
`moderations` включен для согласованности — операторы в режиме блокировки могут исключить его через
`resolveDisabledGuardrails`.

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной
запуск) состоит из двух задач:

- **`promptfoo-guard` (блокирующий)** — запускает `promptfoo eval -c promptfooconfig.yaml`
  с `INJECTION_GUARD_MODE=block`. Каждый adversarial-кейс (например, "игнорировать все
  предыдущие инструкции...", джейлбрейки в стиле DAN) подтверждает, что ответ содержит
  `error.code === "SECURITY_001"`, то есть защита фактически отклонила запрос.
- **`garak` (консультативный)** — запускает garak `--probes promptinject,dan,leakreplay`
  против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Ограничен
  секретом провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается и имеет суффикс
  `|| true`, поэтому он сообщает о результатах, не приводя к сбою CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`)
охватывает каждый маршрут `/v1`, содержащий промпты; текст промпта извлекается из
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью
`extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
