## ခြုံငုံသုံးသပ်ချက်

OmniRoute စီမံခန့်ခွဲမှု API route အားလုံးကို ကာကွယ်မှုအဆင့် သုံးဆင့်အနက်
တစ်ဆင့်အဖြစ် ခွဲခြားထားသည်။ ဤခွဲခြားမှုသည် ပြောင်းလဲခြင်းမရှိဘဲ `src/server/authz/routeGuard.ts`
တွင် သတ်မှတ်ထားပြီး အခြား auth branch တစ်ခုခု မလုပ်ဆောင်မီ အကဲဖြတ်သည်။

## အဆင့်များ

### အဆင့် 1 — LOCAL_ONLY

**အကောင်အထည်ဖော် ကန့်သတ်ပုံ:** `isLocalOnlyPath(path)` → loopback host စစ်ဆေးမှု  
**ကျော်လွှားနိုင်မှု:** မူလသတ်မှတ်ချက်အရ မရှိပါ။ တောင်းဆိုမှုတွင် `manage` scope ပါဝင်သော မှန်ကန်သည့် API key ရှိပါက `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ထဲရှိ path များအတွက်သာ ကျဉ်းမြောင်းသော ခြွင်းချက်ရှိသည် ([Manage-scope ခြွင်းချက်](#manage-scope-carve-out) ကို ကြည့်ပါ)။

ဤ route များသည် child process များကို စတင်ခြင်း သို့မဟုတ် runtime code ကို execute လုပ်ခြင်းတို့ ပြုလုပ်သည်။ ၎င်းတို့ကို loopback မဟုတ်သော traffic အတွက် ဖွင့်ပေးထားပါက မှန်ကန်သည့် JWT ကို ရရှိထားသော တိုက်ခိုက်သူတစ်ဦးသည် (ဥပမာ၊ Cloudflared/Ngrok tunnel မှတစ်ဆင့်) process စတင်ခြင်းကို လှုံ့ဆော်နိုင်မည်ဖြစ်ပြီး၊ ၎င်းသည် လူသိများသော CVE အမျိုးအစားတစ်ခုဖြစ်သည် ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))။

**GHSA-fhh6-4qxv-rpqj ဆိုသည်မှာ (တိုက်ခိုက်မှုပုံစံ):** management/agent server တစ်ခုက subprocess (`npm install`, `node`, browser တစ်ခု၊ proxy တစ်ခု၊ `git`, `tar`, …) ကို စတင်သည့် endpoint တစ်ခုအား ဖွင့်ပေးထားခြင်းဖြစ်သည်။ အကယ်၍ အဆိုပါ endpoint ကို host ပြင်ပမှ ဝင်ရောက်နိုင်လျှင် — operator က OmniRoute ကို nginx/Cloudflare/Tailscale tunnel နောက်တွင် ထားရှိပြီး JWT ပေါက်ကြားသွားခြင်း သို့မဟုတ် auth ကို မှားယွင်းစွာ စီစဉ်ထားခြင်းကြောင့် — တိုက်ခိုက်သူသည် "API တစ်ခုကို ခေါ်ခြင်း" ကို "host ပေါ်တွင် command တစ်ခုကို run ခြင်း" (remote code execution) အဖြစ် ပြောင်းလဲနိုင်သည်။ OmniRoute သည် spawn ပြုလုပ်နိုင်သော route တိုင်းတွင် **မည်သည့် auth စစ်ဆေးမှုမတိုင်မီ loopback host စစ်ဆေးမှုကို ခြွင်းချက်မရှိ မဖြစ်မနေ အကောင်အထည်ဖော်ခြင်း** ဖြင့် ၎င်းကို ပိတ်ဆို့ထားသည်။ ထို့ကြောင့် tunnel မှတစ်ဆင့် token ပေါက်ကြားသွားသော်လည်း spawn လုပ်ဆောင်ချက်သို့ ဝင်ရောက်နိုင်မည်မဟုတ်ပါ။

**LOCAL_ONLY အစုအဝေး အပြည့်အစုံ။** တရားဝင်အရင်းအမြစ်မှာ `src/server/authz/routeGuard.ts` ထဲရှိ `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` ဖြစ်ပြီး၊ အောက်ပါဇယားသည် လက်ရှိအခြေအနေကို ထင်ဟပ်ဖော်ပြထားသည်။ `check-route-guard-membership` gate သည် spawn ပြုလုပ်နိုင်သော prefix များအောက်ရှိ `route.ts` တိုင်းကို စာရင်းကောက်ယူပြီး၊ မည်သည့်တစ်ခုမဆို local-only အဖြစ် အမျိုးအစားခွဲခြားမထားပါက CI ကို မအောင်မြင်စေသည်။

#### Manage scope အတွက် ခြွင်းချက်

တောင်းဆိုမှုတွင် metadata ထဲ၌ `manage` scope (သို့မဟုတ် `admin`) ပါဝင်သော
`Authorization: Bearer <api-key>` ပါရှိမှသာ LOCAL_ONLY path များ၏ အစိတ်အပိုင်းတစ်ခုကို
non-loopback မှလည်း ဝင်ရောက်နိုင်သည်။ ခြွင်းချက်ကို path တစ်ခုချင်းစီအလိုက်
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` မှတစ်ဆင့် အတိအလင်း ထိန်းချုပ်ထားသောကြောင့်
LOCAL_ONLY path အသစ်တိုင်းအတွက် မူလသတ်မှတ်ချက်သည် strict-loopback အဖြစ် ဆက်ရှိနေသည်။ အထောက်အထားမပြထားသော
တောင်းဆိုမှုများနှင့် manage မဟုတ်သော key များပါသည့် တောင်းဆိုမှုများကို
`403 LOCAL_ONLY` ဖြင့် ဆက်လက်ငြင်းပယ်သည်။

လက်ရှိတွင် ကျော်ဖြတ်နိုင်သော prefix တစ်ခုတည်းမှာ `/api/mcp/` ဖြစ်သည်။ `/api/cli-tools/runtime/` နှင့်
`/api/services/` တို့သည် မည်သည့် subprocess မဆို (`npm install`, `node`) စတင်နိုင်သောကြောင့်
ရည်ရွယ်ချက်ရှိရှိ ဖယ်ထုတ်ထားသည်။ ယင်းသည် LOCAL_ONLY အဆင့်ဖြင့်
ကာကွယ်ရန် ရည်ရွယ်ထားသည့် CVE အမျိုးအစား အတိအကျပင် ဖြစ်သည်။

**#7895 — `mcp:connect` ကျဉ်းမြောင်းသော scope:** `/api/mcp/` ခြွင်းချက်သည်
ကျဉ်းမြောင်းသော `mcp:connect` scope
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`) ပါရှိသည့် Bearer key ကိုလည်း လက်ခံပြီး
`src/server/authz/policies/management.ts` ရှိ `hasMcpConnectOrManageScope()` မှတစ်ဆင့် စစ်ဆေးသည်။
၎င်းသည် `/api/mcp/` အတွက်သာ ကန့်သတ်ထားသည် — `mcp:connect` သည် အခြား
management route မည်သည့်နေရာတွင်မျှ ခွင့်ပြုချက်မပေးပါ (အနာဂတ်တွင် ထည့်သွင်းလာနိုင်သည့် အခြား LOCAL_ONLY bypass prefix တိုင်းအပါအဝင်)၊ ထို့ပြင် ၎င်းကို
`MANAGEMENT_API_KEY_SCOPES` မှ တမင်ဖယ်ထုတ်ထားသည်။ `manage`/`admin` ပါရှိသည့် key သည်
ယခင်အတိုင်းပင် ခြွင်းချက်ကို ဖြတ်သန်းနိုင်ဆဲဖြစ်ပြီး၊ `mcp:connect` သည် ကျယ်ပြန့်သော management access
မလိုအပ်သင့်သည့် အဝေးမှ MCP သီးသန့်ခေါ်ဆိုသူများအတွက် လုပ်ပိုင်ခွင့်နိမ့်သော အခြားရွေးချယ်စရာ

#### Operator လမ်းညွှန်ချက်နှင့် စာရင်းစစ်ဆေးခြင်း

OmniRoute ကို reverse proxy သို့မဟုတ် tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) နောက်ကွယ်တွင် အသုံးပြုပါက၊ loopback စစ်ဆေးမှုသည် အထက်ပါ
စတင်လုပ်ဆောင်နိုင်သော route များကို ဆက်လက်ကာကွယ်ပေးသည် — client address သည် non-loopback ဖြစ်သော တောင်းဆိုမှုကို
**auth မလုပ်ဆောင်မီ** `403 LOCAL_ONLY` ဖြင့် ငြင်းပယ်သောကြောင့် ပေါက်ကြားသွားသော JWT သည် spawn တစ်ခုကို
မရောက်ရှိနိုင်ပါ။ Operator ၏ တာဝန်နှစ်ခု ကျန်ရှိနေသေးသည်:

- **client IP ကို loopback အဖြစ် အတုလုပ်ပြီး 403 ကို "ပြင်ဆင်ခြင်း" မလုပ်ပါနှင့်။**
  `X-Forwarded-For: 127.0.0.1` ဟု သတ်မှတ်ခြင်း သို့မဟုတ် source address ကို
  loopback အဖြစ် ပြန်လည်ရေးသားသည့် proxy ကို အသုံးပြုခြင်းက ဤ tier ပိတ်ထားသော RCE အမျိုးအစားကို
  အတိအကျ ပြန်ဖွင့်ပေးရာရောက်သည်။ dashboard/API ကို
  proxy မှတစ်ဆင့် ဖော်ထုတ်ပါ — spawn လုပ်နိုင်သော route များကို မည်သည့်အခါမျှ မဖော်ထုတ်ပါနှင့်။
- **manage-scope bypass ကို အနည်းဆုံးအတိုင်း ထားရှိပါ။** `/api/mcp/` တစ်ခုတည်းသာ bypass လုပ်နိုင်ပြီး
  `manage` scope ပါသော API key ဖြင့်သာ လုပ်နိုင်သည်။ `SPAWN_CAPABLE_PREFIXES` ကို bypass list ထဲသို့
  မည်သည့်အခါမျှ ထည့်၍မရပါ — zod schema က ၎င်းတို့ကို ပယ်ချပြီး
  `isLocalOnlyBypassableByManageScope` က runtime တွင် ၎င်းတို့ကို ငြင်းပယ်သည် (အလွှာစုံကာကွယ်မှု)၊
  dashboard ပေါ်ရှိ "cannot be made bypassable" ဟူသော စာသား၏ အဓိပ္ပာယ်မှာလည်း ယင်းပင်ဖြစ်သည်။ အလားတူ
  deny-list တွင် spawn မလုပ်သော်လည်း မည်သည့်အခါမျှ အဝေးမှ ရောက်ရှိအသုံးပြုနိုင်ခြင်းမရှိရမည့် LOCAL_ONLY route အချို့လည်း
  ပါဝင်သည် — `/api/oauth/kiro/auto-import` (host စက်အတွင်းရှိ Kiro
  အထောက်အထားဖိုင်များကို ဖတ်သည်)၊ `/api/discovery/` နှင့် `/api/issue-agent/` တို့ဖြစ်သည်။ runtime
  snapshot loader သည်လည်း သိမ်းဆည်းထားသော settings row မှ ထိုကဲ့သို့သော entry များကို ဖယ်ရှားပြီး
  အဟောင်း JSON import (`/api/settings/import-json`) သည် bypass key များကို မည်သည့်အခါမျှ မရေးပါ။
  `LOCAL_ONLY_API_PREFIXES` entry တိုင်းသည် deny-list ထဲတွင် ရှိရမည် သို့မဟုတ်
  bypass ခွင့်ပြုနိုင်မှုအတွက် သုံးသပ်ထားရမည် (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)။ `/api/providers/` အောက်ရှိ dynamic-segment
  နှင့် static-path spawn လုပ်နိုင်သော route များ (ဥပမာ `/login`၊
  `/refresh-cursor`) ကို flat ဖြစ်သော
  `SPAWN_CAPABLE_PREFIXES` array ကမဟုတ်ဘဲ
  `src/shared/constants/spawnCapablePrefixes.ts` ရှိ regex အခြေပြု `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` တွဲဖက်က လွှမ်းခြုံထားသည် — ၎င်းတို့ကို ဖမ်းယူနိုင်ရန် flat array တွင်
  `/api/providers/` prefix တစ်ခုလုံးကို ထည့်သွင်းရမည်ဖြစ်ပြီး၊ ထိုသို့ပြုလုပ်ပါက
  အဝေးရှိ dashboard များက provider CRUD အတွက် တရားဝင်အသုံးပြုသည့် route tree ကို
  အလွန်ကျယ်ပြန့်စွာ ကန့်သတ်ရာရောက်မည်ဖြစ်သည်။

  လုပ်ဆောင်ချိန် အခြေအနေ snapshot ကို တင်ပေးသည့်စနစ်သည် သိမ်းထားသော setting အတန်းမှလည်း ထိုအချက်များကို ဖယ်ရှားပြီး အဟောင်း JSON import (`/api/settings/import-json`) သည် ကာကွယ်မှုကျော်လွှားရေး သော့များကို မည်သည့်အခါမျှ မရေးပါ။ `LOCAL_ONLY_API_PREFIXES` ရှိ အချက်တိုင်းသည် ပိတ်ပင်စာရင်းတွင် ပါရမည် သို့မဟုတ် စစ်ဆေးပြီး ကျော်လွှားရန် သင့်လျော်ကြောင်း အတည်ပြုထားရမည်။ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)

**ဝင်ရောက်အသုံးပြုမှု စစ်ဆေးခြင်း** — host ပြင်ပမှ မည်သည့်အရာမျှ ဤ route များသို့ မရောက်ရှိကြောင်း အတည်ပြုရန်-

- `/dashboard/settings/security` ရှိ **Authorization Inventory** ကို ဖွင့်ပါ။ ၎င်းတွင်
  လက်ရှိ LOCAL_ONLY prefix list၊ bypass လုပ်နိုင်သော prefix များနှင့် compile-time
  spawn လုပ်နိုင်သော ("cannot be made bypassable") အစုကို ပြသသည်။
- အထက်ပါ prefix များနှင့် non-loopback client address တွဲလျက်ရှိသည်များကို ရှာဖွေရန် သင်၏
  reverse-proxy / access log များတွင် grep လုပ်ပါ။ ထိုကဲ့သို့သော hit တစ်ခုခုက
  `403 LOCAL_ONLY` အစား `200` ပြန်ပေးခဲ့ပါက proxy က client IP အစစ်ကို ဖုံးကွယ်နေခြင်းဖြစ်သည် —
  proxy ကို ပြင်ဆင်ပါ။
- ဤ path များထဲမှ တစ်ခုအတွက် OmniRoute log များရှိ `403 LOCAL_ONLY` သည် guard က
  ရည်ရွယ်ထားသည့်အတိုင်း အလုပ်လုပ်နေခြင်းဖြစ်ပြီး ဖျောက်ထားရမည့် error မဟုတ်ပါ။

### Tier 2 — ALWAYS_PROTECTED

**အကောင်အထည်ဖော်ကန့်သတ်သူ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` bypass ကို ကျော်သွားသည်

data directory ကိုယ်တိုင်ဖြစ်သော၊ ၎င်းအတွင်းရှိသော သို့မဟုတ် ၎င်းကို ထည့်သွင်းထားသော vault ကိုလည်း
ငြင်းပယ်သည်။

#### အထောက်အထား export များသည် operator များအတွက်သာဖြစ်သည်

အထက်ပါ tier သည် _အထောက်အထားတစ်ခုခု_ လိုအပ်ခြင်းရှိမရှိကိုသာ ဆုံးဖြတ်သည်။ သိမ်းဆည်းထားသော
အထောက်အထားများကို download လုပ်သည့် route များသည် handler ထဲတွင် ဒုတိယစစ်ဆေးမှုတစ်ခု ထပ်မံထည့်သွင်းထားသည်။ `GET /api/settings/export-json` (စာဝှက်ဖြည်ထားသော
provider connection များနှင့် API key အကြမ်းများ)၊ `GET /api/db-backups/export` (SQLite file) နှင့်
`GET /api/db-backups/exportAll` (archive အပြည့်အစုံ) တို့သည် `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`) ကို ခေါ်သည်။ ၎င်းသည် dashboard session၊ local CLI subject သို့မဟုတ်
login ပိတ်ထားသော instance ကို လက်ခံပြီး scope တစ်ခုခုရှိ API key များ (`manage`
နှင့် `admin` အပါအဝင်) နှင့် `oma_` access token များကို `403` ဖြင့် တုံ့ပြန်သည်။ Sync token ထုတ်ပေးမှု (`POST /api/sync/tokens`) သည်
တူညီသော helper အပြင် ယုံကြည်ရသော loopback internal-service token ကိုပါ အသုံးပြုသည်။

### အသစ်တပ်ဆင်မှု bootstrap သည် loopback အတွက်သာဖြစ်သည် — `Host` မဟုတ်ဘဲ peer အစစ်ဖြင့် ဆုံးဖြတ်သည်

management password သတ်မှတ်ထားခြင်းမရှိဘဲ (`INITIAL_PASSWORD` လည်း မရှိဘဲ) ဖြစ်နေပါက
`src/shared/utils/apiAuth.ts` ရှိ `isAuthRequired()` သည် အမည်မသိ bootstrap ကို **loopback peer များအတွက်သာ**
ဖွင့်ထားသည်။ Loopback ဖြစ်မဖြစ်ကို ယုံကြည်ရသော peer signal များမှ အောက်ပါအစဉ်အတိုင်း ဆုံးဖြတ်သည်။ token တံဆိပ်တပ်ထားသော TCP peer အစစ်
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`၊ policy က မြင်ရသည့်အရာ)၊ pipeline ကိုယ်တိုင်၏
`AUTHZ_HEADER_PEER_LOCALITY` ဆုံးဖြတ်ချက် (route handler များ မြင်ရသည့်အရာဖြစ်ပြီး
`OMNIROUTE_PEER_STAMP_TOKEN` သတ်မှတ်ထားချိန်တွင်သာ ယုံကြည်ရသည်) သို့မဟုတ် တိုက်ရိုက် caller များအတွက် socket peer အစစ်ဖြစ်သည်။ `Host` /
`nextUrl.hostname` ကို မည်သည့်အခါမျှ မစစ်ဆေးဘဲ ပထမဆုံးစကားဝှက်ရေးသားမှု
(`POST /api/settings/require-login`) ကိုလည်း network peer အားလုံးအတွက် ဖွင့်ထားခြင်းမရှိဘဲ
အလားတူကန့်သတ်ချက်အောက်တွင် ထားရှိသည် (GHSA-7pq4-8pvv-rx7r)။ `managementPolicy` သည် ၎င်း၏
ကိုယ်ပိုင် `peerContext` ဆုံးဖြတ်ချက်ကို အောက်သို့ တိတိကျကျ လက်ဆင့်ကမ်းပေးသဖြင့် ORIGINAL (မဖယ်ရှားမီ) request ၏ header များက
၎င်းကို မဆုံးဖြတ်နိုင်ပါ။

### Tier 3 — MANAGEMENT (မူလသတ်မှတ်ချက်)

အခြားစီမံခန့်ခွဲမှု route များအားလုံး။ `requireLogin=false` ဟု စီစဉ်သတ်မှတ်ထားခြင်းမရှိပါက အထောက်အထားစစ်ဆေးမှု လိုအပ်သည်။ CLI token များဖြင့် ဤ route များကို အထောက်အထားစစ်ဆေးနိုင်သည် (loopback + တရားဝင် HMAC)။

## အကဲဖြတ်မှု အစီအစဉ်

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → နောက်တစ်ဆင့်သို့ ဆက်သွားမည်
     → non-loopback၊ manage-scope Bearer ဖြစ်ပြီး
        isLocalOnlyBypassableByManageScope လည်းဖြစ်ပါက   → ခွင့်ပြုမည် (management_key)
     → ထိုသို့မဟုတ်ပါက                           → 403 LOCAL_ONLY ဖြင့် ငြင်းပယ်မည်
  2. isInternalModelSyncRequest(ctx)?
     → ခွင့်ပြုမည် (system)
  3. hasValidCliToken(headers)?
     → ခွင့်ပြုမည် (cli) [loopback + timingSafeEqual HMAC စစ်ဆေးမှု]
  4. isAlwaysProtectedPath(path) သို့မဟုတ် requireLogin=true ဖြစ်ပါသလား?
     → isDashboardSessionAuthenticated?
        → ခွင့်ပြုမည် (dashboard_session)
     → bypass မပြုနိုင်သော path ပေါ်ရှိ manage-scope Bearer လား?
        → ခွင့်ပြုမည် (management_key)
     → 401/403 ဖြင့် ငြင်းပယ်မည်
  5. requireLogin=false?
     → ခွင့်ပြုမည် (anonymous)
```

အဆင့် 1 ရှိ manage-scope branch သည် LOCAL_ONLY route တစ်ခု၏ သတ်မှတ်ချက်ကို ဖြည့်ဆည်းနိုင်သည့် တစ်ခုတည်းသော authenticated path ဖြစ်သည်။ သက်တမ်းကုန်သွားသော DB ကြောင့် `"deny"` သို့ မသိမသာ အဆင့်လျှော့မသွားစေရန် auth-backend ချို့ယွင်းမှု mode သည် 403 မဟုတ်ဘဲ 503 ကို ပြန်ပေးသည်။

## Spawn လုပ်နိုင်သော route အသစ်တစ်ခု ထည့်သွင်းခြင်း

1. `src/server/authz/routeGuard.ts` ရှိ `LOCAL_ONLY_API_PREFIXES` ထဲသို့ path prefix ကို ထည့်ပါ
2. Prefix အသစ်အတွက် `isLocalOnlyPath()` က true ပြန်ပေးကြောင်း အတည်ပြုသည့် test တစ်ခုကို `tests/unit/authz/routeGuard.test.ts` တွင် ထည့်ပါ
3. **ဤအဆင့်ကို မည်သည့်အခါမျှ မကျော်ပါနှင့်** — `CLAUDE.md` ရှိ Hard Rule #15 ကို ကြည့်ပါ
4. ဆုံးဖြတ်ပါ — ဤ route သည် `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ထဲတွင်လည်း ပါဝင်သင့်သလား?
   မူလအဖြေမှာ **မပါဝင်သင့်ပါ** ဖြစ်သည်။ Manage-scope ကိုင်ဆောင်သူထံ ဖော်ထုတ်ရန် route က ဘေးကင်းသည့်အခါမှသာ ထည့်သွင်းပါ (ဆိုလိုသည်မှာ အသုံးပြုသူက ထိန်းချုပ်ထားသော မည်သည့် code ကိုမဆို spawn မလုပ်ရပါ)။

## Manage-scope ဖြင့် bypass လုပ်နိုင်သော path တစ်ခု ထည့်သွင်းခြင်း

1. Route သည် အသုံးပြုသူပေးထားသော code သို့မဟုတ် command များကို execute မလုပ်ကြောင်း အတည်ပြုပါ။ လုပ်ဆောင်ပါက ရပ်လိုက်ပါ — ဤခြွင်းချက်သည် သင့်လျော်သော နည်းလမ်းမဟုတ်ပါ။
2. Prefix ကို `src/server/authz/routeGuard.ts` ရှိ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ထဲသို့ ထည့်ပါ
3. Request ပုံစံ လေးမျိုးလုံးအတွက် coverage ကို `tests/unit/authz/management-policy.test.ts` တွင် ထည့်ပါ — Bearer မပါခြင်း (403)၊ manage Bearer (ခွင့်ပြုခြင်း)၊ non-manage Bearer (403) နှင့် manage Bearer ပါသည့်တိုင် `/api/cli-tools/runtime/*` သည် strict-loopback အဖြစ် ဆက်လက်ရှိနေကြောင်း စစ်ဆေးသည့် prefix တစ်ခုချင်းစီဆိုင်ရာ regression။

## OpenAPI တွင် လုံခြုံရေး Tier များကို မှတ်တမ်းတင်ခြင်း

`docs/openapi.yaml` တွင် route အသစ်တစ်ခု ထည့်သည့်အခါ၊ ထို route ကို `routeGuard.ts` က အမျိုးအစားသတ်မှတ်ထားပါက သက်ဆိုင်ရာ vendor extension ကို အသုံးပြုပါ။

| routeGuard.ts အမျိုးအစားခွဲခြားမှု | YAML annotation            | အတည်ပြုကျင့်သုံးမှု                                       |
| ---------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`    | non-loopback မှ ဝင်ရောက်မှုကို ခြွင်းချက်မရှိ ပိတ်ပင်သည်  |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true` | `requireLogin=false` ဖြစ်လျှင်ပင် auth လိုအပ်သည်          |
| Internal admin/debug route         | `x-internal: true`         | မူလအတိုင်း /dashboard/api-endpoints မှ ဖျောက်ထားသည်       |
| မရှိပါ (public / standard auth)    | (annotation မလိုအပ်ပါ)     | ပုံမှန် `requireLogin` ဖြင့် ထိန်းချုပ်ထားသော ဝင်ရောက်မှု |

### အတည်ပြုစစ်ဆေးခြင်း

Script နှစ်ခုက YAML annotation များနှင့် `routeGuard.ts` တို့အကြား ကိုက်ညီမှုကို အတည်ပြုကျင့်သုံးသည်။

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% ဖြစ်ပါက မအောင်မြင်ပါ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` သို့မဟုတ်
  `x-always-protected` annotation များသည် compile-time constant များနှင့် ကွဲလွဲပါက မအောင်မြင်ပါ

Script နှစ်ခုလုံးသည် pre-commit hook နှင့် CI တွင် အလုပ်လုပ်သည်။

### False Positive စည်းမျဉ်း

`routeGuard.ts` constant ထဲတွင် မပါဝင်သော route တစ်ခုပေါ်၌ `x-always-protected` သို့မဟုတ် `x-loopback-only` ကို annotation လုပ်ထားပါက coverage script သည် မအောင်မြင်ပါ။ ဖြေရှင်းနည်းမှာ YAML ကို `routeGuard.ts` က အမှန်တကယ် အတည်ပြုကျင့်သုံးသည့်အရာနှင့် အမြဲတမ်း ကိုက်ညီအောင် ပြင်ဆင်ရန် ဖြစ်သည် — enforcement logic ကိုပါ အကောင်အထည်မဖော်ဘဲ route များကို `routeGuard.ts` ထဲသို့ ထည့်ရန် မဟုတ်ပါ။
