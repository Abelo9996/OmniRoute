> **နောက်ဆုံးမွမ်းမံထားသည့်ရက်:** 2026-08-29 — v3.8.51 (Video Bridge transcript ၏ မူလရင်းမြစ်ကို ခေါ်ယူသူက ကြေညာသတ်မှတ်ထားခြင်းဖြစ်ပြီး၊
> server က အတည်ပြုစစ်ဆေးထားခြင်း မရှိသေးပါ — #11661 အရ ရှင်းလင်းထားသည်)

Guardrail များသည် OmniRoute နှင့် upstream provider များကြား နယ်နိမိတ်တွင်
ဘေးကင်းလုံခြုံမှု၊ မူဝါဒနှင့် အကြောင်းအရာပြောင်းလဲမှုများကို အတည်ပြုကျင့်သုံးစေသည်။ Guardrail တစ်ခုစီသည် request payload များကို (`preCall`) နှင့်
upstream response များကို (`postCall`) စစ်ဆေးနိုင်ပြီး (လိုအပ်ပါက
ငြင်းပယ်ခြင်း၊ ပြောင်းလဲခြင်း သို့မဟုတ် မှတ်ချက်ထည့်ခြင်းတို့ကို ပြုလုပ်နိုင်သည်)။

စနစ်သည် **fail-open** ဖြစ်သည်။ Guardrail တစ်ခုကို လုပ်ဆောင်နေစဉ် exception ဖြစ်ပေါ်ပါက registry သည်
error ကို မှတ်တမ်းတင်ပြီး request ကို ပျက်ကွက်စေမည့်အစား နောက် guardrail ဖြင့်
ဆက်လက်လုပ်ဆောင်သည်။ ပိတ်ဆို့ခြင်းသည် မတော်တဆဖြစ်ပေါ်ခြင်း မဟုတ်ဘဲ တိကျရှင်းလင်းသော ဆုံးဖြတ်ချက် (`block: true`) ဖြစ်သည်။

## ထည့်သွင်းပါရှိသော ကာကွယ်ရေးစည်းမျဉ်းများ

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

**ရုပ်ပုံမြင်နိုင်စွမ်းမရှိသော model များ** ထံ ရည်ရွယ်သည့် ရုပ်ပုံပါဝင်သော request များကို ကြားဖြတ်၍ request တစ်ခုလုံးကို ရုပ်ပုံမြင်နိုင်စွမ်းရှိသော model ထံ ပြန်လည်လမ်းကြောင်းပြောင်းပေးသည်၊ သို့မဟုတ် upstream call မတိုင်မီ ပုံအစိတ်အပိုင်းများကို ပြင်ဆင်သတ်မှတ်နိုင်သော vision model တစ်ခုမှ ဖန်တီးပေးသည့် စာသားဖော်ပြချက်များဖြင့် အစားထိုးပေးသည်။ ဤနည်းဖြင့် စာသားသီးသန့် provider များသည် multimodal payload များကို အလိုအလျောက် ပွင့်လင်းမြင်သာစွာ ကိုင်တွယ်နိုင်သည်။

လုပ်ဆောင်ပုံအဆင့်ဆင့်:

1. ပစ်မှတ် model သည် vision ကို ပံ့ပိုးထားပြီးသားဖြစ်ပါက ကျော်သွားသည် (၎င်းသည် အတင်းအကျပ် bridge လုပ်ရန်စာရင်း `isVisionBridgeForcedModel` တွင် ပါရှိခြင်းမရှိလျှင်)။
2. `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) မှတစ်ဆင့် ရုပ်ပုံအစိတ်အပိုင်းများကို ထုတ်ယူသည်။ ၎င်းသည် combo compatibility filter နှင့် မျှဝေအသုံးပြုသည့် တစ်ခုတည်းသော အမှန်တရားရင်းမြစ်ဖြစ်သော `open-sse/utils/mediaParts.ts` ထဲရှိ **ပေါင်းစည်းထားသော media detector**
   `detectMediaParts()` သို့ လွှဲအပ်သည်။
   ထုတ်ယူမှုကို `replaceImageParts` က ပြန်လည် splice လုပ်နိုင်သော ပုံစံများ၏ top-level အစိတ်အပိုင်းများသာ allowlist ပြုလုပ်ထားသည် (extract↔replace သဘောတူညီချက်): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` နှင့် Responses API `input_image` တို့ဖြစ်သည်။ အတွင်းထပ်ဆင့်ရှိသော တွေ့ရှိချက်များနှင့် indicator သီးသန့် ပုံစံများသည် combo-filter အတွက်သာဖြစ်ပြီး မည်သည့်အခါမျှ ထုတ်ယူခြင်းမပြုပါ။
   တစ်ခုမျှ မတွေ့ပါက ကျော်သွားသည်။
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) မှတစ်ဆင့် runtime config ကို ဖြေရှင်းသည်။ `modalityBridge*` settings key အသစ်များကို ဦးစားပေးပြီး အဟောင်း `visionBridge*` key များကို **စက်ဝန်းတစ်ခုစာ fallback** (rollback window) အဖြစ် ဆက်လက်ထားရှိသည်။ Bridge ကို ပိတ်ထားပါက media တစ်ခုခုကို မစစ်ဆေးမီ ကျော်သွားသည်။
4. Mode selector (`modalityBridgeVisionMode`၊ အောက်ပါဇယားကို ကြည့်ပါ) က reroute သို့မဟုတ် describe ကို ဆုံးဖြတ်သည်။ Reroute သည် `model` ကိုသာ လဲလှယ်ထားသော `modifiedPayload` နှင့် meta `{ rerouted, fromModel, toModel, imagesKept }` ကို ပြန်ပေးသည်။
5. Describe လမ်းကြောင်းတွင် ရုပ်ပုံအရေအတွက်ကို `maxImages` ဖြင့် ကန့်သတ်ပြီး၊ task-aware prompt ကို ဖွဲ့စည်းကာ၊ describe cache ကို စစ်ဆေးပြီး vision model ကို **တစ်ပြိုင်နက်တည်း**
   (`Promise.allSettled`) ခေါ်ဆိုကာ `[Image N]: <description>` စာသားအစိတ်အပိုင်းများကို ၎င်းတို့၏နေရာတွင် ထည့်သွင်းသည်။ မအောင်မြင်သော describe သည် `null` ကို ထုတ်ပေးပြီး မူလရုပ်ပုံအစိတ်အပိုင်းကို
   **ဆက်လက်ထိန်းသိမ်းထားသည်** (#4012) — သို့သော် describe အားလုံး မအောင်မြင်သော combo describe လမ်းကြောင်းတွင် အတည်ပြုပြီးသား non-vision upstream ကို
   `(မရရှိနိုင်ပါ — ရုပ်ပုံမြင်နိုင်စွမ်းရှိသော provider ချိတ်ဆက်ထားခြင်းမရှိပါ)` stub တစ်ခုဖြင့် အစားထိုးသည် (#8430)။
6. `modifiedPayload` နှင့် meta (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) ကို ပြန်ပေးသည်။

#### Mode selector (`modalityBridgeVisionMode`)

| Mode       | မူလသတ်မှတ်ချက် | လုပ်ဆောင်ပုံ                                                                                                                                                                                                                                                                                                                   |
| ---------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔              | မပြောင်းလဲထားသော အဟောင်း heuristic (#6640/#7204): မူလ model တွင် အသုံးပြုနိုင်သော credential များ ရှိပြီးသားမဟုတ်လျှင် non-combo/`auto/` model များကို အကောင်းဆုံး vision model ထံ reroute လုပ်သည် (ရှိပြီးသားဆိုလျှင် describe လုပ်သည်)။ Combo ပစ်မှတ်များကို အမြဲ describe လုပ်သည်။                                          |
| `describe` |                | အမြဲ describe လုပ်သည် — reroute block တစ်ခုလုံးကို ကျော်သွားပြီး အသုံးပြုသူရွေးချယ်ထားသော model က အမြဲ အဖြေပေးသည်။                                                                                                                                                                                                             |
| `reroute`  |                | Reroute ကို အတင်းလုပ်သည်: credential ရှိသော model ကို ထိန်းသိမ်းသည့် guard ကို ကျော်လွှားသည်။ Reroute **ပစ်မှတ်** credential guard သည် ဆက်လက်သက်ရောက်နေသည် — အသုံးပြုနိုင်သော vision ပစ်မှတ်မရှိပါက request သည် describe သို့ ဆက်လက်ကျသွားသောကြောင့် raw image များသည် text-only backend ထံ မည်သည့်အခါမျှ မရောက်ရှိပါ (#8430)။ |

အတင်းသတ်မှတ်ထားသော mode များသည် auto heuristic မလုပ်ဆောင်မီ **ချက်ချင်းအဆုံးသတ်** သည်။ `auto` လုပ်ဆောင်ပုံသည် PR-1 မတိုင်မီ guardrail နှင့် byte အလိုက် လုံးဝတူညီသည်။

#### API-key နယ်ပယ် (`visionBridgeKeyScope.ts`)

ခေါ်ဆိုသူ၏ API key က `allowedConnections`၊ quota pool များ
(`allowedQuotas`) သို့မဟုတ် model များ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) ကို ကန့်သတ်ထားသောအခါ bridge သည် အဆိုပါ key အသုံးပြုခွင့်ရှိသော connection များပေါ်မှ key အသုံးပြုခွင့်ရှိသည့် reroute နှင့် describe model များကိုသာ ရွေးချယ်သည်။ ထို့နောက် describe call သည် `x-omniroute-self-loop-key-id` header ပါဝင်သော OmniRoute self-loop မှတစ်ဆင့် အမြဲသွားသောကြောင့် လက်ခံရရှိသည့် chat request က ထို key ၏ connection နှင့် model policy ကို ထပ်မံအတည်ပြုကျင့်သုံးသည်။ `enforceApiKeyPolicy()` သည် ထို header ကို self-loop bearer နှင့် တွဲပါမှသာ လက်ခံသောကြောင့် access ကို ပိုမိုကျဉ်းမြောင်းစေရန်သာ လုပ်နိုင်ပြီး ဖြေရှင်း၍မရသော id ကို ငြင်းပယ်သည်။

Key အတွက် ခွင့်ပြုထားသော vision model မရှိပါက describe လမ်းကြောင်းသည် ဘေးဖယ်ပေးပြီး request ကို မပြောင်းလဲဘဲ ဆက်လက်ဖြတ်သန်းစေသည်။ ၎င်းသည် ပိတ်ထားသော guardrail တစ်ခုကဲ့သို့ fail-open လုပ်ဆောင်ပုံနှင့် တူညီသည် (meta `{ skipped: true, reason: "no_permitted_vision_model" }`)။
Key မပါသော request များနှင့် ဤကန့်သတ်ချက်များမရှိသော key များသည် ယခင်အတိုင်း အတိအကျ လုပ်ဆောင်သည်။

#### Task-aware describe prompt (`modalityBridgeVisionTaskAware`)

မူလသတ်မှတ်ချက်မှာ **true** ဖြစ်သည်။ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) သည် အခြေခံဖော်ပြချက် prompt နောက်တွင် **နောက်ဆုံး user message** ၏ စာသားကို (စာလုံးရေ 500 အထိ ဖြတ်တောက်၍) ထည့်သွင်းပေးသည်။ ထို့ကြောင့် ဖော်ပြချက်ကို အသုံးပြုသူ အမှန်တကယ် မေးမြန်းထားသည့်အရာဘက်သို့ ဦးတည်စေပြီး (codex-vision-proxy ပုံစံ) vision model အား မြင်ရသောစာသားကို ကူးရေးရန် တောင်းဆိုသည်။ flag ကို ပိတ်ထားလျှင် — သို့မဟုတ် user စာသား မရှိလျှင် — အခြေခံ prompt ကို မပြောင်းလဲဘဲ အသုံးပြုသည်။

describe self-loop ၏ ကိုယ်ပိုင် OpenAI-compatible request (`visionBridgeHelpers.ts` ရှိ `callVisionModelSingle()`) သည် caller/provider အားလုံးအတွက် client signal တစ်စုံတစ်ရာအပေါ် မမူတည်ဘဲ `image_url.detail: "high"` ကို အမြဲတမ်း တောင်းဆိုသည်။ detail နည်းသော sampling သည် ဤ prompt တောင်းဆိုထားသည့် စာသားကူးရေးခြင်း task အတွက် OCR တိကျမှုကို အထူးသဖြင့် ကျဆင်းစေသောကြောင့် မူရင်း inbound request အသုံးပြုခဲ့သည့် detail level ကို မကြည့်ဘဲ describe call ကိုယ်တိုင်က high detail ကို အမြဲတောင်းဆိုသည်။ ၎င်းသည် အတွင်းပိုင်း describe request body ကိုသာ သက်ရောက်သည်။ OmniRoute က caller ၏ ကိုယ်ပိုင် `image_url.detail` ကို primary request တွင် forward ပြုလုပ်ပုံအား မပြောင်းလဲပါ — ထို default ကို သီးခြားအသုံးချပြီး OpenCode client များအဖြစ် ရှာဖွေသတ်မှတ်ခံရသည့်အခါမှသာ `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) တွင် အသုံးပြုသည်။ describe self-loop ၏ Anthropic wire-format branch တွင် `detail` field မရှိသဖြင့် default နှစ်ခုစလုံး၏ သက်ရောက်မှု မရှိပါ။

#### Describe output ကန့်သတ်ချက် (`modalityBridgeVisionMaxChars`)

| Key                            | မူလတန်ဖိုး | အပိုင်းအခြား            |
| ------------------------------ | ---------- | ----------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` သို့မဟုတ် 100–50000 |

`0` (မူလတန်ဖိုး) သည် **ကန့်သတ်ချက်မရှိ** ဟု ဆိုလိုသည် — `callVisionModel()` မှ ပြန်ပေးသော ဖော်ပြချက်ကို မပြင်ဆင်ဘဲ တိုက်ရိုက်ဖြတ်သန်းစေပြီး လက်ရှိအပြုအမူကို ထိန်းသိမ်းထားသည်။ 100–50000 အပိုင်းအခြားအတွင်းရှိ မည်သည့်တန်ဖိုးမဆို ဖော်ပြချက်ကို `[Image N]: <description>` အဖြစ် ပြန်လည်ထည့်သွင်းမပေါင်းစပ်မီ `…` suffix ဖြင့် ဖြတ်တောက်သည် (`src/lib/guardrails/visionBridge.ts` ရှိ `VisionBridgeGuardrail.preCall()`)။ downstream model က စာသားကူးရေးမှုအပြည့်အစုံ လိုအပ်သည့် အသေးစိတ်များသော OCR task များအတွက် ဤတန်ဖိုးကို မြှင့်ပါ။ စကားများသော vision model များ၏ token အသုံးပြုမှုကို ကန့်သတ်ရန် လျှော့ချပါ။ dashboard field သည် Vision tab ၏ Advanced panel တွင် ရှိပြီး (`ModalityBridgeVisionTab.tsx` ရှိ `modality-bridge-max-chars`) 1 နှင့် 99 ကြား မည်သည့်တန်ဖိုးကိုမဆို အနိမ့်ဆုံး 100 သို့ clamp လုပ်သော်လည်း အတိအလင်း သတ်မှတ်ထားသော `0` ကို မပြောင်းလဲဘဲ ထားသည် — `0` သည် "unset" မူလတန်ဖိုးသာ မဟုတ်ဘဲ ၎င်းကိုယ်တိုင် မှန်ကန်သော Zod တန်ဖိုးဖြစ်သည် (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)။

#### Describe cache (`modalityBridge/bridgeCache.ts`)

describe output များအတွက် process တစ်ခုလုံးအနှံ့ မျှဝေအသုံးပြုသည့် in-memory LRU + TTL cache ဖြစ်သည်။
Key = `sha256(imageRef + composedPrompt + configuredBridgeModel)` ဖြစ်ပြီး length-prefix framing ကို အသုံးပြုထားသည် (field နယ်နိမိတ် တိုက်မိခြင်းများ မရှိပါ)။ model အစိတ်အပိုင်းသည် အမှန်တကယ် ဖြေဆိုခဲ့သော model မဟုတ်ဘဲ **ပြင်ဆင်သတ်မှတ်ထားသော** bridge model ဖြစ်သည် — `callVisionModel` သည် အတွင်းပိုင်း၌ fallback ပြုလုပ်နိုင်ပြီး attempt တစ်ခုချင်းစီအလိုက် key သတ်မှတ်ခြင်းက cache ကို အစိတ်စိတ်အမြွှာမြွှာ ဖြစ်စေမည်။ မအောင်မြင်သော describe များကို မည်သည့်အခါမျှ cache မလုပ်ပါ။ ဆက်တင်များ-

| Key                             | မူလတန်ဖိုး | အပိုင်းအခြား |
| ------------------------------- | ---------- | ------------ |
| `modalityBridgeCacheEnabled`    | `true`     | —            |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440       |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000      |

#### Remote image ပုံမှန်ပြုလုပ်ခြင်း (self-loop describe/base64 fetch)

bridge က **remote** image တစ်ခုကို ကိုယ်တိုင် fetch လုပ်သည့်အခါ — Anthropic describe self-call နှင့် claude-wire-format base64 conversion (`ensureBase64ImagesForClaudeWire`) နှစ်ခုစလုံးသည် `visionBridgeHelpers.ts` ရှိ `fetchRemoteImageAsDataUri()` မှတစ်ဆင့် လုပ်ဆောင်သည် — ရရှိလာသော data URI ကို vision-model request တွင် မထည့်သွင်းမီ `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) မှတစ်ဆင့် ဖြတ်သန်းစေသည်။ အရွယ်အစားလွန်ကဲသော image များကို **အရှည်ဆုံးအနား 2048px** အထိ ချုံ့သည် (OpenAI/Anthropic တို့က server-side တွင် အသုံးပြုထားပြီးဖြစ်သည့် resize ကန့်သတ်ချက်နှင့် ကိုက်ညီသည်)။ ထိုသို့ပြုလုပ်ခြင်းဖြင့် vision model မြင်ရသောအရာကို မပြောင်းလဲဘဲ upload byte ပမာဏ/ကြာချိန်ကို လျှော့ချပေးသည်။ resize ပြုလုပ်ရန် dynamic import မှတစ်ဆင့် load လုပ်သည့် `sharp` ကို အသုံးပြုသည်။ ၎င်း၏ native binary ကို load မလုပ်နိုင်သော platform တစ်ခုတွင် `normalizeDataUri()` သည် **မည်သည့်အခါမျှ error မပစ်ပါ** — မူရင်း byte များကို passthrough လုပ်သည့်နည်းလမ်းသို့ fallback ပြုလုပ်သဖြင့် describe/base64-conversion လမ်းကြောင်းသည် အမြဲဆက်လက် အလုပ်လုပ်နိုင်သည်။ image မဟုတ်သော byte များ (decode လုပ်နိုင်သော image ကို ပြန်မပေးသည့် fetch တစ်ခု) ကိုလည်း မပြင်ဆင်ဘဲ တိုက်ရိုက်ဖြတ်သန်းစေသည်။ ဤပုံမှန်ပြုလုပ်ခြင်းကို bridge က ၎င်း၏ကိုယ်ပိုင် self-call အတွက် fetch လုပ်သော image များ၌သာ ကန့်သတ်အသုံးပြုသည် — caller ၏ raw passthrough payload တွင် မည်သည့်အခါမျှ အသုံးမပြုပါ။ ၎င်းသည် opt-in-only mutation မူဝါဒ (Hard Rule #20) နှင့် ကိုက်ညီသည်။

ကန့်သတ်ချက်များ၊ runtime
counter များနှင့် guard ပြုလုပ်ထားသော sample request တို့ကို ပေးထားသည်။ Audio tab ကိုလည်း လက်တွေ့အသုံးပြုနိုင်သည်။ ၎င်းတွင်
ဖွင့်/ပိတ်သတ်မှတ်ခြင်း၊ Auto ပါဝင်သော STT-only model picker၊ timeout/max-clip ကန့်သတ်ချက်များ၊ audio

FFmpeg/ffprobe runtime အခြေအနေကို ဖော်ပြပြီး explicit UI state လေးမျိုးအနက် တစ်မျိုးဖြစ်သည် (`unknown` သည်
probe လုပ်ဆောင်နေဆဲဖြစ်ချိန် သို့မဟုတ် မပြီးမြောက်နိုင်ချိန်၊ `restricted` သည် non-loopback
dashboard host ပေါ်တွင် client-side မှ probe ကို ကျော်သွားချိန်၊ `unavailable` သည် probe ပြုလုပ်ပြီး
မရှိကြောင်း အတည်ပြုပြီးချိန်၊ သို့မဟုတ် `available` သည် FFmpeg/ffprobe version များနှင့်အတူ ရရှိနိုင်ချိန်)။ ထို့ပြင်
enable/model/frame/video/timeout ကန့်သတ်ချက်များကို သိမ်းဆည်းထားပြီး model picker ကို vision အသုံးပြုနိုင်သော
model များသာ ပြသရန် စစ်ထုတ်ကာ video counter များကို ပေးထားသည်။

AI settings အောက်ရှိ ယခင် Vision Bridge card သည် စာမျက်နှာအသစ်သို့ compatibility link တစ်ခုအဖြစ်
အသုံးပြုထားသည်။ ၎င်းသည် form ၏ ဒုတိယ copy ကို မထိန်းချုပ်တော့ပါ။ Media Providers သည်လည်း
လက်ရှိ Speech-to-Text playground ကို မဖယ်ရှားဘဲ Image-to-Text နှင့် Speech-to-Text workflow များကို သက်ဆိုင်ရာ Modality
Bridge tab များနှင့် ချိတ်ဆက်ပေးသည်။

**Self-loop admission bypass:** describe call သည် OmniRoute ၏
ကိုယ်ပိုင် `/v1` self-loop (စံမဟုတ်သော provider model) မှတစ်ဆင့် route လုပ်သည့်အခါ sub-request သည်
`x-omniroute-admission-bypass: internal` ကို ပေးပို့ပြီး ဖြေရှင်းထားသော
self-loop credential ဖြင့် authentication ပြုလုပ်သည်။ ၎င်း credential သည် local mode တွင် local `sk_omniroute` sentinel ဖြစ်ပြီး၊ သို့မဟုတ်
operator က သတ်မှတ်ထားသော `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350) ဖြစ်သောကြောင့်
`REQUIRE_API_KEY=true` deployment များတွင်လည်း describe call ကို ဆက်လက်လုပ်ဆောင်နိုင်သည်။ Bypass ကို
ထို credential အတိအကျများအတွက်သာ လက်ခံသောကြောင့် ပြင်ပ client များက admission ကို ကျော်ရန်
header ကို အသုံးမပြုနိုင်ပါ။

Legacy default များသည် `src/shared/constants/visionBridgeDefaults.ts` တွင်ရှိပြီး
mode/task-aware/cache default အသစ်များနှင့် settings resolver သည်
`src/shared/constants/modalityBridgeDefaults.ts` တွင်ရှိသည်။ Guardrail သည်
`deps` constructor option ကို ပေးထားသောကြောင့် test များက `getSettings` နှင့်
`callVisionModel` implementation အတုများကို inject လုပ်နိုင်သည်။

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Audio input ကို လက်ခံနိုင်ကြောင်း မသိရသေးသော target သို့ audio ပါဝင်သည့် chat request များ မရောက်မီ
ကြားဖြတ်လုပ်ဆောင်သည်။ ၎င်းသည် chat request ကို မည်သည့်အခါမျှ route ပြောင်းပေးခြင်းမရှိပါ။ Audio part များကို
လက်ရှိ OpenAI-compatible multipart endpoint မှတစ်ဆင့် စာသားအဖြစ် ကူးပြောင်းပြီး
ရွေးချယ်ထားသော chat model သည် စာသား transcript များဖြင့် ဆက်လက်လုပ်ဆောင်သည်။

စီးဆင်းပုံ-

1. `getResolvedModelCapabilities()` မှတစ်ဆင့် `supportsAudio` ကို ဖြေရှင်းပါ။ Explicit
   provider-registry metadata ကို ဦးစားပေးပြီး၊ ထို့နောက် static model metadata၊ ထို့နောက် sync လုပ်ထားသော
   `modalities_input` ကို အသုံးပြုသည်။ `audio` မပါသော ကြေညာထားသည့် input list သည် `false` ဖြစ်ပြီး
   capability အထောက်အထား လုံးဝမရှိပါက `null` ဖြစ်သည်။ `false` နှင့် `null` နှစ်မျိုးလုံးသည်
   သတိထားလုပ်ဆောင်သော bridge ကို activate လုပ်ပြီး `true` ဖြစ်ပါက ၎င်းကို bypass လုပ်သည်။
2. `modalityBridgeAudio*` setting များကို ဖြေရှင်းပြီး shared `detectMediaParts()`
   detector မှတစ်ဆင့် message တိုင်းမှ splice လုပ်နိုင်သော top-level audio part များကို ထုတ်ယူပါ။
   ပံ့ပိုးထားသော wire shape များမှာ OpenAI `input_audio`, `audio_url` နှင့်
   `source.media_type: "audio/*"` တို့ဖြစ်သည်။ Nested audio ကို routing အတွက် ရှာဖွေသိရှိသော်လည်း
   splice path မှ မဖယ်ရှားပါ။ လုပ်ဆောင်မှုကို `modalityBridgeAudioMaxClips` ဖြင့် ကန့်သတ်ထားပြီး
   နောက်ပိုင်း part များကို မပြောင်းလဲဘဲ ထားသည်။
3. ဖွဲ့စည်းသတ်မှတ်ထားသော `provider/model` ကို လိုက်နာပါ၊ သို့မဟုတ် `selectAudioBridgeModel()` က
   stable catalog အစဉ်အတိုင်း `AUDIO_TRANSCRIPTION_PROVIDERS` ကို စစ်ဆေးပြီး အသုံးပြုနိုင်သော
   active provider credential ပါသည့် ပထမဆုံး model ကို ရွေးချယ်စေပါ။
4. `callAudioTranscription()` သည် base64/data-URI audio ကို multipart
   `file` အဖြစ် ပြောင်းလဲသည်၊ သို့မဟုတ် remote `audio_url` ကို DNS pinning နှင့် 25 MB ကန့်သတ်ချက်ပါဝင်သော
   public-only outbound guard မှတစ်ဆင့် download လုပ်သည်။ ထို့နောက် file နှင့် ရွေးချယ်ထားသော
   model ကို local `/v1/audio/transcriptions` self-loop သို့ POST လုပ်ပြီး
   `resolveSelfLoopBearer()` ဖြင့် authentication ပြုလုပ်သည်။ လက်ရှိ transcription route သည် ပုံမှန်
   credential ရှာဖွေမှု၊ cooldown/rate-limit ကိုင်တွယ်မှုနှင့် provider dispatch တို့ကို လုပ်ဆောင်သည်။
5. အောင်မြင်သော call များသည် ၎င်းတို့၏ part များကို `[Audio N]: <transcript>` ဖြင့် အစားထိုးသည်။ Call များကို
   `Promise.allSettled` ဖြင့် လုပ်ဆောင်ပြီး call တစ်ခုချင်းစီ မအောင်မြင်ပါက မူလ
   audio part ကို ဆက်လက်ထိန်းသိမ်းထားသည် (#4012 contract)။ Call အားလုံး မအောင်မြင်ပြီး target သည်
   `supportsAudio === false` ဖြစ်ကြောင်း သက်သေပြထားပါက part များသည်
   `[Audio N]: (unavailable — no STT provider connected)` ဖြစ်လာသည် (#8430 contract)။ မသိရသေးသော
   target (`null`) အတွက် အားလုံးမအောင်မြင်သည့် ရလဒ်ကို မပြောင်းလဲဘဲထားသည်။ အသုံးပြုနိုင်သော
   STT credential မရှိသည့် text-only target တစ်ခုတွင် network call မပြုလုပ်ဘဲ အလားတူ explicit
   stub ကို ထည့်သွင်းပေးသည်။

အောင်မြင်သော transcript များသည် process တစ်ခုလုံးအတွက် Modality Bridge LRU/TTL cache ကို အသုံးပြုသည်။
Key သည် audio reference၊ တည်ငြိမ်သော `audio-transcription` operation
label နှင့် ရွေးချယ်ထားသော STT model တို့ကို ပေါင်းစပ်ထားသည်။ မအောင်မြင်မှုများကို မည်သည့်အခါမျှ cache မလုပ်ပါ။ Audio attempt များသည်
shared `bridged`, `cacheHits`, `failures` နှင့် `lastUsedAt` counter များကို update လုပ်သည်။
ပြောင်းလဲထားသော response များတွင်
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ပါဝင်ပြီး မပြောင်းလဲထားသော
request များတွင် Audio Bridge segment မပါဝင်ပါ။

Runtime setting များသည် DB-backed ဖြစ်ပြီး Zod ဖြင့် validate လုပ်ထားသည်-

| ကီး                           | မူလတန်ဖိုး | အပိုင်းအခြား                 |
| ----------------------------- | ---------- | ---------------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                            |
| `modalityBridgeAudioModel`    | `""`       | အလိုအလျောက် သို့မဟုတ် STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000                  |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                         |

မျှဝေသုံးစွဲသည့် cache ကို `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` နှင့် `modalityBridgeCacheMaxEntries` တို့ဖြင့် ဆက်လက်ထိန်းချုပ်သည်။

### ဗီဒီယို Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

မူရင်းဗီဒီယိုပံ့ပိုးမှုရှိကြောင်း မသိရသည့် ပစ်မှတ်တစ်ခုကို မခေါ်ဆိုမီ Chat Completions `messages` နှင့် Responses
API `input` အတွင်းရှိ ထိပ်ဆုံးအဆင့် ဗီဒီယိုအစိတ်အပိုင်းများကို ကြားဖြတ်ဆောင်ရွက်သည်။
ပံ့ပိုးထားသော ပုံစံများမှာ `input_video`, `video_url`, `video_source`, HTTPS URLs
နှင့် `data:video/*;base64,...` data URIs တို့ဖြစ်သည်။ စာသားအတွင်းရှိ သာမန်ဖိုင်အမည်များကို
ဗီဒီယိုအဖြစ် မသတ်မှတ်ပါ။

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) သည် တောင်းဆိုချက်အတွင်း လှည့်လည်စစ်ဆေးခြင်း၊
စွမ်းဆောင်ရည်/မူဝါဒ စစ်ဆေးခြင်း၊ တောင်းဆိုချက်တစ်ခုချင်းအလိုက် စုစည်းခြင်းနှင့် တုံ့ပြန်မှု payload တို့ကို တာဝန်ယူသည်။
ဗီဒီယိုတစ်ခုချင်းအလိုက် လုပ်ဆောင်မှုများ — ရယူခြင်း၊ ရလဒ်တစ်ခုလုံး cache၊ frame
အစဉ်တစ်ခုကို ဖော်ပြခြင်း (ခေါ်ဆိုသူက သတ်မှတ်ထားသည့် အသံ transcript ရှိပါက ပေါင်းစပ်ပေးခြင်း) နှင့် ကြိုးပမ်းမှုတစ်ကြိမ်ချင်းအလိုက်
metrics/abort/cleanup — ကို `videoBridgePipeline.ts` ရှိ `processVideoPart` နောက်ကွယ်တွင်
ဖုံးကွယ်ထားပြီး `preCall` ၏ loop အတွင်း ဗီဒီယိုအစိတ်အပိုင်းတစ်ခုလျှင် တစ်ကြိမ် ခေါ်ဆိုသည်။
ထို module တွင် ရှင်းလင်းစွာသတ်မှတ်ထားသော port နယ်နိမိတ်များဖြစ်သည့် `VideoMediaBrokerPort`
(bytes ရယူခြင်းနှင့် နမူနာယူထားသော frames များ ထုတ်ယူခြင်း)၊ `VideoAudioTranscriptionPort`
(ခေါ်ဆိုသူသတ်မှတ်ထားသော အသံ transcript ကို နမူနာယူထားသော captions များနှင့် ပေါင်းစပ်ခြင်း) နှင့်
`VideoDrilldownPort` (frame drill-down သိမ်းဆည်းမှုနယ်နိမိတ်၊ `processVideoPart` နှင့် ချိတ်ဆက်မထားသေးပါ —
ယနေ့တွင် သီးခြား `/api/modality-bridge/video/drilldown` route သာ drill-down entries များကို ရေးသားသည်) တို့ကိုလည်း သတ်မှတ်ထားသည်။

အများသုံး `/v1` တောင်းဆိုချက်လမ်းကြောင်းသည် subprocess တစ်ခုကို မည်သည့်အခါမျှ import သို့မဟုတ် invoke မလုပ်ပါ။ အဝေးရှိ
ဗီဒီယိုများကို 50 MiB ကန့်သတ်ချက်အောက်တွင် ဒေါင်းလုဒ်လုပ်သည်။ inline base64 ဗီဒီယိုများတွင်
model/messages/framing envelope သည် 50 MiB ဖြစ်သော အများသုံး JSON တောင်းဆိုချက် လက်ခံရေးကန့်သတ်ချက်အတွင်း

ဖွင့်နိုင်သော ရွေးချယ်စရာများ မဟုတ်ပါ။ ဖွင့်နိုင်သော streams အားလုံးသည် ကန့်သတ်ချက်များကို ပြည့်မီရမည်ဖြစ်ပြီး

`scene_aware` နှင့် စမ်းသပ်ဆဲ `segment_aware` မူဝါဒများသည် အတည်ပြုပြီးသား local stream ပေါ်တွင်
နောက်ထပ် သတ်မှတ်ထားသော FFmpeg pass တစ်ကြိမ် လုပ်ဆောင်ကာ ကန့်သတ်ထားသည့်
`showinfo` scene timestamps များကို ရွေးချယ်ပြီး detector မအောင်မြင်ခြင်း၊ timeout ဖြစ်ခြင်း၊ output ပုံစံမမှန်ခြင်း
သို့မဟုတ် candidate set ဗလာဖြစ်ခြင်းတို့တွင် တူညီသော uniform midpoints များသို့ deterministic အနေနှင့်
fallback လုပ်သည်။ Segment-aware mode သည် အတည်ပြုထားသော scene intervals များနှင့် အချိုးကျစွာ
midpoint samples များကို ခွဲဝေပေးသည်။ segment-aware အထောက်အထားနှင့် fallback အပြုအမူကို
အောက်တွင် အသေးစိတ်ဖော်ပြထားသည်။ မူဝါဒတိုင်းတွင်
ရွေးချယ်ပြီးနောက် တင်းကျပ်သော 16-frame ကန့်သတ်ချက်ကို သက်ရောက်စေသည်။ Scene-aware တောင်းဆိုချက်တစ်ခုတွင်
frame တစ်ခုစာ budget သာရှိပါက လက်ရှိ full-video သို့မဟုတ် focus window ၏ uniform midpoint ကို အသုံးပြုပြီး
`policyEffective: uniform` ဟု အစီရင်ခံသည်။ ရွေးချယ်ထားသော scene frame တစ်ခုတည်းသည် timeline ၏ အစနှင့်အဆုံး
နှစ်ဖက်စလုံးကို မထိန်းသိမ်းနိုင်ပါ။ ခေါ်ဆိုသူသည် finite focus window (`start`/`end` seconds) ကို
ရွေးချယ်၍ ပေးနိုင်သည်။ bounds များကို media duration အတွင်းသို့ clamp လုပ်ပြီး ပြောင်းပြန်ဖြစ်နေသော သို့မဟုတ်
finite မဟုတ်သော windows များကို ပယ်ချကာ sampling မူဝါဒအားလုံးကို normalized interval အတွင်းတွင်သာ
လုပ်ဆောင်သည်။ ရရှိလာသော window ကို sampling metadata နှင့် ယုံကြည်မထားရသော description
prefix နှစ်ခုစလုံးတွင် ထည့်သွင်းထားသောကြောင့် downstream models များက အာရုံစိုက်ထားသော အပိုင်းတိုတစ်ခုကို
timeline အပြည့်နှင့် ခွဲခြားနိုင်သည်။

caption model ထံ မည်သည့်အခါမျှ မပို့ပါ။ `focused` mode တွင် bridge သည် တူညီသော Chat သို့မဟုတ် Responses
container မှ အသုံးပြုသူရေးသားထားသည့် နောက်ဆုံး non-empty `text`/`input_text` ကိုသာ ဖတ်ရှုပြီး
NFC သို့ normalize လုပ်ကာ control characters နှင့် whitespace များကို ပေါင်းချုံ့ပြီး
Unicode code points 500 အထိ ကန့်သတ်သည်။ ရလဒ်ဗလာဖြစ်ပါက အတိအကျတူညီသော `full` prompt သို့
fallback လုပ်သည်။ အသုံးပြုနိုင်သော hint ကို သီးခြား untrusted-user-context block အတွင်း JSON အဖြစ်
serialize လုပ်ထားပြီး မျက်မြင်လေ့လာနိုင်သော အသေးစိတ်အချက်များကိုသာ ဦးစားပေးနိုင်သည်။ ၎င်းသည် media အတွင်း
မြင်ရသော သို့မဟုတ် ကြားရသော ညွှန်ကြားချက်များကို မလိုက်နာရန် သီးခြားသတိပေးချက်ကို override မလုပ်နိုင်ပါ။

#### FU-07 ဖွဲ့စည်းပုံဆိုင်ရာ segment အထောက်အထား

`segment_aware` သည် အတည်ပြုပြီးသား local video stream ကို ကန့်သတ်ထားသည့် ကြိုတင်ဆန်းစစ်မှုတစ်ကြိမ်ဖြင့် လုပ်ဆောင်သည်။ ပုံသေ filter chain သည် ဦးစွာ အကျယ်ကို အများဆုံး 320 pixels အထိ ချုံ့ပြီး scene အပြောင်းအလဲများနှင့် ရပ်တန့်နေသည့် interval များကို ရှာဖွေကာ ထို့နောက် blur၊ ပျမ်းမျှ luma နှင့် spatial/temporal အချက်အလက်တို့အတွက် တစ်စက္ကန့်လျှင် 1 frame နှုန်းဖြင့် sample ယူသည်။ ဤလုပ်ဆောင်မှုကို structural sample 600 ခု၊ FFmpeg/filter thread တစ်ခု၊ တူညီသော `file`-သာ protocol နှင့် container allowlist များ၊ process output အများဆုံး 1 MiB နှင့် broker ၏ မျှဝေထားသော abort/deadline အတွင်း အများဆုံး 30 စက္ကန့်ဖြင့် ကန့်သတ်ထားသည်။ ၎င်းသည် request မှ command၊ filter၊ path သို့မဟုတ် URL တစ်ခုခုကို မည်သည့်အခါမျှ လက်မခံပါ။

Structural value များသည် သတ်မှတ်တိကျစွာ ပြန်လည်ရရှိနိုင်သော sampling အထောက်အထားများသာဖြစ်ပြီး video ၏ အဓိပ္ပာယ်ကို နားလည်ခြင်းမဟုတ်ပါ။ ၎င်းတို့သည် အကြောင်းအရာပုဂ္ဂိုလ်များ၊ လုပ်ဆောင်ချက်များ၊ caption များ၊ စကားပြောသံ သို့မဟုတ် အသုံးပြုသူ၏ ရည်ရွယ်ချက်ကို ခန့်မှန်းမဖော်ထုတ်ပါ။ Scene နှင့် freeze boundary များက segment များကို ဖွဲ့စည်းသည်။ Freeze coverage၊ blur၊ exposure၊ spatial detail နှင့် temporal change တို့သည် ရှိပြီးသား frame budget 1–16 ကို မည်သို့ခွဲဝေမည်ကိုသာ သက်ရောက်စေသည်။ လုံးဝရပ်တန့်နေသော segment တစ်ခုကို frame တစ်ခုအထိသာ ကန့်သတ်ထားပြီး ရပ်တန့်မနေသော segment များသည် ကျန်ရှိသည့် budget အတွက် ယှဉ်ပြိုင်ကြသည်။ Boundary အရေအတွက်က frame အရေအတွက်ထက် များသည့်အခါ အစပိုင်းရှိ လျင်မြန်သော cut များကြောင့် နောက်ဆုံးရှိ ရှည်လျားသော segment တစ်ခု မပျောက်ကွယ်စေရန် timeline တစ်လျှောက် ညီမျှသော coverage ကို ဆက်လက်ထိန်းသိမ်းထားသည်။ Freeze boundary တစ်ခု၏ 1-second analysis resolution အတွင်းရှိ scene boundary များကို ပေါင်းစည်းသည်။

Filter မရှိခြင်း၊ ပုံစံပျက်နေသော/ဗလာဖြစ်သော evidence၊ detector error သို့မဟုတ် ကန့်သတ်ထားသည့် ကြိုတင်ဆန်းစစ်မှု timeout တို့ဖြစ်ပေါ်ပါက အတိအကျတူညီသော uniform midpoint policy သို့ fail open လုပ်သည်။ Caller abort သို့မဟုတ် broker deadline ဖြစ်ပါက fail open မလုပ်ပါ။ ၎င်းသည် လုပ်ဆောင်နေဆဲ subprocess ကို ရပ်တန့်စေပြီး နောက်ထပ် frame extraction ကို တားဆီးကာ private temporary tree ကို `finally` အတွင်း ဖယ်ရှားသည်။

`scripts/perf/video-bridge-fu07-eval.ts` သည် post-dedup caption-call ချွေတာမှု၊ dense-motion budget allocation၊ blur/exposure/SI-TI evidence၊ ရှည်လျားသော နောက်ပိုင်းအပိုင်းပါသည့် လျင်မြန်သော cut များနှင့် gradual-fade false positive များအတွက် သတ်မှတ်တိကျစွာ ပြန်လည်ဖန်တီးနိုင်သော FFmpeg fixture အစစ်များကို ထုတ်လုပ်သည်။ ၎င်းသည် ကြိုတင်ဆန်းစစ်မှု wall time ကို မှတ်တမ်းတင်ပြီး `/usr/bin/time` ရရှိနိုင်သည့်နေရာတွင် child CPU နှင့် peak RSS ကိုပါ မှတ်တမ်းတင်သည်။ ၎င်း၏ quality check များသည် structural oracle များသာဖြစ်သည်။ ဤ harness တွင် ခွင့်ပြုထားသော endpoint သို့မဟုတ် အတည်ပြုထားသော frozen judge မရှိသောကြောင့် caption model အစစ်၏ အရည်အသွေးသည် `HOLD` အဖြစ် ဆက်ရှိနေသည်။ `--caption-cost-per-call-usd` က call တစ်ကြိမ်လျှင် အတိအလင်း အပေါင်းတန်ဖိုးရှိသော ခန့်မှန်းကုန်ကျစရိတ်ကို မပေးထားပါက ငွေကြေးချွေတာမှုသည်လည်း `HOLD` အဖြစ် ဆက်ရှိနေသည်။ Script သည် ရလဒ်တစ်ခုခုကို မည်သည့်အခါမျှ လုပ်ကြံဖန်တီးခြင်းမပြုပါ။

Frame တစ်ခုစီကို 4 MiB အထိ၊ raw frame အားလုံးပေါင်းကို 23 MiB အထိနှင့် serialized broker response ကို 32 MiB အထိ ကန့်သတ်ထားသည်။ Private temporary directory ကို `finally` အတွင်း ဖယ်ရှားသည်။ OmniRoute တွင် FFmpeg ကို တစ်ပါတည်းမထည့်သွင်းထားသကဲ့သို့ စိတ်ကြိုက် executable path ကိုလည်း လက်မခံပါ။ Caption မပြုလုပ်မီ bridge သည် ရုပ်ပုံအပေါ် သတိထားကန့်သတ်ထားသော deduplication pass တစ်ခုကို လုပ်ဆောင်သည်။ JPEG တစ်ခုစီကို 16×16 grayscale buffer အဖြစ် ချုံ့ပြီး နောက်ဆုံးထိန်းသိမ်းထားသည့် frame နှင့်သာ နှိုင်းယှဉ်သည်။ တောင်းဆိုထားသော caption budget သည် frame တစ်ခုထက်များပါက extraction သည် ထို budget ၏ နှစ်ဆအထိဖြစ်ပြီး frame 16 ခုထက် မပိုသော ကန့်သတ် candidate pool တစ်ခုကို ပေးသည်။ တောင်းဆိုထားသော cap ကို deduplication ပြီးနောက်မှသာ အသုံးချပြီး budget သည် အနည်းဆုံး နှစ်ခုဖြစ်ပါက နောက်ဆုံး thinning လုပ်စဉ် ပထမနှင့် နောက်ဆုံးရွေးချယ်ထားသော candidate များကို ထိန်းသိမ်းထားသည်။ Version သတ်မှတ်ထားသော `grayscale-16x16-mean-cells-v2` policy သည် ပျမ်းမျှ luma delta နှင့် normalized delta အနည်းဆုံး 0.05 ရှိသော thumbnail cell အချိုးတို့အနက် ပိုကြီးသည့်တန်ဖိုးကို အသုံးပြုသည်။ Duplicate threshold သည် ကိန်းသေ 0.04 ဖြစ်ပြီး runtime setting အဖြစ် ဖော်ထုတ်ထားခြင်းထက် ကြိုတင်ခန့်မှန်းနိုင်မှုအတွက် ရွေးချယ်ထားခြင်းဖြစ်သည်။ ဤဒုတိယ high-contrast signal သည် mean-only comparison ဖြင့် ဖုံးကွယ်သွားနိုင်သည့် သေးငယ်သော လှုပ်ရှားမှုနှင့် မြင်ရသောစာသား အပြောင်းအလဲများကို ထိန်းသိမ်းပေးသည်။ Comparator သို့မဟုတ် decoder error များဖြစ်ပါက fail open လုပ်ပြီး coverage ကို ဆက်လက်ထိန်းသိမ်းသည်။ Output metadata သည် ထုတ်ယူထားသော candidate များ၊ အောင်မြင်စွာ အသုံးပြုထားသော frame များနှင့် ဖယ်ရှားထားသော visual duplicate များကို သီးခြားခွဲပြသည်။

အတိအလင်း အမှတ်အသားပြုထားသော video part တစ်ခုသည် timestamp ပါသော contact sheet ကို တောင်းဆိုနိုင်သည်။ Bridge သည် အများဆုံး column 4 ခု၊ frame 16 ခုပါဝင်သော JPEG grid ကို တည်ဆောက်သည်။ 512-pixel cell တစ်ခုစီတွင် ၎င်း၏ မူရင်း timestamp ကို အောက်ခြေရှိ high-contrast band ပေါ်၌ တိုက်ရိုက်ထည့်သွင်းပြီး အောက်ဆင့်ဆက်စပ်သတ်မှတ်ခြင်းနှင့် စစ်ဆေးခြင်းတို့အတွက် တူညီသော timestamp များကို textual metadata ထဲတွင်လည်း ထိန်းသိမ်းထားသည်။ ပြီးပြည့်စုံသော JPEG ကို 32 MiB အထိသာ ကန့်သတ်ထားသည်။ `sharp` က grid ကို decode သို့မဟုတ် compose မလုပ်နိုင်ပါက bridge သည် JPEG frame တစ်ခုချင်းစီကို ပြန်လည်အသုံးပြုသည်။ Client abort ဖြစ်ပါက sheet operation တစ်လျှောက် ဆက်လက်သက်ရောက်သည်။

Promotion evidence ကို synthetic composition microbenchmark မှ တမင်သီးခြားခွဲထားသည်။ `scripts/perf/video-bridge-contact-sheet-eval.ts` သည် OpenAI-compatible vision model အစစ်များအတွက် schema-versioned A/B harness တစ်ခုကို သတ်မှတ်သည်။ ၎င်းသည် provider က တင်ပြသော token များ၊ end-to-end wall latency (sheet composition အပါအဝင်)၊ model-call count နှင့် manifest က သတ်မှတ်ထားသော fact retention တို့ကို တိုင်းတာသည်။ Raw model response များကို report ထဲသို့ မရေးဘဲ SHA-256 digest များနှင့် ကိုက်ညီသည့် fact ID များကိုသာ ထိန်းသိမ်းထားသည်။ `--execute-real` ကို ပေးထားပြီး `--model`၊ `OMNIROUTE_BASE_URL` နှင့် `OMNIROUTE_API_KEY` တို့ကို configure လုပ်ထားခြင်းမရှိပါက harness သည် network သို့မဟုတ် အခပေး model call တစ်ခုမျှ မပြုလုပ်ပါ။ ထိုကဲ့သို့ အတိအလင်း လုပ်ဆောင်သော real run မရှိပါက ၎င်း၏ machine-readable verdict သည် `HOLD` အဖြစ် ဆက်ရှိနေသည်။ Synthetic payload/call-count တိုင်းတာမှုများတစ်ခုတည်းသည် promotion evidence မဟုတ်ပါ။

Caller များသည် အချိန်နှင့်ချိန်ညှိထားသော စာသားကို ရရှိထားပြီးဖြစ်ပါက ပံ့ပိုးထားသော video part တစ်ခုတွင် ရွေးချယ်နိုင်သည့် `transcript.cues` array ကို ပူးတွဲနိုင်သည်။ Cue တစ်ခုစီတွင် `text`၊ စမ်းသပ်တိုင်းတာထားသော duration အတွင်းရှိ အဆုံးသတ်တန်ဖိုးရှိသည့် `start`/`end` interval နှင့် whitelist ထဲပါဝင်သော `source` (`client`၊ `embedded` သို့မဟုတ် `audio-bridge`) တို့ ပါရှိရမည်။ `confidence` သည် ပုံသေအားဖြင့် `1` ဖြစ်ပြီး `0` နှင့် `1` ကြားတွင် ရှိရမည်။ လုံးဝတူညီသော cue များကို ပေါင်းစည်းသည်။ OmniRoute သည် ဤ metadata မှ transcription ကို မည်သည့်အခါမျှ စတင်ခြင်းမရှိပါ။ အတည်ပြုပြီးသော cue များကို source၊ confidence နှင့် interval တို့နှင့်အတူ ဖော်ပြထားသည့် result ထဲသို့ ကူးယူပြီး frame caption များနှင့်အတူ မယုံကြည်ရသော observation များအဖြစ် ဖော်ပြသည်။ မမှန်ကန်သော၊ အပိုင်းအခြားပြင်ပရောက်နေသော သို့မဟုတ် provenance မပါသော စာသားကို caption stream ထဲသို့ ရောထည့်မည့်အစား ပယ်ချသည်။ Request-body transcript channel နှစ်ခုစလုံးသည် ကိုယ်တိုင်အခိုင်အမာဆိုထားသော `embedded` သို့မဟုတ် `audio-bridge` label များအပါအဝင် ပေးထားသည့် provenance ကို `client` အဖြစ် normalize လုပ်သည်။ Server ပိုင် adapter တစ်ခုသာ code-only `trustedSource` argument မှတစ်ဆင့် ယုံကြည်ရသော label များကို သတ်မှတ်နိုင်သည်။ Request JSON field တစ်ခုသည် ထို argument ကို မရောက်ရှိနိုင်ပါ။ Transcript စာသားသည် ၎င်း၏ provenance မည်သို့ပင်ဖြစ်စေ မယုံကြည်ရသော media-derived content အဖြစ် ဆက်ရှိနေပြီး authorization ကို မည်သည့်အခါမျှ ဆုံးဖြတ်ခွင့်မရှိပါ။

အဆင့်မြင့် caller တစ်ခုသည် တူညီသော video အတွက် `audioTranscript` track တစ်ခုကို ပေးနိုင်သည်၊
၎င်းကို server က transcription ပြုလုပ်ထားကြောင်း သက်သေအဖြစ်မဟုတ်ဘဲ client က ပေးထားသော စာသားအဖြစ် သတ်မှတ်သည်။
ပေါင်းစည်းရေး seam သည် deadline တစ်ခုနှင့် abort signal တစ်ခုအောက်တွင်

အတွင်းပိုင်း `/api/modality-bridge/video/drilldown` lifecycle သည် သီးခြားဖြစ်ပြီး loopback/token ဖြင့် အထောက်အထားစိစစ်ထားသော cache substrate တစ်ခုဖြစ်သည်။ Operation တစ်ခုစီအတွက် canonical opaque principal ID တစ်ခုလည်း လိုအပ်သည်။ Production caller တစ်ခုကို enable မလုပ်မီ ၎င်းသည် အထောက်အထားစိစစ်ပြီးသော tenant မှ ထို ID ကို derive လုပ်ရမည်ဖြစ်ပြီး client က ရွေးချယ်ထားသော value ကို မည်သည့်အခါမျှ forward မလုပ်ရပါ။ Cache key များသည် ထို principal ကို canonical session နှင့် video-reference ID များနှင့် bind လုပ်ပြီး ၎င်းတို့၏ SHA-256-derived key များကိုသာ သိမ်းဆည်းကာ read နှင့် deletion နှစ်မျိုးလုံးကို တူညီသော principal အတွင်းသာ scope သတ်မှတ်သည်။ Cache သည် entry တစ်ခုလျှင် derive လုပ်ထားသော JPEG frame 16 ခုအထိသာ သိမ်းဆည်းပြီး ဆယ်မိနစ်အကြာတွင် ၎င်းတို့ကို expire လုပ်ကာ အကန့်အသတ်ရှိသော `start`/`end` read များ သို့မဟုတ် session ကို အတိအလင်း delete လုပ်ခြင်းကို ပံ့ပိုးသည်။

Principal တစ်ခုစီကို entry 16 ခုနှင့် canonical JPEG data 64 MiB အထိ ကန့်သတ်ထားသည်။ ထိုကန့်သတ်ချက်များသည် global entry 64 ခု/256 MiB အများဆုံးကန့်သတ်ချက်နှင့် သီးခြားဖြစ်သည်။ Principal quota ဖိအားဖြစ်ပေါ်ပါက global LRU eviction ကို မစဉ်းစားမီ ထို principal ၏ မကြာသေးမီက အနည်းဆုံးအသုံးပြုထားသော entry များကိုသာ evict လုပ်သည်။ Cache လုပ်ဆောင်မှုရှိသည့်အခါ expire ဖြစ်ပြီးသော entry များကို principal နှင့် global accounting နှစ်ခုလုံးမှ ရှင်းလင်းဖယ်ရှားပြီး cancellation နှင့် validation failure တို့သည် တစ်စိတ်တစ်ပိုင်း replacement ကို commit မလုပ်ပါ။

Cache သည် canonical မဟုတ်သော Base64၊ လွန်ကဲသော padding၊ JPEG မဟုတ်သည့် media၊ ပုံစံပျက်နေသော သို့မဟုတ် ဖြတ်တောက်ထားသော JPEG များနှင့် အကန့်အသတ်ရှိသော full-image `sharp` decode ပြုလုပ်စဉ် warning ဖြစ်ပေါ်စေသော JPEG များကို ငြင်းပယ်သည်။ လက်ခံထားသော image တစ်ခုစီကို canonical JPEG အဖြစ် ပြန်လည် encode လုပ်ပြီး caller ပေးသော field များကို ယုံကြည်မည့်အစား decode လုပ်ထားသော byte များမှ width နှင့် height ကို derive လုပ်ကာ နောက်ဆက်တွဲ polyglot byte များကို ထိန်းသိမ်းမထားဘဲ စွန့်ပစ်သည်။ အကန့်အသတ်ရှိသော canonical compressed buffer ကိုသာ quota နှစ်ခုလုံးတွင် ထည့်သွင်းတွက်ချက်သည်။ JSON wire limit တွင် 32 MiB decoded-input ceiling အတွက် Base64 overhead ပါဝင်သည်။ သိမ်းဆည်းထားသော derivation တစ်ခုစီသည် validation ပြီးသော JPEG format/resolution၊ sampling policy၊ derivation version၊ ဖန်တီးချိန်၊ server က တွက်ချက်ထားသော content hash၊ hashed parent reference နှင့် trusted caller ၏ parent-content hash တို့ကို မှတ်တမ်းတင်သည်။ Atomic cache commit မပြုလုပ်မီ asynchronous decode/hash phase များကြားတွင် cancellation ကို စစ်ဆေးသည်။

ဤ tranche သည် production producer တစ်ခုကို route နှင့် မချိတ်ဆက်ရသေးသလို multi-resolution variant ရွေးချယ်မှုကိုလည်း မပံ့ပိုးသေးပါ။ ထို့ကြောင့် transparent Video Bridge request path တွင် ထပ်ဆောင်းလုပ်ဆောင်မှု မရှိဘဲ tenant နှင့် bind လုပ်ထားသော principal derivation နှင့် FU-08 multi-resolution lifecycle အပြည့်အစုံသည် ပြီးစီးထားသော အပြုအမူအဖြစ် မှတ်တမ်းတင်ထားခြင်းမဟုတ်ဘဲ နောက်ဆက်တွဲ လုပ်ဆောင်ရမည့်အလုပ်များအဖြစ် ဆက်လက်ရှိနေသည်။

Frame များကို configure လုပ်ထားသော Video model ဖြင့် အစဉ်လိုက် caption ရေးသားသည်။ Video override အလွတ်ဖြစ်ပါက Vision setting ကို ဆက်ခံသည်။ နှစ်ခုလုံး အလွတ်ဖြစ်ပါက Vision auto-router က ထိရောက်အသုံးပြုမည့် vision-capable model ကို ရွေးချယ်သည်။ အောင်မြင်သော caption များသည် မူလ part ကို တည်ငြိမ်သော `[Video description:` prefix ပါသည့် စာသားဖြင့် အစားထိုးသည်။ ထို prefix သည် စာသားကို ယုံကြည်၍မရသော media-derived observation အဖြစ်လည်း မှတ်သားပေးပြီး media ထဲတွင် တွေ့ရှိသော instruction များကို မလိုက်နာရန် downstream model များအား အသိပေးသည်။ Frame-caption cache key များတွင် JPEG byte များ၊ prompt၊ timestamp နှင့် effective model တို့ ပါဝင်ပြီး အောင်မြင်သော caption များကိုသာ cache လုပ်သည်။ Cache entry များသည် fallback model အပါအဝင် အမှန်တကယ် အောင်မြင်စွာ ထုတ်လုပ်ပေးခဲ့သော producer model ကို ထိန်းသိမ်းထားသည်။ မတူညီသော frame များကို မတူညီသော model များက ထုတ်လုပ်ထားပါက bridge က `mixed` ဟု report လုပ်သည်။ Cache hit တစ်ခုသည် requested routing plan အဖြစ် label ပြန်တပ်မည့်အစား ထို producer identity ကို ပြန်လည်အသုံးပြုသည်။ Whole-video result cache ကို output ပြောင်းလဲစေသော input အားလုံး—prompt၊ effective model၊ sampling policy၊ frame count၊ semantic analysis mode၊ normalized focus hint ၏ SHA-256 fingerprint၊ focus window၊ `transcript`၊ `audioTranscript` နှင့် contact-sheet flag—အပေါ် အခြေခံ၍ key သတ်မှတ်ထားသည်။ ထို့ကြောင့် ထို dimension များထဲမှ တစ်ခုခုပြောင်းလဲပါက cache miss ဖြစ်ပြီး stale data ကို မည်သည့်အခါမျှ ပြန်လည်အသုံးမပြုပါ။ Visual dedup policy version၊ threshold နှင့် အကန့်အသတ်ရှိသော candidate-frame count တို့ကိုလည်း result-cache key နှင့် metadata တွင် အတိအလင်း ထည့်သွင်းထားသည်။ ထို့ကြောင့် policy အပြောင်းအလဲတစ်ခုသည် stale whole-video description ကို ပြန်လည်အသုံးမပြုနိုင်ပါ။ Result-cache v4 metadata သည် mode နှင့် fingerprint ကို ထိန်းသိမ်းထားသော်လည်း raw user task ကို မည်သည့်အခါမျှ မသိမ်းဆည်းပါ။ Guardrail metadata သည် requested analysis mode နှင့် effective analysis mode နှစ်ခုလုံးကို report လုပ်သည်။ အသုံးပြုနိုင်သော user text မပါဘဲ `focused` mode ကို request လုပ်ထားပါက ထိရောက်စွာ `full` ဖြစ်သည်ဟု report လုပ်သည်။

Guardrail သည် ပံ့ပိုးထားသော video part အားလုံးကို extract လုပ်သော်လည်း `modalityBridgeVideoMaxVideos` ထက်ပို၍ description မလုပ်ပါ။ `supportsVideo === false` ဖြစ်ကြောင်း သက်သေပြထားသော target တစ်ခုအတွက် မအောင်မြင်သော video နှင့် ကန့်သတ်ချက်ကျော်လွန်သော video များကို အတိအလင်း safe text marker များအဖြစ် ပြောင်းလဲသဖြင့် raw video တစ်ခုမျှ မကျန်ရှိပါ။ Capability ကို မသိနိုင်သည့်အခါ ထို part များသည် ၎င်းတို့၏ video carrier ကို ဆက်လက်ထိန်းသိမ်းထားပြီး fallback transcript ရှိပါက အထက်ပါ အကန့်အသတ်ရှိသော text conversion ကို လိုက်နာသည်။ `supportsVideo === true` ဖြစ်သော target များသည် bridge ကို bypass လုပ်သည်။ Client request abort signal သည် download၊ broker queue၊ subprocess များနှင့် caption call များတစ်လျှောက် propagate ဖြစ်သည်။ Abort များသည် video များကြားတွင် ရပ်တန့်စေပြီး raw media ကို fail open လုပ်ခြင်း မရှိပါ။

### PII Masker (`piiMasker.ts`)

အဆင့် **နှစ်ဆင့်လုံး** တွင် အလုပ်လုပ်သည်။

- **`preCall`** သည် payload ကို clone လုပ်ပြီး `system`၊ `messages`၊ `input` နှင့်
  `prompt` (ရိုးရိုး string item များအပါအဝင်) တစ်လျှောက် စစ်ဆေးကာ string `content`/`text`
  field များတွင် (`@/shared/utils/inputSanitizer` မှ) `processPII()` ကို အသုံးချသည်။
  `PII_REDACTION_ENABLED=true` ဖြစ်သောအခါ တွေ့ရှိထားသော PII ကို outbound
  payload တွင် ဖုံးကွယ်သည်။ ဤလုပ်ဆောင်ချက်သည် prompt-injection policy ကိုသာ ထိန်းချုပ်သည့်
  `INPUT_SANITIZER_MODE` နှင့် သီးခြားဖြစ်သည်။ ဖုံးကွယ်ခြင်း ပိတ်ထားသောအခါ content ကို
  ပြန်လည်ရေးသားခြင်းမပြုဘဲ တွေ့ရှိမှုအရေအတွက်များကို call က မှတ်တမ်းတင်သည်။
- **`postCall`** သည် response ကို deep-clone လုပ်ပြီး `sanitizePIIResponse()` နှင့်
  Responses-API-shape masker (`maskResponsesOutput` — `output_text` နှင့်
  `output[].content[].text` ကို လွှမ်းခြုံသည်) ကို အသုံးပြုသည်။ ဖုံးကွယ်မှုတစ်စုံတစ်ရာ ဖြစ်ပေါ်ပါက
  ပြင်ဆင်ထားသော response သည် မူလ response ကို အစားထိုးသည်။

guardrail သည် မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်းမပြုဘဲ (`meta.detections`၊
`meta.redacted`) ဖြင့် မှတ်သားခြင်း သို့မဟုတ် ပြန်လည်ရေးသားခြင်းသာ ပြုလုပ်သည်။

### Prompt Injection (`promptInjection.ts`)

အသုံးပြုသူပေးထားသော content အတွင်းရှိ ရန်လိုသောဖွဲ့စည်းပုံများကို ရှာဖွေပြီး
ပြင်ဆင်သတ်မှတ်ထားသော policy ကို အတည်ပြုကျင့်သုံးသည်။ အပြုအမူကို environment variable များနှင့် constructor
option များက ထိန်းချုပ်သည်။

| သတ်မှတ်ချက်      | Env var                                                                                               | မူလသတ်မှတ်ချက် | အကျိုးသက်ရောက်မှု                                                                                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ဖွင့်ထားမှု      | `INPUT_SANITIZER_ENABLED`                                                                             | `true`         | `false` ဖြစ်ပါက guardrail သည် လုပ်ဆောင်ချက်ကို တိုက်ရိုက်ရပ်တန့်သည်။                                                                                                                                                         |
| Mode             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`         | Injection policy: `block`၊ `warn` သို့မဟုတ် `log`။ (`redact` ကို နောက်ကြောင်းပြန်လိုက်ဖက်မှုအတွက် လက်ခံသော်လည်း injection text ကို **မ**ဖယ်ရှားပါ။ request PII ပြန်လည်ရေးသားမှုကို `PII_REDACTION_ENABLED` က ထိန်းချုပ်သည်။) |
| ပိတ်ဆို့မှုအဆင့် | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`         | ပိတ်ဆို့ရန် လိုအပ်သော အနည်းဆုံး severity ဖြစ်သည်။ မူလသတ်မှတ်ချက်အရ Medium ကို စောင့်ကြည့်ရုံသာ ပြုလုပ်သည်။                                                                                                                   |

**Mode ဦးစားပေးအစီအစဉ်** (`getMode`): caller `options.mode` →
`INJECTION_GUARD_MODE` **DB feature-flag override** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`။ ထို့ကြောင့် dashboard override သည် env var များထက် ဦးစားပေးသဖြင့် Feature
Flags UI မှ လည်ပတ်နေသော guard ကို restart လုပ်စရာမလိုဘဲ တိုက်ရိုက်ထိန်းချုပ်နိုင်သည်။ DB ဖတ်ရှုမှုသည် fail-safe
ဖြစ်သည်။ error ဖြစ်ပါက guard သည် env အခြေပြုအပြုအမူသို့ ပြန်သွားပြီး
override မသတ်မှတ်ထားသည့်အခါ အပြုအမူသည် env-only resolution နှင့် တူညီသည်။

ရှာဖွေမှုရင်းမြစ်များ-

1. `@/shared/utils/inputSanitizer` မှ `sanitizeRequest()` (pipeline ၏ အခြားနေရာများတွင်
   အသုံးပြုသော shared detector အစု)။
2. ထည့်သွင်းထားသော `DEFAULT_GUARD_PATTERNS` (လက်ရှိတွင် `system_override_inline` နှင့်
   `markdown_system_block` ဖြစ်ပြီး နှစ်ခုလုံးသည် `high` severity ဖြစ်သည်)။
3. constructor option များမှတစ်ဆင့် ပေးပို့သော ရွေးချယ်နိုင်သည့် `customPatterns` (string၊ regex
   သို့မဟုတ် `{ name, pattern, severity }` record များ)။

`mode === "block"` **ဖြစ်ပြီး** ရှာဖွေတွေ့ရှိမှု အနည်းဆုံးတစ်ခုသည် ပြင်းထန်မှု
သတ်မှတ်ချက်ကို ပြည့်မီသည့်အခါ `preCall` သည် `{ block: true, message: "Request rejected:
suspicious content detected" }` ကို ပြန်ပေးသည်။ `warn`/`log` မုဒ်များတွင် guardrail က မှတ်တမ်းတင်သော်လည်း
ခေါ်ဆိုမှုကို ခွင့်ပြုသည်။ registry မှတစ်ဆင့် မသွားဘဲ prompt များကို အကဲဖြတ်ရန်လိုအပ်သည့်
ခေါ်ဆိုသူများအတွက် မျှဝေသုံး helper `evaluatePromptInjection()` ကိုလည်း export လုပ်ထားသည်။

**စစ်ဆေးမှု အကန့်အသတ် (v3.8.20):** detector သည် ပေါင်းစပ်ထားသော prompt စာသား၏ **ပထမ 16 KB** ကိုသာ
စစ်ဆေးသည် — `src/shared/utils/inputSanitizer.ts` ရှိ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes) ဖြစ်သည်။
`detectInjection()` နှင့် `evaluatePromptInjection()` နှစ်ခုစလုံးသည် pattern loop ကို မလုပ်ဆောင်မီ
`slice(0, MAX_INJECTION_SCAN_BYTES)` ကို အသုံးပြုသည်။ Injection ညွှန်ကြားချက်များသည် input ၏ အစပိုင်းအနီးတွင် ရှိတတ်သောကြောင့်
၎င်းသည် ရှာဖွေတွေ့ရှိနိုင်စွမ်းကို မလျော့စေဘဲ ရာနှင့်ချီသော KB payload များပေါ်ရှိ regex CPU/GC သုံးစွဲမှုကို
ကန့်သတ်ပေးသည် (cf.
#3932, #4041)။

### အထောက်အထားဖုံးကွယ်ကိရိယာ (`credentialMasker.ts`)

အဆင့် **နှစ်ခုစလုံး** တွင် လုပ်ဆောင်ပြီး မူလ chain ထဲ၌ နောက်ဆုံးဖြစ်သည် (ဦးစားပေးအဆင့် `95`)။ အပြင်သို့ပို့မည့် payload (message
အကြောင်းအရာ၊ tool-call arguments၊ tool results) **နှင့်** provider response တို့မှ
လူသိများသော API-key / secret-token pattern များကို ဖုံးကွယ်သည်။ ထို့ကြောင့် prompt ထဲသို့ ထည့်ထားသော credential (သို့မဟုတ် tool result က
ပြန်လည်ဖော်ပြသော credential) သည် upstream provider သို့ဖြစ်စေ client ထံသို့ ပြန်၍ဖြစ်စေ
ပေါက်ကြားမည်မဟုတ်ပါ။

- **ရွေးချယ်ဖွင့်သုံးမှသာ လုပ်ဆောင်သည်**၊ PII ဖုံးကွယ်ခြင်းနှင့် တူညီသော သတ်မှတ်ချက်ဖြစ်သည် (Hard Rule #20 နှင့် ဆက်စပ်):
  `settings.credentialRedactionEnabled === true` **သို့မဟုတ်**
  `CREDENTIAL_REDACTION_ENABLED=true` မဟုတ်လျှင် ပိတ်ထားသည်။ ပိတ်ထားသည့်အခါ guardrail သည် မည်သည့်လုပ်ဆောင်ချက်မျှ မလုပ်ပါ —
  မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်း သို့မဟုတ် ပြန်လည်ရေးသားခြင်း မပြုပါ။
- `redactCredentials()` သည် payload/response tree တစ်ခုလုံးကို ဖြတ်သန်းစစ်ဆေးပြီး (`walkValue()`,
  prototype pollution မှ လုံခြုံကာ `WeakSet` မှတစ်ဆင့် cycle များကို ဘေးကင်းစွာ ကိုင်တွယ်သည်) ကိုက်ညီမှုများကို
  `[REDACTED:<type>]` placeholder ဖြင့် အစားထိုးကာ အမှန်တကယ် ပြောင်းလဲသွားသော
  branch များကိုသာ clone လုပ်သည်။
- `CREDENTIAL_PATTERNS` သည် LLM provider key များ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate)၊ VCS/SaaS token များ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord)၊ ငွေပေးချေမှု key များ (Stripe, Square)၊ cloud
  key များ (AWS access key, Twilio, SendGrid, Mailgun)၊ private key များ / JWT များ၊
  credential ပါဝင်သော connection string များ (`mongodb://user:pass@...` စသည်) နှင့်
  ယေဘုယျ `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern တို့ကို လွှမ်းခြုံသည်။ Header ပုံစံ key များ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) ကို ယေဘုယျ text regex ဖြင့် မဟုတ်ဘဲ ဖွဲ့စည်းပုံအလိုက် ဖုံးကွယ်သည် (value ကိုသာ ဖုံးကွယ်ပြီး
  `Bearer `/`Basic ` ကဲ့သို့သော scheme prefix ကို ဆက်လက်ထိန်းသိမ်းထားသည်)။
- guardrail သည် မည်သည့်အခါမျှ ပိတ်ဆို့ခြင်းမပြုဘဲ ပြန်လည်ရေးသားခြင်း (`modifiedPayload` /
  `modifiedResponse`) နှင့် မှတ်ချက်အချက်အလက် ထည့်သွင်းခြင်း (`meta.credentialsRedacted`, `meta.count`) ကိုသာ ပြုလုပ်သည်။

Regression အကာအကွယ်: `tests/unit/credential-masker-guardrail.test.ts`။

## အခြေခံ Contract (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ဖြစ်ပါက chain ကို ချက်ချင်းရပ်တန့်စေသည်
  message?: string; // ပိတ်ဆို့သည့်အခါ ဖော်ပြသည်
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // request ကို ပြန်လည်ရေးသားရန် preCall မှ ပြန်ပေးသည်
  modifiedResponse?: TValue; // response ကို ပြန်လည်ရေးသားရန် postCall မှ ပြန်ပေးသည်
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Guardrail တစ်ခုသည် `void`၊ `{}` သို့မဟုတ် `{ block: false }` တစ်ခုခုကို
ပြန်ပေးခြင်းဖြင့် "ပြောင်းလဲမှုမရှိ" ကြောင်း အချက်ပြသည်။ `modifiedPayload`/`modifiedResponse`
ကို ပြန်ပေးခြင်းသည် နောက်ဆက်တွဲ guardrail များသို့ chain တစ်လျှောက် စီးဆင်းနေသော
တန်ဖိုးကို အစားထိုးသည်။ `signal?: AbortSignal` သည် ခေါ်ဆိုသူ၏ lifecycle ကို
guardrail များသို့ သယ်ဆောင်ပေးသည်။ Request ကို ရပ်ဆိုင်းခြင်းသည် ရည်ရွယ်ထားသော
fail-open ခြွင်းချက်ဖြစ်သည်—media bridge များသည် အလုပ်လုပ်ခြင်းကို ရပ်တန့်ပြီး cleanup
ပြုလုပ်ကာ raw media ကို ပံ့ပိုးနိုင်ခြင်းမရှိကြောင်း သိထားသော target တစ်ခုသို့
ပြန်လည်မထည့်သွင်းပါ။

## Registry (`registry.ts`)

Singleton `guardrailRegistry` တွင် အောက်ပါတို့ ပါဝင်သည်-

- `register(guardrail)` — guardrail တစ်ခုကို ထည့်သွင်းပြီး (သို့မဟုတ် normalize လုပ်ထားသော
  name အလိုက် အစားထိုးပြီး) `priority` ငယ်ရာမှ ကြီးရာသို့ ပြန်လည်စီသည်။
- `clear()` / `list()` — စီမံခန့်ခွဲရေး အကူ method များ။
- `runPreCallHooks(payload, context)` — အသက်ဝင်နေသော guardrail များကို တစ်ခုပြီးတစ်ခု
  လုပ်ဆောင်ကာ payload ကို `modifiedPayload` မှတစ်ဆင့် လက်ဆင့်ကမ်းပြီး ပထမဆုံး
  `block: true` တွင် ရပ်တန့်သည်။
- `runPostCallHooks(response, context)` — response ဘက်တွင် အလားတူ flow ကို လုပ်ဆောင်သည်။
- `resetGuardrailsForTests({ registerDefaults })` — test တစ်ခုချင်းစီကို သီးခြားသန့်ရှင်းစွာ
  လုပ်ဆောင်နိုင်ရန် state ကို ရှင်းလင်းပြီး ရွေးချယ်မှုအလိုက် မူလ guardrail များကို
  ပြန်လည် register လုပ်သည်။

Runner နှစ်ခုစလုံးသည် `{ blocked, payload|response, results, guardrail?, message? }`
ကို ပြန်ပေးသည်။ ဤနေရာတွင် `results` သည် guardrail တစ်ခုချင်းစီ၏ `blocked`,
`skipped`, `modified`, `error` နှင့် `meta` field များ ပါဝင်သော
`GuardrailExecutionResult` record များ၏ array ဖြစ်ပြီး tracing အတွက် အသုံးဝင်သည်။

### Request တစ်ခုချင်းစီအလိုက် Guardrail များကို ပိတ်ခြင်း

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` သည် လက်ရှိ request အတွက်
ကျော်သွားသင့်သော guardrail name များကို ထပ်နေမှုမရှိအောင် စုစည်းပေးသည်။
ရင်းမြစ်များအားလုံးသည် မဖြစ်မနေ မဟုတ်ဘဲ ပေါင်းစည်းအသုံးပြုသည်-

- `apiKeyInfo.disabledGuardrails`
- Request body ၏ ထိပ်ဆုံးအဆင့်ရှိ `disabledGuardrails`
- Request body ၏ `metadata.disabledGuardrails`
- Header `x-omniroute-disabled-guardrails` (သို့မဟုတ် အဟောင်းဖြစ်သော
  `x-disabled-guardrails`)

တန်ဖိုးများသည် string array များ သို့မဟုတ် ကော်မာဖြင့် ခွဲထားသော string တစ်ခု
ဖြစ်နိုင်သည်။ Name များကို စာလုံးအသေး kebab-case အဖြစ် normalize လုပ်သည်
(`pii_masker` → `pii-masker`)။ ရလဒ်ကို `context.disabledGuardrails` မှတစ်ဆင့်
registry သို့ ပေးပို့ပြီး ၎င်း registry က ကိုက်ညီသော guardrail များကို ကျော်သွားသည်
(`results` ထဲတွင် `skipped: true`)။

## လုပ်ဆောင်မှု အစီအစဉ်

`src/sse/handlers/chat.ts` နှင့်
`open-sse/handlers/chatCore.ts` တို့မှတစ်ဆင့် ဖြတ်သန်းသည့် request တစ်ခုစီအတွက်-

1. `resolveDisabledGuardrails(...)` သည် API key၊ body နှင့် headers တို့မှ skip list ကို တည်ဆောက်သည်။
2. `guardrailRegistry.runPreCallHooks(body, ctx)` သည် guardrails များကို priority ငယ်စဉ်ကြီးလိုက်ဖြင့် လုပ်ဆောင်သည်-
   - ပိတ်ထားသော guardrails များကို `skipped` အဖြစ် မှတ်တမ်းတင်သည်။
   - Guardrail တစ်ခုစီ၏ `preCall` သည် `modifiedPayload` မှတစ်ဆင့် payload ကို ပြန်လည်ရေးသားနိုင်သည်။
   - ပထမဆုံး `block: true` သည် chain ကို ချက်ချင်းရပ်တန့်စေပြီး handler က guardrail ငြင်းပယ်မှု response ကို ပြန်ပေးသည်။
3. (ပြန်လည်ရေးသားထားနိုင်သည့်) payload သည် combo routing နှင့် upstream dispatch ထဲသို့ စီးဆင်းသွားသည်။
4. Response ကို စုစည်းပြီးနောက် `guardrailRegistry.runPostCallHooks(...)` သည် response ပေါ်တွင် တူညီသော chain ကို လုပ်ဆောင်သည်။ ဤနေရာရှိ `block: true` သည် upstream response ကို စွန့်ပစ်သည်။

Exception ပစ်သော guardrails များကို `error: <message>` ဖြင့် မှတ်တမ်းတင်ပြီး
`logger.warn` မှတစ်ဆင့် log ရေးသော်လည်း chain သည် ဆက်လက်လုပ်ဆောင်သည် — ဒီဇိုင်းအရ fail-open ဖြစ်သည်။

## စိတ်ကြိုက် Guardrail များ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

အဆင့်များ-

1. `BaseGuardrail` ကို တိုးချဲ့ထားသော `src/lib/guardrails/myGuardrail.ts` ကို ဖန်တီးပါ။
2. `preCall` နှင့်/သို့မဟုတ် `postCall` ကို အကောင်အထည်ဖော်ပါ။
3. Import ပြုလုပ်ချိန်တွင် register လုပ်ပါ (`registerDefaultGuardrails` မှ push လုပ်ခြင်း) သို့မဟုတ်
   runtime တွင် `guardrailRegistry.register(...)` ကို ခေါ်ပါ — registry သည် normalized name တူညီသည့်
   ယခင် guardrail တစ်ခုခုကို အစားထိုးပါမည်။
4. `tests/unit/` အောက်တွင် test များ ထည့်ပါ (ရှိပြီးသား နမူနာများ-
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)။

## Injection-guard route လွှမ်းခြုံမှုနှင့် red-team (Phase 8 · Block D)

Injection-guard (`createInjectionGuard` / `withInjectionGuard`) သည် user prompt များကို
လက်ခံသည့် route အားလုံးကို လွှမ်းခြုံသည်။ ၎င်းသည် `INJECTION_GUARD_MODE` ကို လိုက်နာသည် (မူလ `warn` = log သာရေးခြင်း၊
`block` = HTTP 400 `SECURITY_001` ကို ပြန်ပေးခြင်း)။

| အမျိုးအစား        | Route များ                                                                                                                                           | မူလ mode |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |

| Generative        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn     |
| Data              | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn     |

စာသားထုတ်ယူမှု (`extractMessageContents`) သည် `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ကို လွှမ်းခြုံသည်။
