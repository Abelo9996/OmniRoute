> **အသုံးပြုသူများအတွက်**: ရိုးရှင်းသောလမ်းညွှန်ကို ရှာဖွေနေပါသလား။ အခမဲ့ AI ရယူရန် အဆင့်ဆင့်ညွှန်ကြားချက်များအတွက် [အခမဲ့အဆင့်များ လမ်းညွှန်](../getting-started/FREE-TIERS-GUIDE.md) ကို ကြည့်ပါ။

> **နောက်ဆုံးသုတေသနပြုခဲ့သည့်ရက်:** 2026-06-17 — အခမဲ့အဆင့် ခွဲတမ်းတိုင်းနှင့် ToS ကို ပြန်လည်အသစ်ပြုထားသည့် ဝန်ဆောင်မှုပေးသူတစ်ခုချင်းစီအလိုက် ဝဘ်သုတေသန (တရားဝင်စာရွက်စာတမ်းများ + နောက်ဆုံး 7 ရက်အတွင်း သတင်းများ၊ ဆန့်ကျင်ဘက်ရှုထောင့်မှ အတည်ပြုခြင်းပါဝင်သော agent 50 ခုဖြင့် စိစစ်မှု)။ **တစ်စိတ်တစ်ပိုင်း ပြန်လည်စစ်ဆေးမှု 2026-09-02** (`gemini`, `ollama-cloud`, `groq`, `nara`, `mistral` — အောက်ရှိ ရက်စွဲတပ်ထားသော မှတ်ချက်ကို ကြည့်ပါ)။
> **ယုံကြည်ရသော မူရင်းရင်းမြစ် (ကတ်တလောက်):** `open-sse/config/freeModelCatalog.ts` (MODEL တစ်ခုချင်းစီအလိုက် ဘတ်ဂျက်များ၊ ထပ်နေသော pool များကို ဖယ်ရှားထားသည်)။ အောက်ပါ token ဘတ်ဂျက်ကိန်းဂဏန်းများသည် လက်ရှိဝဘ်သုတေသနမှ ရရှိလာပြီး **အနီးစပ်ဆုံး ခန့်မှန်းချက်** ဖြစ်သည် — [နည်းစနစ်နှင့် သတိပြုရန်အချက်များ](#methodology--caveats) ကို ကြည့်ပါ။

## TL;DR — OmniRoute က အခမဲ့ inference မည်မျှကို အမှန်တကယ် စုစည်းပေးသနည်း။

ဤကိန်းဂဏန်းများသည် ကတ်တလောက်တစ်လျှောက်ရှိ သီးခြား ပြင်ပအဖွဲ့အစည်းအကောင့်များနှင့် အရည်အချင်းပြည့်မီမှုဆိုင်ရာ သတ်မှတ်ချက်များကို ဖော်ပြသည်။ OmniRoute က ဤဘတ်ဂျက်ကို ပေးအပ်ခြင်းမဟုတ်ပါ။ လိုအပ်သော အကောင့်များ သို့မဟုတ် အထောက်အထားများကို သင်ကိုယ်တိုင် ရယူရမည်၊ အရည်အချင်းပြည့်မီသော ဝန်ဆောင်မှုပေးသူများကို ချိတ်ဆက်ရမည်၊ ထို့ပြင် ၎င်းတို့၏ ကန့်သတ်ချက်များကို လိုက်နာရမည်။ အရည်အချင်းပြည့်မီသော route မရှိသည့် အသစ်ထည့်သွင်းထားသော စနစ်တွင် သုညဖြစ်နိုင်ခြင်းအပါအဝင် အမှန်တကယ် အသုံးပြုနိုင်သည့် ပမာဏသည် ပိုနည်းနိုင်သည်။ `tos: avoid` ဟု အမှတ်အသားပြုထားသော ဝန်ဆောင်မှုပေးသူများကို ပုံသေအားဖြင့် အလိုအလျောက် routing မှ ဖယ်ထုတ်ထားသည်။

## နည်းလမ်းနှင့် သတိပြုရန်အချက်များ

- ကိန်းဂဏန်းများသည် web research ဖြင့် စုဆောင်းထားသော၊ provider တစ်ခုစီက **2026-06-17** ရက်နေ့အထိ မှတ်တမ်းတင်ထားသည့် free-tier limit များမှ ရရှိသော **ဖြစ်နိုင်သည့် အများဆုံးခန့်မှန်းချက်များ** ဖြစ်သည်။ Free tier များသည် အမြဲပြောင်းလဲနေသည် — ကိန်းဂဏန်းတစ်ခုကို အားထားအသုံးမပြုမီ ပြန်လည်အတည်ပြုပါ။
- **Entry တစ်ခုက အမှန်တကယ် အာမခံပေးသည့်အရာ။** Entry တစ်ကြောင်းချင်းစီတွင် confidence rating မပါဝင်သလို API ကလည်း ယင်းကို မပေးပါ — အထက်ပါကိန်းဂဏန်းတိုင်းကို မဖော်ပြထားသည့် တူညီသော အရည်အသွေးအဆင့်ရှိသော ခန့်မှန်းချက်အဖြစ်သာ သဘောထားပါ။ သို့သော် အချက်နှစ်ချက်သည် inference ပြုလုပ်ထားခြင်းမဟုတ်ဘဲ လက်ဖြင့် စိစစ်ထည့်သွင်းထားသောကြောင့် ကွဲပြားသည်- entry 44 ခုတွင် သီးခြားမှတ်တမ်းတင်ထားသည့် hard stop ပါရှိပြီး (ယင်းတို့အနက် 39 ခုသည် နေ့စဉ် allowance တစ်ခုတည်းကို မျှဝေသည့် xKiro row များဖြစ်သည်)၊ entry 13 ခုတွင် prompt-training disclosure ပါရှိသည်။ အခမဲ့ allowance ကျော်လွန်ပါက အလိုအလျောက် စတင်ငွေကောက်ခံခြင်းမပြုဘဲ request ကို ငြင်းပယ်မည်ဟု provider ၏ ကိုယ်ပိုင်စည်းမျဉ်းများတွင် ဖော်ပြထားသည့်အခါမှသာ `hardStopGuaranteed` ကို သတ်မှတ်ပြီး၊ source ကို entry ဘေးရှိ comment တွင် ထည့်ထားသည်။ ၎င်းကို မည်သည့်အခါမျှ default အနေဖြင့် `true` မသတ်မှတ်ဘဲ၊ မည်သူမျှ အတည်မပြုရသေးသော entry သည် unset အဖြစ်သာ ရှိနေသည်။ ထို့ကြောင့် hard-stop flag မရှိခြင်းသည် "အတည်မပြုရသေး" ဟု ဆိုလိုပြီး "ငွေကောက်ခံမည်ဟု သိထားသည်" ဟု မဆိုလိုပါ။ **STRICT mode** (ရွေးချယ်ဖွင့်နိုင်သည့် `freeAccessPolicy=strict` routing guard) သည် flag ပါရှိသော entry များကိုသာ ယုံကြည်သည်။ အခြား free tier အားလုံးကို `no-hard-stop` အဖြစ် ဖယ်ထုတ်သည် (`open-sse/services/autoCombo/strictZeroCostFilter.ts` ကို ကြည့်ပါ)။ Guard က pool တစ်ခုကို filter လုပ်သည့်အခါ operator မြင်နိုင်သော log တွင် ဖယ်ထုတ်ထားသည့် အရေအတွက်နှင့် ယင်းတို့အနက် `no-hard-stop` ဖြစ်သည့် အချိုးနှစ်ခုစလုံးကို အစီရင်ခံသည်။
- `estMonthlyFreeTokens` = လစဉ် ထပ်တလဲလဲရရှိသည့် token များသာ။ **တစ်ကြိမ်တည်းရရှိသော signup credit များသည် ထပ်မံမရရှိပါ**၊ ထို့ကြောင့် 0 အဖြစ် ရေတွက်သည်။ ရပ်ဆိုင်းထားသော tier များကိုလည်း 0 အဖြစ် ရေတွက်သည်။
- နေ့စဉ် token cap → `monthly = daily × 30`။ RPD သာ မှတ်တမ်းတင်ထားပါက → `RPD × ~800 output tokens × 30`။ RPM/TPM သာရှိပြီး နေ့စဉ် cap မရှိပါက → **uncapped** (အောက်တွင် ကြည့်ပါ)။
- **အမြဲတမ်းအခမဲ့ဖြစ်သော်လည်း ထုတ်ပြန်ထားသော token cap မရှိခြင်း** (`siliconflow`, `glm-cn`, `tencent`, `baidu`, `kilo-gateway`, `opencode-zen`, `gemini`, `ollama-cloud`)- ၎င်းတို့သည် အမှန်တကယ် ထပ်တလဲလဲရရှိသော အခမဲ့အသုံးပြုခွင့်များဖြစ်ပြီး rate/concurrency ကန့်သတ်ချက်များရှိသည်။ ၎င်းတို့ကို `recurring-uncapped` အဖြစ် သတ်မှတ်ပြီး **မည်သည့်အခါမျှ ပေါင်းမတွက်ပါ** — `RPM × 24/7 × 30d` ဖြင့် မြှောက်ခြင်းသည် လက်တွေ့မကျသော အမြင့်ဆုံးပမာဏကို ဖြစ်ပေါ်စေမည်ဖြစ်ပြီး၊ ထိုသို့ ပမာဏဖောင်းပွစေခြင်းကို ကျွန်ုပ်တို့ လက်မခံပါ။ ၎င်းတို့ရှိနေကြောင်း သိနိုင်စေရန် စာရင်းတွင် ထည့်သွင်းထားသည်။
- **Deposit-unlock boost:** တစ်ကြိမ်တည်းသာ ပြုလုပ်ရသော ပမာဏနည်းသည့် top-up တစ်ခုက အခမဲ့ quota ကို အမြဲတမ်း တိုးမြှင့်ပေးခြင်း (OpenRouter: $10 → 1000 req/day ≈ +24M/mo)။ သီးခြားကိန်းဂဏန်းအဖြစ် အစီရင်ခံပြီး ပုံမှန်တည်ငြိမ်သည့် headline ထဲတွင် မထည့်ထားပါ။
- **အရည်အချင်းပြည့်မီမှုဖြင့် ကန့်သတ်ထားသည့် quota များ** (`eligibilityGate: "regional-identity"`)- ဒေသနှင့်ဆက်စပ်သည့် ကိုယ်ရေးအထောက်အထားစစ်ဆေးမှု ပြီးမြောက်ပြီးမှသာ ဖွင့်ပေးသော အမှန်တကယ် ထပ်တလဲလဲရရှိသည့် quota ဖြစ်သည် (လက်ရှိတွင် တရုတ်ပြည်မကြီး၏ အမည်ရင်းအတည်ပြုခြင်း)။ တူညီသော pool-dedupe စည်းမျဉ်းဖြင့် သီးခြားကိန်းဂဏန်း (`gatedRecurringTokens`) ထဲသို့ ရေတွက်ပြီး၊ ပုံမှန်တည်ငြိမ်သည့် headline ထဲတွင် မည်သည့်အခါမျှ မထည့်ပါ။ စနစ် (`freeType`) သည် မပြောင်းလဲသောကြောင့် routing လည်း မပြောင်းလဲပါ။
- **အထောက်အထားအမျိုးအစားများ။** စည်းမျဉ်းမှာ- catalog ထဲရှိ ကိန်းဂဏန်းတစ်ခုသည် ၎င်း၏ source ကို entry ဘေးရှိ `// evidence:` comment တွင် ကိုးကားရမည် — `public-page` (မည်သူမဆို ဖတ်ရှုနိုင်သည့် provider page)၊ `api-public` (provider ၏ authentication မလိုသော endpoint၊ ဥပမာ router.bynara.id ရှိ NaraRouter ၏ public plans endpoint) သို့မဟုတ် `console-verified <date> por <who>` (ကိန်းဂဏန်းကို account console အတွင်း၌သာ မြင်နိုင်သည်။ Comment တွင် မည်သူက မည်သည့်အချိန်၌ မြင်ခဲ့သည်ကို မှတ်တမ်းတင်ပြီး cap ရှိကြောင်း ဖော်ပြသည့် public page ကိုလည်း ထည့်သွင်းထားသည်)။ လက်ရှိအခြေအနေမှာ- 2026-09-02 တွင် ပြန်လည်စစ်ဆေးခဲ့သော block ငါးခု (`gemini`, `groq`, `mistral`, `ollama-cloud`, `nara`) တွင် ယင်းအထောက်အထား ပါရှိသည်။ 2026-09-02 ပြန်လည်စစ်ဆေးမှုမတိုင်မီကတည်းက ရှိခဲ့သော entry များသည် ပြင်ဆင်ကိုင်တွယ်သည့်အချိန်အထိ ယခင်သုတေသနကို ဆက်လက်အမွေဆက်ခံထားသည်။ Evidence comment မပါဘဲ **အသစ်ထည့်သွင်းထားသော သို့မဟုတ် ပြောင်းလဲထားသော** ကိန်းဂဏန်းတိုင်းသည် bug တစ်ခုဖြစ်သည်။ လက်ရှိတွင် `mistral` တစ်ခုတည်းသာ console-verified ဖြစ်သည်။

## ကျွန်ုပ်တို့၏ ကိန်းဂဏန်းသည် အခြား စုစည်းဖော်ပြသည့် ဝန်ဆောင်မှုများ၏ ကိန်းဂဏန်းထက် အဘယ်ကြောင့် နည်းရသနည်း

ဤနယ်ပယ်ရှိ "တစ်လလျှင် အခမဲ့ token များ" ဟူသော ကိန်းဂဏန်းအများစုသည် model တစ်ခုချင်းစီအလိုက် ဖော်ပြထားသည့် ပမာဏများကို ပေါင်းထားခြင်းဖြစ်သည်။ ကျွန်ုပ်တို့၏ ကိန်းဂဏန်းမှာ ရည်ရွယ်ချက်ရှိရှိ ထိုသို့မဟုတ်ပါ-

- **မျှဝေသုံးစွဲသည့် pool တစ်ခုစီကို တစ်ကြိမ်သာ ရေတွက်ထားသည်။** Mistral ၏ အခမဲ့အစီအစဉ်သည် organization တစ်ခုလျှင် တစ်လ 1B ရရှိသည့် allowance တစ်ခုတည်းဖြစ်သည်။ ၎င်းကို model ငါးခုအောက်တွင် စာရင်းပြုစုထားခြင်းကြောင့် 5B ဖြစ်မသွားပါ။ Model တစ်ခုချင်းစီအလိုက် ပေါင်းပါက ကျွန်ုပ်တို့၏ ကိုယ်ပိုင် catalog သည် **~7.4B** ဟု ဖော်ပြမည်ဖြစ်သည် (2026-09-03 တွင် ပြန်လည်တွက်ချက်ထားသည်။ ဤကိန်းဂဏန်းကို CI ဖြင့် စစ်ဆေးထိန်းချုပ်ထားခြင်းမရှိသဖြင့် catalog ပြောင်းလဲတိုင်း ပြန်လည်တိုင်းတာပါ) — headline တွင် **~1.47B** ဟု ဖော်ပြရခြင်းမှာ provider တစ်ခုစီမှ account တစ်ခုက အမှန်တကယ် သုံးစွဲနိုင်သည့် ပမာဏဖြစ်သောကြောင့်ဖြစ်သည်။
- **နေ့စဉ်ကန့်သတ်ချက်များကို ပြောင်းလဲတွက်ချက်သော်လည်း rate များကို မပြောင်းလဲပါ။** မှတ်တမ်းတင်ဖော်ပြထားသော tokens/day ကန့်သတ်ချက်ကို `× 30` အဖြစ် ပြောင်းလဲတွက်ချက်သည်။ မှတ်တမ်းတင်ဖော်ပြထားသော requests/day ကန့်သတ်ချက်ကို `RPD × ~800 tokens × 30` အဖြစ် ပြောင်းလဲတွက်ချက်သည်။ Requests-per-minute ကိုသာ ထုတ်ပြန်ထားသည့် provider တွင် လစဉ်ကိန်းဂဏန်း **မရှိ** သဖြင့် _ကန့်သတ်ချက်မရှိ_ ဟု စာရင်းပြုစုကာ မည်သည့်အခါမျှ ပေါင်းထည့်မတွက်ပါ။ Rate limit ကို 24/7 ဖြင့် မြှောက်ခြင်းသည် ကျွန်ုပ်တို့ လက်မခံသည့် ပမာဏဖောင်းပွမှုဖြစ်သည်။
- **ဒေသအလိုက် identity စစ်ဆေးမှုနောက်ကွယ်ရှိ quota များကို သီးခြားဖော်ပြထားသည်** (`+~6M behind regional identity verification`)၊ အကြောင်းမှာ စာဖတ်သူအများစုက ၎င်းတို့ကို အသုံးမပြုနိုင်သောကြောင့်ဖြစ်သည်။
- **Signup credit များသည် ပထမလအတွက်သာဖြစ်ပြီး** သီးခြား ဒုတိယကိန်းဂဏန်းအဖြစ် ဖော်ပြထားကာ ပုံမှန်ရရှိသည့် ကိန်းဂဏန်းနှင့် မည်သည့်အခါမျှ ရောနှောမထားပါ။
- **ဤကိန်းဂဏန်းကို CI ဖြင့် အတည်ပြုထိန်းသိမ်းထားသည်။** `npm run check:docs-counts` သည် catalog မှ စုစုပေါင်းပမာဏများကို ပြန်လည်တွက်ချက်ပြီး ဤဖိုင်၊ README သို့မဟုတ် budget card ရှိ ကိန်းဂဏန်းများနှင့် ကွာဟသွားပါက build ကို မအောင်မြင်စေပါ။

## ToS သတိပြုရန် ဇယား

> **ToS flag သည် အကြံပြုသတိပေးချက်သာဖြစ်ပြီး routing gate မဟုတ်ပါ။** `tos` ဟု အမှတ်အသားပြုထားသော provider များကို routing နှင့် combo/fallback တို့တွင် မူလသတ်မှတ်ချက်အရ ဆက်လက်ထည့်သွင်းထားသည်။ Flag ကို `/dashboard/free-tiers` နှင့် `/api/free-tier/summary` တို့တွင်သာ ဖော်ပြသည်။ `excludeTosAvoid` query parameter သည် summary view ကိုသာ သက်ရောက်ပြီး global routing ကို မသက်ရောက်ပါ။ သတ်မှတ်ချက်သည် `open-sse/config/freeTierCatalog.ts` တွင် ရှိသည် (အသိပေးရန်သာဖြစ်ပြီး routing engine များက ဖတ်ရှုခြင်းမရှိပါ)။

> Self-hosted၊ single-user personal proxy တစ်ခုအတွက် provider တစ်ခုစီ၏ စည်းမျဉ်းများကို အကျဉ်းချုပ်ဖတ်ရှုထားခြင်းဖြစ်သည်။ `caution` = စစ်ဆေးသင့်သည့် personal-use သို့မဟုတ် proxy ဆိုင်ရာ အပိုဒ်၊ `ambiguous` = မရှင်းလင်း၊ `ok` = ရှင်းလင်းစွာ ခွင့်ပြုထားသည်။ အသိပေးရန်သာဖြစ်ပြီး ဥပဒေအကြံဉာဏ်မဟုတ်ပါ — သင်ကိုယ်တိုင် ဆုံးဖြတ်ပါ။

### ⚠️ သတိပြုရန် — စစ်ဆေးသင့်သည့် personal-use / proxy ဆိုင်ရာ အပိုဒ်များ (16)

## OpenCode Free: client-contract ကန့်သတ်ချက် (#14313)

သော့မလိုအပ်သော `opencode` provider (အများသုံး `https://opencode.ai/zen/v1`) သည် OpenCode client contract နှင့် မကိုက်ညီသည့် မည်သည့် request ကိုမဆို **403 `FreeTierError`** နှင့် _"OpenCode ၏ အခမဲ့အဆင့်ကို OpenCode အတွင်းမှသာ အသုံးပြုနိုင်သည်"_ ဟူသော စာသားဖြင့် ငြင်းပယ်သည်။ ၎င်းသည် request တစ်ခုချင်းအလိုက် ငြင်းပယ်ခြင်းဖြစ်ပြီး (တူညီသော request ပုံစံအတွက် account အားလုံးတွင် တူညီသော ဆုံးဖြတ်ချက် ရရှိသည်) model ပိတ်ပင်မှု သို့မဟုတ် connection cooldown မဟုတ်ပါ — OmniRoute က ၎င်းကို `project_route_error` အဖြစ် အမျိုးအစားခွဲခြားပြီး model lockout / cooldown ကို ကျော်သွားကာ (ဖန်တီးထားသော `noauth` လမ်းကြောင်းတွင်) auto-combo ပြန်လည်ရွေးချယ်မှုကို TTL အတိုတစ်ခုအတွက် ခေတ္တရပ်ထားသည်။ ဗလာမဟုတ်သော tool list၊ `stream: true` နှင့် OpenCode session/UA headers (`opencodeFreeTierContract.ts`) ပါဝင်သည့် request များကို ပေးပို့ပါ၊ သို့မဟုတ်ပါက 403 ကို မျှော်လင့်ထားပါ။
