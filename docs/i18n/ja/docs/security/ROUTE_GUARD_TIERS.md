## 概要

OmniRoute のすべての管理 API ルートは、3 つの保護階層のいずれかに分類されます。分類は静的で、`src/server/authz/routeGuard.ts` で定義されており、他の認証分岐が実行される前に評価されます。

## ティア

### ティア 1 — LOCAL_ONLY

**適用方法:** `isLocalOnlyPath(path)` → ループバックホストのチェック  
**バイパス:** デフォルトではなし。リクエストに `manage` スコープを持つ有効な API キーが含まれている場合に限り、`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 内のパスに対する限定的な例外があります（[manage スコープの例外](#manage-scope-carve-out)を参照）。

これらのルートは、子プロセスを起動するか、ランタイムコードを実行します。これらを非ループバックトラフィックに公開すると、有効な JWT を取得した攻撃者（例: Cloudflared/Ngrok トンネル経由）がプロセスの起動を引き起こせるようになります。これは既知の CVE クラスです（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj とは何か（攻撃クラス）:** 管理/エージェントサーバーが、サブプロセス（`npm install`、`node`、ブラウザ、プロキシ、`git`、`tar`、…）を起動するエンドポイントを公開します。オペレーターが OmniRoute を nginx/Cloudflare/Tailscale トンネルの背後に配置し、JWT が漏洩した場合や、認証が誤って構成されていた場合など、そのエンドポイントがホスト外部から到達可能であれば、攻撃者は「API を呼び出す」ことを「ホスト上でコマンドを実行する」こと（リモートコード実行）に変えられます。OmniRoute は、プロセスを起動可能なすべてのルートに対して、**認証チェックより前に無条件でループバックホストのチェックを適用する**ことで、これを防止します。トンネル経由でトークンが漏洩しても、プロセス起動には到達できません。

**LOCAL_ONLY の完全な一覧。** 正式な情報源は、`src/server/authz/routeGuard.ts` 内の `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` です。以下の表は現在の状態を反映しています。`check-route-guard-membership` ゲートは、プロセス起動が可能なプレフィックス配下にあるすべての `route.ts` を列挙し、いずれかがローカル専用として分類されていない場合は CI を失敗させます。

**違反時のレスポンス：** `403 LOCAL_ONLY`

#### 管理スコープの例外

LOCAL_ONLY パスの一部には、リクエストがメタデータに `manage` スコープ（または `admin`）を含む `Authorization: Bearer <api-key>` を伴う場合に限り、非ループバックからもアクセスできます。この例外は `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` を介してパスごとに明示的に制御されるため、新しい LOCAL_ONLY パスのデフォルトは引き続き厳格なループバック限定となります。未認証のリクエスト、および管理スコープを持たないキーによるリクエストは、引き続き `403 LOCAL_ONLY` で拒否されます。

現時点でバイパス可能なプレフィックスは `/api/mcp/` のみです。`/api/cli-tools/runtime/` と `/api/services/` は、任意のサブプロセス（`npm install`、`node`）を起動できるため、意図的に除外されています。これはまさに、LOCAL_ONLY 層が防止するために存在する CVE の種類です。

**#7895 — `mcp:connect` の限定スコープ：** `/api/mcp/` の例外では、限定的な `mcp:connect` スコープ（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`）を持つ Bearer キーも受け入れます。これは `src/server/authz/policies/management.ts` の `hasMcpConnectOrManageScope()` を介してチェックされます。このスコープは `/api/mcp/` **のみに**限定されます。`mcp:connect` は、その他の管理ルート（今後追加される可能性がある他のすべての LOCAL_ONLY バイパスプレフィックスを含む）に対して一切の権限を付与せず、意図的に `MANAGEMENT_API_KEY_SCOPES` から除外されています。`manage`／`admin` を持つキーは従来どおりこの例外を通過します。`mcp:connect` は、広範な管理アクセスを必要としないリモートの MCP 専用呼び出し元向けの、より低権限な代替手段です。

| リクエスト                                                | パス                       | 結果                 |
| --------------------------------------------------------- | -------------------------- | -------------------- |
| 非ループバック、Bearer なし                               | `/api/mcp/*`               | 403 LOCAL_ONLY       |
| 非ループバック、`manage` スコープを持つ Bearer            | `/api/mcp/*`               | 許可                 |
| 非ループバック、`mcp:connect` スコープを持つ Bearer       | `/api/mcp/*`               | 許可                 |
| 非ループバック、`manage`／`mcp:connect` を持たない Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY       |
| 非ループバック、`mcp:connect` スコープを持つ Bearer       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY       |
| 非ループバック、`manage` スコープを持つ Bearer            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY       |
| ループバック、Bearer の有無を問わず                       | 任意の LOCAL_ONLY          | 許可（ゲートを通過） |

#### オペレーター向けガイダンスと監査

OmniRoute をリバースプロキシまたはトンネル（nginx、Caddy、Cloudflare Tunnel、Tailscale、Ngrok）の背後で実行する場合でも、ループバックチェックによって、上記のプロセス起動可能なルートは保護されます。クライアントアドレスが非ループバックであるリクエストは、**認証が実行される前に** `403 LOCAL_ONLY` で拒否されるため、JWT が漏洩してもプロセス起動には到達できません。オペレーターには、引き続き次の 2 つの責任があります：

- **クライアント IP をループバックに偽装して 403 を「修正」しないでください。**
  `X-Forwarded-For: 127.0.0.1` を設定したり、送信元アドレスをループバックに
  書き換えるプロキシを使用したりすると、この階層が防いでいる RCE の脆弱性クラスを
  そのまま再び開放することになります。プロキシ経由で公開するのは
  ダッシュボード/API に限定し、プロセスを起動できるルートは決して公開しないでください。
- **`manage` スコープによるバイパスは最小限に保ってください。** バイパス可能なのは
  `/api/mcp/` のみであり、かつ `manage` スコープの API キーを使用する場合に限られます。
  `SPAWN_CAPABLE_PREFIXES` をバイパスリストに追加することは一切できません。zod スキーマが
  それらを拒否し、実行時にも `isLocalOnlyBypassableByManageScope` が拒否します
  （多層防御）。これが、ダッシュボードに「バイパス可能にはできない」と表示される理由です。
  同じ拒否リストには、プロセスを起動しないものの、決してリモートからアクセス可能に
  してはならない LOCAL_ONLY ルートもいくつか含まれます。
  `/api/oauth/kiro/auto-import`（ホストローカルの Kiro 認証情報ファイルを読み取る）、
  `/api/discovery/`、および `/api/issue-agent/` です。実行時のスナップショットローダーも、
  保存済みの設定行からそのようなエントリを削除し、従来の JSON インポート
  （`/api/settings/import-json`）ではバイパスキーが一切書き込まれません。
  すべての `LOCAL_ONLY_API_PREFIXES` エントリは、拒否リストに含まれるか、
  バイパス対象として適格かどうかをレビュー済みでなければなりません
  （`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。`/api/providers/` 配下にある、
  動的セグメントおよび静的パスのプロセス起動可能ルート（例: `/login`、
  `/refresh-cursor`）は、フラットな `SPAWN_CAPABLE_PREFIXES` 配列ではなく、
  `src/shared/constants/spawnCapablePrefixes.ts` にある正規表現ベースの
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` によって保護されます。
  フラット配列でこれらを捕捉するには `/api/providers/` プレフィックス全体を
  対象にする必要があり、リモートダッシュボードがプロバイダーの CRUD に正当に使用する
  ルートツリーまで過度に制限してしまいます。

**アクセスの監査** — オフホストからこれらのルートに到達していないことを確認するには:

- `/dashboard/settings/security` の **Authorization Inventory** を開きます。ここには、
  現在有効な LOCAL_ONLY プレフィックスのリスト、バイパス可能なプレフィックス、
  およびコンパイル時に決定されるプロセス起動可能な
  （「バイパス可能にはできない」）セットが表示されます。
- リバースプロキシ/アクセスログで、上記のプレフィックスと非ループバックの
  クライアントアドレスの組み合わせを grep してください。そのようなアクセスが
  `403 LOCAL_ONLY` ではなく `200` を返していた場合、プロキシが実際のクライアント IP を
  隠しています。プロキシを修正してください。
- OmniRoute のログでこれらのパスのいずれかに対して `403 LOCAL_ONLY` が記録されるのは、
  ガードが意図どおり動作していることを示しており、抑制すべきエラーではありません。

### 階層 2 — ALWAYS_PROTECTED

**適用方法:** `isAlwaysProtectedPath(path)` → `requireLogin=false` によるバイパスをスキップ
**バイパス:** `requireLogin=false` の場合でもなし。常に JWT が必要

これらのルートは、破壊的または不可逆的な操作を実行します。「パスワードなし」の
インストール環境でこれらを許可すると、同じ LAN 上の誰もがデータベースを消去したり、
サーバープロセスを停止したりできることになります。

| パス                                      | 理由                                                          |
| ----------------------------------------- | ------------------------------------------------------------- |
| `/api/shutdown`                           | サーバープロセスを終了する                                    |
| `/api/settings/database`                  | データベースのエクスポート、インポート、消去                  |
| `/api/db-backups`                         | データベースの完全バックアップアーカイブへのアクセス          |
| `/api/settings/export-json`               | 設定 blob 全体（シークレットを含む）をエクスポートする        |
| `/api/settings/import-json`               | 設定 blob 全体を置き換える                                    |
| `/api/providers/health-autopilot/actions` | 自動修復アクションを実行する                                  |
| `/api/settings/obsidian`                  | 任意の vault ルート用に再利用可能な WebDAV 認証情報を発行する |

**違反時のレスポンス:** `401 Authentication required`

`/api/settings/obsidian` は、その子パス `/webdav` も対象に含みます。`POST` は、
Next.js より前段にあるカスタム Node レイヤーによって、このパイプライン外で提供される
WebDAV ファイルサービスのルートを呼び出し元が選択した場所に設定し、新たに発行した
Basic 認証情報を応答として返します。`DELETE` はそれらをローテーションし、親ルートの
`POST` は Obsidian REST API トークンを保存します。GHSA-62vw でマスクされたのは
`GET` によるパスワードの露出だけであり、認証情報の発行は依然としてフェイルオープンの
階層にありました（GHSA-7pq4-8pvv-rx7r）。さらに、`enableObsidianVaultSync()` は、
データディレクトリそのもの、データディレクトリ内にある vault、または
データディレクトリを内包する vault を拒否します。

#### 認証情報のエクスポートはオペレーター専用

上記の階層が決定するのは、_何らかの_認証情報が必要かどうかだけです。保存済みの
認証情報をダウンロードするルートでは、ハンドラー内でさらに 2 段階目のチェックが
行われます。`GET /api/settings/export-json`（復号済みのプロバイダー接続情報と未加工の
API キー）、`GET /api/db-backups/export`（SQLite ファイル）、および
`GET /api/db-backups/exportAll`（完全なアーカイブ）は、`requireOperatorCredential()`
（`src/lib/api/operatorCredential.ts`）を呼び出します。これは、ダッシュボードセッション、
ローカル CLI サブジェクト、またはログインが無効化されたインスタンスを受け入れますが、
あらゆるスコープの API キー（`manage` と `admin` を含む）および `oma_` アクセストークンには
`403` を返します。同期トークンの発行（`POST /api/sync/tokens`）でも同じヘルパーが使用され、
さらに信頼されたループバック内部サービストークンも受け入れます。

### 新規インストール時のブートストラップはループバック限定 — `Host` ではなく実際のピアに基づく

管理パスワードが設定されておらず（かつ `INITIAL_PASSWORD` もない）場合、
`src/shared/utils/apiAuth.ts` の `isAuthRequired()` は、匿名ブートストラップを
**ループバックピアに対してのみ**開放します。ループバックかどうかは、信頼された
ピアシグナルから次の順序で判定されます。トークンでスタンプされた実際の TCP ピア
（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`、ポリシーが参照する情報）、パイプライン自身の
`AUTHZ_HEADER_PEER_LOCALITY` 判定（ルートハンドラーが参照する情報で、
`OMNIROUTE_PEER_STAMP_TOKEN` が設定されている間のみ信頼される）、または直接呼び出し元の
実際のソケットピアです。`Host` / `nextUrl.hostname` は一切参照されません。また、
最初のパスワード書き込み（`POST /api/settings/require-login`）にも同じ制約が適用され、
すべてのネットワークピアに開放されることはありません（GHSA-7pq4-8pvv-rx7r）。
`managementPolicy` は独自の `peerContext` 判定を明示的に下流へ渡すため、ORIGINAL
（除去前）リクエストのヘッダーによって判定が決まることはありません。

### 階層 3 — MANAGEMENT（デフォルト）

その他すべての管理ルート。`requireLogin=false` が設定されていない限り、
認証が必要です。CLI トークンを使用して、これらのルートを認証できます（ループバック + 有効な HMAC）。

## 評価順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → ループバック                                  → 次へ進む
     → 非ループバック、manage スコープの Bearer
        かつ isLocalOnlyBypassableByManageScope      → 許可 (management_key)
     → それ以外                                      → 拒否 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 許可 (system)
  3. hasValidCliToken(headers)?
     → 許可 (cli) [ループバック + timingSafeEqual による HMAC チェック]
  4. isAlwaysProtectedPath(path) または requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 許可 (dashboard_session)
     → バイパス不可のパスで manage スコープの Bearer?
        → 許可 (management_key)
     → 拒否 401/403
  5. requireLogin=false?
     → 許可 (anonymous)
```

ステップ 1 の manage スコープ分岐は、LOCAL_ONLY ルートの条件を満たせる唯一の認証済み経路です。認証バックエンドで障害が発生した場合は 403 ではなく 503 を返すため、期限切れの DB によって暗黙的に「拒否」へダウングレードされることはありません。

## 新しい spawn 対応ルートの追加

1. `src/server/authz/routeGuard.ts` の `LOCAL_ONLY_API_PREFIXES` にパスプレフィックスを追加する
2. `tests/unit/authz/routeGuard.test.ts` に、新しいプレフィックスに対して `isLocalOnlyPath()` が true を返すことを確認するテストを追加する
3. **この手順は絶対に省略しないでください** — `CLAUDE.md` のハードルール #15 を参照してください
4. 判断する：このルートは `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` にも含めるべきか？
   デフォルトの回答は **いいえ** です。manage スコープ保持者に公開しても安全なルート（すなわち、ユーザーが制御できる任意のコードを spawn しないルート）に限って明示的に追加してください。

## manage スコープでバイパス可能なパスの追加

1. そのルートがユーザー指定のコードやコマンドを実行しないことを確認します。実行する場合は中止してください。この例外措置は適切な手段ではありません。
2. `src/server/authz/routeGuard.ts` の `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` にプレフィックスを追加する
3. `tests/unit/authz/management-policy.test.ts` に、4 種類すべてのリクエスト形式についてテストを追加する：Bearer なし（403）、manage Bearer（許可）、manage 以外の Bearer（403）、および manage Bearer がある場合でも `/api/cli-tools/runtime/*` が厳格なループバック限定のままであることを確認するプレフィックス単位のリグレッションテスト

## OpenAPI でのセキュリティティアの文書化

`docs/openapi.yaml` に新しいルートを追加する際、そのルートが `routeGuard.ts` によって分類されている場合は、対応するベンダー拡張を適用してください。

| routeGuard.ts の分類         | YAML アノテーション        | 適用される制約                                       |
| ---------------------------- | -------------------------- | ---------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 非ループバックからのアクセスを無条件でブロック       |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | `requireLogin=false` の場合でも認証が必要            |
| 内部管理/debug ルート        | `x-internal: true`         | デフォルトで /dashboard/api-endpoints に表示されない |
| なし（公開 / 標準認証）      | （アノテーション不要）     | 標準の `requireLogin` によって制御されるアクセス     |

### 検証

2 つのスクリプトにより、YAML アノテーションと `routeGuard.ts` の整合性が強制されます。

- `scripts/check/check-openapi-coverage.mjs` — カバレッジが 99% 未満の場合に失敗
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` または
  `x-always-protected` のアノテーションがコンパイル時定数と一致しない場合に失敗

両方のスクリプトは、pre-commit フックおよび CI で実行されます。

### 誤検出に関するルール

`routeGuard.ts` の定数に含まれていないルートに `x-always-protected` または `x-loopback-only` が付与されている場合、カバレッジスクリプトは失敗します。修正方法は常に、YAML を `routeGuard.ts` が実際に適用している内容に合わせることです。適用ロジックも実装せずにルートを `routeGuard.ts` へ追加してはいけません。
