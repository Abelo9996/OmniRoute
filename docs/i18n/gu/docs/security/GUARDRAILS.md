> **સત્યનો અધિકૃત સ્રોત:** `src/lib/guardrails/`
> **છેલ્લે અપડેટ કરેલું:** 2026-08-29 — v3.8.51 (Video Bridge ટ્રાન્સક્રિપ્ટનું મૂળ કૉલર દ્વારા જાહેર કરવામાં આવે છે,
> હજી સર્વર દ્વારા ચકાસાયેલું નથી — #11661 અનુસાર સ્પષ્ટ કરવામાં આવ્યું)

Guardrails, OmniRoute અને અપસ્ટ્રીમ પ્રદાતાઓ વચ્ચેની સીમા પર સુરક્ષા, નીતિ અને કન્ટેન્ટ રૂપાંતરણો લાગુ કરે છે. દરેક guardrail વિનંતીના payloads (`preCall`) અને અપસ્ટ્રીમ પ્રતિસાદો (`postCall`)નું નિરીક્ષણ કરી શકે છે (અને વૈકલ્પિક રીતે તેમને નકારી, રૂપાંતરિત અથવા ઍનોટેટ કરી શકે છે).

સિસ્ટમ **fail-open** છે: જો કોઈ guardrail કાર્યરત હોય ત્યારે અપવાદ ફેંકે, તો registry ભૂલ નોંધે છે અને વિનંતીને નિષ્ફળ કરવાને બદલે આગામી guardrail સાથે ચાલુ રહે છે. બ્લૉક કરવું હંમેશાં સ્પષ્ટ નિર્ણય (`block: true`) હોય છે, ક્યારેય આકસ્મિક ઘટના નહીં.

## બિલ્ટ-ઇન ગાર્ડરેલ્સ

ઇમ્પોર્ટ કરતી વખતે રજિસ્ટ્રી પ્રાથમિકતાના ક્રમમાં છ ગાર્ડરેલ્સ આપમેળે લોડ કરે છે
(`registry.ts` → `registerDefaultGuardrails()` જુઓ):

| પ્રાથમિકતા | નામ                 | તબક્કો(ઓ)      | ફાઇલ                  |
| ---------- | ------------------- | -------------- | --------------------- |
| `5`        | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`        | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`        | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`       | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`       | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`       | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

ઓછી પ્રાથમિકતા સંખ્યાઓ **પહેલાં** ચાલે છે.

### વિઝન બ્રિજ (`visionBridge.ts`) — મોડેલિટી બ્રિજ PR-1

**વિઝન વિનાનાં મોડલ્સ**ને લક્ષ્ય કરતી, ઇમેજ ધરાવતી વિનંતીઓને અવરોધે છે અને કાં તો
આખી વિનંતીને વિઝન-સક્ષમ મોડલ તરફ ફરી મોકલે છે અથવા અપસ્ટ્રીમ કૉલ પહેલાં
ઇમેજના ભાગોને રૂપરેખાંકિત કરી શકાય તેવા વિઝન મોડલ દ્વારા બનાવવામાં આવેલા
ટેક્સ્ટ વર્ણનોથી બદલે છે. આ ટેક્સ્ટ-માત્ર પ્રદાતાઓને મલ્ટિમોડલ પેલોડ્સ
પારદર્શક રીતે સંભાળવાની સુવિધા આપે છે.

પ્રવાહ:

1. જો લક્ષ્ય મોડલ પહેલેથી જ વિઝનને સપોર્ટ કરતું હોય, તો તેને છોડો (સિવાય કે તે
   ફરજિયાત-બ્રિજ સૂચિ `isVisionBridgeForcedModel`માં હોય).
2. `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) દ્વારા ઇમેજના ભાગો કાઢો, જે
   `open-sse/utils/mediaParts.ts`માંના **એકીકૃત મીડિયા ડિટેક્ટર**
   `detectMediaParts()`ને કાર્ય સોંપે છે — આ કોમ્બો સુસંગતતા ફિલ્ટર સાથે
   વહેંચાયેલ સત્યનો એકમાત્ર સ્રોત છે.
   એક્સ્ટ્રેક્શન માત્ર `replaceImageParts` ફરી જોડી શકે તેવા ટોચના-સ્તરના
   ભાગોના આકારો પૂરતું અનુમતિ-સૂચિબદ્ધ છે (એક્સ્ટ્રેક્ટ↔રિપ્લેસ કરાર): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"`, અને Responses API `input_image`. નેસ્ટેડ મેળ અને
   માત્ર-સૂચક આકારો કોમ્બો-ફિલ્ટર માટેની સામગ્રી છે અને ક્યારેય કાઢવામાં આવતા નથી.
   જો કંઈ ન મળે તો છોડો.
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) દ્વારા રનટાઇમ કૉન્ફિગ
   ઉકેલો: નવી `modalityBridge*` સેટિંગ્સ કીઝને અગ્રતા મળે છે; જૂની
   `visionBridge*` કીઝ **એક-ચક્રના ફૉલબૅક** (રોલબૅક વિન્ડો) તરીકે યથાવત્ રહે છે.
   બ્રિજ અક્ષમ હોય ત્યારે કોઈપણ મીડિયા ટ્રાવર્સલ પહેલાં છોડી દો.
4. મોડ સિલેક્ટર (`modalityBridgeVisionMode`, નીચેનું કોષ્ટક જુઓ) રીરાઉટ કરવું કે
   વર્ણન કરવું તે નક્કી કરે છે. રીરાઉટ માત્ર `model` બદલાયેલું હોય તેવું
   `modifiedPayload`, તેમજ `{ rerouted, fromModel, toModel, imagesKept }` મેટા
   પરત કરે છે.
5. વર્ણન પાથ: ઇમેજોની સંખ્યા `maxImages` સુધી મર્યાદિત કરો, કાર્ય-અવગત પ્રૉમ્પ્ટ
   બનાવો, વર્ણન કૅશ તપાસો, વિઝન મોડલને **સમાંતર રીતે**
   (`Promise.allSettled`) કૉલ કરો અને તેમની જગ્યાએ
   `[Image N]: <description>` ટેક્સ્ટ ભાગો દાખલ કરો. નિષ્ફળ વર્ણન `null` આપે છે
   અને મૂળ ઇમેજ ભાગ **જાળવી રાખવામાં આવે છે** (#4012) — સિવાય કે કોમ્બો વર્ણન
   પાથ પર દરેક વર્ણન નિષ્ફળ ગયું હોય; એ સ્થિતિમાં પુષ્ટિ થયેલા નૉન-વિઝન
   અપસ્ટ્રીમને તેના બદલે
   `(અનુપલબ્ધ — કોઈ વિઝન-સક્ષમ પ્રદાતા જોડાયેલ નથી)` સ્ટબ મળે છે (#8430).
6. `modifiedPayload` + મેટા (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) પરત કરો.

#### મોડ સિલેક્ટર (`modalityBridgeVisionMode`)

| મોડ        | ડિફૉલ્ટ | વર્તણૂક                                                                                                                                                                                                                                                                                    |
| ---------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔       | જૂની હ્યુરિસ્ટિક, અપરિવર્તિત (#6640/#7204): નૉન-કોમ્બો/`auto/` મોડલ્સ શ્રેષ્ઠ વિઝન મોડલ તરફ રીરાઉટ થાય છે, સિવાય કે મૂળ મોડલ પાસે પહેલેથી જ ઉપયોગી ક્રેડેન્શિયલ્સ હોય (ત્યારે વર્ણન થાય છે); કોમ્બો લક્ષ્યો હંમેશાં વર્ણન કરે છે.                                                          |
| `describe` |         | હંમેશાં વર્ણન કરો — રીરાઉટ બ્લૉક સંપૂર્ણપણે છોડવામાં આવે છે; વપરાશકર્તાએ પસંદ કરેલું મોડલ હંમેશાં જવાબ આપે છે.                                                                                                                                                                             |
| `reroute`  |         | રીરાઉટ ફરજિયાત કરો: ક્રેડેન્શિયલ ધરાવતા મોડલને જાળવી રાખતો ગાર્ડ બાયપાસ થાય છે. રીરાઉટ-**લક્ષ્ય** ક્રેડેન્શિયલ ગાર્ડ હજુ પણ લાગુ પડે છે — જ્યારે ઉપયોગી વિઝન લક્ષ્ય ઉપલબ્ધ ન હોય, ત્યારે વિનંતી વર્ણન તરફ આગળ વધે છે, જેથી કાચી ઇમેજો ક્યારેય ટેક્સ્ટ-માત્ર બૅકએન્ડ સુધી ન પહોંચે (#8430). |

ફરજિયાત મોડ્સ ઑટો હ્યુરિસ્ટિક ચાલે તે **પહેલાં** શૉર્ટ-સર્કિટ થાય છે; `auto`ની
વર્તણૂક PR-1 પહેલાંના ગાર્ડરેલ સાથે બાઇટ-સમાન છે.

#### API-કીનો વ્યાપ (`visionBridgeKeyScope.ts`)

જ્યારે કૉલરની API કી `allowedConnections`, ક્વોટા પૂલ્સ
(`allowedQuotas`) અથવા મોડલ્સ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`)ને મર્યાદિત કરે છે,
ત્યારે બ્રિજ માત્ર તે જ રીરાઉટ અને વર્ણન મોડલ્સ પસંદ કરે છે જેનો ઉપયોગ કી કરી
શકે, અને માત્ર એવી કનેક્શન્સ પર જેનો ઉપયોગ કી કરી શકે. ત્યારબાદ વર્ણન કૉલ
હંમેશાં `x-omniroute-self-loop-key-id` હેડર સાથે OmniRoute સેલ્ફ-લૂપ મારફતે
થાય છે, જેથી પ્રાપ્ત કરતી ચેટ વિનંતી તે કીની કનેક્શન અને મોડલ નીતિ ફરીથી
લાગુ કરે. `enforceApiKeyPolicy()` તે હેડરને માત્ર સેલ્ફ-લૂપ બેરર સાથે જ
માન્ય રાખે છે, તેથી તે ફક્ત ઍક્સેસને વધુ મર્યાદિત કરી શકે છે, અને જે id ઉકેલી
શકાતું નથી તે નકારવામાં આવે છે.

જો કી માટે કોઈ વિઝન મોડલની પરવાનગી ન હોય, તો વર્ણન પાથ બાજુએ થઈ જાય છે અને
વિનંતી અપરિવર્તિત રીતે પસાર થાય છે—અક્ષમ ગાર્ડરેલ જેવી જ ફેલ-ઓપન વર્તણૂક
(મેટા `{ skipped: true, reason: "no_permitted_vision_model" }`).
કી વિનાની વિનંતીઓ અને આ મર્યાદાઓ વિનાની કીઝ પહેલાની જેમ જ વર્તે છે.

#### કાર્ય-અવગત વર્ણન પ્રૉમ્પ્ટ (`modalityBridgeVisionTaskAware`)

ડિફૉલ્ટ **true** છે. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) મૂળભૂત
વર્ણન પ્રોમ્પ્ટમાં **છેલ્લા વપરાશકર્તા સંદેશા**નો ટેક્સ્ટ (500 અક્ષરો સુધી કાપેલો)
ઉમેરે છે, જેથી વર્ણન વપરાશકર્તાએ ખરેખર જે પૂછ્યું હોય તે તરફ દોરાય
(codex-vision-proxy પેટર્ન) અને વિઝન મોડલને દૃશ્યમાન ટેક્સ્ટનું લિપ્યંતરણ કરવા કહે છે.
ફ્લૅગ બંધ હોય — અથવા વપરાશકર્તાનો કોઈ ટેક્સ્ટ ન હોય — ત્યારે મૂળભૂત પ્રોમ્પ્ટનો
કોઈ ફેરફાર કર્યા વિના ઉપયોગ થાય છે.

વર્ણન સેલ્ફ-લૂપની પોતાની OpenAI-સુસંગત વિનંતી (`callVisionModelSingle()`
`visionBridgeHelpers.ts`માં) હંમેશાં `image_url.detail: "high"`ની વિનંતી કરે છે —
બિનશરતી રીતે, દરેક કોલર/પ્રદાતા માટે, કોઈપણ ક્લાયન્ટ સંકેત પર આધાર રાખ્યા વિના.
ઓછી-વિગતવાળું સેમ્પલિંગ આ પ્રોમ્પ્ટ જે ટેક્સ્ટ-લિપ્યંતરણ કાર્ય માટે કહે છે તેની
OCR ચોકસાઈ ઘટાડે છે, તેથી મૂળ ઇનબાઉન્ડ વિનંતીમાં જે પણ વિગત સ્તર વપરાયું હોય
તેને ધ્યાનમાં લીધા વિના વર્ણન કૉલ પોતે હંમેશાં ઊંચી વિગત માટે કહે છે. આ ફક્ત
આંતરિક વર્ણન વિનંતીના બૉડીને અસર કરે છે; OmniRoute પ્રાથમિક વિનંતીમાં કોલરનું
પોતાનું `image_url.detail` કેવી રીતે ફૉર્વર્ડ કરે છે તે બદલાતું નથી — તે ડિફૉલ્ટ
અલગથી અને ફક્ત શોધાયેલા OpenCode ક્લાયન્ટ્સ માટે `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`)માં લાગુ થાય છે. વર્ણન સેલ્ફ-લૂપની
Anthropic વાયર-ફૉર્મેટ શાખામાં `detail` ફીલ્ડ નથી અને બંનેમાંથી કોઈપણ ડિફૉલ્ટથી
તેને અસર થતી નથી.

#### વર્ણન આઉટપુટ મર્યાદા (`modalityBridgeVisionMaxChars`)

| કી                             | ડિફૉલ્ટ | શ્રેણી             |
| ------------------------------ | ------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`     | `0` અથવા 100–50000 |

`0` (ડિફૉલ્ટ)નો અર્થ **કોઈ મર્યાદા નહીં** થાય છે — `callVisionModel()` દ્વારા
પરત કરાયેલ વર્ણન કોઈ ફેરફાર વિના પસાર કરવામાં આવે છે, જેથી હાલનું વર્તન જળવાય.
100–50000 શ્રેણીનું કોઈપણ મૂલ્ય વર્ણનને `[Image N]: <description>` તરીકે પાછું
જોડતાં પહેલાં `…` પ્રત્યય સાથે કાપે છે (`src/lib/guardrails/visionBridge.ts`માં
`VisionBridgeGuardrail.preCall()`). વિગત-સભર OCR કાર્યો માટે, જ્યાં અનુગામી
મોડલને સંપૂર્ણ લિપ્યંતરણની જરૂર હોય, આ મૂલ્ય વધારો; વધુ બોલકાં વિઝન મોડલ્સ માટે
ટોકન વપરાશને મર્યાદિત કરવા તેને ઘટાડો. ડૅશબોર્ડ ફીલ્ડ Vision ટૅબની Advanced
પૅનલમાં છે (`ModalityBridgeVisionTab.tsx`માં `modality-bridge-max-chars`) અને
સ્પષ્ટ `0`ને અસ્પર્શિત રાખીને 1 અને 99 વચ્ચેના કોઈપણ મૂલ્યને લઘુત્તમ 100 સુધી
લાવે છે — `0` પોતે એક માન્ય Zod મૂલ્ય છે
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ફક્ત
"સેટ ન કરેલું" ડિફૉલ્ટ નથી.

#### વર્ણન કૅશ (`modalityBridge/bridgeCache.ts`)

વર્ણન આઉટપુટ માટે ઇન-મેમરી LRU + TTL કૅશ, જે સમગ્ર પ્રોસેસમાં શેર થાય છે.
કી = `sha256(imageRef + composedPrompt + configuredBridgeModel)`, જેમાં
લંબાઈ-ઉપસર્ગ ફ્રેમિંગ છે (ફીલ્ડ-સીમા અથડામણો વિના). મોડલ ઘટક
**કૉન્ફિગર કરેલું** બ્રિજ મોડલ છે, વાસ્તવમાં જવાબ આપનાર મોડલ નહીં —
`callVisionModel` આંતરિક રીતે ફૉલબૅક કરી શકે છે અને દરેક પ્રયાસ મુજબ કી બનાવવાથી
કૅશ વિખંડિત થઈ જશે. નિષ્ફળ વર્ણનો ક્યારેય કૅશ થતા નથી. સેટિંગ્સ:

| કી                              | ડિફૉલ્ટ | શ્રેણી  |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### રિમોટ ઇમેજ નૉર્મલાઇઝેશન (સેલ્ફ-લૂપ વર્ણન/base64 ફેચ)

જ્યારે બ્રિજ પોતે કોઈ **રિમોટ** ઇમેજ ફેચ કરે છે — Anthropic વર્ણન સેલ્ફ-કૉલ
અને claude-વાયર-ફૉર્મેટ base64 રૂપાંતરણ (`ensureBase64ImagesForClaudeWire`),
બંને `visionBridgeHelpers.ts`માં `fetchRemoteImageAsDataUri()` દ્વારા — ત્યારે
પરિણામી ડેટા URIને વિઝન-મોડલ વિનંતીમાં એમ્બેડ કરતા પહેલાં
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`)માંથી પસાર કરવામાં આવે
છે. અતિમોટી ઇમેજને **2048px લાંબી ધાર** સુધી ડાઉનસ્કેલ કરવામાં આવે છે (OpenAI/
Anthropic પહેલેથી સર્વર-સાઇડ પર લાગુ કરે છે તે રિસાઇઝ મર્યાદા સાથે મેળ ખાતું),
જેનાથી વિઝન મોડલ જે જુએ છે તે બદલ્યા વિના અપલોડ બાઇટ્સ/લેટન્સી ઘટે છે. રિસાઇઝિંગ
માટે ડાયનેમિક ઇમ્પોર્ટ દ્વારા લોડ કરાયેલ `sharp`નો ઉપયોગ થાય છે: જે પ્લેટફૉર્મ પર
તેની નેટિવ બાઇનરી લોડ થવામાં નિષ્ફળ જાય ત્યાં `normalizeDataUri()` **ક્યારેય
થ્રો કરતું નથી** — તે મૂળ બાઇટ્સને જેમનાં તેમ પસાર કરવા પર ફૉલબૅક કરે છે, જેથી
વર્ણન/base64-રૂપાંતરણ પાથ હંમેશાં કાર્યરત રહે. બિન-ઇમેજ બાઇટ્સ (એવું ફેચ જેણે
ડીકોડ કરી શકાય તેવી ઇમેજ પરત ન કરી હોય) પણ અસ્પર્શિત રીતે પસાર થાય છે. આ
નૉર્મલાઇઝેશન બ્રિજ પોતાના સેલ્ફ-કૉલ માટે ફેચ કરે તેવી ઇમેજ સુધી મર્યાદિત છે —
તે કોલરના કાચા પાસથ્રૂ પેલોડ પર ક્યારેય લાગુ થતું નથી, જે ફક્ત સ્પષ્ટ સંમતિથી
પરિવર્તન કરવાના સિદ્ધાંત (Hard Rule #20) સાથે સુસંગત છે.

#### સેટિંગ્સ સ્કીમા + માઇગ્રેશન

નવી `modalityBridge*` કીઝ `updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`)માં Zod દ્વારા માન્ય કરવામાં આવે છે:
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCache*`ની ત્રણેય કીઝ અને Audio Bridge દ્વારા વપરાતું
`modalityBridgeAudio*` જૂથ. માઇગ્રેશન `141_modality_bridge_settings.sql` હાલનાં
લેગસી `visionBridge*` મૂલ્યોને મેળ ખાતી નવી કીઝમાં કૉપી કરે છે (આઇડેમ્પોટન્ટ,
ઑપરેટર દ્વારા સેટ કરાયેલા `modalityBridge*` મૂલ્યને ક્યારેય ઓવરરાઇટ કરતું નથી);
એક રિલીઝ ચક્ર માટે લેગસી કીઝને રીડ ફૉલબૅક તરીકે સ્વીકારવાનું ચાલુ રહે છે.

#### પારદર્શિતા હેડર + આંકડા

વર્ણન દ્વારા રૂપાંતરિત પ્રતિસાદોમાં
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` હોય છે
(`modalityBridge/bridgeStats.ts`માં `buildModalityBridgeHeader()` દ્વારા બનાવેલું,
`src/sse/handlers/chatHelpers.ts`માં `withModalityBridgeHeader()` દ્વારા ઉમેરેલું).
ફરી રૂટ કરાયેલી વિનંતીઓને **કોઈ** હેડર મળતું નથી — પેલોડ અસ્પર્શિત હતું અને
મોડલની અદલાબદલી પ્રતિસાદ બૉડીના `model` ફીલ્ડમાં પહેલેથી દૃશ્યમાન છે.

`GET /api/modality-bridge/stats` (મેનેજમેન્ટ auth, `GET /api/settings` જેવું જ સ્તર)
`vision`, `audio`, અને `video` માટે ઇન-મેમરી, પ્રતિ-મોડાલિટી કાઉન્ટર્સ
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` પરત કરે છે. `averageLatencyMs` તેના
છેદ તરીકે બધા attempts નહીં, પરંતુ `latencySamples` વાપરે છે; સમય-માપન વિનાનું
ઓપરેશન શૂન્ય-મિલિસેકન્ડનો બનાવટી સેમ્પલ ઉમેરતું નથી. સફળ રૂપાંતરણો માટે
`bridged` બેકવર્ડ-કમ્પેટિબલ ઉપનામ તરીકે યથાવત્ રહે છે; નિષ્ફળ attempts તેને
વધારતા નથી.
ડિઝાઇન મુજબ પ્રોસેસ રીસ્ટાર્ટ થતાં કાઉન્ટર્સ રીસેટ થાય છે
(ટેલિમેટ્રી, હિસાબ નહીં).

#### ડૅશબોર્ડ કન્ફિગરેશન

સમર્પિત ડૅશબોર્ડ પેજ
`/dashboard/settings/modality-bridge` છે. તેની URL દ્વારા ઍક્સેસ કરી શકાય તેવી `Vision`, `Audio`,
અને `Video` ટૅબ્સ `tab` મૂલ્ય બદલતી વખતે ક્વેરી પેરામીટર્સ જાળવી રાખે છે.
Vision ટૅબ સક્ષમતા, મોડ, મોડલ પસંદગી (ઑટોમેટિક ડિફૉલ્ટ સહિત),
ટાસ્ક-અવેર પ્રોમ્પ્ટિંગ, અદ્યતન timeout/image/description-length/cache
મર્યાદાઓ, રનટાઇમ
કાઉન્ટર્સ અને સુરક્ષિત સેમ્પલ રિક્વેસ્ટ ઉપલબ્ધ કરાવે છે. Audio ટૅબ પણ લાઇવ છે: તે
સક્ષમતા, Auto સાથે માત્ર STT માટેનું મોડલ પિકર, timeout/max-clip મર્યાદાઓ, audio
કાઉન્ટર્સ અને `input_audio` સેમ્પલ ટેસ્ટ ઉપલબ્ધ કરાવે છે. Video ટૅબ કાર્યરત છે: તે
FFmpeg/ffprobe રનટાઇમ સ્થિતિ દર્શાવે છે — ચાર સ્પષ્ટ UI સ્થિતિઓમાંથી એક (`unknown` જ્યારે
પ્રોબ ચાલુ હોય અથવા પૂર્ણ ન થઈ શક્યો હોય, નોન-લૂપબૅક ડૅશબોર્ડ હોસ્ટ પર જ્યાં
ક્લાયન્ટ-સાઇડ પ્રોબ છોડવામાં આવે ત્યાં `restricted`, પ્રોબ કર્યા પછી ગેરહાજરીની
પુષ્ટિ થાય ત્યારે `unavailable`, અથવા FFmpeg/ffprobe વર્ઝન્સ સાથે `available`) — enable/model/frame/video/timeout
મર્યાદાઓ કાયમી રાખે છે, મોડલ પિકરને vision-ક્ષમ
મોડલ્સ સુધી ફિલ્ટર કરે છે અને video કાઉન્ટર્સ ઉપલબ્ધ કરાવે છે.

AI સેટિંગ્સ હેઠળનું અગાઉનું Vision Bridge કાર્ડ નવા પેજની કમ્પેટિબિલિટી લિંક
છે; હવે તે ફોર્મની બીજી નકલ ધરાવતું નથી. Media Providers પણ
હાલના Speech-to-Text પ્લેગ્રાઉન્ડને દૂર કર્યા વિના Image-to-Text અને Speech-to-Text
વર્કફ્લોને સંબંધિત Modality Bridge ટૅબ્સ સાથે લિંક કરે છે.

**સેલ્ફ-લૂપ ઍડમિશન બાયપાસ:** જ્યારે describe કૉલ OmniRouteના પોતાના
`/v1` સેલ્ફ-લૂપ (નોન-સ્ટાન્ડર્ડ provider model) મારફતે રૂટ થાય છે, ત્યારે સબ-રિક્વેસ્ટ
`x-omniroute-admission-bypass: internal` મોકલે છે અને ઉકેલાયેલા
સેલ્ફ-લૂપ ક્રેડેન્શિયલ વડે પ્રમાણિત થાય છે — લોકલ મોડમાં લોકલ `sk_omniroute` સેન્ટિનલ, અથવા
ઑપરેટર દ્વારા કન્ફિગર કરેલી `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` env key (#1350), જેથી
`REQUIRE_API_KEY=true` ડિપ્લોયમેન્ટ્સ હજુ પણ describe કૉલ ચલાવી શકે. બાયપાસ
ફક્ત આ ચોક્કસ ક્રેડેન્શિયલ્સ માટે જ માન્ય રાખવામાં આવે છે, તેથી બાહ્ય ક્લાયન્ટ્સ ઍડમિશન
છોડવા માટે આ હેડરનો ઉપયોગ કરી શકતા નથી.

લેગસી ડિફૉલ્ટ્સ `src/shared/constants/visionBridgeDefaults.ts`માં છે;
નવા mode/task-aware/cache ડિફૉલ્ટ્સ અને સેટિંગ્સ રિઝોલ્વર
`src/shared/constants/modalityBridgeDefaults.ts`માં છે. ગાર્ડરેલ
`deps` કન્સ્ટ્રક્ટર વિકલ્પ ઉપલબ્ધ કરાવે છે, જેથી ટેસ્ટ્સ નકલી `getSettings` અને
`callVisionModel` ઇમ્પ્લિમેન્ટેશન્સ ઇન્જેક્ટ કરી શકે.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

એવી ટાર્ગેટ સુધી પહોંચે તે પહેલાં audio ધરાવતી chat રિક્વેસ્ટ્સને ઇન્ટરસેપ્ટ કરે છે,
જે audio ઇનપુટ સ્વીકારવા માટે જાણીતી નથી. તે chat રિક્વેસ્ટને ક્યારેય ફરી રૂટ કરતું નથી:
હાલના OpenAI-કમ્પેટિબલ multipart એન્ડપૉઇન્ટ દ્વારા audio ભાગોનું
ટ્રાન્સક્રિપ્શન થાય છે અને પસંદ કરેલું chat મોડલ ટેક્સ્ટ ટ્રાન્સક્રિપ્ટ્સ સાથે આગળ વધે છે.

પ્રવાહ:

1. `getResolvedModelCapabilities()` દ્વારા `supportsAudio` ઉકેલો. સ્પષ્ટ
   provider-registry મેટાડેટાને પ્રાથમિકતા મળે છે, ત્યારબાદ સ્ટેટિક model મેટાડેટા અને પછી સિંક થયેલું
   `modalities_input`. `audio` વિનાની જાહેર કરેલી ઇનપુટ સૂચિ `false` છે; ક્ષમતા
   અંગે કોઈ પુરાવો ન હોય તો મૂલ્ય `null` રહે છે. `false` અને `null` બંને
   કન્ઝર્વેટિવ બ્રિજને સક્રિય કરે છે, જ્યારે `true` તેને બાયપાસ કરે છે.
2. `modalityBridgeAudio*` સેટિંગ્સ ઉકેલો અને શેર કરેલા `detectMediaParts()`
   ડિટેક્ટર દ્વારા દરેક મેસેજમાંથી સ્પ્લાઇસ કરી શકાય તેવા ટોપ-લેવલ
   audio ભાગો એક્સટ્રેક્ટ કરો. સમર્થિત વાયર શેપ્સ OpenAI `input_audio`, `audio_url`, અને
   `source.media_type: "audio/*"` છે. નેસ્ટેડ audio રૂટિંગ માટે શોધાય છે, પરંતુ
   splice પાથ દ્વારા દૂર થતું નથી. કાર્ય `modalityBridgeAudioMaxClips` દ્વારા મર્યાદિત છે;
   પછીના ભાગો અસ્પર્શિત રહે છે.
3. કન્ફિગર કરેલા `provider/model`નું પાલન કરો, અથવા `selectAudioBridgeModel()`ને
   સ્થિર કૅટલોગ ક્રમમાં `AUDIO_TRANSCRIPTION_PROVIDERS`માંથી પસાર થઈને ઉપયોગ કરી શકાય
   તેવા સક્રિય provider ક્રેડેન્શિયલ ધરાવતું પ્રથમ મોડલ પસંદ કરવા દો.
4. `callAudioTranscription()` base64/data-URI audioને multipart
   `file`માં રૂપાંતરિત કરે છે, અથવા DNS પિનિંગ અને 25 MB મર્યાદા સાથે public-only outbound
   ગાર્ડ દ્વારા રિમોટ `audio_url` ડાઉનલોડ કરે છે. ત્યારબાદ તે ફાઇલ અને પસંદ કરેલા
   મોડલને લોકલ `/v1/audio/transcriptions` સેલ્ફ-લૂપ પર POST કરે છે અને
   `resolveSelfLoopBearer()` વડે પ્રમાણિત કરે છે. હાલનો ટ્રાન્સક્રિપ્શન રૂટ સામાન્ય
   ક્રેડેન્શિયલ લુકઅપ, cooldown/rate-limit હેન્ડલિંગ અને provider ડિસ્પૅચ કરે છે.
5. સફળ કૉલ્સ તેમના ભાગોને `[Audio N]: <transcript>`થી બદલે છે. કૉલ્સ
   `Promise.allSettled` સાથે ચાલે છે: વ્યક્તિગત નિષ્ફળતા મૂળ
   audio ભાગને જાળવી રાખે છે (#4012 કોન્ટ્રાક્ટ). જો દરેક કૉલ નિષ્ફળ જાય અને ટાર્ગેટ માટે
   `supportsAudio === false` સાબિત થયેલું હોય, તો ભાગો
   `[Audio N]: (unavailable — no STT provider connected)` બને છે (#8430 કોન્ટ્રાક્ટ). અજ્ઞાત
   ટાર્ગેટ (`null`) માટે, તમામ કૉલ્સની નિષ્ફળતાનું પરિણામ અસ્પર્શિત રહે છે. કોઈ ઉપયોગ કરી શકાય તેવું
   STT ક્રેડેન્શિયલ ન ધરાવતા સાબિત થયેલા text-only ટાર્ગેટને નેટવર્ક કૉલ કર્યા વિના
   એ જ સ્પષ્ટ સ્ટબ મળે છે.

સફળ ટ્રાન્સક્રિપ્ટ્સ પ્રોસેસ-વ્યાપી Modality Bridge LRU/TTL cache વાપરે છે.
કીમાં audio રેફરન્સ, સ્થિર `audio-transcription` ઓપરેશન
લેબલ અને પસંદ કરેલું STT મોડલ સંયોજિત થાય છે; નિષ્ફળતાઓ ક્યારેય cache થતી નથી. Audio attempts
શેર કરેલા `bridged`, `cacheHits`, `failures`, અને `lastUsedAt` કાઉન્ટર્સ અપડેટ કરે છે.
રૂપાંતરિત રિસ્પોન્સમાં
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` હોય છે; અસ્પર્શિત
રિક્વેસ્ટ્સને Audio Bridge સેગમેન્ટ મળતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| કી                            | ડિફૉલ્ટ | શ્રેણી               |
| ----------------------------- | ------- | -------------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                    |
| `modalityBridgeAudioModel`    | `""`    | સ્વચાલિત અથવા STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000          |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10                 |

શેર કરેલી કૅશ હજુ પણ `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` અને `modalityBridgeCacheMaxEntries` દ્વારા નિયંત્રિત થાય છે.

### વીડિયો બ્રિજ (`videoBridge.ts`, `videoBridgePipeline.ts`)

જાણીતા નેટિવ વીડિયો સપોર્ટ વિનાના લક્ષ્યને કૉલ કરવામાં આવે તે પહેલાં Chat Completionsના `messages` અને Responses
APIના `input`માં ટોચના સ્તરના વીડિયો ભાગોને ઇન્ટરસેપ્ટ કરે છે.
સમર્થિત સ્વરૂપો `input_video`, `video_url`, `video_source`, HTTPS URLs
અને `data:video/*;base64,...` ડેટા URIs છે. ટેક્સ્ટમાં સાદા ફાઇલનામોને
વીડિયો તરીકે ગણવામાં આવતાં નથી.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) રિક્વેસ્ટ ટ્રાવર્સલ,
ક્ષમતા/નીતિ તપાસ, પ્રતિ-રિક્વેસ્ટ એકત્રીકરણ અને રિસ્પોન્સ પેલોડ સંભાળે છે.
પ્રતિ-વીડિયો કાર્ય — પ્રાપ્તિ, સંપૂર્ણ-પરિણામ કૅશ, ફ્રેમ
ક્રમનું વર્ણન કરવું (જે કૉલર દ્વારા જાહેર કરાયેલી કોઈપણ ઑડિયો ટ્રાન્સક્રિપ્ટને સંયોજિત કરે છે), અને પ્રતિ-પ્રયાસ
મેટ્રિક્સ/નિરસ્તીકરણ/ક્લીનઅપ — `videoBridgePipeline.ts`માં `processVideoPart` પાછળ
છુપાયેલું છે, જેને `preCall`ના લૂપની અંદર દરેક વીડિયો ભાગ માટે એક વાર કૉલ કરવામાં આવે છે.
આ મોડ્યુલ સ્પષ્ટ પોર્ટ સીમાઓ `VideoMediaBrokerPort`
(બાઇટ્સ પ્રાપ્ત કરવી અને નમૂના લીધેલી ફ્રેમ્સ કાઢવી), `VideoAudioTranscriptionPort`
(કૉલર દ્વારા જાહેર કરાયેલી ઑડિયો ટ્રાન્સક્રિપ્ટને નમૂના લીધેલાં કૅપ્શન્સ સાથે સંયોજિત કરવી), અને
`VideoDrilldownPort` (ફ્રેમ ડ્રિલ-ડાઉન પર્સિસ્ટન્સ સીમા; હજુ સુધી
`processVideoPart` સાથે જોડાયેલ નથી — હાલમાં ફક્ત અલગ `/api/modality-bridge/video/drilldown`
રૂટ જ ડ્રિલ-ડાઉન એન્ટ્રીઓ લખે છે) પણ વ્યાખ્યાયિત કરે છે.

સાર્વજનિક `/v1` રિક્વેસ્ટ પાથ ક્યારેય સબપ્રોસેસને ઇમ્પોર્ટ કે ઇન્વોક કરતો નથી. રિમોટ
વીડિયો 50 MiBની મર્યાદા હેઠળ ડાઉનલોડ થાય છે; ઇનલાઇન base64 વીડિયો માટે
પ્રતિ-વીડિયો ડિકોડ કરેલા ડેટાની રૂઢિચુસ્ત 36 MiB મર્યાદા છે, જેથી મોડલ/મેસેજ/ફ્રેમિંગ એન્વલપ
50 MiBની સાર્વજનિક JSON રિક્વેસ્ટ સ્વીકૃતિ મર્યાદાની અંદર રહી શકે. ફાળવણી પહેલાં ઇનલાઇન
લંબાઈ અને ડિકોડ કરેલા કદના અંદાજોની તપાસ કરવામાં આવે છે. પ્રારંભિક રિમોટ URL અને દરેક રીડાયરેક્ટ પર
HTTPS આવશ્યક છે, જેમાં DNS પિનિંગ સાથેના હાલના
ફક્ત-સાર્વજનિક આઉટબાઉન્ડ ગાર્ડનો ઉપયોગ થાય છે. ત્યારબાદ બાઇટ્સ ચોક્કસ આંતરિક
`POST /api/modality-bridge/video/extract` બ્રોકર સીમા પાર કરે છે. આ રૂટ
`LOCAL_ONLY` અને `SPAWN_CAPABLE` બંને છે, ફક્ત પ્રતિ-પ્રોસેસ પ્રમાણિત,
વિશ્વસનીય-લૂપબૅક રિક્વેસ્ટ સ્વીકારે છે અને ક્યારેય URL, ફાઇલસિસ્ટમ પાથ, એક્ઝિક્યુટેબલ
અથવા આર્ગ્યુમેન્ટ સૂચિ સ્વીકારતો નથી. API બૉડી-સાઇઝ પાઇપલાઇન અને હૅન્ડલરનું ઇન્ક્રિમેન્ટલ બૉડી
રીડર સ્વતંત્ર રીતે 50 MiB બ્રોકર ઇનપુટ મર્યાદા લાગુ કરે છે. તેની મર્યાદિત કતાર
એક સમયે એક એક્સટ્રેક્શન ચલાવે છે, ચાર બાકી જોબ્સને મંજૂરી આપે છે અને બાકી ઇનપુટને
100 MiB સુધી મર્યાદિત કરે છે.

બ્રોકરની અંદર, `ffprobe` એક ખાનગી લોકલ ફાઇલ વાંચે છે; નિશ્ચિત ફોર્મેટ
અનુમતિસૂચિ પ્લેલિસ્ટ અને મેનિફેસ્ટ ફોર્મેટ્સને બાકાત રાખે છે. મંજૂર MOV-ફૅમિલી
કન્ટેનર્સ માટે, બાહ્ય MOV ડેટા રેફરન્સ ડિફૉલ્ટ રૂપે અક્ષમ રહે છે અને
નિશ્ચિત કમાન્ડ તેમને સક્ષમ કરવાનું પસંદ કરતો નથી. `ffprobe` અને `ffmpeg` બંને
ફક્ત-`file` પ્રોટોકૉલ અનુમતિસૂચિ, એક થ્રેડ, નિશ્ચિત આર્ગ્યુમેન્ટ એરે, કોઈ શેલ નહીં,
અને `PATH`માંથી રિઝોલ્વ કરેલા એક્ઝિક્યુટેબલ્સનો ઉપયોગ કરે છે. જોડાયેલા-ચિત્રવાળા કવર સ્ટ્રીમ્સ
પ્લે કરી શકાય તેવા ઉમેદવારો નથી. પ્લે કરી શકાય તેવા તમામ સ્ટ્રીમ્સે મર્યાદાઓ સંતોષવી આવશ્યક છે, અને
નિર્ધારિત સૌથી નીચા-ઇન્ડેક્સ ફૉલબૅક પહેલાં સ્પષ્ટ ડિફૉલ્ટ સ્ટ્રીમને પ્રાથમિકતા આપવામાં આવે છે.
વીડિયો 600 સેકન્ડ, પ્રતિ પરિમાણ 8,192 પિક્સેલ અને
33,554,432 સોર્સ પિક્સેલ સુધી મર્યાદિત છે. FFmpeg 1–16 મધ્યબિંદુ JPEG ફ્રેમ્સના નમૂના લે છે,
નાના ઇનપુટ્સને અપસ્કેલ કર્યા વિના લાંબી ધારને વધુમાં વધુ 1,024 પિક્સેલ સુધી નાની કરે છે અને
તેને ક્યારેય URL મળતો નથી. ડિફૉલ્ટ રૂપે સેમ્પલિંગ `uniform` છે. વૈકલ્પિક
`scene_aware` અને પ્રાયોગિક `segment_aware` નીતિઓ પહેલેથી માન્ય કરાયેલા
લોકલ સ્ટ્રીમ પર એક વધારાનો નિશ્ચિત FFmpeg પાસ કરે છે, મર્યાદિત
`showinfo` સીન ટાઇમસ્ટૅમ્પ્સ પસંદ કરે છે અને ડિટેક્ટર નિષ્ફળતા, સમયસમાપ્તિ, વિકૃત આઉટપુટ અથવા ખાલી
ઉમેદવાર સમૂહના કિસ્સામાં નિર્ધારિત રીતે એ જ સમાન મધ્યબિંદુઓ પર ફૉલબૅક કરે છે.
સેગમેન્ટ-અવેર મોડ માન્ય કરાયેલા સીન અંતરાલોના પ્રમાણમાં મધ્યબિંદુ નમૂનાઓ ફાળવે છે;
સેગમેન્ટ-અવેર પુરાવા અને ફૉલબૅક વર્તનની વિગતો
નીચે આપવામાં આવી છે. દરેક નીતિમાં પસંદગી પછી 16-ફ્રેમની સખત મર્યાદા
લાગુ કરવામાં આવે છે. જ્યારે સીન-અવેર રિક્વેસ્ટમાં ફક્ત એક-ફ્રેમનું બજેટ હોય, ત્યારે તે
સક્રિય સંપૂર્ણ-વીડિયો અથવા ફોકસ વિન્ડોના સમાન મધ્યબિંદુનો ઉપયોગ કરે છે અને
`policyEffective: uniform` રિપોર્ટ કરે છે: પસંદ કરેલી એકમાત્ર સીન ફ્રેમ
બંને ટેમ્પોરલ છેડાઓને જાળવી શકતી નથી. કૉલર વૈકલ્પિક રીતે
મર્યાદિત ફોકસ વિન્ડો (`start`/`end` સેકન્ડ) પ્રદાન કરી શકે છે; સીમાઓને મીડિયાના
સમયગાળા સુધી ક્લૅમ્પ કરવામાં આવે છે, ઉલટાવેલી અથવા અ-મર્યાદિત વિન્ડોઝ નકારવામાં આવે છે અને તમામ સેમ્પલિંગ
નીતિઓ ફક્ત નોર્મલાઇઝ કરેલા અંતરાલની અંદર અમલમાં મૂકવામાં આવે છે. પરિણામી
વિન્ડો સેમ્પલિંગ મેટાડેટામાં અને અવિશ્વસનીય વર્ણન
પ્રિફિક્સમાં સામેલ કરવામાં આવે છે, જેથી ડાઉનસ્ટ્રીમ મોડલ્સ કેન્દ્રિત અંશને સંપૂર્ણ
ટાઇમલાઇનથી અલગ ઓળખી શકે.

સિમેન્ટિક કૅપ્શન ફોકસ એક અલગ, સ્પષ્ટ સેટિંગ છે. ડિફૉલ્ટ `full`
વિશ્લેષણ મોડ હાલના ફ્રેમ પ્રોમ્પ્ટને જાળવે છે અને રિક્વેસ્ટ
ટેક્સ્ટને કૅપ્શન મોડલ સુધી ક્યારેય ફૉર્વર્ડ કરતો નથી. `focused` મોડમાં, બ્રિજ એ જ Chat અથવા Responses
કન્ટેનરમાંથી ફક્ત વપરાશકર્તા દ્વારા લખાયેલ નવીનતમ બિન-ખાલી `text`/`input_text` વાંચે છે,
તેને NFCમાં નોર્મલાઇઝ કરે છે, કંટ્રોલ કેરેક્ટર્સ અને વ્હાઇટસ્પેસને સંકોચે છે
અને તેને 500 Unicode કોડ પોઇન્ટ્સ સુધી મર્યાદિત કરે છે. ખાલી પરિણામ ચોક્કસ
`full` પ્રોમ્પ્ટ પર ફૉલબૅક કરે છે. ઉપયોગી સંકેતને સમર્પિત
અવિશ્વસનીય-વપરાશકર્તા-સંદર્ભ બ્લોકમાં JSON તરીકે સિરિયલાઇઝ કરવામાં આવે છે અને તે ફક્ત અવલોકન કરી શકાય તેવી વિગતોને
પ્રાથમિકતા આપી શકે છે; તે મીડિયામાં દેખાતી
અથવા સંભળાતી સૂચનાઓનું અનુસરણ ન કરવાની અલગ ચેતવણીને ઓવરરાઇડ કરી શકતું નથી. ટેક્સ્ચ્યુઅલ ફોકસ ક્યારેય
`start`/`end`નું અનુમાન કરતું નથી અથવા ટેમ્પોરલ સેમ્પલરને બદલતું નથી.

#### FU-07 માળખાકીય સેગમેન્ટ પુરાવા

`segment_aware` પહેલેથી માન્ય કરાયેલા સ્થાનિક વિડિયો સ્ટ્રીમ પર એક મર્યાદિત પૂર્વ-વિશ્લેષણ પાસનો ઉપયોગ કરે છે. નિશ્ચિત ફિલ્ટર ચેઇન પહેલાં પહોળાઈને વધુમાં વધુ 320 પિક્સેલ સુધી સ્કેલ કરે છે, દૃશ્ય પરિવર્તનો અને સ્થિર અંતરાલો શોધે છે, ત્યારબાદ ધૂંધળાશ, સરેરાશ લ્યુમા અને સ્થાનીય/કાલિક માહિતી માટે પ્રતિ સેકન્ડ 1 ફ્રેમનું સેમ્પલિંગ કરે છે. આ પાસ 600 માળખાકીય સેમ્પલ, એક FFmpeg/ફિલ્ટર થ્રેડ, સમાન માત્ર-`file` પ્રોટોકોલ અને કન્ટેનર અનુમતિ-સૂચિઓ, 1 MiB પ્રક્રિયા-આઉટપુટ મર્યાદા અને બ્રોકરના સહિયારા રદકરણ/સમયમર્યાદાની અંદર વધુમાં વધુ 30 સેકન્ડ સુધી મર્યાદિત છે. તે વિનંતીમાંથી ક્યારેય કોઈ કમાન્ડ, ફિલ્ટર, પાથ અથવા URL સ્વીકારતું નથી.

માળખાકીય મૂલ્યો નિર્ધારિત સેમ્પલિંગ પુરાવા છે, અર્થવિષયક વિડિયો સમજણ નથી. તેઓ વિષયો, ક્રિયાઓ, કૅપ્શનો, વાણી અથવા વપરાશકર્તાના આશયનું અનુમાન કરતા નથી. દૃશ્ય અને સ્થિરતા સીમાઓ સેગમેન્ટ બનાવે છે; સ્થિરતા આવરણ, ધૂંધળાશ, એક્સપોઝર, સ્થાનીય વિગતો અને કાલિક પરિવર્તન માત્ર વર્તમાન 1–16 ફ્રેમના બજેટની ફાળવણીને પ્રભાવિત કરે છે. સંપૂર્ણપણે સ્થિર સેગમેન્ટ વધુમાં વધુ એક ફ્રેમ સુધી મર્યાદિત હોય છે, જ્યારે બિન-સ્થિર સેગમેન્ટ બાકીના બજેટ માટે સ્પર્ધા કરે છે. જ્યારે સીમાઓની સંખ્યા ફ્રેમ કરતાં વધી જાય છે, ત્યારે સમયરેખાનું સમાન આવરણ જાળવવામાં આવે છે, જેથી શરૂઆતના ઝડપી કટ્સ લાંબા અંતિમ સેગમેન્ટને છુપાવી ન શકે. સ્થિરતા સીમાના 1-સેકન્ડના વિશ્લેષણ રિઝોલ્યુશનની અંદરની દૃશ્ય સીમાઓને એકત્રિત કરવામાં આવે છે.

ગુમ થયેલા ફિલ્ટરો, વિકૃત/ખાલી પુરાવા, ડિટેક્ટરની ભૂલ અથવા મર્યાદિત પૂર્વ-વિશ્લેષણ સમયસમાપ્તિના કિસ્સામાં ચોક્કસ સમાન મધ્યબિંદુ નીતિ પર ખુલ્લી નિષ્ફળતા થાય છે. કૉલર દ્વારા રદકરણ અથવા બ્રોકરની સમયમર્યાદા ખુલ્લી નિષ્ફળતા થવા દેતી નથી: તે ચાલુ ઉપપ્રક્રિયાને સમાપ્ત કરે છે, ત્યારબાદનું ફ્રેમ નિષ્કર્ષણ અટકાવે છે અને ખાનગી અસ્થાયી ટ્રીને `finally` માં દૂર કરવામાં આવે છે.

સ્પષ્ટ રીતે ચિહ્નિત વિડિયો ભાગ ટાઇમસ્ટેમ્પવાળી કૉન્ટેક્ટ શીટની વિનંતી કરી શકે છે. બ્રિજ વધુમાં વધુ 4-કૉલમ, 16-ફ્રેમની JPEG ગ્રીડ બનાવે છે. દરેક 512-પિક્સેલ સેલ તેના સ્રોત ટાઇમસ્ટેમ્પને ઉચ્ચ-કોન્ટ્રાસ્ટવાળા તળિયાના પટ્ટામાં અંકિત કરે છે, જ્યારે એ જ ટાઇમસ્ટેમ્પ્સ અનુગામી જોડાણ અને ઑડિટ માટે ટેક્સ્ટ મેટાડેટામાં પણ રહે છે. સંપૂર્ણ JPEG 32 MiB સુધી મર્યાદિત રહે છે. જો `sharp` ગ્રીડને ડિકોડ અથવા સંયોજિત ન કરી શકે, તો બ્રિજ અલગ-અલગ JPEG ફ્રેમ્સ પર પાછો ફરે છે; ક્લાયન્ટનું રદકરણ હજી પણ શીટ ઑપરેશનમાં પ્રસારિત થાય છે.

પ્રમોશનનો પુરાવો કૃત્રિમ સંયોજન માઇક્રોબેન્ચમાર્કથી જાણીજોઈને અલગ રાખવામાં આવ્યો છે. `scripts/perf/video-bridge-contact-sheet-eval.ts` વાસ્તવિક OpenAI-સુસંગત વિઝન મોડેલો માટે સ્કીમા-સંસ્કરણબદ્ધ A/B હાર્નેસ વ્યાખ્યાયિત કરે છે. તે પ્રદાતા દ્વારા જણાવાયેલા ટોકન્સ, શરૂઆતથી અંત સુધીની વાસ્તવિક વિલંબતા (શીટ સંયોજન સહિત), મોડેલ-કૉલની સંખ્યા અને મેનિફેસ્ટ દ્વારા વ્યાખ્યાયિત હકીકતોની જાળવણી માપે છે. રૉ મોડેલ પ્રતિસાદ રિપોર્ટમાં લખવામાં આવતા નથી; માત્ર SHA-256 ડાઇજેસ્ટ્સ અને મેળ ખાતા ફેક્ટ IDs જાળવવામાં આવે છે. જ્યાં સુધી `--execute-real` પાસ કરવામાં ન આવે અને `--model`, `OMNIROUTE_BASE_URL` તથા `OMNIROUTE_API_KEY` કૉન્ફિગર ન હોય, ત્યાં સુધી હાર્નેસ કોઈ નેટવર્ક અથવા ચૂકવણીવાળો મોડેલ કૉલ કરતું નથી. તે સ્પષ્ટ વાસ્તવિક રન વિના, તેનો મશીન-વાંચનીય ચુકાદો `HOLD` જ રહે છે; માત્ર કૃત્રિમ પેલોડ/કૉલ-સંખ્યા માપનો પ્રમોશન પુરાવો નથી.

જ્યારે કૉલર્સ પાસે પહેલેથી સંરેખિત લખાણ હોય, ત્યારે તેઓ સમર્થિત વિડિયો ભાગ સાથે વૈકલ્પિક `transcript.cues` એરે જોડી શકે છે. દરેક ક્યૂમાં `text`, તપાસેલા સમયગાળાની અંદરનું સીમિત `start`/`end` અંતરાલ અને અનુમતિ-સૂચિમાં રહેલું `source` (`client`, `embedded` અથવા `audio-bridge`) હોવું આવશ્યક છે; `confidence`નું ડિફૉલ્ટ મૂલ્ય `1` છે અને તે `0` તથા `1` વચ્ચે જ હોવું આવશ્યક છે. બરાબર સમાન ડુપ્લિકેટ ક્યૂઝને એકત્રિત કરવામાં આવે છે. OmniRoute આ મેટાડેટામાંથી ક્યારેય ટ્રાન્સક્રિપ્શન શરૂ કરતું નથી: માન્ય કરાયેલા ક્યૂઝને સ્રોત, વિશ્વાસ અને અંતરાલ સાથે વર્ણવેલા પરિણામમાં કૉપી કરવામાં આવે છે અને ફ્રેમ કૅપ્શનોની સાથે અવિશ્વસનીય અવલોકનો તરીકે રેન્ડર કરવામાં આવે છે. અમાન્ય, શ્રેણીની બહારનું અથવા ઉદ્ભવ-માહિતી વિનાનું લખાણ કૅપ્શન સ્ટ્રીમમાં ભેળવવાને બદલે નકારવામાં આવે છે. બંને વિનંતી-બોડી ટ્રાન્સક્રિપ્ટ ચેનલો પૂરા પાડવામાં આવેલા ઉદ્ભવને `client` તરીકે સામાન્યકૃત કરે છે, જેમાં સ્વ-ઘોષિત `embedded` અથવા `audio-bridge` લેબલ્સ પણ સામેલ છે. માત્ર સર્વર-માલિકીનું ઍડૅપ્ટર કોડ-માત્ર `trustedSource` આર્ગ્યુમેન્ટ દ્વારા તે વિશ્વસનીય લેબલ્સ સોંપી શકે છે; વિનંતીનું JSON ફીલ્ડ તે આર્ગ્યુમેન્ટ સુધી પહોંચી શકતું નથી. ટ્રાન્સક્રિપ્ટ લખાણ તેના ઉદ્ભવને ધ્યાનમાં લીધા વિના અવિશ્વસનીય મીડિયા-ઉદ્ભવિત સામગ્રી જ રહે છે અને તેણે ક્યારેય અધિકૃતતા નક્કી કરવી જોઈએ નહીં.

એક અદ્યતન કૉલર એ જ વિડિયો માટે `audioTranscript` ટ્રૅક પ્રદાન કરી શકે છે;
તેને ક્લાયન્ટ દ્વારા પ્રદાન કરાયેલ ટેક્સ્ટ તરીકે ગણવામાં આવે છે, સર્વર ટ્રાન્સક્રિપ્શનના પુરાવા તરીકે નહીં.
ફ્યુઝન સીમ એક જ સમયમર્યાદા અને અબોર્ટ સિગ્નલ હેઠળ દૃશ્ય અને ઑડિયો અવલોકનો ચલાવે છે,
તેમને એક સામાન્ય સમયરેખા પર ક્રમબદ્ધ કરે છે, સચોટ ડુપ્લિકેટ્સને એકમાં સમેટે છે,
અને માત્ર એક બાજુ સફળ થાય ત્યારે આંશિક પરિણામની જાણ કરે છે.
અમાન્ય `audioTranscript` ને કારણે પરિણામ આંશિક બને છે — દૃશ્ય
વર્ણન જાળવી રાખવામાં આવે છે અને ઑડિયો બ્રાન્ચ સ્વચ્છ કરેલો નિષ્ફળતા કોડ નોંધે છે —
સમગ્ર વિડિયોને નિષ્ફળ કરવાને બદલે. દરેક બ્રાન્ચની ઉપલબ્ધતા, આંશિક ફ્લૅગ,
અને સ્વચ્છ કરેલા નિષ્ફળતા કોડ્સ વર્ણવેલા પરિણામમાં, ગાર્ડરેલ મેટાડેટામાં
(`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), પરિણામ-કૅશ મેટાડેટામાં અને બ્રિજ
ફ્યુઝન કાઉન્ટર્સમાં જાળવવામાં આવે છે. ડિફૉલ્ટ Video Bridge પાથ speech-to-text
ચાલુ કરતો નથી કે મીડિયાની બીજી નકલ ડાઉનલોડ કરતો નથી; તે સ્પષ્ટ ટ્રૅક વિના,
તે માત્ર-વિડિયો રહે છે.

ફિંગરપ્રિન્ટ જાળવે છે, મૂળ યુઝર ટાસ્કને ક્યારેય નહીં. ગાર્ડરેલ મેટાડેટા વિનંતી કરેલા અને
અસરકારક એનાલિસિસ મોડ બંને રિપોર્ટ કરે છે; ઉપયોગી યુઝર ટેક્સ્ટ વિના વિનંતી કરાયેલ `focused`
મોડને અસરકારક રીતે `full` તરીકે રિપોર્ટ કરવામાં આવે છે.

ગાર્ડરેલ દરેક સપોર્ટેડ વિડિયો પાર્ટને એક્સ્ટ્રૅક્ટ કરે છે, પરંતુ
`modalityBridgeVideoMaxVideos` કરતાં વધુનું વર્ણન કરતું નથી. જે ટાર્ગેટ માટે
`supportsVideo === false` હોવાનું સાબિત થયું હોય, તેમાં નિષ્ફળ અને મર્યાદા કરતાં વધુ વિડિયો સ્પષ્ટ સુરક્ષિત
ટેક્સ્ટ માર્કરમાં રૂપાંતરિત થાય છે, જેથી કોઈ રૉ વિડિયો બાકી ન રહે. જ્યારે ક્ષમતા અજ્ઞાત હોય, ત્યારે એ પાર્ટ્સ
તેમનું વિડિયો કૅરિયર જાળવી રાખે છે; કોઈપણ ફૉલબૅક ટ્રાન્સક્રિપ્ટ ઉપરોક્ત મર્યાદિત ટેક્સ્ટ
રૂપાંતરણને અનુસરે છે. `supportsVideo === true` ધરાવતા ટાર્ગેટ બ્રિજને બાયપાસ કરે છે.
ક્લાયન્ટ રિક્વેસ્ટનું અબૉર્ટ સિગ્નલ ડાઉનલોડ, બ્રોકર ક્યૂ,
સબપ્રોસેસ અને કૅપ્શન કૉલ સુધી પ્રસારિત થાય છે; અબૉર્ટ વિડિયો વચ્ચે પ્રક્રિયા અટકાવે છે અને ક્યારેય રૉ મીડિયા તરફ
ફેલ-ઓપન થતું નથી.

રનટાઇમ સેટિંગ્સ DB-બૅક્ડ અને Zod-વૅલિડેટેડ છે:

| કી                                  | ડિફૉલ્ટ     | શ્રેણી / વર્તણૂક                                                                                          |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | વૈકલ્પિક રનટાઇમ, પસંદગી દ્વારા સક્ષમ                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` સામાન્ય કૅપ્શનો જાળવે છે; `focused` મર્યાદિત, અવિશ્વસનીય નવીનતમ-વપરાશકર્તા સંદર્ભનો ઉપયોગ કરે છે   |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge મોડેલ વારસામાં મેળવો                                                                        |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, અથવા પ્રમાણસર `segment_aware`; ડિટેક્ટર નિષ્ફળ જાય તો `uniform` પર પાછું ફરે છે |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                       |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                            |

120 સેકન્ડથી વધુના જૂના સંગ્રહિત Video સમયસમાપ્તિ મૂલ્યોને
બ્રોકરની સમયમર્યાદા સુધી મર્યાદિત કરવામાં આવે છે; એ મર્યાદાથી વધુના નવા સેટિંગ્સ લખાણો નકારવામાં આવે છે.
`GET /api/modality-bridge/video/runtime` ને પ્રમાણીકરણ અથવા રનટાઇમ ચકાસણી પહેલાં વિશ્વસનીય રીતે મુદ્રાંકિત લૂપબૅક
સ્થાનિકતા જરૂરી છે, અને ત્યારબાદ વ્યવસ્થાપન
પ્રમાણીકરણ જરૂરી છે. તે ફક્ત `available`, શુદ્ધ કરેલ FFmpeg/ffprobe આવૃત્તિઓ અને રનટાઇમ અનુપલબ્ધ હોય ત્યારે એક નિશ્ચિત
કારણ પરત કરે છે. આંતરિક નિષ્કર્ષણ એન્ડપોઇન્ટ
સાર્વજનિક અપલોડ API નથી: કતાર સંતૃપ્તિ `503` સાથે `Retry-After` પરત કરે છે, કૉલર
ડિસ્કનેક્ટ થાય તો `499` પરત થાય છે અને નિશ્ચિત બ્રોકર સમયમર્યાદા `504` પરત કરે છે. રૂપાંતરિત પ્રતિસાદો
Vision અથવા Audio સેગમેન્ટ્સ દૂર કર્યા વિના કેન્દ્રીય
`x-omniroute-modality-bridge` હેડરમાં `video->text;model=<visionModel>;parts=<videos>` ઉમેરે છે.

### PII માસ્કર (`piiMasker.ts`)

**બંને** તબક્કાઓ પર ચાલે છે.

- **`preCall`** પેલોડને ક્લોન કરે છે, `system`, `messages`, `input`, અને
  `prompt` (સાદી સ્ટ્રિંગ આઇટમ્સ સહિત) માંથી પસાર થાય છે અને સ્ટ્રિંગ `content`/`text`
  ફીલ્ડ્સ પર (`@/shared/utils/inputSanitizer` માંથી)
  `processPII()` લાગુ કરે છે. જ્યારે
  `PII_REDACTION_ENABLED=true` હોય, ત્યારે શોધાયેલ PII ને આઉટબાઉન્ડ
  પેલોડમાં સંપાદિત કરવામાં આવે છે. આ `INPUT_SANITIZER_MODE` થી સ્વતંત્ર છે (જે ફક્ત
  પ્રોમ્પ્ટ-ઇન્જેક્શન નીતિને નિયંત્રિત કરે છે). જ્યારે સંપાદન બંધ હોય, ત્યારે કૉલ સામગ્રીને ફરીથી લખ્યા વિના શોધની
  સંખ્યાઓ રેકોર્ડ કરે છે.
- **`postCall`** પ્રતિસાદને ડીપ-ક્લોન કરે છે, `sanitizePIIResponse()` સાથે
  Responses-API-આકાર માસ્કર (`maskResponsesOutput` — જે
  `output_text` અને `output[].content[].text` ને આવરે છે) ચલાવે છે. જો કોઈ સંપાદન થાય, તો
  સંશોધિત પ્રતિસાદ મૂળ પ્રતિસાદને બદલે છે.

ગાર્ડરેલ ક્યારેય અવરોધતું નથી; તે ફક્ત ટિપ્પણી ઉમેરે છે (`meta.detections`,
`meta.redacted`) અથવા ફરીથી લખે છે.

### પ્રોમ્પ્ટ ઇન્જેક્શન (`promptInjection.ts`)

વપરાશકર્તા દ્વારા પૂરી પાડવામાં આવેલી સામગ્રીમાં પ્રતિકૂળ રચનાઓ શોધે છે અને
રૂપરેખાંકિત નીતિ લાગુ કરે છે. વર્તણૂક એન્વાયરમેન્ટ વેરિએબલ્સ અને કન્સ્ટ્રક્ટર
વિકલ્પો દ્વારા નિયંત્રિત થાય છે:

| સેટિંગ          | એન્વાયરમેન્ટ વેરિએબલ                                                                                  | ડિફૉલ્ટ | અસર                                                                                                                                                                                                                              |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| સક્ષમ           | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | જ્યારે `false` હોય, ત્યારે ગાર્ડરેલ શૉર્ટ-સર્કિટ થાય છે.                                                                                                                                                                         |
| મોડ             | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | ઇન્જેક્શન નીતિ: `block`, `warn`, અથવા `log`. (`redact` ને પાછળની સુસંગતતા માટે સ્વીકારવામાં આવે છે, પરંતુ તે ઇન્જેક્શન ટેક્સ્ટને દૂર **કરતું નથી**; વિનંતીમાં PIIનું પુનર્લેખન `PII_REDACTION_ENABLED` દ્વારા નિયંત્રિત થાય છે.) |
| બ્લૉક થ્રેશોલ્ડ | `blockThreshold` વિકલ્પ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ઉપનામ `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | અવરોધવા માટે જરૂરી ન્યૂનતમ ગંભીરતા. ડિફૉલ્ટ રીતે મધ્યમ ગંભીરતા ફક્ત અવલોકન માટે છે.                                                                                                                                              |

**મોડ અગ્રતા** (`getMode`): કૉલર `options.mode` →
`INJECTION_GUARD_MODE` **DB ફીચર-ફ્લૅગ ઓવરરાઇડ** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`. તેથી ડૅશબોર્ડ ઓવરરાઇડ env vars કરતાં અગ્રતા મેળવે છે, જેથી Feature
Flags UI ચાલતા ગાર્ડને લાઇવ નિયંત્રિત કરે છે (પુનઃપ્રારંભ વિના). DB વાંચન નિષ્ફળતા-સુરક્ષિત છે:
જો તેમાં ભૂલ થાય, તો ગાર્ડ env-આધારિત વર્તણૂક પર પાછું ફરે છે, અને જ્યારે કોઈ
ઓવરરાઇડ સેટ ન હોય ત્યારે વર્તણૂક ફક્ત-env રિઝોલ્યુશન જેવી જ હોય છે.

શોધના સ્રોતો:

1. `@/shared/utils/inputSanitizer` માંથી `sanitizeRequest()` (પાઇપલાઇનમાં
   અન્યત્ર ઉપયોગમાં લેવાતો સહિયારો ડિટેક્ટર સમૂહ).
2. બિલ્ટ-ઇન `DEFAULT_GUARD_PATTERNS` (હાલમાં `system_override_inline` અને
   `markdown_system_block`, બંને `high` ગંભીરતા ધરાવે છે).
3. કન્સ્ટ્રક્ટર વિકલ્પો દ્વારા પસાર કરાયેલા વૈકલ્પિક `customPatterns` (સ્ટ્રિંગ્સ, regex,
   અથવા `{ name, pattern, severity }` રેકોર્ડ્સ).

જ્યારે `mode === "block"` હોય **અને** ઓછામાં ઓછી એક શોધ તીવ્રતા
થ્રેશોલ્ડને પૂર્ણ કરતી હોય, ત્યારે `preCall` `{ block: true, message: "Request rejected:
suspicious content detected" }` પરત કરે છે. `warn`/`log` મોડમાં ગાર્ડરેલ લૉગ કરે છે પરંતુ
કૉલને મંજૂરી આપે છે. શેર કરેલ હેલ્પર `evaluatePromptInjection()` પણ એવા
કૉલર્સ માટે એક્સપોર્ટ કરવામાં આવે છે જેમને રજિસ્ટ્રી મારફતે ગયા વિના પ્રોમ્પ્ટનું મૂલ્યાંકન કરવાની જરૂર હોય.

**સ્કૅન મર્યાદા (v3.8.20):** ડિટેક્ટર જોડાયેલા પ્રોમ્પ્ટ ટેક્સ્ટના માત્ર **પ્રથમ 16 KB**નું
નિરીક્ષણ કરે છે — `src/shared/utils/inputSanitizer.ts`માં
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 બાઇટ્સ). પેટર્ન લૂપ ચલાવતા પહેલાં
`detectInjection()` અને `evaluatePromptInjection()` બંને
`slice(0, MAX_INJECTION_SCAN_BYTES)` કરે છે. ઇન્જેક્શન નિર્દેશો ઇનપુટની શરૂઆતની નજીક હોય છે, તેથી આ
શોધને નબળી પાડ્યા વિના અનેક-સો-KB પેલોડ્સ પર regex CPU/GCને મર્યાદિત કરે છે (જુઓ
#3932, #4041).

### ક્રેડેન્શિયલ માસ્કર (`credentialMasker.ts`)

**બંને** તબક્કાઓમાં, ડિફૉલ્ટ ચેઇનમાં છેલ્લે (પ્રાથમિકતા `95`) ચાલે છે. આઉટબાઉન્ડ પેલોડમાંથી
(સંદેશની સામગ્રી, ટૂલ-કૉલ આર્ગ્યુમેન્ટ્સ, ટૂલ પરિણામો) **અને** પ્રોવાઇડરના પ્રતિસાદમાંથી
જાણીતી API-key / secret-token પેટર્નને રિડેક્ટ કરે છે, જેથી પ્રોમ્પ્ટમાં પેસ્ટ કરાયેલ
ક્રેડેન્શિયલ (અથવા ટૂલ પરિણામ દ્વારા પાછું પ્રતિધ્વનિત થયેલું) અપસ્ટ્રીમ પ્રોવાઇડર અથવા
ક્લાયન્ટ સુધી લીક ન થાય.

- **માત્ર ઑપ્ટ-ઇન**, PII રિડૅક્શન જેવો જ નિયમ (Hard Rule #20ની નજીક):
  `settings.credentialRedactionEnabled === true` **અથવા**
  `CREDENTIAL_REDACTION_ENABLED=true` ન હોય ત્યાં સુધી અક્ષમ રહે છે. તે બંધ હોય ત્યારે, ગાર્ડરેલ કોઈ કાર્યવાહી કરતું નથી —
  તે ક્યારેય બ્લૉક કરતું નથી અને ક્યારેય ફરીથી લખતું નથી.
- `redactCredentials()` સંપૂર્ણ પેલોડ/પ્રતિસાદ ટ્રીમાં ટ્રાવર્સ કરે છે (`walkValue()`,
  પ્રોટોટાઇપ-પોલ્યુશનથી સુરક્ષિત, `WeakSet` દ્વારા સાઇકલથી સુરક્ષિત) અને મેળ ખાતા ભાગોને
  `[REDACTED:<type>]` પ્લેસહોલ્ડરથી બદલે છે, અને માત્ર ખરેખર બદલાયેલી શાખાઓને જ
  ક્લોન કરે છે.
- `CREDENTIAL_PATTERNS` LLM પ્રોવાઇડર કીઝ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ટોકન્સ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), પેમેન્ટ કીઝ (Stripe, Square), ક્લાઉડ
  કીઝ (AWS access key, Twilio, SendGrid, Mailgun), પ્રાઇવેટ કીઝ / JWTs,
  ક્રેડેન્શિયલ ધરાવતી કનેક્શન સ્ટ્રિંગ્સ (`mongodb://user:pass@...`, વગેરે), અને
  સામાન્ય `Authorization`/`x-api-key`/`api-key`/`apikey` હેડર-વૅલ્યુ
  પેટર્નને આવરી લે છે. હેડર-આકારની કીઝ (`authorization`, `x-api-key`, `api-key`,
  `apikey`)ને સામાન્ય ટેક્સ્ટ regex દ્વારા નહીં, પરંતુ રચનાત્મક રીતે રિડેક્ટ કરવામાં આવે છે (માત્ર મૂલ્ય,
  `Bearer `/`Basic ` જેવા સ્કીમ પ્રિફિક્સ જાળવવામાં આવે છે).
- ગાર્ડરેલ ક્યારેય બ્લૉક કરતું નથી; તે માત્ર ફરીથી લખે છે (`modifiedPayload` /
  `modifiedResponse`) અને ઍનોટેટ કરે છે (`meta.credentialsRedacted`, `meta.count`).

રિગ્રેશન ગાર્ડ: `tests/unit/credential-masker-guardrail.test.ts`.

## મૂળભૂત કરાર (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ચેઇનને તરત જ અટકાવે છે
  message?: string; // અવરોધિત કરતી વખતે દર્શાવવામાં આવે છે
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // વિનંતીને ફરી લખવા માટે preCall દ્વારા પરત કરવામાં આવે છે
  modifiedResponse?: TValue; // પ્રતિસાદને ફરી લખવા માટે postCall દ્વારા પરત કરવામાં આવે છે
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ગાર્ડરેલ `void`, `{}`, અથવા `{ block: false }` પરત કરીને "કોઈ ફેરફાર નહીં"નો સંકેત આપે છે. `modifiedPayload`/`modifiedResponse` પરત કરવાથી ચેઇનમાં આગળના ગાર્ડરેલ્સ તરફ વહેતું મૂલ્ય બદલાઈ જાય છે.
`signal?: AbortSignal` કૉલરની લાઇફસાઇકલને ગાર્ડરેલ્સ સુધી લઈ જાય છે. વિનંતી રદ થવી એ ઇરાદાપૂર્વકનો fail-open અપવાદ છે: મીડિયા બ્રિજ કામ અટકાવે છે અને જે લક્ષ્ય તેને સપોર્ટ કરતું નથી તે જાણીતું હોવા છતાં તેમાં મૂળ મીડિયા પુનઃસ્થાપિત કર્યા વિના ક્લીનઅપ કરે છે.

## રજિસ્ટ્રી (`registry.ts`)

સિંગલટન `guardrailRegistry` નીચેની સુવિધાઓ પ્રદાન કરે છે:

- `register(guardrail)` — ગાર્ડરેલ ઉમેરે છે (અથવા સામાન્યકૃત નામ દ્વારા બદલે છે) અને
  ચઢતા `priority` મુજબ ફરીથી ગોઠવે છે.
- `clear()` / `list()` — વહીવટી સહાયકો.
- `runPreCallHooks(payload, context)` — સક્રિય ગાર્ડરેલ્સ પર ક્રમશઃ ફરે છે, પેલોડને
  `modifiedPayload` મારફતે આગળ ધપાવે છે અને પ્રથમ `block: true` પર અટકે છે.
- `runPostCallHooks(response, context)` — પ્રતિસાદની બાજુએ સમાન પ્રવાહ.
- `resetGuardrailsForTests({ registerDefaults })` — સ્વચ્છ ટેસ્ટ અલગીકરણ માટે સ્ટેટ સાફ કરે છે અને વૈકલ્પિક રીતે
  ડિફૉલ્ટ્સને ફરીથી રજિસ્ટર કરે છે.

બંને રનર્સ `{ blocked, payload|response, results, guardrail?, message? }`
પરત કરે છે, જ્યાં `results` એ `GuardrailExecutionResult` રેકોર્ડ્સની એરે છે, જેમાં
દરેક ગાર્ડરેલ માટેના `blocked`, `skipped`, `modified`, `error`, અને `meta` ફીલ્ડ્સ
સમાવિષ્ટ હોય છે, જે ટ્રેસિંગ માટે ઉપયોગી છે.

### દરેક વિનંતી માટે ગાર્ડરેલ્સ અક્ષમ કરવા

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` વર્તમાન
વિનંતી માટે છોડવામાં આવનાર ગાર્ડરેલ નામોની ડુપ્લિકેટ-રહિત યાદી એકત્રિત કરે છે.
સ્ત્રોતો (બધા વૈકલ્પિક, બધા મર્જ કરવામાં આવે છે):

- `apiKeyInfo.disabledGuardrails`
- વિનંતી બોડીનું `disabledGuardrails` (ટોચના સ્તરે)
- વિનંતી બોડીનું `metadata.disabledGuardrails`
- હેડર `x-omniroute-disabled-guardrails` (અથવા જૂનું
  `x-disabled-guardrails`)

મૂલ્યો સ્ટ્રિંગ્સની એરે અથવા કૉમાથી અલગ કરેલી સ્ટ્રિંગ હોઈ શકે છે; નામોને
લોઅરકેસ kebab-caseમાં સામાન્યકૃત કરવામાં આવે છે (`pii_masker` → `pii-masker`). પરિણામ
`context.disabledGuardrails` મારફતે રજિસ્ટ્રીને આપવામાં આવે છે, જે
મેળ ખાતા ગાર્ડરેલ્સને છોડી દે છે (`results`માં `skipped: true`).

## અમલીકરણ ક્રમ

`src/sse/handlers/chat.ts` અને
`open-sse/handlers/chatCore.ts`માંથી પસાર થતી દરેક વિનંતી માટે:

1. `resolveDisabledGuardrails(...)` API કી, બોડી અને હેડર્સમાંથી સ્કિપ સૂચિ બનાવે છે.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ચડતા પ્રાથમિકતા ક્રમમાં ગાર્ડરેલ્સ ચલાવે છે:
   - અક્ષમ કરેલા ગાર્ડરેલ્સ `skipped` તરીકે નોંધાય છે.
   - દરેક ગાર્ડરેલનું `preCall`, `modifiedPayload` મારફતે પેલોડને ફરી લખી શકે છે.
   - પ્રથમ `block: true` ચેઇનને શોર્ટ-સર્કિટ કરે છે અને હેન્ડલર
     ગાર્ડરેલ અસ્વીકાર પ્રતિસાદ પરત કરે છે.
3. (સંભવિત રીતે ફરી લખાયેલો) પેલોડ કોમ્બો રાઉટિંગ અને અપસ્ટ્રીમ
   ડિસ્પેચમાં જાય છે.
4. પ્રતિસાદ તૈયાર થયા પછી, `guardrailRegistry.runPostCallHooks(...)`
   પ્રતિસાદ પર એ જ ચેઇન ચલાવે છે. અહીં `block: true` અપસ્ટ્રીમ
   પ્રતિસાદને કાઢી નાખે છે.

જે ગાર્ડરેલ્સ અપવાદ ફેંકે છે તે `error: <message>` સાથે નોંધાય છે અને
`logger.warn` મારફતે લૉગ થાય છે, પરંતુ ચેઇન ચાલુ રહે છે — ડિઝાઇન મુજબ ફેઇલ-ઓપન.

| ------------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | શોધને સંપૂર્ણપણે અક્ષમ કરવા માટે `false` સેટ કરો.                                                               |

## કસ્ટમ ગાર્ડરેલ્સ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

પગલાં:

1. `BaseGuardrail`ને વિસ્તૃત કરતી `src/lib/guardrails/myGuardrail.ts` બનાવો.
2. `preCall` અને/અથવા `postCall` અમલમાં મૂકો.
3. કાં તો ઇમ્પોર્ટ સમયે નોંધણી કરો (`registerDefaultGuardrails`માંથી પુશ કરો) અથવા
   રનટાઇમ પર `guardrailRegistry.register(...)` કૉલ કરો — રજિસ્ટ્રી સમાન સામાન્યકૃત
   નામ ધરાવતા કોઈપણ અગાઉના ગાર્ડરેલને બદલી નાખે છે.
4. `tests/unit/` હેઠળ પરીક્ષણો ઉમેરો (હાલનાં ઉદાહરણો:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## પરીક્ષણ

જાણીતી સ્થિતિથી શરૂઆત કરવા માટે પરીક્ષણો વચ્ચે `resetGuardrailsForTests()`નો ઉપયોગ કરો.
ખાલી રજિસ્ટ્રીથી શરૂઆત કરવા માટે `{ registerDefaults: false }` પાસ કરો અને
માત્ર પરીક્ષણ હેઠળના ગાર્ડરેલ્સની નોંધણી કરો. Vision Bridge ડિપેન્ડન્સી
ઇન્જેક્શન (`deps.getSettings`, `deps.callVisionModel`) સ્વીકારે છે; Audio Bridge
સેટિંગ્સ, ક્ષમતાઓ, STT મોડેલ પસંદગી, ક્રેડેન્શિયલ તપાસો અને ટ્રાન્સક્રિપ્શન માટે
સમકક્ષ સીમ્સ ઉપલબ્ધ કરાવે છે. તેથી પરીક્ષણો DB અથવા નેટવર્ક ઍક્સેસ વિના બંને
પ્રવાહોને ચકાસી શકે છે.

## ઇન્જેક્શન-ગાર્ડ રૂટ કવરેજ અને રેડ-ટીમ (તબક્કો 8 · બ્લૉક D)

ઇન્જેક્શન-ગાર્ડ (`createInjectionGuard` / `withInjectionGuard`) વપરાશકર્તા પ્રોમ્પ્ટ્સ
સ્વીકારતા તમામ રૂટ્સને આવરી લે છે. તે `INJECTION_GUARD_MODE`નું પાલન કરે છે (ડિફૉલ્ટ
`warn` = ફક્ત લૉગ; `block` = HTTP 400 `SECURITY_001` પરત કરે છે).

| પ્રકાર           | રૂટ્સ                                                                                                                                                | ડિફૉલ્ટ મોડ |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| ટેક્સ્ટ (હાલનું) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn        |
| જનરેટિવ          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn        |
| ડેટા             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn        |

ટેક્સ્ટ નિષ્કર્ષણ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`ને આવરી લે છે.

**રેડ-ટીમ (દરરોજ રાત્રે, `nightly-llm-security.yml`):** promptfoo ચકાસે છે કે દરેક રૂટ
`INJECTION_GUARD_MODE=block`માં OWASP-LLM કોર્પસને બ્લૉક કરે છે; garak પ્રોબ્સ ચલાવે છે
(સિક્રેટ વિના સ્કિપ કરે છે). સુસંગતતા માટે `moderations`નો સમાવેશ કરવામાં આવ્યો છે —
બ્લૉક-મોડમાં ઑપરેટર્સ `resolveDisabledGuardrails` મારફતે તેને મુક્તિ આપી શકે છે.

રાત્રિકાલીન વર્કફ્લો (`.github/workflows/nightly-llm-security.yml`, cron + મેન્યુઅલ
ડિસ્પેચ)માં બે જૉબ્સ છે:

- **`promptfoo-guard` (બ્લૉકિંગ)** — `INJECTION_GUARD_MODE=block` સાથે
  `promptfoo eval -c promptfooconfig.yaml` ચલાવે છે. દરેક પ્રતિકૂળ કેસ (દા.ત. "અગાઉની
  તમામ સૂચનાઓ અવગણો…", DAN-શૈલીના જેલબ્રેક્સ) ખાતરી કરે છે કે પ્રતિસાદમાં
  `error.code === "SECURITY_001"` હોય, એટલે કે ગાર્ડે વિનંતીને ખરેખર નકારી હતી.
- **`garak` (સલાહકારી)** — સ્થાનિક OmniRoute ઇન્સ્ટન્સ
  (`http://localhost:20128/v1`) સામે garak `--probes promptinject,dan,leakreplay`
  ચલાવે છે. તે પ્રોવાઇડર સિક્રેટ (`PROMPTFOO_PROVIDER_KEY`) પર આધારિત છે; સિક્રેટ
  ન હોય તો સરળતાથી સ્કિપ કરે છે અને તેની પાછળ `|| true` જોડાયેલું છે, તેથી તે CIને
  નિષ્ફળ કર્યા વિના રિપોર્ટ કરે છે.

ગાર્ડ હેલ્પર (`createInjectionGuard` / `withInjectionGuard`)નું કવરેજ પ્રોમ્પ્ટ ધરાવતા
દરેક `/v1` રૂટ સુધી વિસ્તરે છે; પ્રોમ્પ્ટ ટેક્સ્ટને
`src/shared/utils/inputSanitizer.ts`માંના `extractMessageContents()` દ્વારા
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`માંથી
લેવામાં આવે છે.
