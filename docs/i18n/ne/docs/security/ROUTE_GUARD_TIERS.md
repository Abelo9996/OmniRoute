## सिंहावलोकन

सबै OmniRoute व्यवस्थापन API रुटहरूलाई सुरक्षाका तीन तहहरूमध्ये एउटामा वर्गीकृत गरिएको छ। वर्गीकरण स्थिर छ, `src/server/authz/routeGuard.ts` मा परिभाषित गरिएको छ, र अन्य कुनै पनि प्रमाणीकरण शाखा चल्नुअघि मूल्याङ्कन गरिन्छ।

## तहहरू

### तह 1 — LOCAL_ONLY

**लागू गर्ने:** `isLocalOnlyPath(path)` → लूपब्याक होस्ट जाँच  
**बाइपास:** पूर्वनिर्धारित रूपमा कुनै पनि छैन। अनुरोधमा `manage` स्कोप भएको मान्य API कुञ्जी हुँदा `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मा रहेका पाथहरूका लागि सीमित अपवाद (हेर्नुहोस् [Manage-स्कोप अपवाद](#manage-scope-carve-out))।

यी रुटहरूले चाइल्ड प्रोसेसहरू सुरु गर्छन् वा रनटाइम कोड कार्यान्वयन गर्छन्। तिनलाई गैर-लूपब्याक ट्राफिकका लागि खुला गर्दा मान्य JWT प्राप्त गरेको आक्रमणकारीले (उदाहरणका लागि, Cloudflared/Ngrok टनेलमार्फत) प्रोसेस सुरु गर्न सक्छ — यो परिचित CVE वर्ग हो ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj के हो (आक्रमणको वर्ग):** व्यवस्थापन/एजेन्ट सर्भरले सबप्रोसेस सुरु गर्ने एउटा एन्डपोइन्ट खुला गर्छ (`npm install`, `node`, ब्राउजर, प्रोक्सी, `git`, `tar`, …)। यदि त्यो एन्डपोइन्ट होस्टबाहिरबाट पहुँचयोग्य छ — अपरेटरले OmniRoute लाई nginx/Cloudflare/Tailscale टनेलपछाडि राखेको र JWT लिक भएको, वा प्रमाणीकरण गलत रूपमा कन्फिगर गरिएको कारणले — आक्रमणकारीले "API कल गर्ने" कार्यलाई "होस्टमा कमाण्ड चलाउने" कार्यमा रूपान्तरण गर्छ (रिमोट कोड कार्यान्वयन)। OmniRoute ले प्रोसेस सुरु गर्न सक्ने प्रत्येक रुटमा **कुनै पनि प्रमाणीकरण जाँचअघि, बिनासर्त लूपब्याक होस्ट जाँच** लागू गरेर यसलाई रोक्छ: टनेलमार्फत लिक भएको टोकनले पनि प्रोसेस सुरु गर्ने सुविधासम्म पहुँच पाउन सक्दैन।

**पूर्ण LOCAL_ONLY समूह।** आधिकारिक स्रोत `src/server/authz/routeGuard.ts` मा रहेका `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` हुन्; तलको तालिकाले हालको अवस्थालाई प्रतिबिम्बित गर्छ। `check-route-guard-membership` गेटले प्रोसेस सुरु गर्न सक्ने प्रिफिक्सहरूअन्तर्गतका प्रत्येक `route.ts` लाई सूचीकृत गर्छ र कुनै पनि रुट स्थानीय-मात्रका रूपमा वर्गीकृत नभएमा CI असफल गराउँछ।

#### Manage-scope अपवाद

LOCAL_ONLY path हरूको एउटा subset लाई non-loopback बाट पनि access गर्न मिल्न सक्छ यदि र
केवल यदि request ले यस्तो `Authorization: Bearer <api-key>` पठाउँछ जसको
metadata मा `manage` scope (वा `admin`) समावेश छ। यो अपवादलाई
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मार्फत प्रत्येक path का लागि स्पष्ट रूपमा gate गरिएको छ, ताकि
कुनै पनि नयाँ LOCAL_ONLY path को default strict-loopback नै रहोस्। प्रमाणीकरण नगरिएका
request र non-manage key भएका request हरू अझै पनि
`403 LOCAL_ONLY` सहित अस्वीकार गरिन्छन्।

हाल bypass गर्न मिल्ने एकमात्र prefix `/api/mcp/` हो। `/api/cli-tools/runtime/` र
`/api/services/` लाई जानाजानी समावेश गरिएको छैन, किनकि तिनले मनपरी
subprocess (`npm install`, `node`) spawn गर्न सक्छन्, जुन ठ्याक्कै त्यही CVE वर्ग हो जसलाई
रोक्न LOCAL_ONLY tier बनाइएको हो।

**#7895 — `mcp:connect` सीमित scope:** `/api/mcp/` अपवादले
सीमित `mcp:connect` scope भएको Bearer key पनि स्वीकार गर्छ
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), जसलाई
`src/server/authz/policies/management.ts` मा रहेको `hasMcpConnectOrManageScope()` मार्फत जाँचिन्छ।
यो `/api/mcp/` मा मात्र सीमित छ — `mcp:connect` ले अन्य कुनै पनि
management route मा (भविष्यमा थपिएमा अन्य प्रत्येक LOCAL_ONLY bypass prefix समेत) कुनै अनुमति दिँदैन, र यसलाई जानाजानी
`MANAGEMENT_API_KEY_SCOPES` बाट अलग राखिएको छ। `manage`/`admin` भएको key ले
पहिलेजस्तै अपवाद पार गर्छ; व्यापक management access आवश्यक नपर्ने
remote MCP-only caller हरूका लागि `mcp:connect` कम privilege भएको विकल्प हो।

| Request                                           | Path                       | नतिजा                   |
| ------------------------------------------------- | -------------------------- | ----------------------- |
| Non-loopback, Bearer छैन                          | `/api/mcp/*`               | 403 LOCAL_ONLY          |
| Non-loopback, `manage` scope भएको Bearer          | `/api/mcp/*`               | अनुमति                  |
| Non-loopback, `mcp:connect` scope भएको Bearer     | `/api/mcp/*`               | अनुमति                  |
| Non-loopback, `manage`/`mcp:connect` नभएको Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY          |
| Non-loopback, `mcp:connect` scope भएको Bearer     | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY          |
| Non-loopback, `manage` scope भएको Bearer          | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY          |
| Loopback, कुनै पनि/नभएको Bearer                   | कुनै पनि LOCAL_ONLY        | अनुमति (gate पार हुन्छ) |

#### Operator मार्गदर्शन र auditing

यदि तपाईं OmniRoute लाई reverse proxy वा tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) पछाडि चलाउनुहुन्छ भने पनि loopback जाँचले माथिका spawn गर्न सक्ने
route हरूलाई सुरक्षित राख्छ — client address non-loopback भएको request लाई
`403 LOCAL_ONLY` सहित **auth चल्नुअघि नै** अस्वीकार गरिन्छ, त्यसैले leak भएको JWT ले spawn सम्म पहुँच पाउन सक्दैन। अझै दुईवटा
operator जिम्मेवारी बाँकी रहन्छन्:

- **क्लाइन्ट IP लाई लूपब्याकका रूपमा नक्कली बनाएर 403 लाई "ठीक" नगर्नुहोस्।**
  `X-Forwarded-For: 127.0.0.1` सेट गर्दा, वा स्रोत ठेगानालाई
  लूपब्याकमा पुनर्लेखन गर्ने प्रोक्सी प्रयोग गर्दा, यस तहले बन्द गर्ने ठीक त्यही RCE वर्ग पुनः खुल्छ। प्रोक्सीमार्फत
  ड्यासबोर्ड/API लाई उपलब्ध गराउनुहोस् — spawn गर्न सक्ने रुटहरूलाई कहिल्यै होइन।
- **manage-scope बाइपासलाई न्यूनतम राख्नुहोस्।** केवल `/api/mcp/` लाई बाइपास गर्न सकिन्छ, र
  त्यो पनि `manage`-स्कोप भएको API कुञ्जीबाट मात्र। `SPAWN_CAPABLE_PREFIXES` लाई
  बाइपास सूचीमा कहिल्यै थप्न सकिँदैन — zod स्किमाले तिनलाई अस्वीकार गर्छ र
  `isLocalOnlyBypassableByManageScope` ले रनटाइममा तिनलाई निषेध गर्छ (गहन प्रतिरक्षा),
  जसलाई ड्यासबोर्डले "बाइपासयोग्य बनाउन सकिँदैन" भनेर जनाउँछ। सोही
  निषेध-सूचीमा spawn नगर्ने तर टाढाबाट कहिल्यै पहुँचयोग्य हुनु नहुने केही LOCAL_ONLY रुटहरू पनि छन् —
  `/api/oauth/kiro/auto-import` (होस्ट-स्थानीय Kiro
  क्रेडेन्सियल फाइलहरू पढ्छ), `/api/discovery/` र `/api/issue-agent/`। रनटाइम
  स्न्यापसट लोडरले भण्डारित सेटिङ्स पङ्क्तिबाट पनि यस्ता प्रविष्टिहरू हटाउँछ, र
  पुरानो JSON आयात (`/api/settings/import-json`) ले बाइपास कुञ्जीहरू कहिल्यै लेख्दैन।
  प्रत्येक `LOCAL_ONLY_API_PREFIXES` प्रविष्टि या त निषेध-सूचीमा हुनुपर्छ वा
  बाइपास-योग्यताका लागि समीक्षा गरिएको हुनुपर्छ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)। `/api/providers/` अन्तर्गतका डायनामिक-सेगमेन्ट
  र स्थिर-पाथ भएका spawn-सक्षम रुटहरू (जस्तै `/login`,
  `/refresh-cursor`) लाई
  `src/shared/constants/spawnCapablePrefixes.ts` मा रहेको regex-आधारित `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` सहायकले समेट्छ,
  समतल `SPAWN_CAPABLE_PREFIXES` एरेले होइन — तिनलाई समेट्न समतल एरेले
  सम्पूर्ण `/api/providers/` प्रिफिक्स समेट्नुपर्ने हुन्थ्यो, जसले
  दूरस्थ ड्यासबोर्डहरूले प्रदायक CRUD का लागि वैध रूपमा प्रयोग गर्ने रुट ट्रीलाई अनावश्यक रूपमा अति-विस्तृत बनाउँथ्यो।

**पहुँचको अडिट** — होस्टबाहिरबाट कुनै पहुँच यी रुटहरूसम्म पुगिरहेको छैन भन्ने प्रमाणित गर्न:

- `/dashboard/settings/security` मा रहेको **प्राधिकरण सूची** खोल्नुहोस्: यसले
  सक्रिय LOCAL_ONLY प्रिफिक्स सूची, कुन-कुन प्रिफिक्स बाइपासयोग्य छन्, र कम्पाइल-टाइम
  spawn-सक्षम ("बाइपासयोग्य बनाउन सकिँदैन") सेट रेन्डर गर्छ।
- माथिका प्रिफिक्सहरूसँग गैर-लूपब्याक क्लाइन्ट ठेगाना जोडिएका प्रविष्टिहरूका लागि आफ्नो रिभर्स-प्रोक्सी / पहुँच लगहरूमा खोज्नुहोस्।
  `403 LOCAL_ONLY` को सट्टा `200` फर्काएको त्यस्तो कुनै पनि हिटको अर्थ प्रोक्सीले वास्तविक क्लाइन्ट IP लुकाइरहेको छ —
  प्रोक्सी ठीक गर्नुहोस्।
- यी पाथमध्ये कुनै एउटाका लागि OmniRoute का लगहरूमा आएको `403 LOCAL_ONLY` भनेको गार्डले
  अभिप्रेत रूपमा काम गरिरहेको हो, दबाउनुपर्ने त्रुटि होइन।

### तह 2 — ALWAYS_PROTECTED

**यसद्वारा लागू गरिएको:** `isAlwaysProtectedPath(path)` → `requireLogin=false` बाइपास छोड्नुहोस्
**बाइपास:** `requireLogin=false` हुँदा कुनै पनि छैन; JWT सधैँ आवश्यक हुन्छ

यी रुटहरू विनाशकारी वा अपरिवर्तनीय छन्। "पासवर्ड-रहित"
इन्स्टलमा तिनलाई अनुमति दिनुको अर्थ एउटै LAN मा रहेका जोसुकैले पनि डेटाबेस मेटाउन वा
सर्भर प्रक्रिया बन्द गर्न सक्नु हो।

| पाथ                                       | कारण                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| `/api/shutdown`                           | सर्भर प्रक्रिया अन्त्य गर्छ                                                |
| `/api/settings/database`                  | डेटाबेस निर्यात, आयात र मेटाउने कार्य                                      |
| `/api/db-backups`                         | पूर्ण डेटाबेस ब्याकअप अभिलेखमा पहुँच                                       |
| `/api/settings/export-json`               | पूर्ण सेटिङ्स ब्लब निर्यात गर्छ (गोप्य जानकारीसहित)                        |
| `/api/settings/import-json`               | पूर्ण सेटिङ्स ब्लब प्रतिस्थापन गर्छ                                        |
| `/api/providers/health-autopilot/actions` | अटोपाइलट सुधारात्मक कार्यहरू कार्यान्वयन गर्छ                              |
| `/api/settings/obsidian`                  | कुनै पनि भल्ट रुटका लागि पुनः प्रयोगयोग्य WebDAV क्रेडेन्सियल सिर्जना गर्छ |

**उल्लङ्घन हुँदा प्रतिक्रिया:** `401 Authentication required`

`/api/settings/obsidian` ले यसको `/webdav` चाइल्डलाई समेट्छ: `POST` ले WebDAV फाइल सेवालाई —
जुन यस पाइपलाइनबाहिर, Next.js भन्दा अघि कस्टम Node तहद्वारा सेवा गरिन्छ — कलरले रोजेको रुटमा
निर्देश गर्छ र भर्खरै सिर्जना गरिएका Basic क्रेडेन्सियलहरू प्रतिध्वनित गर्छ, `DELETE` ले तिनलाई परिवर्तन गर्छ, र प्यारेन्ट `POST` ले
Obsidian REST API टोकन भण्डारण गर्छ। GHSA-62vw ले `GET` पासवर्ड प्रकटीकरणलाई मात्र लुकाएको थियो; जारी गर्ने कार्य
अझै पनि fail-open तहमा थियो (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ले
डेटा डाइरेक्टरी नै भएको, त्यसको भित्र रहेको, वा त्यसलाई समेट्ने भल्टलाई थप रूपमा अस्वीकार गर्छ।

#### क्रेडेन्सियल निर्यातहरू अपरेटरका लागि मात्र हुन्

माथिको तहले केवल _कुनै_ क्रेडेन्सियल आवश्यक छ कि छैन भन्ने निर्णय गर्छ। भण्डारित
क्रेडेन्सियलहरू डाउनलोड गर्ने रुटहरूले ह्यान्डलरमा दोस्रो जाँच थप्छन्: `GET /api/settings/export-json` (डिक्रिप्ट गरिएका
प्रदायक जडानहरू र कच्चा API कुञ्जीहरू), `GET /api/db-backups/export` (SQLite फाइल) र
`GET /api/db-backups/exportAll` (पूर्ण अभिलेख) ले `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`) कल गर्छन्। यसले ड्यासबोर्ड सेसन, स्थानीय CLI subject, वा
लगइन निष्क्रिय गरिएको इन्स्ट्यान्स स्वीकार गर्छ, र कुनै पनि स्कोपका API कुञ्जीहरू (`manage`
र `admin` सहित) तथा `oma_` पहुँच टोकनहरूलाई `403` जवाफ दिन्छ। सिंक टोकन जारी गर्ने कार्य (`POST /api/sync/tokens`) ले
विश्वसनीय लूपब्याक आन्तरिक-सेवा टोकनसहित सोही सहायक प्रयोग गर्छ।

### नयाँ इन्स्टलको बुटस्ट्र्याप लूपब्याकका लागि मात्र हो — `Host` होइन, वास्तविक peer अनुसार

कुनै व्यवस्थापन पासवर्ड कन्फिगर नगरिएको (र `INITIAL_PASSWORD` पनि नभएको) अवस्थामा,
`src/shared/utils/apiAuth.ts` मा रहेको `isAuthRequired()` ले अज्ञात बुटस्ट्र्यापलाई **लूपब्याक peer का लागि मात्र**
खुला राख्छ। लूपब्याकको निर्णय विश्वसनीय peer सङ्केतहरूबाट यस क्रममा गरिन्छ: टोकनले छाप लगाएको वास्तविक TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, नीतिले देख्ने कुरा), पाइपलाइनको आफ्नै
`AUTHZ_HEADER_PEER_LOCALITY` निर्णय (रुट ह्यान्डलरहरूले देख्ने कुरा, `OMNIROUTE_PEER_STAMP_TOKEN` सेट भएको बेलामा मात्र
विश्वसनीय), वा प्रत्यक्ष कलरहरूका लागि वास्तविक सकेट peer। `Host` /
`nextUrl.hostname` लाई कहिल्यै हेरिँदैन, र पहिलो-पासवर्ड लेख्ने कार्य
(`POST /api/settings/require-login`) प्रत्येक
नेटवर्क peer का लागि खुला नराखी सोही प्रतिबन्धअन्तर्गत राखिन्छ (GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ले आफ्नो `peerContext` निर्णय
स्पष्ट रूपमा तल पठाउँछ, त्यसैले ORIGINAL (हटाउनुअघिको) अनुरोधका हेडरहरूले कहिल्यै यसको निर्णय गर्दैनन्।

### तह 3 — MANAGEMENT (पूर्वनिर्धारित)

अन्य सबै व्यवस्थापन रुटहरू। `requireLogin=false` कन्फिगर गरिएको अवस्थामा बाहेक प्रमाणीकरण आवश्यक हुन्छ। CLI टोकनहरूले यी रुटहरूमा प्रमाणीकरण गर्न सक्छन् (लुपब्याक + मान्य HMAC)।

## मूल्याङ्कन क्रम

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → अर्को चरणमा जाने
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → अनुमति दिने (management_key)
     → अन्यथा                                    → अस्वीकार गर्ने 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → अनुमति दिने (system)
  3. hasValidCliToken(headers)?
     → अनुमति दिने (cli) [loopback + timingSafeEqual HMAC जाँच]
  4. isAlwaysProtectedPath(path) वा requireLogin=true?
     → isDashboardSessionAuthenticated?
        → अनुमति दिने (dashboard_session)
     → बाइपास गर्न नमिल्ने पथमा manage-scope Bearer?
        → अनुमति दिने (management_key)
     → अस्वीकार गर्ने 401/403
  5. requireLogin=false?
     → अनुमति दिने (anonymous)
```

चरण 1 को manage-scope शाखा नै LOCAL_ONLY रुटलाई पूरा गर्न सक्ने एकमात्र प्रमाणीकरण गरिएको पथ हो; auth-backend विफलता मोडले 503 (403 होइन) फर्काउँछ, ताकि म्याद सकिएको DB चुपचाप "अस्वीकार" मा अवनत नहोस्।

## नयाँ spawn-सक्षम रुट थप्ने

1. `src/server/authz/routeGuard.ts` मा रहेको `LOCAL_ONLY_API_PREFIXES` मा path prefix थप्नुहोस्
2. नयाँ prefix का लागि `isLocalOnlyPath()` ले true फर्काउँछ भनी पुष्टि गर्ने परीक्षण
   `tests/unit/authz/routeGuard.test.ts` मा थप्नुहोस्
3. **यो चरण कहिल्यै नछोड्नुहोस्** — `CLAUDE.md` मा रहेको Hard Rule #15 हेर्नुहोस्
4. निर्णय गर्नुहोस्: के यो रुट `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मा पनि पर्छ?
   पूर्वनिर्धारित उत्तर **होइन** हो। रुटलाई manage-scope धारकका लागि उपलब्ध गराउन सुरक्षित
   हुँदा मात्र opt-in गर्नुहोस् (अर्थात्, यसले प्रयोगकर्ताद्वारा नियन्त्रित मनमानी code spawn गर्दैन)।

## manage-scope-bypassable path थप्ने

1. रुटले प्रयोगकर्ताले उपलब्ध गराएको code वा command कार्यान्वयन गर्दैन भनी पुष्टि गर्नुहोस्। यदि
   गर्छ भने, रोक्नुहोस् — यो carve-out त्यसका लागि सही उपाय होइन।
2. `src/server/authz/routeGuard.ts` मा रहेको
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` मा prefix थप्नुहोस्
3. `tests/unit/authz/management-policy.test.ts` मा सबै चार
   request स्वरूपका लागि coverage थप्नुहोस्: Bearer नभएको (403), manage Bearer (allow), non-manage Bearer
   (403), र manage Bearer हुँदा पनि `/api/cli-tools/runtime/*`
   strict-loopback नै रहने प्रति-prefix regression।

## OpenAPI मा सुरक्षा tiers अभिलेखीकरण गर्ने

`docs/openapi.yaml` मा नयाँ रुट थप्दा, यदि रुटलाई `routeGuard.ts` ले वर्गीकृत गरेको छ भने सम्बन्धित
vendor extension लागू गर्नुहोस्:

| routeGuard.ts वर्गीकरण                 | YAML annotation            | प्रवर्तन                                                   |
| -------------------------------------- | -------------------------- | ---------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`              | `x-loopback-only: true`    | non-loopback बाट निःसर्त रूपमा अवरुद्ध                     |
| `ALWAYS_PROTECTED_API_PATHS`           | `x-always-protected: true` | `requireLogin=false` हुँदा पनि auth आवश्यक                 |
| आन्तरिक admin/debug रुट                | `x-internal: true`         | पूर्वनिर्धारित रूपमा /dashboard/api-endpoints बाट लुकाइएको |
| कुनै पनि होइन (public / standard auth) | (annotation आवश्यक छैन)    | मानक `requireLogin`-नियन्त्रित पहुँच                       |

### प्रमाणीकरण

दुई scripts ले YAML annotations र `routeGuard.ts` बीचको एकरूपता लागू गर्छन्:

- `scripts/check/check-openapi-coverage.mjs` — coverage < 99% भएमा असफल हुन्छ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` वा
  `x-always-protected` annotations compile-time constants सँग नमिलेमा असफल हुन्छ

दुवै scripts pre-commit hook र CI मा चल्छन्।

### False Positive नियम

यदि `routeGuard.ts` constant मा नभएको रुटमा `x-always-protected` वा `x-loopback-only`
annotation गरिएको छ भने coverage script असफल हुन्छ। समाधान भनेको YAML लाई
`routeGuard.ts` ले वास्तवमै लागू गर्ने कुरासँग मिलाउनु हो — enforcement logic पनि कार्यान्वयन नगरी
`routeGuard.ts` मा रुटहरू थप्नु होइन।
