> **อัปเดตล่าสุด:** 2026-08-29 — v3.8.51 (ที่มาของทรานสคริปต์ Video Bridge ถูกประกาศโดยผู้เรียก
> และยังไม่ได้รับการตรวจสอบโดยเซิร์ฟเวอร์ — ชี้แจงตาม #11661)

Guardrails บังคับใช้มาตรการด้านความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขต
ระหว่าง OmniRoute กับผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และ
เลือกที่จะปฏิเสธ แปลง หรือใส่คำอธิบายประกอบ) เพย์โหลดคำขอ (`preCall`) และ
การตอบกลับจากต้นทาง (`postCall`)

ระบบนี้เป็นแบบ **fail-open**: หาก Guardrail เกิดข้อผิดพลาดขณะทำงาน รีจิสทรี
จะบันทึกข้อผิดพลาดและดำเนินการต่อด้วย Guardrail ตัวถัดไป แทนที่จะทำให้
คำขอล้มเหลว การบล็อกต้องเกิดจากการตัดสินใจอย่างชัดเจน (`block: true`) ไม่ใช่เหตุบังเอิญ

### บริดจ์การมองเห็น (`visionBridge.ts`) — บริดจ์โมดัลลิตี PR-1

ดักจับคำขอที่มีรูปภาพและมุ่งไปยัง **โมเดลที่ไม่รองรับการมองเห็น** จากนั้น
เปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับการมองเห็น หรือแทนที่ส่วนรูปภาพ
ด้วยคำอธิบายข้อความที่สร้างโดยโมเดลการมองเห็นซึ่งกำหนดค่าได้ ก่อนเรียกใช้
อัปสตรีม ซึ่งทำให้ผู้ให้บริการที่รองรับเฉพาะข้อความสามารถจัดการเพย์โหลด
แบบหลายโมดัลได้อย่างโปร่งใส

โฟลว์:

1. ข้ามหากโมเดลเป้าหมายรองรับการมองเห็นอยู่แล้ว (เว้นแต่โมเดลนั้นปรากฏใน
   รายการบังคับใช้บริดจ์ `isVisionBridgeForcedModel`)
2. แยกส่วนรูปภาพผ่าน `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) ซึ่งมอบหมายให้ **ตัวตรวจจับสื่อแบบรวมศูนย์**
   `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — แหล่งข้อมูลจริง
   เพียงแห่งเดียวที่ใช้ร่วมกับตัวกรองความเข้ากันได้ของคอมโบ
   การแยกจะใช้รายการที่อนุญาตเฉพาะส่วนระดับบนสุดซึ่งมีรูปแบบที่
   `replaceImageParts` สามารถแทรกกลับได้ (สัญญา extract↔replace): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` และ Responses API `input_image` รายการที่ตรวจพบแบบซ้อน
   และรูปแบบที่เป็นเพียงตัวบ่งชี้เป็นข้อมูลสำหรับตัวกรองคอมโบ และจะไม่ถูกแยก
   ข้ามหากไม่พบรายการใด
3. หาค่าคอนฟิกรันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่า
   `modalityBridge*` ใหม่มีลำดับเหนือกว่า ส่วนคีย์ `visionBridge*` เดิมยังคงเป็น
   **ทางเลือกสำรองหนึ่งรอบ** (ช่วงเวลาสำหรับย้อนกลับ) ข้ามก่อนการไล่ตรวจสอบสื่อ
   ใด ๆ เมื่อปิดใช้งานบริดจ์
4. ตัวเลือกโหมด (`modalityBridgeVisionMode` ดูตารางด้านล่าง) จะตัดสินใจระหว่าง
   การเปลี่ยนเส้นทางกับการสร้างคำอธิบาย การเปลี่ยนเส้นทางจะส่งคืน
   `modifiedPayload` โดยสลับเฉพาะ `model` พร้อมเมตา
   `{ rerouted, fromModel, toModel, imagesKept }`
5. เส้นทางการสร้างคำอธิบาย: จำกัดรูปภาพไว้ที่ `maxImages` สร้างพรอมต์ที่รับรู้
   บริบทของงาน ตรวจสอบแคชคำอธิบาย เรียกโมเดลการมองเห็น **แบบขนาน**
   (`Promise.allSettled`) และแทรกส่วนข้อความ `[Image N]: <description>` แทนที่
   รูปภาพเหล่านั้น การสร้างคำอธิบายที่ล้มเหลวจะให้ค่า `null` และส่วนรูปภาพเดิม
   จะถูก **เก็บรักษาไว้** (#4012) — ยกเว้นในเส้นทางการสร้างคำอธิบายของคอมโบ
   เมื่อการสร้างคำอธิบายทั้งหมดล้มเหลว ซึ่งอัปสตรีมที่ยืนยันแล้วว่าไม่รองรับ
   การมองเห็นจะได้รับข้อความแทน
   `(unavailable — no vision-capable provider connected)` (#8430)
6. ส่งคืน `modifiedPayload` + เมตา (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`)

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| โหมด       | ค่าเริ่มต้น | พฤติกรรม                                                                                                                                                                                                                                                                               |
| ---------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔           | ฮิวริสติกเดิมโดยไม่มีการเปลี่ยนแปลง (#6640/#7204): โมเดลที่ไม่ใช่คอมโบ/`auto/` จะเปลี่ยนเส้นทางไปยังโมเดลการมองเห็นที่ดีที่สุด เว้นแต่โมเดลเดิมมีข้อมูลประจำตัวที่ใช้งานได้อยู่แล้ว (ในกรณีนั้นจะสร้างคำอธิบาย) ส่วนเป้าหมายคอมโบจะสร้างคำอธิบายเสมอ                                   |
| `describe` |             | สร้างคำอธิบายเสมอ — ข้ามบล็อกการเปลี่ยนเส้นทางทั้งหมด โดยโมเดลที่ผู้ใช้เลือกจะเป็นผู้ตอบเสมอ                                                                                                                                                                                           |
| `reroute`  |             | บังคับเปลี่ยนเส้นทาง: ข้ามตัวป้องกันการคงโมเดลที่มีข้อมูลประจำตัวไว้ ตัวป้องกันข้อมูลประจำตัวของ **เป้าหมาย** การเปลี่ยนเส้นทางยังคงมีผล — เมื่อไม่มีเป้าหมายการมองเห็นที่ใช้งานได้ คำขอจะเปลี่ยนไปใช้การสร้างคำอธิบาย เพื่อไม่ให้รูปภาพดิบไปถึงแบ็กเอนด์ที่รองรับเฉพาะข้อความ (#8430) |

โหมดที่บังคับจะลัดวงจร **ก่อน** ที่ฮิวริสติกอัตโนมัติจะทำงาน พฤติกรรมของ `auto`
จะเหมือนกับกลไกป้องกันก่อน PR-1 ทุกไบต์

#### ขอบเขตคีย์ API (`visionBridgeKeyScope.ts`)

เมื่อคีย์ API ของผู้เรียกจำกัด `allowedConnections` พูลโควตา
(`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) บริดจ์จะเลือก
เฉพาะโมเดลสำหรับเปลี่ยนเส้นทางและสร้างคำอธิบายที่คีย์ดังกล่าวมีสิทธิ์ใช้
บนการเชื่อมต่อที่คีย์นั้นมีสิทธิ์ใช้ จากนั้นการเรียกเพื่อสร้างคำอธิบายจะผ่าน
การวนกลับเข้าตัวเองของ OmniRoute เสมอ พร้อมส่วนหัว
`x-omniroute-self-loop-key-id` เพื่อให้คำขอแชตที่รับเข้ามาบังคับใช้นโยบาย
การเชื่อมต่อและโมเดลของคีย์นั้นอีกครั้ง `enforceApiKeyPolicy()`
จะยอมรับส่วนหัวดังกล่าวเมื่อใช้ร่วมกับ bearer ของการวนกลับเข้าตัวเองเท่านั้น
จึงทำได้เพียงจำกัดสิทธิ์ให้แคบลง และ id ที่ไม่สามารถแก้ไขได้จะถูกปฏิเสธ

หากไม่มีโมเดลการมองเห็นที่คีย์ได้รับอนุญาต เส้นทางการสร้างคำอธิบายจะไม่เข้า
แทรกแซง และคำขอจะผ่านไปโดยไม่มีการเปลี่ยนแปลง ซึ่งเป็นพฤติกรรมแบบเปิดให้ผ่าน
เมื่อเกิดความล้มเหลวเช่นเดียวกับกลไกป้องกันที่ถูกปิดใช้งาน (เมตา
`{ skipped: true, reason: "no_permitted_vision_model" }`)
คำขอที่ไม่มีคีย์และคีย์ที่ไม่มีข้อจำกัดเหล่านี้จะมีพฤติกรรมเหมือนเดิมทุกประการ

#### พรอมต์สร้างคำอธิบายที่รับรู้บริบทของงาน (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้นคือ **true** `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะผนวก
ข้อความจาก **ข้อความล่าสุดของผู้ใช้** (ตัดให้เหลือไม่เกิน 500 อักขระ) เข้ากับพรอมต์
อธิบายพื้นฐาน เพื่อชี้นำคำอธิบายให้ตรงกับสิ่งที่ผู้ใช้ถามจริง
(รูปแบบ codex-vision-proxy) และขอให้โมเดลวิทัศน์ถอดข้อความที่มองเห็น
เมื่อปิดแฟล็กนี้ — หรือไม่มีข้อความจากผู้ใช้ — ระบบจะใช้พรอมต์พื้นฐานโดยไม่มีการเปลี่ยนแปลง

คำขอที่เข้ากันได้กับ OpenAI ของ describe self-loop (`callVisionModelSingle()`
ใน `visionBridgeHelpers.ts`) จะร้องขอ `image_url.detail: "high"` เสมอ —
โดยไม่มีเงื่อนไข สำหรับผู้เรียก/ผู้ให้บริการทุกราย และไม่ขึ้นกับสัญญาณใดๆ จากไคลเอนต์
การสุ่มตัวอย่างแบบรายละเอียดต่ำทำให้ความแม่นยำของ OCR ลดลงสำหรับงานถอดข้อความ
ที่พรอมต์นี้ร้องขอโดยตรง ดังนั้นคำขอ describe เองจึงขอรายละเอียดสูงเสมอ
ไม่ว่าคำขอขาเข้าดั้งเดิมจะใช้ระดับรายละเอียดใดก็ตาม การตั้งค่านี้มีผลเฉพาะกับเนื้อหา
คำขอ describe ภายในเท่านั้น และไม่เปลี่ยนวิธีที่ OmniRoute ส่งต่อ
`image_url.detail` ของผู้เรียกในคำขอหลัก — ค่าเริ่มต้นดังกล่าวจะถูกใช้แยกต่างหาก
และใช้เฉพาะกับไคลเอนต์ OpenCode ที่ตรวจพบเท่านั้น ใน `defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`) ส่วนแขนงรูปแบบสายสัญญาณ Anthropic
ของ describe self-loop ไม่มีฟิลด์ `detail` และไม่ได้รับผลกระทบจากค่าเริ่มต้นทั้งสองแบบ

#### ขีดจำกัดเอาต์พุตของ describe (`modalityBridgeVisionMaxChars`)

| คีย์                           | ค่าเริ่มต้น | ช่วง               |
| ------------------------------ | ----------- | ------------------ |
| `modalityBridgeVisionMaxChars` | `0`         | `0` หรือ 100–50000 |

`0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งคืนโดย
`callVisionModel()` จะถูกส่งผ่านโดยไม่มีการแก้ไข เพื่อคงลักษณะการทำงานเดิมไว้
ค่าใดๆ ในช่วง 100–50000 จะตัดคำอธิบายและเติมส่วนต่อท้าย `…`
ก่อนนำกลับไปแทรกในรูปแบบ `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`)
ให้เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมาก ซึ่งโมเดลปลายทางต้องใช้ข้อความถอดเสียง
ทั้งหมด หรือลดค่าเพื่อจำกัดการใช้โทเค็นของโมเดลวิทัศน์ที่ให้คำอธิบายยืดยาว
ฟิลด์ในแดชบอร์ดอยู่ในแผง Advanced ของแท็บ Vision
(`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจะปรับค่าใดๆ
ระหว่าง 1 ถึง 99 ขึ้นเป็นค่าต่ำสุด 100 โดยคงค่า `0` ที่ระบุอย่างชัดเจนไว้ —
`0` เป็นค่า Zod ที่ถูกต้องในตัวเอง
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) ไม่ใช่เพียง
ค่าเริ่มต้นสำหรับสถานะ "ไม่ได้ตั้งค่า"

#### แคชของ describe (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำ ซึ่งใช้ร่วมกันทั่วทั้งโปรเซส

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

สกัดกั้นคำขอแชตที่มีเสียงก่อนที่จะไปถึงเป้าหมายซึ่งไม่เป็นที่ทราบว่ารองรับ
อินพุตเสียง โดยจะไม่เปลี่ยนเส้นทางคำขอแชตแต่อย่างใด ส่วนเสียงจะถูกถอดเสียงผ่าน
เอนด์พอยต์ multipart ที่เข้ากันได้กับ OpenAI ซึ่งมีอยู่แล้ว และโมเดลแชตที่เลือก
จะทำงานต่อด้วยข้อความถอดเสียง

ลำดับการทำงาน:

1. แก้ค่า `supportsAudio` ผ่าน `getResolvedModelCapabilities()` เมทาดาทา
   ของรีจิสทรีผู้ให้บริการที่ระบุอย่างชัดเจนมีลำดับความสำคัญสูงสุด ตามด้วยเมทาดาทาโมเดลแบบคงที่ แล้วจึงเป็น
   `modalities_input` ที่ซิงค์มา รายการอินพุตที่ประกาศไว้แต่ไม่มี `audio` จะเป็น `false`
   หากไม่มีหลักฐานด้านความสามารถ ค่าจะยังคงเป็น `null` ทั้ง `false` และ `null` จะเปิดใช้
   บริดจ์แบบระมัดระวัง ขณะที่ `true` จะข้ามบริดจ์
2. แก้ค่าการตั้งค่า `modalityBridgeAudio*` และแยกส่วนเสียงระดับบนสุด
   ที่สามารถตัดต่อได้จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่ใช้ร่วมกัน
   รูปแบบข้อมูลผ่านสายที่รองรับ ได้แก่ `input_audio` ของ OpenAI, `audio_url` และ
   `source.media_type: "audio/*"` ระบบตรวจพบเสียงที่ซ้อนอยู่ภายในเพื่อใช้กำหนดเส้นทาง แต่จะไม่
   นำออกผ่านเส้นทางการตัดต่อ ปริมาณงานถูกจำกัดด้วย `modalityBridgeAudioMaxClips`
   ส่วนที่อยู่ถัดจากขีดจำกัดจะยังคงไม่ถูกแก้ไข
3. ใช้ `provider/model` ที่กำหนดค่าไว้ หรือให้ `selectAudioBridgeModel()` ไล่ดู
   `AUDIO_TRANSCRIPTION_PROVIDERS` ตามลำดับแค็ตตาล็อกที่คงที่ และเลือกโมเดลแรก
   ที่มีข้อมูลรับรองผู้ให้บริการซึ่งเปิดใช้งานอยู่และสามารถใช้งานได้
4. `callAudioTranscription()` แปลงเสียงแบบ base64/data-URI เป็น `file`
   แบบ multipart หรือดาวน์โหลด `audio_url` ระยะไกลผ่านกลไกป้องกันขาออกที่อนุญาตเฉพาะ
   สาธารณะ พร้อมการตรึง DNS และขีดจำกัด 25 MB จากนั้นจะ POST ไฟล์และโมเดลที่เลือก
   ไปยังลูปกลับเข้าตัวเองภายในเครื่อง `/v1/audio/transcriptions` โดยตรวจสอบสิทธิ์ด้วย
   `resolveSelfLoopBearer()` เส้นทางการถอดเสียงที่มีอยู่จะดำเนินการค้นหา
   ข้อมูลรับรอง การจัดการช่วงพัก/ขีดจำกัดอัตรา และการส่งต่อไปยังผู้ให้บริการตามปกติ
5. การเรียกที่สำเร็จจะแทนที่ส่วนดังกล่าวด้วย `[Audio N]: <transcript>` การเรียก
   ทำงานด้วย `Promise.allSettled` โดยความล้มเหลวแต่ละรายการจะคงส่วนเสียงต้นฉบับนั้นไว้
   (#4012 contract) หากทุกการเรียกล้มเหลวและพิสูจน์แล้วว่าเป้าหมายมี
   `supportsAudio === false` ส่วนเหล่านั้นจะกลายเป็น
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 contract) สำหรับ
   เป้าหมายที่ไม่ทราบสถานะ (`null`) ผลลัพธ์ที่ล้มเหลวทั้งหมดจะยังคงไม่ถูกแก้ไข เป้าหมาย
   ที่พิสูจน์แล้วว่ารองรับเฉพาะข้อความและไม่มีข้อมูลรับรอง STT ที่ใช้งานได้ จะได้รับข้อความแทน
   แบบชัดเจนเดียวกันโดยไม่มีการเรียกเครือข่าย

ข้อความถอดเสียงที่สำเร็จจะใช้แคช LRU/TTL ของ Modality Bridge ที่ใช้ร่วมกันทั้งโปรเซส
คีย์ประกอบด้วยการอ้างอิงเสียง ป้ายกำกับการดำเนินการ `audio-transcription` ที่คงที่
และโมเดล STT ที่เลือก ความล้มเหลวจะไม่ถูกแคช ความพยายามประมวลผลเสียงจะอัปเดต
ตัวนับ `bridged`, `cacheHits`, `failures` และ `lastUsedAt` ที่ใช้ร่วมกัน
การตอบสนองที่ผ่านการแปลงจะมี
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ส่วนคำขอ
ที่ไม่ถูกแก้ไขจะไม่ได้รับเซกเมนต์ Audio Bridge

การตั้งค่ารันไทม์ได้รับการสนับสนุนโดย DB และตรวจสอบความถูกต้องด้วย Zod:

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) รับผิดชอบการไล่ตรวจสอบคำขอ

งานต่อวิดีโอ ได้แก่ การรับข้อมูล แคชผลลัพธ์ทั้งหมด การอธิบายลำดับเฟรม
(ซึ่งรวมทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้ หากมี) และเมตริก/การยกเลิก/การล้างข้อมูล
ของแต่ละครั้งที่พยายามดำเนินการ จะถูกซ่อนไว้เบื้องหลัง `processVideoPart` ใน
`videoBridgePipeline.ts` ซึ่งถูกเรียกหนึ่งครั้งต่อส่วนวิดีโอภายในลูปของ `preCall`
โมดูลดังกล่าวยังกำหนดขอบเขตพอร์ตอย่างชัดเจน ได้แก่ `VideoMediaBrokerPort`
(การรับไบต์และแยกเฟรมตัวอย่าง), `VideoAudioTranscriptionPort`
(การรวมทรานสคริปต์เสียงที่ผู้เรียกประกาศไว้กับคำบรรยายของเฟรมตัวอย่าง) และ
`VideoDrilldownPort` (ขอบเขตการจัดเก็บข้อมูลการเจาะลึกเฟรม ซึ่งยังไม่ได้เชื่อมต่อ
เข้ากับ `processVideoPart` — ปัจจุบันมีเพียงเส้นทาง `/api/modality-bridge/video/drilldown`
แยกต่างหากที่เขียนรายการการเจาะลึก)

เส้นทางคำขอสาธารณะ `/v1` จะไม่นำเข้าหรือเรียกใช้กระบวนการย่อย
วิดีโอระยะไกลจะถูกดาวน์โหลดภายใต้ขีดจำกัด 50 MiB ส่วนวิดีโอ base64 แบบอินไลน์มี
ขีดจำกัดขนาดหลังถอดรหัสต่อวิดีโอที่เข้มงวดเป็น 36 MiB เพื่อให้เอนเวโลปของ
โมเดล/ข้อความ/การจัดเฟรมยังคงอยู่ภายในขีดจำกัดการรับคำขอ JSON สาธารณะที่ 50 MiB
ความยาวแบบอินไลน์และค่าประมาณขนาดหลังถอดรหัสจะถูกตรวจสอบก่อนจัดสรรหน่วยความจำ
URL ระยะไกลเริ่มต้นและทุกการเปลี่ยนเส้นทางต้องใช้ HTTPS โดยใช้กลไกป้องกันการส่งออก
เฉพาะสาธารณะที่มีอยู่พร้อมการตรึง DNS จากนั้นไบต์จะข้ามขอบเขตโบรกเกอร์ภายในที่แน่นอน
`POST /api/modality-bridge/video/extract` เส้นทางดังกล่าวเป็นทั้ง
`LOCAL_ONLY` และ `SPAWN_CAPABLE` ยอมรับเฉพาะคำขอที่ผ่านการรับรองความถูกต้อง
เฉพาะต่อกระบวนการและมาจากลูปแบ็กที่เชื่อถือได้ และจะไม่ยอมรับ URL, พาธระบบไฟล์,
ไฟล์ปฏิบัติการ หรือรายการอาร์กิวเมนต์โดยเด็ดขาด ไปป์ไลน์จำกัดขนาดเนื้อความของ API
และตัวอ่านเนื้อความแบบเพิ่มทีละส่วนของตัวจัดการ ต่างก็บังคับใช้ขีดจำกัดอินพุตโบรกเกอร์
ที่ 50 MiB อย่างเป็นอิสระ คิวแบบมีขอบเขตจะดำเนินการแยกข้อมูลครั้งละหนึ่งงาน
อนุญาตให้มีงานรอดำเนินการสี่งาน และจำกัดอินพุตที่รอดำเนินการไว้ที่ 100 MiB

ภายในโบรกเกอร์ `ffprobe` จะอ่านไฟล์ภายในแบบส่วนตัว รายการรูปแบบที่อนุญาตแบบตายตัว
จะไม่รวมรูปแบบเพลย์ลิสต์และแมนิเฟสต์ สำหรับคอนเทนเนอร์ตระกูล MOV ที่อนุญาต
การอ้างอิงข้อมูล MOV ภายนอกจะยังคงถูกปิดใช้งานโดยค่าเริ่มต้น และคำสั่งแบบตายตัว
จะไม่เลือกเปิดใช้คุณสมบัติดังกล่าว ทั้ง `ffprobe` และ `ffmpeg` ใช้รายการโปรโตคอล
ที่อนุญาตเฉพาะ `file` หนึ่งเธรด อาร์เรย์อาร์กิวเมนต์แบบตายตัว ไม่ใช้เชลล์
และไฟล์ปฏิบัติการที่ค้นหาจาก `PATH` สตรีมภาพหน้าปกแบบ attached-picture
จะไม่ถือเป็นตัวเลือกที่เล่นได้ สตรีมที่เล่นได้ทั้งหมดต้องเป็นไปตามขีดจำกัด
และระบบจะเลือกสตรีมเริ่มต้นที่ระบุอย่างชัดเจนก่อนใช้ทางเลือกสำรองแบบกำหนดผลได้
ซึ่งมีดัชนีต่ำที่สุด วิดีโอถูกจำกัดไว้ที่ 600 วินาที, 8,192 พิกเซลต่อมิติ และ
33,554,432 พิกเซลต้นฉบับ FFmpeg จะสุ่มตัวอย่างเฟรม JPEG ที่จุดกึ่งกลางจำนวน 1–16 เฟรม
ลดขนาดด้านยาวให้ไม่เกิน 1,024 พิกเซลโดยไม่ขยายอินพุตที่มีขนาดเล็กกว่า
และจะไม่ได้รับ URL โดยเด็ดขาด การสุ่มตัวอย่างมีค่าเริ่มต้นเป็น `uniform`
นโยบายเสริม `scene_aware` และ `segment_aware` ที่อยู่ในขั้นทดลอง
จะดำเนินการ FFmpeg แบบตายตัวเพิ่มอีกหนึ่งรอบกับสตรีมภายในที่ผ่านการตรวจสอบแล้ว
เลือกไทม์สแตมป์ฉาก `showinfo` ที่มีขอบเขต และย้อนกลับไปใช้จุดกึ่งกลางแบบสม่ำเสมอ
ชุดเดิมโดยกำหนดผลได้ เมื่อการตรวจจับล้มเหลว หมดเวลา เอาต์พุตมีรูปแบบไม่ถูกต้อง
หรือชุดตัวเลือกว่างเปล่า โหมด segment-aware จะจัดสรรตัวอย่างที่จุดกึ่งกลาง
ตามสัดส่วนของช่วงฉากที่ผ่านการตรวจสอบ หลักฐานของ segment-aware และพฤติกรรม
การย้อนกลับจะอธิบายโดยละเอียดด้านล่าง ขีดจำกัดสูงสุดแบบตายตัวที่ 16 เฟรม
จะถูกนำไปใช้หลังการเลือกในทุกนโยบาย เมื่อคำขอแบบ scene-aware มีงบประมาณเพียง
หนึ่งเฟรม ระบบจะใช้จุดกึ่งกลางแบบสม่ำเสมอของหน้าต่างวิดีโอเต็มหรือหน้าต่างโฟกัส
ที่ใช้งานอยู่ และรายงาน `policyEffective: uniform` เพราะเฟรมฉากเดียวที่เลือก
ไม่สามารถรักษาข้อมูลจากปลายช่วงเวลาทั้งสองด้านไว้ได้ ผู้เรียกอาจระบุหน้าต่างโฟกัส
แบบจำกัด (`start`/`end` เป็นวินาที) ได้ โดยขอบเขตจะถูกจำกัดให้อยู่ภายในระยะเวลาของสื่อ
หน้าต่างที่สลับลำดับหรือมีค่าไม่จำกัดจะถูกปฏิเสธ และนโยบายการสุ่มตัวอย่างทั้งหมด
จะดำเนินการเฉพาะภายในช่วงที่ปรับให้อยู่ในรูปแบบมาตรฐานแล้ว หน้าต่างผลลัพธ์
จะรวมอยู่ในเมทาดาทาการสุ่มตัวอย่างและคำนำหน้าคำอธิบายที่ไม่เชื่อถือ
เพื่อให้โมเดลปลายทางแยกแยะช่วงตัดตอนที่โฟกัสจากไทม์ไลน์ทั้งหมดได้

การโฟกัสคำบรรยายเชิงความหมายเป็นการตั้งค่าที่แยกต่างหากและชัดเจน
โหมดการวิเคราะห์เริ่มต้น `full` จะคงพรอมต์เฟรมเดิมไว้และไม่ส่งต่อข้อความคำขอ
ไปยังโมเดลคำบรรยาย ในโหมด `focused` บริดจ์จะอ่านเฉพาะ `text`/`input_text`
ล่าสุดที่ไม่ว่างและเขียนโดยผู้ใช้จากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน
ปรับให้อยู่ในรูปแบบ NFC ยุบอักขระควบคุมและช่องว่าง และจำกัดไว้ที่
500 โค้ดพอยต์ Unicode ผลลัพธ์ที่ว่างเปล่าจะย้อนกลับไปใช้พรอมต์ `full`
ที่ตรงกันทุกประการ คำใบ้ที่ใช้งานได้จะถูกซีเรียลไลซ์เป็น JSON ในบล็อก
บริบทผู้ใช้ที่ไม่เชื่อถือโดยเฉพาะ และอาจใช้ได้เฉพาะเพื่อจัดลำดับความสำคัญ
ของรายละเอียดที่สังเกตได้เท่านั้น ไม่สามารถแทนที่คำเตือนแยกต่างหาก
ที่ห้ามปฏิบัติตามคำสั่งซึ่งมองเห็นหรือได้ยินในสื่อ การโฟกัสเชิงข้อความ
จะไม่อนุมาน `start`/`end` หรือเปลี่ยนตัวสุ่มตัวอย่างตามเวลา

#### หลักฐานเซกเมนต์เชิงโครงสร้าง FU-07

`segment_aware` ใช้การวิเคราะห์ล่วงหน้าแบบมีขอบเขตหนึ่งรอบกับสตรีมวิดีโอภายในที่ผ่านการตรวจสอบแล้ว สายโซ่ตัวกรองแบบคงที่จะปรับขนาดให้มีความกว้างไม่เกิน 320 พิกเซลก่อน จากนั้นตรวจจับการเปลี่ยนฉากและช่วงภาพค้าง แล้วจึงสุ่มตัวอย่างที่ 1 เฟรมต่อวินาทีเพื่อวัดความเบลอ ค่าความสว่างเฉลี่ย และข้อมูลเชิงพื้นที่/เวลา รอบการวิเคราะห์นี้จำกัดไว้ที่ตัวอย่างเชิงโครงสร้าง 600 ตัวอย่าง ใช้เธรด FFmpeg/ตัวกรองหนึ่งเธรด ใช้รายการอนุญาตเฉพาะโปรโตคอล `file` และคอนเทนเนอร์ชุดเดียวกัน จำกัดเอาต์พุตของโพรเซสไว้ที่ 1 MiB และใช้เวลาไม่เกิน 30 วินาทีภายในกลไกยกเลิก/กำหนดเวลาสิ้นสุดที่ใช้ร่วมกันของโบรกเกอร์ โดยจะไม่รับคำสั่ง ตัวกรอง พาธ หรือ URL จากคำขอ

ค่าเชิงโครงสร้างเป็นหลักฐานจากการสุ่มตัวอย่างที่กำหนดผลลัพธ์ได้แน่นอน ไม่ใช่ความเข้าใจเชิงความหมายของวิดีโอ ค่าเหล่านี้ไม่ได้อนุมานตัวแบบ การกระทำ คำบรรยาย เสียงพูด หรือเจตนาของผู้ใช้ ขอบเขตของฉากและภาพค้างจะสร้างเป็นเซกเมนต์ โดยความครอบคลุมของภาพค้าง ความเบลอ การเปิดรับแสง รายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงเชิงเวลา มีผลเพียงต่อวิธีจัดสรรงบประมาณเดิมที่ 1–16 เฟรม เซกเมนต์ที่ค้างทั้งหมดจะถูกจำกัดไว้ที่หนึ่งเฟรม ส่วนเซกเมนต์ที่ไม่ค้างจะแข่งขันกันเพื่อรับงบประมาณที่เหลือ เมื่อจำนวนขอบเขตมากกว่าจำนวนเฟรม ระบบจะยังคงรักษาความครอบคลุมแบบสม่ำเสมอตลอดไทม์ไลน์ เพื่อไม่ให้การตัดฉากอย่างรวดเร็วในช่วงต้นบดบังเซกเมนต์ยาวในช่วงท้าย ขอบเขตฉากที่อยู่ภายในความละเอียดการวิเคราะห์ 1 วินาทีจากขอบเขตภาพค้างจะถูกรวมเข้าด้วยกัน

หากไม่มีตัวกรอง หลักฐานผิดรูปแบบ/ว่างเปล่า ตัวตรวจจับเกิดข้อผิดพลาด หรือการวิเคราะห์ล่วงหน้าแบบมีขอบเขตหมดเวลา ระบบจะเปิดทางให้ทำงานต่อโดยใช้แนวนโยบายจุดกึ่งกลางแบบสม่ำเสมอเดิมทุกประการ การยกเลิกจากผู้เรียกหรือการถึงกำหนดเวลาสิ้นสุดของโบรกเกอร์จะไม่เปิดทางให้ทำงานต่อ แต่จะยุติโพรเซสย่อยที่กำลังทำงาน ป้องกันการแยกเฟรมในภายหลัง และลบโครงสร้างไดเรกทอรีชั่วคราวส่วนตัวใน `finally`

`scripts/perf/video-bridge-fu07-eval.ts` สร้างฟิกซ์เจอร์ FFmpeg จริงที่ให้ผลลัพธ์แน่นอน สำหรับประเมินการลดจำนวนการเรียกสร้างคำบรรยายหลังการขจัดรายการซ้ำ การจัดสรรงบประมาณสำหรับการเคลื่อนไหวหนาแน่น หลักฐานความเบลอ/การเปิดรับแสง/SI-TI การตัดฉากอย่างรวดเร็วที่มีช่วงท้ายยาว และผลบวกลวงจากการเฟดแบบค่อยเป็นค่อยไป สคริปต์นี้บันทึกเวลาจริงที่ใช้ในการวิเคราะห์ล่วงหน้า และเมื่อมี `/usr/bin/time` ก็จะบันทึกเวลา CPU ของโพรเซสลูกและค่า RSS สูงสุดด้วย การตรวจสอบคุณภาพเป็นเพียงออราเคิลเชิงโครงสร้างเท่านั้น คุณภาพของโมเดลสร้างคำบรรยายจริงยังคงเป็น `HOLD` เนื่องจากชุดทดสอบนี้ไม่มีปลายทางที่ได้รับอนุญาตหรือผู้ตัดสินที่ตรึงไว้ การประหยัดค่าใช้จ่ายยังคงเป็น `HOLD` เช่นกัน เว้นแต่ `--caption-cost-per-call-usd` จะระบุค่าประมาณต้นทุนต่อการเรียกที่เป็นบวกอย่างชัดเจน โดยสคริปต์จะไม่สร้างผลลัพธ์ใดขึ้นมาเอง

แต่ละเฟรมถูกจำกัดไว้ที่ 4 MiB เฟรมดิบทั้งหมดรวมกันถูกจำกัดไว้ที่ 23 MiB และการตอบกลับจากโบรกเกอร์ที่ผ่านการซีเรียลไลซ์ถูกจำกัดไว้ที่ 32 MiB ไดเรกทอรีชั่วคราวส่วนตัวจะถูกลบใน `finally` OmniRoute ไม่ได้รวม FFmpeg มาด้วยและไม่ยอมรับพาธไฟล์ปฏิบัติการแบบกำหนดเอง ก่อนสร้างคำบรรยาย บริดจ์จะดำเนินการขจัดภาพซ้ำแบบระมัดระวัง โดยลด JPEG แต่ละภาพให้เป็นบัฟเฟอร์ระดับสีเทาขนาด 16×16 และเปรียบเทียบเฉพาะกับเฟรมล่าสุดที่เก็บไว้ สำหรับงบประมาณคำบรรยายที่ร้องขอซึ่งมากกว่าหนึ่งเฟรม การแยกเฟรมจะจัดเตรียมกลุ่มเฟรมตัวเลือกที่มีขอบเขตไม่เกินสองเท่าของงบประมาณนั้น และไม่เกิน 16 เฟรม ระบบจะใช้ขีดจำกัดที่ร้องขอหลังการขจัดรายการซ้ำเท่านั้น โดยจะเก็บตัวเลือกแรกและตัวเลือกสุดท้ายไว้ระหว่างการลดจำนวนขั้นสุดท้ายเมื่อมีงบประมาณอย่างน้อยสองเฟรม นโยบายแบบมีเวอร์ชัน `grayscale-16x16-mean-cells-v2` ใช้ค่าที่มากกว่าระหว่างผลต่างค่าความสว่างเฉลี่ยกับอัตราส่วนของเซลล์ภาพขนาดย่อที่มีผลต่างแบบปรับมาตรฐานอย่างน้อย 0.05 เกณฑ์สำหรับภาพซ้ำคือค่าคงที่ 0.04 ซึ่งเลือกเพื่อให้คาดการณ์ได้ ไม่ใช่เพื่อเปิดให้เป็นการตั้งค่าขณะทำงาน สัญญาณรองที่มีคอนทราสต์สูงนี้ช่วยคงการเคลื่อนไหวขนาดเล็กและการเปลี่ยนแปลงของข้อความที่มองเห็นได้ ซึ่งการเปรียบเทียบโดยใช้เพียงค่าเฉลี่ยอาจมองข้าม ข้อผิดพลาดของตัวเปรียบเทียบหรือตัวถอดรหัสจะเปิดทางให้ทำงานต่อและรักษาความครอบคลุมไว้ เมทาดาทาเอาต์พุตจะแยกเฟรมตัวเลือกที่แยกออกมา เฟรมที่ใช้งานสำเร็จ และภาพซ้ำที่ถูกตัดทิ้งออกจากกัน

ส่วนวิดีโอที่ทำเครื่องหมายไว้อย่างชัดเจนอาจร้องขอแผ่นรวมภาพพร้อมการประทับเวลา บริดจ์จะสร้างตาราง JPEG ที่มีไม่เกิน 4 คอลัมน์และ 16 เฟรม แต่ละเซลล์ขนาด 512 พิกเซลจะฝังเวลาของแหล่งที่มาลงในแถบคอนทราสต์สูงบริเวณด้านล่าง ขณะเดียวกันเวลาชุดเดียวกันจะยังคงอยู่ในเมทาดาทาแบบข้อความเพื่อการเชื่อมโยงและการตรวจสอบย้อนหลัง Complete JPEG ยังคงถูกจำกัดไว้ที่ 32 MiB หาก `sharp` ไม่สามารถถอดรหัสหรือประกอบตารางได้ บริดจ์จะย้อนกลับไปใช้เฟรม JPEG แต่ละเฟรม และการยกเลิกจากไคลเอนต์จะยังคงถูกส่งต่อไปยังกระบวนการสร้างแผ่นรวมภาพ

หลักฐานสำหรับการเลื่อนสถานะถูกแยกออกจากไมโครเบนช์มาร์กการประกอบภาพสังเคราะห์โดยเจตนา `scripts/perf/video-bridge-contact-sheet-eval.ts` กำหนดชุดทดสอบ A/B แบบมีเวอร์ชันสคีมาสำหรับโมเดลวิชันจริงที่เข้ากันได้กับ OpenAI โดยวัดจำนวนโทเค็นที่ผู้ให้บริการรายงาน เวลาแฝงตั้งแต่ต้นจนจบตามเวลาจริง ซึ่งรวมการประกอบแผ่นรวมภาพ จำนวนการเรียกโมเดล และการคงอยู่ของข้อเท็จจริงที่กำหนดไว้ในไฟล์กำกับ ระบบจะไม่เขียนการตอบกลับดิบจากโมเดลลงในรายงาน แต่จะเก็บไว้เฉพาะไดเจสต์ SHA-256 และ ID ของข้อเท็จจริงที่ตรงกัน ชุดทดสอบจะไม่เรียกเครือข่ายหรือโมเดลแบบมีค่าใช้จ่าย เว้นแต่จะส่ง `--execute-real` และกำหนดค่า `--model`, `OMNIROUTE_BASE_URL` และ `OMNIROUTE_API_KEY` หากไม่มีการรันจริงที่ระบุไว้อย่างชัดเจนดังกล่าว คำตัดสินที่เครื่องอ่านได้จะยังคงเป็น `HOLD` การวัดเพย์โหลดสังเคราะห์/จำนวนการเรียกเพียงอย่างเดียวไม่ถือเป็นหลักฐานสำหรับการเลื่อนสถานะ

ผู้เรียกสามารถแนบอาร์เรย์ `transcript.cues` ซึ่งเป็นตัวเลือกเข้ากับส่วนวิดีโอที่รองรับ เมื่อมีข้อความที่จัดแนวเวลาไว้แล้ว แต่ละคิวต้องมี `text` ช่วงเวลา `start`/`end` ที่มีค่าจำกัดและอยู่ภายในระยะเวลาที่ตรวจสอบได้ รวมถึง `source` ที่อยู่ในรายการอนุญาต (`client`, `embedded` หรือ `audio-bridge`) ส่วน `confidence` มีค่าเริ่มต้นเป็น `1` และต้องอยู่ระหว่าง `0` ถึง `1` คิวที่ซ้ำกันทุกประการจะถูกรวมเข้าด้วยกัน OmniRoute จะไม่เริ่มการถอดเสียงจากเมทาดาทานี้ โดยคิวที่ผ่านการตรวจสอบจะถูกคัดลอกไปยังผลลัพธ์ที่อธิบายไว้พร้อมแหล่งที่มา ความเชื่อมั่น และช่วงเวลา และจะแสดงเป็นข้อสังเกตที่ไม่น่าเชื่อถือควบคู่กับคำบรรยายเฟรม ข้อความที่ไม่ถูกต้อง อยู่นอกช่วง หรือไม่มีแหล่งที่มาจะถูกปฏิเสธ แทนที่จะนำไปปะปนกับสตรีมคำบรรยาย ช่องทางทรานสคริปต์ทั้งสองในเนื้อหาคำขอจะปรับแหล่งที่มาที่ระบุให้เป็น `client` ซึ่งรวมถึงป้ายกำกับ `embedded` หรือ `audio-bridge` ที่อ้างเองด้วย มีเพียงอะแดปเตอร์ที่เซิร์ฟเวอร์เป็นเจ้าของเท่านั้นที่สามารถกำหนดป้ายกำกับที่เชื่อถือได้เหล่านั้นผ่านอาร์กิวเมนต์ `trustedSource` ซึ่งเข้าถึงได้จากโค้ดเท่านั้น ฟิลด์ JSON ในคำขอไม่สามารถเข้าถึงอาร์กิวเมนต์ดังกล่าวได้ ข้อความทรานสคริปต์ยังคงเป็นเนื้อหาที่ไม่น่าเชื่อถือซึ่งได้มาจากสื่อ ไม่ว่าแหล่งที่มาจะเป็นอย่างไรก็ตาม และต้องไม่ใช้เป็นตัวกำหนดการอนุญาตเด็ดขาด

ผู้เรียกใช้งานขั้นสูงอาจระบุแทร็ก `audioTranscript` สำหรับวิดีโอเดียวกันได้;

แคชจะปฏิเสธ Base64 ที่ไม่เป็นมาตรฐาน การเติม padding มากเกินไป สื่อที่ไม่ใช่ JPEG ไฟล์ JPEG ที่มีรูปแบบไม่ถูกต้องหรือถูกตัดขาด และ JPEG ที่ทำให้เกิดคำเตือนระหว่างการถอดรหัสภาพเต็มแบบมีขอบเขตด้วย `sharp` ระบบจะเข้ารหัสภาพที่ยอมรับแต่ละภาพใหม่เป็น JPEG มาตรฐาน คำนวณความกว้างและความสูงจากไบต์ที่ถอดรหัสแล้วแทนการเชื่อถือฟิลด์จากผู้เรียก และทิ้งไบต์ polyglot ที่ต่อท้ายแทนที่จะเก็บไว้ โควตาทั้งสองจะนับเฉพาะบัฟเฟอร์บีบอัดมาตรฐานที่มีขอบเขตเท่านั้น ขีดจำกัดข้อมูลบนสาย JSON รวมโอเวอร์เฮดของ Base64 สำหรับเพดานอินพุตที่ถอดรหัสแล้วขนาด 32 MiB การสร้างข้อมูลอนุพันธ์ที่จัดเก็บไว้ทุกรายการจะบันทึกรูปแบบ/ความละเอียดของ JPEG ที่ผ่านการตรวจสอบ นโยบายการสุ่มตัวอย่าง เวอร์ชันการสร้างข้อมูลอนุพันธ์ เวลาที่สร้าง แฮชเนื้อหาที่เซิร์ฟเวอร์คำนวณ และข้อมูลอ้างอิงพาเรนต์ที่แฮชแล้ว พร้อมกับแฮชเนื้อหาพาเรนต์จากผู้เรียกที่เชื่อถือได้ ระบบจะตรวจสอบการยกเลิกระหว่างเฟสการถอดรหัส/แฮชแบบอะซิงโครนัส ก่อนคอมมิตแคชแบบอะตอมมิก

งานส่วนนี้ยังไม่ได้เชื่อมต่อผู้ผลิตในระบบ production เข้ากับ route และยังไม่มีการเลือกตัวแปรหลายความละเอียด ดังนั้นเส้นทางคำขอ Video Bridge แบบโปร่งใสจึงไม่ก่อให้เกิดงานเพิ่มเติม ขณะที่การสร้าง principal ซึ่งผูกกับ tenant และวงจรการทำงานหลายความละเอียดทั้งหมดของ FU-08 ยังคงเป็นงานติดตามผลที่ระบุไว้อย่างชัดเจน แทนที่จะบันทึกไว้ว่าเป็นพฤติกรรมที่เสร็จสมบูรณ์แล้ว

เฟรมจะได้รับคำบรรยายตามลำดับด้วยโมเดล Video ที่กำหนดค่าไว้ ค่า Video override ที่ว่างจะสืบทอดการตั้งค่า Vision หากทั้งสองค่าว่าง ตัวกำหนดเส้นทางอัตโนมัติของ Vision จะเลือกโมเดลที่มีความสามารถด้านการมองเห็นซึ่งมีผลใช้งาน คำบรรยายที่สำเร็จจะแทนที่ส่วนต้นฉบับด้วยคำนำหน้า `[Video description:` ที่คงที่ ซึ่งยังระบุข้อความว่าเป็นข้อสังเกตที่ไม่น่าเชื่อถือซึ่งได้มาจากสื่อ และแจ้งโมเดลดาวน์สตรีมไม่ให้ทำตามคำสั่งที่พบในสื่อ คีย์แคชคำบรรยายเฟรมประกอบด้วยไบต์ JPEG พรอมต์ การประทับเวลา และโมเดลที่มีผลใช้งาน โดยจะแคชเฉพาะคำบรรยายที่สำเร็จเท่านั้น รายการแคชจะเก็บโมเดลผู้ผลิตที่ทำงานสำเร็จจริง รวมถึงโมเดลสำรอง และบริดจ์จะรายงาน `mixed` เมื่อเฟรมต่าง ๆ ถูกสร้างโดยโมเดลที่แตกต่างกัน เมื่อพบข้อมูลในแคช ระบบจะใช้ข้อมูลระบุตัวตนของผู้ผลิตนั้นซ้ำ แทนการเปลี่ยนป้ายกำกับให้เป็นแผนการกำหนดเส้นทางที่ร้องขอ แคชผลลัพธ์ของวิดีโอทั้งรายการจะใช้ทุกอินพุตที่เปลี่ยนแปลงเอาต์พุตเป็นคีย์ ได้แก่ พรอมต์ โมเดลที่มีผลใช้งาน นโยบายการสุ่มตัวอย่าง จำนวนเฟรม โหมดการวิเคราะห์เชิงความหมาย ลายนิ้วมือ SHA-256 ของคำแนะนำจุดสนใจที่ปรับให้เป็นมาตรฐาน ช่วงจุดสนใจ `transcript` `audioTranscript` และแฟล็ก contact-sheet ดังนั้นการเปลี่ยนแปลงมิติใด ๆ เหล่านี้จะทำให้ไม่พบข้อมูลในแคช และจะไม่มีการนำข้อมูลเก่ามาใช้ซ้ำ เวอร์ชันนโยบายการขจัดภาพซ้ำ เกณฑ์ และจำนวนเฟรมผู้สมัครแบบมีขอบเขตก็ระบุไว้อย่างชัดเจนในคีย์และเมทาดาทาของแคชผลลัพธ์เช่นกัน ดังนั้นการเปลี่ยนแปลงนโยบายจึงไม่สามารถนำคำอธิบายวิดีโอทั้งรายการที่เก่ามาใช้ซ้ำได้ เมทาดาทาของแคชผลลัพธ์ v4 จะเก็บโหมดและลายนิ้วมือไว้ แต่จะไม่เก็บงานดิบของผู้ใช้ เมทาดาทาของ guardrail จะรายงานทั้งโหมดการวิเคราะห์ที่ร้องขอและโหมดที่มีผลใช้งาน โดยโหมด `focused` ที่ร้องขอแต่ไม่มีข้อความผู้ใช้ที่ใช้งานได้จะถูกรายงานว่ามีผลเป็น `full`

Guardrail จะแยกทุกส่วนของวิดีโอที่รองรับ แต่จะอธิบายไม่เกิน `modalityBridgeVideoMaxVideos` สำหรับเป้าหมายที่พิสูจน์แล้วว่ามี `supportsVideo === false` วิดีโอที่ล้มเหลวและวิดีโอที่เกินขีดจำกัดจะถูกแปลงเป็นตัวทำเครื่องหมายข้อความที่ปลอดภัยอย่างชัดเจน เพื่อไม่ให้มีวิดีโอดิบหลงเหลืออยู่ เมื่อไม่ทราบความสามารถ ส่วนเหล่านั้นจะยังคงมีตัวพาวิดีโออยู่ โดย transcript สำรองใด ๆ จะเป็นไปตามการแปลงข้อความแบบมีขอบเขตข้างต้น เป้าหมายที่มี `supportsVideo === true` จะข้ามบริดจ์ สัญญาณยกเลิกคำขอของไคลเอนต์จะแพร่ไปยังการดาวน์โหลด คิวของ broker โปรเซสย่อย และการเรียกคำบรรยาย การยกเลิกจะหยุดการทำงานระหว่างวิดีโอและจะไม่ยอมให้สื่อดิบผ่านไปเมื่อเกิดข้อผิดพลาด

การตั้งค่ารันไทม์ได้รับการสนับสนุนโดย DB และตรวจสอบความถูกต้องด้วย Zod:

| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | รันไทม์เสริม ต้องเลือกเปิดใช้งานเอง                                                                       |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` จะคงคำบรรยายทั่วไปไว้ ส่วน `focused` จะใช้บริบทล่าสุดจากผู้ใช้ที่ถูกจำกัดขอบเขตและไม่เชื่อถือ      |

ยืนยันสิทธิ์ระดับการจัดการ โดยจะส่งคืนเฉพาะ `available`, เวอร์ชัน FFmpeg/ffprobe

### ตัวปกปิด PII (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน

- **`preCall`** จะโคลนเพย์โหลด ไล่ตรวจสอบ `system`, `messages`, `input` และ
  `prompt` (รวมถึงรายการที่เป็นสตริงธรรมดา) และใช้ `processPII()` (จาก
  `@/shared/utils/inputSanitizer`) กับฟิลด์ `content`/`text` ที่เป็นสตริง เมื่อ
  `PII_REDACTION_ENABLED=true` ระบบจะปกปิด PII ที่ตรวจพบในเพย์โหลดขาออก
  การทำงานนี้ไม่ขึ้นกับ `INPUT_SANITIZER_MODE` (ซึ่งควบคุมเฉพาะ
  นโยบายการแทรกพรอมต์) เมื่อปิดการปกปิด การเรียกจะบันทึกจำนวนที่ตรวจพบ
  โดยไม่เขียนเนื้อหาใหม่
- **`postCall`** จะดีปโคลนการตอบกลับ เรียกใช้ `sanitizePIIResponse()` ร่วมกับ
  ตัวปกปิดสำหรับโครงสร้าง Responses API (`maskResponsesOutput` — ครอบคลุม
  `output_text` และ `output[].content[].text`) หากเกิดการปกปิดใดๆ
  การตอบกลับที่แก้ไขแล้วจะแทนที่การตอบกลับเดิม

กลไกป้องกันจะไม่บล็อก โดยจะเพียงใส่คำอธิบายประกอบ (`meta.detections`,
`meta.redacted`) หรือเขียนเนื้อหาใหม่

### การแทรกพรอมต์ (`promptInjection.ts`)

ตรวจจับโครงสร้างที่เป็นอันตรายในเนื้อหาที่ผู้ใช้ป้อน และบังคับใช้
นโยบายที่กำหนดค่าไว้ พฤติกรรมขับเคลื่อนด้วยตัวแปรสภาพแวดล้อมและตัวเลือกของคอนสตรักเตอร์:

| การตั้งค่า    | ตัวแปรสภาพแวดล้อม                                                                                        | ค่าเริ่มต้น | ผล                                                                                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| เปิดใช้งาน    | `INPUT_SANITIZER_ENABLED`                                                                                | `true`      | เมื่อเป็น `false` กลไกป้องกันจะลัดวงจรและหยุดทำงาน                                                                                                                                     |
| โหมด          | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                          | `warn`      | นโยบายการแทรก: `block`, `warn` หรือ `log` (`redact` ยังคงรองรับเพื่อความเข้ากันได้ย้อนหลัง แต่จะ **ไม่** ลบข้อความการแทรกออก การเขียน PII ในคำขอใหม่ควบคุมโดย `PII_REDACTION_ENABLED`) |
| เกณฑ์การบล็อก | ตัวเลือก `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (นามแฝง `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`      | ระดับความรุนแรงขั้นต่ำที่ต้องมีเพื่อบล็อก โดยค่าเริ่มต้น ระดับ Medium จะเป็นเพียงการสังเกตการณ์                                                                                        |

**ลำดับความสำคัญของโหมด** (`getMode`): `options.mode` ของผู้เรียก →
การแทนที่ด้วยแฟล็กฟีเจอร์ใน DB สำหรับ `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → env `INJECTION_GUARD_MODE` → env `INPUT_SANITIZER_MODE` →
`warn` ดังนั้นการแทนค่าจากแดชบอร์ดจึงมีลำดับเหนือกว่าตัวแปร env ทำให้ UI ของ Feature
Flags สามารถควบคุมกลไกป้องกันที่กำลังทำงานได้แบบสดๆ (ไม่ต้องรีสตาร์ต) การอ่าน DB เป็นแบบปลอดภัยเมื่อเกิดข้อผิดพลาด:
หากเกิดข้อผิดพลาด กลไกป้องกันจะย้อนกลับไปใช้พฤติกรรมตาม env และเมื่อไม่ได้ตั้งค่า
การแทนที่ไว้ พฤติกรรมจะเหมือนกับการแก้ค่าจาก env เพียงอย่างเดียว

แหล่งที่มาของการตรวจจับ:

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับร่วม
   ที่ใช้ในส่วนอื่นของไปป์ไลน์)
2. `DEFAULT_GUARD_PATTERNS` ที่มีมาให้ในตัว (ปัจจุบันคือ `system_override_inline` และ
   `markdown_system_block` โดยทั้งคู่มีระดับความรุนแรง `high`)
3. `customPatterns` เสริมที่ส่งผ่านตัวเลือกของคอนสตรักเตอร์ (สตริง, regex
   หรือเรคคอร์ด `{ name, pattern, severity }`)

เมื่อ `mode === "block"` **และ** มีการตรวจพบอย่างน้อยหนึ่งรายการที่ถึงเกณฑ์
ความรุนแรง `preCall` จะคืนค่า `{ block: true, message: "Request rejected:
suspicious content detected" }` ในโหมด `warn`/`log` กลไกป้องกันจะบันทึกล็อก แต่
อนุญาตให้เรียกใช้งานต่อได้ นอกจากนี้ยังส่งออกตัวช่วยที่ใช้ร่วมกัน `evaluatePromptInjection()`
สำหรับผู้เรียกที่ต้องการประเมินพรอมป์โดยไม่ผ่านรีจิสทรี

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของ
ข้อความพรอมป์ที่นำมาต่อกัน — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน
`src/shared/utils/inputSanitizer.ts` ทั้ง `detectInjection()` และ
`evaluatePromptInjection()` จะเรียก `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนดำเนินการ
วนลูปตรวจสอบรูปแบบ คำสั่งแทรกแซงมักอยู่ใกล้ส่วนต้นของอินพุต ดังนั้นการดำเนินการนี้
จึงจำกัดการใช้ CPU/GC ของ regex สำหรับเพย์โหลดขนาดหลายร้อย KB โดยไม่ลดทอนประสิทธิภาพการตรวจจับ (ดู
#3932, #4041)

### ตัวปกปิดข้อมูลรับรอง (`credentialMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน และอยู่ลำดับสุดท้ายในเชนเริ่มต้น (ลำดับความสำคัญ `95`) ปกปิด
รูปแบบ API key / secret token ที่รู้จักกันดีจากเพย์โหลดขาออก (เนื้อหา
ข้อความ อาร์กิวเมนต์การเรียกเครื่องมือ ผลลัพธ์ของเครื่องมือ) **และ** การตอบกลับจากผู้ให้บริการ เพื่อไม่ให้
ข้อมูลรับรองที่วางลงในพรอมป์ (หรือถูกส่งสะท้อนกลับมาโดยผลลัพธ์ของเครื่องมือ) รั่วไหล
ไปยังผู้ให้บริการต้นทางหรือกลับไปยังไคลเอนต์

- **ต้องเลือกเปิดใช้งานเท่านั้น** โดยใช้แนวทางเดียวกับการปกปิด PII (ใกล้เคียงกับกฎตายตัวข้อ #20):
  ปิดใช้งาน เว้นแต่ `settings.credentialRedactionEnabled === true` **หรือ**
  `CREDENTIAL_REDACTION_ENABLED=true` เมื่อปิดอยู่ กลไกป้องกันนี้จะไม่ดำเนินการใด ๆ —
  โดยจะไม่บล็อกและไม่เขียนข้อมูลใหม่
- `redactCredentials()` จะสำรวจโครงสร้างทั้งหมดของเพย์โหลด/การตอบกลับ (`walkValue()`,
  ปลอดภัยจาก prototype pollution และปลอดภัยต่อวงจรอ้างอิงด้วย `WeakSet`) และแทนที่รายการที่ตรงกันด้วย
  ตัวยึดตำแหน่ง `[REDACTED:<type>]` โดยโคลนเฉพาะกิ่งที่มีการเปลี่ยนแปลงจริง
- `CREDENTIAL_PATTERNS` ครอบคลุมคีย์ของผู้ให้บริการ LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), โทเค็น VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), คีย์การชำระเงิน (Stripe, Square), คีย์
  คลาวด์ (AWS access key, Twilio, SendGrid, Mailgun), private key / JWT,
  connection string ที่มีข้อมูลรับรอง (`mongodb://user:pass@...` เป็นต้น) และ
  รูปแบบค่าของเฮดเดอร์ทั่วไป `Authorization`/`x-api-key`/`api-key`/`apikey`
  คีย์ที่มีลักษณะเป็นเฮดเดอร์ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) จะถูกปกปิดตามโครงสร้าง (เฉพาะค่า โดยคงคำนำหน้าสคีม เช่น
  `Bearer `/`Basic ` ไว้) แทนการใช้ regex ข้อความทั่วไป
- กลไกป้องกันนี้จะไม่บล็อก โดยจะเขียนข้อมูลใหม่เท่านั้น (`modifiedPayload` /
  `modifiedResponse`) และเพิ่มคำอธิบายประกอบ (`meta.credentialsRedacted`, `meta.count`)

ตัวป้องกันการถดถอย: `tests/unit/credential-masker-guardrail.test.ts`

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // ค่า true จะลัดวงจรของเชน
  message?: string; // แสดงเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ส่งคืนโดย preCall เพื่อเขียนคำขอใหม่
  modifiedResponse?: TValue; // ส่งคืนโดย postCall เพื่อเขียนการตอบกลับใหม่
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลระบุว่า "ไม่มีการเปลี่ยนแปลง" ด้วยการส่งคืน `void`, `{}` หรือ
`{ block: false }` อย่างใดอย่างหนึ่ง การส่งคืน `modifiedPayload`/`modifiedResponse`
จะแทนที่ค่าที่ไหลผ่านเชนสำหรับการ์ดเรลลำดับถัดไป
`signal?: AbortSignal` ส่งต่อวงจรชีวิตของผู้เรียกไปยังการ์ดเรล การยกเลิกคำขอเป็นข้อยกเว้นแบบยอมให้ทำงานต่อโดยเจตนา: บริดจ์สื่อจะหยุดการทำงานและล้างทรัพยากร โดยไม่กู้คืนสื่อดิบไปยังปลายทางที่ทราบว่าไม่รองรับสื่อนั้น

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` เปิดเผยเมธอดต่อไปนี้:

- `register(guardrail)` — เพิ่มการ์ดเรล (หรือแทนที่ตามชื่อที่ผ่านการทำให้เป็นมาตรฐาน)
  และเรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการดูแลระบบ
- `runPreCallHooks(payload, context)` — วนซ้ำการ์ดเรลที่ทำงานอยู่ ส่งต่อ
  เพย์โหลดผ่าน `modifiedPayload` และหยุดเมื่อพบ `block: true` ครั้งแรก
- `runPostCallHooks(response, context)` — ใช้โฟลว์เดียวกันกับฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและเลือก
  ลงทะเบียนค่าเริ่มต้นใหม่เพื่อแยกการทดสอบอย่างสะอาด

รันเนอร์ทั้งสองส่งคืน `{ blocked, payload|response, results, guardrail?, message? }`
โดย `results` เป็นอาร์เรย์ของเรคคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วย
ฟิลด์ `blocked`, `skipped`, `modified`, `error` และ `meta` ของแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลสำหรับแต่ละคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` รวบรวมรายการ
ชื่อการ์ดเรลที่ตัดรายการซ้ำแล้ว ซึ่งควรข้ามสำหรับคำขอปัจจุบัน
แหล่งที่มา (ทั้งหมดเป็นตัวเลือกและนำมารวมกันทั้งหมด):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` ในเนื้อหาคำขอ (ระดับบนสุด)
- `metadata.disabledGuardrails` ในเนื้อหาคำขอ
- เฮดเดอร์ `x-omniroute-disabled-guardrails` (หรือชื่อเดิม
  `x-disabled-guardrails`)

ค่าอาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค ชื่อจะถูก
ทำให้เป็นอักษรพิมพ์เล็กในรูปแบบ kebab-case (`pii_masker` → `pii-masker`) ผลลัพธ์
จะถูกส่งผ่าน `context.disabledGuardrails` ไปยังรีจิสทรี ซึ่งจะข้าม
การ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

## ลำดับการดำเนินการ

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` สร้างรายการที่ต้องข้ามจาก API key, body
   และ headers
2. `guardrailRegistry.runPreCallHooks(body, ctx)` เรียกใช้ guardrails ตามลำดับ
   priority จากน้อยไปมาก:
   - Guardrails ที่ปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - `preCall` ของแต่ละ guardrail อาจเขียน payload ใหม่ผ่าน `modifiedPayload`
   - รายการแรกที่มี `block: true` จะยุติลำดับการทำงานทันที และ handler จะส่งคืน
     การตอบกลับที่ระบุว่า guardrail ปฏิเสธคำขอ
3. Payload ที่อาจถูกเขียนใหม่จะถูกส่งต่อไปยัง combo routing และการส่งคำขอ
   ไปยัง upstream
4. หลังจากประกอบการตอบกลับแล้ว `guardrailRegistry.runPostCallHooks(...)`
   จะเรียกใช้ลำดับเดิมกับการตอบกลับ หากพบ `block: true` ในขั้นตอนนี้ การตอบกลับ
   จาก upstream จะถูกละทิ้ง

Guardrails ที่ throw ข้อผิดพลาดจะถูกบันทึกด้วย `error: <message>` และเขียน log ผ่าน
`logger.warn` แต่ลำดับการทำงานจะดำเนินต่อไป ซึ่งเป็นการออกแบบแบบ fail-open

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่ guardrails ในตัวอ่าน:

| ตัวแปร                                | ใช้โดย                    | ผลกระทบ                                                                                                  |
| ------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                      |

| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | ควบคุมลักษณะการทำงานของ masker ฝั่งการตอบกลับ                                                            |

ในเอกสารเท่านั้น การเขียนค่าจาก dashboard จะใช้ primary keys ค่าเริ่มต้นและตัวแก้ไข

## การ์ดเรลแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` โดยสืบทอดจาก `BaseGuardrail`
2. อิมพลีเมนต์ `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (เพิ่มจาก `registerDefaultGuardrails`) หรือ
   เรียก `guardrailRegistry.register(...)` ขณะรันไทม์ — รีจิสทรีจะแทนที่
   การ์ดเรลก่อนหน้าที่มีชื่อหลังการปรับรูปแบบเหมือนกัน
4. เพิ่มการทดสอบภายใต้ `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบแต่ละรายการเพื่อเริ่มต้นจากสถานะที่ทราบแน่ชัด
ส่ง `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยรีจิสทรีว่างและ
ลงทะเบียนเฉพาะการ์ดเรลที่กำลังทดสอบ Vision Bridge รองรับการฉีดการพึ่งพา
(`deps.getSettings`, `deps.callVisionModel`); Audio Bridge มีจุดเชื่อมต่อ
ที่เทียบเท่ากันสำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลรับรอง
และการถอดเสียง ดังนั้นการทดสอบจึงสามารถตรวจสอบโฟลว์ทั้งสองได้โดยไม่ต้องเข้าถึง DB
หรือเครือข่าย

## ความครอบคลุมของเส้นทางและการทดสอบแบบเรดทีมสำหรับการป้องกันการแทรกคำสั่ง (Phase 8 · Block D)

การป้องกันการแทรกคำสั่ง (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมทุกเส้นทาง
ที่รับพรอมต์จากผู้ใช้ โดยจะเคารพ `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึกล็อกเท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`)

| ประเภท         | เส้นทาง                                                                                                                                              | โหมดเริ่มต้น |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (เดิม) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์ | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การแยกข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`

**เรดทีม (ทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
คลัง OWASP-LLM ใน `INJECTION_GUARD_MODE=block`; garak เรียกใช้โพรบ (ข้ามหากไม่มีข้อมูลลับ)
`moderations` ถูกรวมไว้เพื่อความสอดคล้อง — ผู้ดูแลระบบที่ใช้โหมดบล็อกสามารถยกเว้นเส้นทางนี้ผ่าน
`resolveDisabledGuardrails`

เวิร์กโฟลว์รายคืน (`.github/workflows/nightly-llm-security.yml`, cron + การสั่งงาน
ด้วยตนเอง) มีสองงาน:

- **`promptfoo-guard` (บล็อกเมื่อไม่ผ่าน)** — เรียกใช้ `promptfoo eval -c promptfooconfig.yaml`
  โดยใช้ `INJECTION_GUARD_MODE=block` กรณีโจมตีแต่ละกรณี (เช่น "เพิกเฉยต่อ
  คำสั่งก่อนหน้าทั้งหมด…", การเจลเบรกแบบ DAN) จะยืนยันว่าการตอบกลับมี
  `error.code === "SECURITY_001"` กล่าวคือ การ์ดได้ปฏิเสธคำขอจริง
- **`garak` (ให้คำแนะนำ)** — เรียกใช้ garak `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ภายในเครื่อง (`http://localhost:20128/v1`) โดยขึ้นอยู่กับ
  ข้อมูลลับของผู้ให้บริการ (`PROMPTFOO_PROVIDER_KEY`); จะข้ามอย่างราบรื่นหากไม่มีข้อมูลดังกล่าว และต่อท้ายด้วย
  `|| true` จึงรายงานผลโดยไม่ทำให้ CI ล้มเหลว

ความครอบคลุมของตัวช่วยการ์ด (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่มีพรอมต์; ข้อความพรอมต์จะถูกดึงจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` โดย
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`
