## Ընդհանուր ակնարկ

OmniRoute-ի կառավարման API-ի բոլոր երթուղիները դասակարգվում են պաշտպանության երեք
մակարդակներից մեկում։ Դասակարգումը ստատիկ է, սահմանված է `src/server/authz/routeGuard.ts`-ում
և գնահատվում է նախքան նույնականացման որևէ այլ ճյուղի գործարկումը։

## Մակարդակներ

### Մակարդակ 1 — LOCAL_ONLY

**Կիրարկվում է՝** `isLocalOnlyPath(path)` → loopback հոսթի ստուգում  
**Շրջանցում՝** Լռելյայն՝ չկա։ Սահմանափակ բացառություն է նախատեսված
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում ընդգրկված ուղիների համար, երբ հարցումը պարունակում է
`manage` scope-ով վավեր API բանալի (տե՛ս [Manage scope-ի բացառությունը](#manage-scope-carve-out))։

Այս երթուղիները գործարկում են դուստր գործընթացներ կամ կատարում են runtime կոդ։ Դրանք
ոչ loopback տրաֆիկի համար հասանելի դարձնելը վավեր JWT ստացած հարձակվողին (օրինակ՝
Cloudflared/Ngrok թունելի միջոցով) թույլ կտար գործարկել գործընթացների ստեղծումը՝ հայտնի CVE
դաս ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))։

**Ինչ է GHSA-fhh6-4qxv-rpqj-ը (հարձակման դասը).** կառավարման/գործակալի սերվերը
հասանելի է դարձնում endpoint, որը գործարկում է ենթագործընթաց (`npm install`, `node`, դիտարկիչ,
պրոքսի, `git`, `tar`, …)։ Եթե այդ endpoint-ը հասանելի է հոսթից դուրս, քանի որ
օպերատորը OmniRoute-ը տեղադրել է nginx/Cloudflare/Tailscale թունելի հետևում, և JWT-ն
արտահոսել է, կամ նույնականացման կարգավորումը սխալ է եղել, հարձակվողը «API կանչը» վերածում է
«հոսթի վրա հրաման գործարկելու» (հեռակա կոդի կատարում)։ OmniRoute-ը կանխում է սա՝ յուրաքանչյուր
գործընթաց ստեղծելու ունակ երթուղու վրա **անվերապահորեն, նույնականացման ցանկացած ստուգումից առաջ կիրառելով loopback հոսթի ստուգում**․ թունելի միջոցով արտահոսած նշանը միևնույն է չի կարող հասնել գործընթացի ստեղծմանը։

**LOCAL_ONLY-ի ամբողջական բազմությունը։** Հեղինակավոր աղբյուրներն են
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` փոփոխականները՝
`src/server/authz/routeGuard.ts`-ում․ ստորև բերված աղյուսակն արտացոլում է ընթացիկ վիճակը։
`check-route-guard-membership` անցակետը թվարկում է գործընթաց ստեղծելու ունակ
նախածանցների ներքո գտնվող յուրաքանչյուր `route.ts` և ձախողում է CI-ն, եթե դրանցից որևէ մեկը դասակարգված չէ որպես միայն տեղային։

| `/api/providers/{id}/login` (կանոնավոր արտահայտություն)                                                  | Գործարկում է տեսանելի միջերեսով Playwright Chromium՝ վեբ cookie-ով մուտք գործելու համար                                     |
| `/api/providers/volcengine-plan/connect` (կանոնավոր արտահայտություն)                                     | Ձեռքով կատարվող տեսանելի միջերեսով հոսք + աշխատաշրջանի վրա հիմնված հեռախոսով/SMS-ով ավտոմատ մուտք (գործարկում է Playwright) |
| `/api/providers/{id}/refresh-cursor` (կանոնավոր արտահայտություն)                                         | Cursor-ի աշխատաշրջանի ձեռքով թարմացում — հուշում է `cursor-agent`-ին                                                        |
| `/api/providers/{id}/chatgpt-web-codex-doctor` (կանոնավոր արտահայտություն)                               | Ախտորոշում է տեղական Codex CLI-ի տեղադրումը (գործարկում է երկուական ֆայլը)                                                  |

**Պատասխան խախտման դեպքում․** `403 LOCAL_ONLY`

#### Կառավարման շրջանակի բացառություն

LOCAL_ONLY ուղիների ենթաբազմությունը ԿԱՐՈՂ Է նաև հասանելի լինել ոչ-loopback հասցեներից, եթե և
միայն եթե հարցումը պարունակում է `Authorization: Bearer <api-key>`, որի
մետատվյալները ներառում են `manage` շրջանակը (կամ `admin`)։ Բացառությունը յուրաքանչյուր ուղու
համար հստակորեն կառավարվում է `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ի միջոցով, որպեսզի
ցանկացած նոր LOCAL_ONLY ուղու համար լռելյայն ռեժիմը մնա խիստ loopback։ Չնույնականացված
հարցումները և կառավարման շրջանակ չունեցող բանալիներով հարցումները շարունակում են մերժվել
`403 LOCAL_ONLY` պատասխանով։

Ներկայում բացառություն թույլատրող միակ նախածանցը `/api/mcp/`-ն է։ `/api/cli-tools/runtime/`-ը և
`/api/services/`-ը միտումնավոր բացառված են, քանի որ կարող են գործարկել կամայական
ենթագործընթացներ (`npm install`, `node`), իսկ դա հենց այն CVE դասն է, որը
LOCAL_ONLY մակարդակը նախատեսված է կանխելու համար։

**#7895 — `mcp:connect` նեղ շրջանակ․** `/api/mcp/` բացառությունը ՆԱԵՎ ընդունում է
նեղ `mcp:connect` շրջանակը պարունակող Bearer բանալի
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), որը ստուգվում է
`src/server/authz/policies/management.ts`-ում գտնվող `hasMcpConnectOrManageScope()`-ի միջոցով։
Սա սահմանափակված է ՄԻԱՅՆ `/api/mcp/`-ով․ `mcp:connect`-ը որևէ իրավունք չի տալիս կառավարման
այլ երթուղիներում (ներառյալ LOCAL_ONLY-ի բացառման ցանկացած այլ նախածանց, եթե երբևէ
այդպիսիք ավելացվեն), և այն միտումնավոր բացառված է
`MANAGEMENT_API_KEY_SCOPES`-ից։ `manage`/`admin` պարունակող բանալին շարունակում է
անցնել բացառության ստուգումը ճիշտ այնպես, ինչպես նախկինում․ `mcp:connect`-ը նվազ արտոնություններով այլընտրանք է
հեռավար, միայն MCP օգտագործող կանչողների համար, որոնց կառավարման լայն հասանելիություն պետք չէ։

| Հարցում                                           | Ուղի                       | Արդյունք                         |
| ------------------------------------------------- | -------------------------- | -------------------------------- |
| Ոչ-loopback, առանց Bearer-ի                       | `/api/mcp/*`               | 403 LOCAL_ONLY                   |
| Ոչ-loopback, `manage` շրջանակով Bearer            | `/api/mcp/*`               | Թույլատրել                       |
| Ոչ-loopback, `mcp:connect` շրջանակով Bearer       | `/api/mcp/*`               | Թույլատրել                       |
| Ոչ-loopback, Bearer՝ առանց `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                   |
| Ոչ-loopback, `mcp:connect` շրջանակով Bearer       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                   |
| Ոչ-loopback, `manage` շրջանակով Bearer            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                   |
| Loopback, ցանկացած Bearer-ով/առանց Bearer-ի       | ցանկացած LOCAL_ONLY        | Թույլատրել (ստուգումն անցնում է) |

#### Օպերատորի ուղեցույց և աուդիտ

Եթե OmniRoute-ը գործարկում եք հակադարձ պրոքսիի կամ թունելի հետևում (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), loopback ստուգումը շարունակում է պաշտպանել վերևում նշված՝
գործընթացներ ստեղծելու ունակ երթուղիները․ այն հարցումը, որի հաճախորդի հասցեն loopback չէ, մերժվում է
`403 LOCAL_ONLY` պատասխանով՝ **նախքան նույնականացման գործարկումը**, ուստի արտահոսած JWT-ն չի կարող հասնել գործընթացի ստեղծմանը։ Մնում է
օպերատորի երկու պարտականություն․

- **Մի՛ «շտկեք» 403-ը՝ կեղծելով հաճախորդի IP հասցեն որպես loopback։** Սահմանելով
  `X-Forwarded-For: 127.0.0.1` կամ օգտագործելով proxy, որը սկզբնաղբյուրի հասցեն վերագրում է
  որպես loopback, կրկին բացվում է հենց այն RCE դասը, որն այս մակարդակը փակում է։ Proxy-ի
  միջոցով հասանելի դարձրեք dashboard/API-ն, բայց երբեք՝ գործընթացներ ստեղծելու հնարավորություն ունեցող երթուղիները։
- **Կառավարման տիրույթի շրջանցումը պահեք նվազագույն։** Միայն `/api/mcp/`-ն է հնարավոր
  շրջանցել, և միայն `manage` տիրույթով API բանալիով։ `SPAWN_CAPABLE_PREFIXES`-ը երբեք չի
  կարող ավելացվել շրջանցման ցանկում. zod սխեման մերժում է դրանք, իսկ
  `isLocalOnlyBypassableByManageScope`-ը մերժում է դրանք կատարման ժամանակ (խորքային պաշտպանություն),
  և dashboard-ում «հնարավոր չէ դարձնել շրջանցելի» արտահայտությունը հենց դա է նշանակում։ Նույն
  արգելման ցանկը ներառում է նաև LOCAL_ONLY մի քանի երթուղի, որոնք գործընթաց չեն ստեղծում, սակայն
  նույնպես երբեք չպետք է հեռակա հասանելի լինեն՝ `/api/oauth/kiro/auto-import` (կարդում է հոսթի տեղային Kiro
  հավատարմագրերի ֆայլերը), `/api/discovery/` և `/api/issue-agent/`։ Կատարման ժամանակի
  snapshot բեռնիչը նաև հեռացնում է այդպիսի գրառումները պահպանված կարգավորումների տողից, իսկ
  հին JSON ներմուծումը (`/api/settings/import-json`) երբեք չի գրում շրջանցման բանալիները։
  `LOCAL_ONLY_API_PREFIXES`-ի յուրաքանչյուր գրառում պետք է կամ լինի արգելման ցանկում, կամ
  ստուգված լինի որպես շրջանցման համար թույլատրելի (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)։ Դինամիկ հատվածներով
  և ստատիկ ուղիներով՝ գործընթաց ստեղծելու հնարավորություն ունեցող երթուղիները `/api/providers/`-ի ներքո (օր.՝ `/login`,
  `/refresh-cursor`) ծածկվում են regex-ի վրա հիմնված `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` ուղեկիցով՝
  `src/shared/constants/spawnCapablePrefixes.ts`-ում, այլ ոչ թե հարթ
  `SPAWN_CAPABLE_PREFIXES` զանգվածով. դրանք հայտնաբերելու համար հարթ զանգվածը ստիպված կլիներ ներառել
  ամբողջ `/api/providers/` նախածանցը՝ չափազանց ընդլայնելով երթուղիների այն ծառը,
  որը հեռակա dashboard-ներն օրինականորեն օգտագործում են մատակարարների CRUD գործողությունների համար։

**Մուտքի աուդիտ** — համոզվելու համար, որ հոսթից դուրս ոչ ոք չի հասնում այս երթուղիներին՝

- Բացեք **Authorization Inventory**-ն `/dashboard/settings/security`-ում. այն ցուցադրում է
  ընթացիկ LOCAL_ONLY նախածանցների ցանկը, շրջանցելի նախածանցները և կոմպիլյացիայի ժամանակ սահմանված՝
  գործընթաց ստեղծելու հնարավորություն ունեցող («հնարավոր չէ դարձնել շրջանցելի») բազմությունը։
- Reverse proxy-ի / մուտքի մատյաններում grep-ով որոնեք վերոնշյալ նախածանցները՝ զուգակցված
  ոչ loopback հաճախորդի հասցեի հետ։ Ցանկացած այդպիսի հարցում, որը `403 LOCAL_ONLY`-ի փոխարեն
  վերադարձրել է `200`, նշանակում է, որ proxy-ն քողարկում է հաճախորդի իրական IP-ն. շտկեք proxy-ն։
- OmniRoute-ի մատյաններում այս ուղիներից մեկի համար `403 LOCAL_ONLY`-ը նշանակում է, որ պաշտպանիչ
  մեխանիզմն աշխատում է ըստ նախատեսվածի, այլ ոչ թե սխալ, որը պետք է թաքցնել։

### Մակարդակ 2 — ALWAYS_PROTECTED

**Կիրառվում է՝** `isAlwaysProtectedPath(path)` → շրջանցել `requireLogin=false` բացառումը
**Շրջանցում՝** Չկա, երբ `requireLogin=false` է. JWT-ն միշտ պարտադիր է

Այս երթուղիները կործանարար են կամ անշրջելի։ Դրանք «առանց գաղտնաբառի»

սերվերի գործընթացը։

| `/api/settings/obsidian`                  | Ստեղծում է բազմակի օգտագործման WebDAV հավատարմագրեր ցանկացած vault արմատի համար |

**Պատասխան խախտման դեպքում՝** `401 Նույնականացում է պահանջվում`

`/api/settings/obsidian`-ը ներառում է իր `/webdav` զավակ ուղին. `POST`-ը WebDAV ֆայլային ծառայությունը,
որը սպասարկվում է հատուկ Node շերտի կողմից՝ Next.js-ից առաջ և այս pipeline-ից դուրս, ուղղում է
կանչողի ընտրած արմատին և վերադարձնում նոր ստեղծված Basic հավատարմագրերը, `DELETE`-ը թարմացնում է դրանք,
իսկ ծնող `POST`-ը պահպանում է Obsidian REST API token-ը։ GHSA-62vw-ն միայն քողարկել էր `GET`-ով
գաղտնաբառի բացահայտումը. տրամադրումը դեռ գտնվում էր անխափան բաց թողնող մակարդակում
(GHSA-7pq4-8pvv-rx7r)։ `enableObsidianVaultSync()`-ը նաև մերժում է այն vault-ը, որը տվյալների
գրացուցակն է, գտնվում է դրա ներսում կամ պարունակում է այն։

#### Հավատարմագրերի արտահանումները հասանելի են միայն օպերատորին

Վերոնշյալ մակարդակը միայն որոշում է, թե արդյոք պահանջվում է _որևէ_ հավատարմագիր։ Պահպանված
հավատարմագրերը ներբեռնող երթուղիները մշակիչում կատարում են երկրորդ ստուգումը՝ `GET /api/settings/export-json`
(վերծանված մատակարարների կապեր և չմշակված API բանալիներ), `GET /api/db-backups/export` (SQLite ֆայլը) և
`GET /api/db-backups/exportAll` (ամբողջական արխիվը) կանչում են `requireOperatorCredential()`-ը
(`src/lib/api/operatorCredential.ts`)։ Այն ընդունում է dashboard-ի session-ը, տեղային CLI subject-ը կամ
անջատված login-ով instance-ը և `403` է վերադարձնում ցանկացած տիրույթի API բանալիների (ներառյալ `manage`
և `admin`) ու `oma_` access token-ների համար։ Sync token-ի տրամադրումը (`POST /api/sync/tokens`) օգտագործում է
նույն helper-ը՝ գումարած վստահելի loopback ներքին ծառայության token-ը։

### Նոր տեղակայման սկզբնական կարգավորումը հասանելի է միայն loopback-ից՝ ըստ իրական peer-ի, ոչ թե `Host`-ի

Երբ կառավարման գաղտնաբառ սահմանված չէ (և չկա `INITIAL_PASSWORD`), `isAuthRequired()`-ը
`src/shared/utils/apiAuth.ts`-ում անանուն սկզբնական կարգավորումը բաց է պահում **միայն loopback peer-երի համար**։
Loopback-ը որոշվում է վստահելի peer ազդանշաններից՝ հետևյալ հերթականությամբ. token-ով նշված իրական TCP peer-ը
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, որը տեսնում է policy-ն), pipeline-ի սեփական
`AUTHZ_HEADER_PEER_LOCALITY` verdict-ը (որը տեսնում են երթուղիների մշակիչները և որը վստահելի է միայն քանի դեռ
`OMNIROUTE_PEER_STAMP_TOKEN`-ը սահմանված է), կամ ուղղակի կանչողների իրական socket peer-ը։ `Host` /
`nextUrl.hostname`-ը երբեք չի ստուգվում, իսկ առաջին գաղտնաբառի գրանցումը
(`POST /api/settings/require-login`) ենթարկվում է նույն սահմանափակմանը՝ բոլոր
ցանցային peer-երի համար բաց լինելու փոխարեն (GHSA-7pq4-8pvv-rx7r)։ `managementPolicy`-ն իր սեփական
`peerContext` verdict-ը բացահայտ կերպով փոխանցում է ներքև, այնպես որ ORIGINAL (մինչև հեռացումը) հարցման
header-ները երբեք չեն որոշում այն։

### Մակարդակ 3 — MANAGEMENT (լռելյայն)

Կառավարման մնացած բոլոր երթուղիները։ Նույնականացումը պարտադիր է, եթե
`requireLogin=false` կարգավորված չէ։ CLI թոքենները կարող են նույնականացվել այս երթուղիներում (loopback + վավեր HMAC)։

## Գնահատման հերթականությունը

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → անցնել հաջորդ քայլին
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → թույլատրել (management_key)
     → հակառակ դեպքում                           → մերժել 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → թույլատրել (system)
  3. hasValidCliToken(headers)?
     → թույլատրել (cli) [loopback + timingSafeEqual HMAC ստուգում]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → թույլատրել (dashboard_session)
     → manage-scope Bearer չշրջանցվող ուղու վրա?
        → թույլատրել (management_key)
     → մերժել 401/403
  5. requireLogin=false?
     → թույլատրել (anonymous)
```

Քայլ 1-ի manage-scope ճյուղը նույնականացված միակ ուղին է, որը կարող է բավարարել
LOCAL_ONLY երթուղու պահանջները․ auth-backend-ի խափանման ռեժիմը վերադարձնում է 503 (ոչ թե 403), որպեսզի
ժամկետանց DB-ն աննկատ չանցնի «մերժել» ռեժիմի։

## Նոր՝ spawn-ի հնարավորություն ունեցող երթուղու ավելացում

1. Ուղու նախածանցն ավելացրեք `LOCAL_ONLY_API_PREFIXES`-ում՝
   `src/server/authz/routeGuard.ts`
2. `tests/unit/authz/routeGuard.test.ts`-ում ավելացրեք թեստ, որը հաստատում է, որ
   `isLocalOnlyPath()`-ը նոր նախածանցի համար վերադարձնում է true
3. **Երբեք բաց մի թողեք այս քայլը** — տե՛ս Hard Rule #15-ը `CLAUDE.md`-ում
4. Որոշեք՝ արդյո՞ք այս երթուղին ՆԱԵՎ պետք է լինի `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ում։
   Լռելյայն պատասխանը **ոչ** է։ Ներառեք միայն այն դեպքում, երբ երթուղին անվտանգ է
   manage-scope կրողին հասանելի դարձնելու համար (այսինքն՝ ՉԻ գործարկում օգտատիրոջ կողմից կառավարվող կամայական կոդ)։

## Manage-scope-ով շրջանցվող ուղու ավելացում

1. Համոզվեք, որ երթուղին չի կատարում օգտատիրոջ տրամադրած կոդը կամ հրամանները։ Եթե
   կատարում է, կանգ առեք․ այս բացառությունը ճիշտ գործիք չէ։
2. Նախածանցն ավելացրեք `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`-ին՝
   `src/server/authz/routeGuard.ts`
3. `tests/unit/authz/management-policy.test.ts`-ում ավելացրեք ծածկույթ հարցման բոլոր չորս
   ձևերի համար՝ առանց Bearer-ի (403), manage Bearer (թույլատրել), ոչ manage Bearer
   (403), ինչպես նաև ըստ նախածանցի ռեգրեսիոն թեստ, որը հաստատում է, որ `/api/cli-tools/runtime/*`-ը
   մնում է խիստ loopback՝ նույնիսկ manage Bearer-ի առկայության դեպքում։

## Անվտանգության մակարդակների փաստաթղթավորումը OpenAPI-ում

`docs/openapi.yaml`-ում նոր երթուղի ավելացնելիս կիրառեք համապատասխան
մատակարարի ընդլայնումը, եթե երթուղին դասակարգված է `routeGuard.ts`-ի կողմից․

| routeGuard.ts դասակարգում                | YAML նշագրում              | Կիրառում                                                           |
| ---------------------------------------- | -------------------------- | ------------------------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`                | `x-loopback-only: true`    | Անվերապահորեն արգելափակվում է non-loopback-ից                      |
| `ALWAYS_PROTECTED_API_PATHS`             | `x-always-protected: true` | Նույնականացումը պարտադիր է նույնիսկ `requireLogin=false`-ի դեպքում |
| Ներքին admin/debug երթուղի               | `x-internal: true`         | Լռելյայն թաքցված է /dashboard/api-endpoints-ից                     |
| Չկա (հանրային / ստանդարտ նույնականացում) | (նշագրում անհրաժեշտ չէ)    | Ստանդարտ՝ `requireLogin`-ով կառավարվող հասանելիություն             |

### Վավերացում

Երկու սկրիպտ ապահովում են YAML նշագրումների և `routeGuard.ts`-ի համապատասխանությունը․

- `scripts/check/check-openapi-coverage.mjs` — ձախողվում է, եթե ծածկույթը < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — ձախողվում է, եթե `x-loopback-only` կամ
  `x-always-protected` նշագրումները տարբերվում են կոմպիլացման ժամանակի հաստատուններից

Երկու սկրիպտներն էլ գործարկվում են pre-commit hook-ում և CI-ում։

### Կեղծ դրական արդյունքի կանոն

Եթե `x-always-protected`-ը կամ `x-loopback-only`-ը նշված է այնպիսի երթուղու վրա, որը ՉԿԱ
`routeGuard.ts` հաստատունում, ծածկույթի սկրիպտը ձախողվում է։ Ուղղումը միշտ YAML-ը
`routeGuard.ts`-ի իրական կիրառած կանոններին համապատասխանեցնելն է, այլ ոչ թե երթուղիները `routeGuard.ts`-ում
ավելացնելը՝ առանց կիրառման տրամաբանությունը նույնպես իրականացնելու։
