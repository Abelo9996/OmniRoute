## Επισκόπηση

Όλες οι διαδρομές του API διαχείρισης του OmniRoute ταξινομούνται σε ένα από τρία επίπεδα
προστασίας. Η ταξινόμηση είναι στατική, ορίζεται στο `src/server/authz/routeGuard.ts`
και αξιολογείται πριν εκτελεστεί οποιοσδήποτε άλλος κλάδος ελέγχου ταυτότητας.

## Επίπεδα

### Επίπεδο 1 — LOCAL_ONLY

**Επιβάλλεται από:** `isLocalOnlyPath(path)` → έλεγχος για διεύθυνση βρόχου επιστροφής
**Παράκαμψη:** Καμία από προεπιλογή. Περιορισμένη εξαίρεση για διαδρομές στο
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` όταν το αίτημα περιέχει έγκυρο
κλειδί API με το πεδίο εφαρμογής `manage` (βλ. [Εξαίρεση πεδίου εφαρμογής manage](#manage-scope-carve-out)).

Αυτές οι διαδρομές εκκινούν θυγατρικές διεργασίες ή εκτελούν κώδικα κατά τον χρόνο εκτέλεσης. Η έκθεσή τους σε
κίνηση που δεν προέρχεται από βρόχο επιστροφής θα επέτρεπε σε έναν εισβολέα που απέκτησε έγκυρο JWT (π.χ.
μέσω μιας σήραγγας Cloudflared/Ngrok) να ενεργοποιήσει την εκκίνηση διεργασιών — μια γνωστή κατηγορία
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Τι είναι το GHSA-fhh6-4qxv-rpqj (η κατηγορία επίθεσης):** ένας διακομιστής διαχείρισης/πράκτορα
εκθέτει ένα τελικό σημείο που εκκινεί μια υποδιεργασία (`npm install`, `node`, ένα πρόγραμμα περιήγησης,
έναν διακομιστή μεσολάβησης, `git`, `tar`, …). Εάν αυτό το τελικό σημείο είναι προσβάσιμο εκτός του κεντρικού υπολογιστή — επειδή
ο χειριστής τοποθέτησε το OmniRoute πίσω από μια σήραγγα nginx/Cloudflare/Tailscale και ένα JWT
διέρρευσε ή ο έλεγχος ταυτότητας είχε ρυθμιστεί εσφαλμένα — ο εισβολέας μετατρέπει το «κάλεσε ένα API» σε «εκτέλεσε μια
εντολή στον κεντρικό υπολογιστή» (απομακρυσμένη εκτέλεση κώδικα). Το OmniRoute αποτρέπει αυτό το ενδεχόμενο επιβάλλοντας
**έλεγχο διεύθυνσης βρόχου επιστροφής άνευ όρων, πριν από οποιονδήποτε έλεγχο ταυτότητας**, σε κάθε
διαδρομή που έχει τη δυνατότητα εκκίνησης διεργασιών: ένα διαρρεύσαν διακριτικό μέσω σήραγγας εξακολουθεί να μην μπορεί να φτάσει στη λειτουργία εκκίνησης.

**Το πλήρες σύνολο LOCAL_ONLY.** Η έγκυρη πηγή είναι τα
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` στο
`src/server/authz/routeGuard.ts`· ο παρακάτω πίνακας αντικατοπτρίζει την τρέχουσα κατάσταση. Η πύλη
`check-route-guard-membership` απαριθμεί κάθε `route.ts` κάτω από τα
προθέματα με δυνατότητα εκκίνησης διεργασιών και προκαλεί αποτυχία του CI εάν κάποιο από αυτά δεν έχει ταξινομηθεί ως αποκλειστικά τοπικό.

#### Εξαίρεση για το scope διαχείρισης

Ένα υποσύνολο των διαδρομών LOCAL_ONLY ΜΠΟΡΕΙ επίσης να προσπελαστεί εκτός loopback εάν και
μόνο εάν το αίτημα περιλαμβάνει `Authorization: Bearer <api-key>` του οποίου τα
μεταδεδομένα περιλαμβάνουν το scope `manage` (ή `admin`). Η εξαίρεση ενεργοποιείται
ρητά ανά διαδρομή μέσω του `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, ώστε η
προεπιλογή για κάθε νέα διαδρομή LOCAL_ONLY να παραμένει αυστηρά loopback. Τα μη
επαληθευμένα αιτήματα και τα αιτήματα με κλειδιά χωρίς scope διαχείρισης εξακολουθούν να απορρίπτονται με
`403 LOCAL_ONLY`.

Προς το παρόν, το μόνο πρόθεμα που μπορεί να παρακάμψει τον περιορισμό είναι το `/api/mcp/`. Τα `/api/cli-tools/runtime/` και
`/api/services/` εξαιρούνται σκόπιμα, επειδή μπορούν να εκκινήσουν αυθαίρετες
υποδιεργασίες (`npm install`, `node`), δηλαδή ακριβώς την κατηγορία CVE που το
επίπεδο LOCAL_ONLY έχει σχεδιαστεί να αποτρέπει.

**#7895 — περιορισμένο scope `mcp:connect`:** η εξαίρεση για το `/api/mcp/` δέχεται ΕΠΙΣΗΣ
ένα κλειδί Bearer που διαθέτει το περιορισμένο scope `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), το οποίο ελέγχεται μέσω της
`hasMcpConnectOrManageScope()` στο `src/server/authz/policies/management.ts`.
Αυτό περιορίζεται ΜΟΝΟ στο `/api/mcp/` — το `mcp:connect` δεν παραχωρεί κανένα δικαίωμα σε οποιαδήποτε άλλη
διαδρομή διαχείρισης (συμπεριλαμβανομένου κάθε άλλου προθέματος παράκαμψης LOCAL_ONLY, εάν προστεθεί
ποτέ κάποιο) και εξαιρείται σκόπιμα από το
`MANAGEMENT_API_KEY_SCOPES`. Ένα κλειδί που διαθέτει `manage`/`admin` εξακολουθεί να περνά την
εξαίρεση ακριβώς όπως πριν· το `mcp:connect` αποτελεί μια εναλλακτική χαμηλότερων προνομίων
για απομακρυσμένους καλούντες αποκλειστικά MCP, οι οποίοι δεν θα πρέπει να χρειάζονται ευρεία πρόσβαση διαχείρισης.

| Αίτημα                                              | Διαδρομή                   | Αποτέλεσμα                    |
| --------------------------------------------------- | -------------------------- | ----------------------------- |
| Εκτός loopback, χωρίς Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με scope `manage`            | `/api/mcp/*`               | Επιτρέπεται                   |
| Εκτός loopback, Bearer με scope `mcp:connect`       | `/api/mcp/*`               | Επιτρέπεται                   |
| Εκτός loopback, Bearer χωρίς `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με scope `mcp:connect`       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Εκτός loopback, Bearer με scope `manage`            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                |
| Loopback, με οποιοδήποτε/χωρίς Bearer               | οποιοδήποτε LOCAL_ONLY     | Επιτρέπεται (ο έλεγχος περνά) |

#### Οδηγίες για διαχειριστές και έλεγχος

Εάν εκτελείτε το OmniRoute πίσω από reverse proxy ή tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), ο έλεγχος loopback εξακολουθεί να προστατεύει τις παραπάνω διαδρομές
που μπορούν να εκκινήσουν διεργασίες — ένα αίτημα του οποίου η διεύθυνση πελάτη δεν είναι loopback απορρίπτεται με
`403 LOCAL_ONLY` **πριν εκτελεστεί ο έλεγχος ταυτότητας**, επομένως ένα JWT που έχει διαρρεύσει δεν μπορεί να προκαλέσει εκκίνηση διεργασίας. Παραμένουν δύο
ευθύνες για τον διαχειριστή:

- **Μην «διορθώνετε» ένα 403 πλαστογραφώντας τη διεύθυνση IP του πελάτη ως loopback.** Ο ορισμός
  `X-Forwarded-For: 127.0.0.1` ή η χρήση διακομιστή μεσολάβησης που επανεγγράφει τη διεύθυνση προέλευσης ως
  loopback επανεκθέτει ακριβώς την κατηγορία RCE που αποκλείει αυτό το επίπεδο. Εκθέστε τον
  πίνακα ελέγχου/API μέσω του διακομιστή μεσολάβησης — ποτέ τις διαδρομές με δυνατότητα εκκίνησης διεργασιών.
- **Διατηρήστε ελάχιστη την παράκαμψη με scope `manage`.** Μόνο το `/api/mcp/` μπορεί να παρακαμφθεί και
  μόνο με κλειδί API που έχει scope `manage`. Τα `SPAWN_CAPABLE_PREFIXES` δεν μπορούν ποτέ να
  προστεθούν στη λίστα παράκαμψης — το σχήμα zod τα απορρίπτει και το
  `isLocalOnlyBypassableByManageScope` τα απορρίπτει κατά την εκτέλεση (άμυνα σε βάθος),
  κάτι που εννοεί ο πίνακας ελέγχου με τη φράση «δεν μπορεί να καταστεί παρακάμψιμο». Η ίδια
  λίστα αποκλεισμού περιλαμβάνει επίσης μερικές διαδρομές LOCAL_ONLY που δεν εκκινούν διεργασίες, αλλά επίσης δεν πρέπει
  να είναι ποτέ προσβάσιμες απομακρυσμένα — `/api/oauth/kiro/auto-import` (διαβάζει τοπικά αρχεία
  διαπιστευτηρίων Kiro του host), `/api/discovery/` και `/api/issue-agent/`. Ο φορτωτής στιγμιοτύπων
  κατά την εκτέλεση αφαιρεί επίσης τέτοιες καταχωρίσεις από μια αποθηκευμένη γραμμή ρυθμίσεων και η
  εισαγωγή παλαιού τύπου JSON (`/api/settings/import-json`) δεν εγγράφει ποτέ τα κλειδιά παράκαμψης.
  Κάθε καταχώριση `LOCAL_ONLY_API_PREFIXES` πρέπει είτε να βρίσκεται στη λίστα αποκλεισμού είτε
  να έχει ελεγχθεί ως επιλέξιμη για παράκαμψη (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Οι διαδρομές
  με δυνατότητα εκκίνησης διεργασιών, με δυναμικά τμήματα και στατικές διαδρομές, κάτω από το `/api/providers/` (π.χ. `/login`,
  `/refresh-cursor`) καλύπτονται από τα συνοδευτικά `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS`, τα οποία βασίζονται σε κανονικές εκφράσεις, στο
  `src/shared/constants/spawnCapablePrefixes.ts`, και όχι από τον επίπεδο πίνακα
  `SPAWN_CAPABLE_PREFIXES` — ο επίπεδος πίνακας θα έπρεπε να καλύπτει ολόκληρο το
  πρόθεμα `/api/providers/` για να τις εντοπίζει, διευρύνοντας υπερβολικά ένα δέντρο διαδρομών
  που οι απομακρυσμένοι πίνακες ελέγχου χρησιμοποιούν νόμιμα για λειτουργίες CRUD παρόχων.

**Έλεγχος πρόσβασης** — για να επαληθεύσετε ότι τίποτα εκτός host δεν φτάνει σε αυτές τις διαδρομές:

- Ανοίξτε το **Ευρετήριο εξουσιοδότησης** στη διεύθυνση `/dashboard/settings/security`: εμφανίζει τη
  ζωντανή λίστα προθεμάτων LOCAL_ONLY, ποια προθέματα μπορούν να παρακαμφθούν και το σύνολο
  με δυνατότητα εκκίνησης διεργασιών («δεν μπορεί να καταστεί παρακάμψιμο») που καθορίζεται κατά τη μεταγλώττιση.
- Αναζητήστε στα αρχεία καταγραφής του reverse proxy / πρόσβασης τα παραπάνω προθέματα σε συνδυασμό με
  διεύθυνση πελάτη που δεν είναι loopback. Κάθε τέτοια πρόσβαση που επέστρεψε `200` αντί για
  `403 LOCAL_ONLY` σημαίνει ότι ο διακομιστής μεσολάβησης αποκρύπτει την πραγματική IP του πελάτη — διορθώστε τον.
- Ένα `403 LOCAL_ONLY` στα αρχεία καταγραφής του OmniRoute για μία από αυτές τις διαδρομές σημαίνει ότι ο μηχανισμός προστασίας
  λειτουργεί όπως προβλέπεται· δεν είναι σφάλμα που πρέπει να κατασταλεί.

### Επίπεδο 2 — ALWAYS_PROTECTED

**Επιβάλλεται από:** `isAlwaysProtectedPath(path)` → παρακάμπτει την παράκαμψη `requireLogin=false`
**Παράκαμψη:** Καμία όταν `requireLogin=false`· απαιτείται πάντα JWT

Αυτές οι διαδρομές είναι καταστροφικές ή μη αναστρέψιμες. Αν επιτρέπονταν σε μια εγκατάσταση
«χωρίς κωδικό πρόσβασης», οποιοσδήποτε στο ίδιο LAN θα μπορούσε να διαγράψει τη βάση δεδομένων ή να τερματίσει τη
διεργασία του διακομιστή.

| Διαδρομή                                  | Αιτία                                                                         |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| `/api/shutdown`                           | Τερματίζει τη διεργασία του διακομιστή                                        |
| `/api/settings/database`                  | Εξαγωγή, εισαγωγή και διαγραφή της βάσης δεδομένων                            |
| `/api/db-backups`                         | Πρόσβαση στο πλήρες αρχείο αντιγράφων ασφαλείας της βάσης δεδομένων           |
| `/api/settings/export-json`               | Εξάγει το πλήρες blob ρυθμίσεων (συμπερ. μυστικών)                            |
| `/api/settings/import-json`               | Αντικαθιστά το πλήρες blob ρυθμίσεων                                          |
| `/api/providers/health-autopilot/actions` | Εκτελεί ενέργειες αποκατάστασης του autopilot                                 |
| `/api/settings/obsidian`                  | Εκδίδει επαναχρησιμοποιήσιμα διαπιστευτήρια WebDAV για οποιαδήποτε ρίζα vault |

**Απόκριση σε παραβίαση:** `401 Authentication required`

Το `/api/settings/obsidian` καλύπτει το θυγατρικό του `/webdav`: το `POST` κατευθύνει την υπηρεσία αρχείων WebDAV —
η οποία εξυπηρετείται από το προσαρμοσμένο επίπεδο Node πριν από το Next.js, εκτός αυτής της διοχέτευσης — σε μια ρίζα
που επιλέγει ο καλών και επιστρέφει τα πρόσφατα εκδοθέντα διαπιστευτήρια Basic, το `DELETE` τα ανανεώνει και το γονικό `POST` αποθηκεύει
το token του REST API του Obsidian. Το GHSA-62vw απέκρυψε μόνο την αποκάλυψη κωδικού πρόσβασης μέσω `GET`· η έκδοση
παρέμενε στο επίπεδο fail-open (GHSA-7pq4-8pvv-rx7r). Το `enableObsidianVaultSync()` επιπλέον
απορρίπτει ένα vault που είναι ο κατάλογος δεδομένων, βρίσκεται μέσα σε αυτόν ή τον περιέχει.

#### Οι εξαγωγές διαπιστευτηρίων προορίζονται μόνο για τον χειριστή

Το παραπάνω επίπεδο αποφασίζει μόνο αν απαιτείται _κάποιο_ διαπιστευτήριο. Οι διαδρομές που πραγματοποιούν λήψη
αποθηκευμένων διαπιστευτηρίων προσθέτουν έναν δεύτερο έλεγχο στον handler: τα `GET /api/settings/export-json` (αποκρυπτογραφημένες
συνδέσεις παρόχων και ακατέργαστα κλειδιά API), `GET /api/db-backups/export` (το αρχείο SQLite) και
`GET /api/db-backups/exportAll` (το πλήρες αρχείο) καλούν το `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Δέχεται μια συνεδρία πίνακα ελέγχου, το τοπικό υποκείμενο CLI ή
μια εγκατάσταση με απενεργοποιημένη σύνδεση και απαντά με `403` σε κλειδιά API οποιουδήποτε scope (συμπεριλαμβανομένων των `manage`
και `admin`) και σε access tokens `oma_`. Η έκδοση token συγχρονισμού (`POST /api/sync/tokens`) χρησιμοποιεί τον
ίδιο βοηθό, μαζί με το αξιόπιστο token εσωτερικής υπηρεσίας loopback.

### Η αρχικοποίηση νέας εγκατάστασης είναι μόνο για loopback — βάσει του πραγματικού peer, όχι του `Host`

Όταν δεν έχει διαμορφωθεί κωδικός πρόσβασης διαχείρισης (και δεν υπάρχει `INITIAL_PASSWORD`), το `isAuthRequired()` στο
`src/shared/utils/apiAuth.ts` διατηρεί την ανώνυμη αρχικοποίηση ανοικτή **μόνο για loopback peers**.
Το loopback καθορίζεται από τα αξιόπιστα σήματα του peer, με την εξής σειρά: το token που έχει ενσωματωθεί στον πραγματικό TCP peer
(`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, αυτό που βλέπει η πολιτική), η ετυμηγορία
`AUTHZ_HEADER_PEER_LOCALITY` της ίδιας της διοχέτευσης (αυτό που βλέπουν οι handlers διαδρομών, αξιόπιστο μόνο όταν
έχει οριστεί το `OMNIROUTE_PEER_STAMP_TOKEN`) ή ένας πραγματικός socket peer για άμεσους καλούντες. Τα `Host` /
`nextUrl.hostname` δεν λαμβάνονται ποτέ υπόψη και η αρχική εγγραφή κωδικού πρόσβασης
(`POST /api/settings/require-login`) υπόκειται στον ίδιο περιορισμό, αντί να είναι ανοικτή σε κάθε
peer του δικτύου (GHSA-7pq4-8pvv-rx7r). Το `managementPolicy` μεταβιβάζει ρητά τη δική του ετυμηγορία
`peerContext`, ώστε τα headers του ΑΡΧΙΚΟΥ αιτήματος (πριν από την αφαίρεσή τους) να μην την καθορίζουν ποτέ.

### Επίπεδο 3 — MANAGEMENT (προεπιλογή)

Όλες οι υπόλοιπες διαδρομές διαχείρισης. Απαιτείται έλεγχος ταυτότητας, εκτός εάν έχει ρυθμιστεί το `requireLogin=false`. Τα διακριτικά CLI μπορούν να χρησιμοποιηθούν για έλεγχο ταυτότητας σε αυτές τις διαδρομές (loopback + έγκυρο HMAC).

## Σειρά αξιολόγησης

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → συνέχισε στο επόμενο βήμα
     → non-loopback, Bearer με manage-scope
        ΚΑΙ isLocalOnlyBypassableByManageScope   → επέτρεψε (management_key)
     → διαφορετικά                               → απόρριψε με 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → επέτρεψε (system)
  3. hasValidCliToken(headers)?
     → επέτρεψε (cli) [loopback + έλεγχος HMAC με timingSafeEqual]
  4. isAlwaysProtectedPath(path) ή requireLogin=true?
     → isDashboardSessionAuthenticated?
        → επέτρεψε (dashboard_session)
     → Bearer με manage-scope σε μη παρακάμψιμη διαδρομή;
        → επέτρεψε (management_key)
     → απόρριψε με 401/403
  5. requireLogin=false?
     → επέτρεψε (anonymous)
```

Ο κλάδος manage-scope του βήματος 1 είναι η μόνη αυθεντικοποιημένη διαδρομή που μπορεί να ικανοποιήσει μια διαδρομή
LOCAL_ONLY· σε περίπτωση αποτυχίας του auth-backend επιστρέφεται 503 (όχι 403), ώστε μια
ληγμένη DB να μην υποβαθμίζεται σιωπηρά σε "deny".

## Προσθήκη νέας διαδρομής με δυνατότητα spawn

1. Προσθέστε το πρόθεμα διαδρομής στο `LOCAL_ONLY_API_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
2. Προσθέστε μια δοκιμή στο `tests/unit/authz/routeGuard.test.ts` που να επαληθεύει ότι το
   `isLocalOnlyPath()` επιστρέφει true για το νέο πρόθεμα
3. **Μην παραλείψετε ποτέ αυτό το βήμα** — δείτε τον Αυστηρό Κανόνα #15 στο `CLAUDE.md`
4. Αποφασίστε: ανήκει αυτή η διαδρομή ΕΠΙΣΗΣ στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`;
   Η προεπιλεγμένη απάντηση είναι **όχι**. Επιλέξτε το μόνο όταν η διαδρομή είναι ασφαλές να εκτεθεί σε έναν
   κάτοχο manage-scope (δηλαδή ΔΕΝ εκκινεί αυθαίρετο κώδικα ελεγχόμενο από τον χρήστη).

## Προσθήκη διαδρομής παρακάμψιμης μέσω manage-scope

1. Επιβεβαιώστε ότι η διαδρομή δεν εκτελεί κώδικα ή εντολές που παρέχονται από τον χρήστη. Αν το
   κάνει, σταματήστε — αυτή η εξαίρεση δεν είναι το κατάλληλο εργαλείο.
2. Προσθέστε το πρόθεμα στο `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` στο
   `src/server/authz/routeGuard.ts`
3. Προσθέστε κάλυψη στο `tests/unit/authz/management-policy.test.ts` και για τις τέσσερις
   μορφές αιτήματος: χωρίς Bearer (403), manage Bearer (επιτρέπεται), μη-manage Bearer
   (403), και τη δοκιμή παλινδρόμησης ανά πρόθεμα που διασφαλίζει ότι το `/api/cli-tools/runtime/*` παραμένει
   αυστηρά loopback ακόμη και με manage Bearer.

## Τεκμηρίωση επιπέδων ασφαλείας στο OpenAPI

Κατά την προσθήκη μιας νέας διαδρομής στο `docs/openapi.yaml`, εφαρμόστε την αντίστοιχη
επέκταση προμηθευτή, εάν η διαδρομή ταξινομείται από το `routeGuard.ts`:

| Ταξινόμηση routeGuard.ts       | Σχολιασμός YAML             | Επιβολή                                              |
| ------------------------------ | --------------------------- | ---------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`      | `x-loopback-only: true`     | Αποκλείεται άνευ όρων από non-loopback               |
| `ALWAYS_PROTECTED_API_PATHS`   | `x-always-protected: true`  | Απαιτείται auth ακόμη και με `requireLogin=false`    |
| Εσωτερική διαδρομή admin/debug | `x-internal: true`          | Κρυφή από το /dashboard/api-endpoints από προεπιλογή |
| Καμία (δημόσια / τυπικό auth)  | (δεν απαιτείται σχολιασμός) | Τυπική πρόσβαση ελεγχόμενη από το `requireLogin`     |

### Επικύρωση

Δύο scripts επιβάλλουν τη συνέπεια μεταξύ των σχολιασμών YAML και του `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — αποτυγχάνει αν η κάλυψη είναι < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — αποτυγχάνει αν οι σχολιασμοί `x-loopback-only` ή
  `x-always-protected` αποκλίνουν από τις σταθερές χρόνου μεταγλώττισης

Και τα δύο scripts εκτελούνται στο pre-commit hook και στο CI.

### Κανόνας ψευδώς θετικών αποτελεσμάτων

Αν το `x-always-protected` ή το `x-loopback-only` έχει προστεθεί ως σχολιασμός σε μια διαδρομή που ΔΕΝ βρίσκεται στη
σταθερά του `routeGuard.ts`, το script κάλυψης αποτυγχάνει. Η διόρθωση είναι πάντα η ευθυγράμμιση του
YAML με ό,τι πραγματικά επιβάλλει το `routeGuard.ts` — όχι η προσθήκη διαδρομών στο `routeGuard.ts`
χωρίς να υλοποιηθεί επίσης η λογική επιβολής.
