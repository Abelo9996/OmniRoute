## 概述

所有 OmniRoute 管理 API 路由均歸類為三種保護層級之一。分類是靜態的，定義於 `src/server/authz/routeGuard.ts`，並會在執行任何其他驗證分支之前進行評估。

## 層級

### 層級 1 — LOCAL_ONLY

**強制執行方式：** `isLocalOnlyPath(path)` → 回環主機檢查  
**略過方式：** 預設無法略過。若請求攜帶具有 `manage` 範圍的有效 API 金鑰，則對
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 中的路徑提供有限的例外
（請參閱[管理範圍例外](#manage-scope-carve-out)）。

這些路由會產生子程序或執行執行階段程式碼。若將其暴露給非回環流量，
取得有效 JWT 的攻擊者（例如透過 Cloudflared/Ngrok 通道）便可觸發程序產生——
這是一種已知的 CVE 類型
（[GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)）。

**GHSA-fhh6-4qxv-rpqj 的意義（攻擊類型）：** 管理／代理伺服器
暴露了一個可啟動子程序（`npm install`、`node`、瀏覽器、
代理伺服器、`git`、`tar`……）的端點。如果該端點可從主機外部存取——例如
操作者將 OmniRoute 放在 nginx/Cloudflare/Tailscale 通道後方，而 JWT
遭到洩漏，或驗證設定錯誤——攻擊者便能將「呼叫 API」轉變為「在主機上執行
命令」（遠端程式碼執行）。OmniRoute 會在每個可產生程序的路由上，
**無條件地在任何驗證檢查之前強制執行回環主機檢查**，藉此封鎖此類攻擊：
即使權杖透過通道洩漏，仍無法觸及程序產生功能。

**完整的 LOCAL_ONLY 集合。** 權威來源為
`src/server/authz/routeGuard.ts` 中的
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`；下表反映目前的狀態。
`check-route-guard-membership` 關卡會列舉可產生程序之前綴下的每個
`route.ts`，若其中任何一個未被歸類為僅限本機，CI 就會失敗。

#### 管理範圍例外

部分 LOCAL_ONLY 路徑也可以從非迴路位址存取，前提是且僅限於
請求帶有 `Authorization: Bearer <api-key>`，且其
中繼資料包含 `manage` 範圍（或 `admin`）。此例外透過
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` 針對各路徑明確控管，因此
任何新增 LOCAL_ONLY 路徑的預設行為仍是嚴格限制為迴路位址。未經驗證的
請求，以及使用不具管理範圍之金鑰的請求，仍會遭到拒絕並回傳
`403 LOCAL_ONLY`。

目前唯一可略過此限制的前綴是 `/api/mcp/`。`/api/cli-tools/runtime/` 與
`/api/services/` 被刻意排除，因為它們可以建立任意
子程序（`npm install`、`node`），而這正是
LOCAL_ONLY 層所要防範的 CVE 類型。

**#7895 — `mcp:connect` 窄化範圍：** `/api/mcp/` 例外也接受
持有窄化 `mcp:connect` 範圍的 Bearer 金鑰
（`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`），並透過
`src/server/authz/policies/management.ts` 中的 `hasMcpConnectOrManageScope()` 進行檢查。
此範圍僅適用於 `/api/mcp/` — `mcp:connect` 不會授予任何其他
管理路由的權限（包括未來可能新增的任何其他 LOCAL_ONLY 略過前綴），且它被刻意排除於
`MANAGEMENT_API_KEY_SCOPES` 之外。持有 `manage`/`admin` 的金鑰仍會
與先前完全相同地通過此例外；`mcp:connect` 是權限較低的替代方案，
適用於不應需要廣泛管理存取權限的遠端 MCP 專用呼叫端。

| 請求                                             | 路徑                       | 結果             |
| ------------------------------------------------ | -------------------------- | ---------------- |
| 非迴路位址，無 Bearer                            | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍            | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍       | `/api/mcp/*`               | 允許             |
| 非迴路位址，Bearer 不具有 `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `mcp:connect` 範圍       | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 非迴路位址，Bearer 具有 `manage` 範圍            | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY   |
| 迴路位址，有或無任何 Bearer                      | 任何 LOCAL_ONLY            | 允許（通過閘門） |

#### 操作者指引與稽核

如果您在反向代理或通道（nginx、Caddy、Cloudflare
Tunnel、Tailscale、Ngrok）後方執行 OmniRoute，迴路位址檢查仍會保護上述
可建立程序的路由 — 用戶端位址為非迴路位址的請求會
在**執行驗證前**遭到拒絕並回傳 `403 LOCAL_ONLY`，因此即使 JWT 外洩也無法觸發程序建立。
操作者仍需承擔兩項責任：

- **請勿透過將用戶端 IP 偽造成回送位址來「修正」403。** 設定
  `X-Forwarded-For: 127.0.0.1`，或使用會將來源位址改寫為
  回送位址的代理，會重新引入此層級原本封鎖的同類 RCE 漏洞。請透過代理公開
  儀表板/API，而絕不可公開具備產生程序能力的路由。
- **將 manage 範圍的繞過機制維持在最低限度。** 只有 `/api/mcp/` 可以被繞過，而且
  只能使用具備 `manage` 範圍的 API 金鑰。`SPAWN_CAPABLE_PREFIXES` 絕不可
  加入繞過清單——zod schema 會拒絕它們，而
  `isLocalOnlyBypassableByManageScope` 也會在執行階段予以拒絕（縱深防禦），
  這正是儀表板中「無法設為可繞過」的含義。同一份
  拒絕清單也包含少數不會產生程序、但同樣絕不可從遠端存取的 LOCAL_ONLY 路由——
  `/api/oauth/kiro/auto-import`（讀取主機本機的 Kiro
  認證檔案）、`/api/discovery/` 與 `/api/issue-agent/`。執行階段
  快照載入器也會從已儲存的設定資料列中移除這類項目，而
  舊版 JSON 匯入（`/api/settings/import-json`）絕不會寫入繞過金鑰。
  每個 `LOCAL_ONLY_API_PREFIXES` 項目都必須位於拒絕清單中，或經過審查並確認
  可繞過（`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`）。位於
  `/api/providers/` 下、具有動態區段與靜態路徑且具備產生程序能力的路由（例如 `/login`、
  `/refresh-cursor`），由
  `src/shared/constants/spawnCapablePrefixes.ts` 中以正規表示式為基礎的
  `SPAWN_CAPABLE_PATTERNS` /
  `SPAWN_CAPABLE_PATTERN_ANCESTORS` 配套機制涵蓋，而不是由扁平的
  `SPAWN_CAPABLE_PREFIXES` 陣列涵蓋——若要捕捉這些路由，扁平陣列就必須涵蓋
  整個 `/api/providers/` 前綴，這會過度擴大限制範圍，波及遠端儀表板為提供者 CRUD
  而合理使用的路由樹。

**稽核存取情況**——若要確認主機外部沒有任何請求抵達這些路由：

- 在 `/dashboard/settings/security` 開啟 **授權清冊**：其中會呈現即時的
  LOCAL_ONLY 前綴清單、哪些前綴可被繞過，以及編譯時期的
  具備產生程序能力（「無法設為可繞過」）集合。
- 在反向代理／存取記錄中搜尋上述前綴，並比對非回送的用戶端位址。任何這類命中若回傳
  `200` 而非 `403 LOCAL_ONLY`，即表示代理遮蔽了真實的用戶端 IP——請修正代理。
- OmniRoute 記錄中，這些路徑之一出現 `403 LOCAL_ONLY`，表示防護機制正按預期運作，
  並不是應予抑制的錯誤。

### 第 2 層級 — ALWAYS_PROTECTED

**強制執行者：** `isAlwaysProtectedPath(path)` → 略過 `requireLogin=false` 繞過機制
**繞過：** `requireLogin=false` 時仍無法繞過；一律需要 JWT

這些路由具有破壞性，或其操作不可逆。若在「無密碼」安裝中允許存取，
就表示同一個 LAN 上的任何人都能清除資料庫或終止伺服器程序。

| 路徑                                      | 原因                                            |
| ----------------------------------------- | ----------------------------------------------- |
| `/api/shutdown`                           | 終止伺服器程序                                  |
| `/api/settings/database`                  | 資料庫匯出、匯入及清除                          |
| `/api/db-backups`                         | 完整資料庫備份封存檔存取                        |
| `/api/settings/export-json`               | 匯出完整設定資料（包括機密資訊）                |
| `/api/settings/import-json`               | 取代完整設定資料                                |
| `/api/providers/health-autopilot/actions` | 執行自動駕駛修復動作                            |
| `/api/settings/obsidian`                  | 為任何 vault 根目錄簽發可重複使用的 WebDAV 認證 |

**違規時的回應：** `401 Authentication required`

`/api/settings/obsidian` 涵蓋其 `/webdav` 子路徑：`POST` 會將 WebDAV 檔案服務——
由自訂 Node 層在 Next.js 之前提供，因此位於此管線之外——指向呼叫者選擇的根目錄，
並回傳新簽發的 Basic 認證；`DELETE` 會輪替這些認證，而父路徑的 `POST` 則會儲存
Obsidian REST API token。GHSA-62vw 僅遮蔽了 `GET` 洩露密碼的問題；簽發功能仍位於
失效開放層級（GHSA-7pq4-8pvv-rx7r）。`enableObsidianVaultSync()` 還會拒絕符合下列
任一情況的 vault：本身就是資料目錄、位於資料目錄內，或包含資料目錄。

#### 認證匯出僅限操作員

上述層級僅決定是否需要_某種_認證。下載已儲存認證的路由會在處理常式中加入第二項檢查：
`GET /api/settings/export-json`（解密後的提供者連線與原始 API 金鑰）、
`GET /api/db-backups/export`（SQLite 檔案）以及
`GET /api/db-backups/exportAll`（完整封存檔）會呼叫 `requireOperatorCredential()`
（`src/lib/api/operatorCredential.ts`）。它接受儀表板工作階段、本機 CLI 主體，或
停用登入的執行個體；對任何範圍的 API 金鑰（包括 `manage` 與 `admin`）以及
`oma_` 存取權杖則回應 `403`。同步權杖簽發（`POST /api/sync/tokens`）使用相同的
輔助函式，另加受信任的回送內部服務權杖。

### 全新安裝的啟動程序僅限回送位址——依據真實對等端，而非 `Host`

若未設定管理密碼（且沒有 `INITIAL_PASSWORD`），
`src/shared/utils/apiAuth.ts` 中的 `isAuthRequired()` 會**僅對回送對等端**開放
匿名啟動程序。回送判定會依序使用受信任的對等端訊號：由權杖標記的真實 TCP 對等端
（`PEER_IP_HEADER` + `VIA_PROXY_HEADER`，即原則所見的資訊）、管線自身的
`AUTHZ_HEADER_PEER_LOCALITY` 判定結果（即路由處理常式所見的資訊，僅在
`OMNIROUTE_PEER_STAMP_TOKEN` 已設定時才受信任），或直接呼叫者的真實 socket
對等端。絕不會參照 `Host` /
`nextUrl.hostname`，而首次密碼寫入
（`POST /api/settings/require-login`）也受同一限制，不會對每個網路對等端開放
（GHSA-7pq4-8pvv-rx7r）。`managementPolicy` 會明確向下傳遞其自身的
`peerContext` 判定結果，因此原始（剝除前）請求的標頭絕不會決定該結果。

### 第 3 層級 — MANAGEMENT（預設）

所有其他管理路由。除非設定 `requireLogin=false`，否則需要驗證。CLI 權杖可驗證這些路由（迴路位址 + 有效的 HMAC）。

## 評估順序

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → 繼續執行
     → 非 loopback、具 manage 範圍的 Bearer
        且 isLocalOnlyBypassableByManageScope   → 允許 (management_key)
     → 否則                                      → 拒絕 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → 允許 (system)
  3. hasValidCliToken(headers)?
     → 允許 (cli) [loopback + timingSafeEqual HMAC 檢查]
  4. isAlwaysProtectedPath(path) 或 requireLogin=true?
     → isDashboardSessionAuthenticated?
        → 允許 (dashboard_session)
     → 在不可繞過路徑上具 manage 範圍的 Bearer？
        → 允許 (management_key)
     → 拒絕 401/403
  5. requireLogin=false?
     → 允許 (anonymous)
```

步驟 1 的 manage 範圍分支，是唯一能滿足 LOCAL_ONLY 路由的已驗證路徑；驗證後端失敗時會傳回 503（而非 403），因此過期的 DB 不會在無提示的情況下降級為「拒絕」。

## 新增可啟動程序的路由

1. 將路徑前綴新增至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_API_PREFIXES`
2. 在 `tests/unit/authz/routeGuard.test.ts` 中新增測試，斷言
   `isLocalOnlyPath()` 對新前綴傳回 true
3. **絕不可略過此步驟** — 請參閱 `CLAUDE.md` 中的硬性規則 #15
4. 決定：此路由是否也應納入 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`？
   預設答案為**否**。僅當該路由能安全地公開給 manage 範圍持有者時，才選擇加入（亦即不會啟動任意由使用者控制的程式碼）。

## 新增可由 manage 範圍繞過的路徑

1. 確認該路由不會執行使用者提供的程式碼或命令。如果會，請停止 — 此例外機制並不適用。
2. 將前綴附加至
   `src/server/authz/routeGuard.ts` 中的 `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`
3. 在 `tests/unit/authz/management-policy.test.ts` 中，針對所有四種請求形式新增測試涵蓋：無 Bearer（403）、manage Bearer（允許）、非 manage Bearer（403），以及每個前綴的迴歸測試，確保 `/api/cli-tools/runtime/*` 即使帶有 manage Bearer，仍嚴格限制為 loopback。

## 在 OpenAPI 中記錄安全層級

將新路由新增至 `docs/openapi.yaml` 時，若該路由由 `routeGuard.ts` 分類，請套用對應的提供者擴充欄位：

| routeGuard.ts 分類           | YAML 註記                  | 強制執行方式                          |
| ---------------------------- | -------------------------- | ------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`    | `x-loopback-only: true`    | 無條件封鎖來自非 loopback 的請求      |
| `ALWAYS_PROTECTED_API_PATHS` | `x-always-protected: true` | 即使 `requireLogin=false` 仍要求驗證  |
| 內部管理員／偵錯路由         | `x-internal: true`         | 預設不顯示於 /dashboard/api-endpoints |
| 無（公開／標準驗證）         | （不需要註記）             | 由標準 `requireLogin` 控制的存取      |

### 驗證

有兩個指令碼會強制確保 YAML 註記與 `routeGuard.ts` 之間的一致性：

- `scripts/check/check-openapi-coverage.mjs` — 若涵蓋率低於 99%，則執行失敗
- `scripts/check/check-openapi-security-tiers.mjs` — 若 `x-loopback-only` 或
  `x-always-protected` 註記與編譯期常數不一致，則執行失敗

這兩個指令碼都會在 pre-commit hook 和 CI 中執行。

### 誤判規則

若某個路由標有 `x-always-protected` 或 `x-loopback-only`，但未列於
`routeGuard.ts` 常數中，涵蓋率指令碼將會失敗。修正方式一律是讓 YAML 與
`routeGuard.ts` 實際強制執行的內容保持一致，而不是在尚未實作強制執行邏輯的情況下，逕自將路由新增至 `routeGuard.ts`。
