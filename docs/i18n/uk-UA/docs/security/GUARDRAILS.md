> **Джерело істини:** `src/lib/guardrails/`
> **Останнє оновлення:** 2026-08-29 — v3.8.51 (Походження стенограми Video Bridge оголошується абонентом,
> ще не перевірено сервером — уточнено згідно з #11661)

Захисні механізми забезпечують безпеку, політику та трансформації вмісту на межі між OmniRoute та вищестоящими провайдерами. Кожен захисний механізм може перевіряти (та за бажанням відхиляти, трансформувати або анотувати) корисні навантаження запитів (`preCall`) та відповіді вищестоящих систем (`postCall`).

Система є **відкритою при збої**: якщо захисний механізм видає помилку під час виконання, реєстр записує помилку та продовжує роботу з наступним захисним механізмом, замість того, щоб відхиляти запит. Блокування є явним рішенням (`block: true`), а не випадковістю.

| Пріоритет | Назва               | Етап(и)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |

### Міст для зображень (`visionBridge.ts`) — міст модальностей PR-1

Перехоплює запити із зображеннями, спрямовані до **моделей без підтримки зображень**, і або
переспрямовує весь запит до моделі з підтримкою зображень, або замінює частини із
зображеннями текстовими описами, створеними налаштовуваною моделлю з підтримкою
зображень, перш ніж виконати висхідний виклик. Це дає змогу постачальникам, що
підтримують лише текст, прозоро обробляти мультимодальні корисні навантаження.

Послідовність:

1. Пропустити, якщо цільова модель уже підтримує зображення (якщо тільки вона не
   входить до списку моделей із примусовим застосуванням мосту
   `isVisionBridgeForcedModel`).
2. Витягти частини із зображеннями за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує роботу **уніфікованому детектору
   медіаданих** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` — єдиному
   джерелу істини, спільному з фільтром сумісності комбінацій.
   Витягування обмежено дозволеним списком частин верхнього рівня, форми яких
   `replaceImageParts` може вставити назад (контракт витягування↔заміни): OpenAI
   `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL
   `source.type:"url"` і Responses API `input_image`. Вкладені збіги та
   форми, що містять лише індикатори, призначені для фільтра комбінацій і ніколи
   не витягуються. Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію середовища виконання через
   `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань
   `modalityBridge*` мають перевагу; застарілі ключі `visionBridge*` залишаються
   **резервним варіантом на один цикл** (вікно відкочування). Якщо міст вимкнено,
   пропустити до будь-якого обходу медіаданих.
4. Селектор режиму (`modalityBridgeVisionMode`, див. таблицю нижче) визначає,
   чи виконувати переспрямування або опис. Переспрямування повертає
   `modifiedPayload`, у якому замінено лише `model`, а також метадані
   `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити кількість зображень значенням `maxImages`, сформувати
   запит з урахуванням завдання, перевірити кеш описів, викликати модель із
   підтримкою зображень **паралельно** (`Promise.allSettled`) і вставити замість
   зображень текстові частини `[Image N]: <description>`. Невдалий опис дає
   `null`, а вихідна частина із зображенням **зберігається** (#4012) — за
   винятком комбінованого шляху опису, коли всі спроби опису завершилися
   невдало: у цьому разі для підтвердженого висхідного сервісу без підтримки
   зображень використовується заглушка
   `(недоступно — не підключено жодного постачальника з підтримкою зображень)`
   (#8430).
6. Повернути `modifiedPayload` + метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режиму (`modalityBridgeVisionMode`)

| Режим      | Типовий | Поведінка                                                                                                                                                                                                                                                                                                                                                |
| ---------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | Застаріла евристика без змін (#6640/#7204): моделі, що не є комбінованими, і моделі `auto/` переспрямовуються до найкращої моделі з підтримкою зображень, якщо тільки вихідна модель уже не має придатних облікових даних (тоді виконується опис); комбіновані цілі завжди використовують опис.                                                          |
| `describe` |         | Завжди виконувати опис — блок переспрямування повністю пропускається; відповідь завжди надає вибрана користувачем модель.                                                                                                                                                                                                                                |
| `reroute`  |         | Примусове переспрямування: перевірка збереження моделі з обліковими даними оминається. Перевірка облікових даних **цілі** переспрямування все одно застосовується — якщо придатної цілі з підтримкою зображень немає, запит переходить до опису, щоб необроблені зображення ніколи не потрапляли до серверної частини, яка підтримує лише текст (#8430). |

Примусові режими виконують раннє завершення **до** запуску автоматичної
евристики; поведінка `auto` побайтово ідентична захисному механізму до PR-1.

#### Область дії ключа API (`visionBridgeKeyScope.ts`)

Коли ключ API викликувача обмежує `allowedConnections`, пули квот
(`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає лише
ті моделі переспрямування й опису, які дозволено використовувати цьому ключу,
через підключення, які дозволено використовувати цьому ключу. Після цього
виклик опису завжди проходить через самозациклення OmniRoute із заголовком
`x-omniroute-self-loop-key-id`, тому чат-запит, що його отримує, повторно
застосовує політику підключень і моделей цього ключа. `enforceApiKeyPolicy()`
враховує цей заголовок лише разом із токеном носія самозациклення, тому він
може лише звужувати доступ, а ідентифікатор, який не вдається розпізнати,
відхиляється.

Якщо для ключа не дозволено жодної моделі з підтримкою зображень, шлях опису
не втручається, а запит передається без змін — це така сама відмовостійка
поведінка з пропуском, як і для вимкненого захисного механізму (метадані
`{ skipped: true, reason: "no_permitted_vision_model" }`).
Запити без ключа та ключі без цих обмежень працюють так само, як і раніше.

#### Запит опису з урахуванням завдання (`modalityBridgeVisionTaskAware`)

Типове значення — **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає
текст **останнього повідомлення користувача** (обрізаний до 500 символів) до базового
запиту опису, спрямовуючи опис на те, про що насправді запитав користувач
(патерн codex-vision-proxy), і просить модель зору транскрибувати видимий
текст. Якщо прапорець вимкнено або текст користувача відсутній, базовий запит
використовується без змін.

Власний OpenAI-сумісний запит циклу самоопису (`callVisionModelSingle()`
у `visionBridgeHelpers.ts`) завжди запитує `image_url.detail: "high"` —
безумовно, для кожного виклику/провайдера, незалежно від будь-якого сигналу клієнта.
Вибірка з низькою деталізацією погіршує точність OCR саме для завдання
транскрибування тексту, якого вимагає цей запит, тому сам виклик опису завжди
запитує високу деталізацію незалежно від рівня деталізації у вихідному вхідному
запиті. Це впливає лише на тіло внутрішнього запиту опису; це не змінює того,
як OmniRoute пересилає власне значення `image_url.detail` виклику в основному
запиті — це типове значення застосовується окремо й лише для виявлених клієнтів
OpenCode у `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`).
Гілка формату обміну Anthropic у циклі самоопису не має поля `detail`, тому
жодне із цих типових значень на неї не впливає.

#### Обмеження виводу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | Типове значення | Діапазон          |
| ------------------------------ | --------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`             | `0` або 100–50000 |

`0` (типове значення) означає **без обмеження** — опис, повернутий
`callVisionModel()`, передається без змін, зберігаючи поточну
поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із
суфіксом `…`, перш ніж його буде вставлено назад як `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`).
Збільшуйте це значення для насичених деталями завдань OCR, де подальшій моделі
потрібна повна транскрипція; зменшуйте його, щоб обмежити використання токенів
багатослівними моделями зору. Поле панелі керування розташоване в розділі
Advanced вкладки Vision (`modality-bridge-max-chars` у
`ModalityBridgeVisionTab.tsx`) і підвищує будь-яке значення від 1 до 99 до
мінімуму 100, залишаючи явно вказаний `0` без змін — `0` сам по собі є
припустимим значенням Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не лише
типовим значенням «не задано».

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Внутрішньопроцесний кеш LRU + TTL для результатів опису, спільний для всього
процесу. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із
фреймінгом за префіксом довжини (без колізій на межах полів). Компонент моделі —
це **налаштована** модель мосту, а не модель, яка фактично відповіла:
`callVisionModel` може внутрішньо перейти на резервну модель, а створення ключа
для кожної спроби фрагментувало б кеш. Невдалі описи ніколи не кешуються.
Налаштування:

| Ключ                            | Типове значення | Діапазон |
| ------------------------------- | --------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`          | —        |
| `modalityBridgeCacheTtlMinutes` | `60`            | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`           | 10–5000  |

#### Нормалізація віддалених зображень (самоопис/отримання base64)

Коли міст самостійно отримує **віддалене** зображення — для самовиклику опису
Anthropic і перетворення у base64 для формату обміну Claude
(`ensureBase64ImagesForClaudeWire`), в обох випадках через
`fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts` — отриманий URI даних
перед вбудовуванням у запит до моделі зору передається через `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`). Надмірно великі зображення зменшуються до
**2048px за довгою стороною** (відповідно до обмеження розміру, яке OpenAI/Anthropic
уже застосовують на стороні сервера), що зменшує обсяг переданих даних і затримку,
не змінюючи того, що бачить модель зору. Для зміни розміру використовується
`sharp`, завантажуваний через динамічний імпорт: на платформі, де не вдається
завантажити його нативний бінарний файл, `normalizeDataUri()` **ніколи не
викидає виняток** — натомість він без змін передає вихідні байти, тому шлях
опису/перетворення у base64 завжди продовжує працювати. Байти, що не є
зображенням (якщо отримані дані неможливо декодувати як зображення), також
передаються без змін. Ця нормалізація обмежена зображеннями, які міст отримує
для власного самовиклику, — вона ніколи не застосовується до необробленого
наскрізного корисного навантаження виклику, відповідно до принципу внесення змін
лише за явною згодою (жорстке правило №20).

#### Схема налаштувань і міграція

Нові ключі `modalityBridge*` перевіряються за допомогою Zod в
`updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`):
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трійка
`modalityBridgeCache*` і група `modalityBridgeAudio*`, яку використовує Audio
Bridge. Міграція `141_modality_bridge_settings.sql` копіює наявні застарілі
значення `visionBridge*` до відповідних нових ключів (ідемпотентно, ніколи не
перезаписуючи встановлене оператором значення `modalityBridge*`); застарілі ключі
продовжують прийматися як резервний варіант читання протягом одного циклу випуску.

#### Заголовок прозорості та статистика

Відповіді, перетворені шляхом опису, містять
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(створюється `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`,
додається `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`).
Перенаправлені запити **не** отримують заголовка — корисне навантаження не
змінювалося, а заміну моделі вже видно в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (автентифікація керування, той самий рівень, що й
`GET /api/settings`) повертає внутрішні лічильники в пам’яті для кожної модальності
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та
`video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як
знаменник; операція без вимірювання часу не створює штучний зразок із нульовою
тривалістю в мілісекундах. `bridged` залишається зворотно сумісним псевдонімом
для успішних перетворень; невдалі спроби не збільшують його значення.
Лічильники навмисно скидаються під час перезапуску процесу
(телеметрія, а не облік).

#### Конфігурація панелі керування

Окрема сторінка панелі керування розташована за адресою
`/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio`
та `Video`, адресовані через URL, зберігають параметри запиту під час зміни
значення `tab`. Вкладка Vision надає налаштування ввімкнення, режиму, вибору
моделі (включно з автоматичним значенням за замовчуванням), підказок з урахуванням
завдання, розширених обмежень часу очікування/зображення/довжини опису/кешу,
лічильники середовища виконання та захищений приклад запиту. Вкладка Audio також
активна: вона надає налаштування ввімкнення, засіб вибору лише STT-моделей із
варіантом Auto, обмеження часу очікування/максимальної тривалості кліпу, лічильники
аудіо та тестовий приклад `input_audio`. Вкладка Video є функціональною: вона
повідомляє стан FFmpeg/ffprobe у середовищі виконання — один із чотирьох явних
станів інтерфейсу (`unknown`, поки перевірка виконується або не може завершитися,
`restricted` на хості панелі керування, що не є loopback-хостом, де перевірка
пропускається на стороні клієнта, `unavailable` після виконання перевірки й
підтвердження відсутності або `available` із версіями FFmpeg/ffprobe) — зберігає
обмеження ввімкнення/моделі/кадрів/відео/часу очікування, фільтрує засіб вибору
моделі, залишаючи моделі з підтримкою зору, і відображає лічильники відео.

Колишня картка Vision Bridge у налаштуваннях ШІ є посиланням для сумісності на
нову сторінку; вона більше не містить другої копії форми. Media Providers також
пов’язує робочі процеси Image-to-Text і Speech-to-Text із відповідними вкладками
Modality Bridge, не видаляючи наявний тестовий майданчик Speech-to-Text.

**Обхід допуску для самозациклення:** коли виклик опису маршрутизується через
власне самозациклення OmniRoute `/v1` (нестандартна модель провайдера), підзапит
надсилає `x-omniroute-admission-bypass: internal` та автентифікується за допомогою
визначених облікових даних самозациклення — локального маркера `sk_omniroute` у
локальному режимі або налаштованого оператором ключа середовища
`OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб розгортання з
`REQUIRE_API_KEY=true` усе одно могли виконувати виклик опису. Обхід приймається
лише для цих точних облікових даних, тому зовнішні клієнти не можуть
використовувати заголовок для пропуску допуску.

Застарілі значення за замовчуванням містяться в
`src/shared/constants/visionBridgeDefaults.ts`; нові значення за замовчуванням
для режиму/врахування завдання/кешу та засіб визначення налаштувань містяться в
`src/shared/constants/modalityBridgeDefaults.ts`. Захисний механізм надає
параметр конструктора `deps`, щоб тести могли впроваджувати підроблені реалізації
`getSettings` і `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює запити чату, що містять аудіо, до того, як вони потраплять до цільового
об’єкта, про який не відомо, чи приймає він аудіовхід. Він ніколи не
перемаршрутизує запит чату: аудіочастини транскрибуються через наявну сумісну з
OpenAI multipart-кінцеву точку, а вибрана модель чату продовжує роботу з
текстовими транскриптами.

Потік:

1. Визначити `supportsAudio` через `getResolvedModelCapabilities()`. Явні
   метадані реєстру провайдерів мають пріоритет, далі йдуть статичні метадані
   моделі, а потім синхронізовані `modalities_input`. Оголошений список вхідних
   даних без `audio` означає `false`; якщо свідчень про можливості немає,
   значення залишається `null`. І `false`, і `null` активують консервативний
   міст, тоді як `true` обходить його.
2. Визначити налаштування `modalityBridgeAudio*` і видобути придатні для
   заміщення аудіочастини верхнього рівня з кожного повідомлення через спільний
   детектор `detectMediaParts()`. Підтримувані формати передавання — OpenAI
   `input_audio`, `audio_url` і `source.media_type: "audio/*"`. Вкладене аудіо
   виявляється для маршрутизації, але не видаляється шляхом заміщення. Обсяг
   роботи обмежується `modalityBridgeAudioMaxClips`; наступні частини залишаються
   незміненими.
3. Використати налаштований `provider/model` або дозволити
   `selectAudioBridgeModel()` пройти `AUDIO_TRANSCRIPTION_PROVIDERS` у
   стабільному порядку каталогу та вибрати першу модель із придатними активними
   обліковими даними провайдера.
4. `callAudioTranscription()` перетворює аудіо у форматі base64/data-URI на
   multipart-`file` або завантажує віддалений `audio_url` через захист вихідних
   з’єднань лише з публічними адресами, із закріпленням DNS і обмеженням 25 MB.
   Потім він надсилає файл і вибрану модель методом POST до локального
   самозациклення `/v1/audio/transcriptions`, автентифікованого за допомогою
   `resolveSelfLoopBearer()`. Наявний маршрут транскрибування виконує звичайний
   пошук облікових даних, обробку періодів очікування/обмежень частоти запитів і
   диспетчеризацію провайдеру.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики
   виконуються за допомогою `Promise.allSettled`: окрема помилка зберігає
   відповідну початкову аудіочастину (контракт #4012). Якщо всі виклики
   завершуються невдало, а для цільового об’єкта доведено
   `supportsAudio === false`, частини стають
   `[Audio N]: (недоступно — не підключено жодного STT-провайдера)` (контракт
   #8430). Для невідомого цільового об’єкта (`null`) результат із суцільними
   помилками залишається незміненим. Цільовий об’єкт, для якого доведено
   підтримку лише тексту й немає придатних облікових даних STT, отримує таку
   саму явну заглушку без виконання мережевого виклику.

Успішні транскрипти використовують спільний для всього процесу LRU/TTL-кеш
Modality Bridge. Ключ поєднує посилання на аудіо, стабільну мітку операції
`audio-transcription` і вибрану STT-модель; помилки ніколи не кешуються. Спроби
обробки аудіо оновлюють спільні лічильники `bridged`, `cacheHits`, `failures` і
`lastUsedAt`. Перетворені відповіді містять
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені
запити не отримують сегмент Audio Bridge.

Налаштування середовища виконання зберігаються в БД і перевіряються через Zod:

| Ключ                          | Типове значення | Діапазон        |
| ----------------------------- | --------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`          | —               |
| `modalityBridgeAudioModel`    | `""`            | Auto або ID STT |
| `modalityBridgeAudioTimeout`  | `60000`         | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`             | 1–10            |

Спільний кеш і надалі контролюється параметрами `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` і `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює відеочастини верхнього рівня в `messages` Chat Completions і `input`
Responses API перед викликом цільового компонента, для якого не заявлено нативну
підтримку відео. Підтримувані формати: `input_video`, `video_url`, `video_source`,
HTTPS URL-адреси та URI даних `data:video/*;base64,...`. Звичайні імена файлів у
тексті не розглядаються як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запиту,
перевірку можливостей і політик, агрегацію в межах запиту та корисне навантаження
відповіді. Обробка окремого відео — отримання даних, кешування повного результату,
опис послідовності кадрів (з об’єднанням будь-якої заявленої викликачем
аудіотранскрипції), а також метрики, переривання та очищення для кожної спроби —
прихована за `processVideoPart` у `videoBridgePipeline.ts`, яка викликається один
раз для кожної відеочастини всередині циклу `preCall`. Цей модуль також визначає
явні межі портів `VideoMediaBrokerPort` (отримання байтів і видобування вибіркових
кадрів), `VideoAudioTranscriptionPort` (об’єднання заявленої викликачем
аудіотранскрипції з підписами вибіркових кадрів) і `VideoDrilldownPort` (межа
збереження деталізації кадрів; ще не підключена до `processVideoPart` — наразі
записи деталізації створює лише окремий маршрут
`/api/modality-bridge/video/drilldown`).

Публічний шлях запиту `/v1` ніколи не імпортує й не викликає підпроцес. Віддалені
відео завантажуються з обмеженням у 50 МіБ; вбудовані відео base64 мають
консервативне обмеження декодованого розміру 36 МіБ на відео, щоб оболонка
моделі, повідомлень і фреймінгу залишалася в межах публічного ліміту приймання
JSON-запитів у 50 МіБ. Довжина вбудованих даних і оцінки декодованого розміру
перевіряються до виділення пам’яті. HTTPS обов’язковий для початкової віддаленої
URL-адреси та кожного переспрямування; використовується наявний захист вихідних
підключень лише до публічних адрес із закріпленням DNS. Потім байти перетинають
точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей
маршрут одночасно має позначки `LOCAL_ONLY` і `SPAWN_CAPABLE`, приймає лише
автентифікований у межах процесу запит через довірений loopback-інтерфейс і
ніколи не приймає URL-адресу, шлях файлової системи, виконуваний файл або список
аргументів. Конвеєр обмеження розміру тіла API та інкрементальний зчитувач тіла
обробника незалежно один від одного забезпечують обмеження вхідних даних брокера
у 50 МіБ. Його обмежена черга виконує по одному видобуванню за раз, допускає
чотири завдання в очікуванні та обмежує обсяг вхідних даних в очікуванні до
100 МіБ.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список
дозволених форматів виключає формати списків відтворення та маніфестів. Для
дозволених контейнерів сімейства MOV зовнішні посилання на дані MOV за
замовчуванням залишаються вимкненими, а фіксована команда не вмикає їх.
І `ffprobe`, і `ffmpeg` використовують список дозволених протоколів лише з
`file`, один потік, фіксовані масиви аргументів, не використовують оболонку, а
виконувані файли знаходяться через `PATH`. Потоки обкладинок із прикріпленими
зображеннями не вважаються кандидатами для відтворення. Усі придатні для
відтворення потоки мають відповідати обмеженням; явно визначеному типовому потоку
надається перевага перед детермінованим резервним вибором потоку з найнижчим
індексом. Відео обмежені тривалістю 600 секунд, 8 192 пікселями на вимір і
33 554 432 вихідними пікселями. FFmpeg відбирає 1–16 проміжних JPEG-кадрів у
серединних точках, зменшує довгу сторону щонайбільше до 1 024 пікселів, не
збільшуючи менші вхідні дані, і ніколи не отримує URL-адресу. За замовчуванням
використовується вибірка `uniform`. Необов’язкова політика `scene_aware` та
експериментальна політика `segment_aware` виконують один додатковий фіксований
прохід FFmpeg уже перевіреним локальним потоком, вибирають обмежені часові мітки
сцен `showinfo` і детерміновано повертаються до тих самих рівномірних серединних
точок у разі помилки детектора, перевищення часу очікування, некоректного
виведення або порожнього набору кандидатів. Режим з урахуванням сегментів
розподіляє вибірки серединних точок пропорційно до перевірених інтервалів сцен;
докази з урахуванням сегментів і резервну поведінку докладно описано нижче.
Жорстке обмеження у 16 кадрів застосовується після вибору для кожної політики.
Коли запит з урахуванням сцен має бюджет лише на один кадр, використовується
рівномірна серединна точка активного вікна всього відео або вікна фокусування, а
в результаті зазначається `policyEffective: uniform`: один вибраний кадр сцени
не може зберегти обидві часові межі. Викликач може за бажанням надати скінченне
вікно фокусування (`start`/`end` у секундах); межі обмежуються тривалістю
медіафайлу, вікна зі зворотним порядком меж або нескінченними значеннями
відхиляються, а всі політики вибірки застосовуються лише в межах нормалізованого
інтервалу. Отримане вікно включається до метаданих вибірки та до ненадійного
префікса опису, щоб подальші моделі могли відрізнити сфокусований уривок від
повної часової шкали.

Семантичне фокусування підписів — це окреме явне налаштування. Типовий режим
аналізу `full` зберігає наявний запит для кадрів і ніколи не передає текст запиту
моделі створення підписів. У режимі `focused` міст зчитує лише найновіший
непорожній текст `text`/`input_text`, створений користувачем, із того самого
контейнера Chat або Responses, нормалізує його до NFC, згортає керівні символи
та пробіли й обмежує до 500 кодових точок Unicode. Порожній результат призводить
до повернення до точного запиту режиму `full`. Придатна підказка серіалізується
як JSON у спеціальному блоці ненадійного користувацького контексту й може лише
визначати пріоритетність спостережуваних деталей; вона не може скасувати окреме
попередження не виконувати інструкції, які видно або чути в медіафайлі. Текстове
фокусування ніколи не виводить значення `start`/`end` і не змінює часовий
семплер.

#### Структурні докази сегментів FU-07

`segment_aware` використовує один обмежений прохід попереднього аналізу вже перевіреного
локального відеопотоку. Фіксований ланцюжок фільтрів спочатку масштабує відео до ширини
не більше ніж 320 пікселів, виявляє зміни сцен і завмерлі інтервали, а потім виконує
вибірку з частотою 1 кадр на секунду для оцінювання розмиття, середньої яскравості
та просторової/часової інформації. Прохід обмежено 600 структурними вибірками, одним
потоком FFmpeg/фільтра, тим самим протоколом лише для `file` і списками дозволених
контейнерів, лімітом у 1 МіБ для виведення процесу та щонайбільше 30 секундами
в межах спільного переривання/граничного терміну брокера. Він ніколи не приймає
команду, фільтр, шлях або URL із запиту.

Структурні значення є детермінованими даними вибірки, а не семантичним розумінням
відео. Вони не визначають суб’єктів, дії, підписи, мовлення чи наміри користувача.
Межі сцен і завмерлих інтервалів формують сегменти; покриття завмерлих інтервалів,
розмиття, експозиція, просторова деталізація та часові зміни впливають лише на те,
як розподіляється наявний бюджет у 1–16 кадрів. Для повністю завмерлого сегмента
встановлено обмеження в один кадр, тоді як незавмерлі сегменти конкурують за решту
бюджету. Коли меж більше, ніж кадрів, зберігається рівномірне покриття часової шкали,
щоб швидкі ранні монтажні склейки не могли приховати довгий кінцевий сегмент. Межі
сцен, що перебувають у межах 1-секундної роздільності аналізу від межі завмерлого
інтервалу, об’єднуються.

Відсутні фільтри, некоректні/порожні дані, помилка детектора або перевищення
обмеженого часу попереднього аналізу призводять до відкритого відмовостійкого
переходу до точної політики рівномірного вибору середніх точок. Переривання з боку
викликувача або досягнення граничного терміну брокера не спричиняє такого переходу:
воно завершує активний підпроцес, запобігає подальшому видобуванню кадрів, а приватне
тимчасове дерево видаляється у `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` створює детерміновані реальні фікстури FFmpeg
для оцінювання скорочення кількості викликів створення підписів після дедуплікації,
розподілу бюджету за умов інтенсивного руху, даних про розмиття/експозицію/SI-TI,
швидких монтажних склейок із довгим кінцевим сегментом і хибнопозитивних спрацювань
під час поступового затемнення. Скрипт записує фактичний час попереднього аналізу,
а там, де доступна `/usr/bin/time`, — процесорний час дочірнього процесу та піковий
RSS. Його перевірки якості є лише структурними оракулами. Якість реальної моделі
створення підписів залишається `HOLD`, оскільки цей стенд не має авторизованої
кінцевої точки або зафіксованого оцінювача. Грошова економія також залишається
`HOLD`, якщо `--caption-cost-per-call-usd` не задає явну додатну оцінку вартості
одного виклику; скрипт ніколи не фабрикує жоден із цих результатів.

Розмір кожного кадру обмежено 4 МіБ, сукупний розмір усіх необроблених кадрів —
23 МіБ, а розмір серіалізованої відповіді брокера — 32 МіБ. Приватний тимчасовий
каталог видаляється у `finally`. OmniRoute не постачає FFmpeg у комплекті та не
приймає власний шлях до виконуваного файлу. Перед створенням підписів міст застосовує
консервативний прохід візуальної дедуплікації: кожен JPEG зменшується до буфера
16×16 у відтінках сірого та порівнюється лише з останнім збереженим кадром. Якщо
запитаний бюджет підписів перевищує один кадр, видобування формує обмежений пул
кандидатів розміром щонайбільше вдвічі більшим за цей бюджет і ніколи не більшим
за 16 кадрів. Запитане обмеження застосовується лише після дедуплікації, а перший
і останній вибрані кандидати зберігаються під час остаточного проріджування, якщо
бюджет становить щонайменше два кадри. Версіонована політика
`grayscale-16x16-mean-cells-v2` використовує більше зі значень: середню різницю
яскравості або частку комірок мініатюри, нормалізована різниця яких становить
щонайменше 0.05. Порогове значення дублювання є сталою 0.04, обраною заради
передбачуваності, а не наданою як параметр середовища виконання. Цей вторинний
висококонтрастний сигнал зберігає невеликі рухи та зміни видимого тексту, які може
приховати порівняння лише за середнім значенням. Помилки компаратора або декодера
обробляються відкрито зі збереженням покриття. Метадані виведення окремо зазначають
видобутих кандидатів, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена відеочастина може запитувати контактний аркуш із часовими позначками.
Міст створює JPEG-сітку щонайбільше з 4 стовпців і 16 кадрів. У кожну 512-піксельну
комірку часова позначка джерела вписується у висококонтрастну нижню смугу, а ті самі
часові позначки зберігаються в текстових метаданих для подальшого зіставлення та
аудиту. Розмір повного JPEG залишається обмеженим 32 МіБ. Якщо `sharp` не може
декодувати або скомпонувати сітку, міст повертається до окремих JPEG-кадрів;
переривання клієнта все одно поширюється на операцію з контактним аркушем.

Докази для просування навмисно відокремлено від синтетичного мікробенчмарку
компонування. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає
A/B-стенд із версіонованою схемою для реальних моделей комп’ютерного зору,
сумісних з OpenAI. Він вимірює кількість токенів, повідомлену постачальником,
наскрізну фактичну затримку (включно з компонуванням контактного аркуша),
кількість викликів моделі та збереження фактів, визначених маніфестом. Необроблені
відповіді моделі не записуються у звіт; зберігаються лише дайджести SHA-256 та
ідентифікатори збігів фактів. Стенд не здійснює жодних мережевих чи платних
викликів моделі, якщо не передано `--execute-real` і не налаштовано `--model`,
`OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без такого явного реального запуску
його машинозчитуваний вердикт залишається `HOLD`; самі лише синтетичні вимірювання
корисного навантаження/кількості викликів не є доказами для просування.

Викликувачі можуть додати необов’язковий масив `transcript.cues` до підтримуваної
відеочастини, якщо вони вже мають синхронізований текст. Кожна репліка повинна
містити `text`, скінченний інтервал `start`/`end` у межах визначеної тривалості
та значення `source` з білого списку (`client`, `embedded` або `audio-bridge`);
значення `confidence` за замовчуванням дорівнює `1` і має залишатися в діапазоні
від `0` до `1`. Точні дублікати реплік згортаються. OmniRoute ніколи не запускає
транскрибування на основі цих метаданих: перевірені репліки копіюються до описаного
результату разом із джерелом, упевненістю та інтервалом і відображаються як
ненадійні спостереження поруч із підписами кадрів. Некоректний текст, текст поза
допустимим діапазоном або текст без зазначеного походження відхиляється, а не
змішується з потоком підписів. Обидва канали транскрипту в тілі запиту нормалізують
надане походження до `client`, включно із самостійно заявленими позначками
`embedded` або `audio-bridge`. Лише адаптер під керуванням сервера може призначати
ці довірені позначки через доступний лише з коду аргумент `trustedSource`; поле JSON
запиту не може передати значення цьому аргументу. Текст транскрипту залишається
ненадійним вмістом, отриманим із медіа, незалежно від його походження, і ніколи
не повинен визначати авторизацію.

Досвідчений викликальник може надати доріжку `audioTranscript` для того самого відео;
вона розглядається як текст, наданий клієнтом, а не як підтвердження серверної транскрипції.
На межі об’єднання візуальні й аудіоспостереження обробляються з
єдиним кінцевим терміном і сигналом переривання, упорядковуються на спільній часовій шкалі,
точні дублікати згортаються, а коли успішною є лише одна сторона, повертається
частковий результат.
Недійсний `audioTranscript` призводить до такого часткового результату — візуальний
опис зберігається, а аудіогілка записує санітизований код помилки —
замість збою обробки всього відео. Доступність кожної гілки, прапорець часткового
результату та санітизовані коди помилок зберігаються в описаному результаті, у
метаданих захисного механізму (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), у метаданих кешу результатів і в лічильниках
об’єднання мосту. Стандартний шлях Video Bridge не запускає перетворення мовлення на текст
і не завантажує другу копію медіафайлу; без явно наданої доріжки він залишається
суто відеошляхом.

**Зберігання транскрипту (#12150 P1).** Це застосовується автоматично щоразу, коли
Video Bridge (який сам є опціональним) відтворює репліку транскрипту — окремого
прапорця зберігання немає. Коли запит відтворює будь-яку репліку транскрипту (оголошений викликальником
`transcript` або об’єднаний `audioTranscript`), захисний механізм позначає його як
`videoBridgeObserved` і створює відредаговану тінь відеоопису —
ідентичне відтворення, у якому довільний текст кожної репліки замінено на
`[redacted-video-transcript]`; вона створюється шляхом підстановки структурованого поля репліки
до складання рядка (а не шляхом розбору зведеного тексту, тож жоден вміст
репліки — зловмисний чи звичайний, зокрема текст, що містить `]`, як-от
`[inaudible]`/`[music]`, — не може зберегтися). У збереженому тілі запиту журналу викликів
кожна текстова частина, отримана з відео, замінюється цією відредагованою тінню зі
зіставленням за рівністю вмісту; опорне значення `fullText` повторно зчитується із завершеного корисного навантаження
захисного механізму перед викликом, тому зіставлення залишається успішним після того, як наступні
ланцюгові захисні механізми (маскувальники персональних даних і облікових даних із пріоритетами 10/95)
змінюють текст опису безпосередньо, а також після того, як ін’єкція системної підказки,
передавання контексту та пам’яті змінює структуру масиву повідомлень. Тіло,
надіслане моделі, не змінюється. Для спостережуваного запиту також не заповнюється
довготривала Memory (видобування як із запиту, так і з відповіді пропускається),
тож власна відповідь моделі не може відлунити текст транскрипту в Memory.

**Необроблені поля відео (#12430).** Коли міст увімкнено, а підтримка нативного відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після невдалого створення опису або досягнення обмеження `maxVideos`. `null` і порожні рядки враховуються; відсутні поля та метадані, що не стосуються відео, — ні. У збережених копіях ці поля редагуються або запит вилучається, а кеші/Memory обходяться.

На цих резервних шляхах дійсні репліки, надані викликальником, стають підтримуваними частинами `text`/`input_text`,
а не нестандартними полями постачальника. Обидві надані в запиті доріжки
залишаються ненадійними спостереженнями `client` із явним попередженням, що відео
не було описано, а часові позначки не перевірялися за медіафайлом. Наявні
обмеження у 256 реплік/64 КіБ загалом і для кожної репліки застосовуються до обох доріжок разом;
часові позначки мають вкладатися в 600-секундну межу брокера та будь-яке надане
вікно фокусування. Недійсні доріжки відкидаються, а не пересилаються як довільний текст;
дійсна споріднена доріжка все одно може використовуватися, якщо не перевищено їхній сукупний бюджет.
Поля зі значенням null або порожні поля не додають тексту. Цей резервний механізм не додає
отримання медіафайлів або транскрипцію.
Поля розширення транскрипту вилучаються з резервного контейнера відео та його
об’єктів `video_url`/`source`. Суворий список дозволених полів протоколу OpenAI не змінюється; нативні
відеоконтейнери з невідомою підтримкою залишаються доступними, а відомі цілі лише для тексту зберігають безпечні маркери.
Структуровані тіні редагування захищають доданий текст транскрипту, тоді як
початковий запит, що належить викликальнику, залишається незмінним. Цілі з нативною підтримкою та
вимкнені мости зберігають наявну поведінку обходу.

Додаткові збережені копії використовують той самий сигнал спостережуваного запиту. Необроблений
знімок клієнтського запиту до застосування захисного механізму, очікуваний запит у пам’яті та журнал
запиту, відхиленого на ранньому етапі, структурно замінюють поля транскрипту у відеочастинах;
рядкові підказки, синтезовані етапами конвеєра та передаванням контексту, редагуються
в місці збереження тіла запиту. Збережений маркер `video_content_removed`
змушує продовження `previous_response_id` завершуватися безпечною відмовою замість відновлення
тексту, який було навмисно видалено. Якщо спостережуваний запит утрачає свою
тінь редагування для окремої частини до журналювання або хоча б одну з кількох відеотіней
не вдається зіставити після наступних змін запиту, збережене тіло запиту
вилучається повністю замість зберігання частково відредагованого транскрипту.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину
транскрипту без структурованої межі репліки. Тому її збережене поле журналу викликів
`responseBody` замінюється маркером вилучення; детальний
артефакт конвеєра (який може містити тіла даних від постачальника/клієнта та фрагменти потоку)
не зберігається. Кеші семантики, ідемпотентності та повторного відтворення міркувань
не виконують читання й запис для такого запиту. Запит до постачальника та видима клієнту
відповідь залишаються незмінними. Ранні байти підтримання з’єднання видаляються з тимчасового
буфера, коли детальний артефакт вилучається. Попередження Kiro про некоректний EventStream
повідомляє лише кількість байтів корисного навантаження, але ніколи не його вміст або необроблену помилку
парсера JSON.
Це не є твердженням, що всі не пов’язані з цим діагностичні дані постачальників/плагінів було
перевірено; ширше охоплення місць зберігання відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремою,
автентифікованою за допомогою loopback/токена основою кешу. Для кожної операції
також потрібен канонічний непрозорий ID принципала. Перш ніж активувати
продукційний виклик, він має отримувати цей ID з автентифікованого тенанта й
ніколи не передавати значення, вибране клієнтом. Ключі кешу пов’язують цього
принципала з канонічними ID сесії та посилання на відео, зберігають лише їхні
ключі, похідні від SHA-256, і обмежують як читання, так і видалення тим самим
принципалом. Кеш зберігає щонайбільше 16 похідних JPEG-кадрів на запис, видаляє
їх після десяти хвилин і підтримує обмежене читання за `start`/`end` або явне
видалення сесії.

Для кожного принципала встановлено обмеження у 16 записів і 64 MiB канонічних
JPEG-даних. Ці обмеження не залежать від глобальної межі у 64 записи/256 MiB:
тиск на квоту принципала спочатку витісняє лише найдавніше використані записи
цього принципала, а вже потім розглядається глобальне LRU-витіснення. Під час
активності кешу прострочені записи вилучаються як з обліку принципала, так і з
глобального обліку, тоді як скасування та помилка валідації не фіксують часткову
заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, дані не у форматі JPEG,
пошкоджені або обрізані JPEG-файли, а також JPEG-файли, що спричиняють
попередження під час обмеженого повного декодування зображення за допомогою
`sharp`. Кожне прийняте зображення повторно кодується як канонічний JPEG, а його
ширина й висота визначаються з декодованих байтів без довіри до полів, наданих
викликачем; будь-які кінцеві поліглотні байти відкидаються, а не зберігаються.
До обох квот зараховується лише обмежений канонічний стиснений буфер. Обмеження
передавання JSON враховує накладні витрати Base64 для граничного обсягу
декодованих вхідних даних у 32 MiB. Для кожного збереженого похідного результату
реєструються перевірені формат і роздільна здатність JPEG, політика вибірки,
версія похідного результату, час створення, обчислений сервером хеш вмісту, а
також хешоване батьківське посилання разом із хешем батьківського вмісту від
довіреного викликача. Скасування перевіряється між асинхронними фазами
декодування й хешування до атомарної фіксації в кеші.

Ця частина роботи ще не підключає продукційного виробника до маршруту й не
забезпечує вибір варіанта з кількох роздільних здатностей. Тому прозорий шлях
запиту Video Bridge не створює додаткової роботи, а прив’язане до тенанта
визначення принципала та повний життєвий цикл FU-08 із кількома роздільними
здатностями залишаються явно визначеною подальшою роботою, а не
задокументованою завершеною поведінкою.

Для кадрів послідовно створюються описи за допомогою налаштованої моделі Video.
Порожнє перевизначення Video успадковує налаштування Vision; якщо обидва
значення порожні, автоматичний маршрутизатор Vision вибирає фактичну модель із
підтримкою візуальних даних. Успішні описи замінюють початкову частину стабільним
префіксом `[Video description:`, який також позначає текст як ненадійне
спостереження, отримане з медіаданих, і вказує наступним моделям не виконувати
інструкції, знайдені в медіа. Ключі кешу описів кадрів включають байти JPEG,
підказку, часову позначку та фактичну модель; кешуються лише успішні описи.
Записи кешу зберігають фактичну модель-виробника, яка успішно створила результат,
включно з резервною моделлю; якщо різні кадри були створені різними моделями,
міст повідомляє `mixed`. У разі влучання в кеш повторно використовується
ідентичність цього виробника, а не змінюється її позначення відповідно до
запитаного плану маршрутизації. Кеш результатів для всього відео має ключ, що
враховує всі вхідні дані, які змінюють результат: підказку, фактичну модель,
політику вибірки, кількість кадрів, режим семантичного аналізу, відбиток SHA-256
нормалізованої підказки щодо фокуса, вікно фокуса, `transcript`,
`audioTranscript` і прапорець контактного аркуша. Тому зміна будь-якого з цих
параметрів призводить до промаху кешу, а не до повторного використання
застарілих даних. Версія політики візуальної дедуплікації, поріг і обмежена
кількість кадрів-кандидатів також явно включаються до ключа й метаданих кешу
результатів; отже, зміна політики не може повторно використати застарілий опис
усього відео. Метадані кешу результатів v4 зберігають режим і відбиток, але
ніколи не зберігають необроблене завдання користувача. Метадані захисних
обмежень повідомляють як запитаний, так і фактичний режими аналізу; запитаний
режим `focused` без придатного тексту користувача повідомляється як фактично
`full`.

Захисне обмеження видобуває всі підтримувані частини відео, але описує не більше
ніж `modalityBridgeVideoMaxVideos`. Для цільової моделі, щодо якої доведено
`supportsVideo === false`, невдалі відео та відео понад ліміт перетворюються на
явні безпечні текстові маркери, щоб жодне необроблене відео не зберігалося. Якщо
можливості невідомі, ці частини зберігають свій відеоконтейнер; будь-який
резервний транскрипт проходить описане вище обмежене перетворення на текст.
Цільові моделі з `supportsVideo === true` обходять міст. Сигнал переривання
клієнтського запиту поширюється на завантаження, чергу брокера, підпроцеси та
виклики створення описів; переривання зупиняють обробку між відео й ніколи не
призводять до небезпечного пропускання необроблених медіаданих.

Налаштування середовища виконання зберігаються в БД та перевіряються за допомогою Zod:

| Ключ                                | Значення за замовчуванням | Діапазон / поведінка                                                                                         |
| ----------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `modalityBridgeVideoEnabled`        | `false`                   | Необов’язкове середовище виконання, активується явно                                                         |
| `modalityBridgeVideoAnalysisMode`   | `"full"`                  | `full` зберігає загальні описи; `focused` використовує обмежений, ненадійний контекст останнього користувача |
| `modalityBridgeVideoModel`          | `""`                      | Успадковує модель Vision Bridge                                                                              |
| `modalityBridgeVideoFrameCount`     | `8`                       | 1–16                                                                                                         |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`               | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора використовується `uniform`  |
| `modalityBridgeVideoMaxVideos`      | `1`                       | 1–4                                                                                                          |
| `modalityBridgeVideoTimeout`        | `120000`                  | 1000–120000 мс                                                                                               |

Збережені застарілі значення тайм-ауту Video, що перевищують 120 секунд, обмежуються
кінцевим терміном брокера; нові спроби записати налаштування понад цю межу відхиляються.
`GET /api/modality-bridge/video/runtime` перед автентифікацією або перевіркою середовища виконання
вимагає довіреної, позначеної локальності зворотного з’єднання, а потім — автентифікації
керування. Він повертає лише `available`, санітизовані версії FFmpeg/ffprobe та фіксовану
причину, коли середовище виконання недоступне. Внутрішня кінцева точка видобування не є
публічним API завантаження: переповнення черги повертає `503` разом із `Retry-After`, від’єднання
викликувачем повертає `499`, а досягнення фіксованого кінцевого терміну брокера повертає `504`. Перетворені відповіді додають
`video->text;model=<visionModel>;parts=<videos>` до центрального
заголовка `x-omniroute-modality-bridge`, не видаляючи сегменти Vision або Audio.

### Маскувальник PII (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` і
  `prompt` (включно з елементами у вигляді звичайних рядків) та застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII редагуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою протидії ін’єкціям у підказки). Коли редагування вимкнене, виклик записує кількість
  виявлень, не переписуючи вміст.
- **`postCall`** створює глибоку копію відповіді, запускає `sanitizePIIResponse()` разом із
  маскувальником структури Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке редагування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або переписує дані.

### Ін’єкція у підказку (`promptInjection.ts`)

Виявляє зловмисні структури у вмісті, наданому користувачем, і забезпечує виконання
налаштованої політики. Поведінка визначається змінними середовища та параметрами
конструктора:

| Налаштування     | Змінна середовища                                                                                           | Значення за замовчуванням | Ефект                                                                                                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Увімкнено        | `INPUT_SANITIZER_ENABLED`                                                                                   | `true`                    | Якщо `false`, захисний механізм завершує роботу достроково.                                                                                                                                          |
| Режим            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                             | `warn`                    | Політика щодо ін’єкцій: `block`, `warn` або `log`. (`redact` підтримується для зворотної сумісності, але **не** видаляє текст ін’єкції; перезапис PII запиту контролюється `PII_REDACTION_ENABLED`.) |
| Поріг блокування | параметр `blockThreshold` / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`                    | Мінімальний рівень серйозності, необхідний для блокування. За замовчуванням середній рівень лише відстежується.                                                                                      |

**Пріоритет режимів** (`getMode`): `options.mode` викликувача →
**перевизначення прапорцем функції з БД** для `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Отже, перевизначення з панелі керування має пріоритет над змінними середовища, тому інтерфейс Feature
Flags керує активним захисним механізмом у реальному часі (без перезапуску). Читання з БД є відмовостійким:
якщо виникає помилка, захисний механізм повертається до поведінки на основі змінних середовища, а коли
перевизначення не задано, поведінка ідентична визначенню лише за змінними середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів,
   що використовується в інших частинах конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` і
   `markdown_system_block`, обидва з рівнем серйозності `high`).
3. Необов’язкові `customPatterns`, передані через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **і** принаймні одне виявлення відповідає пороговому
рівню серйозності, `preCall` повертає `{ block: true, message: "Request rejected:
suspicious content detected" }`. У режимах `warn`/`log` захисний механізм записує
подію в журнал, але дозволяє виклик. Спільний допоміжний засіб
`evaluatePromptInjection()` також експортується для викликачів, яким потрібно
оцінювати промпти без використання реєстру.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ**
об’єднаного тексту промпту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти)
у `src/shared/utils/inputSanitizer.ts`. І `detectInjection()`, і
`evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед
запуском циклу перевірки шаблонів. Директиви ін’єкції розташовуються поблизу
початку вхідних даних, тому це обмежує використання CPU/GC регулярними виразами
для корисних навантажень розміром у сотні КБ без послаблення виявлення (пор.
#3932, #4041).

### Маскувальник облікових даних (`credentialMasker.ts`)

Запускається на **обох** етапах, останнім у стандартному ланцюжку (пріоритет
`95`). Редагує добре відомі шаблони API-ключів / секретних токенів у вихідному
корисному навантаженні (вмісті повідомлень, аргументах викликів інструментів,
результатах інструментів) **і** у відповіді постачальника, щоб облікові дані,
вставлені в промпт (або відтворені в результаті інструмента), не потрапили до
зовнішнього постачальника чи назад до клієнта.

- **Лише за явного ввімкнення**, відповідно до тієї самої домовленості, що й
  редагування PII (суміжне з жорстким правилом №20): вимкнено, якщо
  `settings.credentialRedactionEnabled === true` **або**
  `CREDENTIAL_REDACTION_ENABLED=true` не задано. Коли цей механізм вимкнено,
  захисний бар’єр не виконує жодних дій — він ніколи не блокує й не переписує.
- `redactCredentials()` обходить усе дерево корисного навантаження/відповіді
  (`walkValue()`, із захистом від забруднення прототипу та безпечним опрацюванням
  циклів через `WeakSet`) і замінює збіги заповнювачем `[REDACTED:<type>]`,
  клонуючи лише ті гілки, які фактично змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі постачальників LLM (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні
  ключі (ключ доступу AWS, Twilio, SendGrid, Mailgun), приватні ключі / JWT,
  рядки підключення, що містять облікові дані (`mongodb://user:pass@...` тощо),
  а також загальний шаблон значення заголовка
  `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключі, що мають форму
  заголовків (`authorization`, `x-api-key`, `api-key`, `apikey`), редагуються
  структурно (лише значення, із збереженням префікса схеми, як-от
  `Bearer `/`Basic `), а не за допомогою загального текстового регулярного
  виразу.
- Захисний механізм ніколи не блокує; він лише переписує (`modifiedPayload` /
  `modifiedResponse`) та додає анотації (`meta.credentialsRedacted`,
  `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true перериває ланцюжок
  message?: string; // відображається під час блокування
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Захисний механізм сигналізує про «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що передається ланцюжком до наступних захисних механізмів.
`signal?: AbortSignal` передає життєвий цикл виклику до захисних механізмів. Переривання запиту є навмисним винятком із принципу fail-open: медіамости припиняють роботу й виконують очищення, не відновлюючи необроблені медіадані для цільової системи, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) захисний механізм та пересортовує за зростанням `priority`.
- `clear()` / `list()` — допоміжні функції адміністрування.
- `runPreCallHooks(payload, context)` — ітерує активні захисні механізми, пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — той самий потік на стороні відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан та, за бажанням, повторно реєструє значення за замовчуванням для чистої ізоляції тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`, де `results` — це масив записів `GuardrailExecutionResult`, що містять поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного захисного механізму, корисні для трасування.

### Вимкнення захисних механізмів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує дедуплікований список імен захисних механізмів, які слід пропустити для поточного запиту. Джерела (всі необов'язкові, всі об'єднані):

- `apiKeyInfo.disabledGuardrails`
- Тіло запиту `disabledGuardrails` (верхнього рівня)
- Тіло запиту `metadata.disabledGuardrails`
- Заголовок `x-omniroute-disabled-guardrails` (або застарілий `x-disabled-guardrails`)

Значення можуть бути масивами рядків або рядком, розділеним комами; імена нормалізуються до нижнього регістру в kebab-case (`pii_masker` → `pii-masker`). Результат передається через `context.disabledGuardrails` до реєстру, який пропускає відповідні захисні механізми (`skipped: true` у `results`).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts`:

1.  `resolveDisabledGuardrails(...)` створює список винятків з ключа API, тіла запиту
    та заголовків.
2.  `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні механізми у порядку
    зростання пріоритету:
    - Вимкнені захисні механізми записуються як `skipped`.
    - `preCall` кожного захисного механізму може переписати корисне навантаження
      через `modifiedPayload`.
    - Перший `block: true` перериває ланцюжок, і обробник повертає
      відповідь про відхилення захисним механізмом.
3.  (Потенційно переписане) корисне навантаження надходить до комбінованої маршрутизації
    та вихідної диспетчеризації.
4.  Після формування відповіді `guardrailRegistry.runPostCallHooks(...)`
    запускає той самий ланцюжок на відповіді. `block: true` тут відкидає
    вихідну відповідь.

Захисні механізми, які викликають помилку, записуються з `error: <message>` та
реєструються через `logger.warn`, але ланцюжок продовжується — за задумом,
система працює за принципом "відмова-відкриття".

## Конфігурація

Змінні середовища, які читаються вбудованими захисними механізмами:

| Змінна                                | Використовується               | Ефект                                                                                                          |
| :------------------------------------ | :----------------------------- | :------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`             | Встановіть `false`, щоб повністю вимкнути виявлення.                                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`             | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не переписує текст ін'єкції.         |
| `INJECTION_GUARD_MODE`                | `prompt-injection`             | Режим для захисту від ін'єкцій; також прапорець функції БД, який **перевизначає** змінні середовища (БД > ЗМ). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`             | Мінімальна серйозність, при якій `MODE=block` відхиляє: `high` (за замовчуванням), `medium` або `low`.         |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`             | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`                   | Якщо `true`, PII запиту редагується (незалежно від режиму ін'єкції).                                           |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (нижче за течією) | Контролює поведінку маскувальника на стороні відповіді.                                                        |

Захисні механізми Modality Bridge читають конфігурацію часу виконання зі сховища
налаштувань на основі БД (`getSettings()`), а не зі змінних середовища.
Основними ключами Vision є `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.
Застарілі ключі `visionBridge*` приймаються лише як задокументований
одноцикловий резервний варіант читання; записи на панелі керування
використовують основні ключі. Значення за замовчуванням та резервний
розв'язувач знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`,
а застарілі константи зберігаються в
`src/shared/constants/visionBridgeDefaults.ts`.

Аудіо використовує `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні
налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту
застарілих ключів, оскільки ці ключі були введені зі схемою Modality Bridge.

Відео використовує `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`,
`modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та
`modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`.
Він вимкнений за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими
операційними залежностями, а створення субтитрів кадрів додає затримку та
витрати на модель.

## Користувацькі обмежувачі (Guardrails)

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1.  Створіть `src/lib/guardrails/myGuardrail.ts`, розширюючи `BaseGuardrail`.
2.  Реалізуйте `preCall` та/або `postCall`.
3.  Зареєструйте під час імпорту (виштовхніть з `registerDefaultGuardrails`) або
    викличте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
    будь-який попередній обмежувач з тим самим нормалізованим ім'ям.
4.  Додайте тести до `tests/unit/` (існуючі приклади:
    `tests/unit/guardrails-registry.test.ts`,
    `tests/unit/prompt-injection-guard.test.ts`,
    `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб почати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише обмежувачі, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки для налаштувань, можливостей, вибору моделі STT, перевірок
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва
потоки без доступу до БД або мережі.

## Покриття маршрутів захисту від ін'єкцій та червона команда (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
які приймають підказки користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип              | Маршрути                                                                                                                                             | Режим за замовчуванням |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------- |
| Текст (існуючий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративний     | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані             | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Вилучення тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Червона команда (нічна, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зонди (пропускає без секрету).
`moderations` включено для послідовності — оператори в режимі блокування можуть виключити його через
`resolveDisabledGuardrails`.

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокування)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен ворожий випадок (наприклад, "ігнорувати всі
  попередні інструкції...", "jailbreaks" у стилі DAN) стверджує, що відповідь містить
  `error.code === "SECURITY_001"`, тобто обмежувач фактично відхилив запит.
- **`garak` (консультативний)** — запускає garak `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Залежить від
  секрету провайдера (`PROMPTFOO_PROVIDER_KEY`); пропускається без помилок і має суфікс
  `|| true`, тому він звітує без збою CI.

Покриття допоміжного обмежувача (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що містить підказки; текст підказки витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
