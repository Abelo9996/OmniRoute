## Огляд

Усі маршрути API керування OmniRoute належать до одного з трьох рівнів захисту. Класифікація є статичною, визначається у `src/server/authz/routeGuard.ts` і перевіряється до виконання будь-якої іншої гілки автентифікації.

## Рівні

### Рівень 1 — LOCAL_ONLY

**Забезпечується:** `isLocalOnlyPath(path)` → перевірка loopback-хоста  
**Обхід:** За замовчуванням відсутній. Вузький виняток для шляхів у
`LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, коли запит містить дійсний
API-ключ з областю доступу `manage` (див. [Виняток для області доступу manage](#manage-scope-carve-out)).

Ці маршрути запускають дочірні процеси або виконують код середовища виконання. Надання
доступу до них для трафіку не з loopback-інтерфейсу дозволило б зловмиснику, який отримав дійсний JWT (наприклад,
через тунель Cloudflared/Ngrok), ініціювати запуск процесів — відомий клас
CVE ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**Що таке GHSA-fhh6-4qxv-rpqj (клас атаки):** сервер керування/агента
надає кінцеву точку, яка запускає підпроцес (`npm install`, `node`, браузер,
проксі, `git`, `tar`, …). Якщо ця кінцева точка доступна з-поза хоста — через те, що
оператор розмістив OmniRoute за тунелем nginx/Cloudflare/Tailscale, а JWT
витік або автентифікацію було неправильно налаштовано, — зловмисник перетворює «виклик API» на «виконання
команди на хості» (віддалене виконання коду). OmniRoute усуває цю загрозу, безумовно виконуючи
**перевірку loopback-хоста перед будь-якою перевіркою автентифікації** для кожного
маршруту, здатного запускати процеси: витік токена через тунель усе одно не дає змоги ініціювати запуск.

**Повний набір LOCAL_ONLY.** Авторитетним джерелом є
`LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS` у
`src/server/authz/routeGuard.ts`; наведена нижче таблиця відображає поточний стан. Перевірка
`check-route-guard-membership` перелічує кожен `route.ts` у межах
префіксів, здатних запускати процеси, і спричиняє збій CI, якщо будь-який із них не класифіковано як локальний.

#### Виняток для області керування

До підмножини шляхів LOCAL_ONLY ТАКОЖ МОЖНА отримати доступ не через loopback-інтерфейс тоді й
лише тоді, коли запит містить `Authorization: Bearer <api-key>`, метадані якого
включають область `manage` (або `admin`). Виняток активується
явно для кожного шляху через `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`, тому
за замовчуванням будь-який новий шлях LOCAL_ONLY залишається суворо обмеженим loopback-інтерфейсом. Неавтентифіковані
запити та запити з ключами без області `manage` і надалі відхиляються з
`403 LOCAL_ONLY`.

Наразі єдиним префіксом, для якого дозволений виняток, є `/api/mcp/`. `/api/cli-tools/runtime/` і
`/api/services/` навмисно виключено, оскільки вони можуть запускати довільні
підпроцеси (`npm install`, `node`), а це саме той клас CVE, якому
має запобігати рівень LOCAL_ONLY.

**#7895 — вузька область `mcp:connect`:** виняток для `/api/mcp/` ТАКОЖ приймає
Bearer-ключ із вузькою областю `mcp:connect`
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`), що перевіряється через
`hasMcpConnectOrManageScope()` у `src/server/authz/policies/management.ts`.
Ця область поширюється ЛИШЕ на `/api/mcp/` — `mcp:connect` не надає жодних прав для будь-якого іншого
маршруту керування (включно з усіма іншими префіксами винятків LOCAL_ONLY, якщо
такий колись буде додано), і її навмисно виключено з
`MANAGEMENT_API_KEY_SCOPES`. Ключ з областю `manage`/`admin` і надалі проходить перевірку
винятку так само, як і раніше; `mcp:connect` є альтернативою з нижчим рівнем привілеїв
для віддалених клієнтів, яким потрібен лише MCP і яким не потрібен широкий доступ до керування.

| Запит                                                          | Шлях                       | Результат                      |
| -------------------------------------------------------------- | -------------------------- | ------------------------------ |
| Не через loopback-інтерфейс, без Bearer                        | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не через loopback-інтерфейс, Bearer з областю `manage`         | `/api/mcp/*`               | Дозволити                      |
| Не через loopback-інтерфейс, Bearer з областю `mcp:connect`    | `/api/mcp/*`               | Дозволити                      |
| Не через loopback-інтерфейс, Bearer без `manage`/`mcp:connect` | `/api/mcp/*`               | 403 LOCAL_ONLY                 |
| Не через loopback-інтерфейс, Bearer з областю `mcp:connect`    | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Не через loopback-інтерфейс, Bearer з областю `manage`         | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                 |
| Через loopback-інтерфейс, із будь-яким Bearer або без нього    | будь-який LOCAL_ONLY       | Дозволити (перевірку пройдено) |

#### Рекомендації для операторів і аудит

Якщо ви запускаєте OmniRoute за зворотним проксі або тунелем (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok), перевірка loopback-інтерфейсу й надалі захищає наведені вище
маршрути, здатні запускати процеси: запит, адреса клієнта якого не належить до loopback-інтерфейсу, відхиляється з
`403 LOCAL_ONLY` **до виконання автентифікації**, тому витік JWT не дасть змоги запустити процес. Залишаються два
обов’язки оператора:

- **Не намагайтеся «виправити» помилку 403, підробляючи IP-адресу клієнта як адресу loopback.** Налаштування
  `X-Forwarded-For: 127.0.0.1` або проксі, який переписує адресу джерела на
  loopback, знову уможливлює саме той клас RCE, який блокує цей рівень. Надавайте доступ до
  панелі керування/API через проксі — але ніколи до маршрутів, здатних запускати процеси.
- **Зберігайте обхід для області `manage` мінімальним.** Обхід дозволено лише для `/api/mcp/` і
  лише з API-ключем, що має область `manage`. `SPAWN_CAPABLE_PREFIXES` за жодних умов не можна
  додати до списку обходу — схема zod відхиляє їх, а
  `isLocalOnlyBypassableByManageScope` забороняє їх під час виконання (ешелонований захист),
  що й мається на увазі в панелі керування під фразою «обхід неможливо дозволити». Той самий
  список заборон також містить кілька маршрутів LOCAL_ONLY, які не запускають процеси, але теж
  ніколи не повинні бути віддалено доступними: `/api/oauth/kiro/auto-import` (зчитує локальні
  для хоста файли облікових даних Kiro), `/api/discovery/` і `/api/issue-agent/`. Завантажувач
  знімка стану під час виконання також вилучає такі записи зі збереженого рядка налаштувань, а
  застарілий імпорт JSON (`/api/settings/import-json`) ніколи не записує ключі обходу.
  Кожен запис `LOCAL_ONLY_API_PREFIXES` має або входити до списку заборон, або бути
  перевіреним як придатний для обходу (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). Маршрути
  з динамічними сегментами та статичними шляхами, здатні запускати процеси, у межах `/api/providers/`
  (наприклад, `/login`, `/refresh-cursor`) охоплюються супровідними регулярними виразами
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` у
  `src/shared/constants/spawnCapablePrefixes.ts`, а не пласким масивом
  `SPAWN_CAPABLE_PREFIXES` — інакше плаский масив мав би охоплювати весь
  префікс `/api/providers/`, надмірно розширюючи обмеження на дерево маршрутів,
  яке віддалені панелі керування правомірно використовують для CRUD-операцій із провайдерами.

**Аудит доступу** — щоб переконатися, що жодні зовнішні щодо хоста запити не досягають цих маршрутів:

- Відкрийте **Інвентар авторизації** на `/dashboard/settings/security`: там відображається
  актуальний список префіксів LOCAL_ONLY, префікси, для яких дозволено обхід, і визначений під час
  компіляції набір маршрутів, здатних запускати процеси («обхід неможливо дозволити»).
- Виконайте пошук у журналах зворотного проксі / журналах доступу за наведеними вище префіксами
  разом з адресою клієнта, що не є loopback. Будь-який такий запит, який отримав `200` замість
  `403 LOCAL_ONLY`, означає, що проксі приховує справжню IP-адресу клієнта — виправте проксі.
- Запис `403 LOCAL_ONLY` у журналах OmniRoute для одного з цих шляхів означає, що захисний механізм
  працює належним чином, а не є помилкою, яку слід приховувати.

### Рівень 2 — ALWAYS_PROTECTED

**Забезпечується:** `isAlwaysProtectedPath(path)` → обхід `requireLogin=false` пропускається
**Обхід:** відсутній, коли `requireLogin=false`; JWT потрібен завжди

Ці маршрути виконують руйнівні або незворотні операції. Якщо дозволити їх у встановленні
«без пароля», будь-хто в тій самій LAN зможе стерти базу даних або завершити
серверний процес.

| Шлях                                      | Причина                                                                             |
| ----------------------------------------- | ----------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Завершує серверний процес                                                           |
| `/api/settings/database`                  | Експорт, імпорт і повне очищення бази даних                                         |
| `/api/db-backups`                         | Доступ до повного архіву резервної копії бази даних                                 |
| `/api/settings/export-json`               | Експортує повний об’єкт налаштувань (включно із секретами)                          |
| `/api/settings/import-json`               | Замінює повний об’єкт налаштувань                                                   |
| `/api/providers/health-autopilot/actions` | Виконує коригувальні дії автопілота                                                 |
| `/api/settings/obsidian`                  | Створює повторно використовувані облікові дані WebDAV для будь-якого кореня сховища |

**Відповідь у разі порушення:** `401 Authentication required`

`/api/settings/obsidian` охоплює дочірній маршрут `/webdav`: `POST` спрямовує файловий сервіс WebDAV —
який обслуговується спеціальним шаром Node перед Next.js, поза цим конвеєром — на корінь, вибраний
викликачем, і повертає щойно створені облікові дані Basic, `DELETE` змінює їх, а батьківський `POST`
зберігає токен REST API Obsidian. GHSA-62vw лише приховував розкриття пароля через `GET`; створення
облікових даних усе ще перебувало на рівні з відкритим у разі помилки доступом (GHSA-7pq4-8pvv-rx7r).
`enableObsidianVaultSync()` додатково відхиляє сховище, яке є каталогом даних, міститься в ньому
або містить його.

#### Експорт облікових даних доступний лише оператору

Наведений вище рівень визначає лише те, чи потрібні _якісь_ облікові дані. Маршрути, що завантажують
збережені облікові дані, виконують другу перевірку в обробнику: `GET /api/settings/export-json`
(розшифровані підключення провайдерів і необроблені API-ключі), `GET /api/db-backups/export`
(файл SQLite) і `GET /api/db-backups/exportAll` (повний архів) викликають `requireOperatorCredential()`
(`src/lib/api/operatorCredential.ts`). Вона приймає сеанс панелі керування, локальний суб’єкт CLI
або екземпляр із вимкненим входом і повертає `403` для API-ключів із будь-якою областю (зокрема
`manage` і `admin`), а також для токенів доступу `oma_`. Створення токенів синхронізації
(`POST /api/sync/tokens`) використовує той самий допоміжний механізм, а також довірений токен
внутрішньої служби loopback.

### Початкове налаштування нової інсталяції доступне лише через loopback — за фактичним вузлом, а не за `Host`

Якщо пароль керування не налаштовано (і немає `INITIAL_PASSWORD`), `isAuthRequired()` у
`src/shared/utils/apiAuth.ts` залишає анонімне початкове налаштування відкритим **лише для вузлів
loopback**. Loopback визначається за довіреними сигналами вузла в такому порядку: позначена токеном
реальна адреса TCP-вузла (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, яку бачить політика), власний
вердикт конвеєра `AUTHZ_HEADER_PEER_LOCALITY` (який бачать обробники маршрутів і якому довіряють
лише за наявності `OMNIROUTE_PEER_STAMP_TOKEN`) або реальний сокет вузла для прямих викликів.
`Host` / `nextUrl.hostname` ніколи не враховуються, а перше встановлення пароля
(`POST /api/settings/require-login`) підпорядковується тому самому обмеженню, а не є відкритим для
кожного мережевого вузла (GHSA-7pq4-8pvv-rx7r). `managementPolicy` явно передає нижче власний
вердикт `peerContext`, тому заголовки ПОЧАТКОВОГО запиту (до видалення) ніколи не впливають на це рішення.

### Рівень 3 — MANAGEMENT (типовий)

Усі інші маршрути керування. Автентифікація обов’язкова, якщо не налаштовано `requireLogin=false`. Токени CLI можуть автентифікувати ці маршрути (loopback + дійсний HMAC).

## Порядок оцінювання

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → перейти далі
     → не loopback, Bearer із областю manage
        І isLocalOnlyBypassableByManageScope     → дозволити (management_key)
     → інакше                                     → відхилити 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → дозволити (system)
  3. hasValidCliToken(headers)?
     → дозволити (cli) [loopback + перевірка HMAC через timingSafeEqual]
  4. isAlwaysProtectedPath(path) або requireLogin=true?
     → isDashboardSessionAuthenticated?
        → дозволити (dashboard_session)
     → Bearer із областю manage на маршруті, який не можна обійти?
        → дозволити (management_key)
     → відхилити 401/403
  5. requireLogin=false?
     → дозволити (anonymous)
```

Гілка області manage на кроці 1 — це єдиний автентифікований шлях, який може задовольнити маршрут
LOCAL_ONLY; режим помилки бекенду автентифікації повертає 503 (а не 403), щоб
прострочена БД непомітно не призводила до зниження рівня до «відхилити».

## Додавання нового маршруту, здатного запускати процеси

1. Додайте префікс шляху до `LOCAL_ONLY_API_PREFIXES` у
   `src/server/authz/routeGuard.ts`
2. Додайте тест до `tests/unit/authz/routeGuard.test.ts`, який перевіряє, що
   `isLocalOnlyPath()` повертає true для нового префікса
3. **Ніколи не пропускайте цей крок** — див. жорстке правило №15 у `CLAUDE.md`
4. Вирішіть: чи має цей маршрут ТАКОЖ входити до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`?
   Типова відповідь — **ні**. Додавайте його лише тоді, коли маршрут безпечно надавати
   власнику manage-scope (тобто він НЕ запускає довільний код, керований користувачем).

## Додавання шляху, який можна обійти за допомогою manage-scope

1. Переконайтеся, що маршрут не виконує наданий користувачем код або команди. Якщо
   виконує, зупиніться — цей виняток тут не підходить.
2. Додайте префікс до `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` у
   `src/server/authz/routeGuard.ts`
3. Додайте покриття в `tests/unit/authz/management-policy.test.ts` для всіх чотирьох
   варіантів запиту: без Bearer (403), manage Bearer (дозволити), не-manage Bearer
   (403), а також окрему регресійну перевірку для кожного префікса, щоб
   `/api/cli-tools/runtime/*` залишався доступним лише через loopback навіть із manage Bearer.

## Документування рівнів безпеки в OpenAPI

Під час додавання нового маршруту до `docs/openapi.yaml` застосуйте відповідне
розширення постачальника, якщо маршрут класифіковано в `routeGuard.ts`:

| Класифікація routeGuard.ts                      | YAML-анотація              | Застосування правил                                       |
| ----------------------------------------------- | -------------------------- | --------------------------------------------------------- |
| `LOCAL_ONLY_API_PREFIXES`                       | `x-loopback-only: true`    | Безумовно блокується для з’єднань не через loopback       |
| `ALWAYS_PROTECTED_API_PATHS`                    | `x-always-protected: true` | Автентифікація обов’язкова навіть за `requireLogin=false` |
| Внутрішній маршрут адміністрування/налагодження | `x-internal: true`         | Типово прихований у /dashboard/api-endpoints              |
| Немає (публічний / стандартна автентифікація)   | (анотація не потрібна)     | Стандартний доступ, керований `requireLogin`              |

### Валідація

Два скрипти забезпечують узгодженість між YAML-анотаціями та `routeGuard.ts`:

- `scripts/check/check-openapi-coverage.mjs` — завершується помилкою, якщо покриття < 99%
- `scripts/check/check-openapi-security-tiers.mjs` — завершується помилкою, якщо анотації `x-loopback-only` або
  `x-always-protected` не відповідають константам часу компіляції

Обидва скрипти запускаються в pre-commit hook і в CI.

### Правило щодо хибнопозитивних результатів

Якщо `x-always-protected` або `x-loopback-only` додано до маршруту, якого НЕМАЄ у
відповідній константі `routeGuard.ts`, скрипт перевірки покриття завершується помилкою. Правильне виправлення — завжди узгодити
YAML із тим, що фактично забезпечує `routeGuard.ts`, а не додавати маршрути до `routeGuard.ts`
без одночасної реалізації логіки застосування відповідних правил.
