> **مستند ماخذ:** `src/lib/guardrails/`
> **آخری تازہ کاری:** 2026-08-29 — v3.8.51 (Video Bridge ٹرانسکرپٹ کا ماخذ کالر کی جانب سے بیان کیا جاتا ہے،
> ابھی سرور سے تصدیق شدہ نہیں — #11661 کے مطابق وضاحت کی گئی)

Guardrails، OmniRoute اور اپ اسٹریم فراہم کنندگان کے درمیان حد پر حفاظت، پالیسی، اور مواد کی تبدیلیوں کو نافذ کرتے ہیں۔ ہر guardrail درخواست کے پے لوڈز (`preCall`) اور
اپ اسٹریم جوابات (`postCall`) کا معائنہ کر سکتا ہے (اور اختیاری طور پر انہیں مسترد، تبدیل، یا تشریح شدہ کر سکتا ہے)۔

سسٹم **fail-open** ہے: اگر عمل درآمد کے دوران کوئی guardrail استثنا پیدا کرے، تو رجسٹری
خرابی ریکارڈ کرتی ہے اور درخواست کو ناکام کرنے کے بجائے اگلے guardrail کے ساتھ جاری رہتی ہے۔
بلاک کرنا ایک واضح فیصلہ (`block: true`) ہے، کبھی بھی اتفاقی نتیجہ نہیں۔

رجسٹری import ہونے پر ترجیحی ترتیب میں چھ گارڈ ریلز خودکار طور پر لوڈ کرتی ہے
(`registry.ts` → `registerDefaultGuardrails()` دیکھیں):

| ترجیح | نام                 | مرحلہ/مراحل    | فائل                  |
| ----- | ------------------- | -------------- | --------------------- |
| `5`   | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`   | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`   | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`  | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |

کم ترجیحی نمبر **پہلے** چلتے ہیں۔

### وژن برج (`visionBridge.ts`) — موڈیلیٹی برج PR-1

**نان وژن ماڈلز** کے لیے بھیجی گئی، تصاویر پر مشتمل درخواستوں کو روک کر یا تو
پوری درخواست کو وژن کی صلاحیت رکھنے والے ماڈل کی طرف دوبارہ بھیجتا ہے، یا
اپ اسٹریم کال سے پہلے تصویر کے حصوں کو قابلِ تشکیل وژن ماڈل کی تیار کردہ
متنی وضاحتوں سے بدل دیتا ہے۔ اس طرح صرف متن فراہم کرنے والے پرووائیڈرز
ملٹی موڈل پے لوڈز کو شفاف انداز میں سنبھال سکتے ہیں۔

بہاؤ:

1. اگر ہدف ماڈل پہلے ہی وژن کو سپورٹ کرتا ہو تو اسے چھوڑ دیں (سوائے اس کے کہ وہ
   جبری برج فہرست `isVisionBridgeForcedModel` میں موجود ہو)۔
2. `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`) کے ذریعے تصویر کے حصے اخذ کریں، جو
   `open-sse/utils/mediaParts.ts` میں موجود **متحدہ میڈیا
   ڈیٹیکٹر** `detectMediaParts()` کو ذمہ داری سونپتا ہے — یہ کامبو مطابقت
   فلٹر کے ساتھ اشتراک کردہ واحد مستند ماخذ ہے۔
   اخذ کرنے کا عمل صرف ان اعلیٰ سطحی حصوں کی شکلوں تک محدود ہے جنہیں
   `replaceImageParts` دوبارہ شامل کر سکتا ہے (اخذ↔تبدیلی معاہدہ): OpenAI
   `image_url`، Anthropic base64 `source.type:"base64"`، Anthropic URL
   `source.type:"url"`، اور Responses API `input_image`۔ اندرونی سطح پر ملنے
   والی اشیا اور صرف اشاریے والی شکلیں کامبو فلٹر کا مواد ہیں اور کبھی اخذ
   نہیں کی جاتیں۔ اگر کوئی نہ ملے تو چھوڑ دیں۔
3. `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`) کے ذریعے رن ٹائم
   کنفیگریشن حل کریں: نئی `modalityBridge*` ترتیبات کی کلیدیں فوقیت رکھتی ہیں؛
   پرانی `visionBridge*` کلیدیں **ایک سائیکل کے فال بیک** (رول بیک ونڈو) کے
   طور پر برقرار رہتی ہیں۔ برج غیر فعال ہونے پر کسی بھی میڈیا ٹریورسل سے پہلے
   چھوڑ دیں۔
4. موڈ سلیکٹر (`modalityBridgeVisionMode`، نیچے دی گئی جدول دیکھیں) دوبارہ
   بھیجنے یا وضاحت کرنے کا فیصلہ کرتا ہے۔ دوبارہ بھیجنے کی صورت میں صرف
   `model` تبدیل کر کے `modifiedPayload`، نیز میٹا
   `{ rerouted, fromModel, toModel, imagesKept }` واپس کیا جاتا ہے۔
5. وضاحت کا راستہ: تصاویر کو `maxImages` تک محدود کریں، کام کے مطابق پرامپٹ
   مرتب کریں، وضاحت کا کیش دیکھیں، وژن ماڈل کو **متوازی طور پر**
   (`Promise.allSettled`) کال کریں، اور ان کی جگہ
   `[Image N]: <description>` کے متنی حصے داخل کریں۔ ناکام وضاحت `null` دیتی
   ہے اور اصل تصویر کا حصہ **محفوظ** رہتا ہے (#4012) — سوائے کامبو وضاحت کے
   راستے کے، جب ہر وضاحت ناکام ہو؛ اس صورت میں تصدیق شدہ نان وژن اپ اسٹریم کو
   اس کے بجائے `(unavailable — no vision-capable provider connected)` اسٹب
   ملتا ہے (#8430)۔
6. `modifiedPayload` + میٹا (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) واپس کریں۔

#### موڈ سلیکٹر (`modalityBridgeVisionMode`)

| موڈ        | ڈیفالٹ | طرزِ عمل                                                                                                                                                                                                                                                                                                               |
| ---------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔      | سابقہ ہیورسٹک، بغیر تبدیلی کے (#6640/#7204): نان کامبو/`auto/` ماڈلز کو بہترین وژن ماڈل کی طرف دوبارہ بھیجا جاتا ہے، سوائے اس کے کہ اصل ماڈل کے پاس پہلے ہی قابلِ استعمال اسناد ہوں (تب وضاحت کی جاتی ہے)؛ کامبو اہداف ہمیشہ وضاحت کرتے ہیں۔                                                                           |
| `describe` |        | ہمیشہ وضاحت کریں — دوبارہ بھیجنے والا بلاک مکمل طور پر نظر انداز کر دیا جاتا ہے؛ صارف کا منتخب کردہ ماڈل ہمیشہ جواب دیتا ہے۔                                                                                                                                                                                           |
| `reroute`  |        | دوبارہ بھیجنا لازمی کریں: اسناد رکھنے والے ماڈل کو برقرار رکھنے والا گارڈ بائی پاس کر دیا جاتا ہے۔ دوبارہ بھیجنے کے **ہدف** کا اسنادی گارڈ پھر بھی لاگو ہوتا ہے — جب کوئی قابلِ استعمال وژن ہدف موجود نہ ہو تو درخواست وضاحت کی طرف منتقل ہو جاتی ہے، تاکہ خام تصاویر کبھی صرف متن والے بیک اینڈ تک نہ پہنچیں (#8430)۔ |

جبری موڈز، خودکار ہیورسٹک چلنے سے **پہلے** شارٹ سرکٹ ہو جاتے ہیں؛ `auto` کا طرزِ عمل
PR-1 سے پہلے کے گارڈ ریل سے بائٹ بہ بائٹ یکساں ہے۔

#### API کلید کا دائرۂ کار (`visionBridgeKeyScope.ts`)

جب کالر کی API کلید `allowedConnections`، کوٹا پولز
(`allowedQuotas`) یا ماڈلز (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) کو محدود کرتی ہے،
تو برج صرف وہی دوبارہ بھیجنے اور وضاحت کرنے والے ماڈلز منتخب کرتا ہے جنہیں یہ
کلید استعمال کر سکتی ہے، اور صرف ان کنکشنز پر جنہیں کلید استعمال کر سکتی ہے۔
اس کے بعد وضاحت کی کال ہمیشہ `x-omniroute-self-loop-key-id` ہیڈر کے ساتھ
OmniRoute سیلف لوپ سے گزرتی ہے، تاکہ موصول ہونے والی چیٹ درخواست اس کلید کی
کنکشن اور ماڈل پالیسی دوبارہ نافذ کرے۔ `enforceApiKeyPolicy()` اس ہیڈر کو صرف
سیلف لوپ bearer کے ساتھ قبول کرتا ہے، لہٰذا یہ صرف رسائی کو مزید محدود کر سکتا
ہے، اور حل نہ ہونے والی id مسترد کر دی جاتی ہے۔

اگر کلید کے لیے کسی وژن ماڈل کی اجازت نہ ہو تو وضاحت کا راستہ ایک طرف ہو جاتا ہے
اور درخواست بغیر تبدیلی کے آگے گزر جاتی ہے، جو غیر فعال گارڈ ریل جیسا ہی
فیل اوپن طرزِ عمل ہے (میٹا `{ skipped: true, reason: "no_permitted_vision_model" }`)۔
بغیر کلید والی درخواستیں، اور ایسی کلیدیں جن پر یہ پابندیاں نہ ہوں، بالکل پہلے
کی طرح کام کرتی ہیں۔

#### کام کے مطابق وضاحتی پرامپٹ (`modalityBridgeVisionTaskAware`)

ڈیفالٹ **true** ہے۔ `composeVisionPrompt()` (`visionBridgeHelpers.ts`) بنیادی
describe پرامپٹ میں **آخری صارف کے پیغام** کا متن (500 حروف تک محدود) شامل کرتا ہے،
جس سے وضاحت اس جانب رہنمائی پاتی ہے جو صارف نے حقیقتاً پوچھی تھی
(codex-vision-proxy پیٹرن)، اور vision ماڈل سے نظر آنے والے متن کو نقل کرنے کو کہا جاتا
ہے۔ فلیگ بند ہونے — یا صارف کا متن موجود نہ ہونے — کی صورت میں بنیادی پرامپٹ بغیر کسی
تبدیلی کے استعمال ہوتا ہے۔

describe self-loop کی اپنی OpenAI-compatible درخواست (`callVisionModelSingle()`
در `visionBridgeHelpers.ts`) ہمیشہ `image_url.detail: "high"` کی درخواست کرتی ہے —
ہر caller/provider کے لیے غیر مشروط طور پر، اور کسی client signal پر منحصر نہیں۔
کم تفصیل والی sampling عین اسی text-transcription کام کے لیے OCR کی درستگی کم کرتی
ہے جس کا یہ پرامپٹ تقاضا کرتا ہے، اس لیے describe کال خود ہمیشہ زیادہ تفصیل طلب کرتی
ہے، چاہے اصل inbound درخواست میں کوئی بھی detail level استعمال کیا گیا ہو۔ اس کا اثر
صرف داخلی describe request body پر ہوتا ہے؛ یہ اس طریقے کو تبدیل نہیں کرتا جس سے
OmniRoute بنیادی درخواست پر caller کا اپنا `image_url.detail` آگے بھیجتا ہے —
وہ ڈیفالٹ الگ سے، اور صرف شناخت شدہ OpenCode clients کے لیے،
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) میں لاگو ہوتا
ہے۔ describe self-loop کی Anthropic wire-format شاخ میں کوئی `detail` فیلڈ نہیں ہے
اور دونوں ڈیفالٹس میں سے کسی سے بھی متاثر نہیں ہوتی۔

#### Describe آؤٹ پٹ کی حد (`modalityBridgeVisionMaxChars`)

| کلید                           | ڈیفالٹ | حد               |
| ------------------------------ | ------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`    | `0` یا 100–50000 |

`0` (ڈیفالٹ) کا مطلب **کوئی حد نہیں** ہے — `callVisionModel()` کی واپس کردہ وضاحت
بغیر کسی تبدیلی کے آگے بھیجی جاتی ہے، جس سے موجودہ رویہ برقرار رہتا ہے۔ 100–50000
کی حد میں کوئی بھی قدر وضاحت کو `[Image N]: <description>` کے طور پر واپس شامل کیے
جانے سے پہلے `…` لاحقے کے ساتھ مختصر کر دیتی ہے
(`VisionBridgeGuardrail.preCall()` در `src/lib/guardrails/visionBridge.ts`)۔
زیادہ تفصیل والے OCR کاموں کے لیے اسے بڑھائیں، جہاں downstream ماڈل کو مکمل نقل درکار
ہو؛ زیادہ گفتگو کرنے والے vision ماڈلز پر token استعمال محدود رکھنے کے لیے اسے کم
کریں۔ dashboard فیلڈ Vision ٹیب کے Advanced پینل میں موجود ہے
(`modality-bridge-max-chars` در `ModalityBridgeVisionTab.tsx`) اور 1 سے 99 کے درمیان
کسی بھی قدر کو کم از کم 100 تک بڑھا دیتا ہے، جبکہ واضح `0` کو بغیر تبدیلی کے چھوڑتا
ہے — `0` بذاتِ خود ایک درست Zod قدر ہے
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`)، محض "unset"
ڈیفالٹ نہیں۔

#### Describe کیش (`modalityBridge/bridgeCache.ts`)

describe آؤٹ پٹس کے لیے in-memory LRU + TTL کیش، جو پورے process میں مشترک ہے۔
کلید = `sha256(imageRef + composedPrompt + configuredBridgeModel)`، جس میں
length-prefix framing استعمال ہوتی ہے (فیلڈ حدود کے تصادم کے بغیر)۔ ماڈل کا جزو
**configured** bridge model ہوتا ہے، نہ کہ وہ ماڈل جس نے حقیقتاً جواب دیا —
`callVisionModel` داخلی طور پر fallback کر سکتا ہے، اور ہر کوشش کے مطابق کلید بنانے
سے کیش بکھر جائے گا۔ ناکام describes کبھی کیش نہیں کیے جاتے۔ ترتیبات:

| کلید                            | ڈیفالٹ | حد      |
| ------------------------------- | ------ | ------- |
| `modalityBridgeCacheEnabled`    | `true` | —       |
| `modalityBridgeCacheTtlMinutes` | `60`   | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`  | 10–5000 |

#### Remote تصویر کی normalization (self-loop describe/base64 fetch)

جب bridge خود کوئی **remote** تصویر fetch کرتا ہے — Anthropic describe self-call
اور claude-wire-format base64 conversion (`ensureBase64ImagesForClaudeWire`)،
دونوں `visionBridgeHelpers.ts` میں `fetchRemoteImageAsDataUri()` کے ذریعے — تو
نتیجے میں حاصل ہونے والا data URI، vision-model درخواست میں شامل کیے جانے سے پہلے
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) سے گزارا جاتا ہے۔
ضرورت سے بڑی تصاویر کو **2048px طویل کنارہ** تک downscale کیا جاتا ہے (اس resize
حد کے مطابق جسے OpenAI/Anthropic پہلے ہی server-side لاگو کرتے ہیں)، جس سے vision
ماڈل کو دکھائی دینے والی چیز تبدیل کیے بغیر upload bytes/latency کم ہو جاتی ہے۔
Resize کے لیے `sharp` استعمال ہوتا ہے، جو dynamic import کے ذریعے load کیا جاتا ہے:
اگر کسی platform پر اس کا native binary load ہونے میں ناکام ہو جائے تو
`normalizeDataUri()` **کبھی throw نہیں کرتا** — یہ اصل bytes کو بغیر تبدیلی کے آگے
بھیجنے پر fallback کرتا ہے، اس لیے describe/base64-conversion کا راستہ ہمیشہ کام
کرتا رہتا ہے۔ غیر تصویری bytes (ایسا fetch جس نے قابلِ decode تصویر واپس نہیں کی)
بھی بغیر تبدیلی کے آگے بھیجے جاتے ہیں۔ یہ normalization صرف ان تصاویر تک محدود ہے
جنہیں bridge اپنی self-call کے لیے fetch کرتا ہے — اسے caller کے raw passthrough
payload پر کبھی لاگو نہیں کیا جاتا، جو صرف opt-in تبدیلی کے اصول
(Hard Rule #20) کے مطابق ہے۔

#### Transparency header + stats

Describe کے ذریعے تبدیل شدہ responses میں
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
شامل ہوتا ہے (`modalityBridge/bridgeStats.ts` میں `buildModalityBridgeHeader()`
کے ذریعے بنایا اور `src/sse/handlers/chatHelpers.ts` میں
`withModalityBridgeHeader()` کے ذریعے لگایا جاتا ہے)۔
Rerouted درخواستوں کو **کوئی** header نہیں ملتا — payload بغیر تبدیلی کے رہا، اور
ماڈل کی تبدیلی response body کے `model` فیلڈ میں پہلے ہی نظر آتی ہے۔

`GET /api/modality-bridge/stats` (مینجمنٹ توثیق، وہی درجہ جو
`GET /api/settings` کا ہے) `vision`، `audio`، اور `video` کے لیے اِن میموری فی-موڈیلٹی کاؤنٹرز
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` واپس کرتا ہے۔ `averageLatencyMs` اپنے
مخرج کے طور پر تمام کوششوں کے بجائے `latencySamples` استعمال کرتا ہے؛ ٹائمنگ کے بغیر کوئی
آپریشن فرضی صفر ملی سیکنڈ نمونہ نہیں بناتا۔ `bridged` کامیاب
تبدیلیوں کے لیے پس ماندہ مطابقت رکھنے والا عرف رہتا ہے؛ ناکام کوششیں اسے نہیں بڑھاتیں۔
ڈیزائن کے مطابق پراسیس دوبارہ شروع ہونے پر کاؤنٹرز ری سیٹ ہو جاتے ہیں
(ٹیلی میٹری، اکاؤنٹنگ نہیں)۔

#### ڈیش بورڈ کی تشکیل

مخصوص ڈیش بورڈ صفحہ
`/dashboard/settings/modality-bridge` ہے۔ اس کے URL کے ذریعے قابلِ رسائی `Vision`، `Audio`،
اور `Video` ٹیبز، `tab` کی قدر تبدیل کرتے وقت کوئری پیرامیٹرز برقرار رکھتے ہیں۔
Vision ٹیب فعال کاری، موڈ، ماڈل کا انتخاب (خودکار
ڈیفالٹ سمیت)، کام سے آگاہ پرامپٹنگ، جدید ٹائم آؤٹ/تصویر/تفصیل کی لمبائی/کیش
کی حدود، رن ٹائم
کاؤنٹرز، اور حفاظتی پابندی والی نمونہ درخواست فراہم کرتا ہے۔ Audio ٹیب بھی فعال ہے: یہ
فعال کاری، Auto کے ساتھ صرف STT ماڈل چننے کا آلہ، ٹائم آؤٹ/زیادہ سے زیادہ کلپ کی حدود، آڈیو
کاؤنٹرز، اور ایک `input_audio` نمونہ ٹیسٹ فراہم کرتا ہے۔ Video ٹیب فعال ہے: یہ
FFmpeg/ffprobe کی رن ٹائم حالت رپورٹ کرتا ہے — چار واضح UI حالتوں میں سے ایک (`unknown` جب
پروب جاری ہو یا مکمل نہ ہو سکا ہو، کسی غیر لوپ بیک
ڈیش بورڈ ہوسٹ پر `restricted` جہاں کلائنٹ کی جانب سے پروب چھوڑ دیا جاتا ہے،
پروب کیے جانے اور غیر موجودگی کی تصدیق کے بعد `unavailable`، یا FFmpeg/ffprobe ورژنز کے ساتھ
`available`) — فعال کاری/ماڈل/فریم/ویڈیو/ٹائم آؤٹ کی حدود محفوظ رکھتا ہے، ماڈل چننے کے آلے کو بصری صلاحیت رکھنے والے
ماڈلز تک محدود کرتا ہے، اور ویڈیو کاؤنٹرز فراہم کرتا ہے۔

AI سیٹنگز کے تحت سابقہ Vision Bridge کارڈ نئے صفحے کے لیے ایک مطابقتی لنک ہے؛ اب یہ
فارم کی دوسری نقل کا مالک نہیں ہے۔ Media Providers بھی موجودہ Speech-to-Text پلے گراؤنڈ کو ہٹائے بغیر
Image-to-Text اور Speech-to-Text ورک فلوز کو متعلقہ Modality
Bridge ٹیبز سے منسلک کرتا ہے۔

**سیلف لوپ داخلہ بائی پاس:** جب وضاحت کی کال OmniRoute کے
اپنے `/v1` سیلف لوپ (غیر معیاری پرووائیڈر ماڈل) کے ذریعے روٹ ہوتی ہے، تو ذیلی درخواست
`x-omniroute-admission-bypass: internal` بھیجتی ہے اور حل شدہ
سیلف لوپ اسناد سے توثیق کی جاتی ہے — مقامی موڈ میں مقامی `sk_omniroute` سینٹینل، یا
آپریٹر کی تشکیل کردہ `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` ماحول کلید (#1350)، تاکہ
`REQUIRE_API_KEY=true` والی تعیناتیاں بھی وضاحت کی کال چلا سکیں۔ بائی پاس صرف
انہی عین اسناد کے لیے قبول کیا جاتا ہے، اس لیے بیرونی کلائنٹس داخلہ جانچ کو چھوڑنے کے لیے
ہیڈر استعمال نہیں کر سکتے۔

پرانے ڈیفالٹس `src/shared/constants/visionBridgeDefaults.ts` میں موجود ہیں؛
نئے موڈ/کام سے آگاہ/کیش ڈیفالٹس اور سیٹنگز ریزولوَر
`src/shared/constants/modalityBridgeDefaults.ts` میں موجود ہیں۔ گارڈ ریل ایک
`deps` کنسٹرکٹر آپشن فراہم کرتی ہے تاکہ ٹیسٹس جعلی `getSettings` اور
`callVisionModel` امپلیمینٹیشنز داخل کر سکیں۔

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

آڈیو رکھنے والی چیٹ درخواستوں کو ایسے ہدف تک پہنچنے سے پہلے روک لیتا ہے جس کے بارے میں
یہ معلوم نہ ہو کہ وہ آڈیو ان پٹ قبول کرتا ہے۔ یہ چیٹ درخواست کو کبھی دوبارہ روٹ نہیں کرتا: آڈیو حصوں کی
موجودہ OpenAI سے مطابقت رکھنے والے ملٹی پارٹ اینڈ پوائنٹ کے ذریعے نقل نویسی کی جاتی ہے اور
منتخب کردہ چیٹ ماڈل متنی نقل کے ساتھ جاری رہتا ہے۔

بہاؤ:

1. `getResolvedModelCapabilities()` کے ذریعے `supportsAudio` حل کریں۔ واضح
   پرووائیڈر رجسٹری میٹا ڈیٹا کو ترجیح حاصل ہے، پھر جامد ماڈل میٹا ڈیٹا، اور پھر ہم وقت شدہ
   `modalities_input`۔ `audio` کے بغیر اعلان کردہ ان پٹ فہرست `false` ہے؛ اگر
   صلاحیت کا کوئی ثبوت نہ ہو تو قدر `null` رہتی ہے۔ `false` اور `null` دونوں
   محتاط برج کو فعال کرتے ہیں، جبکہ `true` اسے بائی پاس کرتا ہے۔
2. `modalityBridgeAudio*` سیٹنگز حل کریں اور مشترکہ `detectMediaParts()`
   ڈیٹیکٹر کے ذریعے ہر پیغام سے جوڑنے کے قابل اعلیٰ سطحی آڈیو حصے اخذ کریں۔
   معاونت یافتہ وائر اشکال OpenAI `input_audio`، `audio_url`، اور
   `source.media_type: "audio/*"` ہیں۔ نیسٹڈ آڈیو کو روٹنگ کے لیے شناخت کیا جاتا ہے لیکن
   splice راستے کے ذریعے ہٹایا نہیں جاتا۔ کام `modalityBridgeAudioMaxClips` تک محدود ہے؛
   بعد کے حصے بغیر تبدیلی کے رہتے ہیں۔
3. تشکیل کردہ `provider/model` کا احترام کریں، یا `selectAudioBridgeModel()` کو
   `AUDIO_TRANSCRIPTION_PROVIDERS` میں مستحکم کیٹلاگ ترتیب سے گزرنے دیں اور قابلِ استعمال فعال پرووائیڈر اسناد والا پہلا
   ماڈل منتخب کرنے دیں۔
4. `callAudioTranscription()` base64/data-URI آڈیو کو ملٹی پارٹ
   `file` میں تبدیل کرتا ہے، یا DNS پننگ اور 25 MB حد کے ساتھ صرف عوامی آؤٹ باؤنڈ
   گارڈ کے ذریعے دور دراز `audio_url` ڈاؤن لوڈ کرتا ہے۔ پھر یہ فائل اور منتخب
   ماڈل کو مقامی `/v1/audio/transcriptions` سیلف لوپ پر POST کرتا ہے، جس کی توثیق
   `resolveSelfLoopBearer()` کے ذریعے ہوتی ہے۔ موجودہ نقل نویسی روٹ معمول کے مطابق
   اسناد کی تلاش، کول ڈاؤن/شرح کی حد کی ہینڈلنگ، اور پرووائیڈر ڈسپیچ انجام دیتا ہے۔
5. کامیاب کالز اپنے حصوں کو `[Audio N]: <transcript>` سے بدل دیتی ہیں۔ کالز
   `Promise.allSettled` کے ساتھ چلتی ہیں: کوئی انفرادی ناکامی اس اصل
   آڈیو حصے کو برقرار رکھتی ہے (#4012 معاہدہ)۔ اگر ہر کال ناکام ہو اور ہدف کے لیے
   `supportsAudio === false` ثابت ہو چکا ہو، تو حصے
   `[Audio N]: (دستیاب نہیں — کوئی STT پرووائیڈر منسلک نہیں)` بن جاتے ہیں (#8430 معاہدہ)۔
   نامعلوم ہدف (`null`) کے لیے، تمام کالز ناکام ہونے پر نتیجہ بغیر تبدیلی کے رہتا ہے۔ قابلِ استعمال
   STT اسناد کے بغیر ثابت شدہ صرف متن ہدف کو نیٹ ورک کال کیے بغیر یہی واضح
   متبادل متن موصول ہوتا ہے۔

کامیاب نقلیں پراسیس بھر کے Modality Bridge LRU/TTL کیش کا استعمال کرتی ہیں۔ کلید
آڈیو حوالہ، مستحکم `audio-transcription` آپریشن
لیبل، اور منتخب کردہ STT ماڈل کو یکجا کرتی ہے؛ ناکامیاں کبھی کیش نہیں کی جاتیں۔ آڈیو کوششیں
مشترکہ `bridged`، `cacheHits`، `failures`، اور `lastUsedAt` کاؤنٹرز کو اپ ڈیٹ کرتی ہیں۔
تبدیل شدہ جوابات میں
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` شامل ہوتا ہے؛ بغیر تبدیلی والی
درخواستوں کو Audio Bridge سیگمنٹ موصول نہیں ہوتا۔

رن ٹائم سیٹنگز DB کی پشت پناہی رکھتی اور Zod سے توثیق شدہ ہیں:

| کلید                          | ڈیفالٹ  | حد               |
| ----------------------------- | ------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`  | —                |
| `modalityBridgeAudioModel`    | `""`    | خودکار یا STT ID |
| `modalityBridgeAudioTimeout`  | `60000` | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`     | 1–10             |

مشترکہ کیش بدستور `modalityBridgeCacheEnabled`،
`modalityBridgeCacheTtlMinutes`، اور `modalityBridgeCacheMaxEntries` کے ذریعے کنٹرول ہوتا ہے۔

### ویڈیو برج (`videoBridge.ts`، `videoBridgePipeline.ts`)

معلوم مقامی ویڈیو سپورٹ کے بغیر کسی ہدف کو کال کیے جانے سے پہلے، Chat Completions کے `messages` اور Responses
API کے `input` میں اعلیٰ سطح کے ویڈیو حصوں کو انٹرسیپٹ کرتا ہے۔
معاونت یافتہ شکلیں `input_video`، `video_url`، `video_source`، HTTPS URLs،
اور `data:video/*;base64,...` ڈیٹا URIs ہیں۔ متن میں موجود سادہ فائل ناموں کو ویڈیو
نہیں سمجھا جاتا۔

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) درخواست میں ٹریورسل،
صلاحیت/پالیسی کی جانچ، فی درخواست ایگریگیشن، اور جوابی پے لوڈ کا ذمہ دار ہے۔
ہر ویڈیو کا کام — حصول، مکمل نتیجے کا کیش، فریم
سیکوئنس کی وضاحت (جو کالر کی اعلان کردہ کسی بھی آڈیو ٹرانسکرپٹ کو ضم کرتی ہے)، اور فی کوشش
میٹرکس/منسوخی/صفائی — `videoBridgePipeline.ts` میں `processVideoPart` کے پیچھے پوشیدہ ہے،
جسے `preCall` کے لوپ کے اندر ہر ویڈیو حصے کے لیے ایک بار کال کیا جاتا ہے۔
یہ ماڈیول واضح پورٹ حدود `VideoMediaBrokerPort`
(بائٹس حاصل کرنا اور نمونہ لیے گئے فریم نکالنا)، `VideoAudioTranscriptionPort`
(کالر کی اعلان کردہ آڈیو ٹرانسکرپٹ کو نمونہ لیے گئے کیپشنز کے ساتھ ضم کرنا)، اور
`VideoDrilldownPort` (فریم ڈرل ڈاؤن کی استمراری حد؛ ابھی تک
`processVideoPart` سے منسلک نہیں — آج صرف علیحدہ `/api/modality-bridge/video/drilldown`
روٹ ڈرل ڈاؤن اندراجات لکھتا ہے) بھی متعین کرتا ہے۔

عوامی `/v1` درخواست کا راستہ کبھی کسی ذیلی عمل کو درآمد یا طلب نہیں کرتا۔ ریموٹ
ویڈیوز 50 MiB کی حد کے تحت ڈاؤن لوڈ کی جاتی ہیں؛ اِن لائن base64 ویڈیوز کے لیے

#### FU-07 ساختی سیگمنٹ شواہد

`segment_aware` پہلے سے توثیق شدہ مقامی ویڈیو اسٹریم پر ایک محدود پیشگی تجزیاتی پاس استعمال کرتا ہے۔ مقررہ فلٹر چین پہلے چوڑائی کو زیادہ سے زیادہ 320 پکسل تک اسکیل کرتی ہے، منظر کی تبدیلیوں اور منجمد وقفوں کا پتہ لگاتی ہے، پھر دھندلاہٹ، اوسط لیوما، اور مکانی/زمانی معلومات کے لیے فی سیکنڈ 1 فریم کا نمونہ لیتی ہے۔ یہ پاس 600 ساختی نمونوں، ایک FFmpeg/فلٹر تھریڈ، انہی صرف-`file` پروٹوکول اور کنٹینر کی اجازت فہرستوں، عمل کے آؤٹ پٹ کی 1 MiB حد، اور بروکر کے مشترکہ اسقاط/آخری مہلت کے اندر زیادہ سے زیادہ 30 سیکنڈ تک محدود ہے۔ یہ درخواست سے کبھی کوئی کمانڈ، فلٹر، پاتھ، یا URL قبول نہیں کرتا۔

ساختی اقدار قطعی نمونہ جاتی شواہد ہیں، معنوی ویڈیو فہم نہیں۔ یہ موضوعات، اعمال، کیپشنز، تقریر، یا صارف کے ارادے کا استنباط نہیں کرتیں۔ منظر اور انجماد کی حدیں سیگمنٹس بناتی ہیں؛ انجماد کی کوریج، دھندلاہٹ، ایکسپوژر، مکانی تفصیل، اور زمانی تبدیلی صرف اس بات پر اثر انداز ہوتی ہیں کہ موجودہ 1–16 فریم بجٹ کس طرح مختص کیا جائے۔ مکمل طور پر منجمد سیگمنٹ کو زیادہ سے زیادہ ایک فریم تک محدود کیا جاتا ہے، جبکہ غیر منجمد سیگمنٹس باقی بجٹ کے لیے مقابلہ کرتے ہیں۔ جب حدوں کی تعداد فریموں سے زیادہ ہو تو ٹائم لائن کی یکساں کوریج برقرار رکھی جاتی ہے، تاکہ ابتدائی تیز کٹس کسی طویل آخری سیگمنٹ کو چھپا نہ سکیں۔ انجماد کی حد سے 1 سیکنڈ کی تجزیاتی ریزولیوشن کے اندر آنے والی منظر کی حدوں کو یکجا کر دیا جاتا ہے۔

غائب فلٹرز، بدہیئت/خالی شواہد، ڈیٹیکٹر کی خرابی، یا محدود پیشگی تجزیے کا ٹائم آؤٹ عین یکساں وسطی نقطے کی پالیسی کی طرف کھلی ناکامی کرتے ہیں۔ کالر کا اسقاط یا بروکر کی آخری مہلت کھلی ناکامی نہیں کرتی: یہ زیرِ عمل ذیلی عمل کو ختم کرتی ہے، بعد میں فریم اخذ کرنے سے روکتی ہے، اور نجی عارضی ٹری کو `finally` میں حذف کر دیا جاتا ہے۔

`scripts/perf/video-bridge-fu07-eval.ts` بعد از ڈی ڈپلیکیشن کیپشن کال کی بچت، کثیف حرکت کے بجٹ کی تخصیص، دھندلاہٹ/ایکسپوژر/SI-TI شواہد، طویل آخری حصے کے ساتھ تیز کٹس، اور بتدریج فیڈ کے غلط مثبت نتائج کے لیے قطعی حقیقی FFmpeg فکسچرز تیار کرتا ہے۔ یہ پیشگی تجزیے کا وال ٹائم اور، جہاں `/usr/bin/time` دستیاب ہو، چائلڈ CPU اور چوٹی RSS ریکارڈ کرتا ہے۔ اس کے معیار کے جائزے صرف ساختی اوریکلز ہیں۔ حقیقی کیپشن ماڈل کا معیار `HOLD` ہی رہتا ہے کیونکہ اس ہارنس کے پاس کوئی مجاز اینڈ پوائنٹ یا منجمد جج نہیں ہے۔ مالی بچت بھی `HOLD` رہتی ہے، الا یہ کہ `--caption-cost-per-call-usd` فی کال ایک واضح مثبت تخمینہ فراہم کرے؛ اسکرپٹ کبھی بھی کسی نتیجے کو گھڑتا نہیں ہے۔

ہر فریم 4 MiB تک، تمام خام فریم مجموعی طور پر 23 MiB تک، اور سیریلائز شدہ بروکر جواب 32 MiB تک محدود ہے۔ ایک نجی عارضی ڈائریکٹری کو `finally` میں حذف کر دیا جاتا ہے۔ OmniRoute میں FFmpeg شامل نہیں ہے اور یہ حسبِ ضرورت ایگزیکیوٹیبل پاتھ قبول نہیں کرتا۔ کیپشن بنانے سے پہلے، برج ایک محتاط بصری ڈی ڈپلیکیشن پاس لاگو کرتا ہے: ہر JPEG کو 16×16 گرے اسکیل بفر تک کم کیا جاتا ہے اور اس کا موازنہ صرف آخری برقرار رکھے گئے فریم سے کیا جاتا ہے۔ ایک سے زیادہ فریم کے مطلوبہ کیپشن بجٹ کے لیے، اخذ کرنے کا عمل اس بجٹ سے زیادہ سے زیادہ دو گنا اور کبھی بھی 16 فریم سے زیادہ نہ ہونے والا محدود امیدوار پول فراہم کرتا ہے۔ مطلوبہ حد صرف ڈی ڈپلیکیشن کے بعد لاگو ہوتی ہے، اور جب بجٹ کم از کم دو ہو تو حتمی چھٹائی کے دوران پہلے اور آخری منتخب امیدواروں کو محفوظ رکھا جاتا ہے۔ ورژن شدہ `grayscale-16x16-mean-cells-v2` پالیسی اوسط لیوما فرق اور ان تھمب نیل سیلز کے تناسب میں سے بڑی قدر استعمال کرتی ہے جن کا معمول پر لایا گیا فرق کم از کم 0.05 ہو۔ ڈپلیکیٹ حد مستقل 0.04 ہے، جسے رن ٹائم ترتیب کے طور پر ظاہر کرنے کے بجائے پیش گوئی پذیری کے لیے منتخب کیا گیا ہے۔ یہ ثانوی زیادہ تضاد والا سگنل چھوٹی حرکت اور نمایاں متن کی ان تبدیلیوں کو محفوظ رکھتا ہے جنہیں صرف اوسط پر مبنی موازنہ چھپا سکتا ہے۔ کمپیریٹر یا ڈیکوڈر کی خرابیاں کھلی ناکامی کرتی ہیں اور کوریج برقرار رکھتی ہیں۔ آؤٹ پٹ میٹا ڈیٹا اخذ شدہ امیدواروں، کامیابی سے استعمال شدہ فریموں، اور حذف شدہ بصری ڈپلیکیٹس کو الگ الگ دکھاتا ہے۔

واضح طور پر نشان زد ویڈیو پارٹ ٹائم اسٹیمپ شدہ کانٹیکٹ شیٹ کی درخواست کر سکتا ہے۔ برج زیادہ سے زیادہ 4 کالموں اور 16 فریموں پر مشتمل JPEG گرڈ بناتا ہے۔ ہر 512 پکسل سیل اپنے ماخذ ٹائم اسٹیمپ کو زیادہ تضاد والی زیریں پٹی پر ثبت کرتا ہے، جبکہ یہی ٹائم اسٹیمپس بعد کے مرحلے میں تعلق قائم کرنے اور آڈٹ کے لیے متنی میٹا ڈیٹا میں بھی برقرار رہتے ہیں۔ مکمل JPEG بدستور 32 MiB تک محدود رہتا ہے۔ اگر `sharp` گرڈ کو ڈی کوڈ یا مرتب نہ کر سکے تو برج انفرادی JPEG فریموں کی طرف واپس چلا جاتا ہے؛ کلائنٹ کا اسقاط پھر بھی شیٹ آپریشن کے ذریعے آگے منتقل ہوتا ہے۔

پروموشن کے شواہد کو مصنوعی کمپوزیشن مائیکروبینچ مارک سے جان بوجھ کر الگ رکھا گیا ہے۔ `scripts/perf/video-bridge-contact-sheet-eval.ts` حقیقی OpenAI-مطابقت پذیر وژن ماڈلز کے لیے اسکیما-ورژن شدہ A/B ہارنس متعین کرتا ہے۔ یہ فراہم کنندہ کی اطلاع کردہ ٹوکن تعداد، ابتدا سے انتہا تک وال لیٹنسی (بشمول شیٹ کمپوزیشن)، ماڈل کالز کی تعداد، اور مینی فیسٹ میں متعین حقائق کے برقرار رہنے کی پیمائش کرتا ہے۔ ماڈل کے خام جوابات رپورٹ میں نہیں لکھے جاتے؛ صرف SHA-256 ڈائجسٹس اور مماثل فیکٹ IDs برقرار رکھی جاتی ہیں۔ ہارنس اس وقت تک کوئی نیٹ ورک یا بامعاوضہ ماڈل کال نہیں کرتا جب تک `--execute-real` پاس نہ کیا جائے اور `--model`، `OMNIROUTE_BASE_URL`، اور `OMNIROUTE_API_KEY` ترتیب شدہ نہ ہوں۔ اس واضح حقیقی رن کے بغیر، اس کا مشین کے ذریعے قابلِ مطالعہ فیصلہ `HOLD` رہتا ہے؛ صرف مصنوعی پے لوڈ/کال کی تعداد کی پیمائشیں پروموشن کا ثبوت نہیں ہیں۔

کالرز کسی معاونت یافتہ ویڈیو پارٹ کے ساتھ اختیاری `transcript.cues` ایرے منسلک کر سکتے ہیں، جب ان کے پاس پہلے ہی ہم وقت متن موجود ہو۔ ہر کیو میں `text`، پروب شدہ دورانیے کے اندر ایک محدود `start`/`end` وقفہ، اور اجازت فہرست میں شامل `source` (`client`، `embedded`، یا `audio-bridge`) ہونا ضروری ہے؛ `confidence` کی ڈیفالٹ قدر `1` ہے اور اسے `0` اور `1` کے درمیان رہنا چاہیے۔ بالکل یکساں کیوز کو یکجا کر دیا جاتا ہے۔ OmniRoute اس میٹا ڈیٹا سے کبھی ٹرانسکرپشن شروع نہیں کرتا: توثیق شدہ کیوز کو ماخذ، اعتماد، اور وقفے سمیت بیان کردہ نتیجے میں نقل کیا جاتا ہے، اور فریم کیپشنز کے ساتھ غیر معتبر مشاہدات کے طور پر رینڈر کیا جاتا ہے۔ غلط، حد سے باہر، یا ماخذی نسبت سے محروم متن کو کیپشن اسٹریم میں ملانے کے بجائے مسترد کر دیا جاتا ہے۔ درخواست باڈی کے دونوں ٹرانسکرپٹ چینلز فراہم کردہ ماخذی نسبت کو `client` پر معمول پر لاتے ہیں، جس میں خود بیان کردہ `embedded` یا `audio-bridge` لیبلز بھی شامل ہیں۔ صرف سرور کی ملکیت والا اڈاپٹر کوڈ کے لیے مخصوص `trustedSource` آرگیومنٹ کے ذریعے وہ معتبر لیبلز تفویض کر سکتا ہے؛ درخواست کا JSON فیلڈ اس آرگیومنٹ تک نہیں پہنچ سکتا۔ ٹرانسکرپٹ متن اپنی ماخذی نسبت سے قطع نظر غیر معتبر، میڈیا سے اخذ شدہ مواد ہی رہتا ہے، اور اسے کبھی بھی اجازت کا تعین نہیں کرنا چاہیے۔

ایک جدید کالر اسی ویڈیو کے لیے `audioTranscript` ٹریک فراہم کر سکتا ہے؛
اسے کلائنٹ کی فراہم کردہ عبارت سمجھا جاتا ہے، نہ کہ سرور ٹرانسکرپشن کا ثبوت۔
فیوژن سیم بصری اور آڈیو مشاہدات کو ایک ہی ڈیڈ لائن اور abort سگنل کے تحت
چلاتی ہے، انہیں ایک مشترکہ ٹائم لائن پر ترتیب دیتی ہے، بالکل یکساں نقول کو
یکجا کرتی ہے، اور جب صرف ایک جانب کامیاب ہو تو جزوی نتیجہ رپورٹ کرتی ہے۔
ایک نامعتبر `audioTranscript` اسی جزوی نتیجے میں تنزلی کا باعث بنتا ہے — بصری
تفصیل برقرار رکھی جاتی ہے اور آڈیو برانچ ایک صاف کردہ ناکامی کوڈ ریکارڈ کرتی ہے —
بجائے اس کے کہ پوری ویڈیو ناکام ہو جائے۔ ہر برانچ کی دستیابی، جزوی پرچم،
اور صاف کردہ ناکامی کوڈز بیان کردہ نتیجے میں، guardrail میٹا ڈیٹا
(`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`)، نتیجہ-cache میٹا ڈیٹا، اور bridge
فیوژن کاؤنٹرز میں محفوظ رکھے جاتے ہیں۔ ڈیفالٹ Video Bridge راستہ speech-to-text
کو استعمال نہیں کرتا اور نہ ہی میڈیا کی دوسری نقل ڈاؤن لوڈ کرتا ہے؛ اس واضح
ٹریک کے بغیر، یہ صرف ویڈیو تک محدود رہتا ہے۔

**خام ویڈیو فیلڈز (#12430)۔** جب bridge فعال ہو اور مقامی ویڈیو سپورٹ نامعلوم یا غیر موجود ہو، تو متعین `transcript`/`audioTranscript` فیلڈز بھی `videoBridgeObserved` کو فعال کرتی ہیں، حتیٰ کہ تفصیل کی ناکامی یا `maxVideos` حد کے بعد بھی۔ `null` اور خالی اسٹرنگز شمار ہوتی ہیں؛ غیر موجود فیلڈز اور غیر ویڈیو میٹا ڈیٹا شمار نہیں ہوتے۔ برقرار رکھی گئی نقول میں ان فیلڈز کو redact کیا جاتا ہے یا درخواست حذف کر دی جاتی ہے، اور caches/Memory کو bypass کیا جاتا ہے۔

ان fallback راستوں پر، کالر کے درست cues غیر معیاری provider فیلڈز کے بجائے
معاونت یافتہ `text`/`input_text` حصے بن جاتے ہیں۔ درخواست کے ذریعے فراہم کردہ
دونوں ٹریکس ناقابلِ اعتماد `client` مشاہدات ہی رہتے ہیں، اور ان کے ساتھ واضح
تنبیہ ہوتی ہے کہ ویڈیو کو بیان نہیں کیا گیا اور timestamps کی میڈیا کے مقابلے
میں تصدیق نہیں کی گئی۔ موجودہ 256-cue/64-KiB مجموعی اور فی-cue بجٹس دونوں
ٹریکس پر مشترکہ طور پر لاگو ہوتے ہیں؛ timestamps کو broker کی 600 سیکنڈ کی حد
اور فراہم کردہ کسی بھی focus ونڈو کے اندر ہونا چاہیے۔ نامعتبر ٹریکس کو ضائع
کر دیا جاتا ہے، من مانے متن کے طور پر آگے نہیں بھیجا جاتا؛ ان کا درست sibling
تب تک استعمال کیا جا سکتا ہے جب تک ان کا مشترکہ بجٹ تجاوز نہ کرے۔ Null/خالی
فیلڈز کوئی عبارت شامل نہیں کرتے۔ اس fallback کے ذریعے کوئی media fetch یا
transcription شامل نہیں کیا جاتا۔ ٹرانسکرپٹ extension فیلڈز fallback ویڈیو
carrier اور اس کے `video_url`/`source` آبجیکٹس سے ہٹا دی جاتی ہیں۔ OpenAI wire
allowlist سخت رہتی ہے؛ نامعلوم مقامی ویڈیو carriers دستیاب رہتے ہیں اور معلوم
صرف-متن targets محفوظ markers برقرار رکھتے ہیں۔ ساختی redaction shadows شامل
کی گئی ٹرانسکرپٹ عبارت کی حفاظت کرتے ہیں، جبکہ کالر کی ملکیت والی اصل درخواست
بلا تبدیلی رہتی ہے۔ مقامی طور پر معاونت یافتہ targets اور غیر فعال bridges
اپنا موجودہ bypass طرزِ عمل برقرار رکھتے ہیں۔

گیا تھا۔ اگر کسی مشاہدہ شدہ درخواست کا فی-part redaction shadow لاگنگ سے پہلے
ضائع ہو جائے، یا بعد کی درخواست تبدیلیوں کے بعد کئی ویڈیو shadows میں سے ایک

ٹرانسکرپٹ کے کسی بھی حصے کا اقتباس دے سکتا ہے۔ لہٰذا اس کی محفوظ کردہ call-log

نظر آنے والا جواب بلا تبدیلی رہتے ہیں۔ جب تفصیلی artifact حذف کیا جاتا ہے تو

یہ tranche ابھی تک کسی production producer کو route سے منسلک نہیں کرتی اور
multi-resolution variant selection فراہم نہیں کرتی۔ لہٰذا شفاف Video Bridge request
path پر کوئی اضافی کام عائد نہیں ہوتا، جبکہ tenant سے منسلک principal derivation اور
مکمل FU-08 multi-resolution lifecycle واضح follow-up کام رہتے ہیں،
نہ کہ مکمل شدہ رویے کے طور پر دستاویزی شکل میں پیش کیے جاتے ہیں۔

Frames کو ترتیب وار configured Video model کے ذریعے caption کیا جاتا ہے۔ ایک خالی
Video override، Vision setting کو inherit کرتا ہے؛ اگر دونوں خالی ہوں، تو Vision
auto-router مؤثر vision-capable model منتخب کرتا ہے۔ کامیاب captions
اصل part کو ایک مستقل `[Video description:` prefix سے بدل دیتے ہیں، جو متن کو
غیر معتبر، میڈیا سے اخذ کردہ observation کے طور پر بھی نشان زد کرتا ہے اور downstream
models کو میڈیا میں پائی جانے والی ہدایات پر عمل نہ کرنے کا کہتا ہے۔ Frame-caption cache keys
میں JPEG bytes، prompt، timestamp، اور effective model شامل ہوتے ہیں؛ صرف کامیاب
captions کیش کیے جاتے ہیں۔ Cache entries اصل کامیاب producer model کو برقرار رکھتی ہیں،
جس میں fallback model بھی شامل ہے؛ جب مختلف frames
مختلف models کے ذریعے تیار کیے گئے ہوں تو bridge `mixed` رپورٹ کرتا ہے۔ cache hit اسی producer identity
کو requested routing plan کے طور پر دوبارہ label کرنے کے بجائے reuse کرتی ہے۔ whole-video result
cache کی key ہر ایسے input پر مبنی ہوتی ہے جو output کو تبدیل کرتا ہے — prompt، effective
model، sampling policy، frame count، semantic analysis mode، normalized focus hint کا SHA-256
fingerprint، focus window، `transcript`،
`audioTranscript`، اور contact-sheet flag — لہٰذا ان میں سے کسی بھی
dimension کی تبدیلی cache miss ہوتی ہے، کبھی stale reuse نہیں۔ visual dedup policy
version، threshold، اور محدود candidate-frame count بھی
result-cache key اور metadata میں واضح طور پر شامل ہوتے ہیں؛ اس لیے policy میں تبدیلی کسی stale
whole-video description کو reuse نہیں کر سکتی۔ Result-cache v4 metadata، mode اور
fingerprint کو برقرار رکھتا ہے، raw user task کو کبھی نہیں۔ Guardrail metadata requested اور
effective analysis modes دونوں رپورٹ کرتا ہے؛ قابل استعمال user text کے بغیر requested `focused` mode
کو مؤثر طور پر `full` رپورٹ کیا جاتا ہے۔

guardrail ہر supported video part کو extract کرتا ہے، لیکن
`modalityBridgeVideoMaxVideos` سے زیادہ کو describe نہیں کرتا۔ ایسے target کے لیے جس کے بارے میں ثابت ہو کہ
`supportsVideo === false` ہے، failed اور over-limit videos واضح محفوظ
text markers بن جاتے ہیں تاکہ کوئی raw video باقی نہ رہے۔ جب capability نامعلوم ہو، تو وہ parts
اپنے video carrier کو برقرار رکھتے ہیں؛ کوئی بھی fallback transcript اوپر دی گئی محدود text
conversion کی پیروی کرتا ہے۔ `supportsVideo === true` والے targets bridge کو bypass کرتے ہیں۔
client request abort signal، download، broker queue،
subprocesses، اور caption calls میں propagate ہوتا ہے؛ aborts videos کے درمیان رک جاتے ہیں اور کبھی raw media کے لیے fail open
نہیں کرتے۔

Runtime settings DB-backed اور Zod-validated ہیں:

| کلید                                | ڈیفالٹ      | حد / رویہ                                                                                                |
| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | اختیاری رن ٹائم، صریح شمولیت درکار ہے                                                                    |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` عمومی کیپشنز برقرار رکھتا ہے؛ `focused` محدود، ناقابلِ اعتماد تازہ ترین صارف سیاق استعمال کرتا ہے |

بروکر ڈیڈ لائن تک محدود کر دیا جاتا ہے؛ اس حد سے زیادہ نئی ترتیبات محفوظ کرنے کی کوششیں مسترد کر دی جاتی ہیں۔
`GET /api/modality-bridge/video/runtime` کو توثیق یا رن ٹائم کی جانچ سے پہلے قابلِ اعتماد، مہر شدہ loopback
مقامیت درکار ہوتی ہے، اور پھر انتظامی
توثیق درکار ہوتی ہے۔ یہ صرف `available`، صاف کردہ FFmpeg/ffprobe ورژنز، اور رن ٹائم
دستیاب نہ ہونے کی صورت میں ایک مقررہ وجہ واپس کرتا ہے۔ داخلی استخراجی اینڈ پوائنٹ
عوامی اپ لوڈ API نہیں ہے: قطار بھرنے پر `503` کے ساتھ `Retry-After` واپس ہوتا ہے، کال کرنے والے کا
کنکشن منقطع ہونے پر `499`، اور مقررہ بروکر ڈیڈ لائن پر `504` واپس ہوتا ہے۔ تبدیل شدہ جوابات
Vision یا Audio حصوں کو ہٹائے بغیر مرکزی
`x-omniroute-modality-bridge` ہیڈر میں `video->text;model=<visionModel>;parts=<videos>` شامل کرتے ہیں۔

### PII ماسکر (`piiMasker.ts`)

**دونوں** مراحل پر چلتا ہے۔

- **`preCall`** پے لوڈ کا کلون بناتا ہے، `system`، `messages`، `input`، اور
  `prompt` (سادہ اسٹرنگ آئٹمز سمیت) سے گزرتا ہے، اور اسٹرنگ `content`/`text`
  فیلڈز پر `processPII()` (`@/shared/utils/inputSanitizer` سے) لاگو کرتا ہے۔ جب
  `PII_REDACTION_ENABLED=true` ہو، تو دریافت شدہ PII کو آؤٹ باؤنڈ
  پے لوڈ میں مخفی کر دیا جاتا ہے۔ یہ `INPUT_SANITIZER_MODE` سے آزاد ہے (جو صرف
  پرامپٹ انجیکشن پالیسی کو کنٹرول کرتا ہے)۔ جب مخفی کاری بند ہو، تو کال مواد کو دوبارہ لکھے
  بغیر دریافت کی تعداد ریکارڈ کرتی ہے۔
- **`postCall`** جواب کا ڈیپ کلون بناتا ہے، `sanitizePIIResponse()` کے ساتھ
  Responses-API شکل کا ماسکر (`maskResponsesOutput` — جو
  `output_text` اور `output[].content[].text` کا احاطہ کرتا ہے) چلاتا ہے۔ اگر کوئی مخفی کاری ہو، تو
  ترمیم شدہ جواب اصل جواب کی جگہ لے لیتا ہے۔

گارڈ ریل کبھی بلاک نہیں کرتی؛ یہ صرف تشریح شامل کرتی ہے (`meta.detections`،
`meta.redacted`) یا دوبارہ لکھتی ہے۔

### پرامپٹ انجیکشن (`promptInjection.ts`)

صارف کے فراہم کردہ مواد میں مخالفانہ ساختوں کا پتہ لگاتا ہے اور
تشکیل شدہ پالیسی نافذ کرتا ہے۔ رویہ ماحول کے متغیرات اور کنسٹرکٹر
اختیارات کے ذریعے متعین ہوتا ہے:

| ترتیب      | ماحولیاتی متغیر                                                                                     | ڈیفالٹ | اثر                                                                                                                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| فعال       | `INPUT_SANITIZER_ENABLED`                                                                           | `true` | `false` ہونے پر گارڈ ریل مختصر راستے سے واپس آ جاتی ہے۔                                                                                                                                                      |
| موڈ        | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                     | `warn` | انجیکشن پالیسی: `block`، `warn`، یا `log`۔ (`redact` پسماندہ مطابقت کے لیے قبول ہوتا ہے مگر انجیکشن متن کو **نہیں** ہٹاتا؛ درخواست میں PII کی دوبارہ تحریر `PII_REDACTION_ENABLED` کے ذریعے کنٹرول ہوتی ہے۔) |
| بلاک کی حد | `blockThreshold` اختیار / `INPUT_SANITIZER_BLOCK_THRESHOLD` (عرف `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high` | بلاک کرنے کے لیے درکار کم از کم شدت۔ ڈیفالٹ طور پر درمیانی شدت صرف مشاہدے کے لیے ہے۔                                                                                                                         |

**موڈ کی ترجیح** (`getMode`): کالر کا `options.mode` →
`INJECTION_GUARD_MODE` **DB فیچر فلیگ اوور رائیڈ** (Dashboard → Settings →
Feature Flags) → `INJECTION_GUARD_MODE` env → `INPUT_SANITIZER_MODE` env →
`warn`۔ لہٰذا ڈیش بورڈ اوور رائیڈ env vars پر فوقیت رکھتا ہے، اس لیے Feature
Flags UI چلتے ہوئے گارڈ کو براہِ راست کنٹرول کرتا ہے (دوبارہ شروع کرنے کی ضرورت نہیں)۔ DB ریڈ فیل سیف ہے:
اگر اس میں خرابی آئے، تو گارڈ env پر مبنی رویے پر واپس آ جاتا ہے، اور جب کوئی
اوور رائیڈ مقرر نہ ہو تو رویہ صرف env پر مبنی ریزولیوشن کے عین مطابق ہوتا ہے۔

دریافت کے ذرائع:

1. `@/shared/utils/inputSanitizer` سے `sanitizeRequest()` (پائپ لائن میں دیگر مقامات پر استعمال ہونے والا مشترکہ ڈیٹیکٹر
   مجموعہ)۔
2. پہلے سے شامل `DEFAULT_GUARD_PATTERNS` (فی الحال `system_override_inline` اور
   `markdown_system_block`، دونوں کی شدت `high` ہے)۔
3. کنسٹرکٹر اختیارات کے ذریعے فراہم کیے گئے اختیاری `customPatterns` (اسٹرنگز، regex،
   یا `{ name, pattern, severity }` ریکارڈز)۔

جب `mode === "block"` ہو **اور** کم از کم ایک شناخت شدت کی
حد پر پوری اترتی ہو، تو `preCall` یہ واپس کرتا ہے: `{ block: true, message: "Request rejected:
suspicious content detected" }`۔ `warn`/`log` موڈز میں guardrail لاگ کرتا ہے، لیکن
کال کی اجازت دیتا ہے۔ مشترکہ معاون `evaluatePromptInjection()` بھی export کیا جاتا ہے
تاکہ وہ callers جو registry سے گزرے بغیر prompts کا جائزہ لینا چاہتے ہیں، اسے استعمال کر سکیں۔

**اسکین کی حد (v3.8.20):** detector، یکجا کیے گئے prompt متن کے صرف **پہلے 16 KB** کا
معائنہ کرتا ہے — `src/shared/utils/inputSanitizer.ts` میں
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 bytes)۔ `detectInjection()` اور
`evaluatePromptInjection()` دونوں pattern loop چلانے سے پہلے
`slice(0, MAX_INJECTION_SCAN_BYTES)` استعمال کرتے ہیں۔ Injection directives عموماً input کے
ابتدائی حصے کے قریب ہوتے ہیں، اس لیے یہ multi-hundred-KB payloads پر regex CPU/GC کو محدود
کرتا ہے، جبکہ شناخت کو کمزور نہیں کرتا (ملاحظہ کریں
#3932، #4041)۔

### Credential Masker (`credentialMasker.ts`)

**دونوں** stages پر default chain میں سب سے آخر میں چلتا ہے (priority `95`)۔ outbound payload
(message content، tool-call arguments، tool results) **اور** provider response سے معروف
API-key / secret-token patterns کو redact کرتا ہے، تاکہ prompt میں paste کی گئی credential
(یا tool result کے ذریعے واپس دہرائی گئی credential) upstream provider یا واپس client تک
لیک نہ ہو۔

- **صرف opt-in**، PII redaction کے اسی convention کے مطابق (سخت اصول #20 سے ملحق):
  یہ غیر فعال رہتا ہے، جب تک `settings.credentialRedactionEnabled === true` **یا**
  `CREDENTIAL_REDACTION_ENABLED=true` نہ ہو۔ اس کے بند ہونے پر guardrail کوئی کارروائی نہیں کرتا —
  یہ نہ کبھی block کرتا ہے اور نہ کبھی rewrite کرتا ہے۔
- `redactCredentials()` مکمل payload/response tree میں traversal کرتا ہے (`walkValue()`،
  prototype-pollution سے محفوظ، `WeakSet` کے ذریعے cycle-safe) اور matches کو
  `[REDACTED:<type>]` placeholder سے بدل دیتا ہے، جبکہ صرف انہی branches کو clone کرتا ہے
  جو حقیقتاً تبدیل ہوئی ہوں۔
- `CREDENTIAL_PATTERNS` میں LLM provider keys (OpenAI، OpenAI-proj،
  Anthropic، Google، Hugging Face، Replicate)، VCS/SaaS tokens (GitHub، Slack،
  Linear، Notion، npm، Postman، Discord)، payment keys (Stripe، Square)، cloud
  keys (AWS access key، Twilio، SendGrid، Mailgun)، private keys / JWTs،
  credential پر مشتمل connection strings (`mongodb://user:pass@...`، وغیرہ)، اور
  ایک عمومی `Authorization`/`x-api-key`/`api-key`/`apikey` header-value
  pattern شامل ہیں۔ Header کی شکل والی keys (`authorization`، `x-api-key`، `api-key`،
  `apikey`) کو عمومی text regex کے ذریعے نہیں بلکہ ساختی طور پر redact کیا جاتا ہے (صرف value،
  جبکہ `Bearer `/`Basic ` جیسا scheme prefix محفوظ رہتا ہے)۔
- guardrail کبھی block نہیں کرتا؛ یہ صرف rewrite (`modifiedPayload` /
  `modifiedResponse`) اور annotate (`meta.credentialsRedacted`، `meta.count`) کرتا ہے۔

Regression guard: `tests/unit/credential-masker-guardrail.test.ts`۔

## بنیادی کنٹریکٹ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true چین کو فوری طور پر روک دیتا ہے
  message?: string; // بلاک ہونے پر ظاہر کیا جاتا ہے
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // درخواست کو دوبارہ لکھنے کے لیے preCall کے ذریعے واپس کیا جاتا ہے
  modifiedResponse?: TValue; // جواب کو دوبارہ لکھنے کے لیے postCall کے ذریعے واپس کیا جاتا ہے
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ایک گارڈ ریل `void`، `{}`، یا `{ block: false }` واپس کرکے "کوئی تبدیلی نہیں" کا اشارہ دیتی ہے۔ `modifiedPayload`/`modifiedResponse` واپس کرنے سے چین میں آگے آنے والی گارڈ ریلز تک پہنچنے والی قدر تبدیل ہو جاتی ہے۔
`signal?: AbortSignal` کالر کے لائف سائیکل کو گارڈ ریلز تک پہنچاتا ہے۔ درخواست کا منسوخ ہونا دانستہ fail-open استثنا ہے: میڈیا برجز کام روک دیتے ہیں اور صفائی کرتے ہیں، مگر خام میڈیا کو ایسے ہدف کے لیے بحال نہیں کرتے جس کے بارے میں معلوم ہو کہ وہ اسے سپورٹ نہیں کرتا۔

## رجسٹری (`registry.ts`)

سنگلٹن `guardrailRegistry` درج ذیل سہولیات فراہم کرتی ہے:

- `register(guardrail)` — ایک گارڈ ریل شامل کرتی ہے (یا نارملائزڈ نام کے لحاظ سے تبدیل کرتی ہے) اور
  صعودی `priority` کے مطابق دوبارہ ترتیب دیتی ہے۔
- `clear()` / `list()` — انتظامی معاون فنکشنز۔
- `runPreCallHooks(payload, context)` — فعال گارڈ ریلز پر تکرار کرتی ہے، پے لوڈ کو
  `modifiedPayload` کے ذریعے آگے بڑھاتی ہے، اور پہلے `block: true` پر رک جاتی ہے۔
- `runPostCallHooks(response, context)` — جواب کی جانب بھی یہی بہاؤ استعمال کرتی ہے۔
- `resetGuardrailsForTests({ registerDefaults })` — حالت صاف کرتی ہے اور صاف ستھری ٹیسٹ علیحدگی کے لیے، اختیاری طور پر
  ڈیفالٹس کو دوبارہ رجسٹر کرتی ہے۔

دونوں رنرز `{ blocked, payload|response, results, guardrail?, message? }`
واپس کرتے ہیں، جہاں `results`، `GuardrailExecutionResult` ریکارڈز کی ایک ارے ہے جس میں
ہر گارڈ ریل کے `blocked`، `skipped`، `modified`، `error`، اور `meta` فیلڈز شامل ہوتے ہیں،
جو ٹریسنگ کے لیے مفید ہیں۔

### ہر درخواست کے لیے گارڈ ریلز کو غیر فعال کرنا

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` گارڈ ریل ناموں کی ایک
نقل سے پاک فہرست یکجا کرتا ہے جنہیں موجودہ درخواست کے لیے چھوڑ دینا چاہیے۔
ذرائع (سب اختیاری، سب ضم کیے جاتے ہیں):

- `apiKeyInfo.disabledGuardrails`
- درخواست کی باڈی کا `disabledGuardrails` (اعلیٰ سطح پر)
- درخواست کی باڈی کا `metadata.disabledGuardrails`
- ہیڈر `x-omniroute-disabled-guardrails` (یا قدیمی
  `x-disabled-guardrails`)

اقدار اسٹرنگز کی ارے یا کوما سے جدا کی گئی اسٹرنگ ہو سکتی ہیں؛ ناموں کو
لوئرکیس kebab-case میں نارملائز کیا جاتا ہے (`pii_masker` → `pii-masker`)۔ نتیجہ
`context.disabledGuardrails` کے ذریعے رجسٹری کو دیا جاتا ہے، جو مماثل
گارڈ ریلز کو چھوڑ دیتی ہے (`results` میں `skipped: true`)۔

## عمل درآمد کی ترتیب

`src/sse/handlers/chat.ts` اور `open-sse/handlers/chatCore.ts` سے گزرنے والی ہر درخواست کے لیے:

1. `resolveDisabledGuardrails(...)`، API کلید، باڈی، اور ہیڈرز سے نظر انداز کیے جانے والے عناصر کی فہرست بناتا ہے۔
2. `guardrailRegistry.runPreCallHooks(body, ctx)` ترجیح کی صعودی ترتیب میں گارڈ ریلز چلاتا ہے:
   - غیر فعال گارڈ ریلز کو `skipped` کے طور پر ریکارڈ کیا جاتا ہے۔
   - ہر گارڈ ریل کا `preCall`، `modifiedPayload` کے ذریعے پے لوڈ دوبارہ لکھ سکتا ہے۔
   - پہلا `block: true` سلسلے کو فوری طور پر روک دیتا ہے اور ہینڈلر گارڈ ریل کی جانب سے مسترد کیے جانے کا جواب واپس کرتا ہے۔
3. (ممکنہ طور پر دوبارہ لکھا گیا) پے لوڈ کومبو روٹنگ اور اپ اسٹریم ڈسپیچ میں جاتا ہے۔
4. جواب تیار ہونے کے بعد، `guardrailRegistry.runPostCallHooks(...)` جواب پر یہی سلسلہ چلاتا ہے۔ یہاں `block: true` اپ اسٹریم جواب کو خارج کر دیتا ہے۔

خرابی پیدا کرنے والی گارڈ ریلز کو `error: <message>` کے ساتھ ریکارڈ کیا جاتا ہے اور `logger.warn` کے ذریعے لاگ کیا جاتا ہے، لیکن سلسلہ جاری رہتا ہے — یہ ڈیزائن کے لحاظ سے فیل-اوپن ہے۔

## کنفیگریشن

بلٹ اِن گارڈ ریلز کے ذریعے پڑھے جانے والے ماحولیاتی متغیرات:

| متغیر                                 | استعمال کنندہ              | اثر                                                                                                    |
| ------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`         | تشخیص کو مکمل طور پر غیر فعال کرنے کے لیے `false` مقرر کریں۔                                           |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`         | انجیکشن پالیسی: `warn`، `block`، یا `log`۔ پرانی قدر `redact` انجیکشن متن کو دوبارہ نہیں لکھتی۔        |
| `INJECTION_GUARD_MODE`                | `prompt-injection`         | انجیکشن گارڈ کا موڈ؛ یہ DB فیچر فلیگ بھی ہے جو ماحولیاتی متغیرات کو **اوور رائیڈ** کرتا ہے (DB > ENV)۔ |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`         | کم از کم شدت جسے `MODE=block` مسترد کرتا ہے: `high` (ڈیفالٹ)، `medium`، یا `low`۔                      |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`         | `INPUT_SANITIZER_BLOCK_THRESHOLD` کا پرانا عرف۔                                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`               | `true` ہونے پر، درخواست کا PII حذف کر دیا جاتا ہے (انجیکشن موڈ سے آزاد)۔                               |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (ڈاؤن اسٹریم) | جواب کی جانب ماسکر کے رویے کو کنٹرول کرتا ہے۔                                                          |

Modality Bridge گارڈ ریلز ماحولیاتی متغیرات کے بجائے DB کی معاونت والے سیٹنگز اسٹور (`getSettings()`) سے رن ٹائم کنفیگریشن پڑھتی ہیں۔ Vision کی بنیادی کلیدیں `modalityBridgeVisionEnabled`، `modalityBridgeVisionMode`، `modalityBridgeVisionModel`، `modalityBridgeVisionTaskAware`، `modalityBridgeVisionPrompt`، `modalityBridgeVisionTimeout`، `modalityBridgeVisionMaxImages`، `modalityBridgeVisionMaxChars`، `modalityBridgeCacheEnabled`، `modalityBridgeCacheTtlMinutes`، اور `modalityBridgeCacheMaxEntries` ہیں۔ پرانی `visionBridge*` کلیدیں صرف دستاویزی، ایک سائیکل کے ریڈ فال بیک کے طور پر قبول کی جاتی ہیں؛ ڈیش بورڈ رائٹس بنیادی کلیدیں استعمال کرتی ہیں۔ ڈیفالٹس اور فال بیک ریزالور `src/shared/constants/modalityBridgeDefaults.ts` میں موجود ہیں، جبکہ پرانے کانسٹنٹس `src/shared/constants/visionBridgeDefaults.ts` میں برقرار رکھے گئے ہیں۔

Audio، `modalityBridgeAudioEnabled`، `modalityBridgeAudioModel`، `modalityBridgeAudioTimeout`، اور `modalityBridgeAudioMaxClips` کے ساتھ مشترکہ `modalityBridgeCache*` سیٹنگز استعمال کرتا ہے۔ Audio کے لیے پرانی کلیدوں کا کوئی فال بیک نہیں ہے کیونکہ یہ کلیدیں Modality Bridge اسکیما کے ساتھ متعارف کرائی گئی تھیں۔

Video، `modalityBridgeVideoEnabled`، `modalityBridgeVideoAnalysisMode`، `modalityBridgeVideoModel`، `modalityBridgeVideoFrameCount`، `modalityBridgeVideoSamplingPolicy`، `modalityBridgeVideoMaxVideos`، اور `modalityBridgeVideoTimeout` کے ساتھ مشترکہ `modalityBridgeCache*` سیٹنگز استعمال کرتا ہے۔ یہ ڈیفالٹ طور پر غیر فعال ہے کیونکہ FFmpeg/ffprobe اختیاری آپریشنل انحصارات ہیں اور فریم کیپشننگ تاخیر اور ماڈل کی لاگت میں اضافہ کرتی ہے۔

## حسبِ ضرورت Guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

مراحل:

1. `BaseGuardrail` کو توسیع دیتے ہوئے `src/lib/guardrails/myGuardrail.ts` بنائیں۔
2. `preCall` اور/یا `postCall` نافذ کریں۔
3. یا تو import کے وقت رجسٹر کریں (`registerDefaultGuardrails` سے push کریں) یا
   runtime پر `guardrailRegistry.register(...)` کو کال کریں — registry اسی normalized نام والے
   کسی بھی سابقہ guardrail کو بدل دیتی ہے۔
4. `tests/unit/` کے تحت ٹیسٹ شامل کریں (موجودہ مثالیں:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)۔

## ٹیسٹنگ

معلوم حالت سے آغاز کرنے کے لیے ٹیسٹس کے درمیان `resetGuardrailsForTests()` استعمال کریں۔
خالی registry سے آغاز کرنے اور صرف زیرِ ٹیسٹ guardrails رجسٹر کرنے کے لیے
`{ registerDefaults: false }` پاس کریں۔ Vision Bridge dependency
injection (`deps.getSettings`, `deps.callVisionModel`) قبول کرتا ہے؛ Audio Bridge
settings، capabilities، STT model کے انتخاب، credential
کی جانچ، اور transcription کے لیے مساوی seams فراہم کرتا ہے۔ اس طرح ٹیسٹس DB
یا network تک رسائی کے بغیر دونوں flows کو آزما سکتے ہیں۔

## Injection-guard route coverage اور red-team (مرحلہ 8 · بلاک D)

injection-guard (`createInjectionGuard` / `withInjectionGuard`) ان تمام routes کا احاطہ کرتا ہے
جو user prompts قبول کرتے ہیں۔ یہ `INJECTION_GUARD_MODE` کا احترام کرتا ہے (default `warn` = صرف log؛
`block` = HTTP 400 `SECURITY_001` واپس کرتا ہے)۔

| قسم          | Routes                                                                                                                                               | Default mode |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| متن (موجودہ) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| تخلیقی       | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ڈیٹا         | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

متن اخذ کرنا (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` کا احاطہ کرتا ہے۔

**Red-team (ہر شب، `nightly-llm-security.yml`):** promptfoo تصدیق کرتا ہے کہ ہر route
`INJECTION_GUARD_MODE=block` میں OWASP-LLM corpus کو block کرتا ہے؛ garak probes چلاتا ہے (secret نہ ہونے پر چھوڑ دیتا ہے)۔
`moderations` کو یکسانیت کے لیے شامل کیا گیا ہے — block-mode میں operators اسے
`resolveDisabledGuardrails` کے ذریعے مستثنیٰ کر سکتے ہیں۔

ہر شب چلنے والے workflow (`.github/workflows/nightly-llm-security.yml`، cron + دستی
dispatch) میں دو jobs ہیں:

- **`promptfoo-guard` (blocking)** — `INJECTION_GUARD_MODE=block` کے ساتھ
  `promptfoo eval -c promptfooconfig.yaml` چلاتا ہے۔ ہر مخالفانہ case (مثلاً "ignore all
  previous instructions…"، DAN-style jailbreaks) تصدیق کرتا ہے کہ response میں
  `error.code === "SECURITY_001"` موجود ہے، یعنی guard نے واقعی request مسترد کی۔
- **`garak` (مشاورتی)** — مقامی OmniRoute instance (`http://localhost:20128/v1`) کے خلاف
  garak کو `--probes promptinject,dan,leakreplay` کے ساتھ چلاتا ہے۔ اسے provider
  secret (`PROMPTFOO_PROVIDER_KEY`) کے ذریعے مشروط کیا گیا ہے؛ یہ مؤدبانہ طور پر چھوڑ دیتا ہے اور اس کے آخر میں
  `|| true` شامل ہے، لہٰذا یہ CI کو ناکام کیے بغیر رپورٹ کرتا ہے۔

guard helper (`createInjectionGuard` / `withInjectionGuard`) کی coverage
ہر prompt رکھنے والے `/v1` route تک پھیلی ہوئی ہے؛ prompt کا متن
`src/shared/utils/inputSanitizer.ts` میں موجود `extractMessageContents()` کے ذریعے
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` سے حاصل کیا جاتا ہے۔
