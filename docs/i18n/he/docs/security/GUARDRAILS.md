> **מקור האמת:** `src/lib/guardrails/`
> **עדכון אחרון:** 2026-08-29 — v3.8.51 (מקור התמליל של Video Bridge מוצהר על ידי הקורא,
> ועדיין אינו מאומת על ידי השרת — הובהר בהתאם ל-#11661)

מנגנוני הגנה אוכפים בטיחות, מדיניות והתמרות תוכן בגבול
שבין OmniRoute לספקים במעלה הזרם. כל מנגנון הגנה יכול לבדוק (ובאופן
אופציונלי לדחות, להתמיר או להוסיף הערות אל) מטעני בקשות (`preCall`) ותגובות
במעלה הזרם (`postCall`).

המערכת פועלת בגישת **fail-open**: אם מנגנון הגנה זורק חריגה במהלך הביצוע, הרישום
מתעד את השגיאה וממשיך למנגנון ההגנה הבא במקום להכשיל את
הבקשה. חסימה היא החלטה מפורשת (`block: true`), ולעולם אינה מתרחשת בטעות.

## מנגנוני הגנה מובנים

הרישום טוען אוטומטית בעת הייבוא שישה מנגנוני הגנה לפי סדר עדיפויות
(ראו `registry.ts` → `registerDefaultGuardrails()`):

| עדיפות | שם                  | שלב(ים)        | קובץ                  |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

מספרי עדיפות נמוכים יותר מופעלים **ראשונים**.

### גשר ראייה (`visionBridge.ts`) — גשר מודאליות PR-1

מיירט בקשות המכילות תמונות ומיועדות ל**מודלים ללא יכולות ראייה**, ומנתב
מחדש את הבקשה כולה למודל בעל יכולות ראייה או מחליף את חלקי התמונה בתיאורי
טקסט שהופקו באמצעות מודל ראייה הניתן להגדרה, לפני הקריאה לשירות החיצוני.
כך יכולים ספקי טקסט בלבד לטפל בשקיפות במטענים מרובי־מודאליות.

זרימה:

1. דלג אם מודל היעד כבר תומך בראייה (אלא אם הוא מופיע ברשימת הגישור הכפוי
   `isVisionBridgeForcedModel`).
2. חלץ חלקי תמונה באמצעות `extractImageParts(messages)`
   ‏(`visionBridgeHelpers.ts`), שמעבירה את הטיפול אל **גלאי המדיה המאוחד**
   `detectMediaParts()` שב־`open-sse/utils/mediaParts.ts` — מקור האמת היחיד
   המשותף למסנן התאימות המשולב. החילוץ מוגבל באמצעות רשימת היתרים לחלקים
   ברמה העליונה, בצורות שאותן `replaceImageParts` יכול לשלב בחזרה
   (חוזה החילוץ↔ההחלפה): `image_url` של OpenAI, ‏`source.type:"base64"`
   בקידוד base64 של Anthropic, כתובת URL מסוג `source.type:"url"` של
   Anthropic, ו־`input_image` של Responses API. התאמות מקוננות וצורות הכוללות
   מחוונים בלבד הן חומר עבור המסנן המשולב ולעולם אינן מחולצות. דלג אם לא
   נמצאו התאמות.
3. פתור את תצורת זמן הריצה באמצעות `resolveVisionBridgeRuntimeSettings()`
   ‏(`src/shared/constants/modalityBridgeDefaults.ts`): למפתחות ההגדרות
   החדשים `modalityBridge*` יש קדימות; המפתחות הישנים `visionBridge*` נשארים
   כ**חלופה למחזור אחד** (חלון חזרה לאחור). דלג לפני כל מעבר על המדיה כאשר
   הגשר מושבת.
4. בורר המצבים (`modalityBridgeVisionMode`, ראו טבלה להלן) מחליט אם לנתב
   מחדש או לתאר. ניתוב מחדש מחזיר `modifiedPayload` שבו רק `model` הוחלף,
   יחד עם מטא־נתונים `{ rerouted, fromModel, toModel, imagesKept }`.
5. נתיב התיאור: הגבל את מספר התמונות ל־`maxImages`, הרכב הנחיה המותאמת
   למשימה, בדוק את מטמון התיאורים, קרא למודל הראייה **במקביל**
   (`Promise.allSettled`), והזרק במקומן חלקי טקסט מסוג
   `[תמונה N]: <תיאור>`. תיאור שנכשל מחזיר `null`, וחלק התמונה המקורי
   **נשמר** (#4012) — למעט בנתיב התיאור המשולב, כאשר כל ניסיונות התיאור
   נכשלו, שבו שירות חיצוני שאושר כחסר יכולות ראייה מקבל במקום זאת מציין
   `(לא זמין — לא מחובר ספק בעל יכולות ראייה)` (#8430).
6. החזר `modifiedPayload` יחד עם מטא־נתונים (`imagesProcessed`,
   `descriptions`, `processingTimeMs`, `visionModel`).

#### בורר מצבים (`modalityBridgeVisionMode`)

| מצב        | ברירת מחדל | התנהגות                                                                                                                                                                                                                                                 |
| ---------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | היוריסטיקה הישנה, ללא שינוי (#6640/#7204): מודלים שאינם משולבים או מודלי `auto/` מנותבים מחדש למודל הראייה הטוב ביותר, אלא אם למודל המקורי כבר יש פרטי גישה שמישים (ואז מתבצע תיאור); יעדים משולבים תמיד משתמשים בתיאור.                                |
| `describe` |            | תמיד תאר — מקטע הניתוב מחדש נעקף לחלוטין; המודל שנבחר בידי המשתמש תמיד משיב.                                                                                                                                                                            |
| `reroute`  |            | כפה ניתוב מחדש: מנגנון ההגנה ששומר על מודל בעל פרטי גישה נעקף. מנגנון ההגנה על פרטי הגישה של **יעד** הניתוב מחדש עדיין חל — כאשר אין יעד ראייה שמיש, הבקשה ממשיכה לנתיב התיאור כדי שתמונות גולמיות לעולם לא יגיעו למערכת קצה התומכת בטקסט בלבד (#8430). |

מצבים כפויים מבצעים קיצור דרך **לפני** הפעלת היוריסטיקת `auto`; ההתנהגות של
`auto` זהה ברמת הבתים למנגנון ההגנה שקדם ל־PR-1.

#### תחום מפתח API (`visionBridgeKeyScope.ts`)

כאשר מפתח ה־API של מבצע הקריאה מגביל את `allowedConnections`, מאגרי המכסות
(`allowedQuotas`) או המודלים (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), הגשר בוחר רק
מודלים לניתוב מחדש ולתיאור שהמפתח רשאי להשתמש בהם, בחיבורים שהמפתח רשאי
להשתמש בהם. לאחר מכן, קריאת התיאור עוברת תמיד דרך הלולאה העצמית של
OmniRoute עם הכותרת `x-omniroute-self-loop-key-id`, כך שבקשת הצ'אט המקבלת
אוכפת שוב את מדיניות החיבורים והמודלים של אותו מפתח. `enforceApiKeyPolicy()`
מכבד את הכותרת הזו רק יחד עם אסימון הנושא של הלולאה העצמית, ולכן היא יכולה
רק לצמצם את הגישה, ומזהה שאינו ניתן לפתרון נדחה.

אם לא מותר למפתח להשתמש באף מודל ראייה, נתיב התיאור מפנה את הדרך והבקשה
עוברת ללא שינוי, באותה התנהגות כשל־פתוח של מנגנון הגנה מושבת (מטא־נתונים
`{ skipped: true, reason: "no_permitted_vision_model" }`). בקשות ללא מפתח,
ומפתחות ללא הגבלות אלה, מתנהגים בדיוק כפי שהתנהגו קודם לכן.

#### הנחיית תיאור מותאמת למשימה (`modalityBridgeVisionTaskAware`)

ברירת המחדל היא **true**. הפונקציה `composeVisionPrompt()` (`visionBridgeHelpers.ts`) מצרפת
את הטקסט של **הודעת המשתמש האחרונה** (מקוצר ל-500 תווים) להנחיית התיאור
הבסיסית, כך שהתיאור מונחה לפי מה שהמשתמש ביקש בפועל
(דפוס codex-vision-proxy), ומבקשת ממודל הראייה לתמלל טקסט גלוי.
כאשר הדגל כבוי — או כשאין טקסט מהמשתמש — נעשה שימוש בהנחיה הבסיסית ללא שינוי.

הבקשה תואמת-OpenAI של לולאת התיאור העצמית (`callVisionModelSingle()`
ב-`visionBridgeHelpers.ts`) מבקשת תמיד `image_url.detail: "high"` —
ללא תנאי, עבור כל קורא/ספק, וללא תלות באות כלשהו מהלקוח.
דגימה ברמת פירוט נמוכה פוגעת בדיוק ה-OCR בדיוק עבור משימת תמלול הטקסט
שהנחיה זו מבקשת לבצע, ולכן קריאת התיאור עצמה תמיד מבקשת רמת פירוט גבוהה,
ללא קשר לרמת הפירוט שבה השתמשה הבקשה הנכנסת המקורית. הדבר משפיע רק על גוף
בקשת התיאור הפנימית; הוא אינו משנה את האופן שבו OmniRoute מעביר את
`image_url.detail` של הקורא בבקשה הראשית — ברירת מחדל זו מוחלת בנפרד, ורק
עבור לקוחות OpenCode שזוהו, ב-`defaultImageDetail()`
(`open-sse/handlers/chatCore/upstreamBody.ts`). לענף בפורמט התעבורה של
Anthropic בלולאת התיאור העצמית אין שדה `detail`, ולכן אף אחת מברירות המחדל
אינה משפיעה עליו.

#### מגבלת פלט התיאור (`modalityBridgeVisionMaxChars`)

| מפתח                           | ברירת מחדל | טווח             |
| ------------------------------ | ---------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` או 100–50000 |

`0` (ברירת המחדל) פירושו **ללא מגבלה** — התיאור שמוחזר על ידי
`callVisionModel()` מועבר ללא שינוי, וכך נשמרת ההתנהגות הקיימת.
כל ערך בטווח 100–50000 מקצר את התיאור ומוסיף לו סיומת `…` לפני שהוא משולב
בחזרה בתור `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()`
ב-`src/lib/guardrails/visionBridge.ts`). הגדילו ערך זה עבור משימות OCR
עתירות פרטים שבהן המודל שבהמשך זקוק לתמלול המלא; הקטינו אותו כדי להגביל
את השימוש בטוקנים במודלי ראייה שמפיקים פלט רב.
השדה בלוח הבקרה נמצא בחלונית Advanced של לשונית Vision
(`modality-bridge-max-chars` ב-`ModalityBridgeVisionTab.tsx`), והוא מעלה כל
ערך בין 1 ל-99 לסף המינימלי 100, תוך השארת ערך `0` מפורש ללא שינוי —
`0` הוא ערך Zod תקין בפני עצמו
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), ולא רק
ברירת המחדל של מצב "לא מוגדר".

#### מטמון תיאורים (`modalityBridge/bridgeCache.ts`)

מטמון LRU + TTL בזיכרון עבור פלטי תיאור, המשותף לכל התהליך.
מפתח = `sha256(imageRef + composedPrompt + configuredBridgeModel)` עם
מסגור הכולל קידומת אורך (ללא התנגשויות בין גבולות השדות). רכיב המודל הוא
מודל הגשר **המוגדר**, ולא המודל שהשיב בפועל —
`callVisionModel` עשוי לעבור פנימית למודל חלופי, ויצירת מפתח לכל ניסיון
תפצל את המטמון. תיאורים שנכשלו לעולם אינם נשמרים במטמון. הגדרות:

| מפתח                            | ברירת מחדל | טווח    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### נרמול תמונות מרוחקות (קריאת תיאור עצמית/אחזור base64)

כאשר הגשר מאחזר בעצמו תמונה **מרוחקת** — קריאת התיאור העצמית של Anthropic
וההמרה ל-base64 בפורמט התעבורה של Claude
(`ensureBase64ImagesForClaudeWire`), שתיהן באמצעות
`fetchRemoteImageAsDataUri()` ב-`visionBridgeHelpers.ts` — ה-URI של הנתונים
שנוצר מועבר דרך `normalizeDataUri()`
(`open-sse/utils/imageNormalize.ts`) לפני הטמעתו בבקשה למודל הראייה.
תמונות גדולות מדי מוקטנות כך שהצלע הארוכה תהיה **2048px** (בהתאם למגבלת
שינוי הגודל ש-OpenAI/Anthropic כבר מחילים בצד השרת), דבר שמפחית את מספר
הבתים בהעלאה ואת זמן ההשהיה, מבלי לשנות את מה שמודל הראייה רואה. שינוי
הגודל משתמש ב-`sharp`, שנטען באמצעות ייבוא דינמי: בפלטפורמה שבה הטעינה של
הקובץ הבינארי המקורי שלו נכשלת, `normalizeDataUri()` **לעולם אינה זורקת
חריגה** — היא חוזרת להעברה ללא שינוי של הבתים המקוריים, כך שמסלול
התיאור/ההמרה ל-base64 ממשיך תמיד לפעול. גם בתים שאינם תמונה (אחזור שלא
החזיר תמונה שניתן לפענח) מועברים ללא שינוי. נרמול זה מוגבל לתמונות שהגשר
מאחזר עבור הקריאה העצמית שלו — הוא לעולם אינו מוחל על מטען ההעברה הגולמי
של הקורא, בהתאם לעקרון שלפיו שינוי מתבצע רק בהסכמה מפורשת (כלל קשיח מס'
20).

#### סכמת הגדרות + מיגרציה

מפתחות `modalityBridge*` החדשים עוברים אימות Zod ב-`updateSettingsSchema`
(`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`,
`modalityBridgeVisionMode`, `modalityBridgeVisionModel`,
`modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`,
`modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`,
`modalityBridgeVisionMaxChars`, שלישיית `modalityBridgeCache*`, וקבוצת
`modalityBridgeAudio*` המשמשת את Audio Bridge. המיגרציה
`141_modality_bridge_settings.sql` מעתיקה ערכי `visionBridge*` קיימים
מהמערכת הישנה למפתחות החדשים המתאימים (אידמפוטנטית, ולעולם אינה דורסת ערך
`modalityBridge*` שהוגדר על ידי המפעיל); המפתחות הישנים ממשיכים להתקבל
כאפשרות נסיגה לקריאה במשך מחזור גרסה אחד.

#### כותרת שקיפות + סטטיסטיקות

תגובות שעברו המרה באמצעות תיאור כוללות
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
(נבנית על ידי `buildModalityBridgeHeader()` ב-`modalityBridge/bridgeStats.ts`,
ונחתמת על ידי `withModalityBridgeHeader()` ב-`src/sse/handlers/chatHelpers.ts`).
בקשות שנותבו מחדש אינן מקבלות **שום** כותרת — המטען לא השתנה, והחלפת המודל
כבר גלויה בשדה `model` שבגוף התגובה.

`GET /api/modality-bridge/stats` (אימות ניהולי, באותה רמה כמו
`GET /api/settings`) מחזירה את המונים בזיכרון לכל מודליות
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` עבור `vision`,‏ `audio` ו-
`video`. הערך `averageLatencyMs` משתמש ב-`latencySamples`, ולא בכל הניסיונות,
כמכנה; פעולה ללא מדידת זמן אינה מייצרת דגימה מלאכותית של אפס אלפיות השנייה.
`bridged` נשאר הכינוי התואם לאחור להמרות מוצלחות;
ניסיונות שנכשלו אינם מגדילים אותו.
המונים מתאפסים בעת הפעלה מחדש של התהליך, לפי התכנון
(טלמטריה, לא הנהלת חשבונות).

#### תצורת לוח המחוונים

העמוד הייעודי בלוח המחוונים הוא
`/dashboard/settings/modality-bridge`. הלשוניות `Vision`,‏ `Audio`
ו-`Video`, שניתנות לכתיבה ב-URL, משמרות את פרמטרי השאילתה בעת החלפת הערך `tab`.
הלשונית Vision מציגה הפעלה, מצב, בחירת מודל (כולל ברירת המחדל האוטומטית),
הנחיות תלויות-משימה, מגבלות מתקדמות עבור זמן קצוב/תמונה/אורך תיאור/מטמון, מוני
זמן ריצה ובקשת דוגמה מוגנת. גם הלשונית Audio פעילה: היא מציגה
הפעלה, בורר מודלים ל-STT בלבד עם Auto, מגבלות זמן קצוב/אורך מרבי של קטע שמע,
מוני שמע ובדיקת דוגמה מסוג `input_audio`. הלשונית Video מתפקדת: היא מדווחת
על מצב זמן הריצה של FFmpeg/ffprobe — אחד מארבעה מצבי ממשק משתמש מפורשים (`unknown` כאשר
הבדיקה מתבצעת או לא הצליחה להסתיים, `restricted` במארח לוח מחוונים שאינו loopback
שבו הבדיקה מדולגת בצד הלקוח, `unavailable` לאחר שבוצעה בדיקה ואושר שהכלים חסרים,
או `available` עם גרסאות FFmpeg/ffprobe) — שומרת
מגבלות הפעלה/מודל/פריימים/וידאו/זמן קצוב, מסננת את בורר המודלים למודלים
התומכים בראייה, ומציגה מוני וידאו.

כרטיס Vision Bridge הקודם תחת הגדרות AI הוא קישור תאימות לעמוד
החדש; הוא כבר אינו מחזיק עותק נוסף של הטופס. Media Providers מקשר גם
תהליכי עבודה של Image-to-Text ו-Speech-to-Text ללשוניות Modality
Bridge המתאימות, מבלי להסיר את סביבת הניסוי הקיימת של Speech-to-Text.

**עקיפת בקרת קבלה בלולאה עצמית:** כאשר קריאת התיאור מנותבת דרך
לולאת `/v1` העצמית של OmniRoute (מודל ספק לא תקני), בקשת המשנה שולחת
`x-omniroute-admission-bypass: internal` ומאומתת באמצעות פרטי הגישה שנבחרו
עבור הלולאה העצמית — ערך הסמן המקומי `sk_omniroute` במצב מקומי, או מפתח
הסביבה `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` שהוגדר בידי המפעיל (#1350), כך
שפריסות עם `REQUIRE_API_KEY=true` עדיין יוכלו להריץ את קריאת התיאור. העקיפה
מכובדת רק עבור פרטי הגישה המדויקים האלה, ולכן לקוחות חיצוניים אינם יכולים
להשתמש בכותרת כדי לדלג על בקרת הקבלה.

ברירות המחדל הקודמות נמצאות ב-`src/shared/constants/visionBridgeDefaults.ts`;
ברירות המחדל החדשות של מצב/תלות-במשימה/מטמון ופותר ההגדרות נמצאים ב-
`src/shared/constants/modalityBridgeDefaults.ts`. מנגנון ההגנה חושף אפשרות
בנאי `deps`, כדי שבדיקות יוכלו להזריק מימושים מדומים של `getSettings` ושל
`callVisionModel`.

### גשר שמע (`audioBridge.ts`) — Modality Bridge PR-3

מיירט בקשות צ'אט המכילות שמע לפני שהן מגיעות ליעד שלא ידוע כי הוא
מקבל קלט שמע. הוא לעולם אינו מנתב מחדש את בקשת הצ'אט: חלקי השמע
מתומללים דרך נקודת הקצה הקיימת מרובת-החלקים ותואמת OpenAI, ומודל
הצ'אט שנבחר ממשיך עם תמלילי טקסט.

תהליך:

1. פתור את `supportsAudio` באמצעות `getResolvedModelCapabilities()`. מטא-נתונים
   מפורשים מרישום הספקים מקבלים קדימות, לאחר מכן מטא-נתונים סטטיים של המודל,
   ולבסוף `modalities_input` מסונכרן. רשימת קלט מוצהרת ללא `audio` היא `false`;
   בהיעדר ראיות ליכולת, הערך נשאר `null`. גם `false` וגם `null` מפעילים את
   הגשר השמרני, בעוד `true` עוקף אותו.
2. פתור את הגדרות `modalityBridgeAudio*` וחלץ חלקי שמע ניתנים לשילוב מחדש
   ברמה העליונה מכל הודעה באמצעות הגלאי המשותף `detectMediaParts()`.
   תבניות התעבורה הנתמכות הן `input_audio` של OpenAI,‏ `audio_url` ו-
   `source.media_type: "audio/*"`. שמע מקונן מזוהה לצורכי ניתוב, אך אינו
   מוסר במסלול השילוב מחדש. העבודה מוגבלת לפי `modalityBridgeAudioMaxClips`;
   חלקים מאוחרים יותר נשארים ללא שינוי.
3. כבד הגדרת `provider/model`, או אפשר ל-`selectAudioBridgeModel()` לעבור על
   `AUDIO_TRANSCRIPTION_PROVIDERS` לפי סדר הקטלוג היציב ולבחור את המודל הראשון
   בעל פרטי גישה שימושיים של ספק פעיל.
4. `callAudioTranscription()` ממירה שמע בקידוד base64/data-URI ל-`file`
   מרובה-חלקים, או מורידה `audio_url` מרוחק דרך מנגנון ההגנה הציבורי בלבד
   לתעבורה יוצאת, עם הצמדת DNS ומגבלה של 25 MB. לאחר מכן היא שולחת באמצעות
   POST את הקובץ ואת המודל שנבחר ללולאה העצמית המקומית
   `/v1/audio/transcriptions`, עם אימות באמצעות `resolveSelfLoopBearer()`.
   נתיב התמלול הקיים מבצע חיפוש רגיל של פרטי גישה, טיפול בתקופות צינון/הגבלת
   קצב וניתוב לספק.
5. קריאות מוצלחות מחליפות את החלקים שלהן ב-`[Audio N]: <transcript>`. הקריאות
   מופעלות באמצעות `Promise.allSettled`: כשל יחיד משמר את חלק השמע המקורי
   המתאים (חוזה #4012). אם כל הקריאות נכשלות והוכח כי היעד הוא
   `supportsAudio === false`, החלקים הופכים ל-
   `[Audio N]: (unavailable — no STT provider connected)` (חוזה #8430). עבור
   יעד לא ידוע (`null`), תוצאה שבה כל הקריאות נכשלו נשארת ללא שינוי. יעד
   שהוכח כי הוא תומך בטקסט בלבד ושאין עבורו פרטי גישה שימושיים ל-STT מקבל את
   אותו ממלא מקום מפורש, ללא ביצוע קריאת רשת.

תמלולים מוצלחים משתמשים במטמון LRU/TTL הכלל-תהליכי של Modality Bridge. המפתח
משלב את הפניית השמע, את תווית הפעולה היציבה `audio-transcription`
ואת מודל ה-STT שנבחר; כשלים לעולם אינם נשמרים במטמון. ניסיונות שמע מעדכנים
את המונים המשותפים `bridged`,‏ `cacheHits`,‏ `failures` ו-`lastUsedAt`.
תגובות שעברו המרה כוללות
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; בקשות
שלא שונו אינן מקבלות מקטע Audio Bridge.

הגדרות זמן הריצה מגובות במסד הנתונים ומאומתות באמצעות Zod:

| מפתח                          | ברירת מחדל | טווח                |
| ----------------------------- | ---------- | ------------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                   |
| `modalityBridgeAudioModel`    | `""`       | אוטומטי או מזהה STT |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000         |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10                |

המטמון המשותף עדיין נשלט באמצעות `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes` ו-`modalityBridgeCacheMaxEntries`.

### גשר וידאו (`videoBridge.ts`, `videoBridgePipeline.ts`)

מיירט חלקי וידאו ברמה העליונה ב-`messages` של Chat Completions וב-`input` של
Responses API, לפני שמתבצעת קריאה ליעד שלא ידוע כי הוא תומך בווידאו באופן
מובנה. הצורות הנתמכות הן `input_video`,‏ `video_url`,‏ `video_source`, כתובות URL
מסוג HTTPS וכתובות URI לנתונים מסוג `data:video/*;base64,...`. שמות קבצים
רגילים בטקסט אינם מטופלים כווידאו.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) אחראי למעבר על הבקשה, לבדיקת
היכולת/המדיניות, לצבירה לפי בקשה ולמטען התגובה. העבודה עבור כל סרטון — השגה,
מטמון התוצאה המלאה, תיאור רצף פריימים (המשלב כל תמלול שמע שהוגדר על ידי הקורא)
ומדדים/ביטול/ניקוי עבור כל ניסיון — מוסתרת מאחורי `processVideoPart` בקובץ
`videoBridgePipeline.ts`, שנקראת פעם אחת לכל חלק וידאו בתוך הלולאה של `preCall`.
מודול זה מגדיר גם את גבולות היציאות המפורשים `VideoMediaBrokerPort`
(השגת בתים וחילוץ פריימים שנדגמו), `VideoAudioTranscriptionPort`
(שילוב תמלול שמע שהוגדר על ידי הקורא עם הכתוביות שנדגמו), וכן
`VideoDrilldownPort` (גבול השמירתיות של התעמקות בפריימים; הוא טרם חובר אל
`processVideoPart` — כיום רק הנתיב הנפרד `/api/modality-bridge/video/drilldown`
כותב רשומות התעמקות).

נתיב הבקשה הציבורי `/v1` לעולם אינו מייבא או מפעיל תהליך משנה. סרטונים מרוחקים
יורדים תחת מגבלה של 50 MiB; לסרטוני base64 מוטבעים יש מגבלה שמרנית של 36 MiB
מפוענחים לכל סרטון, כדי שמעטפת המודל/ההודעות/המסגור תוכל להישאר בתוך מגבלת
הקבלה של בקשות JSON ציבוריות, העומדת על 50 MiB. האורך המוטבע והערכות הגודל
המפוענח נבדקים לפני ההקצאה. HTTPS נדרש בכתובת ה-URL המרוחקת הראשונית ובכל
הפניה מחדש, באמצעות מנגנון ההגנה הקיים לתעבורה יוצאת ציבורית בלבד, עם הצמדת
DNS. לאחר מכן הבתים חוצים את גבול המתווך הפנימי המדויק
`POST /api/modality-bridge/video/extract`. נתיב זה הוא גם `LOCAL_ONLY` וגם
`SPAWN_CAPABLE`, מקבל רק בקשה מאומתת לכל תהליך מלולאת משוב מהימנה, ולעולם אינו
מקבל כתובת URL, נתיב במערכת הקבצים, קובץ הפעלה או רשימת ארגומנטים. צינור עיבוד
גודל הגוף של ה-API וקורא הגוף ההדרגתי של המטפל אוכפים באופן בלתי תלוי מגבלת
קלט של 50 MiB למתווך. התור המוגבל שלו מפעיל חילוץ אחד בכל פעם, מאפשר ארבע
משימות ממתינות ומגביל את הקלט הממתין ל-100 MiB.

בתוך המתווך, `ffprobe` קורא קובץ מקומי פרטי; רשימת הפורמטים הקבועה המותרת אינה
כוללת פורמטים של רשימות השמעה ומניפסטים. עבור מכלים מותרים ממשפחת MOV, הפניות
חיצוניות לנתוני MOV נותרות מושבתות כברירת מחדל, והפקודה הקבועה אינה מפעילה
אותן. הן `ffprobe` והן `ffmpeg` משתמשים ברשימה מורשית של פרוטוקול `file` בלבד,
בתהליכון אחד, במערכי ארגומנטים קבועים, ללא מעטפת, ובקובצי הפעלה שנפתרים מתוך
`PATH`. זרמי תמונת עטיפה מצורפת אינם מועמדים להפעלה. כל הזרמים הניתנים להפעלה
חייבים לעמוד במגבלות, וזרם ברירת מחדל מפורש מקבל עדיפות לפני ברירת המחדל
הדטרמיניסטית בעלת האינדקס הנמוך ביותר. סרטונים מוגבלים ל-600 שניות, ל-8,192
פיקסלים בכל ממד ול-33,554,432 פיקסלים במקור. FFmpeg דוגם 1–16 פריימים מסוג JPEG
בנקודות אמצע, מקטין את הצלע הארוכה ל-1,024 פיקסלים לכל היותר בלי להגדיל קלטים
קטנים יותר, ולעולם אינו מקבל כתובת URL. ברירת המחדל של הדגימה היא `uniform`.
המדיניות האופציונלית `scene_aware` והמדיניות הניסיונית `segment_aware` מבצעות
מעבר FFmpeg קבוע נוסף אחד על הזרם המקומי שכבר אומת, בוחרות חותמות זמן מוגבלות
של סצנות מ-`showinfo`, וחוזרות באופן דטרמיניסטי לאותן נקודות אמצע אחידות במקרה
של כשל בגלאי, חריגה מזמן ההמתנה, פלט פגום או קבוצת מועמדים ריקה. מצב מודע
למקטעים מקצה דגימות של נקודות אמצע באופן יחסי למרווחי הסצנות המאומתים; הראיות
והתנהגות הנסיגה במצב מודע למקטעים מפורטות להלן. המגבלה הקשיחה של 16 פריימים
מוחלת לאחר הבחירה בכל מדיניות. כאשר לבקשה מודעת לסצנות יש תקציב של פריים אחד
בלבד, היא משתמשת בנקודת האמצע האחידה של הסרטון המלא הפעיל או של חלון המיקוד,
ומדווחת `policyEffective: uniform`: פריים סצנה יחיד שנבחר אינו יכול לשמר את שני
הקצוות הזמניים. הקורא רשאי לספק חלון מיקוד סופי (`start`/`end` בשניות);
הגבולות מוצמדים למשך המדיה, חלונות הפוכים או לא-סופיים נדחים, וכל מדיניות
הדגימה מבוצעת רק בתוך המרווח המנורמל. החלון המתקבל נכלל במטא-נתונים של הדגימה
ובקידומת התיאור הלא-מהימנה, כדי שמודלים במורד הזרם יוכלו להבחין בין מקטע ממוקד
לבין ציר הזמן המלא.

מיקוד סמנטי של כתוביות הוא הגדרה נפרדת ומפורשת. מצב הניתוח `full`, שהוא ברירת
המחדל, משמר את הנחיית הפריימים הקיימת ולעולם אינו מעביר טקסט מהבקשה למודל
הכתוביות. במצב `focused`, הגשר קורא רק את ה-`text`/`input_text` האחרון שאינו
ריק ושנכתב על ידי המשתמש, מאותו מכל של Chat או Responses, מנרמל אותו ל-NFC,
מכווץ תווי בקרה ורווחים ומגביל אותו ל-500 נקודות קוד Unicode. תוצאה ריקה גורמת
לנסיגה להנחיית `full` המדויקת. רמז שמיש עובר סריאליזציה כ-JSON בבלוק ייעודי של
הקשר משתמש לא-מהימן, ורשאי רק לתעדף פרטים ניתנים לצפייה; הוא אינו יכול לעקוף
את האזהרה הנפרדת שלא לציית להוראות הנראות או נשמעות במדיה. מיקוד טקסטואלי לעולם
אינו מסיק `start`/`end` ואינו משנה את הדוגם הזמני.

#### ראיות מבניות למקטעים FU-07

`segment_aware` משתמש במעבר קדם-ניתוח תחום יחיד על זרם הווידאו המקומי שכבר אומת. שרשרת המסננים הקבועה מקטינה תחילה את הרוחב ל-320 פיקסלים לכל היותר, מזהה חילופי סצנות ומקטעים קפואים, ולאחר מכן דוגמת בקצב של פריים אחד לשנייה כדי למדוד טשטוש, בהיקות ממוצעת ומידע מרחבי/זמני. המעבר מוגבל ל-600 דגימות מבניות, לתהליכון FFmpeg/מסנן אחד, לאותן רשימות היתרים של פרוטוקול `file` בלבד ושל קונטיינרים, למגבלת פלט תהליך של 1 MiB, ולכל היותר 30 שניות במסגרת הביטול/המועד האחרון המשותפים של הברוקר. הוא לעולם אינו מקבל מהבקשה פקודה, מסנן, נתיב או URL.

הערכים המבניים הם ראיות דגימה דטרמיניסטיות, ולא הבנה סמנטית של הווידאו. הם אינם מסיקים נושאים, פעולות, כתוביות, דיבור או כוונת משתמש. גבולות של סצנות וקיפאון יוצרים מקטעים; כיסוי קיפאון, טשטוש, חשיפה, פירוט מרחבי ושינוי זמני משפיעים רק על אופן הקצאת התקציב הקיים של 1–16 פריימים. מקטע שקפוא במלואו מוגבל לפריים אחד, בעוד שמקטעים שאינם קפואים מתחרים על התקציב הנותר. כאשר מספר הגבולות גדול ממספר הפריימים, נשמר כיסוי אחיד של ציר הזמן, כך שחיתוכים מהירים בתחילת הסרטון אינם יכולים להסתיר מקטע ארוך בסופו. גבולות סצנה שנמצאים בטווח רזולוציית הניתוח של שנייה אחת מגבול קיפאון מאוחדים.

מסננים חסרים, ראיות פגומות/ריקות, שגיאת גלאי או חריגה ממגבלת הזמן של קדם-הניתוח התחום גורמים למעבר בטוח למדיניות נקודות האמצע האחידה המדויקת. ביטול מצד הקורא או הגעה למועד האחרון של הברוקר אינם גורמים למעבר בטוח: הם מסיימים את תת-התהליך הפעיל, מונעים חילוץ פריימים בהמשך, ועץ הקבצים הזמני הפרטי מוסר בתוך `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` יוצר תרחישי בדיקה דטרמיניסטיים באמצעות FFmpeg אמיתי עבור חיסכון בקריאות ליצירת כתוביות לאחר הסרת כפילויות, הקצאת תקציב לתנועה צפופה, ראיות טשטוש/חשיפה/SI-TI, חיתוכים מהירים עם מקטע סיום ארוך, ותוצאות חיוביות כוזבות של מעברי עמעום הדרגתיים. הוא מתעד את זמן הקיר של קדם-הניתוח, ובמקומות שבהם `/usr/bin/time` זמין, גם את זמן המעבד של תהליך הבן ואת שיא ה-RSS. בדיקות האיכות שלו הן אורקלים מבניים בלבד. איכות אמיתית של מודל הכתוביות נשארת במצב `HOLD`, משום שלרתמה זו אין נקודת קצה מורשית או שופט מוקפא. גם החיסכון הכספי נשאר במצב `HOLD`, אלא אם `--caption-cost-per-call-usd` מספק אומדן חיובי ומפורש של העלות לכל קריאה; הסקריפט לעולם אינו ממציא אף אחת מהתוצאות.

כל פריים מוגבל ל-4 MiB, כלל הפריימים הגולמיים מוגבלים יחד ל-23 MiB, ותגובת הברוקר לאחר סריאליזציה מוגבלת ל-32 MiB. ספרייה זמנית פרטית מוסרת בתוך `finally`. OmniRoute אינו כולל את FFmpeg בחבילה ואינו מקבל נתיב מותאם אישית לקובץ הרצה. לפני יצירת הכתוביות, הגשר מפעיל מעבר שמרני להסרת כפילויות חזותיות: כל JPEG מוקטן למאגר גווני אפור בגודל 16×16 ומושווה רק לפריים האחרון שנשמר. עבור תקציב כתוביות מבוקש הגדול מפריים אחד, החילוץ מספק מאגר מועמדים תחום בגודל של עד פי שניים מהתקציב, ולעולם לא יותר מ-16 פריימים. המכסה המבוקשת מוחלת רק לאחר הסרת הכפילויות, כאשר המועמד הראשון והאחרון שנבחרו נשמרים במהלך הדילול הסופי אם התקציב הוא שניים לפחות. המדיניות מבוססת-הגרסה
`grayscale-16x16-mean-cells-v2` משתמשת בערך הגדול מבין הפרש הבהיקות הממוצע לבין היחס של תאי התמונה הממוזערת שההפרש המנורמל שלהם הוא 0.05 לפחות. סף הכפילות הוא הקבוע 0.04, שנבחר לצורך יכולת חיזוי ולא נחשף כהגדרת זמן ריצה. האות המשני ורב-הניגודיות הזה משמר תנועה קטנה ושינויים בטקסט גלוי שהשוואה המבוססת על ממוצע בלבד עלולה להסתיר. שגיאות במשווה או במפענח גורמות למעבר בטוח ומשמרות את הכיסוי. מטא-נתוני הפלט מפרידים בין מועמדים שחולצו, פריימים שנעשה בהם שימוש בהצלחה וכפילויות חזותיות שהושמטו.

חלק וידאו שסומן במפורש יכול לבקש גיליון תמונות ממוזערות עם חותמות זמן. הגשר בונה רשת JPEG הכוללת לכל היותר 4 עמודות ו-16 פריימים. כל תא ברוחב 512 פיקסלים מטמיע את חותמת הזמן של המקור שלו בפס תחתון בעל ניגודיות גבוהה, ואותן חותמות זמן נשמרות גם במטא-נתונים טקסטואליים לצורך שיוך וביקורת בהמשך. קובץ ה-JPEG השלם נותר מוגבל ל-32 MiB. אם `sharp` אינו מצליח לפענח או להרכיב את הרשת, הגשר חוזר להשתמש בפריימי ה-JPEG הנפרדים; ביטול מצד הלקוח עדיין מועבר דרך פעולת הגיליון.

ראיות לקידום מופרדות בכוונה מהמיקרו-בנצ'מרק הסינתטי של ההרכבה. `scripts/perf/video-bridge-contact-sheet-eval.ts` מגדיר רתמת A/B מבוססת-גרסת-סכימה עבור מודלי ראייה אמיתיים התואמים ל-OpenAI. היא מודדת טוקנים שעליהם דיווח הספק, זמן השהיה מקצה לקצה לפי זמן קיר (כולל הרכבת הגיליון), מספר קריאות למודל ושימור עובדות המוגדר במניפסט. תגובות גולמיות של המודל אינן נכתבות לדוח; נשמרים רק תקצירי SHA-256 ומזהי העובדות שנמצאה להם התאמה. הרתמה אינה מבצעת קריאת רשת או קריאה למודל בתשלום, אלא אם מועבר `--execute-real` ומוגדרים `--model`, `OMNIROUTE_BASE_URL` ו-`OMNIROUTE_API_KEY`. ללא הרצה אמיתית ומפורשת זו, ההכרעה הקריאה-למכונה שלה נשארת `HOLD`; מדידות סינתטיות של מטען/מספר קריאות לבדן אינן מהוות ראיות לקידום.

קוראים יכולים לצרף מערך `transcript.cues` אופציונלי לחלק וידאו נתמך כאשר כבר יש ברשותם טקסט מיושר. כל רמז חייב להכיל `text`, מרווח `start`/`end` סופי הנמצא בתוך משך הזמן שנבדק, ו-`source` מתוך רשימת ההיתרים (`client`, `embedded` או `audio-bridge`); ברירת המחדל של `confidence` היא `1`, וערכו חייב להישאר בין `0` ל-`1`. רמזים כפולים זהים מצומצמים לאחד. OmniRoute לעולם אינו מתחיל תמלול על סמך מטא-נתונים אלה: רמזים מאומתים מועתקים אל התוצאה המתוארת יחד עם המקור, רמת הביטחון ומרווח הזמן, ומוצגים כתצפיות בלתי מהימנות לצד כתוביות הפריימים. טקסט לא תקין, מחוץ לטווח או ללא מקור מתועד נדחה במקום להיות מעורב בזרם הכתוביות. שני ערוצי התמלול בגוף הבקשה מנרמלים את המקור שסופק ל-`client`, כולל תוויות `embedded` או `audio-bridge` שהוצהרו עצמאית. רק מתאם בבעלות השרת יכול להקצות תוויות מהימנות אלה באמצעות הארגומנט הזמין-בקוד-בלבד `trustedSource`; שדה JSON בבקשה אינו יכול להגיע לארגומנט זה. טקסט התמלול נשאר תוכן בלתי מהימן שמקורו במדיה, ללא תלות במקורו המתועד, ולעולם אסור שישמש לקביעת הרשאה.

מתקשר מתקדם יכול לספק ערוץ `audioTranscript` עבור אותו סרטון;
הוא מטופל כטקסט שסופק על ידי הלקוח, ולא כהוכחה לתמלול בצד השרת.
נקודת האיחוד מריצה תצפיות חזותיות וקוליות תחת
מועד יעד ואות ביטול משותפים, מסדרת אותן על ציר זמן משותף, מאחדת
כפילויות זהות לחלוטין, ומדווחת על תוצאה חלקית כאשר רק צד אחד מצליח.
`audioTranscript` לא תקין מצטמצם לאותה תוצאה חלקית — התיאור החזותי
נשמר, וענף השמע מתעד קוד כשל מחוטא — במקום להכשיל את הסרטון כולו.
הזמינות של כל ענף, דגל התוצאה החלקית וקודי הכשל המחוטאים נשמרים בתוצאה
המתוארת, במטא-נתונים של מנגנון ההגנה (`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`), במטא-נתונים של מטמון התוצאות ובמוני האיחוד של
הגשר. נתיב ברירת המחדל של Video Bridge אינו מפעיל המרת דיבור לטקסט
ואינו מוריד עותק מדיה נוסף; ללא הערוץ המפורש הזה, הוא נשאר
מבוסס וידאו בלבד.

**שמירת תמלילים (#12150 P1).** הדבר חל אוטומטית בכל פעם שבה
Video Bridge (שהוא עצמו מצריך הפעלה מפורשת) מעבד רמז תמלול — אין דגל
שמירה נפרד. כאשר בקשה מעבדת רמז תמלול כלשהו (`transcript` שהוצהר
על ידי המתקשר או `audioTranscript` מאוחד), מנגנון ההגנה מסמן אותה כ-
`videoBridgeObserved` ומפיק עותק צל מושחר של תיאור הסרטון —
עיבוד זהה שבו גוף הטקסט החופשי של כל רמז מוחלף ב-
`[redacted-video-transcript]`, ונבנה באמצעות החלפת שדה הרמז המובנה
לפני הרכבת המחרוזת (לעולם לא באמצעות ניתוח הטקסט המשוטח, כך ששום תוכן
של רמז — זדוני או רגיל, לרבות גופים המכילים `]` כגון
`[inaudible]`/`[music]` — אינו יכול לשרוד). גוף הבקשה המתועד ביומן הקריאות
מחליף כל חלק טקסט שמקורו בסרטון באותו עותק צל מושחר, בהתאמה לפי שוויון
תוכן; העוגן `fullText` נקרא מחדש ממטען מנגנון ההגנה שהושלם לפני הקריאה,
כך שההתאמה עדיין מצליחה לאחר שמנגנוני הגנה מאוחרים יותר בשרשרת (מסכות
PII ופרטי הגישה, בעדיפויות 10/95) משכתבים את טקסט התיאור במקום,
ולאחר שהזרקת הנחיית המערכת/העברת ההקשר/הזיכרון מעצבת מחדש את מערך ההודעות.
הגוף שנשלח במעלה הזרם אל המודל אינו משתנה. בקשה שנצפתה גם אינה מאכלסת
זיכרון מתמשך כלשהו (החילוץ שמקורו בבקשה ובתגובה אינו מתבצע),
כך שהתשובה של המודל עצמו אינה יכולה להדהד טקסט מהתמליל אל הזיכרון.

**שדות וידאו גולמיים (#12430).** כאשר הגשר מופעל והתמיכה המקורית בווידאו אינה ידועה או אינה קיימת, גם שדות `transcript`/`audioTranscript` מוגדרים מפעילים את `videoBridgeObserved`, אפילו לאחר כשל בתיאור או מגבלת `maxVideos`. ערכי `null` ומחרוזות ריקות נחשבים; שדות חסרים ומטא-נתונים שאינם של וידאו אינם נחשבים. עותקים שנשמרים משחירים שדות אלה או משמיטים את הבקשה, והמטמונים/הזיכרון נעקפים.

בנתיבי נסיגה אלה, רמזים תקינים מהמתקשר הופכים לחלקי `text`/`input_text`
נתמכים במקום לשדות ספק שאינם תקניים. שני הערוצים שסופקו בבקשה
נשארים תצפיות `client` שאינן מהימנות, עם אזהרה מפורשת שהסרטון
לא תואר ושחותמות הזמן לא אומתו מול המדיה. המגבלות הקיימות של
256 רמזים/64 KiB בסך הכול ולכל רמז חלות על שני הערוצים יחד;
חותמות הזמן חייבות לעמוד בתקרה של 600 שניות של המתווך ובכל חלון מיקוד
שסופק. ערוצים לא תקינים נזרקים ואינם מועברים כטקסט שרירותי; עדיין ניתן
להשתמש בערוץ אח תקין, אלא אם חורגים מהמגבלה המשולבת שלהם. שדות ריקים/
`null` אינם מוסיפים טקסט. נסיגה זו אינה מוסיפה אחזור מדיה או תמלול.
שדות הרחבת התמליל מוסרים ממכל הווידאו של הנסיגה ומהאובייקטים
`video_url`/`source` שלו. רשימת ההרשאות לתעבורה של OpenAI נשארת מחמירה;
מכלי וידאו שהתמיכה המקורית בהם אינה ידועה נשארים זמינים, ויעדים ידועים
התומכים בטקסט בלבד שומרים על סמנים בטוחים. עותקי צל מובנים ומושחרים מגנים
על טקסט התמליל שנוסף, בעוד שהבקשה המקורית שבבעלות המתקשר נשארת ללא שינוי.
יעדים עם תמיכה מקורית וגשרים מושבתים שומרים על התנהגות העקיפה הקיימת שלהם.

עותקים שמורים נוספים משתמשים באותו אות של בקשה שנצפתה. תמונת המצב
הגולמית של בקשת הלקוח מלפני מנגנון ההגנה, הבקשה הממתינה בזיכרון ויומן
הבקשות שנדחו בשלב מוקדם מחליפים באופן מובנה שדות תמליל בחלקי וידאו;
הנחיות מחרוזת שנוצרו על ידי שלבי צינור העיבוד והעברת ההקשר מושחרות
בנקודת הקליטה של גוף הבקשה הנשמר. הסמן השמור `video_content_removed`
גורם להמשך באמצעות `previous_response_id` להיכשל באופן סגור במקום לשחזר
טקסט שהושלך במכוון. אם בקשה שנצפתה מאבדת את עותק הצל המושחר שלה לכל חלק
לפני התיעוד, או אם אפילו אחד מבין כמה עותקי צל של וידאו אינו מתאים לאחר
שינויים מאוחרים יותר בבקשה, גוף הבקשה הנשמר מושמט לחלוטין במקום לשמור
תמליל שהושחר חלקית.

עבור בקשה שנצפתה, תגובת המודל עשויה לצטט כל חלק מהתמליל ללא גבול מובנה
של רמז. לכן `responseBody` הנשמר ביומן הקריאות מוחלף בסמן השמטה;
פריט צינור העיבוד המפורט (שעשוי לכלול גופי בקשה/תגובה במעלה הזרם או של
הלקוח ומקטעי זרם) אינו נשמר. מטמוני סמנטיקה, אידמפוטנטיות ושחזור הנמקה
עוקפים קריאות וכתיבות עבור בקשה זו. בקשת הספק והתגובה הגלויה ללקוח
נשארות ללא שינוי. בתים מוקדמים של keepalive מנוקזים מהמאגר הזמני כאשר
הפריט המפורט מושמט. האזהרה של Kiro לגבי EventStream פגום מדווחת רק על
מספר הבתים במטען, ולעולם לא על תוכנו או על השגיאה הגולמית של מנתח JSON.
אין בכך טענה שכל אבחון בלתי קשור של ספק/תוסף עבר ביקורת;
הסריקה הרחבה יותר של נקודות קליטה שומרות מתועדת ב-#11658.

מחזור החיים הפנימי של `/api/modality-bridge/video/drilldown` הוא תשתית מטמון נפרדת, המאומתת באמצעות loopback/אסימון. כל פעולה דורשת גם מזהה עיקרון אטום וקנוני. לפני שמפעילים קורא בסביבת ייצור, עליו לגזור מזהה זה מהדייר המאומת, ולעולם אסור לו להעביר ערך שנבחר בידי הלקוח. מפתחות המטמון קושרים עיקרון זה למזהי הפעלה והפניית-וידאו קנוניים, מאחסנים רק את המפתחות שלהם שנגזרו באמצעות SHA-256, ומגבילים הן את הקריאות והן את המחיקה לאותו עיקרון. המטמון מאחסן לכל היותר 16 פריימי JPEG נגזרים בכל רשומה, מפוגג אותם לאחר עשר דקות ותומך בקריאות `start`/`end` תחומות או במחיקה מפורשת של הפעלה.

כל עיקרון מוגבל ל-16 רשומות ול-64 MiB של נתוני JPEG קנוניים. מגבלות אלה בלתי תלויות בתקרה הגלובלית של 64 רשומות/256 MiB: לחץ על מכסת עיקרון מפנה תחילה רק את הרשומות של אותו עיקרון לפי מדיניות השימוש האחרון המוקדם ביותר, לפני שנשקל פינוי LRU גלובלי. רשומות שפג תוקפן מנוקות הן מהחישוב החשבונאי של העיקרון והן מזה הגלובלי בעת פעילות במטמון, בעוד שביטול וכשל אימות אינם מבצעים החלפה חלקית.

המטמון דוחה Base64 שאינו קנוני, ריפוד עודף, מדיה שאינה JPEG, קובצי JPEG פגומים או קטועים וקובצי JPEG שמפיקים אזהרה במהלך פענוח תמונה מלאה ותחום באמצעות `sharp`. הוא מקודד מחדש כל תמונה שהתקבלה כ-JPEG קנוני, גוזר את הרוחב והגובה מהבתים המפוענחים במקום לתת אמון בשדות שסופקו בידי הקורא, ומשליך בתים פוליגלוטיים עודפים במקום לשמרם. רק המאגר הדחוס, התחום והקנוני מחויב בשתי המכסות. מגבלת התעבורה בתבנית JSON כוללת את התקורה של Base64 עבור תקרת הקלט המפוענח של 32 MiB. כל נגזרת מאוחסנת מתעדת את פורמט ה-JPEG והרזולוציה שאומתו, מדיניות הדגימה, גרסת הגזירה, זמן היצירה, גיבוב תוכן שחושב בשרת והפניית האב המגובבת, יחד עם גיבוב תוכן האב של הקורא המהימן. הביטול נבדק בין שלבי הפענוח והגיבוב האסינכרוניים, לפני השמירה האטומית במטמון.

מקבץ עבודה זה עדיין אינו מחבר מפיק בסביבת ייצור לנתיב ואינו מספק בחירת וריאנט מרובה-רזולוציות. לפיכך, נתיב הבקשה השקוף של Video Bridge אינו כרוך בעבודה נוספת, בעוד שגזירת עיקרון הקשור לדייר ומחזור החיים המלא של FU-08 מרובה-הרזולוציות נשארים במפורש כעבודת המשך, במקום להיות מתועדים כהתנהגות שהושלמה.

לפריימים נוצרות כתוביות בזו אחר זו באמצעות מודל ה-Video שהוגדר. דריסת Video ריקה יורשת את הגדרת Vision; אם שתיהן ריקות, הנתב האוטומטי של Vision בוחר את המודל האפקטיבי התומך בראייה. כתוביות שהופקו בהצלחה מחליפות את החלק המקורי בקידומת היציבה `[Video description:`, שגם מסמנת את הטקסט כתצפית בלתי מהימנה שנגזרה ממדיה ומורה למודלים בהמשך השרשרת שלא לפעול לפי הוראות שנמצאו במדיה. מפתחות מטמון הכתוביות לפריימים כוללים את בתי ה-JPEG, ההנחיה, חותמת הזמן והמודל האפקטיבי; רק כתוביות שהופקו בהצלחה נשמרות במטמון. רשומות המטמון שומרות את מודל המפיק שהצליח בפועל, לרבות מודל חלופי; הגשר מדווח `mixed` כאשר פריימים שונים הופקו בידי מודלים שונים. פגיעה במטמון עושה שימוש חוזר בזהות מפיק זו במקום לתייג אותה מחדש כתוכנית הניתוב שהתבקשה. מטמון התוצאה של הסרטון השלם ממופתֵח לפי כל קלט שמשנה את הפלט — ההנחיה, המודל האפקטיבי, מדיניות הדגימה, מספר הפריימים, מצב הניתוח הסמנטי, טביעת האצבע מסוג SHA-256 של רמז המיקוד המנורמל, חלון המיקוד, `transcript`,‏ `audioTranscript` ודגל גיליון-התמונות — כך ששינוי של כל אחד מהממדים האלה גורם להחטאת מטמון ולעולם לא לשימוש חוזר בתוצאה מיושנת. גם גרסת מדיניות הסרת הכפילויות החזותית, הסף ומספר הפריימים המועמדים התחום מפורטים במפורש במפתח ובמטא-נתונים של מטמון התוצאה; לכן שינוי מדיניות אינו יכול לעשות שימוש חוזר בתיאור מיושן של הסרטון השלם. מטא-הנתונים של מטמון התוצאה בגרסה v4 שומרים את המצב ואת טביעת האצבע, ולעולם לא את משימת המשתמש הגולמית. מטא-הנתונים של מנגנון ההגנה מדווחים הן על מצב הניתוח שהתבקש והן על המצב האפקטיבי; מצב `focused` שהתבקש ללא טקסט משתמש שמיש מדווח כאילו הוא למעשה `full`.

מנגנון ההגנה מחלץ כל חלק וידאו נתמך, אך מתאר לא יותר מ-`modalityBridgeVideoMaxVideos`. עבור יעד שהוכח כי `supportsVideo === false`, סרטונים שנכשלו וסרטונים שמעבר למגבלה הופכים לסמני טקסט בטוחים ומפורשים, כך ששום וידאו גולמי אינו נותר. כאשר היכולת אינה ידועה, חלקים אלה משמרים את מעטפת הווידאו שלהם; כל תמליל חלופי כפוף להמרת הטקסט התחומה שלעיל. יעדים שבהם `supportsVideo === true` עוקפים את הגשר. אות הביטול של בקשת הלקוח מתפשט דרך ההורדה, תור הברוקר, תהליכי המשנה וקריאות הפקת הכתוביות; ביטולים עוצרים בין סרטונים ולעולם אינם נכשלים באופן שמאפשר למדיה גולמית לעבור.

הגדרות זמן הריצה מגובות במסד נתונים ומאומתות באמצעות Zod:

| מפתח                                | ברירת מחדל  | טווח / התנהגות                                                                        |
| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | זמן ריצה אופציונלי, מופעל לפי בחירה                                                   |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` משמר כתוביות כלליות; `focused` משתמש בהקשר מוגבל ולא מהימן של המשתמש האחרון    |
| `modalityBridgeVideoModel`          | `""`        | יורש את המודל של Vision Bridge                                                        |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                  |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`,‏ `scene_aware`, או `segment_aware` יחסי; כשל בגלאי מוביל לחזרה ל-`uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                   |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 מילישניות                                                                 |

ערכי זמן קצוב ישנים של Video שנשמרו ושעולים על 120 שניות מוגבלים למועד הסופי של
המתווך; ניסיונות חדשים לכתוב הגדרות מעל מגבלה זו נדחים.
`GET /api/modality-bridge/video/runtime` דורש מקומיות loopback חתומה ומהימנה
לפני אימות או בדיקת זמן הריצה, ולאחר מכן דורש אימות ניהול.
הוא מחזיר רק את `available`, גרסאות FFmpeg/ffprobe שעברו טיהור וסיבה קבועה
כאשר זמן הריצה אינו זמין. נקודת הקצה הפנימית לחילוץ אינה
API ציבורי להעלאות: רוויה של התור מחזירה `503` יחד עם `Retry-After`, ניתוק של מבצע
הקריאה מחזיר `499`, והמועד הסופי הקבוע של המתווך מחזיר `504`. תגובות שהומרו מוסיפות
`video->text;model=<visionModel>;parts=<videos>` לכותרת המרכזית
`x-omniroute-modality-bridge` מבלי להסיר מקטעי Vision או Audio.

### ממסך PII (`piiMasker.ts`)

פועל **בשני** השלבים.

- **`preCall`** משכפל את המטען, עובר על `system`,‏ `messages`,‏ `input` ו-
  `prompt` (כולל פריטי מחרוזת פשוטים), ומחיל את `processPII()` (מתוך
  `@/shared/utils/inputSanitizer`) על שדות המחרוזת `content`/`text`. כאשר
  `PII_REDACTION_ENABLED=true`, פרטי PII שזוהו מושחרים במטען היוצא.
  פעולה זו אינה תלויה ב-`INPUT_SANITIZER_MODE` (ששולט רק במדיניות
  הזרקת הנחיות). כאשר ההשחרה כבויה, הקריאה מתעדת את מספר הזיהויים
  מבלי לשכתב את התוכן.
- **`postCall`** מבצע שכפול עמוק של התגובה, מריץ את `sanitizePIIResponse()` וכן
  את הממסך למבנה של Responses API (`maskResponsesOutput` — מכסה את
  `output_text` ואת `output[].content[].text`). אם מתבצעת השחרה כלשהי,
  התגובה ששונתה מחליפה את המקורית.

מנגנון ההגנה לעולם אינו חוסם; הוא רק מוסיף הערות (`meta.detections`,
`meta.redacted`) או משכתב.

### הזרקת הנחיות (`promptInjection.ts`)

מזהה מבנים עוינים בתוכן שסופק על ידי המשתמש ואוכף את
המדיניות שהוגדרה. ההתנהגות נקבעת באמצעות משתני סביבה ואפשרויות
הבנאי:

| הגדרה    | משתנה סביבה                                                                                             | ברירת מחדל | השפעה                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| מופעל    | `INPUT_SANITIZER_ENABLED`                                                                               | `true`     | כאשר הערך הוא `false`, מנגנון ההגנה מסיים מיד.                                                                                                                    |
| מצב      | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                         | `warn`     | מדיניות הזרקה: `block`,‏ `warn` או `log`. (`redact` מתקבל לצורך תאימות לאחור, אך **אינו** מסיר טקסט מוזרק; שכתוב PII בבקשה נשלט באמצעות `PII_REDACTION_ENABLED`.) |
| סף חסימה | האפשרות `blockThreshold` /‏ `INPUT_SANITIZER_BLOCK_THRESHOLD` (כינוי `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`     | דרגת החומרה המזערית הנדרשת לחסימה. ברמת ברירת המחדל, חומרה בינונית מיועדת לתצפית בלבד.                                                                            |

**סדר קדימות המצבים** (`getMode`):‏ `options.mode` של מבצע הקריאה →
עקיפת דגל התכונה של `INJECTION_GUARD_MODE` **במסד הנתונים** (Dashboard → Settings →
Feature Flags) → משתנה הסביבה `INJECTION_GUARD_MODE` → משתנה הסביבה `INPUT_SANITIZER_MODE` →
`warn`. לפיכך, עקיפה מלוח הבקרה גוברת על משתני הסביבה, כך שממשק המשתמש של Feature
Flags שולט במנגנון ההגנה הפעיל בזמן אמת (ללא הפעלה מחדש). הקריאה ממסד הנתונים בטוחה במקרה של כשל:
אם מתרחשת שגיאה, מנגנון ההגנה חוזר להתנהגות המבוססת על משתני הסביבה, וכאשר לא
מוגדרת עקיפה, ההתנהגות זהה לחלוטין לזו של פתרון המבוסס על משתני סביבה בלבד.

מקורות הזיהוי:

1. `sanitizeRequest()` מתוך `@/shared/utils/inputSanitizer` (ערכת גלאים משותפת
   המשמשת במקומות נוספים בצינור העיבוד).
2. `DEFAULT_GUARD_PATTERNS` המובנים (נכון לעכשיו `system_override_inline` ו-
   `markdown_system_block`, שניהם בדרגת חומרה `high`).
3. `customPatterns` אופציונליים שמועברים באמצעות אפשרויות הבנאי (מחרוזות, ביטויים רגולריים
   או רשומות `{ name, pattern, severity }`).

כאשר `mode === "block"` **וגם** לפחות זיהוי אחד עומד בסף החומרה,
`preCall` מחזירה `{ block: true, message: "Request rejected:
suspicious content detected" }`. במצבי `warn`/`log`, מנגנון ההגנה מתעד ביומן אך
מאפשר את הקריאה. פונקציית העזר המשותפת `evaluatePromptInjection()` מיוצאת גם היא
עבור צרכנים שצריכים להעריך הנחיות מבלי לעבור דרך ה-registry.

**מגבלת סריקה (v3.8.20):** הגלאי בוחן רק את **16 ה-KB הראשונים** של
טקסט ההנחיות המשורשר — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16,384 בתים) בקובץ
`src/shared/utils/inputSanitizer.ts`. הן `detectInjection()` והן
`evaluatePromptInjection()` מבצעות `slice(0, MAX_INJECTION_SCAN_BYTES)` לפני הרצת
לולאת התבניות. הוראות הזרקה ממוקמות בסמוך לתחילת הקלט, ולכן הגבלה זו מצמצמת את
צריכת המעבד/GC של ביטויים רגולריים במטענים בגודל מאות KB, מבלי להחליש את הזיהוי (ראו
#3932, #4041).

### מסווה פרטי כניסה (`credentialMasker.ts`)

פועל בשני השלבים, אחרון בשרשרת ברירת המחדל (עדיפות `95`). הוא משחיר
תבניות מוכרות של מפתחות API / אסימונים סודיים במטען היוצא (תוכן הודעות,
ארגומנטים של קריאות לכלים, תוצאות כלים) **וגם** בתגובת הספק, כך שפרטי כניסה
שהודבקו בהנחיה (או הוחזרו בתוצאה של כלי) לא ידלפו לספק שבמעלה הזרם או בחזרה
ללקוח.

- **הצטרפות מפורשת בלבד**, בהתאם לאותה מוסכמה של השחרת PII (בסמוך לכלל קשיח #20):
  מושבת אלא אם `settings.credentialRedactionEnabled === true` **או**
  `CREDENTIAL_REDACTION_ENABLED=true`. כאשר האפשרות כבויה, מנגנון ההגנה אינו עושה דבר —
  הוא לעולם אינו חוסם ולעולם אינו משכתב.
- `redactCredentials()` עוברת על כל עץ המטען/התגובה (`walkValue()`,
  בטוחה מפני זיהום אב-טיפוס ובטוחה מפני מחזורים באמצעות `WeakSet`) ומחליפה התאמות
  במציין מיקום מסוג `[REDACTED:<type>]`, תוך שכפול רק של הענפים שהשתנו בפועל.
- `CREDENTIAL_PATTERNS` מכסה מפתחות של ספקי LLM‏ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), אסימוני VCS/SaaS‏ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), מפתחות תשלום (Stripe, Square), מפתחות
  ענן (מפתח גישה של AWS,‏ Twilio,‏ SendGrid,‏ Mailgun), מפתחות פרטיים / JWT,
  מחרוזות חיבור המכילות פרטי כניסה (`mongodb://user:pass@...` וכו'), וכן
  תבנית כללית לערכי כותרות `Authorization`/`x-api-key`/`api-key`/`apikey`.
  מפתחות בצורת כותרת (`authorization`, `x-api-key`, `api-key`,
  `apikey`) מושחרים באופן מבני (הערך בלבד, תוך שמירת קידומת הסכמה כגון
  `Bearer `/`Basic `), במקום באמצעות הביטוי הרגולרי הכללי לטקסט.
- מנגנון ההגנה לעולם אינו חוסם; הוא רק משכתב (`modifiedPayload` /
  `modifiedResponse`) ומוסיף הערות (`meta.credentialsRedacted`, `meta.count`).

הגנת רגרסיה: `tests/unit/credential-masker-guardrail.test.ts`.

## חוזה בסיס (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true עוצר מיד את השרשרת
  message?: string; // מוצג בעת חסימה
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // מוחזר על ידי preCall כדי לשכתב את הבקשה
  modifiedResponse?: TValue; // מוחזר על ידי postCall כדי לשכתב את התגובה
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

מנגנון הגנה מסמן "ללא שינוי" באמצעות החזרת `void`, `{}`, או
`{ block: false }`. החזרת `modifiedPayload`/`modifiedResponse` מחליפה
את הערך שזורם בשרשרת עבור מנגנוני ההגנה שבהמשך.
`signal?: AbortSignal` מעביר אל מנגנוני ההגנה את מחזור החיים של הקורא. ביטול בקשה הוא החרגת fail-open מכוונת: גשרי מדיה מפסיקים את העבודה ומבצעים ניקוי מבלי לשחזר מדיה גולמית ליעד שידוע כי אינו תומך בה.

## מרשם (`registry.ts`)

היחידון `guardrailRegistry` חושף:

- `register(guardrail)` — מוסיף מנגנון הגנה (או מחליף לפי שם מנורמל) וממיין
  מחדש לפי `priority` בסדר עולה.
- `clear()` / `list()` — כלי עזר ניהוליים.
- `runPreCallHooks(payload, context)` — עובר על מנגנוני ההגנה הפעילים, מעביר את
  המטען דרך `modifiedPayload`, ועוצר ב-`block: true` הראשון.
- `runPostCallHooks(response, context)` — אותה זרימה בצד התגובה.
- `resetGuardrailsForTests({ registerDefaults })` — מנקה את המצב, ולפי הצורך
  רושם מחדש את ברירות המחדל לצורך בידוד נקי של בדיקות.

שני המריצים מחזירים `{ blocked, payload|response, results, guardrail?, message? }`
כאשר `results` הוא מערך של רשומות `GuardrailExecutionResult` הכוללות
את השדות `blocked`, `skipped`, `modified`, `error` ו-`meta` לכל מנגנון הגנה,
ושימושיות למעקב.

### השבתת מנגנוני הגנה לכל בקשה

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` אוסף רשימה
ללא כפילויות של שמות מנגנוני הגנה שיש לדלג עליהם עבור הבקשה הנוכחית.
המקורות (כולם אופציונליים וכולם ממוזגים):

- `apiKeyInfo.disabledGuardrails`
- `disabledGuardrails` בגוף הבקשה (ברמה העליונה)
- `metadata.disabledGuardrails` בגוף הבקשה
- הכותרת `x-omniroute-disabled-guardrails` (או הכותרת הישנה
  `x-disabled-guardrails`)

הערכים יכולים להיות מערכי מחרוזות או מחרוזת מופרדת בפסיקים; השמות
מנורמלים ל-kebab-case באותיות קטנות (`pii_masker` → `pii-masker`). התוצאה
מועברת דרך `context.disabledGuardrails` אל המרשם, שמדלג על
מנגנוני הגנה תואמים (`skipped: true` בתוך `results`).

## סדר הביצוע

עבור כל בקשה שעוברת דרך `src/sse/handlers/chat.ts` ודרך
`open-sse/handlers/chatCore.ts`:

1. `resolveDisabledGuardrails(...)` בונה את רשימת הדילוג ממפתח ה-API, מגוף הבקשה
   ומהכותרות.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` מפעיל את מנגנוני ההגנה לפי סדר
   עדיפויות עולה:
   - מנגנוני הגנה מושבתים מתועדים כ-`skipped`.
   - ה-`preCall` של כל מנגנון הגנה עשוי לשכתב את המטען באמצעות `modifiedPayload`.
   - המופע הראשון של `block: true` עוצר את השרשרת, וה-handler מחזיר
     תגובת דחייה של מנגנון ההגנה.
3. המטען (שייתכן ששוכתב) מועבר לניתוב משולב ולשליחה לשירות שבמעלה הזרם.
4. לאחר הרכבת התגובה, `guardrailRegistry.runPostCallHooks(...)`
   מפעיל את אותה שרשרת על התגובה. `block: true` בשלב זה מבטל את התגובה
   משירות מעלה הזרם.

מנגנוני הגנה שזורקים חריגה מתועדים עם `error: <message>` ונרשמים ביומן באמצעות
`logger.warn`, אך השרשרת ממשיכה — זהו תכנון מסוג fail-open.

## תצורה

משתני סביבה שנקראים על ידי מנגנוני ההגנה המובנים:

| משתנה                                 | בשימוש על ידי             | השפעה                                                                                    |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | יש להגדיר `false` כדי להשבית לחלוטין את הזיהוי.                                          |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | מדיניות הזרקה: `warn`,‏ `block` או `log`. הערך הישן `redact` אינו משכתב טקסט של הזרקה.   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | מצב מגן ההזרקה; משמש גם כדגל תכונה במסד הנתונים אשר **דורס** את משתני הסביבה (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | רמת החומרה המזערית שאותה `MODE=block` דוחה: `high` (ברירת המחדל), `medium` או `low`.     |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | כינוי ישן עבור `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | כאשר הערך הוא `true`, מידע אישי מזהה בבקשה מושחר (ללא תלות במצב ההזרקה).                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (במורד הזרם) | שולט בהתנהגות המיסוך בצד התגובה.                                                         |

`modalityBridgeVisionEnabled`,‏ `modalityBridgeVisionMode`,

`modalityBridgeVisionMaxImages`,‏ `modalityBridgeVisionMaxChars`,

כתיבות מלוח הבקרה משתמשות במפתחות הראשיים. ברירות המחדל ופותר מנגנון הגיבוי
נמצאים ב-`src/shared/constants/modalityBridgeDefaults.ts`, בעוד שהקבועים הישנים

## מנגנוני הגנה מותאמים אישית

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

שלבים:

1. צרו את `src/lib/guardrails/myGuardrail.ts` כך שירחיב את `BaseGuardrail`.
2. ממשו את `preCall` ו/או את `postCall`.
3. בצעו רישום בזמן הייבוא (הוספה מתוך `registerDefaultGuardrails`) או
   קראו ל-`guardrailRegistry.register(...)` בזמן ריצה — הרישום מחליף
   כל מנגנון הגנה קודם בעל אותו שם מנורמל.
4. הוסיפו בדיקות תחת `tests/unit/` (דוגמאות קיימות:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## בדיקות

השתמשו ב-`resetGuardrailsForTests()` בין הבדיקות כדי להתחיל ממצב ידוע.
העבירו `{ registerDefaults: false }` כדי להתחיל עם רישום ריק ולרשום
רק את מנגנוני ההגנה הנבדקים. Vision Bridge תומך בהזרקת תלויות

לכן הבדיקות יכולות להפעיל את שני התהליכים ללא גישה למסד נתונים
או לרשת.

## כיסוי נתיבים ובדיקות צוות אדום למנגנון ההגנה מפני הזרקה (שלב 8 · בלוק D)

מנגנון ההגנה מפני הזרקה (`createInjectionGuard` / `withInjectionGuard`) מכסה את כל הנתיבים
שמקבלים הנחיות משתמש. הוא מכבד את `INJECTION_GUARD_MODE` (ברירת המחדל `warn` = רישום בלבד;
`block` = החזרת HTTP 400 עם `SECURITY_001`).

| סוג         | נתיבים                                                                                                                                               | מצב ברירת מחדל |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| טקסט (קיים) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| יצירתי      | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| נתונים      | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

חילוץ טקסט (`extractMessageContents`) מכסה את `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**צוות אדום (מדי לילה, `nightly-llm-security.yml`):** ‏promptfoo מאמת שכל נתיב חוסם
את קורפוס OWASP-LLM כאשר `INJECTION_GUARD_MODE=block`; ‏garak מריץ בדיקות חדירה (ומדלג ללא סוד).
`moderations` נכלל למען העקביות — מפעילים במצב חסימה יכולים להחריג אותו באמצעות
`resolveDisabledGuardrails`.

תהליך העבודה הלילי (`.github/workflows/nightly-llm-security.yml`, ‏cron + הפעלה ידנית)
כולל שתי משימות:

- **`promptfoo-guard` (חוסמת)** — מריצה את `promptfoo eval -c promptfooconfig.yaml`
  עם `INJECTION_GUARD_MODE=block`. כל מקרה עוין (למשל "התעלם מכל
  ההוראות הקודמות…", פריצות בסגנון DAN) מוודא שהתשובה מכילה
  `error.code === "SECURITY_001"`, כלומר שמנגנון ההגנה אכן דחה את הבקשה.
- **`garak` (מייעצת)** — מריצה את garak עם `--probes promptinject,dan,leakreplay`
  מול מופע OmniRoute מקומי (`http://localhost:20128/v1`). ההרצה מותנית בסוד
  של ספק (`PROMPTFOO_PROVIDER_KEY`); היא מדלגת בצורה תקינה בהיעדרו ומסתיימת בסיומת
  `|| true`, כך שהיא מדווחת מבלי להכשיל את CI.

הכיסוי של פונקציית העזר של מנגנון ההגנה (`createInjectionGuard` / `withInjectionGuard`)
משתרע על כל נתיב `/v1` שמכיל הנחיה; טקסט ההנחיה נשלף מתוך
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` באמצעות
`extractMessageContents()` שב-`src/shared/utils/inputSanitizer.ts`.
