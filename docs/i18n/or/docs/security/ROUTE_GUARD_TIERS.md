## ସାରାଂଶ

ସମସ୍ତ OmniRoute ପରିଚାଳନା API ରୁଟ୍କୁ ତିନୋଟି ସୁରକ୍ଷା
ସ୍ତର ମଧ୍ୟରୁ ଗୋଟିଏରେ ବର୍ଗୀକୃତ କରାଯାଇଛି। ବର୍ଗୀକରଣ ସ୍ଥିର, ଯାହା `src/server/authz/routeGuard.ts`ରେ
ପରିଭାଷିତ ହୋଇଛି, ଏବଂ ଅନ୍ୟ କୌଣସି ପ୍ରମାଣୀକରଣ ଶାଖା ଚାଲିବା ପୂର୍ବରୁ ଏହାର ମୂଲ୍ୟାଙ୍କନ କରାଯାଏ।

## ସ୍ତରଗୁଡ଼ିକ

### ସ୍ତର 1 — LOCAL_ONLY

**ପ୍ରୟୋଗ କରାଯାଏ:** `isLocalOnlyPath(path)` → ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ
**ବାଇପାସ୍:** ଡିଫଲ୍ଟ ଭାବେ କିଛି ନାହିଁ। ଅନୁରୋଧରେ `manage` ସ୍କୋପ୍ ସହିତ ଏକ ବୈଧ
API କୀ ଥିଲେ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ଅନ୍ତର୍ଗତ ପଥଗୁଡ଼ିକ ପାଇଁ
ସୀମିତ ବ୍ୟତିକ୍ରମ ରହିଛି ([Manage-scope ବ୍ୟତିକ୍ରମ](#manage-scope-carve-out) ଦେଖନ୍ତୁ)।

ଏହି ରୁଟ୍ଗୁଡ଼ିକ ଚାଇଲ୍ଡ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି କରନ୍ତି କିମ୍ବା ରନ୍ଟାଇମ୍ କୋଡ୍ ନିଷ୍ପାଦନ କରନ୍ତି। ସେଗୁଡ଼ିକୁ
ନନ୍-ଲୁପ୍ବ୍ୟାକ୍ ଟ୍ରାଫିକ୍ ପାଇଁ ଉନ୍ମୁକ୍ତ କଲେ, ଏକ ବୈଧ JWT ପାଇଥିବା ଆକ୍ରମଣକାରୀ (ଉଦାହରଣ ସ୍ୱରୂପ,
ଏକ Cloudflared/Ngrok ଟନେଲ୍ ମାଧ୍ୟମରେ) ପ୍ରୋସେସ୍ ସୃଷ୍ଟିକୁ ଟ୍ରିଗର୍ କରିପାରିବ — ଏହା ଏକ ଜଣାଶୁଣା CVE
ଶ୍ରେଣୀ ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj))।

**GHSA-fhh6-4qxv-rpqj କ’ଣ (ଆକ୍ରମଣ ଶ୍ରେଣୀ):** ଏକ ପରିଚାଳନା/ଏଜେଣ୍ଟ ସର୍ଭର୍
ଏପରି ଏକ ଏଣ୍ଡପଏଣ୍ଟ ଉନ୍ମୁକ୍ତ କରେ, ଯାହା ଏକ ସବ୍ପ୍ରୋସେସ୍ (`npm install`, `node`, ଏକ ବ୍ରାଉଜର୍,
ଏକ ପ୍ରକ୍ସି, `git`, `tar`, …) ଆରମ୍ଭ କରେ। ଯଦି ସେହି ଏଣ୍ଡପଏଣ୍ଟକୁ ହୋଷ୍ଟ ବାହାରୁ ପହଞ୍ଚିହୁଏ — କାରଣ
ଅପରେଟର୍ OmniRouteକୁ ଏକ nginx/Cloudflare/Tailscale ଟନେଲ୍ ପଛରେ ରଖିଥିଲେ ଏବଂ ଏକ JWT
ଲିକ୍ ହୋଇଥିଲା, କିମ୍ବା ପ୍ରମାଣୀକରଣ ଭୁଲ୍ ଭାବେ ବିନ୍ୟାସ ହୋଇଥିଲା — ତେବେ ଆକ୍ରମଣକାରୀ "ଏକ APIକୁ କଲ୍ କରିବା"କୁ "ହୋଷ୍ଟରେ ଏକ
କମାଣ୍ଡ ଚଲାଇବା"ରେ ପରିଣତ କରେ (ରିମୋଟ୍ କୋଡ୍ ନିଷ୍ପାଦନ)। ପ୍ରତ୍ୟେକ
ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ରୁଟ୍ରେ **କୌଣସି ପ୍ରମାଣୀକରଣ ଯାଞ୍ଚ ପୂର୍ବରୁ, ବିନା ସର୍ତ୍ତରେ ଏକ ଲୁପ୍ବ୍ୟାକ୍ ହୋଷ୍ଟ ଯାଞ୍ଚ** ପ୍ରୟୋଗ କରି OmniRoute ଏହାକୁ ବନ୍ଦ କରେ:
ଏକ ଟନେଲ୍ ମାଧ୍ୟମରେ ଲିକ୍ ହୋଇଥିବା ଟୋକନ୍ ମଧ୍ୟ ପ୍ରୋସେସ୍ ସୃଷ୍ଟି ପର୍ଯ୍ୟନ୍ତ ପହଞ୍ଚିପାରିବ ନାହିଁ।

**ସମ୍ପୂର୍ଣ୍ଣ LOCAL_ONLY ସେଟ୍।** ପ୍ରାମାଣିକ ଉତ୍ସ ହେଉଛି
`src/server/authz/routeGuard.ts`ରେ ଥିବା `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`;
ନିମ୍ନର ସାରଣୀ ବର୍ତ୍ତମାନର ସ୍ଥିତିକୁ ପ୍ରତିଫଳିତ କରେ। `check-route-guard-membership` ଗେଟ୍
ପ୍ରୋସେସ୍-ସୃଷ୍ଟି-ସକ୍ଷମ ପ୍ରିଫିକ୍ସଗୁଡ଼ିକ ଅଧୀନରେ ଥିବା ପ୍ରତ୍ୟେକ `route.ts`କୁ ତାଲିକାଭୁକ୍ତ କରେ ଏବଂ କୌଣସିଟି
ଲୋକାଲ୍-ଓନ୍ଲି ଭାବେ ଶ୍ରେଣୀବଦ୍ଧ ହୋଇନଥିଲେ CIକୁ ବିଫଳ କରେ।

#### ଅପରେଟର୍ ମାର୍ଗଦର୍ଶନ ଏବଂ ଅଡିଟିଂ

ଯଦି ଆପଣ OmniRouteକୁ ଏକ ରିଭର୍ସ ପ୍ରକ୍ସି କିମ୍ବା ଟନେଲ୍ (nginx, Caddy, Cloudflare

**ପ୍ରମାଣୀକରଣ ଚାଲିବା ପୂର୍ବରୁ** `403 LOCAL_ONLY` ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରାଯାଏ, ତେଣୁ ଏକ ଲିକ୍ ହୋଇଥିବା JWT
କୌଣସି ସ୍ପନ୍କୁ ପହଞ୍ଚିପାରିବ ନାହିଁ। ଅପରେଟର୍ଙ୍କ ଦୁଇଟି ଦାୟିତ୍ୱ ରହିଛି:

- **କ୍ଲାଏଣ୍ଟ IPକୁ loopback ଭାବେ ଜାଲିଆତି କରି 403କୁ "ଠିକ୍" କରନ୍ତୁ ନାହିଁ।** `X-Forwarded-For: 127.0.0.1` ସେଟ୍ କରିବା, କିମ୍ବା ଉତ୍ସ ଠିକଣାକୁ loopback ଭାବେ ପୁନଃଲିଖନ କରୁଥିବା proxy ବ୍ୟବହାର କରିବା, ଏହି ସ୍ତର ବନ୍ଦ କରୁଥିବା ଠିକ୍ ସେହି RCE ଶ୍ରେଣୀକୁ ପୁନଃ ଖୋଲିଦିଏ। proxy ମାଧ୍ୟମରେ dashboard/APIକୁ ପ୍ରକାଶ କରନ୍ତୁ — spawn-ସକ୍ଷମ routeଗୁଡ଼ିକୁ କେବେ ନୁହେଁ।
- **manage-scope bypassକୁ ସର୍ବନିମ୍ନ ରଖନ୍ତୁ।** କେବଳ `/api/mcp/`କୁ bypass କରାଯାଇପାରିବ, ଏବଂ ତାହା ମଧ୍ୟ କେବଳ `manage`-scope ଥିବା API key ସହିତ। `SPAWN_CAPABLE_PREFIXES`କୁ କେବେ ମଧ୍ୟ bypass ତାଲିକାରେ ଯୋଡ଼ାଯାଇପାରିବ ନାହିଁ — zod schema ସେଗୁଡ଼ିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ ଏବଂ runtimeରେ `isLocalOnlyBypassableByManageScope` ସେଗୁଡ଼ିକୁ ଅନୁମତି ଦିଏ ନାହିଁ (defence-in-depth), dashboardରେ "cannot be made bypassable" କହିବାର ଅର୍ଥ ଏହାହିଁ। ସେହି deny-listରେ କିଛି LOCAL_ONLY route ମଧ୍ୟ ରହିଛି, ଯେଉଁଗୁଡ଼ିକ spawn କରନ୍ତି ନାହିଁ କିନ୍ତୁ କେବେ ମଧ୍ୟ ଦୂରରୁ ପହଞ୍ଚଯୋଗ୍ୟ ହେବା ଉଚିତ୍ ନୁହେଁ — `/api/oauth/kiro/auto-import` (host-local Kiro credential fileଗୁଡ଼ିକ ପଢ଼େ), `/api/discovery/` ଏବଂ `/api/issue-agent/`। runtime snapshot loader ମଧ୍ୟ ସଂରକ୍ଷିତ settings rowରୁ ଏପରି entryଗୁଡ଼ିକୁ ବାଦ ଦିଏ, ଏବଂ legacy JSON import (`/api/settings/import-json`) କେବେ ମଧ୍ୟ bypass keyଗୁଡ଼ିକୁ ଲେଖେ ନାହିଁ। ପ୍ରତ୍ୟେକ `LOCAL_ONLY_API_PREFIXES` entry ନିଶ୍ଚିତ ଭାବେ deny-listରେ ଥିବା ଉଚିତ୍ କିମ୍ବା bypass-ଯୋଗ୍ୟ ଭାବେ ସମୀକ୍ଷିତ ହେବା ଉଚିତ୍ (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`)। `/api/providers/` ଅଧୀନରେ ଥିବା dynamic-segment ଏବଂ static-path spawn-ସକ୍ଷମ routeଗୁଡ଼ିକ (ଯଥା `/login`, `/refresh-cursor`) flat `SPAWN_CAPABLE_PREFIXES` array ଦ୍ୱାରା ନୁହେଁ, ବରଂ `src/shared/constants/spawnCapablePrefixes.ts`ର regex-ଆଧାରିତ `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` ସହାୟକ ଦ୍ୱାରା ଆବୃତ — ସେଗୁଡ଼ିକୁ ଧରିବା ପାଇଁ flat arrayକୁ ସମ୍ପୂର୍ଣ୍ଣ `/api/providers/` prefix ଆବୃତ କରିବାକୁ ପଡ଼ିବ, ଯାହା provider CRUD ପାଇଁ remote dashboardଗୁଡ଼ିକ ବୈଧ ଭାବେ ବ୍ୟବହାର କରୁଥିବା route treeକୁ ଅତ୍ୟଧିକ ବ୍ୟାପକ କରିଦେବ।

**ପ୍ରବେଶ ଅଡିଟ୍ କରିବା** — host ବାହାରୁ କିଛି ମଧ୍ୟ ଏହି routeଗୁଡ଼ିକରେ ପହଞ୍ଚୁ ନଥିବା ଯାଞ୍ଚ କରିବା ପାଇଁ:

- `/dashboard/settings/security`ରେ **Authorization Inventory** ଖୋଲନ୍ତୁ: ଏହା ସକ୍ରିୟ LOCAL_ONLY prefix ତାଲିକା, କେଉଁ prefixଗୁଡ଼ିକ bypass-ଯୋଗ୍ୟ, ଏବଂ compile-time spawn-ସକ୍ଷମ ("cannot be made bypassable") ସେଟ୍ ପ୍ରଦର୍ଶନ କରେ।
- ଉପରୋକ୍ତ prefixଗୁଡ଼ିକ ସହିତ ଯୋଡ଼ି ରହିଥିବା non-loopback client address ପାଇଁ ଆପଣଙ୍କ reverse-proxy / access logଗୁଡ଼ିକୁ grep କରନ୍ତୁ। ଏପରି କୌଣସି hit ଯଦି `403 LOCAL_ONLY` ପରିବର୍ତ୍ତେ `200` ଫେରାଇଥାଏ, ତେବେ proxy ପ୍ରକୃତ client IPକୁ ଲୁଚାଉଛି — proxyକୁ ଠିକ୍ କରନ୍ତୁ।
- ଏହି pathଗୁଡ଼ିକ ମଧ୍ୟରୁ ଗୋଟିଏ ପାଇଁ OmniRouteର logରେ ଥିବା `403 LOCAL_ONLY` ହେଉଛି guard ଉଦ୍ଦିଷ୍ଟ ଭାବେ କାମ କରୁଥିବାର ସଙ୍କେତ, ଦମନ କରିବାକୁ ଥିବା କୌଣସି ତ୍ରୁଟି ନୁହେଁ।

### ସ୍ତର 2 — ALWAYS_PROTECTED

**ଏହା ଦ୍ୱାରା ବାଧ୍ୟତାମୂଳକ:** `isAlwaysProtectedPath(path)` → `requireLogin=false` bypassକୁ ଏଡ଼ାଇବା  
**Bypass:** `requireLogin=false` ଥିବାବେଳେ କିଛି ନାହିଁ; JWT ସର୍ବଦା ଆବଶ୍ୟକ

ଏହି routeଗୁଡ଼ିକ ବିନାଶକାରୀ କିମ୍ବା ଅପରିବର୍ତ୍ତନୀୟ। ଏକ "no-password" installationରେ ସେଗୁଡ଼ିକୁ ଅନୁମତି ଦେବାର ଅର୍ଥ, ସମାନ LANରେ ଥିବା ଯେକେହି databaseକୁ ସମ୍ପୂର୍ଣ୍ଣ ମିଟାଇପାରିବ କିମ୍ବା server processକୁ ବନ୍ଦ କରିପାରିବ।

| Path                                      | କାରଣ                                                                  |
| ----------------------------------------- | --------------------------------------------------------------------- |
| `/api/shutdown`                           | server processକୁ ସମାପ୍ତ କରେ                                           |
| `/api/settings/database`                  | Database export, import ଏବଂ ସମ୍ପୂର୍ଣ୍ଣ ମିଟାଇବା                        |
| `/api/db-backups`                         | ସମ୍ପୂର୍ଣ୍ଣ database backup archive ପ୍ରବେଶ                             |
| `/api/settings/export-json`               | ସମ୍ପୂର୍ଣ୍ଣ settings blob export କରେ (secret ସମେତ)                     |
| `/api/settings/import-json`               | ସମ୍ପୂର୍ଣ୍ଣ settings blobକୁ ବଦଳାଏ                                      |
| `/api/providers/health-autopilot/actions` | autopilot ପ୍ରତିକାର କାର୍ଯ୍ୟଗୁଡ଼ିକ ଚଲାଏ                                 |

**ଉଲ୍ଲଂଘନରେ ପ୍ରତିକ୍ରିୟା:** `401 Authentication required`

`/api/settings/obsidian` ଏହାର `/webdav` childକୁ ଆବୃତ କରେ: `POST`, WebDAV file serviceକୁ — ଯାହା ଏହି pipeline ବାହାରେ Next.js ପୂର୍ବରୁ custom Node layer ଦ୍ୱାରା ପରିବେଷଣ କରାଯାଏ — caller ଚୟନ କରିଥିବା rootକୁ ନିର୍ଦ୍ଦେଶ କରେ ଏବଂ ସଦ୍ୟ ସୃଷ୍ଟି ହୋଇଥିବା Basic credentialଗୁଡ଼ିକୁ ପୁନଃ ପ୍ରଦାନ କରେ, `DELETE` ସେଗୁଡ଼ିକୁ ପରିବର୍ତ୍ତନ କରେ, ଏବଂ parent `POST` Obsidian REST API tokenକୁ ସଂରକ୍ଷଣ କରେ। GHSA-62vw କେବଳ `GET` password ପ୍ରକାଶକୁ ଲୁଚାଇଥିଲା; credential ଜାରି କରିବା ତଥାପି fail-open ସ୍ତରରେ ଥିଲା (GHSA-7pq4-8pvv-rx7r)। `enableObsidianVaultSync()` ଅତିରିକ୍ତ ଭାବେ ଏପରି vaultକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ, ଯାହା data directory ନିଜେ, ତାହାର ଭିତରେ ଅଛି, କିମ୍ବା ତାହାକୁ ଧାରଣ କରେ।

#### Credential exportଗୁଡ଼ିକ କେବଳ operator ପାଇଁ

ଉପରୋକ୍ତ ସ୍ତର କେବଳ _କୌଣସି ଏକ_ credential ଆବଶ୍ୟକ କି ନାହିଁ ତାହା ନିର୍ଦ୍ଧାରଣ କରେ। ସଂରକ୍ଷିତ credential download କରୁଥିବା routeଗୁଡ଼ିକ handlerରେ ଦ୍ୱିତୀୟ ଯାଞ୍ଚ ଯୋଡ଼ନ୍ତି: `GET /api/settings/export-json` (decrypt କରାଯାଇଥିବା provider connection ଏବଂ raw API key), `GET /api/db-backups/export` (SQLite file) ଏବଂ `GET /api/db-backups/exportAll` (ସମ୍ପୂର୍ଣ୍ଣ archive) `requireOperatorCredential()`କୁ call କରନ୍ତି (`src/lib/api/operatorCredential.ts`)। ଏହା dashboard session, local CLI subject, କିମ୍ବା login ଅକ୍ଷମ ଥିବା instanceକୁ ଗ୍ରହଣ କରେ, ଏବଂ ଯେକୌଣସି scopeର API key (`manage` ଏବଂ `admin` ସମେତ) ଓ `oma_` access tokenଗୁଡ଼ିକୁ `403` ଉତ୍ତର ଦିଏ। Sync token ଜାରିକରଣ (`POST /api/sync/tokens`) ସେହି helper ସହିତ trusted loopback internal-service tokenକୁ ମଧ୍ୟ ବ୍ୟବହାର କରେ।

### ନୂତନ installation bootstrap କେବଳ loopback ପାଇଁ — ପ୍ରକୃତ peer ଆଧାରରେ, `Host` ଆଧାରରେ ନୁହେଁ

କୌଣସି management password configure ହୋଇ ନଥିଲେ (ଏବଂ `INITIAL_PASSWORD` ମଧ୍ୟ ନଥିଲେ), `src/shared/utils/apiAuth.ts`ର `isAuthRequired()` anonymous bootstrapକୁ **କେବଳ loopback peer ପାଇଁ** ଖୋଲା ରଖେ। ବିଶ୍ୱସ୍ତ peer signalଗୁଡ଼ିକ ଆଧାରରେ ନିମ୍ନଲିଖିତ କ୍ରମରେ loopback ନିର୍ଦ୍ଧାରଣ କରାଯାଏ: token-stamped ପ୍ରକୃତ TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, policy ଯାହା ଦେଖେ), pipelineର ନିଜସ୍ୱ `AUTHZ_HEADER_PEER_LOCALITY` verdict (route handlerଗୁଡ଼ିକ ଯାହା ଦେଖନ୍ତି, କେବଳ `OMNIROUTE_PEER_STAMP_TOKEN` ସେଟ୍ ଥିବାବେଳେ ବିଶ୍ୱସ୍ତ), କିମ୍ବା direct caller ପାଇଁ ପ୍ରକୃତ socket peer। `Host` / `nextUrl.hostname`କୁ କେବେ ମଧ୍ୟ ବିଚାର କରାଯାଏ ନାହିଁ, ଏବଂ ପ୍ରଥମ password ଲେଖନ (`POST /api/settings/require-login`) ପ୍ରତ୍ୟେକ network peer ପାଇଁ ଖୋଲା ରହିବା ପରିବର୍ତ୍ତେ ସେହି ସମାନ ସୀମାବଦ୍ଧତା ଅଧୀନରେ ରହେ (GHSA-7pq4-8pvv-rx7r)। `managementPolicy` ଏହାର ନିଜସ୍ୱ `peerContext` verdictକୁ ସ୍ପଷ୍ଟ ଭାବେ ତଳକୁ ପଠାଏ, ତେଣୁ ORIGINAL (pre-strip) requestର headerଗୁଡ଼ିକ ଏହାକୁ କେବେ ମଧ୍ୟ ନିର୍ଦ୍ଧାରଣ କରନ୍ତି ନାହିଁ।

### ସ୍ତର 3 — MANAGEMENT (ଡିଫଲ୍ଟ)

ଅନ୍ୟ ସମସ୍ତ ପରିଚାଳନା ରୁଟ୍। `requireLogin=false` ବିନ୍ୟାସ କରାଯାଇ ନଥିଲେ
ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ। CLI ଟୋକେନ୍ଗୁଡ଼ିକ ଏହି ରୁଟ୍ଗୁଡ଼ିକୁ ପ୍ରମାଣୀକୃତ କରିପାରିବେ (ଲୁପ୍ବ୍ୟାକ୍ + ବୈଧ HMAC)।

## ମୂଲ୍ୟାଙ୍କନ କ୍ରମ

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → ପରବର୍ତ୍ତୀ ପଦକ୍ଷେପକୁ ଯାଆନ୍ତୁ
     → non-loopback, manage-scope Bearer
        AND isLocalOnlyBypassableByManageScope   → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → ଅନ୍ୟଥା                                    → 403 LOCAL_ONLY ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  2. isInternalModelSyncRequest(ctx)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (system)
  3. hasValidCliToken(headers)?
     → ଅନୁମତି ଦିଅନ୍ତୁ (cli) [loopback + timingSafeEqual HMAC ଯାଞ୍ଚ]
  4. isAlwaysProtectedPath(path) or requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ଅନୁମତି ଦିଅନ୍ତୁ (dashboard_session)
     → bypass କରିହେଉ ନଥିବା ପଥରେ manage-scope Bearer?
        → ଅନୁମତି ଦିଅନ୍ତୁ (management_key)
     → 401/403 ସହିତ ପ୍ରତ୍ୟାଖ୍ୟାନ କରନ୍ତୁ
  5. requireLogin=false?
     → ଅନୁମତି ଦିଅନ୍ତୁ (anonymous)
```

ପଦକ୍ଷେପ 1ର manage-scope ଶାଖା ହେଉଛି ଏକମାତ୍ର ପ୍ରମାଣୀକୃତ ପଥ ଯାହା ଏକ
LOCAL_ONLY ରୁଟ୍କୁ ସନ୍ତୁଷ୍ଟ କରିପାରେ; auth-backend ବିଫଳତା ମୋଡ୍ 503 ଫେରାଏ
(403 ନୁହେଁ), ଯାହାଫଳରେ ଏକ ମିଆଦ ଶେଷ ହୋଇଥିବା DB ନିରବରେ "deny"କୁ
ଡାଉନ୍ଗ୍ରେଡ୍ ହୁଏ ନାହିଁ।

## ଏକ ନୂତନ spawn-ସକ୍ଷମ ରୁଟ୍ ଯୋଡ଼ିବା

1. ପଥ ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_API_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
2. `tests/unit/authz/routeGuard.test.ts`ରେ ଏକ ପରୀକ୍ଷା ଯୋଡ଼ନ୍ତୁ, ଯାହା ନୂତନ
   ପ୍ରିଫିକ୍ସ ପାଇଁ `isLocalOnlyPath()` true ଫେରାଉଥିବା ନିଶ୍ଚିତ କରେ
3. **ଏହି ପଦକ୍ଷେପକୁ କେବେବି ଏଡ଼ାନ୍ତୁ ନାହିଁ** — `CLAUDE.md`ର କଠୋର ନିୟମ #15 ଦେଖନ୍ତୁ
4. ନିଷ୍ପତ୍ତି ନିଅନ୍ତୁ: ଏହି ରୁଟ୍ଟି କ’ଣ `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ
   ମଧ୍ୟ ରହିବା ଉଚିତ? ଡିଫଲ୍ଟ ଉତ୍ତର ହେଉଛି **ନା**। କେବଳ ସେତେବେଳେ opt-in କରନ୍ତୁ,
   ଯେତେବେଳେ ରୁଟ୍ଟିକୁ ଏକ manage-scope ଧାରକଙ୍କ ପାଇଁ ଉନ୍ମୁକ୍ତ କରିବା ସୁରକ୍ଷିତ
   (ଅର୍ଥାତ୍, ଏହା ଇଚ୍ଛାମତେ ବ୍ୟବହାରକାରୀ-ନିୟନ୍ତ୍ରିତ କୋଡ୍ spawn କରେ **ନାହିଁ**)।

## ଏକ manage-scope-bypassable ପଥ ଯୋଡ଼ିବା

1. ରୁଟ୍ଟି ବ୍ୟବହାରକାରୀ-ପ୍ରଦତ୍ତ କୋଡ୍ କିମ୍ବା କମାଣ୍ଡ ଚାଲୁ କରେ ନାହିଁ ବୋଲି
   ନିଶ୍ଚିତ କରନ୍ତୁ। ଯଦି କରେ, ଅଟକି ଯାଆନ୍ତୁ — ଏହି ବ୍ୟତିକ୍ରମ ଏଥିପାଇଁ ଉପଯୁକ୍ତ
   ଉପକରଣ ନୁହେଁ।
2. ପ୍ରିଫିକ୍ସକୁ `src/server/authz/routeGuard.ts`ର
   `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES`ରେ ଯୋଡ଼ନ୍ତୁ
3. ସମସ୍ତ ଚାରିଟି ଅନୁରୋଧ ରୂପ ପାଇଁ `tests/unit/authz/management-policy.test.ts`ରେ
   କଭରେଜ୍ ଯୋଡ଼ନ୍ତୁ: Bearer ନାହିଁ (403), manage Bearer (ଅନୁମତି), non-manage Bearer
   (403), ଏବଂ manage Bearer ଥିଲେ ମଧ୍ୟ `/api/cli-tools/runtime/*`
   strict-loopback ରହୁଥିବା ପ୍ରତି-ପ୍ରିଫିକ୍ସ ରିଗ୍ରେସନ୍।

## OpenAPIରେ ସୁରକ୍ଷା ଟିଅର୍ଗୁଡ଼ିକୁ ଡକ୍ୟୁମେଣ୍ଟ କରିବା

`docs/openapi.yaml`ରେ ଏକ ନୂତନ ରୁଟ୍ ଯୋଡ଼ିବାବେଳେ, ଯଦି ରୁଟ୍ଟି
`routeGuard.ts` ଦ୍ୱାରା ବର୍ଗୀକୃତ ହୋଇଛି, ତେବେ ସମ୍ପର୍କିତ vendor extension
ପ୍ରୟୋଗ କରନ୍ତୁ:

| routeGuard.ts ବର୍ଗୀକରଣ             | YAML ଆନୋଟେସନ୍                 | ପ୍ରବର୍ତ୍ତନ                                       |
| ---------------------------------- | ----------------------------- | ------------------------------------------------ |
| `LOCAL_ONLY_API_PREFIXES`          | `x-loopback-only: true`       | non-loopbackରୁ ନିଃସର୍ତ୍ତ ଭାବେ ଅବରୋଧିତ            |
| `ALWAYS_PROTECTED_API_PATHS`       | `x-always-protected: true`    | `requireLogin=false` ଥିଲେ ମଧ୍ୟ ପ୍ରମାଣୀକରଣ ଆବଶ୍ୟକ |
| ଆଭ୍ୟନ୍ତରୀଣ admin/debug ରୁଟ୍        | `x-internal: true`            | ଡିଫଲ୍ଟ ଭାବେ /dashboard/api-endpointsରୁ ଲୁକ୍କାୟିତ |
| କିଛି ନୁହେଁ (ସାର୍ବଜନୀନ / ମାନକ auth) | (କୌଣସି ଆନୋଟେସନ୍ ଆବଶ୍ୟକ ନାହିଁ) | ମାନକ `requireLogin`-ନିୟନ୍ତ୍ରିତ ପ୍ରବେଶ            |

### ବୈଧତା ଯାଞ୍ଚ

ଦୁଇଟି ସ୍କ୍ରିପ୍ଟ YAML ଆନୋଟେସନ୍ ଏବଂ `routeGuard.ts` ମଧ୍ୟରେ ସମନ୍ୱୟକୁ
ବାଧ୍ୟତାମୂଳକ କରେ:

- `scripts/check/check-openapi-coverage.mjs` — କଭରେଜ୍ < 99% ହେଲେ ବିଫଳ ହୁଏ
- `scripts/check/check-openapi-security-tiers.mjs` — `x-loopback-only` କିମ୍ବା
  `x-always-protected` ଆନୋଟେସନ୍ଗୁଡ଼ିକ compile-time କନ୍ଷ୍ଟାଣ୍ଟଠାରୁ ଭିନ୍ନ ହେଲେ ବିଫଳ ହୁଏ

ଉଭୟ ସ୍କ୍ରିପ୍ଟ pre-commit hook ଏବଂ CIରେ ଚାଲେ।

### ଭୁଲ୍ ସକାରାତ୍ମକ ନିୟମ

ଯଦି `routeGuard.ts` କନ୍ଷ୍ଟାଣ୍ଟରେ ନଥିବା ଏକ ରୁଟ୍ରେ `x-always-protected`
କିମ୍ବା `x-loopback-only` ଆନୋଟେଟ୍ କରାଯାଏ, ତେବେ କଭରେଜ୍ ସ୍କ୍ରିପ୍ଟ ବିଫଳ ହୁଏ।
ସମାଧାନ ହେଉଛି ସର୍ବଦା YAMLକୁ `routeGuard.ts` ପ୍ରକୃତରେ ଯାହା ପ୍ରବର୍ତ୍ତନ କରେ
ତାହା ସହିତ ସମନ୍ୱିତ କରିବା — ପ୍ରବର୍ତ୍ତନ ଲଜିକ୍ ମଧ୍ୟ କାର୍ଯ୍ୟକାରୀ ନକରି କେବଳ
`routeGuard.ts`ରେ ରୁଟ୍ ଯୋଡ଼ିବା ନୁହେଁ।
