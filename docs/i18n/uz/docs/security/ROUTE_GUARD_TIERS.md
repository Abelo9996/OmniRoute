## Umumiy ko‘rinish

Barcha OmniRoute boshqaruv API marshrutlari uchta himoya darajasidan biriga tasniflanadi. Tasnif statik bo‘lib, `src/server/authz/routeGuard.ts` faylida belgilangan va boshqa autentifikatsiya tarmoqlaridan oldin tekshiriladi.

## Darajalar

### 1-daraja — LOCAL_ONLY

**Majburiy tekshiruv:** `isLocalOnlyPath(path)` → loopback xost tekshiruvi  
**Chetlab oʻtish:** Odatiy holatda mavjud emas. Soʻrov `manage` doirasiga ega yaroqli API kalitini oʻz ichiga olganida, `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` ichidagi yoʻllar uchun tor doiradagi istisno mavjud ([Manage doirasidagi istisno](#manage-scope-carve-out) boʻlimiga qarang).

Bu marshrutlar ichki jarayonlarni ishga tushiradi yoki bajarilish vaqtidagi kodni bajaradi. Ularni loopback boʻlmagan trafik uchun ochish yaroqli JWT’ni qoʻlga kiritgan hujumchiga (masalan, Cloudflared/Ngrok tunneli orqali) jarayonlarni ishga tushirish imkonini beradi — bu maʼlum CVE toifasidir ([GHSA-fhh6-4qxv-rpqj](https://github.com/advisories/GHSA-fhh6-4qxv-rpqj)).

**GHSA-fhh6-4qxv-rpqj nima (hujum toifasi):** boshqaruv/agent serveri quyi jarayonni (`npm install`, `node`, brauzer, proksi, `git`, `tar`, …) ishga tushiradigan oxirgi nuqtani ochadi. Agar bu oxirgi nuqtaga xost tashqarisidan kirish mumkin boʻlsa — masalan, operator OmniRoute’ni nginx/Cloudflare/Tailscale tunneli ortiga joylashtirgan va JWT sizib chiqqan yoki autentifikatsiya notoʻgʻri sozlangan boʻlsa — hujumchi «API’ni chaqirish» imkoniyatini «xostda buyruq bajarish»ga (masofadan kod bajarishga) aylantiradi. OmniRoute buni jarayon ishga tushira oladigan har bir marshrutda **har qanday autentifikatsiya tekshiruvidan oldin, hech qanday istisnosiz loopback xost tekshiruvini qoʻllash** orqali bartaraf etadi: tunnel orqali sizib chiqqan token ham jarayonni ishga tushirish nuqtasiga yetib bora olmaydi.

**Toʻliq LOCAL_ONLY toʻplami.** Asosiy manba `src/server/authz/routeGuard.ts` faylidagi `LOCAL_ONLY_API_PREFIXES` / `LOCAL_ONLY_API_PATTERNS`; quyidagi jadval joriy holatni aks ettiradi. `check-route-guard-membership` nazorat bosqichi jarayon ishga tushira oladigan prefikslar ostidagi har bir `route.ts` faylini sanab chiqadi va ulardan birortasi faqat lokal deb tasniflanmagan boʻlsa, CI bajarilishini muvaffaqiyatsiz yakunlaydi.

#### Boshqaruv doirasi uchun istisno

LOCAL_ONLY yoʻllarining bir qismiga loopback boʻlmagan manzildan ham FAQAT
soʻrovda metamaʼlumotlari `manage` doirasini (yoki `admin`) oʻz ichiga olgan
`Authorization: Bearer <api-key>` mavjud boʻlsa kirish MUMKIN. Istisno har bir
yoʻl uchun `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` orqali aniq boshqariladi,
shuning uchun har qanday yangi LOCAL_ONLY yoʻli uchun standart holat qatʼiy
loopback boʻlib qoladi. Autentifikatsiyadan oʻtmagan soʻrovlar va boshqaruv
huquqiga ega boʻlmagan kalitli soʻrovlar hali ham `403 LOCAL_ONLY` bilan rad
etiladi.

Hozirda istisno qoʻllanishi mumkin boʻlgan yagona prefiks `/api/mcp/`.
`/api/cli-tools/runtime/` va `/api/services/` ataylab chiqarib tashlangan,
chunki ular ixtiyoriy quyi jarayonlarni (`npm install`, `node`) ishga tushira
oladi, bu esa LOCAL_ONLY darajasi oldini olish uchun yaratilgan aynan oʻsha
CVE turidir.

**#7895 — `mcp:connect` tor doirasi:** `/api/mcp/` istisnosi, SHUNINGDEK,
tor `mcp:connect` doirasiga ega Bearer kalitini ham qabul qiladi
(`src/shared/constants/managementScopes.ts::MCP_CONNECT_SCOPE`); bu
`src/server/authz/policies/management.ts` faylidagi
`hasMcpConnectOrManageScope()` orqali tekshiriladi. Bu FAQAT `/api/mcp/` bilan
cheklangan — `mcp:connect` boshqa hech qanday boshqaruv yoʻnalishida (jumladan,
kelajakda qoʻshilishi mumkin boʻlgan boshqa barcha LOCAL_ONLY istisno
prefikslarida) hech qanday huquq bermaydi va u ataylab
`MANAGEMENT_API_KEY_SCOPES` tarkibidan chiqarib tashlangan. `manage`/`admin`
huquqiga ega kalit avvalgidek istisnodan oʻtadi; `mcp:connect` keng boshqaruv
huquqiga muhtoj boʻlmagan, faqat MCPʼdan masofadan foydalanuvchi chaqiruvchilar
uchun kamroq imtiyozli muqobildir.

| ----------------------------------------------------------- | -------------------------- | ------------------------------------- |
| Loopback boʻlmagan, Bearer yoʻq                             | `/api/mcp/*`               | 403 LOCAL_ONLY                        |
| Loopback boʻlmagan, `manage` doirasiga ega Bearer           | `/api/mcp/*`               | Ruxsat beriladi                       |
| Loopback boʻlmagan, `mcp:connect` doirasiga ega Bearer      | `/api/mcp/*`               | Ruxsat beriladi                       |
| Loopback boʻlmagan, `manage`/`mcp:connect` huquqisiz Bearer | `/api/mcp/*`               | 403 LOCAL_ONLY                        |
| Loopback boʻlmagan, `mcp:connect` doirasiga ega Bearer      | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                        |
| Loopback boʻlmagan, `manage` doirasiga ega Bearer           | `/api/cli-tools/runtime/*` | 403 LOCAL_ONLY                        |
| Loopback, istalgan/Bearer yoʻq                              | istalgan LOCAL_ONLY        | Ruxsat beriladi (tekshiruvdan oʻtadi) |

#### Operator uchun koʻrsatmalar va audit

Agar OmniRouteʼni teskari proksi yoki tunnel (nginx, Caddy, Cloudflare
Tunnel, Tailscale, Ngrok) ortida ishga tushirsangiz, loopback tekshiruvi
yuqoridagi jarayon ishga tushira oladigan yoʻnalishlarni himoya qilishda davom
etadi — mijoz manzili loopback boʻlmagan soʻrov `403 LOCAL_ONLY` bilan
**autentifikatsiya ishga tushishidan oldin** rad etiladi, shuning uchun sizib
chiqqan JWT jarayonni ishga tushirishgacha yetib bora olmaydi. Operatorning
ikkita majburiyati saqlanib qoladi:

- **403 xatosini mijoz IP manzilini loopback sifatida soxtalashtirish orqali «tuzatmang».**
  `X-Forwarded-For: 127.0.0.1` ni o‘rnatish yoki manba manzilini loopback sifatida
  qayta yozadigan proksi aynan shu daraja yopadigan RCE toifasini qayta ochadi.
  Dashboard/API’ni proksi orqali taqdim eting — jarayon ishga tushira oladigan
  marshrutlarni hech qachon taqdim etmang.
- **`manage` doirasidagi chetlab o‘tishni minimal saqlang.** Faqat `/api/mcp/` ni
  chetlab o‘tish mumkin va bu faqat `manage` doirasidagi API kaliti bilan amalga
  oshiriladi. `SPAWN_CAPABLE_PREFIXES` hech qachon chetlab o‘tish ro‘yxatiga
  qo‘shilmaydi — zod sxemasi ularni rad etadi va
  `isLocalOnlyBypassableByManageScope` ularni bajarilish vaqtida bloklaydi
  (ko‘p qatlamli himoya), dashboard’dagi «chetlab o‘tiladigan qilib bo‘lmaydi»
  degan ibora shuni anglatadi. Xuddi shu taqiqlash ro‘yxatida jarayon ishga
  tushirmaydigan, ammo masofadan hech qachon foydalanib bo‘lmaydigan bir nechta
  LOCAL_ONLY marshrutlar ham bor — `/api/oauth/kiro/auto-import` (xostdagi lokal
  Kiro hisob ma’lumotlari fayllarini o‘qiydi), `/api/discovery/` va
  `/api/issue-agent/`. Bajarilish vaqtidagi snapshot yuklagichi ham bunday
  yozuvlarni saqlangan sozlamalar qatoridan olib tashlaydi, eski JSON importi esa
  (`/api/settings/import-json`) chetlab o‘tish kalitlarini hech qachon yozmaydi.
  Har bir `LOCAL_ONLY_API_PREFIXES` yozuvi taqiqlash ro‘yxatida bo‘lishi yoki
  chetlab o‘tish uchun yaroqli deb tekshirilgan bo‘lishi kerak
  (`tests/unit/authz/local-only-bypass-spawn-denylist.test.ts`). `/api/providers/`
  ostidagi dinamik segmentli va statik yo‘lli, jarayon ishga tushira oladigan
  marshrutlar (masalan, `/login`, `/refresh-cursor`) oddiy
  `SPAWN_CAPABLE_PREFIXES` massivi emas, balki
  `src/shared/constants/spawnCapablePrefixes.ts` ichidagi regex asosidagi
  `SPAWN_CAPABLE_PATTERNS` / `SPAWN_CAPABLE_PATTERN_ANCESTORS` yordamchi
  mexanizmi bilan qamrab olinadi — ularni aniqlash uchun oddiy massiv butun
  `/api/providers/` prefiksini qamrab olishi kerak bo‘lardi, bu esa masofaviy
  dashboard’lar provayder CRUD amallari uchun qonuniy ravishda foydalanadigan
  marshrutlar daraxtini haddan tashqari kengaytirardi.

**Kirishni audit qilish** — xost tashqarisidan hech narsa bu marshrutlarga
kirmayotganini tekshirish uchun:

- `/dashboard/settings/security` sahifasida **Authorization Inventory**’ni oching:
  u amaldagi LOCAL_ONLY prefikslar ro‘yxatini, qaysi prefikslarni chetlab o‘tish
  mumkinligini va kompilyatsiya vaqtida aniqlanadigan, jarayon ishga tushira
  oluvchi («chetlab o‘tiladigan qilib bo‘lmaydi») to‘plamni ko‘rsatadi.
- Teskari proksi / kirish jurnallarida yuqoridagi prefikslarni loopback bo‘lmagan
  mijoz manzili bilan birga qidiring. `403 LOCAL_ONLY` o‘rniga `200` qaytargan
  har qanday bunday so‘rov proksi haqiqiy mijoz IP manzilini yashirayotganini
  anglatadi — proksini tuzating.
- OmniRoute jurnallaridagi shu yo‘llardan biri uchun `403 LOCAL_ONLY` himoya
  kutilganidek ishlayotganini bildiradi, bostirilishi kerak bo‘lgan xatoni emas.

### 2-daraja — ALWAYS_PROTECTED

**Majburan qo‘llovchi:** `isAlwaysProtectedPath(path)` → `requireLogin=false` orqali chetlab o‘tishni bekor qiladi
**Chetlab o‘tish:** `requireLogin=false` bo‘lganda mavjud emas; JWT har doim talab qilinadi

Bu marshrutlar buzuvchi yoki qaytarib bo‘lmaydigan amallarni bajaradi. Ularga
«parolsiz» o‘rnatmada ruxsat berish bir xil LAN’dagi istalgan foydalanuvchi
ma’lumotlar bazasini o‘chirishi yoki server jarayonini to‘xtatishi mumkinligini
anglatadi.

| Yo‘l                                      | Sabab                                                                                 |
| ----------------------------------------- | ------------------------------------------------------------------------------------- |
| `/api/shutdown`                           | Server jarayonini tugatadi                                                            |
| `/api/settings/database`                  | Ma’lumotlar bazasini eksport, import va tozalash                                      |
| `/api/db-backups`                         | Ma’lumotlar bazasining to‘liq zaxira arxiviga kirish                                  |
| `/api/settings/export-json`               | Sozlamalarning to‘liq to‘plamini eksport qiladi (jumladan, sirlarni)                  |
| `/api/settings/import-json`               | Sozlamalarning to‘liq to‘plamini almashtiradi                                         |
| `/api/providers/health-autopilot/actions` | Avtopilotning tuzatish amallarini bajaradi                                            |
| `/api/settings/obsidian`                  | Istalgan vault ildizi uchun qayta ishlatiladigan WebDAV hisob ma’lumotlarini yaratadi |

**Buzilish holatidagi javob:** `401 Authentication required`

`/api/settings/obsidian` o‘zining `/webdav` ichki marshrutini ham qamrab oladi:
`POST` Next.js’dan oldin maxsus Node qatlami orqali, ushbu pipeline’dan tashqarida
xizmat ko‘rsatiladigan WebDAV fayl xizmatini chaqiruvchi tanlagan ildizga
yo‘naltiradi va yangi yaratilgan Basic hisob ma’lumotlarini javobda qaytaradi,
`DELETE` ularni almashtiradi, ota-yo‘ldagi `POST` esa Obsidian REST API tokenini
saqlaydi. GHSA-62vw faqat `GET` orqali parol oshkor bo‘lishini yashirgan; hisob
ma’lumotlarini chiqarish esa hanuz fail-open darajasida edi
(GHSA-7pq4-8pvv-rx7r). `enableObsidianVaultSync()` qo‘shimcha ravishda ma’lumotlar
katalogining o‘zi bo‘lgan, uning ichida joylashgan yoki uni o‘z ichiga olgan
vault’ni rad etadi.

#### Hisob ma’lumotlari eksporti faqat operator uchun

Yuqoridagi daraja faqat _qandaydir_ hisob ma’lumoti talab qilinishini belgilaydi.
Saqlangan hisob ma’lumotlarini yuklab olish marshrutlari ishlov beruvchida ikkinchi
tekshiruvni qo‘shadi: `GET /api/settings/export-json` (shifri ochilgan provayder
ulanishlari va xom API kalitlari), `GET /api/db-backups/export` (SQLite fayli) va
`GET /api/db-backups/exportAll` (to‘liq arxiv) `requireOperatorCredential()` ni
chaqiradi (`src/lib/api/operatorCredential.ts`). U dashboard sessiyasini, lokal
CLI subyektini yoki kirish o‘chirilgan instansiyani qabul qiladi hamda istalgan
doiradagi API kalitlariga (jumladan, `manage` va `admin`) va `oma_` kirish
tokenlariga `403` javobini qaytaradi. Sinxronlash tokenlarini chiqarish
(`POST /api/sync/tokens`) xuddi shu yordamchi funksiyadan hamda ishonchli loopback
ichki xizmat tokenidan foydalanadi.

### Yangi o‘rnatmadagi boshlang‘ich sozlash faqat loopback uchun — `Host` bo‘yicha emas, haqiqiy peer bo‘yicha

Hech qanday boshqaruv paroli sozlanmagan (va `INITIAL_PASSWORD` mavjud bo‘lmagan)
holatda `src/shared/utils/apiAuth.ts` ichidagi `isAuthRequired()` anonim
boshlang‘ich sozlashni **faqat loopback peer’lar uchun** ochiq saqlaydi. Loopback
quyidagi tartibda ishonchli peer signallaridan aniqlanadi: token bilan belgilangan
haqiqiy TCP peer (`PEER_IP_HEADER` + `VIA_PROXY_HEADER`, siyosat ko‘radigan
qiymat), pipeline’ning o‘z `AUTHZ_HEADER_PEER_LOCALITY` hukmi (marshrut ishlov
beruvchilari ko‘radigan qiymat, faqat `OMNIROUTE_PEER_STAMP_TOKEN` o‘rnatilganida
ishonchli) yoki bevosita chaqiruvchilar uchun haqiqiy socket peer. `Host` /
`nextUrl.hostname` hech qachon tekshirilmaydi va birinchi parolni yozish
(`POST /api/settings/require-login`) har bir tarmoq peer’i uchun ochiq bo‘lish
o‘rniga xuddi shu cheklovga bo‘ysunadi (GHSA-7pq4-8pvv-rx7r).
`managementPolicy` o‘zining `peerContext` hukmini bevosita quyi qatlamga uzatadi,
shuning uchun ORIGINAL (olib tashlashdan oldingi) so‘rov sarlavhalari hech qachon
bu qarorni belgilamaydi.

### 3-daraja — MANAGEMENT (standart)

Boshqa barcha boshqaruv marshrutlari. `requireLogin=false` qilib
sozlanmagan bo‘lsa, autentifikatsiya talab qilinadi. CLI tokenlari ushbu marshrutlarda autentifikatsiyadan o‘tishi mumkin (loopback + haqiqiy HMAC).

## Baholash tartibi

```
managementPolicy.evaluate(ctx)
  1. isLocalOnlyPath(path)?
     → loopback                                  → keyingi bosqichga oʻtish
     → loopback emas, manage-scope doirasidagi Bearer
        VA isLocalOnlyBypassableByManageScope    → ruxsat berish (management_key)
     → aks holda                                 → rad etish 403 LOCAL_ONLY
  2. isInternalModelSyncRequest(ctx)?
     → ruxsat berish (system)
  3. hasValidCliToken(headers)?
     → ruxsat berish (cli) [loopback + timingSafeEqual HMAC tekshiruvi]
  4. isAlwaysProtectedPath(path) yoki requireLogin=true?
     → isDashboardSessionAuthenticated?
        → ruxsat berish (dashboard_session)
     → chetlab oʻtib boʻlmaydigan yoʻldagi manage-scope doirasidagi Bearer?
        → ruxsat berish (management_key)
     → rad etish 401/403
  5. requireLogin=false?
     → ruxsat berish (anonymous)
```

1-bosqichdagi manage-scope tarmogʻi LOCAL_ONLY marshrutini qanoatlantira oladigan yagona autentifikatsiyalangan yoʻldir; autentifikatsiya bekendi nosozligi holatida 503 qaytariladi (403 emas), shuning uchun amal qilish muddati tugagan DB sezdirmasdan «rad etish» holatiga tushib qolmaydi.

## Yangi spawn imkoniyatiga ega marshrut qoʻshish

1. Yoʻl prefiksini `src/server/authz/routeGuard.ts` faylidagi `LOCAL_ONLY_API_PREFIXES` roʻyxatiga qoʻshing
2. `tests/unit/authz/routeGuard.test.ts` fayliga yangi prefiks uchun `isLocalOnlyPath()` true qaytarishini tasdiqlovchi test qoʻshing
3. **Bu bosqichni hech qachon oʻtkazib yubormang** — `CLAUDE.md` faylidagi 15-qatʼiy qoidaga qarang
4. Qaror qiling: bu marshrut `LOCAL_ONLY_MANAGE_SCOPE_BYPASS_PREFIXES` roʻyxatiga HAM kirishi kerakmi?
   Standart javob — **yoʻq**. Faqat marshrutni manage-scope egasiga ochish xavfsiz boʻlgandagina (yaʼni foydalanuvchi boshqaradigan ixtiyoriy kodni ishga tushirmasa) uni ixtiyoriy ravishda kiriting.
